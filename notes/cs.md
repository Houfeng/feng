# C# 中的处理方案

## 情景

C# 中，A 和 B 同命名空间，C 是另外一个命名空间， A 中定义了 Class1， C 中也定义了 Class1。

第 1 种情况： 在 A 中 using C，此时会怎样？
第 2 种情况，在 A 中不 using C，但在 B 中 using C 但未使用 Class1，此时会怎样？
第 3 种情况，在 A 中不 using C，但在 B 中 using C ，并使用 Class1，此时会怎样？

## 解决方案

这三种情况完美覆盖了 C# 符号决议在“多文件、同命名空间、外部导入”联动时的所有边界。

为了更清晰地说明，我们假设 **A 和 B 属于 `NS_Local` 命名空间**，而 **C 是另一个命名空间 `NS_External**`。它们都各自包含一个 `Class1`。

以下是这三种情况的底层编译行为：

---

### 第 1 种情况：在 A 中 `using C;`，此时会怎样？

**结论**：在 A 文件中**不直接报错**，但只要 A 文件内部尝试直接写出裸名 `Class1`，就会立刻触发**编译期二义性错误（CS0104）**。

#### 编译行为拆解：

* **符号表状态**：在 A 文件的物理视口内，编译器同时看到了 `NS_Local.Class1`（由于 A 自身就在 `NS_Local` 里）和 `NS_External.Class1`（由于显式 `using C;`）。
* **行为**：
* 如果 A 文件里只是写着 `using C;`，但**没有在任何代码里用到 `Class1**`，编译器会保持沉默，**完美编译**（最多只有一行“using 指令是不必要的”警告）。
* 一旦 A 文件内写了 `Class1 myObj;`，编译器由于无法在平级的两个来源中做选择，立刻报错：`'Class1' is an ambiguous reference`。



---

### 第 2 种情况：A 中不 `using C`，但 B 中 `using C` 且“未使用” `Class1`，此时会怎样？

**结论**：**全项目完美编译，没有任何冲突和错误。**

#### 编译行为拆解：

* **A 文件的视角**：A 文件非常纯粹，它不知道 C 的存在。在 A 文件里写 `Class1`，编译器会毫无悬念地直接决议为本地的 `NS_Local.Class1`。
* **B 文件的视角**：B 文件虽然写了 `using C;`，导致 B 文件的符号表里同时存在了两个 `Class1`。但是，由于 B 文件内部**根本没有写 `Class1` 这个单词**，二义性碰撞只停留在符号表的潜在可能中，并没有被代码触发。
* **隔离效果**：B 文件中的 `using C;` 被死死锁在 B 文件内部，绝对不会渗透给 A 文件。因此整个编译链条一路绿灯。

---

### 第 3 种情况：A 中不 `using C`，但 B 中 `using C` 并且“使用”了 `Class1`，此时会怎样？

**结论**：**A 文件完美编译；但 B 文件在编译时会立刻报二义性冲突错误（CS0104）。**

#### 编译行为拆解：

* **A 文件**：依然安全。因为 A 文件没有任何外部导入干扰，它代码里的 `Class1` 会稳定绑定到 A 自身定义的那个类上。
* **B 文件**：直接崩溃。当编译器扫描到 B 文件里的 `Class1` 时，遇到了前面提到的平级碰撞：
1. 它是同一个命名空间 `NS_Local` 的成员（由 A 定义，对 B 隐式可见）。
2. 它是显式导入 `using C;` 的成员（由 C 定义，对 B 显式可见）。
由于两者的解析权重完全一致，编译器拒绝猜测，报错熔断：


> `error CS0104: 'Class1' is an ambiguous reference between 'NS_Local.Class1' and 'NS_External.Class1'`



---

### 总结给 `feng` 的决议机制

这三种情况为 `feng` 的编译器前端（Name Resolver）提供了一套极其标准的天平测试用例（Test Cases）：

1. **惰性碰撞（Lazy Collision）**：名字空间冲突不应该在 `import/using` 发生时立即报错（除非是别名直接撞本地定义），而应该在**代码真正引用该符号（Identifier Resolution）时**才去检查是否存在二义性。
2. **零副作用隔离**：B 文件的符号表无论膨胀成什么样，只要 A 文件没写 `import`，A 文件的语义空间就必须是一片净土。
