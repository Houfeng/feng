# Feng 语言泛型规范

> **状态**: 草案。
> 本文档当前只收敛已经确认的泛型语法与编译期约束：泛型声明入口、表达式位置显式类型实参的 `<...>` 语法，以及“泛型 `type` 内的方法泛型参数不得与外层类型泛型参数重名”的规则。
> 由于 Feng 支持 `.fb` 二进制分发，泛型实现不能把“consumer 总能拿到 provider 源码并对所有实例做全量单态化发码”作为前提。
> 当前实现方向以非单态泛型为主；单态化发码仅作为编译器后续可选优化项，不作为首发或通用前提。
> 类型参数约束的基础语法、调用点泛型推导与无约束最小语义已在本文定义；当前阶段不支持协变/逆变，也不提供基于 variance 的语言级转换；非单态 lowering 的最终承载形态以及与 C ABI 的交叉规则暂不在本文定义。

## 1 职责

- 为 Feng 增加类型参数机制，允许在 `type`、`func`、`spec` 和成员方法上声明泛型参数。
- 在不让 Parser 反向依赖 Semantic 的前提下，为显式泛型调用提供无歧义语法。
- 在调用点省略显式类型实参时，允许编译器按既定规则完成泛型推导。
- 收敛已经确认的命名约束：泛型 `type` 内的方法泛型参数不得与所在类型的泛型参数重名。

## 2 术语

- 类型泛型参数：声明在 `type Name<T>` 或 `spec Name<T>` 上的类型参数。
- 函数泛型参数：声明在顶层 `func Name<T>` 上的类型参数。
- 方法泛型参数：声明在 `type` 成员方法 `func Name<T>` 上的类型参数。
- 泛型参数数量：某个泛型声明头中类型参数列表的长度，例如 `foo<T, U>` 的泛型参数数量是 `2`。
- 约束泛型参数：在类型参数名后写出泛型约束的泛型参数，例如 `T: Named`。
- 无约束泛型参数：未声明泛型约束的泛型参数，例如 `T`。
- 泛型推导：调用点未显式写出类型实参时，编译器依据实参类型、接收者静态类型与上下文目标类型推导类型参数的过程。
- 显式泛型 target：在表达式位置直接在调用目标、类型构造目标或数组创建目标后写出 `<...>` 的语法片段，例如 `callee<T>`、`Map<string, int>`。
- 显式泛型调用：在表达式位置显式写出类型实参的函数调用、方法调用或类型构造器调用，统一使用 `callee<...>(...)` 语法。
- 类型构造器调用：在表达式位置直接以泛型类型名作为调用目标的表达式，如 `Map<string, int>()`；当需要显式写出类型实参时，与函数泛型调用相同，使用普通 `<...>` 语法。
- 非调用位置：除函数、方法或类型构造器调用点外的其他所有位置，包括声明头、类型引用、字段类型、参数类型、返回类型和类型实参内部。
- 类型位置：变量类型标注、字段类型、参数类型、返回类型等只允许出现类型的语法位置；此处使用普通 `<...>` 语法，不使用 `:<...>`。

## 3 语法

正确语法一，泛型声明：

```feng
type List<T> { ... }

func map<T, U>(left: T, right: U): T { ... }

spec Comparable<T> {
  func compare(other: T): int;
}

spec Mapper<T, U>(value: T): U;
```

正确语法二，泛型类型中的泛型方法：

```feng
type Box<T> {
  func get(): T { ... }

  func map<U>(value: U): T { ... }
}
```

正确语法三，带约束与不带约束的类型参数：

```feng
spec Named {
  let name: string;
}

spec Process(x: int): void;

spec Value: int | string;

type Box<T: Named> {
  func get_name(value: T): string {
    return value.name;
  }
}

type Runner<F: Process> {
  func run(handler: F) {
    handler(1);
  }
}

type Cell<V: Value> {
  let value: V;
}

type IntBox<I: int> {
  let value: I;
}

type Plain<T> {
  let value: T;
}
```

正确语法四，泛型 `spec` 的父 `spec` 使用与父子约束传递（非 variance）：

```feng
spec List<T> {
  func size(): int;
}

spec MyList: List<int> {}

spec MyListEx<T>: List<T> {}

spec Named {
  let name: string;
}

spec NamedList<T: Named> {
  func first(): T;
}

spec UserList<T: Named>: NamedList<T> {}

spec Animal {}

spec Canine: Animal {}

spec A<T: Animal> {}

spec B<T: Canine>: A<T> {}   // 合法：同一个 T 继续上传，按单值 spec 匹配处理

spec StrongNamed: Named {}

spec StrictNamedList<T: StrongNamed>: NamedList<T> {}
```

正确语法五，类型位置中的泛型实例化：

```feng
type Holder<T> {
  let value: T;
}

let a: List<int> = ...;

func wrap(value: Holder<string>): List<string> { ... }

let b = List<int>();
```

正确语法六，显式泛型调用（函数与方法）：

```feng
let a = map(data, option);
let b = map<int, string>(data, option);
let c = pkg.map<int>(data);
let d = obj.map<int>(data);
let e = foo<Map<int>>(data);
```

正确语法六-b，显式泛型类型构造器调用：

```feng
let m = Map<string, int>();
let b = Box<User>();
```

正确语法七，省略显式类型实参时的泛型推导：

```feng
func id<T>(value: T): T { ... }
func pair<T, U>(left: T, right: U): T { ... }

let a = id(1);
let b = pair(1, "x");
```

正确语法八，泛型参与重载：

```feng
func foo() { ... }
func foo<T>() { ... }

func bar(value: int) { ... }
func bar<T>(value: T) { ... }

foo();         // 命中非泛型 foo()
foo<int>();    // 命中泛型 foo<T>()

bar(1);        // 命中精确类型的非泛型 bar(value: int)
bar<int>(1);   // 命中泛型 bar<T>(value: T)
```

正确语法九，具名泛型声明名称相同但泛型参数个数不同：

```feng
spec Foo {}

type UserType<T: Foo> { ... }
type UserType<T: Foo, U> { ... }

spec Reader<T> { ... }
spec Reader<T, U> { ... }
```

错语法一，继续使用旧的 `:<...>` 显式泛型语法：

```feng
let a = map:<int, string>(data, option);
let b = pkg.map:<int>(data);
let c = obj.map:<int>(data);
let d = Map:<string, int>();
```

错语法二，方法泛型参数与所在类型泛型参数重名：

```feng
type Box<T> {
  func bad<T>(value: T): T { ... }
}
```

错语法三，泛型参数定义位置直接写具体 `spec` 或 `type`，而不是参数名：

```feng
spec Process<int>(value: int): void;
type Box<User> { ... }
```

错语法四，向父泛型 `spec` 传递类型参数，但未满足父 `spec` 约束：

```feng
spec Named {
  let name: string;
}

spec NamedList<T: Named> {
  func first(): T;
}

spec BadList<T>: NamedList<T> {}
```

错语法五，同名声明仅靠泛型参数名或约束不同来区分重载：

```feng
func foo<T>() { ... }
func foo<U>() { ... }              // 错误：泛型参数名不参与重载区分

func bar<T: Named>(value: T) { ... }
func bar<U: Process>(value: U) { ... }   // 错误：约束不参与重载区分
```

错语法六，终结器带参数、带返回值、重载或声明泛型参数：

```feng
type Resource<T> {
  func ~Resource(x: int) {}     // 错误：终结器不能有参数
}

type File {
  func ~File(): int {}          // 错误：终结器不能声明非 void 返回类型
  func ~File() {}               // 错误：终结器不允许重载；每个 type 至多一个终结器
}

type Box {
  func ~Box<T>() {}             // 错误：终结器不允许泛型
}
```

错语法七，在显式泛型 target 的内层类型参数中继续使用旧 `:<...>`：

```feng
let e = foo<Map:<int>>(data);
```

## 4 约束语义细则

### 4.1 object-form `spec` 约束

当泛型类型参数的约束是 object-form `spec` 时：

- 调用点需要同时提供 `subject` 与 `witness`；编译器负责在调用点构造对应的胖值对。
- 在泛型声明体内，被约束参数的值已持有 witness；可直接访问该 `spec` 声明的字段与方法，不需要额外收窄。
- 约束传递：向父 `spec` 传递的参数约束不得比目标 `spec` 的参数约束更宽松。

### 4.2 union-form `spec` 约束

当泛型类型参数的约束是 union-form `spec` 时：

- 调用点只传入值本身，**不传入 witness**；union-form 约束不物化 witness。
- 在泛型声明体内，被约束参数的值处于 union 视角；**未经 `match 目标值 { ... }` 收窄时，不允许对其做成员访问、方法调用或 `==` / `!=` 比较**。
- 利用 `match 目标值 { ... }` 对参数值进行 member 匹配后，分支内的值按已收窄到的 member 的既有规则操作。
- 当前阶段每个类型参数至多一个 union-form 约束；不支持 union-form 约束与 object-form `spec` 约束同时修饰同一参数。
- 约束传递规则与 object-form `spec` 约束相同：向上传递的约束不得比目标约束更宽松。

以下示例说明两种约束的区别：

```feng
spec Named {
  let name: string;
}

spec Value: int | string;

// object-form 约束：声明体内可直接访问 name
type NamedBox<T: Named> {
  func get_name(value: T): string {
    return value.name;   // 合法：T 持有 Named 的 witness
  }
}

// union-form 约束：声明体内必须先收窄
type ValueBox<V: Value> {
  func describe(value: V): string {
    if value {
      int {
        return "is int";   // 收窄后合法
      }
      string {
        return "is string"; // 收窄后合法
      }
    }
    // return value.something;  // 非法：未收窄时不可访问
  }
}
```

错语法八，在非调用位置使用旧 `:<...>`：

```feng
type Box:<T> { ... }
let x: List:<int> = ...;
```

错语法九，省略显式类型实参但无法完成唯一推导：

```feng
func make<T>(): T { ... }

let value = make();
```

错语法十，无约束类型参数直接访问成员或做关系/逻辑运算：

```feng
type Plain<T> {
  func bad_member(value: T): string {
    return value.name;        // 错误：无约束 T 不能访问成员
  }

  func bad_compare(left: T, right: T): bool {
    return left < right;      // 错误：无约束 T 不能做关系运算
  }

  func bad_logic(value: T): bool {
    return value && value;    // 错误：无约束 T 不能做逻辑运算
  }
}
```

错语法十一，把不同泛型实例当作容器 variance 自动转换：

```feng
spec Animal {}

spec Canine: Animal {}

type Box<T> {
  let value: T;
}

let dogs: Box<Canine> = ...;
let animals: Box<Animal> = dogs;
```

错语法十二，仅靠约束不同声明同名同泛型参数个数的具名泛型声明：

```feng
spec Foo {}
spec Bar {}

type UserType<T: Foo> { ... }
type UserType<T: Bar> { ... }

spec Reader<T: Foo> { ... }
spec Reader<T: Bar> { ... }
```

## 4 语义

- Feng 允许在 `type`、顶层 `func`、object-form `spec`、callable-form `spec` 和成员方法上声明泛型参数。
- 泛型声明头继续使用普通角括号语法，即 `Name<T>`、`Name<T, U>`。
- 泛型参数定义位置必须写参数名；具体 `type` 或 `spec` 引用都不能直接写在参数列表中。
- 类型参数可选择声明泛型约束，语法为 `T: SomeSpec`；无约束时直接写作 `T`。
- 当前阶段每个类型参数至多声明一个泛型约束。
- 泛型约束只能是 `spec` 引用，包括 object-form、callable-form 和 union-form。
- 当调用点省略显式类型实参时，编译器必须尝试执行泛型推导。
- 泛型推导至少可利用三类信息：实参位置上的已知类型、方法接收者的静态类型，以及当前表达式所在位置已知的目标类型。
- 若省略显式类型实参后仍不能唯一确定全部类型参数，则该调用在编译期报错。
- 若泛型约束是 object-form `spec`，则该类型参数在泛型声明体内可按该 `spec` 已声明的字段与行为签名使用。
- 若泛型约束是 callable-form `spec`，则该类型参数在泛型声明体内可按该可调用签名直接调用。
- 若泛型约束是 union-form `spec`，则该类型参数在泛型声明体内遵循 union-form 的既有规则；是否允许成员访问、比较或其他操作，仍取决于 union-form 自身是否要求先收窄。
- 约束语法不引入新的结构匹配或鸭子类型语义；它只表示“该类型参数在当前泛型声明体内可按泛型约束已有语义使用”。
- 在 `spec Child: Parent<int>`、`spec Child<T>: Parent<T>` 这类父 `spec` 列表中，`Parent<int>`、`Parent<T>` 都属于对泛型 `spec` 的使用，而不是新的类型参数定义。
- 因此，父 `spec` 列表允许写具体类型实参，也允许把当前 `spec` 自己的类型参数继续传递给父泛型 `spec`。
- 但父 `spec` 列表右侧仍然必须解析为 `spec`；这一点不因泛型而放宽为可写任意 `type`。
- 若把当前 `spec` 的类型参数继续传递给父泛型 `spec`，则必须检查该类型参数是否满足父 `spec` 对应类型参数的既有约束；不满足时必须报错。
- 若当前类型参数自身已经带有更强的泛型约束，例如 `T: StrongNamed` 传给 `Parent<T: Named>`，或 `T: Canine` 传给 `A<T: Animal>`，则编译器必须进一步检查该泛型约束在当前可见契约关系下是否可按父约束使用；满足则合法，不满足则报错。
- 这类“同一个类型参数在更强约束到更弱约束之间的继续传递”属于单值约束匹配，不属于不同泛型实例之间的 variance。
- 类型位置（字段类型、参数类型、返回类型、类型标注等）中的泛型实例化继续直接使用 `<...>` 语法；`List<int>`、`Map<string, int>` 这类写法不引入歧义。
- 表达式位置在需要显式写出类型实参时，同样直接使用普通 `<...>`：`foo<T>(...)`、`pkg.foo<T>(...)`、`obj.foo<T>(...)`、`Map<string, int>()`、`Type<Args>[:n]` 都属于显式泛型语法。
- Parser 对表达式位置的 `<...>` 仅做纯语法识别：当 postfix 目标以合法标识符结尾，`<...>` 内部可按类型实参列表稳定解析，且匹配到的 `>` 后紧跟 `(`、`{`、`[`、`;`、`)`、`]` 或 `}` 之一时，Parser 必须把它视为显式泛型 target，而不依赖 Semantic 再决定这是不是泛型。
- 显式泛型 target 的类型实参列表内部，每一项仍然是普通类型语法。若某个类型实参本身是泛型类型，则继续写成 `Map<int>`、`Result<string, int>`，例如 `foo<Map<int>>(...)`。
- 是否形成“合法的显式泛型调用 / 类型构造 / 数组创建 / 对象构造”由后续语义阶段判定；若某个显式泛型 target 最终没有落在合法用法上，编译器必须在语义阶段报错。
- 当调用点不显式写出类型实参时，调用表面语法仍与普通调用完全一致，例如 `map(data, option)`；编译器此时必须按本文规则尝试完成泛型推导。
- 无约束类型参数在泛型声明体内不提供任何额外可见成员集；因此不能直接访问 `T` 的成员，也不能把 `T` 当作已知可比较值或 `bool` 来做关系运算与逻辑运算。
- 约束语法本身不自动赋予关系运算或逻辑运算资格；这些运算仍须满足 [Feng 语言表达式与运算规范](./feng-expression.md) 的既有规则。
- Feng 当前阶段不支持泛型容器类型的 variance。泛型实例之间按不变处理；只有泛型构造器相同、类型参数数量相同且各位置类型实参完全一致时，才视为同一泛型实例类型。
- 因而，即使两个类型实参之间存在 `type` / `spec` 满足关系、父子 `spec` 关系或其他可见契约关系，也不因此自动建立对应泛型实例之间的兼容关系。
- 本文当前不支持基于协变/逆变的隐式或显式自动转换；需要时开发者必须手动编程完成遍历、重建或适配目标值。
- 因而，“`B<T: Canine>: A<T>` 合法”与“`Box<Canine>` 可自动当作 `Box<Animal>` 使用”是两类不同问题：前者是同一个类型参数沿父子约束链的单值 `spec` 匹配，后者属于泛型容器 variance，而 Feng 当前阶段不支持后者。
- 同一作用域内,同 category 的具名泛型 `type` 或具名泛型 `spec` 的声明 identity 按“名称 + 泛型参数数量”确定；泛型参数名与泛型约束都不参与 identity。category 划分详见 [dev/feng-type-arity-overload-dev.md](../dev/feng-type-arity-overload-dev.md) §0.3（7 类 `FengOverloadCategory`）。
- 因此，`type UserType<T: Foo>` 与 `type UserType<T: Bar>` 冲突；`type UserType<T: Foo>` 与 `type UserType<T: Foo, U>` 可共存。`spec` 的对应规则相同。
- 因此，`UserType<T>` 与 `UserType<T, U>` 是两个不同的具名 `type`。在字段类型、参数类型、返回类型、父 `spec` 使用以及 `fit` 左侧这类所有类型使用位置，都必须按“名称 + 泛型参数数量”精确解析；若当前作用域中不存在精确匹配的声明，则属于“找不到该 `type` / `spec` 声明”，而不是对其他同名不同参数数量声明的模糊匹配。
- 泛型函数与泛型方法在现有重载决议基础上，把“泛型参数数量”并入重载签名；泛型参数名本身以及其泛型约束都不参与重载区分。
- 因此，`foo()` 与 `foo<T>()` 可共存，因为泛型参数数量不同。
- 同理，`foo<T>(t: T)` 与 `foo(t: int)` 可共存，因为泛型参数数量不同；当某次调用同时可匹配精确具体类型的非泛型候选与泛型候选时，优先选择精确具体类型候选。
- 泛型 `type` 内的方法可以同时使用所在类型的泛型参数与方法自己的泛型参数；为避免重名遮蔽，方法泛型参数名不得与外层类型泛型参数名重名。
- 终结器仍然是 `type` 的特殊成员函数；泛型语法不会放宽其既有约束。终结器不允许有参数、不允许声明非 `void` 返回类型、不允许重载，也不允许声明类型参数。
- 本文当前阶段不支持协变/逆变；不同泛型实例之间不建立额外兼容关系，后续若要引入，必须单独收敛规则并更新权威规范。
- 本文当前不定义泛型与 `extern`、`@abi`、`@cdecl` / `@stdcall` / `@fastcall` 等 C ABI 相关机制的交叉规则；这一部分留待后续 C ABI 规范统一处理。

## 5 规则

分为「必须、禁止、建议」。

- [必须] 泛型声明在声明名后使用 `<...>` 书写类型参数列表。
- [必须] 泛型参数定义位置必须写参数名；具体 `type` 或 `spec` 引用都不能直接写在参数列表中。
- [必须] 约束类型参数使用 `T: SomeSpec` 语法；无约束类型参数直接写作 `T`。
- [必须] 当前阶段每个类型参数至多声明一个泛型约束。
- [必须] 泛型约束只能是 `spec` 引用，包括 object-form、callable-form 和 union-form。
- [必须] 当调用点省略显式类型实参时，编译器必须尝试推导全部类型参数；若不能唯一确定，则编译期报错。
- [必须] 在 `spec Child: Parent<int>` 或 `spec Child<T>: Parent<T>` 中，父 `spec` 列表右侧属于泛型 `spec` 使用位置，不属于类型参数定义位置。
- [必须] 父 `spec` 列表可以使用具体类型实参，也可以转发当前 `spec` 自己的类型参数。
- [必须] 若当前 `spec` 把自己的类型参数继续传递给父泛型 `spec`，则该类型参数必须满足父 `spec` 对应类型参数的既有约束。
- [必须] 若当前类型参数已经带有更强的泛型约束，并继续传递到需要更弱 `spec` 约束的位置，则编译器必须依据该泛型约束在当前可见契约关系下是否满足目标 `spec` 来判定合法性。
- [必须] 上述“同一个类型参数沿父泛型 `spec` 继续传递”的合法性，属于单值约束匹配，不属于泛型容器类型的协变/逆变。
- [必须] 类型位置（字段类型、参数类型、返回类型、类型标注等）中的泛型实例化继续直接使用 `<...>` 语法。
- [必须] 表达式位置显式写出类型实参时，同样直接使用 `<...>`；该规则适用于顶层函数、模块函数、成员方法调用、泛型类型构造器调用、泛型数组创建以及后续由对象字面量后缀消费的泛型类型目标。
- [必须] Parser 在表达式位置识别显式泛型 target 时，只能依据局部语法规则，不得依赖 Semantic。
- [必须] 显式泛型 target 的类型实参列表内部，继续按普通类型语法书写；若某个类型实参本身是泛型类型，仍使用 `<...>`，不得在内层再次写 `:<...>`。
- [必须] 除函数或方法调用点的显式类型实参外，其他所有位置一律继续使用普通 `<...>` 语法。
- [必须] 无约束类型参数不得直接访问成员，也不得直接参与关系运算或逻辑运算。
- [必须] 当前阶段泛型容器类型按不变处理；只有泛型构造器相同、类型参数数量相同且各位置类型实参完全一致时，才视为同一泛型实例类型。
- [必须] 同一作用域内,同 category 的具名泛型 `type` 与具名泛型 `spec` 的声明 identity 按“名称 + 泛型参数数量”确定; 泛型参数名和泛型约束不参与 identity。category 划分详见 [dev/feng-type-arity-overload-dev.md](../dev/feng-type-arity-overload-dev.md) §0.3。
- [必须] 所有具名泛型 `type` / `spec` 的使用位置都必须按“名称 + 泛型参数数量”精确解析到已存在声明; 不存在精确匹配时,编译器必须按“找不到声明”报错。
- [必须] 泛型函数与泛型方法的重载在现有规则基础上额外区分“泛型参数数量”；泛型参数名和泛型约束不参与重载区分。
- [必须] 当精确具体类型的非泛型候选与泛型候选同时可匹配某次调用时，优先选择精确具体类型的非泛型候选。
- [必须] 泛型候选参与重载决议前，必须先完成类型参数推导，并验证推导结果满足该候选声明的全部泛型约束；推导不出或约束不满足的泛型候选不进入候选集。
- [必须] 进入候选集后，非泛型候选的匹配优先级高于泛型候选；仅当不存在任何可匹配的非泛型候选时，泛型候选才可胜出。
- [必须] 在泛型 `type` 内声明泛型方法时，方法泛型参数名不得与所在类型的泛型参数名重名。
- [必须] 终结器若出现于泛型 `type` 中，仍必须遵守 [Feng 语言类型规范](./feng-type.md) 的既有规则：无参数、无返回值（省略或 `: void`）、每个 `type` 至多一个，且不得声明类型参数。
- [禁止] 继续使用旧的 `:<...>` 显式泛型语法；无论在调用位置还是非调用位置，`:<...>` 都必须报错。
- [禁止] 把显式泛型 target 留作最终合法语义结果；若 `<...>` 已被 Parser 识别为显式泛型 target，但后续未形成合法调用、对象构造、数组创建或其他已定义消费形式，语义阶段必须报错。
- [禁止] 依赖协变/逆变把一种泛型容器实例通过隐式或显式自动转换当作另一种类型实参不同的泛型实例使用；需要时只能手动编程转换。
- [禁止] 仅靠泛型参数名或泛型约束不同声明同名且泛型参数个数相同的具名泛型 `type` 或具名泛型 `spec`。
- [禁止] 仅靠泛型参数名或泛型约束不同来区分同名重载。
- [禁止] 为终结器声明类型参数。
- [禁止] 在泛型 `type` 内声明与外层类型泛型参数同名的方法泛型参数。
- [建议] 当调用点不需要显式指定类型实参时，优先使用普通调用语法，避免无必要的显式 `<...>`。

## 6 编译期

- 编译器必须识别 `type`、顶层 `func`、`spec` 和成员方法上的泛型声明头。
- 编译器必须识别类型参数上的可选约束语法 `T: SomeSpec`。
- 编译器必须把表达式位置的 `<...>` 识别为显式泛型 target 语法的一部分，并据此解析后续的调用、对象字面量后缀或数组创建。
- 编译器必须把显式泛型 target 中每个类型实参按普通类型引用解析；例如 `foo<Map<int>>(...)` 合法，而 `foo<Map:<int>>(...)` 必须报错。
- 编译器必须拒绝所有 `:<...>` 写法。
- 编译器不得要求 Parser 先知道某个目标是不是泛型声明，才能决定 `<...>` 是否按显式泛型 target 解析。
- 编译器必须检查泛型参数定义位置是否使用了参数名，而不是具体 `type` 或 `spec` 引用。
- 编译器必须检查每个类型参数是否至多声明一个泛型约束，并检查该泛型约束是否是合法的 `spec` 引用。
- 编译器必须在调用点省略显式类型实参时执行泛型推导，并在不能唯一确定全部类型参数时报错。
- 编译器必须把 `spec Child: Parent<int>`、`spec Child<T>: Parent<T>` 中的 `Parent<...>` 解析为父 `spec` 使用，而不是新的类型参数定义。
- 编译器必须检查父 `spec` 列表右侧的泛型实例是否确实解析为 `spec`，并检查类型实参数量是否与父泛型 `spec` 的声明匹配。
- 编译器必须在 `spec` 继承链分析时检查传递给父泛型 `spec` 的每个类型实参是否满足父 `spec` 对应类型参数的约束；若把当前 `spec` 的类型参数继续上传，也必须在当前声明处完成该检查。
- 编译器必须在 `T: StrongNamed -> Parent<T: Named>`、`T: Canine -> A<T: Animal>` 这类传递中，依据当前泛型约束在当前可见契约关系下是否满足目标 `spec` 完成合法性判定。
- 编译器必须在语义分析阶段拒绝无约束类型参数上的成员访问、关系运算和逻辑运算。
- 编译器必须按不变规则检查泛型实例兼容性；若泛型构造器相同但任一位置类型实参不同，即使这些实参之间存在 `type` / `spec` 满足关系或其他可见契约关系，也必须拒绝任何基于 variance 的隐式或显式自动转换；需要时只能由开发者手动编程完成转换。
- 编译器必须按“名称 + 泛型参数数量”检查具名泛型 `type` 与具名泛型 `spec` 的重复声明冲突；泛型参数名和泛型约束不同，不构成新的声明 identity。
- 编译器必须按“名称 + 泛型参数数量”解析所有具名泛型 `type` / `spec` 的使用位置；若不存在精确匹配的声明，必须按“找不到声明”报错，不得回退到其他同名但参数数量不同的声明。
- 编译器必须按“名称 + 泛型参数数量 + 参数个数 + 参数类型”检查泛型函数与泛型方法的重载集合冲突；泛型参数名和泛型约束不同，不构成新的重载区分维度。
- 编译器必须在重载决议时优先选择精确具体类型的非泛型候选；只有在不存在更优的精确具体类型候选时，泛型候选才可胜出。
- 编译器必须在重载候选筛选阶段对每个泛型候选执行类型参数推导与约束验证；若类型参数无法推导，或推导结果不满足该候选声明的泛型约束，该泛型候选必须从候选集中剔除，不得继续参与优先级比较。
- 编译器必须按“非泛型精确匹配 > 非泛型非精确匹配 > 泛型匹配”的优先级分层裁定重载；“非泛型精确匹配”指实参类型与形参类型一致，“非泛型非精确匹配”指需要既有合法隐式转换（如 union-form `spec` 的 member 上转）才能匹配的非泛型候选，“泛型匹配”指经类型参数推导匹配的泛型候选。
- 编译器必须检查泛型 `type` 内的方法泛型参数名是否与外层类型泛型参数名重名；若重名，必须在编译期报错并阻止通过。
- 编译器必须拒绝任何带类型参数的终结器声明，并继续执行终结器已有的无参数、无返回值和唯一性检查。
- 编译器在当前阶段不要求支持泛型与 C ABI 交叉使用；相关规则待后续 C ABI 规范统一定义。

## 9 实现分阶段工作（非规范性）

本节说明“若 Feng 支持本文定义的泛型语法，编译器与运行时各阶段至少需要承担哪些工作”。本节用于指导实现拆分，不额外增加新的语言语义承诺；当前实现方向已经收口为“共享 body + 类型参数描述符 + witness + 编译期单态 wrapper”，本节只描述这一方向下各阶段至少需要交付的工作。

同时，Feng 支持 `.fb` 二进制分发且这会是重要分发路径之一，因此泛型实现不能建立在“provider 源码总在 consumer 编译时可见”的假设上。

当前实现收敛方向是：非单态泛型作为主要形态；单态化发码只作为编译器进阶优化项，并且仅在编译器可直接看到泛型定义源码的场景下才可能启用，例如当前工程内源码。

### 9.1 词法分析

- 无需新增关键字；继续复用 `type`、`func`、`spec`、`:`、`<`、`>`、`,`、标识符等既有 token。
- 词法器必须稳定产出显式泛型 target 所需 token 序列，不得把 `<` / `>` 与其它运算符错误合并到无法支撑泛型解析的形态。
- 若词法器当前把 `>>`、`>>>` 视为单个移位 token，则必须为嵌套泛型实参列表提供可消费策略；否则 `Map<string, List<int>>` 这类写法无法稳定解析。

### 9.2 语法分析

- 扩展声明语法，使 `type`、顶层 `func`、`spec` 和成员方法都可携带类型参数列表。
- 扩展类型参数语法，使单个类型参数可携带可选泛型约束 `T: SomeSpec`；参数定义位置本身必须是参数名。
- 扩展类型引用语法，使类型位置可解析 `Name<T>`、`Name<T, U>` 这类实例化写法。
- 扩展 `spec` 父列表语法，使 `spec Child: Parent<int>`、`spec Child<T>: Parent<T>` 这类父泛型 `spec` 使用可被稳定解析为“父 `spec` 引用 + 类型实参列表”。
- 扩展 postfix 语法，使表达式位置支持显式泛型 target；即在 postfix 目标后直接解析 `<...>`，再由后续 `(` / `{` / `[` 或闭合分隔符决定其后续组合形态。
- 在省略显式类型实参的普通调用语法上，不新增额外语法标记；是否为泛型调用以及如何补全类型参数，留给语义分析阶段决定。
- 解析 `foo<Map<int>>(...)` 时，外层 `<...>` 表示“显式泛型 target / 调用”，内层 `Map<int>` 仍按普通类型引用语法处理。
- Parser 必须继续保持“仅根据语法判断是否合法”的边界，不得依赖 Semantic 才决定某个 `<...>` 是否是泛型调用。
- Parser 需要把终结器继续视为 `type` 的特殊成员，不因泛型声明能力的引入而把终结器纳入普通泛型方法语法。
- Parser 可先把 `foo<T>` 这类形状识别为显式泛型 target，再由后续语义阶段判断其是否形成了合法的泛型调用、对象构造、数组创建或其他已定义消费形式。
- AST 需要新增或扩展以下信息：声明上的类型参数表、类型引用上的类型实参表、调用表达式上的显式类型实参表。

### 9.3 语义分析

- 为每个泛型声明建立独立的类型参数作用域，并把类型参数作为可解析名字引入该作用域。
- 为每个带约束的类型参数记录其泛型约束；该泛型约束必须是任意 form 的 `spec` 引用。
- 若泛型约束是 object-form `spec`，在泛型声明体内按该 `spec` 视角提供可见成员集；若是 callable-form `spec`，则提供可调用签名；若是 union-form `spec`，则继续复用 union-form 的既有访问/收窄规则。
- 在分析 `spec Child: Parent<int>` 或 `spec Child<T>: Parent<T>` 时，把 `Parent<...>` 视为父 `spec` 的实例化使用，并沿用 `spec` 既有继承/满足链规则。
- 若子 `spec` 向父泛型 `spec` 传递自己的类型参数，则在当前声明处验证该传递是否满足父 `spec` 的对应约束；不得等到某个后续具体实例化点再补做。
- 若当前类型参数自身已经带有更强泛型约束，则在需要满足父 `spec` 约束时，进一步基于该泛型约束已声明的满足关系完成证明。
- 这一检查针对的是同一个类型参数在父子约束链上的继续传递，不应与不同泛型实例之间的 variance 兼容性混淆。
- 在泛型 `type` 内解析成员方法时，需要同时看见“外层类型泛型参数 + 当前方法泛型参数”，并执行重名检查。
- 检查同一类型参数列表中的重名、方法泛型参数与外层类型泛型参数重名、以及其他命名冲突。
- 在类型位置解析类型引用时，区分“具名类型引用”和“类型参数引用”。
- 对无约束类型参数，成员访问与关系/逻辑运算都必须在语义阶段直接拒绝；不得等到发码或运行时再决定。
- 当前阶段泛型实例兼容性按不变规则处理；语义分析不得因为类型实参之间存在满足关系，就额外建立两个泛型实例之间的兼容性。
- 泛型重载集合在现有重载规则基础上还要纳入“泛型参数数量”；泛型约束不同不形成新签名。
- 当调用点省略显式类型实参时，在语义阶段按实参类型、接收者静态类型与上下文目标类型执行泛型推导；若结果不唯一则报错。
- 检查泛型实例化与显式泛型调用的实参数量是否匹配声明上的类型参数个数。
- 检查显式类型实参是否只出现在已定义的合法消费位置上；若某个显式泛型 target 没有被合法消费，或对非泛型目标写显式类型实参，必须报错。
- 为后续发码产出稳定语义结论：调用点命中了哪个声明、使用了哪些显式类型实参、替换后的参数类型和返回类型是什么。
- 终结器继续按 `type` 特殊成员规则处理，不参与泛型重载集合，也不得携带类型参数。
- 若后续支持“省略显式类型实参”的推导，则推导过程也应在语义分析阶段完成，而不是推给 codegen 或运行时。

### 9.4 符号表与跨模块

- 公开泛型声明进入 `.ft` / `.fb` 的权威规则,以 [feng-symbol-table.md](./feng-symbol-table.md) 与 [feng-package.md](./feng-package.md) 为准; 本小节只说明实现阶段至少需要消费哪些结论。
- 若公开泛型声明需要进入 `.ft` / `.fb` 导出层，则符号表必须保留泛型参数列表、参数个数以及未实例化签名骨架，不能只导出某个已替换后的具体文本签名。
- 当前阶段公开符号表无需导出 variance 元信息；泛型实例兼容性统一按不变规则处理即可。
- 若公开泛型声明支持省略显式类型实参的调用，则 `.ft` / `.fb` 导出层还必须保留支撑推导所需的参数类型、返回类型与约束事实，不能只保留“已推导后的使用结果”。
- 由于 `.fb` 二进制分发是重要路径，跨包消费泛型时不得把“读取 provider 源码后再由 consumer 重新全量单态化”当作唯一成立方式。
- 导入外部包中的泛型 `type`、`func`、`spec` 后，语义分析对其使用方式应与本地声明尽量保持一致；“本地/外部”的差异应尽量留在导出、链接和发码阶段，而不是复制两套泛型语义规则。

### 9.5 发码

- 发码阶段应直接消费语义分析已经得出的泛型结论，不重新做一次名字解析、重载决议或泛型调用判定。
- 首发实现可先只支持非单态 lowering，不把单态化发码作为阻塞项。
- 非单态 lowering 作为主要形态时，发码需要为泛型声明保留可复用的共享实现、稳定 ABI 入口以及必要的类型参数描述符 / witness / 布局辅助元数据通路。泛型 `type` 的实例布局按具体类型实参生成，成员方法主体必须优先编译为共享实现；具体实例可生成仅负责传递 `self`、类型参数描述符、字段 offset 等辅助信息的轻量 wrapper，但不得把 wrapper 当作复制后的方法主体。
- 顶层泛型函数与泛型方法采用同一条共享实现路线：共享主体只编译一份，具体实例由编译期单态 wrapper 负责绑定类型参数描述符并转发；两者区别仅在于顶层函数没有 `self` 与宿主布局输入段。
- 当前阶段不把泛型与 `extern` / `@abi` / C ABI 的交叉发码作为交付目标；相关问题留待后续 C ABI 专题统一处理。
- 由于 Feng 支持 `.fb` 二进制分发，泛型 lowering 不能把“consumer 总能拿到 provider 源码并在本地对所有实例做全量单态化发码”作为唯一前提。
- 若后续引入单态化发码，它应只作为优化项：在编译器能直接看见泛型定义源码、并且收益明确的场景下，按需为部分实例生成专门实现。
- 若启用单态化发码，发码仍必须为这些专门实例生成稳定且不冲突的内部名字，并保证它与非单态主路径共存，不改变跨包消费前提。
- 泛型 `type` 若在某个具体实例下变成受管对象类型，则无论走非单态主路径还是单态化优化路径，发码都必须产出与实际字段替换结果一致的类型描述、引用枚举信息和默认零值/销毁辅助逻辑。

### 9.6 分阶段交付建议

- 第一阶段：先交付非单态泛型主路径，覆盖声明解析、语义检查、跨包导出/导入和基础发码闭环，不处理单态化发码。
- 第二阶段：在第一阶段稳定后，再把单态化发码作为编译器优化项增量引入，仅对可见源码场景按需启用。

### 9.7 运行时

- 运行时不得承担“泛型名字解析”“泛型重载选择”或“根据类型实参动态搜索实现”这类工作；这些都应在编译期完成。
- 非单态主路径下，运行时只消费编译期已经安排好的共享实现入口、类型描述、类型参数描述符、witness 或其他辅助对象，不负责重新做泛型决议。
- 若后续启用实例化发码优化，运行时通常也无需理解“泛型语法”本身，只需要处理发码后得到的具体类型、具体函数和具体类型描述。
- 若泛型实例生成新的受管对象布局，运行时只需要消费与该具体实例对应的类型描述和托管字段枚举结果，不应在运行期反推类型参数。
- 二进制分发场景下，运行时至多只消费编译期已经导出的泛型辅助入口、类型描述、类型参数描述符或 witness 对象；不得要求 provider 源码在运行期或 consumer 编译期重新出现。
- 只有当最终 lowering 方案显式要求类型描述、类型参数描述符或 witness 在运行时随值传递时，运行时才需要承载这些额外对象；即便如此，运行时也只负责消费编译期已经选定的结果，不负责重新决议。
