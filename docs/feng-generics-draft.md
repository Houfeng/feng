# Feng 语言泛型规范

> **状态**: 草案。
> 本文档当前只收敛已经确认的泛型语法与编译期约束：泛型声明入口、显式泛型调用的 `:<...>` 语法，以及“泛型 `type` 内的方法泛型参数不得与外层类型泛型参数重名”的规则。
> 由于 Feng 支持 `.fb` 二进制分发，泛型实现不能把“consumer 总能拿到 provider 源码并对所有实例做全量单态化发码”作为前提。
> 当前实现方向以非单态泛型为主；单态化发码仅作为编译器后续可选优化项，不作为首发或通用前提。
> 类型参数约束、类型推导细则、实例化策略与代码生成策略暂不在本文定义。

## 1 职责

- 为 Feng 增加类型参数机制，允许在 `type`、`fn`、`spec` 和成员方法上声明泛型参数。
- 在不让 Parser 反向依赖 Semantic 的前提下，为显式泛型调用提供无歧义语法。
- 收敛已经确认的命名约束：泛型 `type` 内的方法泛型参数不得与所在类型的泛型参数重名。

## 2 术语

- 类型泛型参数：声明在 `type Name<T>` 或 `spec Name<T>` 上的类型参数。
- 函数泛型参数：声明在顶层 `fn Name<T>` 上的类型参数。
- 方法泛型参数：声明在 `type` 成员方法 `fn Name<T>` 上的类型参数。
- 显式泛型调用：在调用点显式写出类型实参的函数或方法调用，统一使用 `callee:<...>(...)` 语法。
- 非调用位置：除函数或方法调用点外的其他所有位置，包括声明头、类型引用、字段类型、参数类型、返回类型和类型实参内部。
- 类型位置：变量类型标注、字段类型、参数类型、返回类型以及类型构造等只允许出现类型的语法位置。

## 3 语法

正确语法一，泛型声明：

```feng
type List<T> { ... }

fn map<T, U>(left: T, right: U): T { ... }

spec Comparable<T> {
  fn compare(other: T): int;
}

spec Mapper<T, U>(value: T): U;
```

正确语法二，泛型类型中的泛型方法：

```feng
type Box<T> {
  fn get(): T { ... }

  fn map<U>(value: U): T { ... }
}
```

正确语法三，类型位置中的泛型实例化：

```feng
type Holder<T> {
  let value: T;
}

let a: List<int> = ...;

fn wrap(value: Holder<string>): List<string> { ... }

let b = List<int>();
```

正确语法四，显式泛型调用：

```feng
let a = map(data, option);
let b = map:<int, string>(data, option);
let c = pkg.map:<int>(data);
let d = obj.map:<int>(data);
let e = foo:<Map<int>>(data);
```

错语法一，把 `<...>` 直接写在调用目标后面：

```feng
let a = map<int, string>(data, option);
let b = pkg.map<int>(data);
let c = obj.map<int>(data);
```

错语法二，方法泛型参数与所在类型泛型参数重名：

```feng
type Box<T> {
  fn bad<T>(value: T): T { ... }
}
```

错语法三，在显式泛型调用的内层类型参数中重复使用 `:`：

```feng
let e = foo:<Map:<int>>(data);
```

错语法四，在非调用位置使用 `:<...>`：

```feng
type Box:<T> { ... }
let x: List:<int> = ...;
```

## 4 语义

- Feng 允许在 `type`、顶层 `fn`、object-form `spec`、callable-form `spec` 和成员方法上声明泛型参数。
- 泛型声明头继续使用普通角括号语法，即 `Name<T>`、`Name<T, U>`。
- 类型位置中的泛型实例化继续直接使用 `<...>` 语法；`List<int>`、`Map<string, int>` 这类写法不引入歧义，因此不使用 `:<...>`。
- 显式泛型调用只在函数或方法调用处引入歧义消解语法。凡是在调用点显式写出类型实参，无论目标是顶层函数、模块函数还是成员方法，都统一使用 `:<...>`。
- `:<...>` 只作用于最外层“这是一次显式泛型调用”的语法标记；类型实参列表内部的每一项仍然是普通类型语法。若某个类型实参本身是泛型类型，则继续写成 `Map<int>`、`Result<string, int>`，例如 `foo:<Map<int>>(...)`。
- 因而，`:<...>` 仅用于函数或方法调用时显式指定泛型参数；除这一处以外，其他所有无歧义位置都继续使用普通 `<...>`，不引入 `:`。
- 因此，`foo<T>(...)`、`pkg.foo<T>(...)`、`obj.foo<T>(...)` 都不作为显式泛型调用语法。
- 当调用点不显式写出类型实参时，调用表面语法仍与普通调用完全一致，例如 `map(data, option)`；是否允许省略、以及省略时如何推导，由后续泛型推导规则定义。
- 泛型 `type` 内的方法可以同时使用所在类型的泛型参数与方法自己的泛型参数；为避免重名遮蔽，方法泛型参数名不得与外层类型泛型参数名重名。
- `:<...>` 的引入仅用于语法消歧，使 Parser 仅根据词法序列就能识别“这里是显式泛型调用”，而不需要反向依赖 Semantic。

## 5 规则

分为「必须、禁止、建议」。

- [必须] 泛型声明在声明名后使用 `<...>` 书写类型参数列表。
- [必须] 类型位置中的泛型实例化继续直接使用 `<...>` 语法，不得改写为 `:<...>`。
- [必须] 显式泛型调用统一使用 `callee:<...>(...)` 语法；该规则同时适用于顶层函数、模块函数和成员方法调用。
- [必须] 显式泛型调用的类型实参列表内部，继续按普通类型语法书写；若某个类型实参本身是泛型类型，仍使用 `<...>`，不得在内层再次写 `:`。
- [必须] 除函数或方法调用点的显式类型实参外，其他所有位置一律继续使用普通 `<...>` 语法。
- [必须] 在泛型 `type` 内声明泛型方法时，方法泛型参数名不得与所在类型的泛型参数名重名。
- [禁止] 把 `foo<T>(...)`、`pkg.foo<T>(...)` 或 `obj.foo<T>(...)` 当作显式泛型调用语法。
- [禁止] 在 `:<...>` 的内层类型实参中再次使用 `:` 作为泛型类型实例化前缀，例如 `foo:<Map:<int>>(...)`。
- [禁止] 在非调用位置使用 `:<...>`，例如 `type Box:<T>` 或 `List:<int>`。
- [禁止] 在泛型 `type` 内声明与外层类型泛型参数同名的方法泛型参数。
- [建议] 当调用点不需要显式指定类型实参时，优先使用普通调用语法，避免无必要的 `:<...>`。

## 6 编译期

- 编译器必须识别 `type`、顶层 `fn`、`spec` 和成员方法上的泛型声明头。
- 编译器必须把 `:<...>` 识别为显式泛型调用语法的一部分，并据此解析后续的实参调用。
- 编译器必须把显式泛型调用中每个类型实参按普通类型引用解析；例如 `foo:<Map<int>>(...)` 合法，而 `foo:<Map:<int>>(...)` 必须报错。
- 编译器必须拒绝在非调用位置使用 `:<...>` 的写法。
- 编译器不得把 `foo<T>(...)`、`pkg.foo<T>(...)` 或 `obj.foo<T>(...)` 解释为显式泛型调用；这些写法若不能按普通表达式语法成立，则必须报错。
- 编译器必须检查泛型 `type` 内的方法泛型参数名是否与外层类型泛型参数名重名；若重名，必须在编译期报错并阻止通过。

## 7 运行时

- 本文档当前不引入新的运行时可见语义承诺。
- `:<...>` 仅用于语法消歧，本身不规定泛型实例化、代码生成或运行时表示方式。
- 泛型的实例化策略、运行时布局与代码生成规则待后续规范补充。

## 9 实现分阶段工作（非规范性）

本节说明“若 Feng 支持本文定义的泛型语法，编译器与运行时各阶段至少需要承担哪些工作”。本节用于指导实现拆分，不额外增加语言语义承诺；尤其不在此决定“实例化发码”“共享 body + 类型描述/字典传递”或其他 lowering 方案哪一条最终采纳。

同时，Feng 支持 `.fb` 二进制分发且这会是重要分发路径之一，因此泛型实现不能建立在“provider 源码总在 consumer 编译时可见”的假设上。

当前实现收敛方向是：非单态泛型作为主要形态；单态化发码只作为编译器进阶优化项，并且仅在编译器可直接看到泛型定义源码的场景下才可能启用，例如当前工程内源码。

### 9.1 词法分析

- 无需新增关键字；继续复用 `type`、`fn`、`spec`、`:`、`<`、`>`、`,`、标识符等既有 token。
- 词法器必须稳定产出 `callee:<...>(...)` 所需 token 序列，不得把 `:<` 误并入其他运算符或特殊 token。
- 若词法器当前把 `>>`、`>>>` 视为单个移位 token，则必须为嵌套泛型实参列表提供可消费策略；否则 `Map<string, List<int>>` 这类写法无法稳定解析。

### 9.2 语法分析

- 扩展声明语法，使 `type`、顶层 `fn`、`spec` 和成员方法都可携带类型参数列表。
- 扩展类型引用语法，使类型位置可解析 `Name<T>`、`Name<T, U>` 这类实例化写法。
- 扩展调用语法，使 postfix 调用目标支持 `callee:<...>(...)` 这一显式泛型调用后缀。
- 解析 `foo:<Map<int>>(...)` 时，外层 `:<...>` 表示“显式泛型调用”，内层 `Map<int>` 仍按普通类型引用语法处理。
- Parser 必须继续保持“仅根据语法判断是否合法”的边界，不得依赖 Semantic 才决定某个 `<...>` 是否是泛型调用。
- `foo<T>(...)`、`pkg.foo<T>(...)`、`obj.foo<T>(...)` 不得在 parse 阶段被解释为显式泛型调用；它们若不能按现有普通表达式语法成立，应在后续阶段报错或拒绝通过。
- AST 需要新增或扩展以下信息：声明上的类型参数表、类型引用上的类型实参表、调用表达式上的显式类型实参表。

### 9.3 语义分析

- 为每个泛型声明建立独立的类型参数作用域，并把类型参数作为可解析名字引入该作用域。
- 在泛型 `type` 内解析成员方法时，需要同时看见“外层类型泛型参数 + 当前方法泛型参数”，并执行重名检查。
- 检查同一类型参数列表中的重名、方法泛型参数与外层类型泛型参数重名、以及其他命名冲突。
- 在类型位置解析类型引用时，区分“具名类型引用”和“类型参数引用”。
- 检查泛型实例化与显式泛型调用的实参数量是否匹配声明上的类型参数个数。
- 检查显式类型实参是否只出现在泛型可调用目标上；若对非泛型函数、非泛型方法写 `:<...>`，必须报错。
- 为后续发码产出稳定语义结论：调用点命中了哪个声明、使用了哪些显式类型实参、替换后的参数类型和返回类型是什么。
- 若后续支持“省略显式类型实参”的推导，则推导过程也应在语义分析阶段完成，而不是推给 codegen 或运行时。

### 9.4 符号表与跨模块

- 若公开泛型声明需要进入 `.ft` / `.fb` 导出层，则符号表必须保留泛型参数列表、参数个数以及未实例化签名骨架，不能只导出某个已替换后的具体文本签名。
- 由于 `.fb` 二进制分发是重要路径，跨包消费泛型时不得把“读取 provider 源码后再由 consumer 重新全量单态化”当作唯一成立方式。
- 导入外部包中的泛型 `type`、`fn`、`spec` 后，语义分析对其使用方式应与本地声明尽量保持一致；“本地/外部”的差异应尽量留在导出、链接和发码阶段，而不是复制两套泛型语义规则。

### 9.5 发码

- 发码阶段应直接消费语义分析已经得出的泛型结论，不重新做一次名字解析、重载决议或泛型调用判定。
- 首发实现可先只支持非单态 lowering，不把单态化发码作为阻塞项。
- 非单态 lowering 作为主要形态时，发码需要为泛型声明保留可复用的共享实现、稳定 ABI 入口以及必要的类型描述/字典/辅助元数据通路；具体承载形态由后续设计收敛。
- 由于 Feng 支持 `.fb` 二进制分发，泛型 lowering 不能把“consumer 总能拿到 provider 源码并在本地对所有实例做全量单态化发码”作为唯一前提。
- 若后续引入单态化发码，它应只作为优化项：在编译器能直接看见泛型定义源码、并且收益明确的场景下，按需为部分实例生成专门实现。
- 若启用单态化发码，发码仍必须为这些专门实例生成稳定且不冲突的内部名字，并保证它与非单态主路径共存，不改变跨包消费前提。
- 泛型 `type` 若在某个具体实例下变成受管对象类型，则无论走非单态主路径还是单态化优化路径，发码都必须产出与实际字段替换结果一致的类型描述、引用枚举信息和默认零值/销毁辅助逻辑。

### 9.6 分阶段交付建议

- 第一阶段：先交付非单态泛型主路径，覆盖声明解析、语义检查、跨包导出/导入和基础发码闭环，不处理单态化发码。
- 第二阶段：在第一阶段稳定后，再把单态化发码作为编译器优化项增量引入，仅对可见源码场景按需启用。

### 9.7 运行时

- 运行时不得承担“泛型名字解析”“泛型重载选择”或“根据类型实参动态搜索实现”这类工作；这些都应在编译期完成。
- 非单态主路径下，运行时只消费编译期已经安排好的共享实现入口、类型描述、字典或其他辅助对象，不负责重新做泛型决议。
- 若后续启用实例化发码优化，运行时通常也无需理解“泛型语法”本身，只需要处理发码后得到的具体类型、具体函数和具体类型描述。
- 若泛型实例生成新的受管对象布局，运行时只需要消费与该具体实例对应的类型描述和托管字段枚举结果，不应在运行期反推类型参数。
- 二进制分发场景下，运行时至多只消费编译期已经导出的泛型辅助入口、类型描述或字典对象；不得要求 provider 源码在运行期或 consumer 编译期重新出现。
- 只有当最终 lowering 方案显式要求类型描述、字典或 witness 在运行时随值传递时，运行时才需要承载这些额外对象；即便如此，运行时也只负责消费编译期已经选定的结果，不负责重新决议。
