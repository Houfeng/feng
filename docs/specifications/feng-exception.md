# Feng 语言异常模型规范

本文档用于补充 [feng-language.md](./feng-language.md) 中的异常处理概要说明,聚焦 Feng 语言中的 `throw`、异常传播、`try/catch` 表达式与 C ABI 边界规则。

> **设计原则基础**: `extern func` 自身的无函数体约束属于语法层; `@abi` 边界上的异常限制属于语义与代码生成层。详见 [Feng 语言设计原则](./feng-principles.md)。

## 1 异常模型概览

- Feng 支持结构化异常处理,使用 `throw` 触发异常,使用 `try/catch` 处理异常。
- `try` 后只能是表达式,不能是语句块。
- 异常沿调用栈向外传播,直到被最近的 `catch` 捕获。
- 每个 `try` 至少包含一个 `catch` 子句；普通调用产生但未被当前函数捕获的异常自动继续向上传播。
- 异常不能跨越 C ABI 边界传播。

## 2 `throw` 语句

`throw 表达式;` 用于显式抛出新的异常值；无参数的 `throw;` 用于在匿名 `catch` 中原样重抛。

规则说明:

- 带参数的 `throw` 后必须跟一个非 `void` 表达式。
- 带参数的 `throw` 语句通常以分号结束；当它是 `if`、`match` 或 `try` 表达式的分支块中最后一条语句时，末尾分号可加可不加。无参数形式写作 `throw;`，必须有分号。
- 对具体静态类型，`throw` 与带具体类型的 `catch ex: Type` 共用 §3.3 定义的有限异常载荷类型集合。
- 直接泛参 E 具有[泛型主规范 §4.3](./feng-generics-draft.md#43-内建-throw-约束)的 `throw` 约束时，可以抛出 E 的值；异常仍携带实际具体类型和值，并按实际类型适用 §3.3 的精确匹配和 §4.1 的生命周期规则。
- 无约束或仅有 spec 约束的直接泛参不能抛出；`Box<E>` 等在当前可用替换后仍含开放泛参的复合类型也不能因 E 具有该约束而抛出。
- 无参数的 `throw;` 所在的最近一层 catch 必须是当前函数、方法或 Lambda 内的匿名 `catch { ... }`，普通嵌套块不改变该归属；具名 `catch ex: Type` 与新的 callable 边界不能继承外层匿名 catch 的重抛权限。
- `throw;` 原样重抛该匿名 catch 捕获的异常，保留异常对象、具体类型和值，不创建新的异常载荷；带参数的 `throw` 保持原有规则。
- 在 catch 中执行的嵌套异常处理（包括被调用 callable 内的处理）结束后，仍然活跃的外层 catch 恢复其原异常上下文；随后合法的 `throw;` 重抛外层原异常，而非已经处理完毕的内层异常。
- `defer` 块中的限制仍遵循 [defer 规范](./feng-defer.md#4-defer-块内的语句限制)，无参数形式不例外。
- `throw` 会终止当前执行路径,其后的同级语句不可达。

```feng
func ensure_positive(x: int) {
    if x < 0 {
        throw "x must be positive";
    }
}
```

## 3 `try/catch`

### 3.1 `try/catch` 用法

作为普通语句使用

```feng

// 常规语句
try foo() catch ex: string {
  puts(ex);
} catch { // 兜底 catch 子句
  puts("unknown error");
  return; // 作为语句时，使用 return 结束函数
}

// 匿名 catch，不建立异常值绑定
try foo() catch {
  // 这里不能访问 ex，因为 ex 没有绑定，也就不存在 ex
  puts("unknown error");
}

```

作为表达式使用

```feng

// 常规表达式
let x = try foo() catch ex: string {
  puts(ex);
  // 作为表达式时，最后一个表达式作为 catch 块的求值结果（可带可不带分号，与 if 表达式一致）
  // 正常执行到块末时必须有结果；return 会直接返回所属 callable
  // 正常结果的类型按流程控制规范的统一分支规则确定
  123; 
};

// 匿名 catch，不建立异常值绑定
let x = try foo() catch {
  // 这里不能访问 ex，因为 ex 没有绑定，也就不存在 ex
  puts("unknown error");
  // 作为表达式时，最后一个表达式作为 catch 块的求值结果（可带可不带分号，与 if 表达式一致）
  // 正常执行到块末时必须有结果；return 会直接返回所属 callable
  // 正常结果的类型按流程控制规范的统一分支规则确定
  123;  
};

```

### 3.2 `try`

- `try` 用于求值一个可能抛出异常的表达式。
- 语法形态: `try <expr> (catch [ex: Type] { ... })+`，后必须附加至少一个 `catch` 子句；各子句可为绑定形式 `catch ex: Type { ... }` 或匿名形式 `catch { ... }`。
- `try` 后只能是单个表达式,不允许 `try { ... }` 语句块形态。

### 3.3 `catch`

- `catch` 捕获从对应 `try` 表达式或其内部调用链抛出的异常。
- `catch` 有两种形式：
  - **绑定形式** `catch ex: Type { ... }`：将捕获的异常值以不可变绑定方式绑定到 `ex`，类型注解必须显式给出，不可省略。
  - **匿名形式** `catch { ... }`：不绑定异常值，无需类型注解；body 内不可访问被捕获的异常值，但可按 §2 使用 `throw;` 原样重抛，或 `throw` 任意合法值作为新异常。
- 支持多个 `catch` 子句，按书写顺序逐一尝试匹配，第一个匹配成功的子句生效，后续子句不再执行。
- 带具体类型注解的 `catch ex: Type` 仅在抛出值的精确具体类型身份与 `Type` 一致时匹配；不按字段布局、
  底层标量、父类型或其他结构兼容关系匹配。
- 匿名 `catch { ... }` 匹配任意类型的抛出值，必须置于所有具体类型子句之后，后面不能再有 catch 子句。
- 每个 `catch` 子句独立匹配一个类型，不支持在单个子句内列举多个类型。
- 每个绑定形式 `catch` 都有独立的子句头部作用域,异常名称声明在该作用域中; 紧随的花括号 body
  是其子级块,可以按变量绑定规范合法屏蔽异常名称。不同 `catch` 子句的头部作用域彼此独立,
  可以复用同一异常名称。
- `catch` 块中可执行常规语句；继续上抛的形式遵循 §2。
- `throw` 与具体类型 `catch` 允许以下静态类型：
  - `bool`；
  - 数值标量 `i8`、`i16`、`i32`、`i64`、`u8`、`u16`、`u32`、`u64`、`f32`、`f64`；
  - `string`；
  - 具名 `enum`；
  - 普通实体 `type` 与具名 tuple；
  - `@value type`；
  - 上述用户类型的闭合泛型实例，即完成类型实参替换后不再包含开放类型参数的具体类型；
  - 普通 `@abi type` 与 `@value @abi type`。`@abi` 只增加 C ABI 投影，不抹除 Feng 类型身份，且不
    改变 §5 的异常边界规则。
- 对具体载荷，`throw` 与具体类型 `catch` 一律拒绝以下静态类型：
  - array；当前数组实例共享对象类型身份，不能仅按精确具体数组类型进行无额外运行时工作的匹配；
  - object-form、intersection-form、union-form 与 callable-form 在内的所有 `spec`；
  - 完成当前可用替换后仍包含开放类型参数的复合类型；
  - pointer 与 `void`；
  - 函数值、函数类型、lambda 与成员方法等 callable 值。
- `catch ex: E` 始终不允许使用直接泛参，即使 E 具有 `throw` 约束也不例外。直接泛参用于 throw 的规则见 §2。
- array 或 `spec` 即使在运行时携带元素信息、subject 或 witness，也不得在异常匹配阶段读取这些实例数据
  以推断类型。若需抛出实现某个 `spec` 的对象或联合成员，应在具体静态类型可见时抛出该具体值。
- 具名类型采用名义精确匹配：不同具名 enum 即使底层值相同也不匹配，enum 与其底层整数不匹配；不同
  具名 tuple 或 `@value type` 即使布局相同也不匹配；闭合泛型实例按完整类型实参区分。

### 3.4 语句用法与表达式用法

`try/catch` 可作为独立**语句**或赋值右侧**表达式**使用，两种用法下 `catch` 块的求值与控制流规则不同，参照 `if` 语句与 `if` 表达式的区别。

**作为语句使用时：**

- `try/catch` 语句以最后一个 `catch` 块的 `}` 结束，末尾不得添加分号，与 `if`、`match`、`while` 和 `for` 等花括号控制流语句保持一致。
- `catch` 块可执行任意语句，无需以结果表达式结束。
- 可使用 `return <value>;` 提前退出当前函数。
- 可使用 `throw <expr>;` 终止当前路径并继续上抛。

**作为表达式使用时（出现在赋值右值或需要求值的位置）：**

- 每个存在正常完成路径的 `catch` 块必须以可达结果表达式结束（块中最后一个表达式作为求值结果，
  可带可不带分号，与 `if` 表达式一致）。
- 结果分支中的 `return` 控制转移边界统一遵循
  [Feng 语言流程控制规范 §4.1](./feng-flow.md#41-if--match--try-%E8%A1%A8%E8%BE%BE%E5%BC%8F%E7%BB%93%E6%9E%9C%E7%B1%BB%E5%9E%8B)，
  不在异常规范中另行定义一套规则。
- `try` 主表达式与各 `catch` 块的结果类型按 [Feng 语言流程控制规范 §4.1](./feng-flow.md#41-if--match--try-%E8%A1%A8%E8%BE%BE%E5%BC%8F%E7%BB%93%E6%9E%9C%E7%B1%BB%E5%9E%8B)统一选择目标类型并贴合。
- 若 catch 内的路径返回所属 callable，或通过 `throw <expr>;` 逃逸当前 `try/catch`，则该路径无需
  提供结果表达式；被 catch 内部的嵌套 `try/catch` 捕获并正常继续的异常路径不属于逃逸路径。
- 当 `try` 主表达式结果类型为 `void` 时，`catch` 块可以只执行语句并正常结束，不需要结果表达式。
- 若表达式上下文提供目标类型，则 `try` 主表达式结果与各 `catch` 块结果都必须分别符合该目标类型。

### 3.5 `if`/`match` 表达式分支中的异常路径

`if` 表达式和 `match` 表达式的各分支块允许通过 `throw` 逃逸，与 `try/catch` 表达式的 catch 子句
结果规则一致。路径级结果判定统一由流程控制规范定义，本文只说明异常行为。

- 通过 `throw` 逃逸的路径不产生结果值，也不参与结果类型推导和一致性比较。
- 若同一结果块的其他路径能够正常完成，则这些路径仍须到达块末结果表达式。
- 嵌套控制结构的全部路径均逃逸时，不要求外层结果块再提供一个不可达结果表达式。
- `throw` 后的不可达末尾表达式不构成分支结果，也不参与类型推导。

```feng
let x = if cond {
  throw "error";
} else {
  42;
};

let label = if value {
  0 { "zero"; }
  1 { throw "unexpected one"; }
  else { "other"; }
};
```

## 4 异常传播规则

- 未被当前函数处理的异常会继续向调用方传播。
- 若异常传播到程序入口 `main` 仍未被捕获,程序立即以异常失败状态结束。
- 对于 `try/catch` 表达式,`catch` 完成结果返回后,控制流从该表达式之后继续执行。
- 当前 `try/catch` 没有匹配当前异常的子句时，异常继续向外传播。

### 4.1 异常路径上的资源清理

- 异常沿调用栈传播时,栈上所有已经初始化、当前作用域可见的托管局部(由编译器与运行时共同管理引用计数的对象,例如字符串、数组、对象实例)必须被释放,等价于这些局部正常走完作用域。
- 释放顺序与正常退出相同:按声明的逆序逐个释放,且每个槽位释放后被置空,任何后续路径都不会重复释放。
- 抛出表达式自身的值在传递到 `catch` 之前持有 +1 引用;`catch` 块结束后由运行时释放该引用。`catch` 中再次执行 `throw <expr>;` 时,按新抛出值独立适用相同生命周期规则。
- 每个尚未退出的 catch 独立持有其异常；内部再次抛出或处理异常不能提前释放外层异常。正常落尾、`return`、合法的 `break` / `continue` 和异常传播均只清理实际离开的 catch，并在该 catch 的局部值与 `defer` 清理完成后结束其异常持有。
- 匿名重抛将原异常的持有转交给继续传播的路径；具名绑定被保存到 catch 外、作为结果返回或以 `throw <expr>;` 再次抛出时，先按普通值规则建立目标持有，再清理已退出的 catch。
- 任何被 `@abi` ABI 边界拦截或在程序入口外仍未被捕获的异常,在终止进程前同样要释放沿途所有可见的托管局部,以保证调试信息一致、不掩盖真实泄漏。

## 5 与 C ABI 的边界约束

- 异常不得穿过 `@abi` ABI 边界传播到 C 调用方。
- 用于 ABI 边界的顶层 `@abi func`（含回调函数来源,以及未来的公开导出 surface）均须确保内部异常在函数体内被捕获处理，不得向 C 调用方传播。
- 编译器在语义阶段对 `@abi` ABI 边界做静态异常传播分析：若用于 ABI 边界的顶层 `@abi func` 内存在可能未被捕获而到达函数出口的异常路径，编译期报错，而非依赖运行时检测。
- 若未捕获异常到达 `@abi` 的 ABI 边界,运行时直接终止当前进程,不得向 C 侧继续返回未定义状态。
- C ABI 路径下的 `extern func` 导入声明本身不向 Feng 异常系统抛出可捕获异常; 来自 C 的错误应通过返回值、错误码或显式回调约定传递。

## 6 编译期异常摘要

编译器为函数、方法、构造函数、终结器及 Lambda 记录可能逃出该 callable 的异常摘要。
摘要用于编译期边界检查和语言服务，不改变异常载荷、运行时传播协议或 ABI；普通调用
仍允许未捕获异常自动向上传播，不要求增加异常声明或显式处理语法。

- 直接抛出的异常按精确类型身份记录；普通条件分支保守取并集，不按值条件真假裁剪。
- 调用合并被调用者的对外摘要；参数、接收者、初始化及其他实际求值路径产生的异常也须计入。
- 开放泛参保留声明和槽位身份，调用点同时代入类型级与 callable 级实参。仍开放时继续转传，
  不能仅因尚未闭合就丢弃信息或将其视为无异常。
- 每个 `try/catch` 按 §3.3 的匹配规则，从自身保护范围扣除被捕获的异常，再合并可能执行的
  处理代码向外传播的异常；不能从整个函数摘要统一扣除所有 catch 类型。
- 兜底 catch 扣除保护范围传入的全部异常，包括未知来源。`throw expr` 按结果类型重新计入；
  `throw;` 按 §2 恢复当前匿名 catch 实际接收的剩余异常，不恢复已由前置具体 catch 处理的部分。
- 捕获及重抛依赖泛参时，保留类型筛选关系，在实参代入后求值。处理代码内的调用和嵌套捕获
  使用相同规则；普通分支中的重抛仍按可能发生记录。
- 无法确定的间接调用显式保留未知。未知、尚未完成分析和已证明为空是不同状态；递归求解
  未完成或元数据缺失不能解释为不抛异常。
- 创建、传递或返回 callable 值不等于执行该值；其调用依赖随值保留，实际调用时才计入异常。
- 跨包使用保留参数化摘要、精确类型身份、调用依赖及捕获条件，消费侧不需要依赖源码。
  产物格式及完整性要求由[符号表规范](./feng-symbol-table.md)定义。

§5 的 `@abi` 检查使用求解后的摘要：只有能证明边界没有逃逸异常时通过；已知异常、
未消除的开放依赖或未知部分均报错。边界内部的完整捕获可以消除这些部分，外围捕获不能
代替边界自身的证明。C ABI `extern func` 继续按 §5 的既有契约处理。

核心编译器记录异常摘要及调用点的异常事实，不感知编辑器或提示用途，也不为普通调用
生成异常传播提示。摘要计算包括类型代入、调用传播及 catch 筛选，不等同于要求处理异常。
严格边界使用摘要进行合法性检查；上层模块按自己的用途读取摘要。
异常元信息以结构化形式提供：保留参数化推导模板和已求解的声明／调用结果，不保存诊断正文、
未知原因说明或预格式化的类型列表。`unknown` 使用结构化标记；泛型代入及 catch 筛选条件
仍保留。LSP 和边界检查分别消费这份元信息，按需生成展示文本或诊断，不将文本写回元信息。

语言服务仅在函数／方法及调用点的 Hover 中展示可能的异常类型列表；泛型声明保留开放
类型参数，具体调用使用代入后的结果。未知项显示为 `unknown`，列表去重，不展示未知原因、
条件说明或处理建议。已证明没有可能异常时，不增加异常 Hover 条目。调用点 Hover 展示
被调用者可能抛出的类型，不因调用外层已经捕获而隐藏；外围函数自身的摘要仍按 catch 规则计算。
不再生成调用处的异常传播 Information；CLI 的编译、构建、打包及检查命令也不输出该提示。
原有其他诊断保持不变。普通调用不因可能传播异常而新增
编译错误，继续按原规则自动传播。提示是否展示不影响摘要计算：未知异常仍按上述规则
向上合并、跨包传递和接受 catch 筛选。严格证明用于 §5 的 `@abi` 边界，失败必须是
编译期错误，不以 Information 或 warning 代替；defer 限制仍由其主规范定义。
