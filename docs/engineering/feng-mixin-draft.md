# Feng `...` 成员展开设计草案

> **状态**：讨论草案，尚未进入语言规范，尚未实现。
>
> 本文用于方案评审与后续推敲。评审通过前，不修改
> `docs/specifications/` 中的正式规范，也不据此实现编译器或标准库。

## 1 背景

Feng 当前没有继承，也没有增加继承的计划。retained-mode GUI/TUI 组件通常需要
重复声明一组公共状态，例如样式、布局结果、父子关系和事件绑定，同时只在少量行为
上存在差异。

仅增加类似 Rust trait 的 `spec` 默认实现只能复用行为，不能复用实体字段。直接
转发具体类型的实例方法又会产生接收者语义问题：来源实例方法中的 `self` 是来源
类型，不能安全地动态重绑定为具有不同内存布局的目标类型。

本草案提出 `...` 成员展开语法：目标类型显式选择一个来源类型，编译器在前端早期
生成普通字段和普通 wrapper 方法，之后完全复用现有成员、初始化、重载、`spec`
满足、方法值、代码生成和运行时机制。

本方案不使用 `@mixin` 或 `@mixable`。来源类型不需要额外授权标记，其符合规则的
公开成员均参与展开。

## 2 核心语义原则

本方案的核心原则是：

> `...` 先生成等价的手写字段和 wrapper 方法，再由 Feng 现有规则处理；除明确列出
> 的两项生成规则外，不增加展开专用语义或检查。

这意味着：

- 生成字段是目标类型自己的普通字段，不是来源字段的转发或别名；
- 生成 wrapper 是普通方法，只执行普通的来源静态方法调用；
- 生成成员使用现有可见性、冲突、重载、泛型、`spec`、方法值和代码生成规则；
- 生成字段和 wrapper 与显式手写成员一起参与现有 `spec` 满足检查；
- 编译器不复制具体实例方法的方法体；
- 编译器不重绑定来源实例方法的 `self`；
- 编译器不引入新的方法分派机制；
- 编译器不为生成成员增加手写成员不存在的运行时行为。

两项生成专用规则是：

1. 如果目标类型显式定义的成员与待生成成员冲突，则不生成该成员；是否冲突完全使用
   Feng 现有字段级和方法级成员冲突规则，不另行定义冲突签名或优先级规则。
2. 公开静态方法只有在首参数是 object-form `spec`，且目标类型按现有名义关系声明
   满足该 `spec` 时，才额外生成去掉首参数的实例 wrapper。

除此之外，循环、泛型、初始化、成员顺序、可见性、`fit`、annotation、跨包恢复及
其他合法性均使用等价手写声明原本适用的现有规则；不为 `...` 重复建立检查。

## 3 设计目标

1. 复用公开类型已经定义的实例字段和静态字段。
2. 通过普通静态调用 wrapper 复用安全的公共行为。
3. 不要求来源成员逐个添加 `@mixable` 一类的授权标记。
4. 使展开结果除两项生成专用规则外均等价于手写代码。
5. 在前端早期回到现有 AST、语义分析和代码生成主路径。
6. 支持 `.ft` + 静态库形式的跨包二进制分发，不要求 `.ft` 携带函数体或字段初始
   绑定表达式。
7. 实例字段在目标类型中具有独立存储，热路径成员访问不经过来源实例。
8. 机制不依赖 GUI/TUI，可用于其他需要成员组合的类型。

## 4 非目标

本草案不提供：

- 继承或子类关系；
- 来源类型到目标类型的实体子类型转换；
- 具体实例方法的方法体复制；
- 将来源实例方法的 `self` 重绑定为目标实例；
- Go 风格的具体实例方法自动提升；
- 运行时动态添加或删除成员；
- 来源字段与目标字段之间的长期绑定或同步；
- 来源静态字段与目标静态字段之间的别名关系；
- 用户自定义 `...` 展开算法；
- 独立于现有成员规则的覆盖、重载或动态分派体系。

## 5 语法

### 5.1 完整写法

```feng
type Button {
  ...: View = View(...);
}
```

`View` 是来源类型，`View(...)` 是实例来源对象构造表达式。等号右侧只允许 Feng
现有对象构造表达式，不允许变量引用、成员访问、函数调用结果、条件表达式或其他任意
值表达式。构造结果类型必须与显式来源类型一致。每次构造一个 `Button` 时，该构造
表达式求值一次，其结果用于初始化展开得到的实例字段。

### 5.2 使用来源类型的默认零值

```feng
type Button {
  ...: View;
}
```

该形式使用 `View` 的默认零值作为实例来源值，不执行 `View` 构造函数。

### 5.3 自动推导来源类型

```feng
type Button {
  ... = View(...);
}
```

来源类型由等号右侧对象构造表达式直接确定。该形式同样只允许 Feng 现有对象构造
表达式，不接受其他任意值表达式。

### 5.4 泛型来源

`...` 位于目标类型体内，按普通类型成员作用域解析名称，因此可以直接引用目标类型
的泛型参数：

```feng
type Button<T> {
  ...: View<T> = View<T>(...);
}
```

这里不需要为 annotation 增加向后引用目标泛型参数的特殊作用域规则。来源类型实参
及实例来源对象构造表达式均按现有泛型名称查找、实参替换、构造匹配和约束检查规则
处理。

## 6 参与展开的来源成员

来源类型中符合以下种类且在目标位置公开可见的成员参与展开：

| 来源声明 | 目标中生成的成员 |
| --- | --- |
| 公开实例 `let` / `var` | 同名普通实例字段 |
| 公开静态 `let` / `var` | 同名普通静态字段 |
| 公开静态方法 | 同名普通静态 wrapper |
| 首参数为对象 `spec` 且目标名义声明该 `spec` 的公开静态方法 | 额外生成去掉首参数的同名普通实例 wrapper |

以下成员不参与展开：

- 在目标位置不可见的成员；
- 具体实例方法；
- 构造函数；
- 终结器；
- 不属于上述表格的其他声明。

“所有公开成员参与展开”是指上述可安全展开的成员种类不再需要逐个标注
`@mixable`，并不表示复制具体实例方法的方法体。

来源成员的查找、可见性、泛型替换、`fit` 可见关系及声明合法性全部使用目标位置原本
适用的现有规则。编译器不为 `...` 建立另一套“来源成员面”；等价手写代码在该位置
能够使用的公开成员，才是可参与生成的成员。

## 7 实例字段展开

### 7.1 基本语义

来源声明：

```feng
open type View {
  open let style: WidgetStyle;
  open var parent: Option<Widget>;
}
```

目标声明：

```feng
type Button {
  ...: View = View(...);
  let text: string;
}
```

生成字段在语义上等价于：

```feng
type Button {
  open let style: WidgetStyle;
  open var parent: Option<Widget>;
  let text: string;
}
```

每次构造 `Button` 时，初始化过程等价于：

```text
let source = View(...);
self.style = source.style;
self.parent = source.parent;
```

实例来源对象构造表达式只求值一次，不能为每个字段分别求值。字段值读取完成后，临时
来源值按现有生命周期规则处理。

### 7.2 字段声明事实

生成字段复制来源字段的以下声明级事实：

- 名称；
- 类型；
- `let` / `var` 可变性；
- 可见性。

来源字段的初始绑定表达式不复制到目标字段。目标字段的值来自构造完成的实例来源值
或来源类型默认零值。

### 7.3 值语义

从来源值读取成员并绑定到目标字段时，完全采用普通成员读取、初始化和赋值规则：

- 值类型成员按现有值语义复制；
- 引用类型成员按现有引用语义绑定；
- callable 成员按现有 callable 值语义绑定；
- 不建立来源字段槽位与目标字段槽位之间的后续关联。

如果某个字段值内部保留了来源实例，例如 Lambda 捕获了来源实例，该值继续按普通
引用语义保留来源实例。`...` 不修改该值内部已经形成的绑定。

### 7.4 构造归一化

实例字段及其绑定归入 Feng 现有“成员声明及绑定初值”构造阶段，不引入新的构造
前置阶段。编译器可在该阶段生成一个不可见的普通临时绑定，以保证同一个 `...` 的
实例来源对象构造表达式只求值一次，然后使用该值完成生成字段的普通绑定。

生成的 `let` / `var`、多个 `...`、目标显式字段、构造函数和对象字面量继续使用现有
构造顺序、绑定状态和重复绑定检查。若等价手写代码不合法，后续现有检查自然报错，
`...` 不增加构造专用诊断或绑定状态。

## 8 静态字段展开

来源声明：

```feng
open type View {
  open static let defaultWidth: u32 = 10;
  open static var createdCount: u32 = 0;
}
```

目标声明：

```feng
type Button {
  ...: View;
}
```

概念展开结果：

```feng
type Button {
  open static let defaultWidth: u32 = View.defaultWidth;
  open static var createdCount: u32 = View.createdCount;
}
```

目标静态字段具有独立存储，不是来源静态字段的别名。初始化表达式读取来源静态字段，
之后来源与目标的静态 `var` 可以独立变化。初始化时机、读取顺序和错误处理均使用
现有静态字段规则。

实例来源对象构造表达式不参与静态字段初始化；静态字段只由解析后的来源类型决定。

## 9 静态 wrapper

每个参与展开的公开静态方法都生成静态 wrapper。

来源声明：

```feng
open type View {
  open static func createStyle(): WidgetStyle {
    return WidgetStyle {};
  }
}
```

概念展开结果：

```feng
type Button {
  open static func createStyle(): WidgetStyle {
    return View.createStyle();
  }
}
```

生成的静态 wrapper：

- 使用来源静态方法的名称、泛型参数、普通参数、返回类型和可见性；
- 方法体只执行对来源静态方法的完整限定普通静态调用；
- `void` 返回方法生成普通调用语句，非 `void` 返回方法返回调用结果；
- 不复制来源方法体；
- 不重写来源方法内部对来源类型静态成员的访问。

如果来源静态方法内部修改 `View.createdCount`，通过 `Button` 的静态 wrapper 调用后
修改的仍是 `View.createdCount`，不是独立的 `Button.createdCount`。这与用户手写
`Button.method() { View.method(); }` 的行为相同。

## 10 实例 wrapper

### 10.1 生成条件

公开静态方法满足以下全部条件时，除静态 wrapper 外，同时生成实例 wrapper：

1. 至少有一个参数；
2. 第一个参数的声明类型是对象形式的 `spec`；
3. 目标类型名义声明该 `spec`。

不满足这些条件时，只生成静态 wrapper，不生成实例 wrapper，也不因为缺少实例
wrapper 而产生错误。

展开阶段只检查目标类型声明头中是否存在相应的名义 `spec` 声明，按现有类型名称
解析、泛型实参替换和类型等价规则比较，不在此阶段遍历目标成员验证实际满足关系。

实例 wrapper 生成后，与生成字段、其他生成 wrapper 和目标显式成员一起进入同一个
普通可见成员面。后续现有 `spec` 检查负责验证目标是否真正满足其声明的 `spec`；
所有生成成员均可像手写成员一样参与该检查。若最终不满足，产生现有 `spec` 诊断，
不得在展开阶段静默移除 wrapper，也不需要候选成员固定点或另一套满足算法。

### 10.2 生成结果

来源声明：

```feng
open type View {
  open static func addChild(widget: Widget, child: Widget): void {
    widget.children.add(child);
  }
}
```

当 `Button` 名义声明 `Widget` 时，概念展开结果为：

```feng
type Button {
  open static func addChild(widget: Widget, child: Widget): void {
    View.addChild(widget, child);
  }

  open func addChild(child: Widget): void {
    View.addChild(self, child);
  }
}
```

生成的实例 wrapper：

- 名称与来源静态方法相同；
- 删除来源静态方法的第一个参数；
- 保持其余参数、泛型参数、返回类型和可见性；
- 将目标实例 `self` 作为来源静态方法的第一个普通实参；
- 其余实参按原顺序转发；
- 不复制来源静态方法体；
- 不引入来源实例或动态 `self` 重绑定。

生成后，实例 wrapper 是目标类型的普通实例方法。方法值、`spec` witness、调用和
代码生成均按现有普通实例方法规则处理。

## 11 `a` 调用 `b` 的行为

静态方法形式可以支持传统模板方法的一部分使用场景，具体行为由来源方法中的调用
表达式决定。

```feng
open spec WidgetBehavior {
  func b(): void;
}

open type View {
  open static func a(widget: WidgetBehavior): void {
    widget.b();
  }
}

type Button: WidgetBehavior {
  ...: View;

  func b(): void {
    // Button 的实现
  }
}
```

当 `Button` 名义声明 `WidgetBehavior` 时，`View.a` 同时生成静态 wrapper
和实例 wrapper。生成成员进入普通成员面后，现有检查再验证 `Button` 是否真正满足
`WidgetBehavior`。调用链为：

```text
button.a()
  → View.a(button)
  → widget.b()
  → 通过 WidgetBehavior witness 调用 Button.b()
```

如果来源静态方法写成完整限定静态调用 `View.b(widget)`，该调用仍然固定调用
`View.b`，不会动态选择 `Button.b()`。编译器不重写来源方法体，因此两种行为与
手写代码完全一致。

为避免 Go 内嵌方法中 `a` 固定调用来源 `b` 的问题，需要动态选择目标实现的相关
方法应声明在首参数的对象 `spec` 中，来源静态方法应通过该参数的 `spec` 视角调用：

```feng
widget.b();
```

此时现有 `spec` witness 会选择目标实现。完整限定的来源静态调用表示设计者明确要求
固定调用来源实现，不具有开放调用语义。这一差异直接体现在调用表达式中，不依赖
隐藏的虚方法规则。

如果来源静态方法还可生成默认实例 `b` wrapper，而目标显式定义了与其冲突的
`b`，则依据本草案唯一的特殊冲突规则，跳过生成该实例 `b` wrapper。来源 `a`
通过 `WidgetBehavior` 调用时会使用目标显式定义的 `Button.b()`。

## 12 显式成员优先与冲突

### 12.1 目标显式成员优先

如果目标类型显式定义的成员与某个待生成成员冲突，则跳过该生成成员：

```feng
type Button {
  ...: View;

  func draw(area: Area): void {
    // 显式定义优先，不生成与其冲突的 wrapper。
  }
}
```

“冲突”完全复用当前语言已有规则：

- 字段是否冲突使用现有字段级冲突规则；
- 方法是否冲突使用现有方法级冲突规则；
- 静态成员与实例成员是否处于同一冲突面，使用现有规则；
- 字段与方法是否冲突，使用现有规则；
- 合法重载仍按现有重载规则处理。

本草案不另行规定“按名称跳过”“按完整签名跳过”或其他 mixin 专用判断。

### 12.2 生成成员之间的冲突

目标显式成员优先是唯一特殊冲突行为。两个不同 `...` 产生的生成成员之间没有隐式
先后优先级：它们进入同一个普通成员集合，之后按现有成员冲突规则处理。若等价的
手写成员会产生冲突，则生成成员也产生相同冲突。

编译器不得采用“第一个来源获胜”或“最后一个来源获胜”的静默顺序规则。

### 12.3 其他错误

除显式成员冲突导致跳过生成外，生成成员不获得错误豁免。来源调用参数不匹配、泛型
约束不满足、生成后的普通表达式不合法等情况，均使用现有诊断。

诊断应同时指出目标的 `...` 位置和对应来源成员，以便用户理解生成来源。

## 13 可见性与传递展开

`...` 访问来源类型和来源成员时遵循现有可见性规则：

- 跨包来源类型必须在目标位置可见；
- 只有在目标位置公开可见且属于 §6 所列种类的成员参与展开；
- 私有声明不能通过 `...` 变成 consumer 可访问成员；
- 生成成员使用来源成员的可见性；
- wrapper 对来源静态方法的调用仍执行普通可见性检查。

由于不再存在 `@mixable` 标记，目标导出的生成成员也是普通公开成员。其他类型以后
将该目标作为来源时，这些公开生成成员可以继续参与展开；这种传递性是“公开成员均
可展开”和“生成后等价于普通手写成员”的直接结果。

## 14 跨包与 `.ft`

### 14.1 跨包成立条件

本方案不要求 `.ft` 携带来源字段的初始绑定表达式或来源静态方法体：

- `...: View` 使用来源类型默认零值；
- `...: View = View(...)` 通过公开构造入口创建完整来源值；
- 实例字段值通过普通公开成员读取；
- 静态字段初值通过普通外部静态字段访问取得；
- wrapper 只调用静态库中已有的来源静态方法符号。

consumer 只需要 `.ft` 中现有的公开声明级事实和静态库链接符号。由于所有符合种类
的公开成员都参与展开，`.ft` 不需要新增 `@mixable` 标记或 mixin 模式。

同包声明与 `.ft` 恢复声明必须向现有成员查询提供一致的普通声明事实和顺序。该要求
属于 `.ft` 原有的声明恢复正确性，不形成 `...` 专用的成员顺序或跨包语义。

### 14.2 目标包导出

目标包在导出前已经完成 `...` 展开，因此目标 `.ft` 导出生成后的普通字段和普通
方法声明。consumer 使用目标类型时不需要重新执行目标原始声明中的 `...`。

是否在 `.ft` 中额外保留 `...` 的来源位置只影响 IDE 展示和诊断来源映射，不影响
正确链接和使用目标类型。

### 14.3 包兼容性

来源类型增加、删除或修改符合规则的公开成员，会改变下游重新编译后的目标成员集合，
可能改变对象布局、重载集合或产生新的生成成员冲突，应视为公开源码/API 兼容性
变化。已经编译完成的目标静态库不会在未重新编译时自动改变。

## 15 编译器归一化

建议的前端顺序为：

```text
Lex / Parse
  → 加载并恢复外部 .ft 公开声明
  → 解析 ... 的来源类型或来源表达式静态类型
  → 收集符合种类的公开可见来源成员
  → 根据现有规则跳过与目标显式成员冲突的生成成员
  → 根据目标声明头的名义 spec 关系生成条件实例 wrapper
  → 生成普通字段、静态 wrapper 和现有成员初始化阶段中的普通绑定
  → 建立普通成员表
  → 使用包含所有生成成员的普通成员表执行现有 spec 检查和其他语义分析
  → 执行现有代码生成
```

`...` 需要来源表达式的静态类型、目标的普通成员信息及目标声明头中的名义 `spec`
关系，因此不是纯 Token 变换。但展开应尽早完成，使后续阶段只看到普通成员。

除两项生成专用规则外，归一化不得改变生成代码相对于等价手写代码的含义。循环、
泛型、初始化、顺序、可见性、`fit`、annotation、跨包声明及其他合法性继续由现有
机制处理，不增加同义或重复检查。

## 16 性能模型

实例字段展开把额外成本放在构造阶段：

- 显式实例来源对象构造表达式每个目标实例求值一次；
- 来源为普通引用类型时，可能临时创建一个来源对象；
- 编译器按普通值语义读取并绑定公开实例字段；
- 绑定完成后释放临时来源引用；若字段值保留来源实例，该实例按普通引用语义存活；
- 静态字段继续使用现有静态初始化机制，不产生每实例成本。

稳定运行阶段不存在来源对象转发：

- 生成字段直接进入目标对象布局；
- 字段访问与手写字段相同，不增加间接访问；
- 目标对象不为展开额外保存隐藏来源引用；
- wrapper 只增加普通静态方法调用，行为与手写 wrapper 相同。

正式实现前仍需通过基准确认构造成本、临时分配、引用计数操作和热路径收益。任何会
扩大运行时开销的实现选择均需单独评审。

## 17 语法范围

带等号的 `...` 只允许使用 Feng 现有对象构造表达式作为实例来源，不允许推广为
任意能够产生来源类型值的表达式。构造器匹配、泛型类型实参、对象字面量初始化及
构造表达式合法性全部使用现有规则。

成员顺序、`fit`、annotation、跨包恢复、循环、泛型、初始化与普通诊断均不属于
`...` 的独立语义，统一沿用等价手写代码适用的现有规则。调试信息、LSP 来源展示和
兼容性提示属于实现与工具体验，不改变语言语义。

## 19 当前结论

当前候选方案可以概括为：

```text
目标类型中的 ...: Source / ...: Source = expression / ... = expression
  ↓
收集来源中符合种类的公开成员
  ↓
跳过与目标显式成员冲突的待生成成员
  ↓
普通实例字段 + 普通静态字段 + 普通静态 wrapper
  + 首参数为对象 spec 且目标名义声明该 spec 时的普通实例 wrapper
  ↓
现有成员、初始化、冲突、重载、spec、方法值、代码生成和运行时机制
```

核心边界是：

- 不需要 `@mixin` 或 `@mixable`；
- 公开实例字段生成独立目标存储，不转发；
- 公开静态字段生成独立目标静态存储，不建立别名；
- 所有公开静态方法生成普通静态 wrapper；
- 首参数为对象 `spec` 且目标名义声明该 `spec` 时，同时生成去掉首参数的实例
  wrapper；
- 所有生成成员与显式成员一起参与后续现有 `spec` 满足检查；
- 具体实例方法永不复制或提升；
- 目标显式成员冲突时按现有冲突规则跳过生成；
- 除显式成员冲突跳过和实例 wrapper 的名义 `spec` 生成条件外，生成结果与手写展开
  无差别。

该方案是否进入正式语言规范，等待后续评审决定。
