# Feng `...` 成员展开与 `@mixable` 行为复用设计草案

> **状态**：讨论草案，尚未进入语言规范，尚未实现成员展开与 `@mixable`。
>
> 调用实参位置的 `...args` 预打包变参数组转发已经作为独立语言能力完成，不属于
> 本草案尚未实现的部分。

## 1 背景

Feng 没有继承，也没有增加继承的计划。retained-mode GUI/TUI 组件通常同时需要：

- 复用样式、布局结果、父子关系和事件绑定等实例状态；
- 复用绘制、布局和事件处理等公共行为；
- 通过统一组件契约进行多态调用。

仅使用 `spec` 可以表达多态和行为契约，但不能复用实体字段。Go 风格内嵌会在目标中
保留额外来源对象，并容易让用户误解来源方法内部的 receiver 调用是否会选择目标
实现。复制实例方法体或把来源方法的 `self` 重绑定到目标，又无法保证不同对象布局下
的内存安全。

本草案将三个职责分开：

- 多态由现有 object-form `spec` 和 witness 机制实现；
- 结构复用由 `...` 展开公开实例字段实现；
- 行为复用由显式 `@mixable` 静态方法及普通 wrapper 实现。

成员展开不建立类型链、继承关系或来源类型到目标类型的转换。

## 2 核心原则

本方案遵循以下原则：

1. `...` 只生成等价的普通目标实例字段。
2. 实例方法、静态字段和未标注 `@mixable` 的静态方法均不展开。
3. `@mixable` 静态方法通过静态调用生成复用链，不复制方法体，也不重绑定来源方法的
   `self`。
4. 生成字段和 wrapper 尽早进入普通成员表，后续复用现有可见性、重载、冲突、泛型、
   `spec` 满足、方法值、构造、生命周期和代码生成规则。
5. 目标显式成员优先用于筛选字段和 mix 产生的静态 wrapper；最终保留的
   `@mixable` 静态方法必须无条件派生实例 wrapper，派生后由现有成员规则处理。
6. 不为目标实例保存隐藏来源对象、隐藏 base 字段、方法环境或运行时类型链。

## 3 设计目标

1. 低成本复用 GUI/TUI 组件的实例字段及其初始绑定状态。
2. 通过明确标注的静态方法复用行为，并提供普通实例方法的调用体验。
3. 允许目标显式覆盖行为，并通过完整限定静态调用复用来源行为。
4. 支持多层 mix，保证中间类型不会截断可复用行为。
5. 支持 `.ft` 与静态库形式的跨包二进制分发，不要求复制外部方法体或字段初始化器
   AST。
6. 稳定运行阶段的字段访问与手写字段一致，不增加来源对象间接访问。
7. 机制不依赖 GUI/TUI，可用于其他需要结构和行为组合的类型。

## 4 非目标

本草案不提供：

- 继承、子类关系或类型链；
- `instanceOf`、父类型转换或 `super` 隐式调用；
- Go 风格来源对象内嵌与实例方法提升；
- 来源实例方法的方法体复制；
- 来源方法 `self` 到目标实例的动态重绑定；
- 静态字段展开；
- 未显式标注的静态方法展开；
- 隐藏来源实例或来源实例的长期状态同步；
- 响应式属性、声明式 UI、元素树、diff、patch 或状态管理机制。

响应式更新、布局、事件传播和状态管理属于 GUI/TUI 框架层能力，与本方案正交。

## 5 类型关系与语法位置

Feng 的类型声明头保持现有含义：

```feng
type Button: Widget {
    ...: View;
}
```

`Widget` 必须是现有规则允许出现在声明头中的 object-form `spec`；`View` 是类型体中
显式选择的成员展开来源。

以下写法不表示成员展开，也不因本方案变为合法：

```feng
type Button: View {
}
```

具体 `type` 不能作为声明头中的父类型。展开 `View` 也不会使 `Button` 自动继承
`View` 声明的 `spec` 关系；`Button` 必须按现有规则显式声明自己需要满足的 `spec`。

## 6 实例字段展开语法

### 6.1 显式来源类型和构造表达式

```feng
type Button: Widget {
    ...: View = View();
}
```

`View` 是来源类型，右侧是实例来源对象构造表达式。等号右侧只允许 Feng 现有对象
构造表达式，不允许变量引用、成员访问、普通函数调用结果、条件表达式或其他任意
表达式。

### 6.2 来源类型默认零值

```feng
type Button: Widget {
    ...: View;
}
```

该形式只生成目标字段。每个生成字段直接按照自身类型执行现有默认零值初始化，不创建
完整的 `View` 默认零值临时实例，不执行 `View` 的字段初始化器、构造函数、对象字面量
阶段或终结逻辑。

### 6.3 自动推导来源类型

```feng
type Button: Widget {
    ... = View();
}
```

来源类型由右侧对象构造表达式直接确定。右侧同样只能是 Feng 现有对象构造表达式。

### 6.4 泛型来源

`...` 位于目标类型体内，来源类型和构造表达式按普通类型成员作用域解析，因此可以
引用目标类型的泛型参数：

```feng
type Panel<T> {
    ...: View<T> = View<T>();
}
```

来源泛型实参替换、构造匹配和约束检查完全使用现有泛型规则。

### 6.5 来源类型范围

来源必须解析到一个确定的具体 `type` 声明。允许 `View<T>` 这类已经确定来源声明的
泛型实例，不允许：

- 裸类型参数，例如 `...: T`；
- object-form、callable-form、union-form 或 intersection-form `spec`；
- `enum`；
- 内建类型；
- 数组。

## 7 参与展开的成员

来源成员面只包含：

1. 在目标位置公开可见的来源实例字段；
2. 在目标位置公开可见、显式标注 `@mixable` 的来源静态方法；
3. 在目标位置可见，并可通过普通 `Source.method(...)` 查找和调用、且显式标注
   `@mixable` 的公开 `fit Source` 静态扩展方法。

以下成员不参与展开：

- 来源实例方法；
- 来源静态字段；
- 未标注 `@mixable` 的来源静态方法；
- `fit Source` 实例方法；
- 私有或在目标位置不可见的声明。

不展开静态字段是一项有意的语义边界。来源静态方法中的完整限定静态字段访问始终
指向来源类型。如果同时给目标复制一份静态字段，用户容易误认为修改目标静态字段会
影响来源静态方法，实际却不会。完全排除静态字段可以避免形成两份静态状态及类似
Go receiver 的理解偏差。

## 8 实例字段生成

### 8.1 字段声明事实

每个参与展开的来源实例字段生成一个目标自身的普通实例字段，并保留：

- 名称；
- 类型；
- `let` / `var` 可变性；
- 可见性。

来源字段的初始化器 AST 不复制到目标字段。生成字段不是来源字段的别名，也不通过
来源对象进行运行时转发。

### 8.2 默认零值形式

对于：

```feng
type Button: Widget {
    ...: View;
}
```

概念结果与直接手写来源公开实例字段相同：

```feng
type Button: Widget {
    open let style: WidgetStyle;
    open var parent: Option<Widget>;
}
```

每个字段直接使用自身类型的默认零值。生成的 `let` 保持未显式绑定状态，之后仍可在
目标构造函数或目标对象字面量阶段完成首次显式绑定。生成的 `var` 得到字段类型的默认
零值。

该形式不创建完整来源实例，因此不产生额外来源对象分配、释放、引用计数或终结器
行为。

### 8.3 显式来源构造

来源声明：

```feng
open type View {
    open let style: WidgetStyle = WidgetStyle {};
    open let tag: string;
    open var parent: Option<Widget>;
}
```

目标声明：

```feng
type Button: Widget {
    ...: View = View();
}
```

每次构造 `Button` 时，初始化过程概念上等价于：

```text
let source = View();
self.style = source.style;
self.tag 保持默认零值和未绑定状态;
self.parent = source.parent;
```

同一个 `...` 的来源构造表达式只能求值一次，所有生成字段共用该次构造结果。字段
处理完成后，临时来源值按 Feng 现有生命周期规则释放；编译器不把它保存为目标的
隐藏字段。如果复制出的引用或 callable 自身保留来源实例，则由其普通引用语义和 RC
规则自然决定来源实例的后续生命周期。

### 8.4 `let` 绑定状态

显式来源构造完成后，来源 `let` 的显式绑定集合由以下现有声明事实合并得到：

1. 来源字段在成员声明及绑定初值阶段已经绑定；
2. 当前构造表达式选中的构造函数绑定了该字段；
3. 当前构造表达式的对象字面量阶段绑定了该字段。

对于每个参与展开的字段：

- 来源 `let` 已显式绑定时，读取 `source.field` 绑定目标字段，并把目标 `let` 标记为
  已在目标成员声明及绑定初值阶段完成最终显式绑定；
- 来源 `let` 未显式绑定时，不生成显式赋值，目标字段保持默认零值和未绑定状态；
- 来源 `var` 始终复制来源构造完成后的最终值。

绑定状态是编译期声明事实，不从来源对象读取运行时标志。

### 8.5 值语义和构造阶段

字段绑定使用现有普通规则：

- 值类型成员按值语义复制；
- 引用类型成员按引用语义绑定；
- callable 成员按现有 callable 值语义绑定；
- 不建立来源字段槽位和目标字段槽位之间的后续同步关系。

来源构造及生成字段绑定归入 Feng 现有“成员声明及绑定初值”阶段，不引入新的构造
阶段。多个 `...`、目标显式字段、构造函数和对象字面量继续使用现有顺序、重复绑定、
生命周期和错误处理规则。

## 9 `@mixable` 静态方法

### 9.1 声明约束

`@mixable` 只适用于静态方法：

```feng
type View: Widget {
    @mixable
    static func draw(target: Widget, area: Area): void {
        // 可复用绘制逻辑
    }
}
```

规则如下：

- 静态方法必须至少有一个参数；
- 第一个参数必须是非变长的 object-form `spec`；
- 第一个参数名称没有特殊含义，可以使用 `target`、`widget` 或其他普通参数名；
- 声明该方法的具体类型必须在声明头中名义声明满足第一个参数的 `spec`；
- 方法作为来源展开到目标时，目标类型也必须在声明头中名义声明满足该 `spec`；
- 展开阶段只检查名义声明关系，生成字段和 wrapper 进入普通成员表后，由现有 `spec`
  检查验证声明类型或目标类型是否真正满足该契约；
- 其余参数、方法泛型参数、返回类型、可见性和变参标记保持不变。

`@mixable` 不允许参数，也不表达来源实例、类型链、alias 或其他注入方式。固定注入项
只有目标实例。

### 9.2 统一派生实例入口

每个类型最终成员面中保留的 `@mixable` 静态方法，都无条件为该类型派生一个同名普通
实例 wrapper。该规则不区分静态方法是类型显式声明的，还是从另一个来源 mix 得到的
静态 wrapper。

对于显式声明 `@mixable` 静态方法的 `View`，概念生成：

```feng
type View: Widget {
    static func draw(target: Widget, area: Area): void {
        // 原始方法体
    }

    func draw(area: Area): void {
        View.draw(self, area);
    }
}
```

实例 wrapper 删除静态方法的第一个参数，并把当前实例 `self` 按该参数的 object-form
`spec` 视角作为第一个普通实参。wrapper 始终调用当前类型自己的同名静态方法，使
该静态方法成为当前类型实例行为的唯一入口。

实例 wrapper 生成后是普通实例方法，可以参与 `spec` 满足、方法值、重载、冲突和
代码生成，但它自身不参与后续 mix。

### 9.3 目标静态 wrapper

当目标展开来源时，每个符合条件的 `@mixable` 静态方法只直接生成一个目标静态
wrapper。该 wrapper：

- 保留来源静态方法的完整签名；
- 方法体只执行完整限定的来源静态调用；
- 继续携带 `mixable` 声明事实。

目标静态 wrapper 进入目标最终成员面后，再统一应用 §9.2，派生目标实例 wrapper。

例如：

```feng
type Button: Widget {
    ...: View;
}
```

概念生成：

```feng
type Button: Widget {
    @mixable
    static func draw(target: Widget, area: Area): void {
        View.draw(target, area);
    }

    func draw(area: Area): void {
        Button.draw(self, area);
    }
}
```

这里的两个步骤分别是：

```text
mix View.draw
  → 生成 Button.@mixable static draw
  → @mixable 统一派生 Button 实例 draw
```

静态 wrapper 不复制来源方法体。来源方法内部的静态字段访问仍属于来源类型；需要
访问或动态调用目标能力时，来源方法必须通过第一个 `spec` 参数完成。

### 9.4 多层 mix 的行为传播

目标生成的静态 wrapper 必须继续携带同一个 `mixable` 声明事实。该事实先使当前目标
按 §9.2 派生实例 wrapper；以后当前目标作为另一个 `...` 的来源时，又使下一层生成
新的 `@mixable` 静态 wrapper，并再次统一派生下一层实例 wrapper：

```text
IconButton.draw()
  → Button.draw(iconButton)
  → View.draw(iconButton)
```

该事实必须进入 `.ft`，保证同包、跨包和二进制包消费结果一致。生成的实例 wrapper
只是普通实例方法，不携带 `mixable` 事实，也不作为来源行为继续展开。

静态 wrapper 的存在是多层行为复用链的一部分，不只是当前目标上的调用便利。如果不
生成静态 wrapper，中间类型作为下一层来源时将无法继续提供上一层的原始行为入口。

### 9.5 显式覆盖和来源行为调用

目标可以显式定义自己的 `@mixable` 静态方法，并通过完整限定调用复用来源逻辑：

```feng
type Button: Widget {
    ...: View;

    @mixable
    static func draw(target: Widget, area: Area): void {
        View.draw(target, area);
        // Button 的附加绘制逻辑
    }
}
```

目标显式声明优先，来源中与其冲突的静态 wrapper 候选按 §11 跳过。Button 自己最终
保留的 `@mixable` 静态方法按 §9.2 无条件派生普通实例入口：

```text
button.draw(area)
  → Button.draw(button, area)
  → View.draw(button, area)
  → Button 附加逻辑
```

完整限定静态调用明确表示固定调用来源行为；通过 `target.someMethod()` 发起的调用则
按 `Widget` 等 object-form `spec` 的现有 witness 规则选择目标实现。编译器不隐藏或
推测类似虚方法的开放调用关系。

### 9.6 变参数组转发

如果 `@mixable` 静态方法最后一个参数是变长参数，生成 wrapper 保留其变参声明，并
使用已经实现的通用 `...args` 语法转发预打包数组：

```feng
@mixable
static func log(target: Widget, args: string...): void;
```

在声明类型 `View` 中，实例 wrapper 概念为：

```feng
func log(args: string...): void {
    View.log(self, ...args);
}
```

如果该方法 mix 到 `Button`，则先生成 `Button.log` 静态 wrapper，派生的实例 wrapper
调用 `Button.log(self, ...args)`。两种调用都使用同一个预打包数组。

`...args` 的语法、类型检查、求值和零分配要求以
[`feng-function-variadic.md`](../specifications/feng-function-variadic.md) 为唯一规范
来源。wrapper 不增加专用变参打包路径。

## 10 静态状态归属

静态字段不参与 `...`。例如：

```feng
type View: Widget {
    static var color = "red";

    @mixable
    static func draw(target: Widget): void {
        print(View.color);
    }
}
```

目标只得到 `draw` wrapper，不得到 `Button.color`。调用 `Button.draw(button)` 最终执行
`View.draw(button)`，其中 `View.color` 明确属于来源类型。

目标可以声明自己的同名静态字段，但它与 `View.color` 是无关状态，不会影响来源方法。
由于编译器不会生成容易造成误解的目标静态字段副本，这一差异直接反映在可见成员面和
完整限定访问表达式中。

## 11 显式成员优先与冲突

### 11.1 mix 候选的目标显式成员优先

如果目标类型显式定义的成员与待生成字段或目标静态 wrapper 冲突，则不生成对应 mix
候选。冲突判断完全使用 Feng 现有规则：

- 字段使用现有字段级冲突规则；
- 方法使用现有方法级冲突和重载规则；
- 静态成员与实例成员的冲突面使用现有规则；
- 字段与方法的冲突使用现有规则。

本方案不另行定义按名称、按签名或按来源顺序覆盖的规则。该优先规则只用于筛选从
`...` 来源产生的字段和静态 wrapper 候选，不用于跳过 §9.2 的实例 wrapper。

### 11.2 实例 wrapper 不跳过

目标最终成员面中的每个 `@mixable` 静态方法都必须无条件派生实例 wrapper。编译器
不得因为目标已经存在同名字段、实例方法或另一个派生 wrapper 而预先跳过生成。

所有实例 wrapper 生成后，与其他普通成员一起进入现有成员表。如果属于合法重载，
则按现有规则接受；如果发生字段、方法、静态/实例成员或派生签名冲突，则由后续现有
冲突检查自然报错。本方案不增加 `@mixable` 专用冲突算法或诊断。

这保证不会出现静态方法已经 mix 到目标，但对应实例入口因显式成员优先而被静默遮蔽
的情况。

### 11.3 多个来源的生成成员冲突

两个不同 `...` 产生的生成成员之间没有第一个来源或最后一个来源优先规则。它们进入
同一个普通成员集合；若等价手写声明会冲突，则按现有诊断报错。

诊断应同时指向目标的 `...` 位置和对应来源成员，便于理解生成来源。

## 12 可见性与传递展开

- 跨包来源类型必须在目标位置可见；
- 只有目标位置可见的公开实例字段参与字段展开；
- 只有目标位置可见的公开 `@mixable` 静态方法参与行为展开；
- 私有声明不能通过 `...` 变成目标或 consumer 可访问成员；
- 生成成员使用来源成员的可见性；
- wrapper 对来源静态方法的调用继续执行普通可见性检查。

生成字段是目标的普通字段，因此目标以后作为来源时，这些公开字段可继续参与下一层
字段展开。生成静态 wrapper 保留 `mixable` 事实，因而可以继续参与下一层行为展开。
生成实例 wrapper 不参与展开。

## 13 跨包与 `.ft`

### 13.1 来源消费

本方案不要求 `.ft` 携带来源字段初始化器 AST 或来源静态方法体：

- `...: View` 直接生成目标字段的默认零值初始化；
- `...: View = View()` 通过公开构造入口创建一次完整来源实例；
- 来源 `let` 绑定状态使用 `.ft` 中现有 `bounded_decl`、构造函数成员绑定关系和当前
  对象字面量绑定事实；
- 字段值通过普通公开成员读取；
- wrapper 只调用静态库中已有的公开 `@mixable` 静态方法符号。

`.ft` 必须保存公开静态方法的 `mixable` 声明事实。同包声明与 `.ft` 恢复声明必须向
普通成员/provider 查询提供一致的字段、签名、泛型、变参、构造绑定和 `mixable`
事实。

### 13.2 目标导出

目标包在导出前完成 `...` 和 `@mixable` wrapper 生成。目标 `.ft` 导出生成后的普通
公开字段、静态 wrapper 和实例 wrapper，并为生成 `let` 导出最终 `bounded_decl`
事实。

生成静态 wrapper 的 `mixable` 事实必须继续导出，使目标作为其他包中的展开来源时
保持多层 mix。consumer 不重新执行已经编译目标的原始 `...`。

### 13.3 兼容性

来源增加、删除或修改公开实例字段，会改变下游重新编译后的目标布局。来源增加、删除
或修改公开 `@mixable` 静态方法，会改变目标的静态和实例成员集合。这些变化可能影响
重载、冲突及 `spec` 满足，应视为公开源码/API 兼容性变化。

已经编译完成的目标静态库不会在未重新编译时自动改变。

## 14 编译器归一化

建议前端顺序为：

```text
Lex / Parse
  → 加载并恢复外部 .ft 公开声明
  → 解析 ... 的来源类型或构造表达式静态类型
  → 确认来源为具体 type 声明
  → 收集公开可见实例字段
  → 收集公开可见 @mixable 静态方法及可见 fit 静态方法
  → 根据现有规则跳过与目标显式成员冲突的字段和静态 wrapper 候选
  → 生成目标普通字段和保留 mixable 事实的静态 wrapper
  → 对类型最终保留的每个 @mixable 静态方法无条件派生实例 wrapper
  → 根据来源构造路径计算 let 显式绑定集合
  → 在现有成员声明及绑定初值阶段生成普通字段绑定
  → 建立包含生成成员的普通成员表
  → 使用现有规则检查实例 wrapper 在内的全部成员冲突与重载
  → 执行现有 spec 检查及其他语义分析
  → 执行现有代码生成
```

`...` 需要来源类型、成员声明和构造绑定事实，不是纯 Token 变换。但展开应尽早完成，
使后续阶段尽量只处理普通字段和普通方法。

循环、泛型、初始化顺序、可见性、生命周期和普通成员合法性继续使用等价手写声明适用
的现有规则，不建立平行的运行时或类型系统。

## 15 性能模型

### 15.1 默认零值展开

`...: View` 不创建完整来源实例：

- 生成字段直接进行普通默认零值初始化；
- 不增加来源对象分配和释放；
- 不增加来源对象引用计数；
- 不触发来源类型终结器。

### 15.2 显式来源构造

`...: View = View()` 和 `... = View()` 每个目标实例执行一次来源构造表达式：

- 构造成本与用户显式手写 `let source = View()` 相同；
- 来源公开字段按普通值或引用语义绑定到目标；
- 字段处理后临时来源按现有生命周期规则释放；
- 编译器不保存隐藏来源引用。

### 15.3 稳定运行阶段

- 生成字段直接进入目标对象布局；
- 字段访问与手写目标字段相同，不经过来源对象；
- wrapper 只增加明确的普通静态调用层；
- 多层 mix 的调用层级与源码可见静态 wrapper 链一致；
- 变参 wrapper 使用 `...args` 直接传递同一个预打包数组，不重新分配、复制、遍历或
  打包。

正式实现仍需用基准验证显式来源构造、字段复制、引用计数和多层 wrapper 成本。任何
扩大既定运行时开销的实现选择必须单独评审。

## 17 当前结论

本草案将无继承下的 GUI/TUI 复用模型收敛为：

```text
多态
  → object-form spec / witness

结构复用
  → ... 只展开公开实例字段
  → 默认零值直接初始化，或显式构造一次后复制字段值及绑定状态

行为复用
  → @mixable 静态方法
  → 每个类型最终保留的 @mixable 静态方法统一派生实例 wrapper
  → mix 目标只直接生成静态 wrapper
  → 静态 wrapper 保留 mixable 事实，并在当前层派生实例 wrapper、支持下一层 mix
```

该模型不包含继承、类型链、隐藏来源实例、静态字段复制、实例方法提升或动态 `self`
重绑定。固定来源行为通过完整限定静态调用表达，目标多态行为通过 `spec` 参数调用表达。
结构、行为和多态职责相互独立。
