# Feng `...` 成员展开设计草案

> **状态**：讨论草案，尚未进入语言规范，尚未实现。
>
> 本文用于方案评审与后续推敲。评审通过前，不修改
> `docs/specifications/` 中的正式规范，也不据此实现编译器或标准库。

## 1 背景

Feng 当前没有继承，也没有增加继承的计划。retained-mode GUI/TUI 组件通常需要
重复声明一组公共状态，例如样式、布局结果、父子关系和事件绑定，同时只在少量行为
上存在差异。

仅增加类似 Rust trait 的 `spec` 默认实现只能复用行为，不能复用实体字段。直接
转发具体类型的实例方法又会产生接收者语义问题：来源实例方法中的 `self` 是来源
类型，不能安全地动态重绑定为具有不同内存布局的目标类型。

本草案提出 `...` 成员展开语法：目标类型显式选择一个来源类型，编译器在前端早期
生成普通字段和普通 wrapper 方法，之后完全复用现有成员、初始化、重载、`spec`
满足、方法值、代码生成和运行时机制。

本方案不使用 `@mixin` 或 `@mixable`。来源类型不需要额外授权标记，其符合规则的
公开成员均参与展开。

## 2 核心语义原则

本方案的核心原则是：

> `...` 先生成等价的手写字段和 wrapper 方法，再由 Feng 现有规则处理。来源语法、
> 来源类型范围和字段绑定映射由本文明确规定；成员生成与冲突处理仅增加下列两项
> 专用规则。

这意味着：

- 生成字段是目标类型自己的普通字段，不是来源字段的转发或别名；
- 生成 wrapper 是普通方法，只执行普通的来源静态方法调用；
- 生成成员使用现有可见性、冲突、重载、泛型、`spec`、方法值和代码生成规则；
- 生成字段和 wrapper 与显式手写成员一起参与现有 `spec` 满足检查；
- 编译器不复制具体实例方法的方法体；
- 编译器不重绑定来源实例方法的 `self`；
- 编译器不引入新的方法分派机制；
- 编译器不为生成成员增加手写成员不存在的运行时行为。

两项生成专用规则是：

1. 如果目标类型显式定义的成员与待生成成员冲突，则不生成该成员；是否冲突完全使用
   Feng 现有字段级和方法级成员冲突规则，不另行定义冲突签名或优先级规则。
2. 公开静态方法默认只生成静态 wrapper；只有显式标注
   `@instance(target [, source])` 时，才按固定前缀注入规则额外生成一个实例
   wrapper。标注不控制该静态方法是否参与展开。

除此之外，循环、泛型、初始化、成员顺序、可见性、`fit`、annotation、跨包恢复及
其他合法性均使用等价手写声明原本适用的现有规则；不为 `...` 重复建立检查。

## 3 设计目标

1. 复用公开类型已经定义的实例字段和静态字段。
2. 通过普通静态调用 wrapper 复用安全的公共行为，并允许来源显式请求额外生成实例
   wrapper。
3. 不要求来源成员逐个添加 `@mixable` 一类的授权标记。
4. 使展开结果除两项生成专用规则外均等价于手写代码。
5. 在前端早期回到现有 AST、语义分析和代码生成主路径。
6. 支持 `.ft` + 静态库形式的跨包二进制分发，不要求 `.ft` 携带函数体或字段初始
   绑定表达式。
7. 实例字段在目标类型中具有独立存储，热路径成员访问不经过来源实例。
8. 机制不依赖 GUI/TUI，可用于其他需要成员组合的类型。

## 4 非目标

本草案不提供：

- 继承或子类关系；
- 来源类型到目标类型的实体子类型转换；
- 具体实例方法的方法体复制；
- 将来源实例方法的 `self` 重绑定为目标实例；
- Go 风格的具体实例方法自动提升；
- 运行时动态添加或删除成员；
- 来源字段与目标字段之间的长期绑定或同步；
- 来源静态字段与目标静态字段之间的别名关系；
- 用户自定义 `...` 展开算法；
- 未经 `@instance(...)` 显式声明的静态方法到实例方法转换；
- 独立于现有成员规则的覆盖、重载或动态分派体系。

## 5 语法

### 5.1 完整写法

```feng
type Button {
  ...: View = View();
}
```

`View` 是来源类型，`View()` 是实例来源对象构造表达式。等号右侧只允许 Feng
现有对象构造表达式，不允许变量引用、成员访问、函数调用结果、条件表达式或其他任意
值表达式。构造结果类型必须与显式来源类型一致。每次构造一个 `Button` 时，该构造
表达式求值一次，其结果用于初始化展开得到的实例字段。

### 5.2 使用来源类型的默认零值

```feng
type Button {
  ...: View;
}
```

该形式使用 `View` 的默认零值作为实例来源值，不执行 `View` 构造函数。

### 5.3 自动推导来源类型

```feng
type Button {
  ... = View();
}
```

来源类型由等号右侧对象构造表达式直接确定。该形式同样只允许 Feng 现有对象构造
表达式，不接受其他任意值表达式。

### 5.4 泛型来源

`...` 位于目标类型体内，按普通类型成员作用域解析名称，因此可以直接引用目标类型
的泛型参数：

```feng
type Button<T> {
  ...: View<T> = View<T>();
}
```

这里不需要为 annotation 增加向后引用目标泛型参数的特殊作用域规则。来源类型实参
及实例来源对象构造表达式均按现有泛型名称查找、实参替换、构造匹配和约束检查规则
处理。

### 5.5 来源类型范围

`...` 的来源必须解析到一个具体 `type` 声明。允许来源使用目标类型的泛型参数形成
具体泛型类型实例，例如 `View<T>`；这里需要展开的成员集合仍由确定的 `View`
声明提供，`T` 只参与现有泛型替换。

以下类型不能作为 `...` 来源：

- object-form、callable-form 或 union-form `spec`；
- `enum`；
- 内建类型或数组；
- 裸类型参数，例如 `...: T`；
- 不能解析到具体 `type` 声明的其他类型形式。

禁止裸类型参数作为来源，是因为其具体实参会改变目标成员集合和对象布局，不能在目标
泛型 `type` 的声明分析阶段归一化为一组确定的普通成员。该限制不影响
`...: View<T>`：后者的来源声明及成员集合是确定的，只需执行普通类型实参替换。

## 6 参与展开的来源成员

来源类型中符合以下种类且在目标位置公开可见的成员参与展开：

| 来源声明 | 目标中生成的成员 |
| --- | --- |
| 公开实例 `let` / `var` | 同名普通实例字段 |
| 公开静态 `let` / `var` | 同名普通静态字段 |
| 公开静态方法 | 同名普通静态 wrapper |
| 带 `@instance(target [, source])` 的公开静态方法 | 保留静态 wrapper，并额外生成按标注注入连续前缀参数的同名普通实例 wrapper |

以下成员不参与展开：

- 在目标位置不可见的成员；
- 具体实例方法；
- 构造函数；
- 终结器；
- 不属于上述表格的其他声明。

“所有公开成员参与展开”是指上述可安全展开的成员种类不再需要逐个标注
`@mixable`，并不表示复制具体实例方法的方法体。

来源成员的查找、可见性、泛型替换、`fit` 可见关系及声明合法性全部使用目标位置原本
适用的现有规则。编译器不为 `...` 建立另一套“来源成员面”；等价手写代码在该位置
能够使用的公开成员，才是可参与生成的成员。

来源的公开静态方法面同时包含：

- 来源 `type` 自身声明的公开静态方法；
- 在 `...` 所在位置可见，并且可通过普通 `Source.method(...)` 查找和调用的公开
  `fit Source` 静态扩展方法。

可见 `fit` 提供的静态方法参与展开后，生成的 wrapper 成为目标类型自身的普通成员；
目标完成编译并导出后，consumer 使用该 wrapper 不需要再次看见原始 `fit`。这与在
原始 `fit` 可见位置手写 wrapper 并将目标成员导出一致。

`@instance(...)` 只描述静态方法额外生成实例 wrapper 时的参数注入规则，不是静态
方法参与展开的授权标记。没有该标注的公开静态方法仍生成静态 wrapper，但不生成
实例 wrapper。来源自身或可见 `fit` 提供的静态方法采用相同规则。

`fit Source` 的实例方法仍属于具体来源类型的实例方法，不参与展开。其隐式 `self`
绑定来源实例，不能重绑定为目标实例；是否在目标位置可见不改变这一边界。

## 7 实例字段展开

### 7.1 基本语义

来源声明：

```feng
open type View {
  open let style: WidgetStyle = WidgetStyle {};
  open let tag: string;
  open var parent: Option<Widget>;
}
```

目标声明：

```feng
type Button {
  ...: View = View();
  let text: string;
}
```

生成字段的声明形状等价于：

```feng
type Button {
  open let style: WidgetStyle;
  open let tag: string;
  open var parent: Option<Widget>;
  let text: string;
}
```

每次构造 `Button` 时，初始化过程等价于：

```text
let source = View();
self.style = source.style;
self.tag 保持默认值和未绑定状态;
self.parent = source.parent;
```

实例来源对象构造表达式只求值一次，不能为每个字段分别求值。字段值读取完成后，临时
来源值按现有生命周期规则处理。

### 7.2 字段声明事实

生成字段复制来源字段的以下声明级事实：

- 名称；
- 类型；
- `let` / `var` 可变性；
- 可见性。

来源字段的初始绑定表达式不复制到目标字段。目标字段的值来自构造完成的实例来源值
或来源类型默认零值。

### 7.3 `let` 绑定状态

生成 `let` 字段是否已经完成最终显式绑定，由实例来源的构造路径决定。绑定状态不是
从来源对象中运行时读取的标志，而是编译器按现有三阶段构造规则计算的声明事实。

当使用显式实例来源对象构造表达式时，来源的显式绑定集合由以下事实合并得到：

1. 来源字段在成员声明及绑定初值阶段已经绑定；
2. 当前对象构造表达式选中的构造函数绑定了该字段；
3. 当前对象构造表达式的对象字面量阶段绑定了该字段。

对于每个参与展开的来源实例字段：

- 来源 `let` 位于显式绑定集合中时，目标字段从 `source.field` 读取值，并标记为已经在
  目标成员声明及绑定初值阶段完成最终显式绑定；
- 来源 `let` 不在显式绑定集合中时，不生成对该目标字段的显式赋值；目标字段保留其
  类型默认值和未绑定状态，之后仍可在目标构造函数或目标对象字面量阶段完成首次绑定；
- 来源 `var` 不受单次最终绑定限制，始终从构造完成的来源对象读取并复制最终值。

`...: View` 使用来源类型递归默认零值，不执行来源的成员声明初始化器、构造函数或
对象字面量阶段，因此不会形成来源 `let` 显式绑定集合；生成的目标 `let` 保持默认值
和未绑定状态，生成的目标 `var` 取得来源默认零值。

同包分析直接使用现有字段及构造绑定事实；跨包分析使用 `.ft` 中现有的
`bounded_decl`、构造函数成员绑定关系，并结合 consumer 当前对象构造表达式中的
对象字面量绑定。该过程不需要来源字段初始绑定表达式或来源构造函数体。

### 7.4 值语义

对于实际生成的来源成员读取与目标字段绑定，完全采用普通成员读取、初始化和赋值
规则：

- 值类型成员按现有值语义复制；
- 引用类型成员按现有引用语义绑定；
- callable 成员按现有 callable 值语义绑定；
- 不建立来源字段槽位与目标字段槽位之间的后续关联。

如果某个字段值内部保留了来源实例，例如 Lambda 捕获了来源实例，该值继续按普通
引用语义保留来源实例。`...` 不修改该值内部已经形成的绑定。

### 7.5 构造归一化

实例字段及其绑定归入 Feng 现有“成员声明及绑定初值”构造阶段，不引入新的构造
前置阶段。编译器可在该阶段生成一个不可见的普通临时绑定，以保证同一个 `...` 的
实例来源对象构造表达式只求值一次，然后使用该值完成生成字段的普通绑定。

生成的 `let` / `var`、多个 `...`、目标显式字段、构造函数和对象字面量继续使用现有
构造顺序、绑定状态和重复绑定检查。若等价手写代码不合法，后续现有检查自然报错，
`...` 不增加构造专用诊断，也不引入现有 declaration-bound / unbound 之外的新绑定
状态。

## 8 静态字段展开

来源声明：

```feng
open type View {
  open static let defaultWidth: u32 = 10;
  open static var createdCount: u32 = 0;
}
```

目标声明：

```feng
type Button {
  ...: View;
}
```

概念展开结果：

```feng
type Button {
  open static let defaultWidth: u32 = View.defaultWidth;
  open static var createdCount: u32 = View.createdCount;
}
```

目标静态字段具有独立存储，不是来源静态字段的别名。初始化表达式读取来源静态字段，
之后来源与目标的静态 `var` 可以独立变化。初始化时机、读取顺序和错误处理均使用
现有静态字段规则。

实例来源对象构造表达式不参与静态字段初始化；静态字段只由解析后的来源类型决定。

## 9 静态 wrapper

### 9.1 普通静态 wrapper

每个参与展开的公开静态方法都生成静态 wrapper。

来源声明：

```feng
open type View {
  open static func createStyle(): WidgetStyle {
    return WidgetStyle {};
  }
}
```

概念展开结果：

```feng
type Button {
  open static func createStyle(): WidgetStyle {
    return View.createStyle();
  }
}
```

生成的静态 wrapper：

- 使用来源静态方法的名称、泛型参数、普通参数、返回类型和可见性；
- 方法体只执行对来源静态方法的完整限定普通静态调用；
- `void` 返回方法生成普通调用语句，非 `void` 返回方法返回调用结果；
- 不复制来源方法体；
- 不重写来源方法内部对来源类型静态成员的访问。

如果来源静态方法内部修改 `View.createdCount`，通过 `Button` 的静态 wrapper 调用后
修改的仍是 `View.createdCount`，不是独立的 `Button.createdCount`。这与用户手写
`Button.method() { View.method(); }` 的行为相同。

### 9.2 变参数组零分配转发

来源静态方法可以声明 Feng 现有变长参数。为了让生成 wrapper 继续等价于可手写代码，
Feng 需要先提供通用的预打包变参数组转发语法：

```feng
func wrapper(level: int, args: string...): void {
  source(level, ...args);
}
```

变长参数 `args` 在 wrapper 函数体内已经是调用侧打包完成的 `string[]`。调用实参位置
的 `...args` 表示把该数组直接作为目标变参已经完成打包的结果传递，而不是遍历数组
并重新打包。

第一版规则固定为：

- `...expr` 只允许出现在调用实参列表中；
- `...expr` 必须是实参列表中的最后一项；
- 被调用目标必须声明变长参数；
- `expr` 必须是与目标变参元素类型匹配的只读数组，类型兼容性继续使用现有数组规则；
- `expr` 按普通表达式规则求值一次；表达式自身固有的构造或分配不因 `...` 改变；
- codegen 必须把同一个预打包数组直接传入目标函数的已归一化数组参数；
- `...` 转发本身不得创建新数组、复制或遍历数组元素，也不得重新执行变参打包；
- 数组引用的传递与生命周期继续使用普通函数调用和现有 ARC 规则。

普通调用仍使用现有变参打包：

```feng
source(level, "a", "b");
```

只有显式的 `...args` 才表示预打包数组的零分配转发。该能力属于通用函数调用机制，
必须作为独立代码任务先于 `...` 成员展开实现，不得在生成 wrapper 的 codegen 中
增加用户不可手写的专用转发路径。

来源变参静态方法的 wrapper 使用同一语法：

```feng
open type View {
  open static func log(level: int, args: string...): void { ... }
}

type Button {
  open static func log(level: int, args: string...): void {
    View.log(level, ...args);
  }
}
```

## 10 显式实例 wrapper

### 10.1 `@instance(target [, source])` 参数注入

公开静态方法无论是否带 `@instance(...)`，均按 §9 生成普通静态 wrapper。只有显式
标注 `@instance(target [, source])` 时，才额外生成一个同名普通实例 wrapper。
`target` 是固定且必需的第一个注入项，之后只允许省略 `source` 或带一个 `source`；
不允许省略 `target`，也不允许其他数量或排列。

语法为：

```text
@instance(target [, source])
```

标注参数按顺序对应来源静态方法最前面的 N 个连续参数：

```feng
@instance(target)
open static func draw(widget: Widget, area: Area): void;

@instance(target, source)
open static func merge(current: Widget, base: Widget, area: Area): void;
```

规则如下：

- annotation 参数数量 N 只能是 1 或 2；来源静态方法必须至少有 N 个参数；
- 第一个注入项必须是 `target`，对应来源静态方法的第一个参数；
- 如果存在第二个注入项，则必须是 `source`，对应来源静态方法的第二个参数；
- 每个被注入参数的声明类型必须是 object-form `spec`，且不能是变长参数；
- `target` 表示注入目标实例按该参数 `spec` 建立的目标视角；
- `source` 表示注入本次 `...` 来源按该参数 `spec` 建立的来源视角；
- 生成实例 wrapper 只删除这 N 个连续前缀参数，其余参数保持原顺序；不允许从普通
  参数序列中间省略参数；
- `@instance(target, source)` 表示生成一个同时注入两个参数的实例 wrapper，不表示
  分别生成两个实例 wrapper；
- `@instance()`、`@instance(source)`、`@instance(source, target)` 和
  `@instance(target, target)` 均不合法；`@instance(target, source, source)` 以及任何
  更多注入项同样不合法；
- 同一静态方法只能声明一次 `@instance(...)`，不通过重复标注生成多个实例 wrapper。

`@instance` 只是源码层 annotation 名称。编译器完成 annotation 名称和参数校验后，
必须将其归一化为名为 `mix_to_instance` 的内部声明级事实。编译器 AST 语义事实、
成员/provider 查询、`.ft` 声明事实、实现结构和相关注释均使用 `mix_to_instance`
命名，不使用含义过宽的独立 `instance` 名称表示该机制。

存在 `mix_to_instance` 即表示固定注入 `target`；该事实另外记录是否同时注入可选的
`source`。源码 annotation 节点可为诊断和 IDE 保留原始拼写，但后续成员展开不得
反复解释 annotation 参数，也不保存通用参数映射。

对于固定的第一个 `target` 注入项，展开阶段只检查目标类型声明头中是否存在对应的
名义 `spec` 声明，按现有类型名称解析、泛型实参替换和类型等价规则比较；如果存在
第二个 `source` 注入项，则按相同规则检查来源类型的名义 `spec` 声明。展开阶段不
遍历成员验证实际满足关系。

生成实例 wrapper 后，与生成字段、静态 wrapper 和目标显式成员一起进入同一个普通
可见成员面。后续现有 `spec` 检查负责验证相应类型是否真正满足其声明的 `spec`；
所有生成成员均可像手写成员一样参与该检查。若最终不满足，产生现有 `spec` 诊断，
不得在展开阶段静默移除 wrapper，也不建立另一套满足算法。

### 10.2 目标视角注入

来源声明：

```feng
open type View {
  @instance(target)
  open static func addChild(widget: Widget, child: Widget): void {
    widget.children.add(child);
  }
}
```

当 `Button` 名义声明 `Widget` 时，概念展开结果为：

```feng
type Button {
  open static func addChild(widget: Widget, child: Widget): void {
    View.addChild(widget, child);
  }

  open func addChild(child: Widget): void {
    View.addChild(self, child);
  }
}
```

生成的实例 wrapper：

- 名称与来源静态方法相同；
- 按 `@instance(target [, source])` 删除并注入来源静态方法的连续前缀参数；
- 保持其余参数、泛型参数、返回类型和可见性；
- 为 `target` 注入项将目标实例 `self` 的目标 `spec` 视角作为对应普通实参；
- 为 `source` 注入项将本次展开来源的 `spec` 视角作为对应普通实参；
- 其余实参按原顺序转发；
- 如果最后一个参数是变长参数，则保留其变参声明，并在来源调用中使用 `...args`
  进行预打包数组的零分配转发；
- 不复制来源静态方法体；
- 不引入来源实例或动态 `self` 重绑定。

生成后，实例 wrapper 是目标类型的普通实例方法。方法值、`spec` witness、调用和
代码生成均按现有普通实例方法规则处理。

### 10.3 `target` 加可选 `source` 注入

来源声明：

```feng
open type View {
  @instance(target, source)
  open static func merge(current: Widget,
                          base: Widget,
                          area: Area,
                          names: string...): void {
    // ...
  }
}
```

概念展开结果同时保留完整签名的静态 wrapper，并额外生成：

```feng
type Button {
  open func merge(area: Area, names: string...): void {
    View.merge(targetView(self), sourceView(self), area, ...names);
  }
}
```

`targetView(self)` 与 `sourceView(self)` 在此仅表示按参数注入规则形成的普通
object-form `spec` 参数视角，不是用户可调用的新增函数。两种视角的具体表示继续复用
Feng 现有 object-form `spec` 值与 witness 机制，不要求在目标实例中保存额外来源字段。

此例只从静态方法签名开头删除连续的 `current` 和 `base` 两个参数，`area` 与
`names` 的相对次序和签名保持不变。`source` 不能标记位于普通参数之后的参数，因而
不会产生从实例 wrapper 签名中间省略参数的情况。

生成静态 wrapper 必须保留同一内部 `mix_to_instance` 事实，使其他类型以后将
当前目标作为 `...` 来源时，仍可按同一普通静态签名继续生成实例 wrapper。这是生成
静态 wrapper 自身的声明事实，不表示任意 annotation 都自动传播。

## 11 `a` 调用 `b` 的行为

静态方法形式可以支持传统模板方法的一部分使用场景，具体行为由来源方法中的调用
表达式决定。

```feng
open spec WidgetBehavior {
  func b(): void;
}

open type View {
  @instance(target)
  open static func a(widget: WidgetBehavior): void {
    widget.b();
  }
}

type Button: WidgetBehavior {
  ...: View;

  func b(): void {
    // Button 的实现
  }
}
```

当 `Button` 名义声明 `WidgetBehavior` 时，`View.a` 因显式
`@instance(target)` 同时生成静态 wrapper 和实例 wrapper。生成成员进入普通成员面
后，现有检查再验证 `Button` 是否真正满足 `WidgetBehavior`。调用链为：

```text
button.a()
  → View.a(button)
  → widget.b()
  → 通过 WidgetBehavior witness 调用 Button.b()
```

如果来源静态方法写成完整限定静态调用 `View.b(widget)`，该调用仍然固定调用
`View.b`，不会动态选择 `Button.b()`。编译器不重写来源方法体，因此两种行为与
手写代码完全一致。

为避免 Go 内嵌方法中 `a` 固定调用来源 `b` 的问题，需要动态选择目标实现的相关
方法应声明在 `@instance(...)` 中标记为 `target` 的对象 `spec` 参数上，来源静态方法
应通过该参数的 `spec` 视角调用：

```feng
widget.b();
```

此时现有 `spec` witness 会选择目标实现。完整限定的来源静态调用表示设计者明确要求
固定调用来源实现，不具有开放调用语义。这一差异直接体现在调用表达式中，不依赖
隐藏的虚方法规则。

如果来源静态方法 `b` 也显式声明了 `@instance(...)`，而目标显式定义了与其生成实例
wrapper 冲突的 `b`，则依据本草案唯一的特殊冲突规则，跳过生成该实例 `b` wrapper。
来源 `a` 通过 `WidgetBehavior` 调用时会使用目标显式定义的 `Button.b()`。

## 12 显式成员优先与冲突

### 12.1 目标显式成员优先

如果目标类型显式定义的成员与某个待生成成员冲突，则跳过该生成成员：

```feng
type Button {
  ...: View;

  func draw(area: Area): void {
    // 显式定义优先，不生成与其冲突的 wrapper。
  }
}
```

“冲突”完全复用当前语言已有规则：

- 字段是否冲突使用现有字段级冲突规则；
- 方法是否冲突使用现有方法级冲突规则；
- 静态成员与实例成员是否处于同一冲突面，使用现有规则；
- 字段与方法是否冲突，使用现有规则；
- 合法重载仍按现有重载规则处理。

本草案不另行规定“按名称跳过”“按完整签名跳过”或其他 mixin 专用判断。

### 12.2 生成成员之间的冲突

目标显式成员优先是唯一特殊冲突行为。两个不同 `...` 产生的生成成员之间没有隐式
先后优先级：它们进入同一个普通成员集合，之后按现有成员冲突规则处理。若等价的
手写成员会产生冲突，则生成成员也产生相同冲突。

编译器不得采用“第一个来源获胜”或“最后一个来源获胜”的静默顺序规则。

### 12.3 其他错误

除显式成员冲突导致跳过生成外，生成成员不获得错误豁免。来源调用参数不匹配、泛型
约束不满足、生成后的普通表达式不合法等情况，均使用现有诊断。

诊断应同时指出目标的 `...` 位置和对应来源成员，以便用户理解生成来源。

## 13 可见性与传递展开

`...` 访问来源类型和来源成员时遵循现有可见性规则：

- 跨包来源类型必须在目标位置可见；
- 只有在目标位置公开可见且属于 §6 所列种类的成员参与展开；
- 私有声明不能通过 `...` 变成 consumer 可访问成员；
- 生成成员使用来源成员的可见性；
- wrapper 对来源静态方法的调用仍执行普通可见性检查。

由于不再存在 `@mixable` 标记，目标导出的生成成员也是普通公开成员。其他类型以后
将该目标作为来源时，这些公开生成成员可以继续参与展开；这种传递性是“公开成员均
可展开”和“生成后等价于普通手写成员”的直接结果。生成的静态 wrapper 保留来源
静态方法的内部 `mix_to_instance` 事实；生成的实例 wrapper 本身只是普通具体实例
方法，不作为可展开的来源方法。

## 14 跨包与 `.ft`

### 14.1 跨包成立条件

本方案不要求 `.ft` 携带来源字段的初始绑定表达式或来源静态方法体：

- `...: View` 使用来源类型默认零值；
- `...: View = View()` 通过公开构造入口创建完整来源值；
- 来源 `let` 的绑定状态通过字段 `bounded_decl`、选中构造函数的成员绑定关系和
  consumer 当前对象字面量绑定共同确定；
- 实例字段值通过普通公开成员读取；
- 静态字段初值通过普通外部静态字段访问取得；
- wrapper 只调用静态库中已有的来源静态方法符号，包括目标位置可见的公开 `fit`
  静态扩展方法符号。

consumer 只需要 `.ft` 中的公开声明级事实、公开静态方法的 `mix_to_instance` 事实
和静态库链接符号。由于所有符合种类的公开成员都参与展开，`.ft` 不需要新增
`@mixable` 标记或 mixin 模式，也不需要方法体。

同包声明与 `.ft` 恢复声明必须向现有成员查询提供一致的普通声明事实和顺序。该要求
属于 `.ft` 原有的声明恢复正确性，不形成 `...` 专用的成员顺序或跨包语义。

### 14.2 目标包导出

目标包在导出前已经完成 `...` 展开，因此目标 `.ft` 导出生成后的普通字段和普通
方法声明，并为生成的 `let` 字段导出其最终 `bounded_decl` 事实。生成的静态 wrapper
同时导出其内部 `mix_to_instance` 事实，使它作为其他 `...` 的来源时保持同包与
跨包一致。consumer 使用目标类型时不需要重新执行目标原始声明中的 `...`。

是否在 `.ft` 中额外保留 `...` 的来源位置只影响 IDE 展示和诊断来源映射，不影响
正确链接和使用目标类型。

### 14.3 包兼容性

来源类型增加、删除或修改符合规则的公开成员，会改变下游重新编译后的目标成员集合，
可能改变对象布局、重载集合或产生新的生成成员冲突，应视为公开源码/API 兼容性
变化。已经编译完成的目标静态库不会在未重新编译时自动改变。

## 15 编译器归一化

建议的前端顺序为：

```text
Lex / Parse
  → 加载并恢复外部 .ft 公开声明
  → 解析 ... 的来源类型或来源表达式静态类型，并确认其指向具体 type 声明
  → 收集符合种类的公开可见来源成员及可见 fit 静态方法
  → 根据现有规则跳过与目标显式成员冲突的生成成员
  → 解析并验证来源静态方法的 @instance(...)，归一化为 mix_to_instance 事实
  → 按 mix_to_instance 事实和目标、来源声明头的名义 spec 关系生成实例 wrapper
  → 根据来源构造路径计算 let 显式绑定集合
  → 生成普通字段、静态 wrapper 和现有成员初始化阶段中的普通绑定
  → 建立普通成员表
  → 使用包含所有生成成员的普通成员表执行现有 spec 检查和其他语义分析
  → 执行现有代码生成
```

`...` 需要来源表达式的静态类型、目标的普通成员信息、`mix_to_instance` 事实及
目标和来源声明头中的名义 `spec` 关系，因此不是纯 Token 变换。但展开应尽早完成，
使后续阶段只看到普通成员。

除来源语法、来源类型范围、字段绑定映射和两项成员生成专用规则外，归一化不得改变
生成代码相对于等价手写代码的含义。循环、泛型、初始化、顺序、可见性、`fit`、
annotation、跨包声明及其他合法性继续由现有机制处理，不增加同义或重复检查。

## 16 性能模型

实例字段展开把额外成本放在构造阶段：

- 显式实例来源对象构造表达式每个目标实例求值一次；
- 来源为普通引用类型时，可能临时创建一个来源对象；
- 编译器按普通值语义读取并绑定公开实例字段；
- 绑定完成后释放临时来源引用；若字段值保留来源实例，该实例按普通引用语义存活；
- 静态字段继续使用现有静态初始化机制，不产生每实例成本。

变参 wrapper 使用通用 `...args` 预打包转发：

- wrapper 接收到的变长参数已经是数组；
- 转发时直接传递同一个数组实例；
- 不得产生数组重新分配、元素复制、元素遍历或二次打包。

稳定运行阶段不存在来源对象转发：

- 生成字段直接进入目标对象布局；
- 字段访问与手写字段相同，不增加间接访问；
- 目标对象不为展开额外保存隐藏来源引用；
- wrapper 只增加普通静态方法调用，行为与手写 wrapper 相同。

正式实现前仍需通过基准确认构造成本、临时分配、引用计数操作和热路径收益。任何会
扩大运行时开销的实现选择均需单独评审。

## 17 语法范围

带等号的 `...` 只允许使用 Feng 现有对象构造表达式作为实例来源，不允许推广为
任意能够产生来源类型值的表达式。构造器匹配、泛型类型实参、对象字面量初始化及
构造表达式合法性全部使用现有规则。

来源类型必须解析到具体 `type` 声明；`View<T>` 这类确定来源声明的泛型实例合法，
裸类型参数、`spec`、`enum`、内建类型和数组不能作为来源。调用实参位置的
`...args` 是独立的通用预打包变参数组转发语法，与类型成员位置的 `...` 按语法
上下文区分。

成员顺序、`fit`、annotation、跨包恢复、循环、泛型、初始化与普通诊断均不属于
`...` 的独立语义，统一沿用等价手写代码适用的现有规则。调试信息、LSP 来源展示和
兼容性提示属于实现与工具体验，不改变语言语义。

## 19 当前结论

当前候选方案可以概括为：

```text
目标类型中的 ...: Source / ...: Source = Source() / ... = Source()
  ↓
确认来源解析到具体 type 声明
  ↓
收集来源自身及目标位置可见 fit 中符合种类的公开成员
  ↓
跳过与目标显式成员冲突的待生成成员
  ↓
根据来源构造路径确定生成 let 的绑定状态
  ↓
普通实例字段 + 普通静态字段 + 普通静态 wrapper
  + 显式 @instance(...)（内部 mix_to_instance）生成的普通实例 wrapper
  ↓
现有成员、初始化、冲突、重载、spec、方法值、代码生成和运行时机制
```

核心边界是：

- 不需要 `@mixin` 或 `@mixable`；
- 来源必须解析到具体 `type` 声明；允许 `View<T>`，不允许裸类型参数、`spec`、
  `enum`、内建类型或数组作为来源；
- 公开实例字段生成独立目标存储，不转发；
- 生成 `let` 是否已经完成最终显式绑定，由来源字段声明绑定、选中构造函数绑定及来源
  对象字面量绑定共同决定；默认零值来源不形成显式绑定集合；
- 公开静态字段生成独立目标静态存储，不建立别名；
- 来源自身及目标位置可见 `fit` 提供的所有符合条件的公开静态方法生成普通静态
  wrapper；
- 只有静态方法显式声明 `@instance(target [, source])` 时，才额外生成一个实例
  wrapper；第一个 object-form `spec` 参数固定注入为 `target`，可选的第二个
  object-form `spec` 参数注入为 `source`，并从实例签名中删除这一或两个连续前缀
  参数；
- 变参 wrapper 使用通用 `...args` 直接转发同一个预打包数组，不重新分配、复制、
  遍历或打包；`...args` 必须先作为独立语言能力完成；
- 所有生成成员与显式成员一起参与后续现有 `spec` 满足检查；
- 具体实例方法永不复制或提升；
- 目标显式成员冲突时按现有冲突规则跳过生成；
- 除显式成员冲突跳过和 `@instance(...)` 参数注入外，生成结果与手写展开无差别。

该方案是否进入正式语言规范，等待后续评审决定。
