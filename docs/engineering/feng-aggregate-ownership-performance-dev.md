# Feng 聚合值所有权性能优化

## 目标与范围

2026-09-28，按开发者决定先优化核心语言，再优化上层标准库。本项承接
[binary-trees 调查](feng-binary-trees-performance-investigation.md)，研究并实现
通用的聚合值借用、传递及生命周期发码优化。`binary-trees` 用于衡量实际收益，
不是按名称识别的优化对象；`text-scan` 的读取和容器批量操作另行推进。

语言规则引用[对象生命周期](../specifications/feng-lifetime.md)、
[流程控制](../specifications/feng-flow.md)、[异常](../specifications/feng-exception.md)
及[ABI 互操作](../specifications/feng-interop.md)，不在本文重新定义。
复用 [ARC 所有权方案](feng-arc-ownership-performance-dev.md) 的证明框架；
本项不改变参数／返回契约、runtime API、对象布局、FT 或循环回收策略。
union 紧凑布局涉及 ABI，单独设计并经人工决策后实施。

实施基线为 `7c28a8d0`，工作区干净。调查中的手工 C 副本只用于定位，不作为
通用实现，也不作为本项收益承诺。当前状态：本轮实现、完整回归、五目标发布模式
验证及黑盒对照测量均已完成。深度 16 的耗时中位数减少 46.2%，峰值 RSS 不变；
具体口径与结果见下文。

## 编译期证明

### 稳定聚合借用

现有所有权来源记录区分完整局部拥有者和字段投影，但闭合 union 的受管槽尚未
参与引用计数消除证明，参数和投影也不能直接套用“局部拥有权转移”。本项区分：

- **转移所有权**仍要求本地确实拥有可转移的引用；参数和投影不能被夺取所有权。
- **短期借用**要求使用区间内已有拥有者保活，完整读取路径稳定，值的受管槽不可
  被重新绑定；嵌套聚合成员逐层检查。参数由既有调用契约保活，不能据此延长借用
  到返回、捕获或其他逃逸位置。
- 消除 retain/release 对还必须证明 release 不进入循环候选路径。未知泛参、
  动态 spec、缺少描述符事实的跨包对象和未知布局保持原实现。

match 仍只求值一次，并保持原有匹配与分支绑定语义。借用副本不能通过可变分支
绑定或可变值字段释放／替换原拥有者的受管槽；不能证明这一点时保留拥有副本。
调用准备仍须在后续实参求值前固定当前值，保留所有必要的独立值副本。
本项新增的实参借用只用于语义分析已选定声明的不可变显式参数；可变参数、
间接 callable、extern 和隐式 receiver 保持此前的保护路径。已有优化不重复计入。

### 初始化与静态生命周期

另行审计新分配存储的初始化、已有所有权转移和静态已知聚合槽的生命周期操作。
仅在能够证明等价时消除重复工作；默认初始化、终结器、部分初始化异常退出和
字段释放顺序均须保持。是否能安全展开取决于通用布局和类型事实，不取决于
`Node`、`Option`、字段名或评测用例名称。尚未完成证明的候选不进入实现。

第一项可实施规则复用既有“语言默认零是否等于全零字节”查询：闭合 union 的
首个分支属于平凡表示、且该分支默认值为全零字节时，tag 为 0，转发槽描述为
`FENG_SLOT_NONE`、零 offset 和空 nested，整个默认值可直接清零。非零枚举、
受管首分支、需要嵌套描述符的首分支和动态布局继续走既有描述符初始化。规则
只处理类型默认零，不跳过字段初始化表达式或用户构造函数。

`test/` 覆盖发码结构和保守回退，新增 `fcts/` 覆盖行为及生命周期。重点配对验证：

| 可优化场景 | 必须保守或维持原语义的场景 |
| --- | --- |
| 不可变参数及局部 union 的只读匹配 | 可变源、可变分支绑定、可变值成员 |
| 稳定引用路径上的不可变聚合字段 | 后续实参替换字段、回调改变拥有路径 |

| 正常返回与嵌套递归 | 抛出、defer、捕获、逃逸及终结器顺序 |

## 实施记录

- 已确认 `text-scan` 主要成本来自 std 读取／构建路径，但每次操作中的保活、清理
  和跨模块数组访问也与编译器有关，不能将其全部归因于 runtime API 设计。
- 已实现稳定聚合借用、可证明全零的聚合默认初始化，以及可变参数拥有存储修复。
  新增 Codegen 正反例、既有 ARC 检查、完整回归和发布模式行为验证均已通过。

### 审计发现：可变 union 参数的原有生命周期问题

冻结的原始编译器与第一版修改版均复现以下情况：调用者保有一个带终结器对象的
union，将其传给 `func clear(var value: Choice) { value = none; }`，调用结束后
离开调用者作用域，两个制品均发生 `SIGSEGV`。终结器计数在调用返回后为 0，
程序未能完成作用域退出后的最终计数输出；正确行为应为先输出 0、再输出 1。

生成代码中，可变参数替换调用 `feng_aggregate_assign` 释放原 payload，但该
参数登记为由调用者拥有，入口没有为可变参数建立独立拥有者。调用者的原存储与
清理责任继续存在。该问题在原始制品已复现，不归因于本项借用优化。

复现源、原始／修改版生成 C 和构建记录保存在
`third_party/llvm-c-eh/temp/aggregate-ownership/parameter*`。这一位置是忽略的
验证目录，不作为长期测试交付。修复方向是在现有参数 ABI 下，为需要替换
受管槽的参数建立独立拥有存储，并在正常／异常退出时清理；需要审计固定布局、
共享泛型和捕获入口的一致性。该方向会增加必要的保活成本，按 AGENTS.md 的
运行时开销规则交人工决定。开发者已确认：若为固有问题则一并修复，允许前述
必要的保活成本。修复按可变存储及所有权事实处理，不为 union 类型名设置特判。
验收补充普通函数、方法、callable、固定聚合、共享泛型、捕获参数和异常退出，
同时确认不需要替换受管槽的只读参数仍沿用借用路径。

参数入口统一复用既有物化／清理机制：需要重新绑定的受管参数、以及能够直接
修改受管字段的值语义参数获得函数内独立存储；捕获参数沿用已经拥有引用的
capture cell。固定布局复制与 descriptor 驱动复制使用同一入口，调试变量读取
仅在建立拥有副本时指向新存储；未复制参数保留既有调试读取约定。原 ABI 参数
仍由调用者保活，不能将其当作本函数可以消耗的
引用。修复覆盖字符串、数组、对象和聚合值，不只处理本次复现使用的 union。
共享泛型方法中新建的参数副本也登记源码参数映射，使调试器能够读取实际值。

共享 ABI 的不可重绑定值参数例外地已有完整的独立拥有存储：调用端通过既有
值参数物化入口建立聚合副本，按地址交给被调函数，清理也读取该地址当前的内容。
因此对其可变字段的赋值可以复用这份存储，不能再无条件复制一次。固定布局
按值 ABI 只复制裸表示，仍需入口拥有副本；不可重绑定的引用参数及纯标量不新增
保活。判断依据是绑定可变性、值语义及 ABI 存储方式，不依赖具体函数或类型名。

开发者进一步要求在保证语义和行为正确的前提下尽量降低开销，因此入口拥有副本
还需要通过函数体使用方式筛选。通用 AST 查询区分读取一个值与暴露原存储：
复制到绑定、作为显式实参或返回值沿用既有复制／保活机制；直接写入、取地址、
作为方法接收者及无法证明安全的使用保持入口独立所有权。递归检查控制流、
defer 和异常分支；捕获继续使用既有 capture cell。按名称扫描遇到遮蔽时宁可
保守，未知 AST 种类也不放行，不进行基于生成文本或用例形状的识别。

由此，“类型含可变字段但函数体只复制并返回”的既有 ARC 用例仍应为 2 次 retain，
其原断言保持不变；无法证明只读的受管参数保留独立拥有与清理。

### 经批准的既有断言调整

首版参数独立存储增加了生成 C 的临时变量，使现有
`test_value_method_capture_codegen_has_direct_closure_lowering` 中唯一的
`FengCallableValueDescriptor` 变量由 `_callable_value_desc3` 变为
`_callable_value_desc7`。两版都通过该描述符的 `aggregate_capture_desc`
完成相同的聚合捕获；原断言在检查行为的同时依赖了临时编号。完善共享存储复用
后该例不再增加入口副本，仍保留下述已批准的与编号无关的结构检查。

开发者已批准仅调整这一条断言：从唯一描述符声明提取实际变量名，再验证该变量
的 `aggregate_capture_desc` 访问。其余既有用例及断言不变；本项仍要求
真实描述符参与捕获，不能只检查无关联的成员名是否存在。

这组测量隔离编译器发码差异，不直接替换此前五语言归档报告。

## 后续核心层优化边界

本轮已将可证明的只读遍历转为借用，并消除一部分默认初始化成本，不意味着核心层
已没有优化空间。生成代码仍显示新分配节点的字段经过通用 aggregate assign／take，
销毁仍通过描述符遍历；下一步可继续研究新鲜存储的直接初始化／转移及静态已知槽的
生命周期展开，须补齐部分初始化、异常和终结器顺序的通用证明。

union 紧凑布局仍是内存方向，涉及 ABI，应单独设计并人工决策。本轮未更改 std、
runtime API 或对象布局，`text-scan` 的上层库优化继续保持后置。
