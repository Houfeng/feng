# Feng union 布局与 aggregate 按索引遍历优化方案

> **状态：第一阶段实现及 Linux 全量回归完成；macOS 全量回归待人工运行；后续性能评测安排在第二阶段完成后。第二阶段未实施。日期：2026-10-15。**
>
> 本文提出两阶段方案：先扩展通用 aggregate 遍历机制，再迁移 union 布局。
> 已确认采用 `managed_slot_choice_offset`，0 表示未设置，非零值为实际字节偏移加 1。
> 本轮仅实施通用机制、补齐用例并全量回归，暂不改造 union。

## 1. 目标与已确认的边界

降低 union 值及包含 union 的对象、数组的内存占用，同时保持语言语义、生命周期行为
和现有性能优势。binary-trees 是验收场景之一，实施必须适用于所有 union，不能针对
`Option<Node>`、节点类型或某个评测用例添加特殊处理。

已确认的方案边界：

1. `FENG_SLOT_FORWARD` 保持不变，继续服务于需要逐值保存生命周期描述的场景。
2. 给 `FengAggregateDescriptor` 增加可选的 `managed_slot_choice_offset`：未设置时
   遍历全部 slots；设置时，从值中读取索引，只处理对应的一个 slot。
3. union 将各直接 member 的生命周期信息放入静态 slots，以现有 tag 选择对应项。
   union 值改为 **tag + inline payload + 必要的对齐填充**，移除实例中的 `_fwd`。
4. 保留当前 `uint32_t tag`，不改为一字节，不新增 256 个 member 的限制。
5. 新通用机制和 union 迁移分两阶段，分别验证；第一阶段的正式 union 仍使用原布局。
6. 保持 `feng_release(void *)` 单一实现及现有 aggregate API 签名，不增加释放入口。

不包含对象头压缩、空指针编码、payload 装箱、分配器替换、ARC 增减消除、编译选项
调整或其他库优化。std 的 `Option` 源码不需要为此修改。

当前已实现的行为以 [union 规范](../specifications/feng-union-type.md)、
[union 开发设计](feng-union-type-dev.md) 和
[值模型实现说明](feng-value-model-delivered.md) 为准。通用选择协议收敛至值模型说明 §3.2.1，
本文跟踪变更范围和验证。第二阶段迁移前再更新 union 主规范及关联文档；当前 union
的物理布局和发码保持不变。

## 2. 现状与收益边界

### 2.1 当前结构

当前 union 的静态 aggregate 描述符包含一个指向实例 `_fwd` 的 `FENG_SLOT_FORWARD`。
`_fwd` 再描述当前 payload 的生命周期。tag 决定语言层的 member 身份，两者职责不同。

在当前 64 位布局中，`FengManagedSlotDescriptor` 占 24 字节：`size_t offset`、kind、
对齐填充及 nested 描述符指针。它保存在每份 union 值中，因此复制、数组存储和对象
内嵌字段都会承担这部分空间。保留通用转发机制，并不要求每种 union 都继续使用它。

若 tag 选择的 member 及其生命周期信息能由具体 union 类型的静态描述符确定，就可
将这部分信息从每份值搬到共享描述符中。未闭合的泛型本身不必生成最终描述符；在
具化点生成具体描述符，并通过既有具化依赖传给共享函数体。

### 2.2 已有测量与布局估算

以下是现有 binary-trees 深度 16 的黑盒结果，耗时与进程峰值 RSS 均取正式样本中位数。
它们是优化前基线，不是本方案的验证结果：

| 平台 | Feng 耗时（ms） | Swift 耗时（ms） | Feng RSS（MiB） | Swift RSS（MiB） |
| --- | ---: | ---: | ---: | ---: |
| macOS ARM64 | 265.661 | 298.864 | 30.11 | 13.89 |
| Linux ARM64 | 364.631 | 419.649 | 29.27 | 27.95 |

来源：[macOS 报告](../../benchmarks/results/2026-10-15T06-29-04-172Z/report.md)、
[Linux 报告](../../benchmarks/results/2026-10-15T06-23-35-884Z/report.md)。两平台的绝对
RSS 不直接互比；验收应比较各平台同一环境中的前后结果及同轮 Swift。

在维持当前 64 位指针对齐、对象头和节点字段的条件下，预期布局为：

| 项目 | 当前 | 迁移后估算 |
| --- | ---: | ---: |
| `Option<Node>` | tag／填充 8 + `_fwd` 24 + payload 8 = 40 B | tag／填充 8 + payload 8 = 16 B |
| 含两个 `Option<Node>` 的节点 | 对象头 24 + 字段 80 = 104 B | 对象头 24 + 字段 32 = 56 B |

这意味着每节点请求的布局空间预计减少 48 B，约 46.2%。**这不是 RSS 降幅预测**：
实际分配档位、页占用、分配器留存和其他进程内存都需实测。静态 member 表也会增加
部分只读数据，其大小与具体类型数和 member 数有关，而非 union 实例数。

验收目标是降低内存且保持对 Swift 的速度优势；若内存仍明显高于 Swift，需要评估
速度优势是否足以支持这一取舍。当前不能承诺内存与 Swift 持平或给出优化后的耗时。

## 3. 通用 aggregate 按索引遍历机制

字段编码、使用前提、操作次序及新旧模式组合的唯一规则见
[值模型说明 §3.2.1](feng-value-model-delivered.md#321-按值选择活动-slot)。

第一阶段仅增加描述符字段，并在普通 aggregate 和循环收集两个入口中计算遍历范围。
不抽取新的 helper；选择后沿用现有 slot kind 分派、visitor 和嵌套递归，不
增加 `FENG_SLOT_SELECT`，不修改 `FengManagedSlotDescriptor`，不增加释放函数。

普通描述符未指定新字段时保持零值。按最小实现原则，偏移与索引有效性属于
私有 ABI 使用前提，不新增逐次防御性检查。新增模式判断的成本单独验证，不预先认定为零。

### 3.1 第一阶段验证发现的既有循环收集问题

以下两项均已用修改前 runtime 复现，人工已批准本轮一并修复：

1. 对象／闭包的 aggregate 字段在断边写回及复活 BFS 中被误当成普通指针；
   既有 `FENG_SLOT_FORWARD` 也受影响。这两个入口应与只读扫描一样使用字段的
   `aggregate_desc`，复用现有 aggregate walker。
2. 进入终结器前只恢复组内引用，遗漏组内到组外存活对象的引用。普通指针字段也能
   复现：对象复活后，外部子对象计数应为 2、实际为 1。修复遵循
   [生命周期规范 §13.2](../specifications/feng-lifetime.md#132-终结器执行流程)：
   恢复全部出边后执行终结器；依据执行后的字段和存活判定，清除待回收对象的组内边，
   并释放其剩余组外引用。存活对象先移出待回收列表，避免后续外部析构回调使列表
   留下悬空指针。继续使用 `feng_release`，不新增 API、持有结构或另一套释放逻辑。

无终结器的整组回收快路径保持不变。新增验证覆盖普通字段、aggregate、数组、
共享外部对象、部分复活、终结器替换字段及外部析构回调；既有用例断言保持不变。

发现方式是补充本阶段的循环收集／复活组合用例，再移除新选择机制做独立基线复现：
旧 `FENG_SLOT_FORWARD` 对象环在旧 runtime 中触发 ASan 非法地址读取；只有普通指针
字段的自环复活后，组外 leaf 的引用计数为 1、应为 2。

历史追踪也确认了遗漏来源：`4da72ec8`（2026-04-28）引入带终结器的两阶段循环
收集时，仅恢复组内引用；`945f0fb7`（2026-05-31）增加对象字段的 `aggregate_desc`
时，适配了只读扫描，但没有同步断边写回与复活 BFS。因此这两个问题早于本轮。

既有 runtime 循环夹具 `CycNode` 使用普通指针字段，forward 用例单独验证
retain／release／assign／take，未组合对象 aggregate 字段与终结器循环回收。
既有复活用例验证组内对象及组内叶子，未检查复活对象对仍由组外独立拥有的 leaf
是否保留正确计数。这是组合覆盖缺口；ASan 不会替代尚未执行的路径或引用计数断言。

## 4. union 迁移方案

### 4.1 tag 与静态 slots 一一对应

每个已闭合、实际使用的 union 类型生成具体 aggregate 描述符。slots 的顺序及数量
与现有归一化直接 member 列表一致，tag 无需重新编号：

| member 的生命周期分类 | 对应 slot |
| --- | --- |
| trivial | `FENG_SLOT_NONE` |
| managed pointer | `FENG_SLOT_POINTER` |
| aggregate | `FENG_SLOT_NESTED_AGGREGATE`，引用该具体 member 的描述符 |

同一个具体 union 的所有表项都指向同一 payload 起始偏移，包括 `NONE` 项。不能删除
trivial 项后压缩表，否则 tag 与索引会错位。不同 union 类型的 payload 偏移不必相同。
嵌套 union 仍有各自的 tag 与描述符，不按生命周期分类合并 member，也不展平语义身份。

union 的 aggregate 描述符将 `managed_slot_choice_offset` 设置为
`offsetof(UnionType, tag) + 1`。
值中只保留现有 `uint32_t tag` 和 inline payload，以及 ABI 所需填充；不保存实例
`_fwd`，不改为实例描述符指针，不增加堆分配。

### 4.2 泛型布局是迁移前必须核实的条件

当前共享泛型函数体会借助开放 union 的 C 载体取得 payload 偏移，具体空间大小则由
具化描述符提供。删除 `_fwd` 后，不能假定开放载体与所有闭合载体的自然 C 布局仍然
一致。例如开放 member 的指针表示与闭合后的较小标量可能有不同对齐要求。

迁移必须保证：共享函数体使用的 payload 偏移，与它处理的各具体载体一致，且满足
实际 member 的对齐；不能只从结构体声明中删除一行就认为完成。先盘点现有表示和
目标 ABI，明确统一的前缀／对齐规则，再同步生成具体布局、投影偏移和描述符。
不按某台机器硬编码偏移 8；若现有具化协议无法表达必要信息，须先补充方案并由人工
Review，不能在实现中自行增加另一套实例元数据或 FT 协议。

跨包场景继续利用已有 FT 类型信息及具化依赖，在闭合点生成静态描述符并传给共享
函数体。不得从 `reified_agg_deps` 猜测活动 member 或遍历该依赖表完成生命周期管理；
生命周期仍由当前值与 `managed_slots` 决定。

### 4.3 保持已有静态优化与语言行为

已知类型的发码已有按 tag 分支、直接处理成员的路径，保留这些路径；不能为了统一
新表机制，把可静态完成的清理重新改成通用 runtime 调用。

默认零值仍由归一化后的第一个 member 决定，tag 为 0；移除 `_fwd` 初始化不等于
可以把所有 union 默认初始化替换为清零。保留成员匹配、转换、嵌套身份、复制／移动、
析构次序、异常展开、循环收集和对象复活的原有行为。

重建受影响的 runtime、std、原生库、`.fb` 及项目缓存，不混用旧新制品。
不额外实现双 ABI 兼容层；也不因重建需要改变工具链选择或发行目录结构。

## 8. 性能验证计划

### 8.1 分离两阶段的成本与收益

按人工安排，第二阶段完成后再执行性能评测；在同平台、同工具链和相同构建选项下
对照三个可复现版本：

| 版本 | 用途 |
| --- | --- |
| B0：迁移前 | 确认当前行为、布局与性能基线 |
| B1：第一阶段 | union 仍为旧布局，单独测新增模式判断对原 aggregate／forward 路径的影响 |
| B2：第二阶段 | 对照 B0 与 B1，测静态表、实例缩小及复制量减少的整体效果 |

除正式黑盒评测外，用受控的普通 aggregate、嵌套 aggregate、数组及泛型路径对照
顺序／按索引遍历。观察 retain、release、assign、take 和循环扫描，不能只测节点释放。
这些诊断不改变正式评测程序，也不构成引入类型特判的理由。
