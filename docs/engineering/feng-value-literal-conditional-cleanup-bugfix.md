# 值对象字面量构造期清理登记修复

> **状态：2026-10-16，最小正确性修复已实施，Linux 全量回归及性能复测完成，待人工 Review。**
>
> 本文沿用此前 Review 的文件路径。本轮只复用既有机制补齐清理登记；
> 按异常信息减少登记及其他优化，转入[独立优化方案](feng-exception-cleanup-registration-optimization.md)，本轮不实施。
> [旧补丁文档](feng-value-literal-partial-cleanup-bugfix.md)只保留发现过程与历史证据，不恢复旧 patch。

## 1. 问题与目标

`@value` 字面量已经取得部分字段资源，后续显式字段求值抛异常时，构造结果尚未
交给消费者，也未登记自身清理责任，导致已写入资源遗漏释放。该问题早于 union
布局优化，复现过程见旧补丁文档。

本轮补齐这一生命周期区间，采用与现有局部拥有者一致的登记机制。异常、正常完成
及提前退出均必须准确转移或释放已有拥有权，不改变字段求值顺序或语言行为。
语言规则只引用[异常规范](../specifications/feng-exception.md)和
[生命周期规范](../specifications/feng-lifetime.md)。

## 2. 最小实现范围

实现仅修改 `src/codegen/codegen.c` 的值对象字面量路径：

1. 默认字段初始化及用户构造函数完成后，在第一个显式字段求值前，为含托管槽
   或采用具化存储的构造结果建立临时编译期作用域。
2. 将原存储纳入该作用域的拥有者列表，调用既有 aggregate／具化存储登记入口。
   默认字段或构造函数可能已取得资源，所以不能固定等到第二个字段才登记。
3. 保持原有字段求值和写入过程。后续异常通过既有清理链回收部分构造值；
   `return` 等退出通过既有作用域清理发码处理。
4. 正常完成时使用既有 `cleanup_pop_only` 状态，按 LIFO 顺序撤销构造保护，
   将原拥有权交给消费者，不额外 retain、release 或清空完成值。

没有需要清理资源的固定布局值，不增加清理登记。对需要清理的值，本轮不查询
初始化表达式是否可能抛异常，也不增加运行时判定。登记、撤销和字段释放都复用
既有实现，不新增 runtime API／ABI、节点种类或 LLVM 插件逻辑。

撤回前一候选版本的字段异常结果查询、语义分析修改和编译器内部的“省略节点”
标记。普通局部变量、tuple、std、DAP、union 布局和循环识别保持现状。

## 4. 正常路径成本与两步交付

人工已决定先补齐正确性，再独立优化登记。本轮直接登记会增加部分成功构造路径
的节点初始化和清理链维护，即使字段本次不抛异常；不能将“没有新增 ARC 对”
等同于没有成本，也不能预先假定 ThinLTO 会全部消除。

本轮交付条件是缺陷修复、既有行为保持及完整回归通过，实际成本单独报告。
减少登记、复用登记或改用静态异常清理的方案和性能目标只在独立优化文档定义，
不以扩大本次实现范围消化成本。发现新的额外成本取舍仍需人工决定。

本轮在 Linux ARM64 容器中，以 `3dbdb9c2` 为基线，使用相同工具链、Release／
ThinLTO 及标准评测输入。两个版本交错采样，先预热 2 轮，再测量 15 轮；
每次执行均校验输出。复用现有评测器，没有修改正式评测框架。

| 标准用例 | 修复前中位数 | 本轮中位数 | 差值 |
| --- | ---: | ---: | ---: |
| nbody | 654.258 ms | 653.640 ms | −0.09% |
| binary-trees | 322.219 ms | 323.317 ms | +0.34% |
| text-scan | 108.427 ms | 108.108 ms | −0.29% |
| fannkuch-redux | 1667.530 ms | 1668.916 ms | +0.08% |
| spectral-norm | 103.370 ms | 103.202 ms | −0.16% |

五项生成 C 和最终二进制均与基线逐字节相同，以上差值是同一程序的测量波动。
binary-trees 和 text-scan 的 RSS 中位数也分别保持 17.266 MiB 和 245.480 MiB；
小程序的页级 RSS 差异不作为内存优化证据。

| 构造密集诊断（每次 3200 万次构造） | 修复前 | 本轮 | 耗时增量 |
| --- | ---: | ---: | ---: |
| 初始化无异常 | 312.468 ms | 325.761 ms | +4.25%，约 0.42 ns／次 |
| 可能抛异常，实际成功 | 310.395 ms | 326.110 ms | +5.06%，约 0.49 ns／次 |

两种诊断的 RSS 中位数均为 1.5625 MiB。生成 C 在两种构造中都新增了既有
`feng_cleanup_push`／`feng_cleanup_pop`，未增加字段 retain／release。
因此本轮不能宣称所有成功路径都没有退化；这是本次先补齐登记的实际成本，
后续优化应以当前正确实现为基线，再分别减少无必要和必要登记的成本。

日志、采样及校验结果保存在本地 `temp/value-cleanup-registration-20261016/`。
仅提交本文的结论，不提交临时评测制品或 `benchmarks/results/` 内容。
