# 值对象字面量按异常信息登记构造期清理

> **状态：修复方案待 Review，尚未实现或验证。日期：2026-10-16。**
>
> 替代[已废弃的无条件登记方案](feng-value-literal-partial-cleanup-bugfix.md)。
> 原 patch 已删除；本文定义后续修复方案，不表示已应用修复。

## 1. 问题与目标

`@value` 字面量的前一个字段取得托管资源、后一个字段求值抛异常时，正在构造的
值尚未交给消费者，也没有自己的清理责任方，导致已写入资源遗漏释放。该问题已在
union 布局改造前复现；发现过程与旧方案验证记录保留在上述归档文档中。

修复应复用现有异常分析、作用域所有权管理和 runtime 清理链。在保证初始化失败
正确清理的前提下，尽可能消除正常路径的额外开销；不以特定类型、库或评测用例为条件。
语言行为仍以[异常规范](../specifications/feng-exception.md)及
[生命周期规范](../specifications/feng-lifetime.md)为准。

旧方案对所有含托管字段或使用具化存储的值对象字面量登记构造期清理，包括后续
求值已可证明无异常的情况。本方案在编译期决定是否生成登记，不增加运行时的
“是否可能抛异常”判断。

## 2. 需要保护的构造区间

登记条件为：正在构造的值已经持有或可能持有需要清理的资源，且后续求值可能使
异常离开当前构造过程。不能证明没有这种异常时，保留保护。

- 判断范围是整个字段表达式，包括接收者、实参、嵌套表达式及实际发生的调用，
  不能只检查最外层调用。
- 外围 `catch` 接住异常，仍然意味着当前构造失败，不能据此省略清理。
- 字段表达式内部完整捕获异常并继续返回值，且处理代码也不向外抛异常时，可将
  该字段视为不会因异常中断外层构造。
- 默认字段或构造函数可能已在显式字段求值前放入资源。因此，第一个显式字段
  就可能需要保护，不能固定等到第二个字段或第一个显式托管字段完成后才登记。
- 跨包调用使用已有 FT 异常摘要。泛型及间接调用复用现有求解结果；共享函数体
  不能根据某一次具化的无异常结果省略所有实例需要的保护。未知或缺失信息不等于无异常。

优先省略整个不必要的构造保护。需要保护时，复用现有构造作用域的登记与退出流程，
不逐字段反复 push/pop，也不通过改变字段求值顺序、提前计算后续字段来消除风险。

## 3. 最小实现方案

### 3.1 复用语义阶段的异常边界分析

当前公开接口提供声明和调用点异常事实；调用点摘要本身不足以表达整个字段表达式，
经过外围 catch 处理后的摘要也不能直接用于此处。

在 `src/semantic/exception_effects.c/.h` 中复用已有表达式分析和求解器，参照 `defer`
边界保留自身异常根的方式，为字段求值提供边界内的完整摘要。内部 catch 按原规则
参与求解，外围 catch 不消除该边界需要的保护。Codegen 只消费已完成分析的事实，
不另建异常推导算法，也不修改异常判定规则或 FT 格式。

### 3.2 分开编译期所有权与运行时登记

在 `src/codegen/codegen.c` 的值对象字面量构造路径中，将构造存储纳入编译期作用域
所有权管理；是否生成 runtime 清理节点由上述事实决定。记录节点是否实际登记的
状态只存在于编译器，不增加运行时标志或分支。

| 情况 | 发码要求 |
| --- | --- |
| 没有需要清理的资源 | 不增加构造保护 |
| 后续求值已证明不会向构造外抛异常 | 不生成额外的清理链 push/pop |
| 无异常，但存在离开构造过程的 `return` 等控制转移 | 在相应退出路径释放构造存储，由编译期作用域管理清理责任 |
| 后续可能抛异常或无法证明 | 使用现有 aggregate／具化存储清理节点保护 |
| 构造正常完成 | 撤销实际登记的临时保护，按原流程转交已有拥有权 |

不能只删掉 push 而保留 pop；正常完成、异常展开和提前退出都必须与实际登记状态
一致。复用现有字段存储、aggregate 描述符与释放逻辑，保持字段求值临时值、部分
构造值和外部局部值之间的清理顺序，防止遗漏或重复释放。

### 3.3 变更边界

实现限于字段表达式异常事实的提供及值对象字面量构造期清理发码。补充独立 Semantic、
Codegen、FCTS 和必要的 CLI 跨包用例；既有用例不得未经批准修改。

不改 runtime API／ABI、LLVM 异常插件、union 布局、循环识别、DAP 或 std；
不将本轮扩展为 tuple 等其他构造路径的清理优化。默认初始化和构造函数执行顺序保持不变。

## 4. 正常路径成本与验收边界

- 已证明无异常的构造，不应因本修复新增运行时清理登记、retain/release 对、堆分配
  或条件分支；提前退出所需的释放只在实际退出路径执行。
- 可能抛异常的构造，即使本次正常完成，使用现有清理链仍有登记和撤销成本；
  这些成本不能用“不新增 retain/release 对”掩盖，也不能假定 LLVM 一定会将其消除。
- 新登记还可能使原本不需要清理边界的函数或 try 区间产生相应 marker，验证须同时
  检查这一成本，不能只计一次局部 push/pop。
- 以修复正确且性能持平或提升为验收目标。若保护路径出现新增成本或退化，应如实列出，
  交由人工决定下一步方案，不自动视为已接受。五项评测持平不能代替构造密集场景验证。
