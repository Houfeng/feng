## 范围与依据

修复成员 Completion 及对应候选 Resolve：数组 fit 缺失、泛型签名未代入、调用／字段／下标结果丢失类型绑定。源码、编辑恢复和跨包 FT 必须一致。

语言规则引用 [fit](../specifications/feng-fit.md)、[内建及数组 fit](../specifications/feng-fit-builtin-type.md)、[可见性](../specifications/feng-visibility.md)，不在本文重新定义。请求性能和缓存行为沿用 [LSP 性能方案](feng-lsp-performance-optimize.md)；省略返回类型时消费已有有效类型事实，遵循 [callable 返回类型方案](feng-lsp-inferred-callable-return-type-bugfix-pending.md)。

用户已撤销上一轮实现，要求在原实现基础上修复，禁止“前置新路径，失败再执行旧路径”。不修改核心语义、runtime、ABI、FT、标准库或用户项目；不扩展 Hover、Definition、Signature Help 的功能范围。

## 根因与实现约束

旧 AST／symbol 接收者状态已保存完整类型引用，但 fit 枚举仅使用类型声明或内建名称。数组无法进入查询。候选 formatter 直接读取声明，调用转换也直接读取声明返回类型，没有持续应用接收者和方法泛参绑定。

1. 保留既有请求入口、作用域收集、文本修复、索引生命周期、可见性与静态／实例过滤。
2. 在原成员查询位置统一消费完整接收者类型。AST、Semantic、FT 是输入适配来源，不能分别维护目标匹配规则。
3. 结构匹配保留数组层级及可写性、声明身份、泛型实参和泛参声明身份。匹配与泛型替换共用绑定，候选签名、字段、调用结果和后续链式查询都消费该绑定。
4. 扩展或整合原接收者解析，删除被替代的补全专用实现；共享给其他 LSP 请求的助手保留。不得保留新旧成员补全算法互相兜底。
5. 优先使用现有 AST 和已发布类型事实；当前 AST 确实缺少表达式时才通过现有 parser 恢复接收者。不得复制表达式语法或重新分析函数体。
6. 未知／歧义结果不选第一个同名重载；合法且信息充分的结果必须支持。开放泛参仅显示约束提供的成员。
7. 复用现有签名格式化与 JSON 输出。请求内实例化结果统一释放，同一候选签名只构造一次。候选 Resolve 保留精确声明和有效版本，不退回同名猜测。
8. 不添加类型名、变量名、方法名或项目特判；不新增 Python／`.inc` 文件。

## 问题与验证记录

后续发现的问题先记录现象和证据，再分析、解决。未确定的方案及额外范围由人工决定；不得把环境失败记为代码修复成功。

### B01 基线实测

独立构建撤销后的 `19f76734`，通过真实 `feng lsp --stdio` 验证：`int[]` 的 `fit T[]` 候选为空；`Box<int>` 的扩展签名仍显示 `func marker(value: T): T`；`Box<string>` 的 `value.item.` 未返回 string 的扩展成员。协议输入和结果保存于系统临时目录的 `feng-lsp-fit-baseline.json`，执行文件位于工程 `build/lsp-fit-baseline/bin`。

当前实现将两条原成员补全分支接入同一个完整类型查询，删除被替代的 AST／FT 文本接收者状态机及不再使用的补全助手；已通过 `-Wall -Wextra -Werror` 编译。签名实例化后交由现有 member formatter 输出。

### I01 局部声明的类型输入

新增首个数组用例 `let value: int[] = []; value.` 返回空。原因是原 `local_receiver_type` 仅覆盖参数／收窄绑定等，局部 binding 的显式类型需读取 `binding->type`；统一转换遗漏了该输入，转而读取空数组初始化值。修复是在同一局部变量转换中优先消费声明类型，再使用已有事实／初始化值，不增加回退算法。

### I02 限定模块名的函数调用

专项用例 `fit_completion.values().` 返回空，而同模块 `values().` 正常。限定路径查询将当前模块也按外部模块过滤，只保留公开函数。按实际模块身份决定可见性，源码／FT 一致处理；外部源码仍使用既有导入可见性检查。

### I03 FT 方法泛参约束的展示

审查统一签名适配发现，FT 方法泛参仅转入名称，未转入已有约束元信息，会使源码与 FT 的签名不一致。适配时读取现有 `constraint_kind` 和 `value_type`，经同一绑定代入约束中的类型参数，并补充源码／真实 FT 的约束签名用例；不改变 FT 或语义规则。

直接读取新夹具的 FB 确认：外层 `T` 在方法约束中保存为未绑定的单段 NAMED，方法参数中则为 TYPE_PARAM_REF。统一适配对无目标声明、无实参的单段引用先按精确词法作用域解析泛参，与源码规则一致，再进行名义类型查询；不按参数拼写特判。

### I04 手动脚本插入锚点

`test_lsp_chained_member_completion.py` 和 `test_lsp_mixed_receiver_completion.py` 使用已从 TUI 示例删除的语句作为插入锚点。两处均经人工批准，仅改为现有 `app.init();`，原查询、断言和时间门槛不变。

### I05 上下文推导与链式查询的边界核实

核对 `values<T>(item: T, n: i32): T[]`：在返回类型明确为 `string[]` 的函数中直接 `return values("x", 1);`，基线检查通过。原完整打包夹具将 `values("x", 1).strings()` 放在返回 `int` 的表达式内，编译报 AE0512；显式 `<string>` 则通过。

初次判断未分开独立语句与外层返回类型上下文，错误地据此将部分泛型推导的链式编辑状态设为空候选负例。I08 复核确认独立语句合法，因此这些负例不能作为正确性依据，必须修正。当前 AST 已有有效类型事实时优先消费该事实的原则不变。

### I06 macOS 全量回归中的 SIGKILL

I07 修正前的一次完整回归在既有 `native-eh-package` CLI 用例处中断：shell 报生成的 `native_consumer` 被 signal 9 终止，随后退出码断言失败。此前编译器各层测试通过，无 ASan／UBSan／LSan 错误报告。先保留原生成物并原样重跑，再核对系统记录；不据此改动编译器、用例或超时。是否由本机安全软件导致，须以系统证据区分，不能仅凭信号断言。

同一生成物原样重跑（保留 `detect_leaks=1`）退出码 0，输出 `native-package`，没有 sanitizer 诊断。系统日志可见同一 PID 被安全软件扫描，但没有明确的终止原因，故不认定来源。随后保持代码、配置和用例不变，从头重跑 `make test` 并通过；I07 后的最终全量回归也通过。

### I07 已发布语义快照的成员身份

两平台首次全量通过后的真实项目核对发现：完整 `list.length();` 输入发布成功语义分析后，候选仍存在，但 Resolve 没有文档。候选携带 `std-0.1.0.fb!mod/std/collections.ft` 路径和全 0 坐标。原因是合成 AST 属于已发布语义快照，不能按物理源码位置重新查找。

统一按数据所有者保留精确身份：语义快照候选记录快照代次和模块／程序／声明／成员序号；当前解析源码使用源码坐标；持久 FT 索引使用索引序号。Resolve 只读取身份所属的同一有效快照，不按名称搜索其他来源。该规则适用于所有语义候选，不针对 FT、数组或某个方法特判。补充完整合法输入、等待语义发布、重载文档与失效候选覆盖，再重新执行两平台全量回归。

### I08 交付复核：合法泛型链式编辑状态仍缺候选

按用户复核问题，以相同核心编译器对象分别链接基线与当前 LSP，通过真实项目 `feng check` 验证：

- `func probe() { values("x", 1).strings(); }`：修复前后均通过。
- `func probe(): int { return values("x", 1).strings(); }`：修复前后均报 AE0512；显式 `<string>` 通过。这是已有的返回上下文推导问题，不能推广为所有链式调用都不合法。
- 当前 LSP 对完整独立语句返回 `strings`，对新打开的 `values("x", 1).` 编辑状态返回空；显式 `values<string>("x", 1).` 返回 `strings`。

原因定位在 `member_call_type`：语法推导将整数常量视作默认整型，与形参 `i32` 的结构匹配失败后丢弃先前从首个实参获得的 `T` 绑定。核心编译器允许该实参的上下文适配；LSP 因而遗漏合法结果。当前源码矩阵的 `partial inference cannot escape` 及对应跨包负例预期有误。需修正补全并迁移这些预期，保留真实冲突、未知和歧义的负例；此处保留 `5423d624` 交付复核时的证据；后续修复、经批准的负例迁移及新增验证已完成，详见 [链式上下文修复文档](feng-generic-chain-context-bugfix.md)。
