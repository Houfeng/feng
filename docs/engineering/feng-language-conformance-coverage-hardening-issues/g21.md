## ISSUE-G21-001：数组层数在 `.ft v1` 与 Semantic subject key 中分别受 32 / 64 位固定容量限制

### 归属

- 发现组：G21 实施前审计；
- 关联组：G23 的 array fit / witness，但一般 fit 语义仍归 G23；
- 发现用例：ARRAY-D04～ARRAY-D06。

### 现象与结论

- `src/symbol/ft_write.c` 当前把数组 rank 写入一个 record，并用 32 位字段保存逐层可写位；rank 大于
  32 时直接报告内部错误。若只删除该 guard，第 33 层以后的 `!` 会丢失，不能视为修复；
- `src/semantic/semantic.h` 的 array subject key 使用单个 `uint64_t writable_mask`，
  `feng_semantic_subject_key_init_array_from_type_ref` 在 rank 达到 64 时返回失败。因此普通类型路径虽然
  使用递归 / 动态结构，超过 64 层的 array fit / witness 身份仍不能建立；
- 两个限制来自内部表示宽度，不是语言语义。它们会使同一个公开数组类型在源码内、导出时和作为
  spec subject 时得到不同结果，属于产品缺陷和测试缺口；
- 语言结论：Feng 不设置固定的数组嵌套层数上限，所有实际出现的有限层数及每层 `!` 都必须精确保留。
  33 / 65 层仅作为越过现有固定容量的回归样本，不形成新的上限。

### 决策与实施

- 状态：语言处理方案已批准，待 G21 实施；
- 分类：产品缺陷、跨包一致性缺口和测试缺口；
- 批准方案：`.ft` 与 Semantic subject key 均改用可随实际类型结构扩展的表示，禁止把 32 / 64 换成
  更大的固定常量，也禁止截断可写位。`.ft v1` 优先复用已有可组合类型 record，以递归或分段方式保持
  旧 reader 可理解的表示；如果完整修复确实需要改变 `.ft` wire 格式或版本，必须先暂停并取得人工
  决策；
- 是否涉及既有测试修改：默认否，新增 33 / 65 层的 Parser、Semantic、Symbol、Codegen 和 FCTS
  回归；若必须修改既有断言，先列出精确名单并再次取得批准；
- 是否涉及运行时性能：否。类型层数和 subject key 仅在编译期处理，生成程序不得新增运行时字段、
  判断、分支、调用、分配或 ARC；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：不得修改 runtime 私有 ABI 或公开 ABI；`.ft`
  内容表示属于本问题范围，但格式 / 版本变更尚未概括授权，触发时须再次决策。

### 验收与关闭

- 待 ARRAY-D04～ARRAY-D06 及 G21 独立全量回归完成后填写。

## ISSUE-G21-002：`Type[:n]` 在范围检查前直接窄化为 `size_t`

### 归属

- 发现组：G21 实施前审计；
- 关联组：G04 的整数语义、G18 的元素默认零值；
- 发现用例：ARRAY-D21～ARRAY-D25。

### 现象与结论

- Semantic 当前只检查 `n` 的静态类型是否为整数，没有检查可确定值的非负范围；
- `cg_emit_array_new` 当前先把 `n` 直接转换为 `size_t`，再调用数组分配函数。负数会变成大无符号值，
  比 `size_t` 更宽的整数在窄目标上还可能截断；runtime 现有乘法、对象总大小和 OOM 防御只能观察
  转换后的值，不能恢复原值是否合法；
- `length()` 的语言结果为目标平台 `int`。若允许数组长度超过 `int` 最大值，后续读取长度才 panic，
  会使“已成功创建的数组”不满足语言长度契约；
- 结论：当前路径没有完整实现合法长度值域，属于产品缺陷、规范缺口和测试缺口，不能把偶然的分配
  溢出 / OOM panic 当作负数或超 `int` 上界的正确诊断。

### 决策与实施

- 状态：处理方案已批准，待 G21 实施；
- 分类：产品缺陷、诊断契约缺口和运行时边界缺口；
- 批准方案：`n` 的合法范围统一为目标平台 `int` 的非负值域。编译期可确定的非法值在长度表达式产生
  新数组段诊断 `AE0204`；动态值先以其原整数类型求值一次并完成范围检查，通过后才转换为分配大小。
  动态非法值在分配及元素默认初始化前 panic，不允许截断、回绕或 UB。合法长度导致的字节数溢出或
  OOM 继续由分配路径 panic；
- 是否涉及既有测试修改：默认否，新增 32 / 64 位 Semantic、Codegen、runtime、隔离 CLI 和 FCTS
  用例；
- 是否涉及运行时性能：静态值必须在编译期消除检查；动态值只在 `Type[:n]` 创建点增加一次已批准的
  值域验证，并尽量与现有分配溢出检查收敛。普通数组读取、写入、`length()`、遍历和 ARC 不得增加
  开销；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：默认均不修改。若正确实现需要新增或改变
  runtime 私有接口，必须先提交接口、调用面、运行时开销和无 ABI 方案比较，由人工再次决策。

### 验收与关闭

- 待 ARRAY-D21～ARRAY-D25、性能约束及 G21 独立全量回归完成后填写。

## ISSUE-G21-003：限定类型路径不能作为 `Type[:n]` 的元素类型入口

### 归属

- 发现组：G21 实施前审计；
- 关联组：G02 的三种公开顶层名称访问形式；
- 发现用例：ARRAY-D20。

### 现象与结论

- 模块主规范已规定公开具名类型可通过导入短名、`import ... as` 别名和完整模块路径用于类型引用与
  构造语境；
- Parser 的 array-new 分支当前只接受标识符或“标识符 + 泛型实参”，`alias.Type[:n]` 和
  `full.module.Type[:n]` 的 target 是成员链，因而被 `SE0201` 误拒绝；
- 结论：这是 G02 已确定通用名称规则在 array-new 语法入口的实现遗漏，不需要新增模块语义。

### 决策与实施

- 状态：待 G21 实施；既有规范已唯一确定结果，无新增人工语义决策；
- 分类：Parser 产品缺陷、跨包行为缺口和测试缺口；
- 方案：让 array-new 从合法的类型目标表达式统一构造完整 type reference，支持短名、alias、完整模块
  路径及其闭合泛型形式；保持局部值优先与现有名称歧义规则，不按模块名或类型名加特判；
- 是否涉及既有测试修改：默认否；G12 的真正非类型 target `factory()[:1]` 继续产生 `SE0201`；
- 是否涉及运行时性能、runtime、ABI 或 `.ft`：否，只修复 Parser AST 与后续已有类型解析路径。

### 验收与关闭

- 待 ARRAY-D20 的 Parser、Semantic、真实 package-public FCTS 和全量回归完成后填写。

## ISSUE-G21-004：无目标的嵌套空数组字面量可能越过 Semantic

### 归属

- 发现组：G21 实施前审计；
- 关联组：G12 的数组字面量语法；
- 发现用例：ARRAY-D10。

### 现象与结论

- `validate_untyped_array_literal_expr` 当前只检查被直接用作绑定 / 参数等入口表达式的空字面量；
  `let value = [[]];` 的外层数组非空，内层 `[]` 又没有收到元素目标，因而可能通过 Semantic；
- Codegen 遇到没有元素类型的内层空数组后仍保留 `CE0182` 防御。该错误是用户源码可修复的目标类型
  缺失，按既定编译阶段边界必须由 Semantic 报 `AE0203`，不能泄漏为 Codegen `CE`；
- 有明确 `T[][]` 目标的 `[[], []]` 合法，修复不能把所有嵌套空数组一律拒绝，也不能改变既有数值
  字面量贴合算法。

### 决策与实施

- 状态：待 G21 实施；既有空数组目标规则已唯一确定结果；
- 分类：Semantic 产品缺陷、阶段错误和测试缺口；
- 方案：递归传递并检查数组元素目标；只在实际没有目标的空字面量左方括号产生唯一 `AE0203`。
  合法输入不得到达 `CE0182`；如果本次触及相应 Codegen 防御，应改为 `IE` 内部不变量错误，不开展
  与新增用例无关的 CE 全面迁移；
- 是否涉及既有测试修改：默认否，新增直接和嵌套正反向矩阵；
- 是否涉及运行时性能、runtime、ABI 或 `.ft`：否，全部发生在编译期。

### 验收与关闭

- 待 ARRAY-D10 的精确 Semantic / Codegen 边界及 G21 独立全量回归完成后填写。

## ISSUE-G21-005：用户手册把无目标 `Type[:length]` 误写为始终可写

### 归属

- 发现组：G21 实施前规范审计；
- 关联组：ARRAY-D13、ARRAY-D26；
- 发现用例：无，属于文档一致性问题。

### 现象与结论

- 中英文类型手册原文均称 `Type[:length]` “创建可写数组”；
- 内建类型与表达式主规范规定：array-new 自身不携带 `!`，无目标时推导为当前层只读的 `T[]`，只有
  明确 `T[!]` 目标才使该层可写；
- 结论：实现和主规范方向一致，用户手册描述错误；内建类型规范示例中无显式 `T[!]` 目标却写入
  `writable_nums` 的写法也必须一并纠正。

### 决策与实施

- 状态：已关闭；
- 分类：文档错误；
- 实际变更：中英文类型与表达式手册已明确无目标结果为 `T[]`、显式 `T[!]` 目标才可写，并补入长度
  值域与索引 panic 摘要；内建类型示例为可写字面量增加显式 `int[!]` 目标；
- 是否涉及既有测试修改、运行时性能、runtime、ABI 或 `.ft`：均否。

### 验收与关闭

- 本次文档更新的 `git diff --check` 已通过，新增 / 调整的相对链接均指向现有文档；ARRAY-D13、
  ARRAY-D26 的实现期 FCTS 仍须提供实际行为证据，不能仅以文档修正代替。

## ISSUE-G21-006：array-new 尚未明确没有有限默认零值的元素类型边界

### 归属

- 发现组：G21 实施前完整性审计；
- 关联组：G18 的 `AE0332` 默认零值有限性；
- 发现用例：ARRAY-D27。

### 现象与结论

- `Type[:n]` 要求每个实际元素按 `Type` 的默认零值初始化。G18 已规定没有有限默认零值的普通对象在
  实际请求默认值时必须由 Semantic 报 `AE0332`；
- 当前 array-new Semantic 分支只解析元素类型和长度，不调用默认零值有限性检查。Codegen 对没有
  可用默认零值工厂的普通对象元素可能退回零指针槽，无法满足 Feng 普通对象的默认零值语义；
- `RecursiveType[:1]` 明确会请求非法默认值，应在 Semantic 拒绝；但 `RecursiveType[:0]` 没有实际
  元素，动态长度又可能为零或正数。现有主规范与 G18 的“实际请求”原则尚不足以唯一确定这两个邻界
  是统一要求元素类型具备默认零值，还是允许编译期可证明的零长度例外；
- 结论：非零路径是产品缺陷；零长度与动态长度资格属于实施前必须明确的语言边界，不能由编译器实现
  自行选择。

### 待人工决策方案

- 方案 A：任何 `Type[:n]` 都静态要求 `Type` 具备有限默认零值。规则最简单、无运行时开销，但会拒绝
  本可不初始化元素的 `RecursiveType[:0]`；
- 方案 B：编译期可证明 `n == 0` 时允许；可证明 `n > 0` 或无法证明恒为零时，静态要求 `Type` 具备
  有限默认零值。该方案最贴合“实际请求”原则，仍不增加运行时检查，但会让资格依赖现有常量证明；
- 方案 C：动态 `n` 在运行时按零 / 非零决定。该方案会为相关 array-new 增加运行时类型资格分支，且
  可能把静态类型错误延后；不建议采用，若考虑必须另行批准运行时开销。

### 决策与实施

- 状态：待人工决策，阻塞 ARRAY-D27，不阻塞其他 G21 文档审计；
- 建议：采用方案 B，在不增加运行时开销的前提下保持 G18 的“实际请求”边界；
- 是否涉及既有测试修改：默认否；根据最终方案新增 `n == 0`、`n > 0` 和动态 `n` 正反向用例；
- 是否涉及运行时性能：方案 A / B 仅增加编译期分析；方案 C 涉及新增运行时开销，未经再次批准不得
  实施；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：方案 A / B 均不涉及。

### 验收与关闭

- 待人工确定方案并完成 ARRAY-D27、Codegen 内部防御及 G21 独立全量回归后填写。

## ISSUE-G21-007：宽整数索引在边界检查前直接窄化为 `size_t`

### 归属

- 发现组：G21 实施前完整性审计；
- 关联组：G14 的索引类型诊断；
- 发现用例：ARRAY-D28、ARRAY-D31～ARRAY-D32。

### 现象与结论

- `cg_emit_index` 当前把所有合法整数索引先转换为 `size_t`，再把转换结果传给一次运行时边界检查；
- 在当前 64 位目标上，有符号负数转换为大无符号值后仍会被 `index >= length` 拒绝，全部 Feng 整数
  位宽也不超过 `size_t`，因此既有目标上没有观察到错误；在较窄目标上，合法静态类型为 `i64` / `u64`
  的索引可能先截断成一个较小的 `size_t`，从而错误命中数组内位置；
- 语言允许所有整数类型作为索引，同时要求原索引位于 `[0, length)`。因此边界检查必须基于窄化前的
  数学值，不能把当前 64 位平台的偶然正确当作跨目标语义。

### 决策与实施

- 状态：待 G21 实施；索引有效范围已由数组主规范确定，无新增语言决策；
- 分类：目标可移植性缺口和测试缺口；
- 方案：生成代码在保持接收者、索引各求值一次的前提下，以原整数的符号与宽度完成同一次边界判定，
  只有判定通过后才转换为元素地址所需的目标大小类型。不得为具体整数类型添加散落特判；
- 是否涉及既有测试修改：默认否；G14 的 `AE1021` / `AE1022` 诊断契约保持不变，新增 32 / 64 位
  Codegen 结构和可运行目标范围内的隔离进程用例；
- 是否涉及运行时性能：索引仍只能有既有的一次边界判断，不得增加第二个动态分支、辅助分配或 ARC；
  若无法在同一次判断中完成且会增加现有目标运行时开销，必须暂停并提交人工决策；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：默认均不涉及。若方案要求改变 runtime 私有
  helper 签名，必须先取得人工批准。

### 验收与关闭

- 待 ARRAY-D28、ARRAY-D31～ARRAY-D32、32 / 64 位 Codegen 证据、性能约束及 G21 独立全量回归完成
  后填写。
