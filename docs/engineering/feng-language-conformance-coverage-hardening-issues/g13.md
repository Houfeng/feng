## ISSUE-G13-001：Semantic 未检查同一词法值作用域中的重复局部绑定

### 归属

- 发现组：G13；
- 关联组：无；
- 发现用例：BIND02～BIND06 实施前的变量作用域审计。

### 现象与结论

- 最小复现：在同一普通花括号块中连续声明 `let value = 1; let value = 2;`；
- 实际结果：`resolver_add_local_entry` 直接把新名称追加到当前 `ScopeFrame`,名称查找再从后向前返回
  最后登记项,没有执行当前作用域唯一性检查；
- 规范依据与预期结果：人工已确认同一作用域块内重复声明必须报错,只有子块可以屏蔽父块；
- 结论及根因：Semantic 局部符号登记缺少当前 scope frame 内的通用重复检查,属于产品缺陷。

### 决策与实施

- 状态：已修复；
- 分类：产品缺陷；
- 建议方案：在通用局部名称登记入口检查当前 frame,只拒绝同级重复,不得查询或拒绝父 frame 中的
  同名绑定；参数、解构及控制头绑定复用同一抽象检查,禁止为各语法形态添加特判；
- 是否涉及既有测试修改：否,新增独立 Semantic 反向用例和 FCTS 正向邻界用例；
- 是否涉及运行时性能：否,仅增加编译期 Semantic 名称登记检查；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否；
- 人工决策与批准范围：同级重复报错、子块允许屏蔽已经人工确认；
- 实际变更：Semantic 新增统一的源码局部声明入口，只检查当前 scope frame 并在后声明名称处报告
  `AE0105`；普通绑定、参数、tuple 解构、`for/in`、`match` 与 `catch` 共用该入口，派生推导和异常
  重放继续使用无诊断登记入口，避免重复报告。

### 验收与关闭

- 本组专项复验结果：Parser、Semantic、Codegen tests 通过，FCTS 1094/1094；BIND02～BIND06 的
  重复声明矩阵均在后声明的精确 token 处只产生一个 `AE0105`；
- 本组沙箱外 `make test` 结果：通过；UBSan 与 normal 两阶段均完成；
- 关闭依据：通用登记实现、反向矩阵、合法子块屏蔽运行证据与全量回归共同覆盖。

## ISSUE-G13-002：块形式 match 的头部绑定与 body 当前共用一个 Semantic scope frame

### 归属

- 发现组：G13；
- 关联组：无；
- 发现用例：BIND10 实施前对 `for`、块形式 / infix `match` 与 `catch` 的作用域实现审计。

### 现象与结论

- 最小复现：块形式 union `match` 分支在分支头绑定 `item`,随后在分支 body 直接声明同名局部
  `item`；
- 实际结果：当前 `for`、infix `match` 和 `catch` 会先建立头部 scope,再为 body 建立子 scope；块形式
  union `match` 则在同一个 scope frame 中先登记分支绑定、再解析 body 内容。现有实现尚未检查
  同级重复,因此差异暂未稳定表现为诊断差异；加入通用重复检查后会错误拒绝块形式 `match` 的合法
  body 屏蔽；
- 规范依据与预期结果：人工已确认这些控制或分支头后的花括号 body 都是独立子块,body 可以屏蔽
  头部绑定；不同分支或子句也各自独立；
- 结论及根因：块形式 union `match` 的 Semantic scope 结构与统一的头部 / body 父子模型不一致,
  属于产品缺陷。

### 决策与实施

- 状态：已修复；
- 分类：产品缺陷；
- 建议方案：统一复用“头部 scope + body block scope”的抽象结构,使块形式 `match` 与既有 `for`、
  infix `match`、`catch` 一致；不得用名称例外绕过重复检查；
- 是否涉及既有测试修改：否,新增独立 Semantic 与 FCTS 用例；
- 是否涉及运行时性能：否,只调整编译期 Semantic 作用域建模；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否；
- 人工决策与批准范围：控制或分支头后的花括号 body 作为独立子块已经人工确认；
- 实际变更：块形式 union `match` 统一建立分支头部 scope，并通过共用 result-block 入口为 body
  建立子 scope；其他 `for`、infix `match` 与 `catch` 路径保持既有父子结构。

### 验收与关闭

- 本组专项复验结果：Semantic tests 通过；FCTS 的块形式 `match`、infix `match`、`for` 与 `catch`
  头部 / body 同名屏蔽用例全部通过；
- 本组沙箱外 `make test` 结果：通过；UBSan 与 normal 两阶段均完成；
- 关闭依据：所有控制头 / body 形态均按统一父子作用域模型通过正向运行和全量回归。

## ISSUE-G13-003：未声明赋值目标产生根因诊断后的可写性级联诊断

### 归属

- 发现组：G13；
- 关联组：无；
- 发现用例：BIND01 未声明名称用于赋值目标。

### 现象与结论

- 最小复现：函数体中直接执行 `missing = 1;`，且当前可见作用域不存在 `missing`；
- 实际结果：Semantic 在 `missing` 处先报告 `AE0001`，随后又在同一位置报告 `AE0104`“赋值目标
  不可写”；
- 规范依据与预期结果：名称查找失败已经确定根因，BIND01 要求在使用位置只报告 `AE0001`，不得再由
  后续可写性诊断重复描述同一无效目标；
- 结论及根因：赋值语句先解析目标表达式并记录未声明名称错误，随后可写性校验仍把无法解析的标识符
  当作已知不可写目标处理，缺少“目标身份未知时停止派生校验”的通用边界，属于产品缺陷。

### 决策与实施

- 状态：已修复；
- 分类：产品缺陷；
- 建议方案：在通用赋值目标可写性校验中区分“已知且不可写”与“名称身份未知”；后者由名称解析阶段
  的 `AE0001` 负责，不再追加可写性诊断，不得按具体名称添加特判；
- 是否涉及既有测试修改：否，新增 BIND01 Semantic 反向用例；
- 是否涉及运行时性能：否，仅调整编译期 Semantic 诊断收敛；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否；
- 人工决策与批准范围：用户已批准实施 G13，并明确要求增补用例发现的编译缺陷先记录、再分析并解决；
- 实际变更：赋值目标可写性校验现在区分已知不可写值与无法解析的名称；未知标识符和裸模块别名
  保留名称解析阶段的根因诊断，不再追加派生 `AE0104`，已知函数、类型、类型参数和不可变绑定仍按
  原规则报告不可写。

### 验收与关闭

- 本组专项复验结果：BIND01 的读取、赋值目标和调用目标均在原始使用 token 处只报告一个
  `AE0001`；Semantic tests 通过；
- 本组沙箱外 `make test` 结果：通过；UBSan 与 normal 两阶段均完成；
- 关闭依据：根因诊断数量、位置和阶段均有精确断言，并通过全量回归。

## ISSUE-G13-004：标准库使用重复 `_` 局部，但主规范未定义 `_` 为丢弃绑定

### 归属

- 发现组：G13；
- 关联组：无；
- 发现用例：完成 BIND02 同级唯一性实现后的 FCTS 构建。

### 现象与结论

- 最小复现：同一函数块连续执行 `let _ = first(); let _ = second();`；
- 实际结果：新的同级唯一性检查按主规范把 `_` 视为普通标识符，在第二个 `_` 处报告 `AE0105`；FCTS
  构建首先在 `std/std/src/compiler/parser/FengParser.ff` 的既有源码中命中该诊断；
- 现有证据：Lexer、Parser、Semantic 与 Codegen 当前都把 `_` 当普通标识符和普通绑定处理；变量绑定
  主规范没有定义 `_` 丢弃绑定或通配模式，tuple 的丢弃位置明确写作空位；但标准库与少量既有测试
  长期使用 `let _ = call()` 表达“求值后忽略结果”，形成了尚未规范化的源码惯例；
- 结论及根因：严格落实“所有同级绑定名称唯一”后，未规范化的 `_` 惯例与正式规则发生冲突。这不是
  模块级绑定问题，也不是运行时缺陷，而是必须先明确语言语义再处理的规范决策点。

### 决策与实施

- 状态：已解决；
- 分类：规范缺口 / 既有源码兼容性；
- 方案 A（建议）：保持 `_` 为普通标识符并适用同级唯一性；在主规范中明确该事实，把仅用于丢弃调用
  结果的 `let _ = call()` 改为 `call();`，其余确需绑定的位置改用含义明确且唯一的名称；该方案不增加
  编译器特判或运行时开销；
- 方案 B：正式新增 `_` 丢弃绑定语义；需先定义它适用普通绑定、参数、`for/in`、`match`、`catch` 与
  解构中的哪些位置，并统一调整 Parser AST、Semantic、Codegen、LSP 和用例，实施范围明显超出单纯
  重复检查；
- 不建议方案：仅让名称 `_` 绕过重复检查但继续作为可引用的普通绑定；这会破坏同级唯一规则，使每次
  `_` 引用的目标依赖最近声明，语义不完整且属于名称特判；
- 是否涉及既有测试修改：方案 A 需要把既有测试源码中同一作用域的重复 `_` 改成无绑定表达式语句
  或唯一名称，需人工批准；方案 B 需要新增并调整更多测试；
- 是否涉及运行时性能：方案 A 不增加开销，去除无用局部后可能减少生成代码；方案 B 必须保证只求值
  右侧且不物化可引用局部，不得增加运行时开销；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：方案 A 不涉及；方案 B 是否影响 `.ft` 取决于
  是否允许模块级 `_`，必须在设计时另行确认；
- 人工决策与批准范围：用户明确确认“Feng 中没有 `_` 丢弃符”，因此采用方案 A；
- 实际变更：变量绑定主规范和中英文用户手册明确 `_` 是可读取的普通标识符，并适用同级唯一与
  子块屏蔽规则；标准库 Parser 与 std Lexer 测试中仅用于忽略结果的 `let _ = call()` 改为
  `call();`；新增 `_` 可读取、子块屏蔽和同级重复的正反向证据。`for let _` 等确实需要绑定的既有
  写法保持普通绑定语义。

### 验收与关闭

- 本组专项复验结果：Semantic 重复 `_` 诊断通过，FCTS `_` 普通绑定运行用例通过，std 601/601、
  FCTS 1094/1094；
- 本组沙箱外 `make test` 结果：通过；UBSan 与 normal 两阶段均完成；
- 关闭依据：人工语义决策已落入主规范、用户手册、源码与正反向用例，并通过全量回归。

## ISSUE-G13-005：BIND04 新增 FCTS 的累计期望值计算错误

### 归属

- 发现组：G13；
- 关联组：无；
- 发现用例：BIND04 tuple 空位置正向运行用例。

### 现象与结论

- 用例计算 `13 + 24 + 56`，实际结果为 `93`，初始断言误写为 `99`；
- Semantic、Codegen 与运行结果一致，空位置未创建绑定，三个非空位置组的值均正确；
- 结论：新增测试期望值计算错误，不是产品缺陷或规范缺口。

### 决策与实施

- 状态：已修正；
- 分类：新增测试缺陷；
- 实际变更：把 BIND04 FCTS 断言从 `99` 修正为 `93`，不修改被测语言行为；
- 是否涉及运行时性能、ABI 或 `.ft` 格式：否。

### 验收与关闭

- 本组专项复验结果：修正后 FCTS 1094/1094；
- 本组沙箱外 `make test` 结果：通过；UBSan 与 normal 两阶段均完成；
- 关闭依据：运行结果精确等于 `13 + 24 + 56 = 93`，语言实现无需变更。
