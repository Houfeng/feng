## ISSUE-G20-001：具名 tuple 被误当成对象构造目标并进入 Codegen

### 归属

- 发现组：G20；
- 关联组：G05、G10、G18；
- 发现用例：TUP-D08～TUP-D12。

### 现象与结论

- 最小复现：

```feng
module g20.tuple_construction;

type Pair(int, int);

func make(): Pair {
  let first = Pair();
  let second = Pair { item1: 1, item2: 2 };
  return second;
}
```

- 修复前实际结果：`Pair()`、`Pair { ... }` 和 `Pair() { ... }` 可通过 Parser 与 Semantic；随后 Codegen
  沿普通对象路径生成不存在的普通对象类型描述符，并形成指针 / tuple 值不匹配的 C，错误最终由宿主
  C 编译器暴露。带非零参数的 `Pair(args)` 虽已被拒绝，但当前落入普通对象“没有匹配构造函数”路径，
  没有指出 tuple 根本不是对象构造目标；
- 规范依据与预期结果：具名 tuple 是圆括号形式声明的值类型，不能由对象构造入口产生；新的字面量
  必须贴合具名 tuple 目标，无初始化器时使用类型默认零值，已有 tuple 值则按普通值流转或允许的显式
  转换规则使用。tuple 不声明构造函数，也不获得对象类型的隐式公开无参构造函数；普通构造和对象
  字面量入口必须在 Semantic 阶段统一拒绝；
- 结论及根因：产品缺陷。构造调用和对象字面量校验当前只检查声明种类是否为 `FENG_DECL_TYPE`，没有
  继续区分花括号对象形式与圆括号 tuple 形式；tuple 与对象在 AST 中共享 type 声明种类，因而被错误
  放入普通对象构造流程。

### 决策与实施

- 状态：已关闭；
- 分类：产品缺陷、诊断契约缺口和测试缺口；
- 建议方案：在 Semantic 建立并复用“是否为花括号对象形式 type”的统一分类判断。普通构造调用
  `Pair()` / `Pair(args)` 及带对象字面量后缀的同类调用，在 tuple 类型目标 token 产生唯一
  `AE0312`；直接 `Pair { ... }` 在对象字面量左花括号产生唯一 `AE1004`。判断必须先于构造器数量、
  可见性和字段检查，避免派生出 `AE0313`、`AE0315` 或字段级诊断；
- 是否涉及既有测试修改：预期不修改既有测试输入或断言，只新增 G20 集中式 Semantic、CLI 和
  Codegen 边界用例；若实际需要修改既有测试，必须列出精确名单并再次取得人工批准；
- 是否涉及运行时性能：否。检查只发生在编译期，不为任何合法 tuple 或对象构造增加运行时判断、
  分支、调用、分配或 ARC；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否。现有导入符号已经记录 tuple 分类；若实施
  发现必须修改任一边界，需暂停并再次取得人工决策；
- 人工决策与批准范围：已确认 tuple 不允许使用普通对象构造语法；允许在 G20 按上述稳定码和阶段补齐
  通用 Semantic 分类检查及新增用例，不改变合法对象类型、tuple 字面量或默认零值行为；
- 实际变更：Semantic 新增统一的“花括号对象形式 type”分类判断；构造调用先拒绝圆括号 tuple type，
  不再登记已解析构造器，也不再进入默认零值构造检查；对象字面量校验对已经由内部构造调用产生的
  `AE0312` 保持单一根诊断，直接 `Pair { ... }` 则继续由对象字面量入口产生唯一 `AE1004`。实现没有
  tuple 名称、模块路径或字段名称特判；同模块、短名导入、alias 和完整模块路径共同使用这一分类。

### 验收与关闭

- 本组专项复验结果：新增 Semantic 构造矩阵覆盖 0 / 非零参数、0 / 2 元素和泛型 tuple、直接对象
  字面量及调用后缀、空 / 完整 / 缺失 / 重复字段，并精确断言唯一 `AE0312` / `AE1004`；新增真实导入
  矩阵覆盖短名、alias 和完整路径；新增 CLI 用例确认 Semantic 失败且不生成 C；新增 Codegen 用例
  确认合法 tuple 仍为值布局且没有 tuple 对象描述符或分配。Parser、Semantic、Symbol、Codegen、
  CLI 专项均通过；
- 本组沙箱外 `make test` 结果：2026-09-06 全量通过；UBSan 与 normal 两阶段的 Smoke、标准库、
  FCTS、性能约束及其余单元 / CLI / Symbol 回归均通过，FCTS 为 `1151/1151`；
- 关闭依据：非法 tuple 对象构造已在 Semantic 形成唯一根诊断且不能进入 Codegen；合法 tuple 的
  字面量、默认零值和值布局行为保持不变；未修改 runtime、ABI 或 `.ft` 格式，未增加运行时开销。

## ISSUE-G20-002：解构模式整体类型标注同时登记为 Parser 与 Semantic 诊断

### 归属

- 发现组：G20；
- 关联组：G10、G12；
- 发现用例：TUP-D03、TUP-D24。

### 现象与结论

- 最小复现：

```feng
module g20.destructure_annotation;

type Pair(int, int);

func read(value: Pair) {
  let (x, y): Pair = value;
}
```

- 实际结果：Parser 已在 `Pair` token 产生唯一 `SE0107` 并停止，G12 已有精确错误码、token、行列、
  数量和阶段断言；Semantic 中仍保留 `AE0110` 防御分支，AE 错误码文档原先也把它列为用户语义错误，
  造成同一非法写法存在两个稳定阶段契约的表面冲突；
- 规范依据与预期结果：解构模式各位置只能是标识符或空位，各非空位置类型从右侧对应元素推断；模式
  后不能为全部位置追加单一类型标注。该形状在 Parser 已可唯一判定，应由 `SE0107` 负责，不形成合法
  Semantic 输入；
- 结论及根因：实际用户可观察行为正确，问题属于主规范描述缺口和错误码目录重复。Semantic 防御只对
  非法手工 AST 可达，不应形成用户源码的第二套稳定诊断契约。

### 决策与实施

- 状态：已关闭；
- 分类：规范歧义和诊断契约重复；
- 建议方案：在 tuple 主规范明确禁止 `let (x, y): Pair = value;`，给出“先建立带类型的普通绑定，再
  解构”的合法写法；SE 文档明确 `SE0107` 的 token 与阶段；AE 文档移除可达 `AE0110` 契约，并说明
  内部 Semantic 防御不属于用户源码稳定诊断。G20 直接映射 G12 既有 Parser 精确证据，不新增人工
  构造 AST 的 `AE0110` 测试；
- 是否涉及既有测试修改：否；
- 是否涉及运行时性能：否，仅调整文档中的编译期语法与诊断边界；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否；
- 人工决策与批准范围：已确认继续禁止解构模式整体类型标注，并保持当前 Parser `SE0107` 行为；
- 实际变更：tuple、SE 与 AE 主规范已按上述边界对齐；G20 TODO 已明确复用 G12 精确证据，不把
  `AE0110` 作为用户源码测试目标。Semantic 内部防御暂不需要产品变更。

### 验收与关闭

- 本组专项复验结果：既有 `test_g12_binding_type_and_callable_syntax` 已精确覆盖 `SE0107`、`Pair`
  token、行列、唯一诊断与 Parser 阶段；本次文档变更执行 `git diff --check` 通过；
- 本组沙箱外 `make test` 结果：2026-09-06 随 G20 独立全量回归通过；UBSan 与 normal 两阶段均通过，
  FCTS 为 `1151/1151`；
- 关闭依据：用户可达阶段和稳定码已唯一收敛为 Parser `SE0107`；tuple、SE、AE 主规范及 G20 TODO
  描述一致，现有产品行为不需要改变。

## ISSUE-G20-003：函数实参 tuple 元素不匹配被计划误写为 `AE1003`

### 归属

- 发现组：G20；
- 关联组：G15；
- 发现用例：TUP-D06。

### 现象与结论

- 最小复现：

```feng
module g20.argument_item_type;

type Pair(i32, string);

func take(value: Pair): void {}

func bad(): void {
  take((1, false));
}
```

- 实际结果：最初的 G20 TODO 要求五种 tuple 字面量目标上下文全部在错误元素产生 `AE1003`；专项用例
  显示普通函数实参路径在重载决议时排除不匹配候选，并在 `take` token 产生唯一 `AE0512`；
- 规范依据与预期结果：tuple 字面量仍使用 `Pair` 参数提供的位置目标完成形状匹配，但普通函数调用的
  候选选择与失败诊断统一遵循 G15 已交付规则。普通重载没有可匹配候选时使用 `AE0512`，不能因为实参
  恰好是 tuple 字面量而建立另一条元素级调用诊断特例；
- 结论及根因：产品实现正确，问题来自 G20 初版 TODO 把固定目标的 `AE1003` 误套到了重载决议路径。

### 决策与实施

- 状态：已关闭；
- 分类：实施文档预期错误和测试缺口；
- 建议方案：TUP-D06 保持绑定、返回、对象字段和显式 cast 的元素级 `AE1003`；函数实参路径改为在
  被调用函数 token 精确断言唯一 `AE0512`，同时由正向 FCTS 证明合法 tuple 字面量仍可贴合参数目标；
- 是否涉及既有测试修改：否，只修正尚未交付的 G20 新用例预期和实施文档；
- 是否涉及运行时性能：否；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否；
- 人工决策与批准范围：沿用已经批准并交付的 G15 普通重载失败诊断，不新增 tuple 特判；
- 实际变更：G20 TUP-D06 与 Semantic 验收码清单已加入 `AE0512` 调用路径；新测试按调用 token 断言。

### 验收与关闭

- 本组专项复验结果：新增 `test_g20_tuple_literal_element_type_diagnostics`，精确验证绑定、返回、对象
  字段、显式 cast 与泛型位置的唯一 `AE1003`，以及普通函数调用在 `take` token 的唯一 `AE0512`；
  新增 FCTS 正向用例真实执行合法 tuple 字面量参数传递；Semantic 专项与 FCTS 均通过；
- 本组沙箱外 `make test` 结果：2026-09-06 全量通过；UBSan 与 normal 两阶段均通过，FCTS 为
  `1151/1151`；
- 关闭依据：测试预期已与 G15 的统一重载决议契约一致，无产品代码特判，正反向证据均已建立。

## ISSUE-G20-004：正向聚合用例混入无关的整数运算类型错误

### 归属

- 发现组：G20；
- 关联组：无；
- 发现用例：TUP-D07、TUP-D17。

### 现象与结论

- 首版 Semantic 正向聚合程序把 8 元素 tuple 声明为 `i8` 元素，却把 `item8` 直接加入 `i32` 返回值；
  同时把直接字面量解构所得的默认 `int` 绑定加入同一表达式，因而产生 `AE1019`；
- tuple 的目标贴合、元素访问和解构均已正确通过，错误来自测试程序额外加入了没有显式转换的跨整数
  类型运算，不是 tuple 实现缺陷；
- 结论：测试夹具问题，不修改编译器语义或整数运算规则。

### 决策与实施

- 状态：已关闭；
- 实际变更：正向聚合程序的 8 元素 tuple 改为 `i32` 元素；直接字面量空位解构仍参与 Parser / Semantic
  验证，但不再被无关的返回值算术表达式消费。可观察值与静态类型行为由独立 G20 FCTS 用例验证；
- 是否涉及既有测试修改：否，仅修正尚未交付的新增 G20 用例；
- 是否涉及运行时性能、runtime、ABI 或 `.ft`：否。

### 验收与关闭

- 本组专项复验结果：Semantic 专项与 G20 FCTS 均通过；
- 本组沙箱外 `make test` 结果：2026-09-06 全量通过，FCTS 为 `1151/1151`；
- 关闭依据：测试源已只验证自身声明的 tuple 语义，不再夹带无关整数类型要求。

## ISSUE-G20-005：tuple 不可变绑定赋值沿用已迁移的旧错误码描述

### 归属

- 发现组：G20；
- 关联组：G13；
- 发现用例：TUP-D19、TUP-D22。

### 现象与结论

- G20 初版 TODO 把 `let` tuple 整体重绑定和 `let` 解构名称赋值写为 `AE0101`；G13 已将所有已知但
  不可写的局部赋值目标统一为 `AE0104`，并以精确用例覆盖普通绑定、参数、`for/in`、`match` 与
  `catch` 绑定；
- tuple 整体绑定和 tuple 解构产生的独立绑定同样属于局部赋值目标，不应恢复旧码，也不应为 tuple
  建立专用诊断；
- 结论：实施文档稳定码映射过期，并缺少一条普通 tuple 解构 `let` 名称赋值的精确直接证据；产品
  实现符合 G13 现行契约。

### 决策与实施

- 状态：已关闭；
- 实际变更：TUP-D19、TUP-D22 的映射统一修正为 `AE0104`；新增 G20 Semantic 反向用例，在解构名称
  token 精确断言唯一 `AE0104`，并继续以 G20 FCTS 验证 `var` 解构名称可独立赋值；
- 是否涉及既有测试修改：否，只新增 G20 用例；
- 是否涉及运行时性能、runtime、ABI 或 `.ft`：否。

### 验收与关闭

- 本组专项复验结果：Semantic 专项通过，`let` 解构名称赋值精确产生唯一 `AE0104`；
- 本组沙箱外 `make test` 结果：2026-09-06 最终全量通过；UBSan 与 normal 两阶段均通过，Smoke
  `91/91`、标准库 `604/604`、FCTS `1151/1151`，性能约束及其余回归全部通过；
- 关闭依据：文档、G13 既有契约和 G20 直接证据已统一，不改变产品语义。
