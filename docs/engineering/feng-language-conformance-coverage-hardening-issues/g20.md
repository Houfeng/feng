## ISSUE-G20-001：具名 tuple 被误当成对象构造目标并进入 Codegen

### 归属

- 发现组：G20；
- 关联组：G05、G10、G18；
- 发现用例：TUP-D08～TUP-D12。

### 现象与结论

- 最小复现：

```feng
module g20.tuple_construction;

type Pair(int, int);

func make(): Pair {
  let first = Pair();
  let second = Pair { item1: 1, item2: 2 };
  return second;
}
```

- 实际结果：`Pair()`、`Pair { ... }` 和 `Pair() { ... }` 当前可通过 Parser 与 Semantic；随后 Codegen
  沿普通对象路径生成不存在的普通对象类型描述符，并形成指针 / tuple 值不匹配的 C，错误最终由宿主
  C 编译器暴露。带非零参数的 `Pair(args)` 虽已被拒绝，但当前落入普通对象“没有匹配构造函数”路径，
  没有指出 tuple 根本不是对象构造目标；
- 规范依据与预期结果：具名 tuple 是圆括号形式声明的值类型，不能由对象构造入口产生；新的字面量
  必须贴合具名 tuple 目标，无初始化器时使用类型默认零值，已有 tuple 值则按普通值流转或允许的显式
  转换规则使用。tuple 不声明构造函数，也不获得对象类型的隐式公开无参构造函数；普通构造和对象
  字面量入口必须在 Semantic 阶段统一拒绝；
- 结论及根因：产品缺陷。构造调用和对象字面量校验当前只检查声明种类是否为 `FENG_DECL_TYPE`，没有
  继续区分花括号对象形式与圆括号 tuple 形式；tuple 与对象在 AST 中共享 type 声明种类，因而被错误
  放入普通对象构造流程。

### 决策与实施

- 状态：待修复；
- 分类：产品缺陷、诊断契约缺口和测试缺口；
- 建议方案：在 Semantic 建立并复用“是否为花括号对象形式 type”的统一分类判断。普通构造调用
  `Pair()` / `Pair(args)` 及带对象字面量后缀的同类调用，在 tuple 类型目标 token 产生唯一
  `AE0312`；直接 `Pair { ... }` 在对象字面量左花括号产生唯一 `AE1004`。判断必须先于构造器数量、
  可见性和字段检查，避免派生出 `AE0313`、`AE0315` 或字段级诊断；
- 是否涉及既有测试修改：预期不修改既有测试输入或断言，只新增 G20 集中式 Semantic、CLI 和
  Codegen 边界用例；若实际需要修改既有测试，必须列出精确名单并再次取得人工批准；
- 是否涉及运行时性能：否。检查只发生在编译期，不为任何合法 tuple 或对象构造增加运行时判断、
  分支、调用、分配或 ARC；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否。现有导入符号已经记录 tuple 分类；若实施
  发现必须修改任一边界，需暂停并再次取得人工决策；
- 人工决策与批准范围：已确认 tuple 不允许使用普通对象构造语法；允许在 G20 按上述稳定码和阶段补齐
  通用 Semantic 分类检查及新增用例，不改变合法对象类型、tuple 字面量或默认零值行为；
- 实际变更：待 G20 实施填写。

### 验收与关闭

- 本组专项复验结果：待 G20 实施填写；
- 本组沙箱外 `make test` 结果：待 G20 实施填写；
- 关闭依据：待 G20 实施填写。

## ISSUE-G20-002：解构模式整体类型标注同时登记为 Parser 与 Semantic 诊断

### 归属

- 发现组：G20；
- 关联组：G10、G12；
- 发现用例：TUP-D03、TUP-D24。

### 现象与结论

- 最小复现：

```feng
module g20.destructure_annotation;

type Pair(int, int);

func read(value: Pair) {
  let (x, y): Pair = value;
}
```

- 实际结果：Parser 已在 `Pair` token 产生唯一 `SE0107` 并停止，G12 已有精确错误码、token、行列、
  数量和阶段断言；Semantic 中仍保留 `AE0110` 防御分支，AE 错误码文档原先也把它列为用户语义错误，
  造成同一非法写法存在两个稳定阶段契约的表面冲突；
- 规范依据与预期结果：解构模式各位置只能是标识符或空位，各非空位置类型从右侧对应元素推断；模式
  后不能为全部位置追加单一类型标注。该形状在 Parser 已可唯一判定，应由 `SE0107` 负责，不形成合法
  Semantic 输入；
- 结论及根因：实际用户可观察行为正确，问题属于主规范描述缺口和错误码目录重复。Semantic 防御只对
  非法手工 AST 可达，不应形成用户源码的第二套稳定诊断契约。

### 决策与实施

- 状态：已关闭；
- 分类：规范歧义和诊断契约重复；
- 建议方案：在 tuple 主规范明确禁止 `let (x, y): Pair = value;`，给出“先建立带类型的普通绑定，再
  解构”的合法写法；SE 文档明确 `SE0107` 的 token 与阶段；AE 文档移除可达 `AE0110` 契约，并说明
  内部 Semantic 防御不属于用户源码稳定诊断。G20 直接映射 G12 既有 Parser 精确证据，不新增人工
  构造 AST 的 `AE0110` 测试；
- 是否涉及既有测试修改：否；
- 是否涉及运行时性能：否，仅调整文档中的编译期语法与诊断边界；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否；
- 人工决策与批准范围：已确认继续禁止解构模式整体类型标注，并保持当前 Parser `SE0107` 行为；
- 实际变更：tuple、SE 与 AE 主规范已按上述边界对齐；G20 TODO 已明确复用 G12 精确证据，不把
  `AE0110` 作为用户源码测试目标。Semantic 内部防御暂不需要产品变更。

### 验收与关闭

- 本组专项复验结果：既有 `test_g12_binding_type_and_callable_syntax` 已精确覆盖 `SE0107`、`Pair`
  token、行列、唯一诊断与 Parser 阶段；本次文档变更执行 `git diff --check` 通过；
- 本组沙箱外 `make test` 结果：本问题仅修改文档，按工程规则不单独执行；G20 实施后的全量回归仍须
  独立完成；
- 关闭依据：用户可达阶段和稳定码已唯一收敛为 Parser `SE0107`；tuple、SE、AE 主规范及 G20 TODO
  描述一致，现有产品行为不需要改变。
