## ISSUE-G25-001：同一类型参数列表缺少重名检查

### 归属

- 发现组：G25，2026-09-10 静态盘点；
- 关联组：无；
- 发现用例：GENERIC01-A；
- 状态：已关闭（修复或获批迁移及最终全量验收通过）。
- 分类：产品缺陷。

### 现象与结论

- 最小复现：实施前分别以 `func duplicate<T, T>(value: T): T { return value; }` 及
  type／spec／method 的同形列表
  建立独立最小程序；每例只保留列表内重名这一个根因。
- 实际结果：[`resolver_push_type_params`](../../../src/semantic/analyzer.c) 当前把新列表逐项追加到作用域，
  返回条件只有空列表和分配失败；列表内没有名称唯一性检查。方法参数与外层 owner 参数重名另有
  `AE1017` 检查，不能覆盖同一列表。
- 规范依据与预期结果：[泛型主规范](../../specifications/feng-generics-draft.md)要求检查同一类型参数列表
  中的重名；第二个同名参数必须在 Semantic 阶段产生唯一诊断并阻止进入后续解析。
- 结论及根因：声明入口缺少共享的参数列表名称校验。该问题适用于 type、func、spec 和方法，不是某一
  声明种类的特殊语义。

### 决策与实施

- 建议方案：在所有泛型声明共用的类型参数入栈前执行列表内唯一性检查，并与方法参数遮蔽 owner 的
  检查复用同一名称冲突辅助逻辑；两类问题均发 `AE1017`，定位后出现的参数名。
- 错误码依据：冲突对象均为类型参数名，根因均为同一可见泛参作用域中的名称冲突，修复均为重命名或
  删除重复参数；按 AE 分配规则复用 `AE1017`，不新增错误码。
- 是否涉及既有测试修改：不涉及；新增 `test/semantic/test_g25.c` 精确矩阵。
- 是否涉及运行时性能：不涉及，只增加声明期 Semantic 检查。
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：不涉及。
- 人工决策与批准范围：错误码复用原则已明确；2026-09-10 已批准 G25 产品修复。
- 实际变更：在公共源码声明入栈入口检查列表重名并复用 AE1017；派生查询参数域仍由原作用域
  管理入口处理，避免重复发码。新增 `01A-*`／`01B-*` 正反例通过。

### 验收与关闭

- 本组专项复验结果：通过，见 G25 用例与验收证据 GENERIC01；
- 本组沙箱外 `make test` 结果：最终两阶段通过，见本文末尾；
- 关闭依据：所有声明入口的重复参数反例均精确产生 `AE1017`，合法邻界通过，且 G25 专项与独立全量
  回归通过后关闭。

## ISSUE-G25-002：显式泛型 target arity 仍产生历史错误码

### 归属

- 发现组：G25，2026-09-10 静态盘点；
- 关联组：G21 的类型 arity 证据、G15 的调用诊断；
- 发现用例：GENERIC02-B～E、GENERIC05-C；
- 状态：已关闭（修复或获批迁移及最终全量验收通过）。
- 分类：产品缺陷、既有测试问题。

### 现象与结论

- 最小复现：`Box<i32, string>()` 对单泛参 type 构造、`identity<i32, string>(1)` 对单泛参函数调用，
  以及对非泛型 type／callable 写 `<i32>`。
- 实际结果：[`analyzer.c`](../../../src/semantic/analyzer.c) 的显式调用后置 arity 检查按构造目标和其他
  callable 分别产生 `AE0232`／`AE0233`。这两个码未进入现行 AE 分段规范；其中
  `test/codegen/test_generic_argument_static.c::arguments_reject_invalid_actuals` 仍精确断言 `AE0233`。
- 规范依据与预期结果：AE 主规范已经用 `AE1014` 表示“目标不是泛型却携带类型实参”，用 `AE1015`
  表示“已解析泛型目标的类型实参数量不匹配”。目标是 type、构造器、函数或方法不改变这两个根因；
  callable 重载集存在多个泛型 arity 时应列出可用集合，不能依赖声明顺序任选一个候选。
- 结论及根因：当前后置检查按 resolver 的目标种类拆码，而不是按用户可修复的错误根因分配，导致
  同类错误跨入口不一致。

### 决策与实施

- 建议方案：统一显式 target 验证顺序；目标集合只有 arity 0 时发 `AE1014`，存在泛型声明但没有与
  显式数量相同的 arity 时发 `AE1015`。多个 callable arity 使用集合消息；所有调用入口复用统一模板
  选择，不再产生 `AE0232`／`AE0233`。
- 错误码依据：非泛型目标和泛型 arity 不匹配是两个不同根因，分别复用 `AE1014` 与 `AE1015`；构造／
  callable 只是不同入口，不再分配入口专用码。
- 是否涉及既有测试修改：涉及一条已知断言；仅允许把
  `test/codegen/test_generic_argument_static.c::arguments_reject_invalid_actuals` 第三个 case 的
  `AE0233` 改为 `AE1015`。既有源码和其他断言保持不变；若发现更多断言受影响须另行列出并批准。
- 是否涉及运行时性能：不涉及，只改变 Semantic 诊断分类和模板。
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：不涉及。
- 人工决策与批准范围：2026-09-10 已批准产品修复和上述一条既有断言迁移。
- 实际变更：公共显式 target 入口按非泛型／错误 arity 发 AE1014／AE1015；移除历史发码。
  新增完整诊断矩阵并仅按白名单迁移既有断言。

### 验收与关闭

- 本组专项复验结果：通过，见 G25 用例与验收证据 GENERIC02／05；
- 本组沙箱外 `make test` 结果：最终两阶段通过，见本文末尾；
- 关闭依据：type／构造／顶层、实例、静态和 fit callable 的非泛型与错误 arity 矩阵分别稳定使用
  `AE1014`／`AE1015`，`src/` 不再有用户源码可达的 `AE0232`／`AE0233`，专项与独立全量回归通过后关闭。

## ISSUE-G25-003：tuple 约束与其他非 spec 约束重复分配错误码

### 归属

- 发现组：G25，2026-09-10 静态盘点；
- 关联组：G20 TUP-D16；
- 发现用例：GENERIC03-B；
- 状态：已关闭（修复或获批迁移及最终全量验收通过）。
- 分类：产品缺陷、既有测试问题。

### 现象与结论

- 最小复现：`type Pair(i32, i32); func bad<T: Pair>(value: T): T`，并与普通 object type 作为约束的
  同形程序配对。
- 实际结果：[`validate_type_param_constraints`](../../../src/semantic/analyzer.c) 对 tuple 单独产生
  `AE0304`，对其他解析成功但不是 spec 的类型产生 `AE0709`。G20 的
  `test_g20_tuple_nominal_and_conversion_diagnostics` 有两个精确 `AE0304` 断言。
- 规范依据与预期结果：泛型主规范只允许任意 form 的 `spec` 作为约束。tuple 和普通 object type 都是
  已解析但不是 spec 的约束引用，用户修复动作都是改用 spec；tuple 不是独立约束机制。
- 结论及根因：实现按被引用类型的形态拆码，违反“同一错误对象、根因和修复动作共码”的分配规则。

### 决策与实施

- 建议方案：tuple 与其他非 spec 类型统一产生 `AE0709`；可以保留“tuple 不能作为约束”的具体消息，
  但消息模板差异不产生新错误码。停止从产品代码产生 `AE0304`。
- 错误码依据：冲突对象都是类型参数约束引用，根因都是引用目标不是 spec，修复都是改用 spec；复用
  `AE0709`，不新增错误码。
- 是否涉及既有测试修改：仅允许把
  `test/semantic/test_semantic.c::test_g20_tuple_nominal_and_conversion_diagnostics` 中两个
  `AE0304` 期望改为 `AE0709`；源码、token、行列、数量和消息断言保持不变。另一个仅检查消息的旧
  tuple 测试无需修改。
- 是否涉及运行时性能：不涉及，只改变声明期 Semantic 诊断码。
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：不涉及。
- 人工决策与批准范围：2026-09-10 已批准产品修复和上述两条既有断言迁移。
- 实际变更：非 spec 约束统一使用 AE0709，tuple 保留原具体消息；只迁移获批的两条 G20
  错误码期望，新增 `03B-*` 配对通过。

### 验收与关闭

- 本组专项复验结果：通过，见 G25 用例与验收证据 GENERIC03-B；
- 本组沙箱外 `make test` 结果：最终两阶段通过，见本文末尾；
- 关闭依据：普通 type、tuple 和必要的其他非 spec 代表均在约束参数 token 精确产生 `AE0709`，合法
  spec 约束通过，`src/` 不再产生 `AE0304`，专项与独立全量回归通过后关闭。

- 核查程序：同一 `T` 对应两个不兼容的已定型实参，以及 `Box<T>`／`T[]` 普通参数推导；
  与同类型实参、显式闭合、合法 fallback 配对。
- 规范依据：泛型主规范 §5～6 的唯一推导与候选筛选；G25 §4.4。
- 处理边界：只修复主规范能唯一确定的编译期问题；不确定语义或既有断言迁移交人工决定，

### 既有测试冲突与人工决定

- `test/semantic/test_semantic.c::test_generic_non_extern_call_does_not_expand_wrapped_array_inference`
  明确断言普通 `same<T>(values: T[]): T[]` 接收 `int[]` 时失败，与 GENERIC04-A 要求的普通嵌套／
  数组参数推导正例冲突；当前实现的 `allow_wrapped_inference` 限制与该反例一致。
- 该测试原不在迁移白名单内，因此曾暂停普通嵌套推导及该测试修改，逐项提交人工决定。
- 2026-09-10 人工经单层、多层和不变性示例澄清后明确“批准优化，同时补齐用例覆盖”。批准
  普通函数／方法复用递归结构推导，覆盖多层组合；保留该旧测试源码并迁移为成功断言。
  不引入协变／逆变、不寻找共同父 spec 合并冲突、不改变裸构造 owner 规则或增加运行时转换。
- 当时决定：已批准实施，无待决策事项。若后续需要其他既有测试迁移或语义选择，另行登记，
  暂停并取得人工决定，不绕过待决策问题。

### 最小程序验证

- 基线 `6b914f6d`：`same<T>(left: T, right: T)` 用 `i32`、`string` 两个已定型实参调用，
  `feng tool compile --target=lib` 成功生成 C，确认不同来源推导冲突被漏检。
- 同基线普通 `same<T>(values: T[]): T[]` 用 `i32[]` 调用产生唯一 `AE0512`，与既有反例一致。
- 直接冲突的根因已确定：两个 applicability matcher 忽略收集失败，后置 materializer 再次保留首次
  绑定。修复须让候选收集与选中结果使用相同的严格一致性检查，合法 fallback 仍按既有优先级选择。
- 人工要求示例说明后，用当前工作区编译器重新核对：`identity<T>(value: T)` 分别接收 `int` 与
  `int[]` 均可生成 C，后一例直接得到 `T = int[]`；`same<T>(values: T[])` 接收 `int[]`，以及
  `sameBox<T>(value: Box<T>)` 接收 `Box<int>`，省略类型实参均产生唯一 `AE0512`，显式写
  `same<int>`／`sameBox<int>` 则均可生成 C。所有调用均不提供结果目标类型，隔离实参结构推导。
  嵌套推导意味着后两例可由实参结构确定 `T = int`，不是让裸 `Box()` 推导 owner 泛参。

## ISSUE-G25-005：无声明节点的非 spec 约束漏过 Semantic

### 发现、分析与方案

- 发现组／用例：G25，GENERIC03-B，2026-09-10；状态：已关闭（修复或获批迁移及最终全量验收通过）。
- 最小程序：`func bad<T: i32>(value: T): T { return value; }`。
- 基线结果：Semantic 接受，随后 Codegen 发 `CE0003`（generic constraint must be a spec）。
- 根因：`validate_type_param_constraints` 只拒绝 `constraint_decl != NULL` 的非 spec；内建、数组／
  指针等没有具名 spec 声明的引用漏过。未知名称则应保留已产生的 `AE1013`，不能追加 `AE0709`。
- 文档冲突：泛型主规范条款写明约束只能为 spec，但“正确语法三”保留 `IntBox<I: int>`。
  不能仅凭当前实现或条款就认定该示例的设计意图已废弃；2026-09-10 人工指出后已恢复示例，
  具体 type 能否作为约束待人工决定。
- 方案：先保留类型解析诊断；解析成功后要求约束本身为具名 spec 引用，所有非 spec 统一
  `AE0709`。与普通 type／tuple 一并覆盖，不按内建种类增加特判。
- 授权状态：具体类型约束存在文档冲突，暂停该项产品改动及新增预期，等待人工决定；
  不影响原已批准的 tuple 与普通具名 type 错误码收敛。
- 验收：内建、数组、指针、枚举、普通 type、tuple 反例精确产生唯一 Semantic `AE0709`，未知
  约束仅 `AE1013`，合法 spec 约束及专项、全量回归通过。

### 人工澄清与继续实施

- 人工反馈：“现在具体类型约束是否会报错？具体类型作为约束其实没有意义”。
- 原样 `IntBox<I: int>` 及追加 `IntBox<int>()` 实例化，两者基线都在 Codegen 发 `CE0003`。
- 按该澄清保留主规范的 spec-only 规则；将原样示例从正确示例移到错误示例，明确 Semantic 拒绝，
  并恢复通用非 spec `AE0709` 检查与内建／数组／指针回归，不引入具体类型约束能力。
