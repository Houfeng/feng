## ISSUE-G18-001：非法显式转换仍产生未进入现行 AE 分段规范的旧 `AE0051`

### 归属

- 发现组：G18；
- 关联组：G19～G25 中涉及显式转换的既有或后续映射；
- 发现用例：TYPE04、TYPE04-A。

### 现象与结论

- 最小复现：`let value: i32 = 1; let invalid = (bool)value;`；
- 实际结果：Semantic 在 `validate_cast_expr` 的通用非法转换出口产生 `AE0051`；该码仍出现在旧总表，
  但没有进入当前 `feng-error-codes-ae.md` 的稳定分段；
- 规范依据与预期结果：显式转换资格由表达式主规范统一定义；不同来源 / 目标组合共享同一个通用非法
  转换出口，应使用 AE 表达式段中的同一稳定诊断，不应按普通类型、spec、tuple 或泛型增加特判；
- 结论及根因：早期错误码结构化未迁移显式转换产生点，属于诊断契约未收敛，不改变任何转换的接受、
  拒绝或运行语义。

### 决策与实施

- 状态：已解决；
- 分类：诊断契约缺口；
- 建议方案：在 AE 表达式段新增 `AE1023`“显式转换资格约束”，将 `validate_cast_expr` 的唯一
  `AE0051` 产生点整体迁移为 `AE1023`；不得只为 G18 普通类型增加分支；
- 是否涉及既有测试修改：是。当前精确断言 `AE0051` 的范围仅有四个 Semantic 测试函数共 11 条：
  `test_object_spec_method_values_reject_invalid_sources`、
  `test_explicit_generic_callable_values_reject_invalid_sources`、
  `test_callable_variadic_shape_mismatches_are_rejected` 和
  `test_object_spec_upcast_rejects_out_of_scope_conversions`；需人工明确批准后才可修改；
- 是否涉及运行时性能：否，只改变编译期错误码；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否；
- 人工决策与批准范围：已批准整体迁移通用非法转换产生点，并仅将列明四个既有测试函数中的 11 条
  `AE0051` 断言更新为 `AE1023`；除此之外如需修改既有用例，必须再次取得人工决策；
- 实际变更：在现行 AE 表达式段登记 `AE1023`，并把 `validate_cast_expr` 的通用非法转换出口由
  `AE0051` 迁移为 `AE1023`；严格按批准范围，只把列明四个既有 Semantic 测试函数中的 11 条错误码
  断言同步为 `AE1023`，其输入、其他断言和测试结构均未改动。新增 G18 显式转换反向矩阵，核对唯一
  诊断及精确位置。

### 验收与关闭

- 本组专项复验结果：`test_semantic` 通过；新增 TYPE04 / TYPE04-A 正反向覆盖通过；
- 本组沙箱外 `make test` 结果：2026-09-03 执行，退出码为 `0`；UBSan 与 normal 两阶段及全部回归
  通过；
- 关闭依据：非法显式转换统一稳定产生 `AE1023`，合法同类型及数值转换继续通过，旧产生点与批准范围
  内的 `AE0051` 精确断言均已清除。

## ISSUE-G18-002：普通对象默认零值循环仍使用旧 Codegen 码且错误复用 ARC 潜在循环图

### 归属

- 发现组：G18；
- 关联组：TYPE08～TYPE09；
- 发现用例：TYPE08、TYPE08-A、TYPE08-B。

### 现象与结论

- 最小复现一：`type Node { var next: Node; } func run() { let node: Node; }`；
- 实际结果一：Semantic 允许声明递归普通对象类型；实际要求默认值时，Codegen 的通用默认值生成路径
  才以旧 `CE0226` 拒绝，导致用户可修复的类型资格错误泄漏到发码阶段；
- 最小复现二：`type Node { var children: Node[]; } func run() { let node: Node; }`；
- 实际结果二：Codegen 的默认零值资格判断首先读取 `feng_semantic_type_is_potentially_cyclic`。该 ARC
  潜在循环图会穿透数组元素类型，因此数组字段形成回边时也会被判为默认零值不安全；
- 规范依据与预期结果：类型规范要求普通对象默认值递归初始化对象字段；内建类型规范同时规定数组
  默认值是长度为零的有效空数组。因此默认零值展开在数组字段处终止，不会为了空数组继续构造元素
  对象。ARC 潜在循环分析需要穿透数组以覆盖对象日后写入数组形成的运行时环，但该图不能直接决定
  初始默认值能否有限生成；
- 结论及根因：默认零值资格与运行时 ARC 潜在循环是两个不同问题，当前 Codegen 复用同一循环标记
  导致数组中断边界过度拒绝；同时默认零值资格本应是 Semantic 的类型合法性检查，Semantic 漏检才
  使用户错误进入 Codegen。

### 决策与实施

- 状态：已解决；
- 分类：产品缺陷、诊断契约缺口和测试缺口；
- 批准方案：新增类型段 `AE0332`，在 Semantic 检查无初始化器绑定及对象构造第一阶段实际请求的
  默认零值；只沿实际需要递归构造默认值的普通对象字段继续，遇到数组、`string`、标量、指针及其他
  已有终止默认值的类别即停止。不得削弱供 ARC 使用的潜在循环图。Codegen 同类出口改为 `IE0002`
  内部不变量防御，不再产生用户可修复的 `CE`；
- 是否涉及既有测试修改：静态审计未发现既有测试精确断言 `CE0226`；优先新增 G18 Codegen 与 FCTS
  用例。若实施时发现必须修改既有测试，先暂停并取得人工决策；
- 是否涉及运行时性能：不得增加既有合法程序的运行时判断、分支、调用、分配或 ARC。修复仅改变
  编译期资格判断；此前被错误拒绝的数组中断程序按既有数组默认值规则生成空数组，不属于给既有合法
  程序增加开销；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否；
- 人工决策与批准范围：已批准将该检查前移至 Semantic 并拆分默认零值有限性判断与 ARC 潜在循环图；
  语义只要通过，Codegen 必须正确发码，不允许的用户程序由 Semantic 报 `AE0332`，Codegen 兜底只报
  `IE0002`。union-form 只有在实际请求默认零值时才沿首成员检查；显式初始化器直接选取非递归 member
  时不得报错。不得增加运行时开销，不得修改 runtime 私有 ABI、公开 ABI 或 `.ft` 格式；
- 实际变更：新增独立的编译期默认零值有限性分析，并只在无初始化器绑定、无初始化器 static 字段和
  普通对象构造第一阶段等实际请求位置调用；分析沿普通对象字段及 union-form 首成员递归，在数组、
  指针和已有有限默认表示处终止，不读取或改变 ARC 潜在循环图。直接 / 间接循环由 Semantic 在请求
  token 产生 `AE0332`；Codegen 的旧 `CE0226` 出口收敛为 `IE0002` 内部不变量防御。

### 验收与关闭

- 本组专项复验结果：`test_semantic`、`test_codegen` 通过；Smoke `91/91`、FCTS `1139/1139`，数组中断
  与递归 union 显式初始化合法边界均已真实运行；
- 本组沙箱外 `make test` 结果：2026-09-03 执行，退出码为 `0`；UBSan 与 normal 两阶段及性能约束
  全部通过；
- 关闭依据：用户可修复的非有限默认零值已在 Semantic 稳定拒绝，数组边不再被 ARC 图误伤，Codegen
  不再对该语义错误产生 `CE`。

## ISSUE-G18-003：TYPE08-A 的“后续阶段覆盖即可免除默认零值”与三阶段主规范冲突

### 归属

- 发现组：G18；
- 关联组：G05；
- 发现用例：TYPE08-A。

### 现象与结论

- 最小复现：`type Node { open var next: Node; }` 与
  `func copy(next: Node): Node { return Node { next: next }; }`；
- 实际结果：Semantic 接受；Codegen 在成员声明及绑定初值阶段为 `next` 请求默认零值，并在字段声明
  token 产生 `CE0911`。对象字面量中的 `next: next` 属于第三阶段，尚未执行；
- 主规范依据：类型规范已经明确对象构造顺序为“成员声明及绑定初值 -> 构造函数 -> 对象字面量”，且
  无声明初始化器的成员在第一阶段取得类型默认零值。因此第二阶段构造函数赋值或第三阶段对象字面量
  赋值都不能倒推取消第一阶段已经要求的默认零值；
- 冲突：G18 TYPE08-A 当前写成“选中构造或对象字面量提供值即可避免默认零值，并且显式覆盖不得
  误报”，与上述主规范和 G05 已交付的三阶段行为不一致；
- 结论：当前证据表明这是 G18 用例计划的描述错误，而不是已确认的 Codegen 产品缺陷。只有字段声明
  初始化器本身提供值时，当前构造路径才无需为该字段先生成默认零值；对象类型自身作为无初始化器
  绑定目标时，仍按不执行字段初始化器的递归零值语义独立判断。

### 决策与实施

- 状态：已解决；
- 分类：实施文档与主规范不一致；
- 批准方案：保持主类型规范和 G05 三阶段语义不变；构造第一阶段实际需要为循环字段生成默认零值时
  必须由 Semantic 产生 `AE0332`，后续构造函数或对象字面量赋值不能免除；字段声明初始化器已提供
  值的构造路径不请求该字段默认零值。本次不增加跨阶段数据流特判；
- 是否涉及既有测试修改：否；
- 是否涉及运行时性能：建议方案不修改运行时，不增加运行时开销；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否；
- 人工决策与批准范围：已确认只有声明处的 `let` / `var` 绑定有初始值时不产生默认零值；无声明
  初始化器时先取得默认零值，构造函数与对象字面量后续赋值不改变这一事实；默认零值非法由 Semantic
  报 `AE`，Codegen 防御报 `IE`。字段声明初始化器若为首成员可递归的 union-form 直接提供非递归
  member，同样不请求该 union-form 的默认零值；
- 实际变更：类型与 union 主规范、G18 用例描述均收敛为同一三阶段边界；Semantic 在构造目标处检查
  第一阶段实际需要的字段默认零值，只跳过带字段声明初始化器的字段。构造函数体或对象字面量中的
  后续写入不能跳过该检查；字段声明初始化器直接提供值时不请求默认零值，包括显式选取首成员递归
  union-form 的非递归 member。

### 验收与关闭

- 本组专项复验结果：新增同包与跨包正反向用例通过；缺少字段声明初始化器的构造在构造目标 token
  稳定产生唯一 `AE0332`，带声明初始化器的构造及递归 union 非递归 member 初始化均通过；
- 本组沙箱外 `make test` 结果：2026-09-03 执行，退出码为 `0`；UBSan 与 normal 两阶段全部通过；
- 关闭依据：实现、主规范与 G18 计划已按既定三阶段语义一致，未增加跨阶段数据流特判。

## ISSUE-G18-004：拆分默认零值图后开放泛型上下文实例误发射直接默认工厂

### 归属

- 发现组：G18；
- 关联组：G25；
- 发现用例：完整 FCTS 的既有跨包泛型组合用例。

### 现象与结论

- 发现过程：完成 `ISSUE-G18-002` 的默认零值图拆分后，首次运行 `make fcts-tests`；
- 实际结果：`fcts_lib` 生成 C 中，开放泛型上下文类型
  `LibCompositionMutualLeft<T>` / `LibCompositionMutualRight<T>` 的直接默认工厂调用了不存在的
  `List<State<T>>__default_zero()`，C 编译器以未声明函数拒绝；
- 根因：`cg_emit_user_type_definition` 已通过 `descriptor_has_default_zero` 正确区分“可静态生成直接默认
  工厂的闭合实例”和“必须通过描述符共享入口生成默认值的开放上下文实例”，但后面的直接工厂发射
  只检查默认零值图安全性，没有复用这一资格。旧 ARC 循环标记曾偶然压制相关工厂；拆分正确的图后
  暴露了既有的发射条件不一致；
- 结论：这是 G18 实现过程中引入并稳定复现的编译回归，不应恢复错误的 ARC 判断，也不应为具体
  `List` 或用例增加特判。

### 决策与实施

- 状态：已解决；
- 分类：Codegen 发射资格缺陷；
- 方案：直接默认工厂与描述符 `default_zero_init` 统一使用 `descriptor_has_default_zero` 资格；开放泛型
  上下文实例继续使用既有 `FengGenericDefaultZero` 描述符共享入口，不生成无描述符的直接工厂；新增
  最小 Codegen 回归并复验完整 FCTS；
- 是否涉及既有测试修改：否；
- 是否涉及运行时性能：否，只纠正编译期函数发射集合和调用目标，不新增运行时分支、调用或分配；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否；
- 人工决策与批准范围：方案复用已有通用资格，不增加特判，属于已批准 G18 修复范围；
- 实际变更：直接默认工厂的发射条件改为复用已经计算的 `descriptor_has_default_zero`，与描述符
  `default_zero_init` 资格保持一致；开放泛型上下文继续走既有描述符共享入口，不恢复 ARC 循环标记，
  也未增加具体容器或类型名特判。新增最小 Codegen 回归覆盖该发射边界。

### 验收与关闭

- 本组专项复验结果：`test_codegen` 通过，完整 FCTS `1139/1139`；此前失败的跨包泛型组合用例通过；
- 本组沙箱外 `make test` 结果：2026-09-03 执行，退出码为 `0`；UBSan 与 normal 两阶段全部通过；
- 关闭依据：直接默认工厂与描述符能力使用同一通用资格，开放泛型缺失符号回归已消除。

## ISSUE-G18-005：Semantic 接受的同类型显式转换在 Codegen 被误拒绝

### 归属

- 发现组：G18；
- 关联组：TYPE04-A、TYPE09；
- 发现用例：新增 FCTS `test_ordinary_type_semantics.ff`。

### 现象与结论

- 最小复现：`let source: string = "same"; let value: string = (string)source;`；
- 实际结果：Semantic 正确接受同类型显式转换，Codegen 的通用 cast 路径却在数值、`bool`、
  array、spec 和 callable 之外直接产生 `CE0193`；
- 影响面：同一缺口会影响 Semantic 已允许的 `string`、普通对象、`@value` 和 `@abi` 同类型
  显式转换，不应只修复 `string` 特例；
- 结论及根因：语义层和发码层的合法转换集合不一致。同类型转换只确认目标静态类型，
  不改变值、表示、所有权或存储属性，应统一 lower 为无操作。

### 决策与实施

- 状态：已解决；
- 分类：Codegen 产品缺陷和测试缺口；
- 方案：在特定视角转换路径之后、数值转换之前，对已求值源和目标执行通用的精确类型
  相等判断；若相等，直接传递原 `ExprResult` 并仅用目标类型替换其静态类型描述，
  保留所有权、可寻址性及泛型存储信息；不按具体用户类型增加特判；
- 是否涉及既有测试修改：否，新增 Codegen 与 FCTS 覆盖；
- 是否涉及运行时性能：否，同类型转换不发射新的运行时调用、分支、分配或 ARC
  操作；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否；
- 人工决策与批准范围：属于 G18 增补用例稳定暴露的通用 Codegen 缺口，按本组已批准
  的“先记录、再分析、并解决”范围实施；
- 实际变更：把已有 spec 槽位精确类型比较推广为通用 `cg_type_identity_equal`，并在 cast 发码路径中
  对精确同类型转换直接移动完整 `ExprResult`、替换静态目标类型；不发射转换指令，且保留所有权、
  可寻址性和泛型存储事实。新增 `string`、普通对象、`@value type`、`@abi type` 的 Codegen 与 FCTS
  用例。

### 验收与关闭

- 本组专项复验结果：`test_codegen` 通过，FCTS `1139/1139`；同类型转换结构与运行行为均通过；
- 本组沙箱外 `make test` 结果：2026-09-03 执行，退出码为 `0`；UBSan 与 normal 两阶段及性能约束
  全部通过；
- 关闭依据：Semantic 接受的精确同类型转换已由 Codegen 统一无操作发码，不再泄漏 `CE0193`。

## ISSUE-G18-006：跨包 `.ft` 丢失实例 `var` 的声明初始化器事实

### 归属

- 发现组：G18；
- 关联组：G05、TYPE08-A；
- 发现用例：跨包构造“递归字段带声明初始化器”的普通对象。

### 现象与结论

- 最小复现：provider 声明 `open type Node { open var next: Node = unavailable(); }`，consumer 通过
  package-public 表面执行 `Node()`；
- 实际结果：同包源码中的 `var` 字段保留 `declaration_bound = true`，Semantic 能确认构造第一阶段
  直接执行声明初始化器；导出符号图时，`field_is_bounded_decl` 只为 `let` 写出 `bounded_decl`，导入
  后该 `var` 字段变成 `declaration_bound = false`，consumer 因而误报 `AE0332`；
- 根因：现有 `.ft` 标志最初只服务 G05 的 `let` 最终绑定检查，尚未承载所有实例字段共同需要的
  “声明初始化器存在”事实；
- 结论：这是跨包语义事实缺口，不是默认零值分析缺陷，也不能通过类型名、`Option` 或 std 特判解决。
