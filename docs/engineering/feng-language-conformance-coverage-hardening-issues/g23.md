## ISSUE-G23-001：内建类型与数组的无块体契约适配被误拒绝

- 状态：已修复，新增 Semantic／FCTS 专项通过，已关闭。
- 关闭：2026-09-07 最终沙箱外 `make test` 退出码 0，UBSan／普通配置全部通过。
- 分类：产品缺陷；关联两条既有测试的诊断预期迁移。

### 归属

- 发现组：G23。
- 关联用例：SPEC04、SPEC06、SPEC15、SPEC16、SPEC27、SPEC28。
- 已有断言：`test_fit_builtin_target_rejects_specs_clause_without_body`、
  `test_fit_array_target_rejects_specs_clause_without_body`。

### 现象与结论

最小合法程序：

```feng
module review.builtin_marker;
spec Marker {}
fit i32: Marker;
```

- 修复前结果：Semantic 在 `i32` token 报 `AE0807: fit with spec clause requires a body`，退出码 1。
  单独将目标改为 `i32[]` 后同样报错。空契约不需要任何成员实现，不能用缺失方法解释这个拒绝。
- 扩展复现：先 `fit i32 { func read(): i32 { return self; } }`，再声明
  `fit i32: Reader;`，其中 `Reader` 只要求该 `read` 方法，当前仍因无块体而报 `AE0807`。
- 规范依据：[fit 规范 §4～§6](../../specifications/feng-fit.md)规定有无块体均声明关系并检查
  满足性；[内建目标 fit 规范 §3～§5](../../specifications/feng-fit-builtin-type.md)复用通用
  满足规则，不要求内建或数组目标独有的块体。
- 根因：[validate_fit_declaration_contracts](../../../src/semantic/analyzer.c) 在内建／数组
  分支中直接以 `spec_count > 0 && !has_body` 拒绝，未依据已存在的可见能力判定。

### 决策与实施

- 方案：移除按目标类别附加的块体门槛，统一检查完整契约与可见实现；与 ISSUE-G23-003 一起
  实施，不能只删除错误出口而允许不完整适配通过。
- 用例：空契约、已有方法、缺少方法、错误签名分别比较无块体／空块体／提供方法块体；覆盖
  标量、string、只读／可写数组及具名目标对照，合法用法纳入 FCTS。
- 既有测试修改：仅 §27.3.2 明列的两条。其源码仍缺少 `greet` 实现，应继续拒绝，但原因改为
  缺少必需方法 `AE0705`，不是无块体。合法无块体场景全部新增，不把旧反例改成正例。
- 运行时性能：方案仅改变编译期资格判断，继续使用既有方法实现与 witness，不增加动态检查。
- runtime 私有 ABI、公开 ABI、`.ft` 格式：不计划变更。
- 人工决策与批准范围：已随 G23 启动批准修复、补测及两条明列的反例诊断迁移。
- 实际变更：移除内建／数组的块体门槛，统一进行完整满足性检查；两条原反例源码未变，按缺失
  `greet` 在 Semantic 断言 `AE0705`。

### 验收与关闭

- 准入复现：标量及数组空契约均在 Semantic 报 `AE0807`；已有方法的标量无块体适配也报同码。
- 本组专项复验结果：`g23_relation_matrix`、`g23_signature_matrix` 及两条获批迁移通过；
  合法运行用例已注册到 `test_g23_spec_fit` 并运行通过。
- 本组沙箱外 `make test` 结果：以主文档 §27.4 的最终记录为准；首轮失败保留在那里。
- 关闭条件：合法无块体适配运行正确，非法适配按真实成员根因在 Semantic 拒绝，迁移获批且通过
  专项及全量回归。

## ISSUE-G23-002：内建类型与数组的单条 fit 列表重复契约漏检

- 状态：已修复，重复列表拒绝及关系幂等专项通过，已关闭。
- 关闭：2026-09-07 最终沙箱外 `make test` 退出码 0，UBSan／普通配置全部通过。
- 分类：产品缺陷。

### 归属

- 发现组：G23。
- 关联用例：SPEC05、SPEC08、SPEC12～SPEC14、SPEC27。

### 现象与结论

最小非法程序：

```feng
module review.builtin_duplicate;
spec Marker {}
fit i32: Marker, Marker {}
```

- 修复前结果：Semantic 无诊断且退出码 0。目标单独改为 `i32[]` 也通过；改为普通 `type Item {}`
  并声明 `fit Item: Marker, Marker;` 则正确在第二个 `Marker` 报 `AE0810`。
- 对照正例：普通 type 上分写两条 `fit Item: Marker;` 当前通过，符合规范；本问题不是要求拒绝
  多条相同关系，更不意味着两个不同的方法实现可以合并。
- 规范依据：[fit 规范 §4～§6](../../specifications/feng-fit.md)明确区分单条列表唯一性、多条
  相同关系幂等和合并后的实现／签名冲突，三者须分别验收。
- 根因：`validate_fit_declaration_contracts` 的具名目标路径执行重复项检查，内建／数组分支在
  解析右侧 spec 和处理孤儿导出后返回，跳过了这项通用校验。

### 决策与实施

- 方案：对全部合法目标复用同一契约列表校验，按已解析的契约身份发现重复，在第二个重复项
  报 `AE0810`；不能靠对最终关系去重来掩盖源声明中的重复列表。
- 用例：具名目标、内建标量、string、只读／可写数组，有无块体，短名与限定名指向同一契约；
  配套多条相同关系且只有一个实现的正例，以及重复实现、仅返回类型不同等独立反例。
- 既有测试修改：不计划修改，全部新增或映射已有直接证据。
- 运行时性能：只增加缺失的编译期声明校验，不增加运行时开销。
- runtime 私有 ABI、公开 ABI、`.ft` 格式：不计划变更。
- 人工决策与批准范围：已批准随 G23 修复及补测，不更改主规范中的幂等语义。
- 实际变更：全部合法目标共用契约列表重复校验，不再由内建／数组提前分支跳过。

### 验收与关闭

- 准入复现：内建／数组单条重复列表均被接受；具名目标同类反例报 `AE0810`；具名目标多条
  同关系声明通过。
- 本组专项复验结果：`g23_relation_matrix` 的重复列表反例及多条相同关系正例通过；
  `g23_declaration_diagnostics` 对实现重复、返回差异和变参冲突独立断言诊断。
- 本组沙箱外 `make test` 结果：以主文档 §27.4 的最终记录为准；首轮失败保留在那里。
- 关闭条件：三个类别分别有准确的正反向证据，无目标类别漏检，关系幂等与实现唯一性同时保持。

## ISSUE-G23-003：内建类型与数组的契约满足检查漏过 Semantic

- 状态：已修复，Semantic 正反矩阵及 FCTS 专项通过，已关闭。
- 关闭：2026-09-07 最终沙箱外 `make test` 退出码 0，UBSan／普通配置全部通过。
- 分类：产品缺陷。

### 归属

- 发现组：G23。
- 关联用例：SPEC02、SPEC03、SPEC07～SPEC11、SPEC15、SPEC17、SPEC21、SPEC27。

### 现象与结论

缺少必需方法且实际使用关系的最小非法程序：

```feng
module review.builtin_missing_used;
spec Reader { func read(): i32; }
fit i32: Reader {}
func run(): i32 {
    let reader: Reader = (i32)7;
    return reader.read();
}
```

- 修复前结果：Semantic 无诊断且退出码 0；Codegen 在形成 `Reader` 视角时以当时实际出口
  `CE0319: codegen: missing implementation for spec member 'read'` 失败。
- 删除 `run` 后，无使用点的 `fit i32: Reader {}` 仍被 Semantic 接受；目标改为 `i32[]`
  的未使用缺失方法声明也通过。普通 type 的对应缺失方法反例正确报 `AE0705`。
- 独立签名反例：把 fit 改为 `fit i32: Reader { func read(): string { return "wrong"; } }`，
  不添加使用点，Semantic 同样无诊断且退出码 0。没有据此声称全部错误签名类别均已复现，
  其他签名、字段、父要求和可见性类别由关联 TODO 补齐覆盖。
- 规范依据：[spec 规范 §5～§6](../../specifications/feng-spec.md)及
  [fit 规范 §5～§6](../../specifications/feng-fit.md)要求编译期精确满足全部成员；带块体不是
  “已经实现”的充分条件。spec 自身的默认 witness 不能用于填补具体目标未实现的契约成员。
- 根因：内建／数组分支跳过具名目标路径中的完整满足检查；当前 witness 成员记录允许空实现，
  该漏检路径直到 Codegen 读取空实现时才失败。只把 `CE0319` 字符串改成 AE 不能修复阶段错误。

### 决策与实施

- 方案：基于目标能力、完整 requirement 和当前可见实现执行统一的 Semantic 检查；字段、方法、
  实例／静态、owner 替换、可见性、冲突均使用对应的通用规则。通过检查后才允许有效实现选择
  进入后续发码；不得要求目标先被使用才发现声明本身不满足契约。
- 用例：未使用／实际使用配对，逐项删除成员或改变一个签名条件，以完全满足的 FCTS 正例对照；
  内建／数组路径必须有直接反例，具名目标保留已有证据，不为每种标量宽度机械复制全套测试。
- 错误码：缺失字段／方法和精确匹配错误使用现有 `AE0701`～`AE0705` 中对应根因，可见性和冲突
  按各自稳定 AE；位置在造成违规的适配声明或相关成员／类型 token。仅收敛本问题实际涉及的 CE
  出口，不能把错误码文档的重排编号当作当前实现已产生的码，也不借此迁移其他 CE。
- 既有测试修改：本问题除 ISSUE-G23-001 所关联的两条迁移候选外不计划修改既有用例；若新检查
  暴露其他原测试的非法源码，先逐项记录并再次申请，不删除检查或刷新预期绕过回归。
- 运行时性能：修复发生在编译期，不添加运行时契约补齐、动态检查或默认实现回退。
- runtime 私有 ABI、公开 ABI、`.ft` 格式：不计划变更；复用现有编译期关系／实现选择机制。
- 人工决策与批准范围：已批准随 G23 修复及补测，不扩大旧测试修改清单。
- 实际变更：通用满足检查支持全部合法 fit 目标，统一查找可见方法并替换 owner／fit 实参；
  不为内建目标构造伪 type，不使用 runtime 兜底。

### 验收与关闭

- 准入复现：无使用点的标量／数组缺失方法、标量返回类型错误均通过 Semantic；有使用点的
  标量缺失方法通过 Semantic 后触发当前 `CE0319`。
- 本组专项复验结果：新增缺失成员、错误签名、静态／实例、父成员、可见性及使用／未使用矩阵
  通过；固定诊断阶段、数量、源码位置和 token；合法 FCTS 运行通过。
- 本组沙箱外 `make test` 结果：以主文档 §27.4 的最终记录为准；首轮失败保留在那里。
- 关闭条件：这些程序均在 Semantic 按真实根因拒绝；合法邻界实际运行；不再把用户错误交给
  Codegen 或运行时处理，专项与全量回归通过。

## ISSUE-G23-004：关系与实现分属不同 fit 时合法程序发码失败

- 状态：已修复，发码结构及多目标／跨包 FCTS 专项通过，已关闭。
- 关闭：2026-09-07 最终沙箱外 `make test` 退出码 0，UBSan／普通配置全部通过。
- 分类：产品缺陷。

### 归属

- 发现组：G23。
- 关联用例：SPEC06、SPEC12～SPEC17、SPEC23、SPEC24、SPEC26～SPEC28。

### 现象与结论

最小合法程序：

```feng
module review.builtin_reuse_body;
spec Reader { func read(): i32; }
fit i32 { func read(): i32 { return self; } }
fit i32: Reader {}
func run(): i32 {
    let reader: Reader = (i32)7;
    return reader.read();
}
```

- 修复前结果：Semantic 无诊断且退出码 0；Codegen 在形成 `Reader` 视角时以当时实际出口
  `CE0324: codegen: fit implementation does not match object-form spec coercion source` 失败。
  关系声明有空块体是为独立复现本问题，避免先被 ISSUE-G23-001 的块体限制截断。
- 预期：已有的可见 `read` 实现可以满足该关系，`run()` 返回 7；关系声明本身无须重复提供方法。
  规范依据为 [fit 规范 §4～§6](../../specifications/feng-fit.md)的可见能力和满足规则。
- 根因：[cg_builtin_fit_targets_spec](../../../src/codegen/codegen.c) 只检查提供实现的那个 fit
  自身列出的 spec；non-type subject witness 发码还要求此条件成立。因此，即使 Semantic 已选中
  合法自扩展中的实现，也会因其自身没有 spec 子句而拒绝。关系来源与方法实现来源被错误绑定。
- 已确认范围：上述标量程序；string、数组、enum、tuple、静态方法及跨包组合是待补测范围，
  不在尚无直接复现时宣称它们全部存在同一缺陷。

### 补充复现：泛型 type 的独立实现来源

新增 FCTS 中 `G23Box<string>` 通过独立 fit 满足 `G23Child<string>`（父契约要求 `g23_head`），
Semantic 通过，Codegen 报 `CE0315`。泛型闭合实例的候选路径也错误要求实现 fit 自身列出该契约。
修复接入 Semantic 已选定的 requirement／实现身份，再核对闭合签名，不能只按名称扩大候选。
这一补充与独立实现来源一起修复并通过本包／跨包运行，不新增语言规则。

### 决策与实施

- 方案：Semantic 统一记录已验证关系、精确 requirement 和实际可见方法实现；Codegen 根据
  实现身份恢复正确符号，保持来源 fit／模块和目标类型身份，不要求同一个 fit 同时声明关系与
  方法。不通过复制方法、添加合成关系或按目标名称特判规避缺口。
- 用例：无块体与空块体关系、实例／静态方法、多个 fit 分别提供不同成员、type 自有成员共同
  满足、不同声明／输入顺序；同模块、跨模块及真实 package-public `.ft` 路径均补直接证据。
  反例覆盖关系不可见、实现不可见、签名不匹配和多个不同实现冲突。
- 发码及性能：具体直接调用与 spec witness 转发复用同一方法实现，使用既有 subject 表示；
  不增加 runtime 搜索、wrapper／closure、额外转发、装箱或 ARC 操作。发码结构断言配合 FCTS，
  不能用减少语义检查或运行时回退换取“编译成功”。
- 既有测试修改：不计划修改；新增合法运行回归及对应反例。
- runtime 私有 ABI、公开 ABI、`.ft` 格式：不计划变更；跨包恢复既有方法实现符号。
- 人工决策与批准范围：已批准随 G23 修复及补测。
- 实际变更：authoritative 路径使用 Semantic 选中的方法身份，移除方法所在 fit 必须同时声明
  关系的错误限制；泛型候选路径保留精确签名和所选实现身份，不按裸名称放宽。

### 验收与关闭

- 准入复现：上述程序 Semantic 通过、Codegen 报当前 `CE0324`。
- 本组专项复验结果：多目标、静态、独立 fit 及真实跨包 FCTS 运行通过；新增返回槽矩阵和既有
  direct-call／witness 结构断言通过。多个 fit 与 type 自有方法共同实现、正反声明顺序另有运行对照。
- 本组沙箱外 `make test` 结果：以主文档 §27.4 的最终记录为准；首轮失败保留在那里。
- 关闭条件：合法复用场景经 FCTS 实际运行正确，非法来源在 Semantic 拒绝，精确方法来源及
  无增量运行时操作的发码断言通过，并完成本组全量回归。

## ISSUE-G23-005：同包跨模块的适配被按模块归属误判为孤儿适配

- 关联用例：SPEC23～SPEC26。

### 现象与复现

以下文件作为同一个包的一批源码编译：

```feng
// types.ff
open module g23.types;
open type Item {}

// specs.ff
open module g23.specs;
open spec Reader { func read(): i32; }

// adapter.ff
open module g23.adapter;
import g23.types;
import g23.specs;
open fit Item: Reader {
    func read(): i32 { return 7; }
}

// consumer.ff
module g23.consumer;
import g23.types;
import g23.specs;
import g23.adapter;
func read(item: Item): i32 {
    let reader: Reader = item;
    return reader.read();
}
```

修复前 `tool semantic --target=lib` 拒绝 consumer 的 `item`，报 `AE1003`，退出码 1。
目标与契约源码均属于当前编译包，仅声明所在模块与 adapter 不同，按
[fit 主规范的孤儿适配定义](../../specifications/feng-fit.md#2-术语)不应移除公开关系。

### 分析

- `maybe_downgrade_orphan_fit_export` 使用 `target_module == context->module` 和
  `spec_module == context->module` 判定本地所有权，而不是当前包归属；把关系降为私有后，consumer
  的 import 无法激活该关系。该函数在本轮修改前即如此，不是本轮满足性检查引入的回归。
- 同函数还把内建标量无条件视为本地目标，与内建目标按外部目标处理的规范不符；真正外包的契约
  与内建／数组目标组合需通过真实 `.ft` 的新增正反例核实，不能只依靠本包源码模拟外包。
- 既有 `test_orphan_pu_fit_emits_info_and_downgrades` 将三个源码 program 一同交给 Semantic，
  实际是同包三模块，却断言产生孤儿 info。它锁定了按模块而非按包判断的旧行为。首轮现有
  Semantic 套件通过也确认这条旧断言仍在生效。

### 建议与人工决策点

- 产品修复沿用现有 `FengSemanticModule.origin` 区分本包源码与外包导入；目标或所需契约由当前
  包拥有时保留导出，内建／数组本身不产生本包所有权。纯自扩展仍不受孤儿限制。
- 申请将 `test/semantic/test_semantic.c` 中
  `test_orphan_pu_fit_emits_info_and_downgrades` 的现有源码保留，改为断言无孤儿 info、fit 保持
  public，并重命名为 `test_same_package_cross_module_fit_keeps_public_export`；入口同步改名。
- 原来的真正孤儿行为通过新增真实 package-public `.ft` provider／consumer 用例覆盖：目标和
  契约均来自外包时移除关系导出、仅产生 info，消费方不可使用该关系；同时验证本包合法适配
  可导出，避免用放宽规则绕过反例。
- 人工已批准以上一条旧用例及其调用入口，不扩大到其他既有测试；G23 尚未整体交付。
- 性能／接口：拟改动为编译期所有权和导出资格检查，不增加运行时开销，不变更公开 ABI、runtime
  私有 ABI、`.ft` 格式或模块级绑定实现。

## ISSUE-G23-008：泛型数组方法返回 T 时把存储地址当成返回值

- 状态：按人工批准完成返回槽修复，引用／值类型专项及运行矩阵通过，已关闭。
- 关闭：2026-09-07 最终沙箱外 `make test` 退出码 0，UBSan／普通配置全部通过。
  关联 SPEC17、SPEC27、SPEC28。
- 发现于新增 FCTS 的泛型数组直接调用；已隔离出无 spec、无外包的最小复现，不能归因于
  ISSUE-G23-006 的关系匹配。数组到 spec 实参遗漏 coercion 的问题归 006。

### 最小复现与根因

```feng
module g23.return_probe;
fit T[] {
    func head(): T { return self[0]; }
}
func check(numbers: i32[]): i32 {
    return numbers.head();
}
```

Semantic 与 Feng Codegen 均通过，但生成的方法返回 `void *`，其值是数组元素的存储地址；
`check` 再将该地址直接强转为 `i32`，不是读取元素值。该事实通过生成 C 确认，不以指针截断后的
偶然运行数值作为预期。新增 FCTS 对 `i32[]` 与 `string[!]` 已断言直接调用和 spec 调用的真实结果。

`cg_builtin_fit_return_uses_out` 只识别依赖目标泛参的具名值语义聚合返回，漏掉裸类型参数 `T`。
后者使用存储地址承载，却走了普通 C 返回路径。已有泛型函数的 `cg_emit_generic_return` 使用
调用方返回槽，并按类型描述符完成正确复制／所有权交接，可作为通用修复基础。
该返回判定已与修改前 `HEAD` 核对，内容相同；它不是本轮孤儿归属修复新增的行为。

### 建议方案与批准边界

- 将裸 `T` 返回纳入既有泛型返回槽规则，同步方法声明、方法体、直接调用及 witness 转发；不按
  `i32`、`string`、方法名或 std 特判，不通过堆装箱修补返回值。
- 底层形态从 `void *head(self, descriptors...)` 改为
  `void head(self, descriptors..., void *out)`；Feng 源码签名不变，但导出 fit 方法的生成 C
  调用约定会变化。相关 provider 与 consumer 必须一起重新编译，不能混用新旧二进制。
- 不计划修改 runtime 私有接口或 `.ft` 格式；这仍触及 G23 原定不变的跨包调用约定，因此必须
  先由人工批准，不能仅以“复用已有机制”为理由绕过 ABI 决策。
- 性能边界：不新增堆分配、装箱或运行时契约搜索；正确返回 `T` 需要既有描述符驱动的值复制／
  必要 ARC。它与当前错误的“直接返回地址”发码不同，不能宣称逐指令无增量；不应影响无关方法。
- 获批后新增 Compiler test 和 FCTS 覆盖只读／可写数组、trivial／受管引用／含受管字段的值、
  直接／spec 调用、本包／真实跨包及返回局部值的生命周期；核对实现和调用方约定一致后重新
  执行完整 `make test`。不修改清单外既有用例。
- 2026-09-07 人工已批准上述修复，并明确 `T` 为引用或值类型都必须正确。补测同时检查借用元素
  返回、局部绑定返回、临时数组退出后的结果生命周期；值返回不能别名原元素存储，引用返回保持
  原对象身份且不能提前释放。ABI 批准仅限本问题所需的返回槽及一致转发，不扩展 runtime 接口。

### 实现与专项验证

- 裸 `T` 使用既有泛型共享体返回槽；同时覆盖方法体、具体调用点、调用者仍处于 open `T` 时的
  临时存储，以及 spec witness 到同一个实现符号的转发。没有按某个类型名、方法名或 std 特判。
- `test_g23_generic_array_return_codegen` 交叉只读／可写数组与 `i32`、`string`、引用 type、
  trivial 值 type、含受管字段的值 type、tuple，共 12 格，检查生成 C 可编译、同一实现符号、
  返回槽和直接调用中没有新增 witness、堆分配、额外 retain 或默认初始化。
- `test_g23_spec_fit` 实际覆盖借用元素、局部绑定和参数返回、open `T` 中再次调用、直接／spec
  调用、本包／真实外包；另有 enum、嵌套数组、闭合泛型值／引用实例、callable、object spec。
  引用保持对象身份；值副本与原元素可独立修改；带受管字段的返回值在原数组退出后仍有效。
- 终结器计数断言返回的引用在使用期间不提前析构，调用方退出后恰好析构一次；不是只检查数值
  “看起来正确”。正确复制和必要 ARC 属于获批修复，不能以旧错误地址返回为基准声称逐指令无增量。
