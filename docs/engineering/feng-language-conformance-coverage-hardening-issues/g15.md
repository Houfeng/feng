## ISSUE-G15-001：FUNC-D04 要求返回值的路径可落到 callable 末尾

### 归属

- 发现组：G15；
- 关联组：G16、G17；
- 发现用例：FUNC-D04 实施前的函数主规范与当前 Semantic / Codegen 行为核对。

### 现象与结论

- 最小复现：

  ```feng
  func choose(flag: bool): i32 {
      if flag {
          return 1;
      }
      // flag == false 时控制流到达函数末尾。
  }
  ```

- 实施前实际结果：Semantic 只校验源码中已经出现的 `return`，不分析非 `void` callable 的所有正常
  路径是否均返回值，因此接受该程序；Codegen 会在非 `void` 顶层函数、普通方法或块 Lambda 的末尾
  分别注入包含 `function reached end without return`、`method reached end without return` 或
  `lambda reached end without return` 的 `feng_panic(...)`，示例调用 `choose(true)` 返回 `1`，调用
  `choose(false)` 则运行到该 panic；
- 实施前规范：函数主规范定义了显式返回类型校验和省略返回类型时多个 `return` 的类型推导，但没有定义
  “非 `void` callable 的所有正常结束路径必须返回值”，也没有定义 `throw`、完整分支、循环或可省略
  `else` 的 `match` 如何参与 callable 末尾可达性判断；
- 结论及根因：FUNC-D04 不是单纯测试缺口。人工已经确认，显式或推导为非 `void` 的 callable
  若存在能够正常到达 body 末尾的分支，必须在编译期报错；函数主规范现已补入该结论及分支、异常与
  循环边界，Semantic 已使用通用控制流结果分析实现并由正反向测试固定对应边界。

### 决策与实施

- 状态：已关闭；
- 分类：规范缺失、产品缺陷，均已修复；
- 人工已确认：具有实现 body 的非 `void` 顶层函数、实例 / 静态 / `fit` 方法和目标返回类型非 `void`
  的块 Lambda，所有能够正常到达 body 末尾的路径都必须在此前执行有值 `return`；省略返回类型但
  存在有值 `return` 时，如果仍有路径可正常落尾，也必须拒绝；仅有无值 `return` 或完全没有
  `return` 的 callable 仍推导为 `void`；
- `throw` / `try/catch` 结论：逃逸当前 callable 的 `throw` 终止路径，不要求随后执行有值 `return`；
  若 `throw` 被当前 callable 内的 `try/catch` 捕获，则由匹配 `catch` body 的控制流结果决定是否继续，
  正常完成的主表达式或任一可达 `catch` 都会保留正常路径，未匹配或重新抛出的异常不产生正常落尾；
- 分支结论：普通块在遇到必然终止语句后不再正常落尾；`if / else if / else` 只有存在最终 `else`
  且每个分支均终止时才整体终止；块 `match` 只有存在 `else` 且所有普通分支与 `else` 均终止时才
  整体终止；省略 `else` 时保留未命中并正常落尾的可能；
- 循环结论：“循环参与终止证明”是指编译器根据循环条件和循环体控制转移，证明循环之后的
  代码永远不可到达。例如：

  ```feng
  func maybe(flag: bool): i32 {
      while flag {
          return 1;
      }
      // flag == false 时循环零次执行，函数会正常落尾，必须报错。
  }

  func once(): i32 {
      while true {
          return 1;
      }
      // 条件恒为 true 且循环体必然 return，循环后不可达，合法。
  }

  func forever(): i32 {
      while true {
      }
      // 函数末尾不可达；虽然没有返回值，但不会正常落尾，因此合法。
  }
  ```

  循环可能零次执行或经 `break` 退出，不能仅因循环体中出现过 `return` 就视为 callable 已终止。
  采用通用控制流结果分析：循环条件可能为 false 或存在作用于当前循环的可达 `break` 时保留“正常
  落尾”；`while` 条件为布尔字面量 `true`，或三段式 `for` 省略条件 / 条件为布尔字面量 `true`，且
  没有作用于当前循环的可达 `break` 时移除“正常落尾”。`for/in` 可能零次迭代或正常耗尽，始终保留
  循环后的正常路径。这会接受 `once()` 和 `forever()`；不得把恒真识别扩展为主规范未定义的常量
  折叠，也不得只在某个测试产生点添加特判；
- 是否涉及既有测试修改：除 `ISSUE-G15-003` 经人工批准把一个错误的块式 `match` 正向用例改为
  `AE0515` 反向用例外，全部新增 G15 最小正反向用例；未修改其他既有程序规避缺口；
- 是否涉及运行时性能：已决方案只增加编译期分析，不允许新增运行时分支、调用、分配或 ARC；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否；
- 人工决策与批准范围：2026-09-02 已确认显式或推导为非 `void` 时，存在正常落尾分支必须由编译器
  检查并报错；随后确认采用“正常落尾可达性”规则：逃逸当前 callable 的 `throw` 终止路径，本地
  捕获继续合并 `catch` 结果，可证明没有正常出口的循环使循环后不可达，永不正常退出的非 `void`
  callable 无需实际产生返回值；正常落尾诊断使用函数段 `AE0515`。

### 验收与关闭

- 本组专项复验结果：Parser、Semantic、Codegen 测试程序全部通过，std `604/604`、FCTS
  `1109/1109` 通过；
- 本组沙箱外 `make test` 结果：2026-09-02 通过，UBSan 与 normal 两阶段的 smoke 均为 `90/90`、
  std 均为 `604/604`、FCTS 均为 `1109/1109`，性能约束及其余回归全部通过；
- 关闭依据：函数主规范 §4.1.1、通用控制流结果分析、命名 callable / 块 Lambda 精确反向矩阵和
  FCTS 正向运行证据一致，且全量回归通过。

## ISSUE-G15-002：函数诊断仍产生未进入当前 AE 分段规范的旧错误码

### 归属

- 发现组：G15；
- 关联组：无；
- 发现用例：FUNC-D01、FUNC-D04-A 与 FUNC-D10 实施前的错误码产生点审计。

### 现象与结论

- 最小复现：显式非 `void` 函数执行空 `return;` 产生 `AE0057`；省略返回类型的 callable 出现冲突
  返回类型产生 `AE0058`；重复顶层函数签名、仅返回类型不同和变参覆盖冲突分别产生 `AE0218`、
  `AE0219`、`AE0220`；
- 实际结果：上述错误码均未进入当前 `feng-error-codes-ae.md` 的函数 / Lambda 分段；同类成员方法与
  object-form `spec` 方法签名冲突已经使用 `AE0508`～`AE0510`，顶层函数仍保留另一组旧码；
- 同组审计还确认，显式 `void` callable 中的 `return expr;` 当前沿用普通表达式目标类型不匹配的
  `AE1003`；该根因是返回语句值形态不合法，应迁移到 `AE0501`。当前没有需要修改的既有精确码断言，
  由 G15 新增用例覆盖；
- 需要迁移的原因：`AE0057`、`AE0058` 是函数专属返回诊断，却仍位于当前规划为跨结构通用语义的
  `AE00` 段；`AE0218`～`AE0220` 是函数签名诊断，却落入当前规划为数组语义的 `AE02` 段。继续保留
  会使错误码编号表达的领域与实际根因不一致；同一种重复签名在顶层函数和成员方法上还会产生不同
  错误码，无法形成统一稳定的用户诊断契约；
- 既有断言必须更新的原因：FUNC01-D～FUNC06-D 的测试主体与语义无需改变，但六条测试把旧码
  `AE0058` 作为精确预期。Semantic 产生点切换到函数段新码后，原断言必然失败，因此只需把这六个
  预期码同步为新稳定码；这不是为了让错误实现通过，也不改变测试程序的接受 / 拒绝行为；
- `AE0057`、`AE0219` 与 `AE0220` 已有直接 Semantic 用例但没有精确码断言；在原用例中只补相应新码
  断言，比复制相同源码新增同构用例更直接，因此一并列入有限白名单。`AE0218` 缺少合适的非泛型
  顶层重复签名精确证据，使用新增用例覆盖，不修改其他既有测试；
- 可选但不建议的替代方案：保留全部旧码并把它们补写进主错误码规范。该方案无需修改六条断言，但会
  永久保留函数诊断跨 `AE00`、`AE02`、`AE05` 三个段分散，以及顶层函数与成员方法同类不同码的问题，
  与当前 AE 分段归类原则不一致；
- 规范依据与预期结果：相同冲突对象、根因和修复动作应复用同一稳定码。顶层函数与成员方法的重复
  签名、仅返回类型不同和变参覆盖冲突统一使用 `AE0508`～`AE0510`；非 `void` callable 的空
  `return;` 复用返回语句值形态码 `AE0501`，冲突的推导返回类型使用 `AE0504`，正常落尾使用
  `AE0515`；
- 结论及根因：错误码分段迁移未覆盖基本返回检查和顶层函数签名冲突，属于诊断契约未收敛，不代表
  现有接受 / 拒绝语义本身均有错误。

### 决策与实施

- 状态：已关闭；
- 分类：产品缺陷；
- 实施方案：将 `AE0057` 迁移为 `AE0501`，将 `AE0058` 迁移为 `AE0504`，将 `AE0218`～`AE0220`
  分别迁移为 `AE0508`～`AE0510`，并将 `void` callable 的 `return expr;` 从 `AE1003` 迁移为
  `AE0501`；ISSUE-G15-001 新增的非 `void` callable 正常落尾诊断使用 `AE0515`。只迁移这些 G15
  直接覆盖的产生点，不开展无关错误码重构；
- 是否涉及既有测试修改：是，且仅允许修改下列白名单中的既有 Semantic 测试函数：

  - FUNC01-D：`test_top_level_function_rejects_conflicting_inferred_return_types`，将精确预期码
    `AE0058` 更新为 `AE0504`；
  - FUNC02-D：`test_instance_method_rejects_conflicting_inferred_return_types`，将精确预期码
    `AE0058` 更新为 `AE0504`；
  - FUNC03-D：`test_static_method_rejects_conflicting_inferred_return_types`，将精确预期码
    `AE0058` 更新为 `AE0504`；
  - FUNC04-D：`test_fit_instance_method_rejects_conflicting_inferred_return_types`，将精确预期码
    `AE0058` 更新为 `AE0504`；
  - FUNC05-D：`test_fit_static_method_rejects_conflicting_inferred_return_types`，将精确预期码
    `AE0058` 更新为 `AE0504`；
  - FUNC06-D：`test_block_lambda_rejects_conflicting_inferred_return_types`，将精确预期码 `AE0058`
    更新为 `AE0504`；
  - `test_explicit_non_void_return_rejects_empty_return`，只新增精确预期码 `AE0501` 断言；
  - `test_function_return_only_overload_error`，只新增精确预期码 `AE0509` 断言；
  - `test_variadic_overload_conflict_rejected`，只新增精确预期码 `AE0510` 断言；
  - `test_variadic_single_fixed_and_variadic_overload_conflict_rejected`，只新增精确预期码 `AE0510`
    断言。

  上述白名单只授权替换或新增列明的错误码断言，不授权修改测试源码字符串、接受 / 拒绝结果、诊断
  数量、路径、token、行列、消息断言或既有 runner 登记。G15 可自由新增测试函数、测试文件及其必要

- 是否涉及运行时性能：否，仅涉及编译期诊断码、规范与测试；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否；
- 人工决策与批准范围：2026-09-02 已批准上述稳定码迁移，并批准严格按十条白名单范围修改既有用例；
  除白名单外只允许新增用例，其他既有用例如需修复必须再次人工决策。

## ISSUE-G15-003：既有块式 `match` 正向用例依赖非 `void` callable 正常落尾

### 归属

- 发现组：G15；
- 关联组：G12；
- 发现用例：`test_match_enum_block_tail_return_value_accepted`。

### 现象与结论

- 最小复现：

  ```feng
  func describe(c: Color): int {
      match c {
          Color.Red { 1; }
          Color.Green { 2; }
          else { 3; }
      }
  }
  ```

- 实施前用例把上述程序作为正向 Semantic 用例；G15 正常落尾检查实施后，专项首轮在函数名
  `describe` 处产生 `AE0515`，导致该既有正向断言失败；
- 该块式 `match` 是语句，不是 `return match ...;` 表达式。分支末尾的 `1;`、`2;`、`3;` 只作为
  分支内表达式语句执行，不会把值返回给 `describe`；现有 Codegen 的块式 `match` 路径同样逐分支
  生成普通语句，随后仍会到达函数末尾兜底，因此该正向断言没有对应的可运行返回行为；
- 结论及根因：这是 G15 新规则揭示的既有测试预期错误，不是应由控制流分析保留的隐式返回语义。
  若要返回 `match` 的结果，合法写法是 `return match c { ... };`；若保留当前源码，则应作为
  `AE0515` 反向用例。

### 决策与实施

- 状态：已关闭；
- 分类：既有测试预期错误；
- 建议方案：将该用例改为反向 Semantic 用例，保留源码不变，重命名为
  `test_match_enum_block_tail_does_not_implicitly_return`，精确断言一个位于 `describe` 名称 token 的
  `AE0515`，并同步修改其既有 runner 登记；这样既保留“块式 `match` 不构成隐式返回”的独立边界，
  又不与紧邻的 `test_match_enum_expression_form_accepted`（已经直接覆盖 `return match ...;`）形成重复；
- 可选方案：只把源码改为 `return match ...;` 并继续作为正向用例；该方案与紧邻的既有表达式形态
  正向用例重复，且无法锁定本次发现的落尾边界，因此不建议；
- 是否涉及既有测试修改：是；该测试不在 `ISSUE-G15-002` 已批准的十条白名单中，实施前必须取得
  新的人工授权；2026-09-02 已批准按建议方案改为 `AE0515` 反向用例，并要求在 FCTS 中补齐
  `match`、`if`、`try/catch`、`for`、`while` 等各类合法分支的运行证据；
- 是否涉及运行时性能、runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否。

### 验收与关闭

- 隔离审计结果：在当前 G15 实现上逐个独立运行全部既有 Semantic 测试，除六条已批准从 `AE0058`
  迁移为 `AE0504` 的白名单断言外，仅该测试出现新的非白名单失败；
- 本组专项复验结果：获批迁移后的 `test_match_enum_block_tail_does_not_implicitly_return` 精确产生一个
  名称 token 上的 `AE0515`；相邻表达式形态正向用例保持通过，`if`、`match`、`try/catch`、`for`、
  `while` 的正向 FCTS 均已补齐并真实运行；
- 本组沙箱外 `make test` 结果：2026-09-02 通过；UBSan 与 normal 两阶段全部通过；
- 关闭依据：人工批准的既有用例迁移、精确 Semantic 断言、FCTS 正向分支证据及全量回归均已完成。

## ISSUE-G15-004：非法块 Lambda 参数触发目标类型级联诊断

### 归属

- 发现组：G15；
- 发现阶段：新增 FUNC-D02 精确 Semantic 反向矩阵；
- 最小复现：

  ```feng
  spec Mapper(value: i32): i32;

  func run(): void {
      let mapper: Mapper = (value: void) -> 1;
  }
  ```

### 现象与分析

- Semantic 在 Lambda 参数类型 `void` 处正确产生 `AE0502` 后，又在 Lambda 起始 `(` 处产生
  `AE0522`，把已经非法的 Lambda 再解释为“不匹配目标函数类型”；
- 根因是带显式类型的 binding 先解析 initializer，再无条件执行目标类型贴合。initializer 解析期间
  虽已追加根因诊断，但解析函数的布尔返回值表达的是解析过程是否可继续，不等同于“没有新增诊断”，
  因而后续目标贴合仍会生成派生诊断；
- `AE0522` 不提供新的修复信息，并违反 G15 最小反向程序“一个根因、一个稳定诊断”的验收约束。

### 处理方案

- 状态：已关闭；
- 在 typed binding 的 initializer 解析前后比较诊断数量；若 initializer 自身已经新增诊断，则跳过该
  initializer 的目标类型贴合，但保留已经记录的根因诊断；
- 该处理按“无效源表达式不再产生派生目标贴合诊断”的通用规则实现，不针对 `void`、Lambda 名称或
  某个测试输入增加特判；
- 是否涉及既有测试修改：否，只新增 G15 精确反向用例；
- 是否涉及运行时性能、runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否，仅改变编译期诊断收敛。

### 验收与关闭

## ISSUE-G15-014：块 Lambda 目标返回检查漏过表达式内部的分支块

### 归属

- 发现组：G15；
- 发现阶段：FUNC-D08 实现审计；
- 发现位置：块 Lambda 的目标返回值与返回形态递归检查。

### 现象与分析

- 当前递归检查直接覆盖语句级块、`if`、`match`、`try/catch`、循环与 `defer`，但对 binding initializer、
  赋值表达式、普通表达式语句和 `return` / `throw` 操作数没有继续遍历表达式树；
- 因此 `let value = try may_fail() catch { return "bad"; };` 中的 `return` 属于当前块 Lambda，却会在
  Lambda 作为直接实参、目标 callable 只在重载选定后才明确时逃过 `i32` 返回目标检查；修复前该
  最小非法程序被 Semantic 错误接受；
- 正常落尾分析已经递归覆盖同一表达式树，因此可能正确判断该 Lambda 没有正常落尾，却未同步验证其中
  的返回值类型，形成两套遍历边界不一致；
- 嵌套 Lambda 的 body 不应进入该遍历，因为它具有独立 callable 返回上下文。

### 处理方案

- 状态：已关闭；
- 新增最小 Semantic 反向用例：目标返回类型为 `i32` 的直接实参块 Lambda，在 binding 内嵌
  `try/catch` 的 catch 中 `return "bad";`；补全候选探测后该 Lambda 不匹配形参 callable，普通函数
  在调用名称处稳定产生一个 `AE0512`，与其他实参签名不匹配保持同一诊断层次；
- 将返回形态和返回值目标检查抽象为完整的 statement / expression 递归遍历，覆盖数组、tuple、对象
  字面量、调用、成员、索引、一元、二元、转换及表达式形式的 `if/match/try`，遇到嵌套 Lambda 时停止；
- 不改变正常落尾规则、诊断码或运行时发码，不增加声明面特判；
- 同时新增合法 FCTS：同一表达式位置的 catch 返回固定宽度数值字面量，必须按 `i32` 目标贴合并真实
  调用运行；
- 是否涉及既有测试修改：否，只新增 G15 精确反向用例；
- 是否涉及运行时性能、runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否，仅完善编译期 AST 遍历。

### 验收与关闭

- 专项结果：最小用例已确认修复前被错误接受；修复后在普通调用名称处精确产生一个 `AE0512`；合法
  FCTS 中表达式内嵌 catch 的 `i32` 返回按目标贴合并真实运行，Semantic 与 FCTS 专项通过；
- 本组沙箱外 `make test`：2026-09-02 通过；UBSan 与 normal 两阶段全部通过；
- 关闭依据：statement / expression 通用递归遍历覆盖表达式拥有的分支块，并在嵌套 Lambda 边界停止；
  反向、正向及全量回归均通过。

## ISSUE-G15-015：块 Lambda 返回目标重放泄漏子块局部绑定

### 归属

- 发现组：G15；
- 发现阶段：全量回归后的最终差异与作用域审计；
- 发现位置：直接实参块 Lambda 在重载选定后的返回目标检查。

### 现象与分析

- 最小复现：

  ```feng
  spec Picker(flag: bool): i32;

  func consume(picker: Picker): i32 {
      return picker(true);
  }

  func run(): i32 {
      return consume((flag: bool) {
          let value: i32 = 1;
          if flag {
              let value: string = "shadow";
          }
          return value;
      });
  }
  ```

- `return value` 按词法作用域应读取外层块的 `i32 value`，子块中的 `string value` 在 `}` 后已经离开
  作用域；当前 Semantic 却在 `consume` 处产生 `AE0512`，错误地认为该 Lambda 不匹配 `Picker`；
- 根因是延迟目标检查为取得块内局部类型，先调用 `infer_block_return_type` 重放整个 Lambda body。该
  既有推断遍历会把递归子块中的临时局部加入同一个重放作用域，离开子块时没有恢复，因此子块
  `string value` 错误遮蔽后续 `return value`；
- 实际源码的首次 Semantic 解析已经在正确的词法作用域内得到每个 `return` 表达式的类型，延迟目标
  检查不应通过第二套不完整作用域模型重新猜测。

### 处理方案

- 状态：已关闭；
- 在首次解析块 Lambda 的 `return expr;` 时，使用已有 Semantic type-fact 机制保存该表达式在真实词法
  作用域中的类型；只记录 Lambda 自身的有值返回，不扩大到所有标识符或普通函数表达式；
- 候选探测与重载选定后的目标检查复用该 type fact，并移除为目标检查预先调用
  `infer_block_return_type` 的三处作用域重放；目标贴合、数值字面量提交及正常落尾仍使用既有通用路径；
- 新增正向 Semantic / FCTS，分别覆盖子块局部返回和子块同名遮蔽结束后恢复外层局部；新增反向
  Semantic，确认子块局部的真实不兼容返回仍被拒绝；
- 是否涉及既有测试修改：否，只扩展 G15 新增测试；
- 是否涉及运行时性能、runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否；仅新增少量编译期 Lambda
  返回表达式类型事实并减少重复推断遍历。

### 验收与关闭

- 专项结果：修复前最小正向程序在 `consume` 处错误产生 `AE0512`；修复后子块局部返回、子块同名
  遮蔽结束后恢复外层局部两项正向 Semantic / FCTS 均通过，真实不兼容子块返回仍稳定产生
  `AE0512`；Parser、Semantic、Codegen、std `604/604` 与 FCTS `1109/1109` 专项通过；
- 本组沙箱外 `make test`：2026-09-02 修复后重新执行并以退出码 `0` 通过；UBSan 与 normal 两阶段
  全部通过；
- 关闭依据：精确表达式类型事实替代不完整作用域重放，最小正反向矩阵、专项和修复后的独立全量
  回归全部通过。
