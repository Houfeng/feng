## ISSUE-G24-001：union 泛型约束漏检无关类型

### 归属

- 发现组：G24，2026-09-07 文档细化。
- 关联组：G25 通用泛型约束检查。
- 关联用例：COMPOSITE23、COMPOSITE24、COMPOSITE27、COMPOSITE28、COMPOSITE31。
- 状态：已关闭（2026-09-09）；约束准入与最终完整回归均已通过。
- 分类：产品缺陷及规范文字不一致。

### 现象与结论

- Review 前的规范事实：[联合类型主规范](../../specifications/feng-union-type.md) §3.12 写明 union 约束不是
  进入 union 的值流站点，并称实参类型必须已是某个 member、不能先进入 union 再传入。
- 既有测试事实：[`test_union.ff`](../../../fcts/fcts_bin/src/test_union.ff) 的
  `simple union as generic constraint (int)`／`(string)` 已明确将整个 `SimpleUnion` 值传给
  `identity_union<T: SimpleUnion>`，另外也覆盖整个 `ParentUnion` 与其 `ChildUnion` member。
  这些是已登记 FCTS 的测试源码，不是注释中的待实现示例。

现有用例的核心结构如下，类型与函数名沿用原例：

```feng
spec SimpleUnion: int | string;

func identity_union<T: SimpleUnion>(value: T): T {
  return value;
}

func example(): SimpleUnion {
  let value: SimpleUnion = 42;
  return identity_union(value);
}
```

这里传入值的静态类型是 `SimpleUnion`，不是其直接 member `int`；不能以运行时 active member
为 `int`，就把该测试归类为“直接传入具体 member”。后续最小程序已分别验证整个 union 类型的
显式实参、推导实参与具体 member，均可编译运行；这只能证明这些合法入口，不能证明约束检查完整。

- 另外，跨包 [`test_generic_advanced_composition_coverage.ff`](../../../fcts/fcts_bin/src/test_generic_advanced_composition_coverage.ff)
  的 `concrete leaves satisfy a generic union constraint directly` 确实直接传入引用、值类型及
  标量 member。这是不同的准入场景，不能用它解释或替代上述整个 union 值的测试。
- 实现事实：[`analyzer.c`](../../../src/semantic/analyzer.c) 的
  `generic_type_arg_satisfies_constraint` 对非 object／intersection form 提前返回 `true`，
  注释明确包含 union。最小反例已确认下列三个入口均漏检，分别编译运行成功，而非 Semantic 报错：

```feng
spec Choice: i32 | string;
func accept<T: Choice>(value: T): T { return value; }
type Box<T: Choice> { var value: T; }

// 分为三个独立程序核验；bool 不满足 Choice 约束。
func explicit_arg() { accept<bool>(true); }
func inferred_arg() { accept(true); }
func owner_arg() { let box = Box<bool> { value: true }; }
```

- 结论：显式调用、推导调用及 type owner 实例化存在已复现的约束漏检。开放泛参转传等入口仍须
  独立补测，不能由这三个反例推断所有入口的行为。泛型体内 match 的独立缺口见 ISSUE-G24-004。

### 决策与实施

- 人工决定：修复约束漏检；union 必须支持作为约束及类型实参。主规范已明确同一完整闭合
  union 的自反准入，并移除“不能先进入 union 再传入”的不准确限制；既有合法实参不转为反例。
- 后续人工已确认准入与普通联合绑定的满足规则一致，复用其编译期检查；规则只在联合主规范
  §3.12 定义。调用、推导、owner 和开放转传须统一查询，不在 Codegen 或运行时补约束检查，
  也不因复用资格判断就物化约束 union 或改变实际 T。间接 leaf、经名义关系进入 spec member
  及开放转传不再单独待决策；原反例和 COMPOSITE23／27 继续覆盖无路径、歧义与错误闭合实例。
- 主计划 §28.1.3.1 的三个程序现为应通过的待实现用例，不是本轮新执行的成功或失败结果。
  配对普通绑定与泛型准入的编译期结果；开放来源约束自身作为实际类型的情况不能漏检。
- 实施诊断：调用入口继续使用既有重载适用性诊断；type／spec owner 的非法类型实参在
  Semantic 使用 `AE0710` 定位到该实参 token。关系证明使用完整实例，不只检查声明身份。
- 是否涉及既有测试修改：本次没有。若决定改变既有 `identity_union`／`identity_parent` 的合法
  预期，必须逐条列出受影响测试并再次批准，不能借修复其他非法实参漏检删除这些正例。
- 是否涉及运行时性能：本次没有。后续准入校验应在 Semantic 完成，不能增加运行时约束判断或
  witness；如果具体修复需要新增成本，另行决策。
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：本项准入检查不需要；共享收窄字段的
  必要契约迁移批准另记 ISSUE-G24-004，不是本项的无关 ABI 改造授权。
- 人工决策与批准范围：已批准上述修复、准入复用及复合 spec 泛型支持；未批准旧用例迁移。
- 实际变更：已接入通用联合绑定资格检查并补齐显式、推导、owner 与开放转传证据；最终实现与
  测试范围见 G24 验收证据。

### 验收与关闭

## ISSUE-G24-002：union 进入路径的固定容量与无深度上限规范不一致

### 归属

- 发现组：G24，2026-09-07 文档细化。
- 关联组：无；不等同于 G21 数组维度问题。
- 关联用例：COMPOSITE10、COMPOSITE31、COMPOSITE32。
- 状态：已关闭（2026-09-09）；可变长路径及深层正反证据已通过最终回归。
- 分类：产品缺陷。

### 现象与结论

- 规范事实：[联合类型主规范](../../specifications/feng-union-type.md) §3.8.4 明确嵌套深度无
  硬限制，§3.8.1 要求编译期确定完整进入路径，运行时执行该路径对应的 tag 与 payload 写入。
- 实现事实：[`analyzer.c`](../../../src/semantic/analyzer.c) 中
  `UNION_MAX_PATH_DEPTH` 固定为 `8U`，`UnionMemberSelection.path_indices` 使用该固定容量；
  `select_union_member_for_expr_type` 在复制嵌套路径时将超过容量的 `copy_len` 限为 7，再在
  前面放入当前层，仍把结果标记为 matched。这里丢失的是选中路径的后缀，不是用户主动结束匹配。
- 既有证据边界：[`test_nested_union.ff`](../../../fcts/fcts_bin/src/test_nested_union.ff) 中的
  两／三层进入与链式匹配无法验证该容量边界；不能由这些测试通过推导更深路径也完整。

已核验的最小程序核心：

```feng
spec U1: i32 | string;
spec U2: U1 | bool;
spec U3: U2 | bool;
spec U4: U3 | bool;
spec U5: U4 | bool;
spec U6: U5 | bool;
spec U7: U6 | bool;
spec U8: U7 | bool;
spec U9: U8 | bool;

func enter(value: i32): U9 {
  return value;
}
```

该源类型到 `U9` 需要 9 个 member 索引。规范预期是完整保留至 `i32` 的路径；实施时应通过
Semantic 路径断言及实际逐层／链式收窄读回非零 payload 验证，并以 `U8` 作边界内对照。

- 实际结果：8 段路径进入并读回 `42` 成功；9 段路径仍编译成功，但生成 C 把终点的标量用于
  初始化内层 `U1` 聚合体，落在 tag 而非其 `i32` payload，伴随 C 聚合初始化警告。链式收窄
  读回不再为 `42`，触发验证程序主动抛出的异常；不是笼统意义上的“编译器崩溃”。
- 结论及根因：路径在 Semantic 的 `UnionMemberSelection` 中静默截断，导致后端缺少完整路径。
  `semantic.h` 的 `FengUnionCoercionSite` 还有独立固定容量，修复须同时覆盖记录、复制、消费和
  释放，不只替换第一处常量。

### 决策与实施

- 实施方向：使用编译期通用可变长路径并明确所有权，所有生产／消费方保留完整路径。不得添加
  “第 9 层”特判，也不能仅把常量调大或给主规范增加深度上限来掩盖问题。
- 实施细节：路径选择结果临时拥有可变长索引数组，转换站点深拷贝并由 Semantic analysis
  统一释放；Codegen 的缺省单层路径使用本地借用索引，不写入共享站点的内存。保持原有静态
  tag／payload 发码，不引入运行时路径遍历。
- 是否涉及既有测试修改：目前不需要，新增容量边界两侧的独立测试；若后续发现旧例需变更，另报。
- 是否涉及运行时性能：编译期路径存储变化不应引入运行时搜索；更深合法 union 本身已有的嵌套
  tag／payload 操作不等于允许在所有 union 上增加开销。具体方案仍须审查，不能提前宣称零成本。
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：本轮没有；在查明所有消费者之前不承诺
  修复完全不涉及承载结构，若实际需要改变上述边界，必须先取得明确批准。
- 人工决策与批准范围：已批准修复，保持既有无深度硬限制规则；未批准 ABI 或格式变更。
- 实际变更：进入路径改为编译期可变长所有权模型，Semantic 记录与 Codegen 消费保留完整路径。

### 验收与关闭

## ISSUE-G24-003：intersection 同名字段冲突未在 Semantic 阶段拒绝

### 归属

- 发现组：G24，2026-09-07 用例矩阵细化。
- 关联组：G23 已交付的 object-form 父字段规则；不改动其结论。
- 关联用例：COMPOSITE20、COMPOSITE26、COMPOSITE31。
- 状态：已关闭（2026-09-09）；交叉字段合并／冲突矩阵已通过最终回归。
- 分类：规范遗漏及 Semantic 检查缺失。

### 现象与结论

- Review 前的规范事实：[`spec` 主规范](../../specifications/feng-spec.md) §4／§5 为 intersection 明确了
  方法签名相同去重、仅返回类型不同冲突、合法不同参数保留重载；同一文件另明确 object-form
  父字段叠加时，同名字段即使类型和 `let`／`var` 相同也冲突。后者的对象是 object-form 父列表，
  不能自动扩大为两个独立 object-form spec 在 intersection 中组合的规则。
- 历史材料：[交叉类型设计记录](../feng-intersection-type-draft.md) §3.1／§8 曾描述把字段
  视为 getter／setter 合并，并称同名不同类型在交叉定义处冲突。它不是本计划的主规范依据，且
  不能单靠该实现描述决定同名同类型、`let`／`var` 不同或实例／静态字段的全部语言预期。
- 既有证据边界：[`test_intersection.ff`](../../../fcts/fcts_bin/src/test_intersection.ff)
  的 `NamedId` 使用不同名的 `iname`／`iid` 字段，证明字段可通过交叉约束使用，但不能证明
  两个独立组成 spec 的同名字段该合并还是拒绝。

经人工 Review 确定验收预期的声明示意：

```feng
spec A { let value: i32; }
spec B { let value: i32; }
```

## ISSUE-G24-004：union 约束泛型体的合法 match 未正确发码

### 归属

- 发现组：G24，2026-09-07 最小程序核验。
- 关联用例：COMPOSITE24、COMPOSITE31、COMPOSITE32、COMPOSITE34、COMPOSITE37～42。
- 状态：已关闭（2026-09-09）；共享泛型体的联合收窄及投影矩阵已完成。
- 分类：产品缺陷；属于已要求支持的复合约束能力，不是新增 match 语义。

### 现象与结论

```feng
spec Choice: i32 | string;

func read<T: Choice>(value: T): i32 {
  return match value {
    v: i32 { v }
    v: string { 11 }
    else { -1 }
  };
}
```

最小程序分别调用 `read<Choice>`、`read<i32>`、`read<string>`，Semantic 接受泛型声明，
Codegen 却在 match 处给出 `CE0211`：目标必须是 integer、bool 或 string。已有返回 `T` 的
identity 用例成功不代表泛型体内收窄也成功；当前开放 `T` 的发码没有正确消费 union 约束视角。

### 决策与实施

- 按联合主规范 §3.12 补齐通用 lowering，同时支持整个 union 和合法 member 作为 `T`；保存
  原始 `T` 布局，不能把裸 member 的存储直接强转为 union 聚合体，也不能无条件重新装箱成 union。
- 实施补充复现：`spec Choice<Element>: Element | bool;` 与
  `read<T: Choice<i32>>` 中的 `match v { x: i32 { x } else { -1 } }` 在 Semantic 得到
  `AE0605`。匹配入口把裸 `T` 引用当作 `Choice` 的实例引用，丢失约束中的 `i32` 替换。
  应先恢复完整约束引用，再走原有标签／成员检查；这是本项泛型收窄缺口的一部分。
  声明期投影事实同时保留原 subject 类型与完整约束类型，不能用后者替换前者的存储身份。
- 投影元信息续作检查：Parser 的 `label.type` 保存首段，`type_chain` 仅保存后续箭头段。
  当前新增 sidecar 对链式标签尚需合并首段与后续段，并新增两／多段元信息断言；
  已通过的四入口 sidecar 用例只覆盖单段，不把它们记为完整链式投影验收。
- 2026-09-08 人工确认按[联合主规范 §3.12／§3.13](../../specifications/feng-union-type.md#312-union-form-可作为泛型类型参数约束)
  补齐共享体收窄能力，不只修复上例的直接 member 标签。新增 COMPOSITE37 对照普通 union
  验证逐级绑定、链式路径、中间层绑定值、非法路径及同包／跨包行为。约束准入边界仍归
  ISSUE-G24-001；不能把此确认解释为允许任意间接叶子或隐式改变实际 `T` 的承载。

  闭合后不因类型归一化或静态不匹配而重排槽位。不增加独立投影隐藏参数或另一条 callee 上下文链，

## ISSUE-G24-006：spec 类型实参使用转接 witness，不能据此宣称无额外开销

### 归属

- 发现组：G24，2026-09-07 生成 C 与共享体实现核验。
- 关联用例：COMPOSITE26、COMPOSITE29、COMPOSITE31、COMPOSITE32、COMPOSITE33～COMPOSITE36。
- 状态：待修复（人工已批准本组暂缓消除优化；不阻塞 G24，不标为已修复）。
- 分类：性能风险；既有转接开销已知且本组允许保留，不是本轮修改引入的回归。

### 现象与结论

```feng
spec Named { func read(): i32; }
spec Tagged { func tag(): i32; }
spec Both: Named & Tagged;

func identity<T: Both>(value: T): T {
  value.read();
  value.tag();
  return value;
}
```

最小程序以引用 subject、值 subject 承载的 `Both` 值调用 `identity<Both>`，结果正确且返回的引用
保持身份；但生成 C 的调用路径为：

```c
/* 结构摘要：共享体先通过类型参数的转接 witness 调用。 */
T_descriptor->witness->read(spec_value_storage);

/* 转接函数再从完整 spec 值中取得实际 subject／witness。 */
value->witness->read(value->subject);
```

`cg_generic_descriptor_expr` 为 spec 实参选择 `cg_ensure_spec_slot_witness`，后者生成上述
转接。非泛型的同一 spec 值调用则直接使用值内 witness，不需要第一层转接。这里确认的是发码
多一层间接调用；未测量耗时，也不把同包优化器可能消除转接说成跨包必然零成本。

本记录中的转接指实际 `T` 为 spec、且共享泛型体通过需要 witness 的约束访问其成员的路径。
spec 仅作为约束而实际 `T` 为具体类型，不产生这一层 spec slot 转接；无约束泛型仅传递／返回
spec 值也不产生上述成员调用转接。不得将它泛化成所有泛型调用都存在的额外层。

整个 union 作为 `T` 的 identity 已可运行且不物化 witness；不能把交叉的转接问题误写成 union
也有 witness。但 union 约束体还存在 ISSUE-G24-004，仍未完成实际 match 的开销核验。

### 后续优化的分析与方案边界（非 G24 实施前置）

- 当前共享泛型体以存储地址和每个类型参数一个 `FengGenericParamDescriptor` 工作，描述符保存
  值分类、布局描述及约束 witness。`T = Both` 时参数仍是完整 `{subject, witness}`，不能仅将
  描述符改为 subject 的具体类型或传入底层对象指针：返回 `T`、字段／数组存储和 ARC 将不再匹配。
- 也不能把某一个实参值内的 witness 当作 `T` 唯一的类型级 witness；同一 `T = Both` 的两个
  值可以由不同具体类型承载，它们的实际 witness 不同。
- 后续若开展消除优化，方案必须同时解决完整 `T` 存储与逐值约束访问、多个同 `T` 参数、泛型转传、owner 字段及
  union 整体／member 的表示差异，复用通用抽象，不能按某个 spec 名称或调用点加特判。
- 主规范现有方向为共享 body，并支持 consumer 不持有 provider 源码的二进制消费。不能仅在
  同包复制专门函数体、依赖内联或忽略跨包便宣称满足要求。如果方案需改变共享体策略、生成 C
  调用约定、runtime 私有 ABI 或 `.ft`，必须列清变动及成本后另行 Review，不能用本次功能批准
  代替该批准。目前尚未选定或实施此类方案，也不断言 ABI 改动必然不可避免。

### 决策与验收

- 人工最新决定：本次不消除已了解的 spec 泛型转接层，允许保留现状；不得增加其他增量运行时
  开销。本项不再作为 G24 开始或交付的前置，不要求先完成其通用消除方案 Review。
- 暂缓仅针对这层既有转接的优化。联合／交叉的编译期约束证明、参数／返回／存储、逐值分派、
  所有权和跨包正确性仍须完整补测；发现错误仍先记录、分析、修复，不能以本项暂缓跳过。
- 本组不增加转接层数，不把原本无需此层的路径改为转接，不引入新的装箱、重复值复制、运行时
  约束查询或其他成本。COMPOSITE36 改为变更前后及同类合法路径的增量成本对照，不要求证明
  现有转接不存在，也不通过本项批准更改 ABI／格式或扩大性能成本。
- 本组沙箱外 `make test` 结果：尚未执行；本轮未修改编译器、runtime 或正式测试。
- G24 可在其余正确性修复、覆盖和无新增成本验收及沙箱外 `make test` 全部通过后独立交付，
  交付记录须明列本项是获批延期而非已修复。本项将来关闭仍需单独的优化方案及成本、行为验证。

## ISSUE-G24-038：else 剩余集合的旧描述与显式绑定规则存在歧义

### 复现与规范核对

因此不能仅按提交先后替人工决定 else 是例外还是仅指匹配剩余集合。建议保持现有显式绑定
模型：else 不自动改变原绑定类型，需要成员访问时再显式匹配绑定；待人工确认后对齐文档和正反例。

### 后续核对

描述，不增加语言能力或改动实现。COMPOSITE14 补单剩余／多剩余、原绑定拒绝与新绑定正例。

```feng
func inner<T: Right>(value: T): i32 { return value.right(); }
func outer<T: Both>(value: T): i32 { return inner<T>(value); }
```

Semantic 通过，`inner<T>(value)` 报 `CE0293`。原因：`FengGenericParamDescriptor.witness`
描述当前约束，Both 的合并布局不能直接作为 Right 的布局；不能只删前缀检查。
已有普通 spec 向上转换可读取父 witness，但开放 T 转传还必须保留实际 T 的 kind／descriptor、
向内层提供不同 constraint witness。当前函数描述符没有相应泛参描述符表。

最小的局部改法会在调用点构造临时三字段泛参描述符，新增初始化／栈占用和父 witness 读取；
不能按“旧 spec adapter 已获批准”自动接受该成本。另一方向是在具化点生成静态泛参描述符，
由共享调用的描述信息选择，避免逐次构造，但需要明确额外描述信息的归属与承载。
本轮未实施以上两种改法；建议先 Review 静态承载方案，再补同／异 form、各组成顺序、泛型
实例、值／引用／spec 实际 T、多层／owner／方法入口与非法反向的完整用例，重新全量回归。

早期 Review 方向（未采用，保留为历史记录）：在 `FengFunctionDescriptor` 增加与两个类型描述符对齐的
`reified_generic_params_count`／`reified_generic_params`，具化点静态生成内层调用所需的
实际 T 加目标约束 witness 描述符；共享转传通过既有 callee 描述符通道选择该静态表。
保留现有泛参隐式参数，不在本项顺带重做整个泛型调用 ABI。增量为函数描述符字段、静态表和
必要读取，不在每次转传时初始化临时描述符，不新增堆分配或 spec adapter 层。
该方向未实施，已由下方的泛参描述符字段方向替代；仍须核对 owner／方法域、递归和导入
信息的完整性。`.ft` 仍为 2.0，只重建当前制品，不增加任何旧制品兼容路径。

### 051 续作范围与描述符生命周期核对（2026-09-09）

人工要求继续修复 051，优先复用当前泛参约束 witness 的组成 witness 指针；类型级与方法级
泛参都必须正确，成员绑定中的 `inner<T>` 也必须覆盖。`inner<T>(value)` 保持同一个实际 T，
不是把交叉 spec 值显式转换到成员视角；052 的显式转换规则不改。

现有约束图已经提供所需的成员 witness，编译期可以确定路径。但
`FengGenericParamDescriptor` 将实际 T 的 kind／descriptor 与当前约束 witness 放在同一
记录中；被调用者仍通过这一记录取 witness，不能只换一条局部 witness 变量后原样传记录。

`const FengGenericParamDescriptor *`，形成闭包时仅复制指针，不复制记录。因此，若仅在
转传点用栈上临时记录更换 witness，内层返回或存储的闭包将可能引用已失效记录。当前没有
实施该临时方案，不将此分析记作已复现的新产品缺陷；旧实现仍在 `CE0293` 阻断该路径。

验收必须包括类型／方法两域、多泛参槽序、成员声明初始化中的直接调用与 callable value
`inner<T>`、构造／实例／静态／fit、多层转传、引用／值／完整 spec 实际 T、同包／真实
跨包，以及内层返回闭包、成员保存后调用、正常／异常清理。若解决稳定描述符承载需要新增
字段或成本，先交人工决策，不通过偷换实际 T、栈上临时指针或新的 adapter 绕过。

### 051 根记录与独立编译的核对（2026-09-09）

续作前的实施审计：当前 HEAD 为 `e0b68b5f`；`src/`、`test/`、`fcts/` 以及这些路径的
提交历史均没有 `constraint_projection_descriptors`。运行时泛参描述符仍只有
kind／descriptor／witness 三字段。`812db8ae` 已完成的显式转换保持原样，不能与本项混计。
专属方案尚未实施，不存在需要先拆除的一套投影字段实现；续作须复用既有描述符缓存及
callable／`.ft` 通道。下述根入口待决事项未解决前，不先合入一套仅覆盖函数泛参的实现后
再改写类型泛参协议，也不把新增一个未消费的字段记作实现完成。

继续实施前核对既有入口：类型／fit 共享方法从 `_type_desc->reified_generic_params`
取得 owner 泛参；方法依赖另由其函数描述符携带。同一个 `Owner<T>` 的两个方法因此取得
同一条 owner T 记录，而方法的依赖集合可以不同。不能直接把每个方法依赖集合的第 0 槽
都写入同一个 T 记录。需用两个独立外部包分别增加 `fit Owner<T>`、引入不同目标交叉约束
的真实二进制程序核对，确认已有通道能否为每个入口选择正确的静态根图。

这不是已复现的新产品缺陷，也不是否定静态投影图；属于原方案尚未确定的根记录／槽位
契约核对。现有串槽产品缺陷仍为 057。未核对前不实施按交叉成员枚举、全局类型名字查询、
借用无关描述符字段或栈上拼装记录等替代方案。

核对结果：隔离工程 `local/g24-delivery/051-roots/` 先构建并打包 base，再由 ac／bc 两个
互不依赖的包仅消费 base `.fb`，最后 consumer 直接消费三个 `.fb`。三个 provider 和
consumer 均编译成功；运行正确结果断言退出 134。对应 057 的错误分派在真实跨包也存在。
两个 provider 的生成 C 均在各自共享 fit 方法中执行：

```c
const FengGenericParamDescriptor *_T = _td->reified_generic_params[0];
/* The current implementation forwards _T unchanged to its own inner call. */
```

consumer 的两个 wrapper 传入同一个
`FengTypeDesc__g24__roots__base__Owner__G__g24__roots__consumer__Value`，但各自的
`FengFunctionDescriptor` 不同。该 owner 描述符为 weak 全局符号，不能让同名描述符
因编译单元所见 fit 集合不同而带不同槽位协议，再依赖链接器选中某一份。

源码核心为（各段分别独立编译；完整探针保留在上述工程）：

```feng
// base 包；A.a()、B.b()、C.c() 均返回 i32。
open spec ABC: A & B & C;
open type Owner<T: ABC> { open var value: T; }

// ac 包只依赖 base，不知道 bc 包。
open spec AC: A & C;
open func inner_ac<T: AC>(value: T): i32 { return value.a() + value.c(); }
open fit Owner<T> {
    func read_ac(): i32 { return inner_ac<T>(self.value); }
}

// bc 包只依赖 base，不知道 ac 包。
open spec BC: B & C;
open func inner_bc<T: BC>(value: T): i32 { return value.b() + value.c(); }
open fit Owner<T> {
    func read_bc(): i32 { return inner_bc<T>(self.value); }
}
```

分析结论：目标记录仍可在具化点静态生成，递归依赖也可写入 `.ft`；缺少的是共享方法
消费该图时的**上下文根入口**。仅给共用的 owner T 记录加一个表指针，尚不能保证两个
独立编译的 fit 各自固定槽位解释正确。把方法依赖简单并入类型依赖，或按 consumer 看到
的 fit 全集排序，会破坏上述独立编译契约；这不是增加 `.ft` 依赖记录本身就能解决的。

需人工确认根入口的承载后继续产品实现。建议按依赖归属提供静态投影根入口：普通函数／
方法／fit 在函数描述符，字段／构造／静态初始化在类型或聚合描述符；下游仍为静态泛参
描述符图，不修改实际 T、不增加隐藏参数、堆分配、动态搜索或 adapter。此建议涉及额外
上下文描述符字段及固定根读取，超出已确认的单个泛参描述符字段，**尚未实施、尚未批准**。
另一条可研究路径是为每个共享方法生成 owner 描述符视图，但会增加整条 owner 元数据并
涉及其身份／初始化／静态状态复用，不将它作为未经批准的绕行实现。

COMPOSITE27 必须补两个外部 fit 同时消费的正式用例，以及提供包／消费包顺序变化、同一
闭合 owner 多方法、引用／值 owner；上面隔离探针不算正式用例完成或全量验收。

## ISSUE-G24-052：交叉类型值缺少向组成 spec 的显式投影

### 复现与人工决定

2026-09-09 在当前编译器上执行独立非泛型 lib 探针：

```feng
spec Left { func left(): i32; }
spec Right { func right(): i32; }
spec Both: Left & Right;

func project(value: Both): Right { return (Right)value; }
```

显式 cast 在 Semantic 报 `AE1023`；普通 `Both` 参数直接传给接收 `Right` 的函数报
`AE0512`。对照的 `Both.right()` 和 object-spec 子到父的显式／隐式转换编译通过。
人工要求补齐交叉值到成员 spec 的显式转换，隐式转换继续拒绝；规范定义已先更新到
[spec 主规范第 4 节](../../specifications/feng-spec.md#4-语义)。

### 原因与实现边界

现有 Semantic 的普通父视角路径只遍历 object-form parent；交叉约束满足检查虽能递归
证明成员关系，但不是值转换路径。Codegen 的交叉 witness 只有合并成员槽，没有组成
spec 的 witness 指针。两者均需补齐，不能只放宽 cast 检查。

复用 object-spec 的静态 witness 投影方式：交叉 witness 保留原合并槽，并按声明组成边
保存与当前 subject 承载相同的成员 witness；Semantic 在显式 cast 处记录精确实例路径，
Codegen 保留 subject 并读取选定路径。嵌套成员和成员父级使用相同机制；字段／方法／
静态成员、默认 subject、引用及装箱值均须保持当前 witness 语义。

确定的增量仅为静态 witness 指针空间及转换时的固定路径读取；交叉成员直接调用不增加
间接层，投影不新增堆分配、装箱或 adapter。保持 `.ft` 2.0，重建制品，不兼容旧制品。
不增加 `FengFunctionDescriptor`、`FengGenericParamDescriptor` 或其他上下文描述符字段，
不在本项处理 051 的开放泛参跨约束转传，也不扩大 implicit coercion 或重载规则。

### 实施与验收

- [x] Semantic 仅在显式入口证明并记录成员投影路径，负例保持编译期拒绝。
