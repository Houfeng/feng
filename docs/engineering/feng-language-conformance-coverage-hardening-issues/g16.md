## ISSUE-G16-001：值形式 `match` 没有隔离指向表达式外部循环的控制转移

### 归属

- 发现组：G16；
- 关联组：G08、G12、G17；
- 发现用例：FLOW01-A、FLOW01-B 与 FLOW02 的实施前规范和当前实现核对。

### 现象与结论

- 最小非法边界：

  ```feng
  func run() {
      while true {
          let value = match 1 {
              1 { break; 10 }
              else { 20 }
          };
      }
  }
  ```

- 对照合法边界：

  ```feng
  func run(): i32 {
      return match 1 {
          1 {
              while true {
                  break;
              }
              10
          }
          else { 20 }
      };
  }
  ```

- 实施前实际结果：值形式 `if` 会暂时隔离外层 `loop_depth`，结果 catch 也有对应隔离，因此直接指向
  表达式外部循环的 `break` / `continue` 已分别被 `AE1110`、`AE1405` 拒绝；值形式 `match` 没有建立
  同样的边界，第一段程序会沿用外层循环目标而被 Semantic 接受；
- 现有正向实现允许值形式 `if` 和结果 catch 的分支内部另行声明循环，并允许该内层循环控制自身；
  这与人工确认的规则一致，必须保留；
- 实施前主流程规范只定义最近循环规则，没有明确值表达式结果分支是否可以越过表达式边界寻找循环
  目标，导致三种值表达式的实际行为不一致。

### 决策与实施

- 状态：已关闭；
- 分类：规范缺失、产品缺陷；
- 人工决策：值形式 `if`、块形式 `match` 与带 `catch` 的 `try` 的每个结果分支均形成控制转移边界；
  `break` / `continue` 不得作用于表达式外部循环，但分支内部新建的 `while`、三段式 `for` 或
  `for/in` 仍可正常控制自身；相同结构作为语句使用时不形成该边界；
- 实施方案：在通用结果分支解析上下文中记录表达式控制转移边界，使 `match` 与 `if` 共享同一规则；
  结果 catch 继续使用异常段诊断。不得以扫描并禁止整个分支子树中的 `break` / `continue` 实现，
  以免错误拒绝内层循环；
- 稳定诊断：值形式 `if` / `match` 使用 `AE1110`，结果 catch 使用 `AE1405`，均定位实际
  `break` / `continue` token；
- 是否涉及既有测试修改：否；既有
  `test_break_inside_loop_inside_if_expr_block_is_accepted` 与
  `test_break_inside_loop_inside_try_expr_catch_block_is_accepted` 必须保持正向，只新增 match 对应正向及
  三种表达式的精确反向矩阵；
- 是否涉及运行时性能：否，只增加编译期上下文检查；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否。

### 验收与关闭

- [x] 三种值表达式均拒绝作用于表达式外部循环的 `break` / `continue`；
- [x] 三种值表达式的结果分支内层循环均可在 FCTS 中实际执行自身的 `break` / `continue`；
- [x] 语句形式分支仍可按最近循环规则控制包围该语句的循环；
- [x] Parser、Semantic、Codegen、FCTS 专项和沙箱外 `make test` 通过。

## ISSUE-G16-002：三段式 `for` 更新子句错误接受绑定声明

### 归属

- 发现组：G16；
- 关联组：G12、G13；
- 发现用例：FLOW05-A 实施前的循环语法、作用域与 lowering 核对。

### 现象与结论

- 最小复现：

  ```feng
  func run() {
      for var i = 0; i < 3; let next = i + 1 {
      }
  }
  ```

- 实施前实际结果：Parser 对初始化和更新子句复用普通 simple-statement 入口，因此更新子句中的
  `let` / `var` 会形成绑定 AST；Semantic 又在解析循环体之前解析更新子句，而 Codegen 把更新语句
  放在循环体之后的独立更新作用域中，三个阶段没有一套可由用户理解的更新绑定可见性模型；
- 实施前规范只定义初始化子句绑定的执行次数、作用域和共享身份，对更新子句只列举赋值、复合赋值和
  函数调用，没有定义更新子句声明绑定的身份与可见范围；
- C#、Go、Java 等具有三段式循环的语言均只允许初始化部分声明局部变量，更新 / post 部分不允许
  声明新绑定；Rust 与当前 Swift 没有三段式更新子句；
- 结论：当前接受行为不是已定义的 Feng 语言能力，应在 Parser 阶段拒绝，不为没有实际用途的更新
  绑定新增特殊作用域和 lowering。

### 决策与实施

- 状态：已关闭；
- 分类：规范缺失、Parser 产品缺陷；
- 人工决策：三段式 `for` 只有初始化子句可以使用 `let` / `var` 声明绑定；更新子句只能操作此前
  已经可见的绑定或执行函数调用，不得引入新绑定；
- 实施方案：更新子句解析到起始 `let` / `var` 时立即产生 `SE1203`，定位绑定关键字并返回空 AST；
  不影响初始化绑定、`for/in` 显式绑定、赋值、复合赋值和函数调用；
- 是否涉及既有测试修改：否，只新增 Parser 精确反向用例、合法 AST 邻界和 FCTS 运行证据；
- 是否涉及运行时性能：否，非法源码在 Parser 阶段停止；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否。

### 验收与关闭

- [x] 更新子句中的 `let` 与 `var` 分别产生唯一 `SE1203`，并精确核对 token、行列、阶段和空 AST；
- [x] 初始化绑定及三类合法更新形式保持原 AST 与运行行为；
- [x] Parser、Semantic、Codegen、FCTS 专项和沙箱外 `make test` 通过。

## ISSUE-G16-003：条件类型诊断仍使用旧码且不能精确定位 `else if` 条件

### 归属

- 发现组：G16；
- 关联组：G12、G14；
- 发现用例：FLOW03～FLOW03-B 实施前的 Semantic 诊断产生点审计。

### 现象与结论

- 实施前实际结果：值形式 `if` 的非 `bool` 条件产生旧 `AE0032`；语句形式 `if`、`while` 与三段式
  `for` 共用旧 `AE0054`。这些旧码没有进入当前 AE 分段规范；
- 语句形式 `if / else if` 校验每个 clause 时传入整个 `if` 语句的起始 token，因此后续
  `else if` 条件出错时可能错误定位到首个 `if`；值形式 `if`、`while` 和 `for` 也没有统一定位实际
  条件表达式；
- 结论：语言已经明确所有这些条件必须为 `bool`，缺口只在稳定诊断码和精确位置，不需要改变合法
  条件语义。

### 决策与实施

- 状态：已关闭；
- 分类：诊断契约缺失、产品缺陷；
- 实施方案：值 / 语句形式 `if` 统一使用分支段 `AE1102`；`while` / 三段式 `for` 统一使用循环段
  `AE1202`；所有产生点定位实际条件表达式起始 token，只迁移这四类 G16 产生点；
- 是否涉及既有测试修改：否，既有测试未锁定这些旧码；新增 G16 精确矩阵，不改写旧用例；
- 是否涉及运行时性能：否，只变更编译期诊断；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否。

### 验收与关闭

- [x] `if` 首条件、语句 / 值形式 `else if`、`while` 与三段式 `for` 分别锁定新码和实际条件 token；
- [x] 合法 `bool` 条件及省略的三段式 `for` 条件进入 FCTS 直接运行；
- [x] G16 范围内不再产生旧 `AE0032` / `AE0054`；
- [x] Semantic、FCTS 专项和沙箱外 `make test` 通过。

## ISSUE-G16-004：三段式 `for` 的函数调用更新误吞循环体

### 归属

- 发现组：G16；
- 关联组：G12；
- 发现用例：FLOW05-A 的合法函数调用更新 Parser AST 邻界。

### 现象与结论

- 最小复现：

  ```feng
  func advance() {}

  func run() {
      for var index = 0; index < 0; advance() {}
  }
  ```

- 实施中实际结果：Parser 没有在更新子句的表达式解析期间关闭对象字面量后缀识别，因而把本应作为
  循环体的 `{}` 吞入 `advance()` 表达式；随后 `parse_block` 到达函数结束 `}`，错误产生 `SE0005`；
- 初始化 / 条件和 `for/in` 头表达式已有“控制流头后的 `{` 必须留给循环体”的解析上下文，更新子句
  尚未复用该规则；
- 结论：函数调用是规范明确允许的更新形态，当前拒绝行为属于 Parser 产品缺陷，不涉及新增语义。

### 决策与实施

- 状态：已关闭；
- 分类：Parser 产品缺陷；
- 实施方案：复用控制流头表达式现有的对象字面量后缀抑制机制，只在解析三段式 `for` 更新子句时
  保留紧随的 `{` 给循环体；不得影响普通表达式语句或带括号 / 字段的合法更新调用；
- 是否涉及既有测试修改：否，仅保留本次新增的 Parser AST 与 FCTS 运行用例；
- 是否涉及运行时性能：否，只影响 Parser；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否。

### 验收与关闭

- [x] `advance()` 更新保留为 `FENG_STMT_EXPR(FENG_EXPR_CALL)`，后续 `{}` 保留为循环体；
- [x] 赋值、复合赋值、空更新和对象字面量相关既有 Parser 用例继续通过；
- [x] Parser、FCTS 专项和沙箱外 `make test` 通过。

## ISSUE-G16-005：值形式 `else if` 非 bool 条件产生级联分支类型诊断

### 归属

- 发现组：G16；
- 关联组：G11；
- 发现用例：FLOW03 的值形式 `else if` 条件精确诊断。

### 现象与结论

- 最小复现：

  ```feng
  let value = if true { 1 } else if 2 { 2 } else { 3 };
  ```

- 实施中实际结果：内层 `else if` 已在实际条件 `2` 产生正确的 `AE1102`，但条件校验追加错误后仍把
  该 if 表达式当作可继续推导；外层 `if` 随后又产生一次分支类型错误，单一根因最终得到两个诊断；
- 结论：条件类型不合法时，该 if 表达式没有可供父表达式继续比较的有效结果类型；继续执行父层分支
  贴合属于级联诊断，应在当前表达式边界终止。

### 决策与实施

- 状态：已关闭；
- 分类：Semantic 产品缺陷；
- 实施方案：保留已经追加的 `AE1102`，并令当前 if 表达式解析失败，不再把无效条件表达式交给外层
  分支结果推导；不屏蔽其他相互独立语句的诊断；
- 是否涉及既有测试修改：否，仅新增值形式首条件与 `else if` 的唯一诊断断言；
- 是否涉及运行时性能：否，只影响编译期错误路径；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否。

### 验收与关闭

- [x] 直接 if 表达式和嵌套的值形式 `else if` 均只产生一个 `AE1102`；
- [x] 诊断精确定位实际非 bool 条件；
- [x] Semantic 专项和沙箱外 `make test` 通过。

## ISSUE-G16-006：表达式分支局部结果在 Codegen 类型探测阶段不可见

### 归属

- 发现组：G16；
- 关联组：G11、G13；
- 发现用例：FLOW01-B / FLOW06-A 的表达式结果分支内层循环 FCTS。

### 现象与结论

- 最小复现：

  ```feng
  let value = if true {
      var count = 0;
      while count < 2 {
          count += 1;
          break;
      }
      count
  } else {
      0
  };
  ```

- 实施中实际结果：Semantic 正确接受；Codegen 在真正发出分支前，仅把末尾 `count` 表达式放入临时
  scope 探测结果类型，没有先建立同一分支中的 `count` 绑定，因此产生 `CE0104`；
- 该失败发生在生成 C 代码之前的编译器内部探测阶段，不是 Feng 语言语义错误；
- `match` / `try` 表达式也使用结果槽与分支探测，需要一并核对，避免只为 `if` 增加特判。

### 决策与实施

- 状态：已关闭；
- 分类：Codegen 产品缺陷；
- 实施方案：优先复用 Semantic 已记录的表达式类型事实；共享分支结果槽在 Codegen 中优先使用该
  已选类型，仅在没有该事实时回退到既有 yield / 结果探测路径；
  不得为探测执行两次运行时代码，不得改变分支求值次数或 ARC；
- 是否涉及既有测试修改：否，新增 Codegen / FCTS 正向用例；
- 是否涉及运行时性能：否；只改变编译期结果类型选择，不重复发出用户语句，也不新增生成程序的
  运行时分支、调用、分配或 ARC；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否。

### 验收与关闭

- [x] `if`、`match`、`try` 分支均可在前置局部声明 / 内层循环后返回该局部值；
- [x] 类型探测不重复发出或执行用户语句，生成代码不新增运行时分支、调用、分配或 ARC；
- [x] Codegen、FCTS 专项和沙箱外 `make test` 通过。

## ISSUE-G16-007：新增合法声明改变收集顺序后跨包泛型构造身份匹配失败

### 归属

- 发现组：G16；
- 关联组：泛型 Codegen、值方法 callable；
- 发现用例：沙箱外全量 `make test` 的 UBSan FCTS 阶段，既有
  `test_value_method_capture.ff` 第 485 行。

### 现象与结论

- 第一次普通构建的 G16 Parser、Semantic、Codegen 专项及增量 `make fcts-tests` 已通过；从干净构建
  开始的沙箱外 `make test` 在 UBSan FCTS 阶段产生：

  ```text
  CE0169: codegen: resolved constructor for type
  'LibValueMethodOwner<string>' was not registered
  ```

- 清理产物后，普通构建也稳定复现同一错误，因此不是 UBSan 特有问题；第一次增量 FCTS 通过是旧
  package 产物未失效，不能作为干净验收结果；
- 使用当前编译器运行未加入 G16 文件的 `HEAD` 基线 FCTS，1109/1109 通过；只把 G16 文件中的
  合法辅助函数逐项加入基线源码，最小触发收敛为：

  ```feng
  func g16_fail(): int {
      throw "g16";
  }
  ```

  该函数本身不会执行到正常落尾，也不引用失败位置的泛型类型；它仅改变后续泛型实例的收集顺序。
- 进一步检查失败实例时，`LibValueMethodOwner<string>` 的声明仍有 5 个成员，但已注册 `UserType`
  的字段、构造、方法计数全部为 0；因此问题发生在成员注册结果丢失，排除了最初的 FT 成员指针
  身份假设；
- 精确插桩确认：注册 `LibValueMethodOwner<string>.readBoth<U>` 的返回类型
  `LibValueMethodPair<string, U>` 时，泛型 `UserType` 数组发生扩容。正在注册的
  `LibValueMethodOwner<string>` 指针随之失效，后续成员计数写入旧地址，最终在既有构造调用处误报
  `CE0169`；
- 扩容的直接原因是泛型成员预收集与成员签名解析使用的上下文不完整对齐：预收集只覆盖实例化点的
  开放参数上下文，而实际成员签名还会使用“类型 owner 参数在前、方法参数在后”的描述符上下文；
  后一种实例此前直到成员注册阶段才被补注册；
- 结论：新增 G16 正向覆盖改变了编译期收集顺序，并在当前变更集中造成真实回归；它暴露的是既有
  泛型预收集缺口，不是旧用例或用户源码错误，也不需要改变 Feng 语义。

### 决策与实施

- 状态：已关闭；
- 分类：Codegen 产品缺陷；
- 实施方案：在成员注册前继续按实例化点的开放参数上下文收集 callable 成员所需泛型实例；当 owner
  已完全闭合时，再按“owner 参数在前、方法参数在后”的成员描述符上下文补全预收集，公共注册入口
  负责去重。开放 owner 继续保留继承而来的实例化上下文，避免把仍开放的参数误作已闭合 owner 参数。
  这样成员注册阶段不再补建该实例，也不会因数组扩容使正在注册的类型指针失效；不得通过扩大数组
  固定容量、忽略 `CE0169` 或修改既有用例规避；
- 是否涉及既有测试修改：否，保留新增 G16 FCTS 文件作为顺序变化回归证据；
- 是否涉及运行时性能：否，只补全编译期预收集，不改变生成 C 的运行时分支、调用、分配或 ARC；
- 是否涉及 runtime 私有 ABI、公开 ABI 或 `.ft` 格式：否。

### 验收与关闭

- [x] 明确失败由 G16 新增合法声明改变收集顺序后触发，并记录基线、最小复现和扩容点证据；
- [x] 修复后重新通过专项和沙箱外 `make test`；
- [x] 既有 `test_value_method_capture.ff` 保持原样，未通过删改旧用例规避回归。

## ISSUE-G16-008：控制转移精确诊断矩阵缺少对称组合

### 归属

- 发现组：G16；
- 关联组：G08；
- 发现用例：FLOW01 / FLOW02 交付映射的逐项收尾核对。

### 现象与结论

- G16 新增矩阵已经覆盖无循环嵌套普通 block、Lambda callable 边界、值形式 `if`、值形式 `match`
  普通分支与 `else` 分支以及结果 catch，但逐项对照 TODO 后仍缺四个精确组合：函数体直接位置的
  `break` / `continue`、值形式 `match` 的 `else` 分支 `break`、普通分支 `continue`；
