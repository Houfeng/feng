## ISSUE-G22-001：别名与非本文件声明的名称冲突仍被急切拒绝

- 状态：已关闭；实现、专项及最终全量回归通过。
- 分类：产品缺陷。

### 归属

- 发现组：G22。
- 关联组：G02 的名称访问形式与文件隔离、G13 的同模块声明检查。
- 发现用例：现有 `test_import_alias_conflicts_with_other_file_local_value`、
  `test_import_alias_conflicts_with_imported_short_name`；计划覆盖 MODULE08～MODULE11、MODULE27。

### 现象与结论

修复前 `src/semantic/analyzer.c` 的 `validate_program_alias_conflicts` 在 import 声明检查阶段
查找同名可见类型和值；遇到兄弟文件声明或普通 import 引入的名称，直接报告 `AE0906`，不依赖
实际引用。调用点位于 `resolve_program_names` 之前。

第一类：同模块其他文件声明与 alias 同名。

```feng
// provider.ff
open module lib.tools;
open func run(): i32 { return 1; }

// a.ff
module app;
import lib.tools as helper;
func call(): i32 { return helper.run(); }

// b.ff
module app;
let helper = 2;
```

第二类：普通 import 引入名称与 alias 同名。

```feng
// values.ff
open module lib.values;
open let helper = 2;

// consumer.ff（同时使用上例 provider.ff）
module consumer;
import lib.values;
import lib.tools as helper;
func call(): i32 { return helper.run(); }
```

- 修复前结果：两类场景都在 alias import 声明处报 `AE0906`；删除 `call` 中的引用仍会报错。
  初次记录依据源码检查和既有断言；后续补齐源码、真实 `.ft` 及 FCTS 矩阵验证修复。
- 规范依据与预期：[模块规范 §4](../../specifications/feng-module.md#4-模块导入规则)。存在碰撞但
  未引用时通过；引用时在 `helper` token 处报告二义性并指出来源，不依据 `.run` 是否存在选边。
- 根因：前置检查未区分“本文件声明产生的急切冲突”和“两类外来声明参与的惰性冲突”；只删除
  前置分支还不够，类型、表达式及赋值目标的使用点必须接入相同的来源判定。

### 决策与实施

- 人工决策：两类冲突均改为使用点惰性报错；本文件顶层声明或其他 alias 与 alias 同名仍急切
  报错。同模块真正的顶层非法重名仍急切检查，合法函数重载除外。
- 边界：“局部值优先于模块路径”按已有定义保持，不扩展成所有具体符号优先；普通 import 与
  本文件或同模块其他文件顶层声明之间的惰性冲突保持现状，不新增顶层本地优先规则。
- 建议方案：统一收集当前使用位置可见的名称来源，在使用点区分明确目标与二义性；覆盖类型位、
  函数值、构造、读写和普通调用，不按模块名、类型名或后续成员存在性添加特判。具体结构在实施时
  依据现有通用解析代码确定。
- 既有测试修改：仅上述两条的声明点 `AE0906` 调整为使用点 `AE0005`，以及必要的来源、token、
  行列与数量断言；完整迁移清单在所属实施文档 §26.3.2。清单外如需修改须再次人工决策。
- 运行时性能：方案只调整编译期查找，不增加运行时名称解析、权限检查或 ARC 操作。
- runtime 私有 ABI、公开 ABI 或 `.ft` 格式：无预期变更；跨包只使用现有公开导出与导入机制。
- 当前交付范围：人工已批准实施 G22、迁移明列的两条既有测试并独立运行全量回归；实现已完成。

### 验收与关闭

- 已补验证：六类声明的未使用／使用配对、各限定访问入口、成员存在性不能消歧、顺序无关、
  文件隔离、显式消歧、真实 `.ft` 往返，以及本文件急切检查不回归。
- 本组专项复验结果：Semantic、真实 `.ft` Symbol 矩阵通过；两类未使用碰撞的 FCTS 运行正例通过。
- 本组沙箱外 `make test` 结果：最终版本退出码 0，详见本文件末节统一验收记录。
- 关闭依据：源码／真实 `.ft` 诊断矩阵、FCTS 运行配对及最终全量回归均通过。

## ISSUE-G22-003：短名二义性候选包含仅经 alias 导入的模块

- 状态：已关闭；专项及最终全量回归通过；分类：产品缺陷；发现组：G22，关联 MODULE12、MODULE18。
- 现象：`collect_symbol_candidates` 遍历 `imported_modules` 的全部公开声明；该列表也包含 alias
  import（它还服务于契约可见性），因此仅写 `import provider as api` 也会使 provider 的同名声明
  参与本文件短名二义性判定，与 alias 不注入短名的规范不符。最初由源码审计确认，后由新增源码及跨包用例复验。
- 最小场景：A、B 均公开 `type Item`，consumer 写 `import A; import B as api;`，裸名 `Item`
  应只来自 A；`api.Item` 来自 B。两者均应通过，不能仅因 B 在可见模块列表中而报二义性。
- 处理：候选收集按当前文件的无别名 import 筛选模块；保留 alias 对契约可见性的既有作用。
  两类导入都存在时，目标模块仍贡献短名候选。通过通用来源判定修复，不按名称特判。
- 测试：新增源码和真实 `.ft` 正例及增加第二个无别名 import 后的反例；不修改额外既有用例。
- 性能／ABI：仅编译期筛选，无运行时或 ABI 变更。
- 验收：源码、真实 `.ft` 与 FCTS 短名隔离正例及最终全量回归通过。

## ISSUE-G22-004：新增真实 .ft 专项运行中进程异常退出

- 状态：已关闭；专项及最终全量回归通过；分类：产品缺陷。
- 发现组：G22，`test_g22_real_ft_module_diagnostics`。
- 现象：新增专项编译成功，运行 `build/bin/test_symbol` 退出码 139，尚无正常诊断输出。
- 后续：先获取调用栈并缩小到具体 consumer，确认是否由新夹具或产品实现导致，再按规范修复；
  不据此预判根因，也不调整既有断言绕过错误。
- 定位结论：产品缺陷。加载超过初始容量的模块后，`cache_append` realloc 移动内联
  `SynthModuleEntry`，先前 `sem_mod.programs` 仍指向旧条目内的 `prog_ptr`，形成悬空指针。
  回溯定位到 analyzer 导入签名扫描读取空 `ext_prog`；不是某类声明的语义问题。
- 修复方案：私有导入缓存改为稳定地址的模块条目、可增长的条目指针数组；保证已返回模块及其
  programs 数组在缓存生命周期内稳定。仅编译器内存管理，不修改 `.ft` 或 runtime ABI。
- 验证：新增真实 `.ft` 矩阵加载多个模块跨过初始缓存容量，并断言首次返回的模块地址、programs
  数组和声明仍有效；`test_symbol` 通过。

## ISSUE-G22-005：跨文件 alias 构造后的成员访问触发 CE0104

- 状态：已关闭；专项及最终全量回归通过；发现组：G22，MODULE18 FCTS 正例。
- 现象：`g22_alias_reuse.ff` 的 `api.G22Record().value` 已通过 Semantic，但 Codegen 报
  `CE0104: identifier 'api' not found`。另一文件也声明 api，但指向不同公开模块。
- 预期：按本文件 alias 解析构造目标并读取实例字段，不能在发码时把模块别名当成运行时标识符。
- 后续：检查是否为别名文件上下文或构造结果类型信息缺失；保留该运行正例，修复通用解析／发码
  链路。若涉及新的运行时开销或未确定语义，再由人工决策。
- 定位结论：普通 `cg_emit_call` 在处理 Semantic 已确认的构造函数前，先把所有 member 形状
  callee 当成方法接收者求值；`alias.Type()` 因此错误求值 alias。与本轮别名拼写或某个类型无关。
- 修复方案：先按 resolved callable 的构造类别分派，抽出原有构造发码供所有名称形式共用，按
  resolved owner 声明身份找类型。不改对象分配、字段初始化、构造调用或 ARC 操作序列。
- 验证：普通 alias／完整路径构造、对象字面量及成员访问 FCTS 通过；Codegen 单元全集通过。

## ISSUE-G22-008：把模块 alias 作为实参时产生调用匹配级联诊断

- 状态：已关闭；专项及最终全量回归通过；分类：产品缺陷；发现 MODULE19 新增反例。
- 现象：`import g22.api as api; func take(value: i32) {} func check() { take(api); }`
  在 `api` 报 AE0904 后，又在 `take` 报 AE0512；实参并不是合法运行时值，后者没有独立意义。
- 分析：调用入口对 callee 新增错误已有停止匹配处理，但实参解析报错后仍进入重载匹配。
- 修复方案：实参解析结束并恢复外层目标上下文后，若该轮新增诊断则停止后续调用匹配；不按
  alias 名字或错误码特判，不影响合法实参的目标类型处理。新增反例要求唯一 AE0904 和准确位置。
- 性能／ABI：仅编译失败路径；无运行时、ABI 或 `.ft` 格式变更。
- 夹具校正：复跑时发现新写的 MODULE13 顺序夹具把 import 放在顶层声明之后，导致 Parser 拒绝。
  这是新用例构造错误，按已有 import 位置规则修正；单 import 场景只交换文件输入顺序，不改语言。

## ISSUE-G22-009：alias 限定静态方法值在 Codegen 丢失 owner 身份

- 状态：已关闭；专项及最终全量回归通过；分类：产品缺陷；发现 MODULE24 FCTS 正例。
- 现象：`let direct: api.G22Unary = api.G22Overloaded.choose;` 已由 Semantic 选中公开静态
  重载，但 Codegen 报 `CE0032: unknown type 'G22Overloaded'`。普通调用和实例方法值不触发该错误。
- 分析方向：静态方法值发码仍按 owner 的短名查找；alias import 不注入短名，必须沿用已解析
  声明身份，而不是把 alias 来源重新加入短名空间。保留完整路径、alias 与短名的统一身份规则。
- 处理边界：只修复编译期方法值目标定位，不改 callable 表示、捕获、权限或运行时操作。
- 定位结论：Semantic 记录 callable 贴合站点时，为声明型 receiver 合成了只有短名的 type ref，
  丢失其 provider module；Codegen 在 consumer 上下文中无法重建该身份。
- 修复方案：在合成 receiver 元数据时记录已解析 owner 的规范模块路径及类型名，泛型实参保持
  原规则；同一声明的三种源码写法由此共享相同 owner 身份，不新增名称优先级或运行时处理。
- 验证：Semantic、Symbol、Codegen 全套专项通过；包含实例／静态方法值及直接调用的新 FCTS
  在当次完整运行中通过（1171/1171）。此结果不包含后续为 MODULE13／MODULE16 补充的运行矩阵。

## ISSUE-G22-010：同名导入下完整路径读取本模块绑定生成错误 C 标识符

- 状态：已关闭；已按批准范围修复，联合专项及最终全量回归通过。
  产品缺陷；发现 MODULE13／MODULE16 FCTS 完整运行矩阵。
- 现象：本模块公开 `g22ImportedVar` 与两个普通 import 的公开同名 var 未被裸名引用，
  Semantic 通过，但 `fcts_bin.g22_collisions.g22ImportedVar` 的生成 C 引用了未声明的

  变更引入。涉及模块级绑定实现的修改先说明原因并取得人工批准，再实施。

### 根因与修复建议

- 根因位于本轮未改动的发码分支：`cg_register_module_binding` 对 bin 目标使用本地存储名称
  `_feng_g__...` 和 `_feng_ensure_g__...`。但 `cg_resolve_imported_module_binding_decl` 的
  member 分支未区分本地模块与导入包，随后 `cg_emit_imported_binding_expr` 直接使用包公开
  `feng__...` 名称。完整路径正确选中了声明，错误发生在发码存储名称选择；同名导入不是必要条件。
- 原 C 中实际声明了 `_feng_g__fcts_bin__g22_collisions__g22ImportedVar`，使用处却引用
  `feng__fcts_bin__g22_collisions__g22ImportedVar` 及不存在的公开 ensure 函数。
- 建议通用方案：限定访问按已解析绑定声明身份取得存储信息；本次编译中已注册的绑定复用其
  实际 slot／ensure 名称，真正导入包的绑定才使用公开接口名称。读取、写入、复合赋值、取址和
  callable 绑定调用采用一致判定，新增本包 bin／跨包 lib 正反向及共享状态证据。
- 不修改绑定的初始化时机、初始化次数、可变性或 ARC 规则，不改已有存储和 ensure 的注册命名，
  不增加运行时判断、存储槽或函数调用；不修改 runtime ABI、公开 ABI 或 `.ft` 格式。
- 人工决策：已批准按声明身份修正绑定访问的 Codegen 符号选择。限定修改读取与赋值共同使用的
  slot／ensure 选择逻辑，取址和 callable 绑定调用复用读取结果；存储注册和初始化函数体不改。
  无额外既有用例迁移，实施后新增本包 bin、跨包 lib 访问及共享存储断言并执行全量回归。

## ISSUE-G22-011：限定访问的 callable 绑定在调用语义检查中丢失类型来源

- 状态：已关闭；额外的模块级绑定类型解析修复已人工批准并完成，专项及最终全量回归通过。
  分类：产品缺陷；发现 ISSUE-G22-010 补充的 callable 绑定调用用例。
- 现象：provider 声明公开 `spec Reader(): i32` 与 `let callback: Reader = read`，consumer
  仅以 alias 导入 provider，调用 `g22.storage.callback()` 时 Semantic 报 AE0507（不可调用），
  放在加法中时另有派生 AE1019。绑定按声明类型应当可调用，Codegen 尚未执行。
- 根因：`infer_global_binding_decl_type` 返回 provider 声明中的原始 `Reader` type ref；
  `validate_callable_typed_expr_call` 经 `resolve_inferred_expr_type_decl` 在 consumer 的可见类型
  环境中重新查找该短名。alias 不注入短名，因此找不到 callable 声明，误报 AE0507。
  此链路在本轮前已存在，不是 ISSUE-G22-010 的 slot 名称选择修复产生的运行时问题。
- Codegen 侧的 `cg_resolve_global_binding_type` 也直接在当前上下文解析绑定的原始 type ref，
  实施时需一并核对声明文件上下文，不能只消除前端错误后留下后端重新查错类型的问题。
- 建议通用方案：绑定的类型引用在其声明文件的名称环境中解析，跨文件访问保留并复用该类型
  身份；具名类型及其嵌套实参均遵守同一来源规则。不向 consumer 注入 provider 短名、不新增
  名称优先级，也不按 callable 名称或某个模块特判。具体复用／元数据结构在获批后实施核验。
- 额外授权范围：模块级绑定的编译期类型来源传递及对应 Codegen 类型取得；这不同于 ISSUE-G22-010
  已批准的存储符号选择；现已取得额外人工批准。
- 实施结构：在分析持有的绑定类型副本中保存声明文件上下文，递归保留嵌套类型的既有来源。
  类型复制和泛型替换保留该编译期信息，Semantic 按来源文件解析具名类型；Codegen 按相同
  来源取得类型并恢复调用方上下文。原始源码类型检查和名称可见性规则不变。
- 修复边界：不改声明类型、初始化时机／次数、可变性、ARC、运行时 callable 表示或调用层，
  不改 runtime ABI、公开 ABI 或 `.ft` 格式；未新增运行时操作。
- 验证计划：保留当前失败用例；补充文件输入顺序交换、声明类型来自本模块／普通 import／alias、
  consumer 存在同名无关类型、泛型类型实参与真实 `.ft` 访问，并配对不可调用值／错误参数反例。
  不额外迁移既有断言，完成后重新执行专项和沙箱外 `make test`。
- 补测时发现：显式 callable 绑定的联合 Codegen 用例和当时 FCTS 1176/1176 通过后，新增泛型推导绑定
  运行正例 `localState.inferred(13) == 13` 在 Semantic 报 AE1019，调用结果类型尚未取得。
  先保留该失败证据，核对推导事实的准备时机及来源传递；不能以只有目标类型的接受断言替代此运行正例。
- 定位补充：交换文件输入顺序即可稳定复现。完整名称检查逐文件准备推导绑定事实，consumer
  先于 provider 时尚无事实，导致后续运算读取未知类型。处理为在完整表达式验证前，以现有文件
  名称环境迭代准备模块绑定的可推导类型事实；随后仍完整验证每个声明和初始化器，不执行初始化器，
  不放宽非法代码检查。迭代只传播新增类型事实，受模块绑定数量限制。
- 具名返回类型补测还要求 callable 的成员签名使用所选声明的文件上下文；泛型实际参数仍各自
  保留实例使用点上下文。两者在现有成员类型替换入口统一传递，避免把参数重定向到成员声明文件。
- 专项结果：源码的声明来源／访问形式／输入顺序矩阵、真实 `.ft` 的三种绑定访问形式、Codegen
  联合用例及 FCTS 1178/1178 通过；包含无目标类型辅助的 `inferred(7) == 7` 与具名返回类型
  字段访问，不仅测试有显式目标类型时能否接受。全过程未迁移额外既有断言。
