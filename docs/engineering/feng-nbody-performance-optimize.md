## 最新实测：C 属性之后仍慢在哪里

在同一 Linux arm64 容器、Clang 22.1.8 O2、默认向量化、无 LTO 条件下，
`const`／`pure`／`nothrow` 已在 IR 生效，但属性版仍比 Swift 慢。进一步控制
实验确认：**数组辅助函数的成功路径和 Math.sqrt 转调逻辑对调用方不可见，
导致外部调用、跨调用栈保存和多余整值写回共同形成主要差距。**

对照只改生成 C 的 `advance` 副本。数组辅助函数直接采用现有 runtime 函数体，
保留空值、容量、长度及越界失败分支；Math 的可见版本保持现有“转调 libm sqrt”
逻辑。没有手动移除边界检查，没有改数组分配器、布局或计算算法。

2000 万步，每组预热 2 次、交替测量 7 次，表内为 wall 中位数。各 Feng 样本
通过等长启动路径控制，payload 页内偏移均为 912（4 KiB 页），五个 Body 不跨页。
首轮路径长度不同导致的 896／912 偏移差异已单独保留，不混入此表。

| 从属性版出发的干预 | 秒 |
| --- | ---: |
| 仅已有 C 属性 | 1.736268 |
| 仅地址查询函数体可见 | 1.582361 |
| 仅下标检查函数体可见 | 1.581435 |
| 仅直接硬件 sqrt | 1.656158 |
| 两类数组函数体可见，保留 std sqrt 调用 | 1.337491 |
| 两类数组函数体可见，改为外部 fsqrt/ret 包装调用 | 1.238872 |
| 两类数组函数体与原 Math.sqrt 转调逻辑均可见 | **0.649730** |
| 同批 Swift 6.2.4，-O | 0.864086 |
| 同批 C++，O2 | 0.642804 |

**严格仅数组两项的独立补测：** 上表从手动添加 C 属性的版本出发，不能将
1.337491 秒当作不依赖这些属性的收益。另以原始生成 C 为基线，移除前轮手动
属性，只暴露数组 data/check 的原实现，并保持 Math.sqrt 原声明与调用，同位置
七轮补测由 1.933861 秒降至 **1.662529 秒，减少约 14.0%**；同批 Swift 为
0.870894 秒，C++ 为 0.644258 秒。数组两项叠加前轮实验属性为 1.345798 秒。
15 项小输入检查与 45 次完整输入执行全部通过，Feng 输出逐字相同。该阶段可以
独立改善数组访问，但尚不足以达到 Swift。原始记录见
[仅数组两项补测](../../temp/apple-container-verify-20260929/c-attributes-nbody/gap-analysis/array-only/RESULTS.md)。

每对天体的热点汇编核对如下；指令数不包含被调用函数内部，栈读写按指令计。

| 版本 | 指令 | 外部调用 | 栈读写 | Body 写回字节 |
| --- | ---: | ---: | ---: | ---: |
| Feng 属性版 | 83 | 9 | 17 | 112 |
| Feng 两类数组函数体可见 | 49 | 1 | 6 | 48 |
| Feng 三项实现均可见 | 41 | 0 | 0 | 48 |
| Swift | 44 | 0 | 0 | 72 |
| C++ | 32 | 0 | 0 | 48 |

这里有两个明确的优化阻碍：

1. `pure` 未说明 data 只读数组头及其返回地址关系；`nothrow` 也未说明 check
   成功返回时不修改内存。check 的外部声明仍是未知内存行为，属性版因此保留
   每对四次 check、四次 data，并写回两份完整 Body。原实现可见后，O2 合并
   检查、消除这些调用，并只写回两个 Body 的六个速度字段。
2. 此容器 std 的 sqrt 包装已经执行硬件 `fsqrt`，并保留 NaN 检查和 libm
   回退。即使替换为仅含 `fsqrt; ret` 的外部包装，调用方仍有每对 56 字节
   栈保存及 56 字节恢复；它与原 std 调用组的循环指令只差 `bl` 目标。
   暴露原转调逻辑后，O2 自动生成 `llvm.sqrt.f64`／循环内 `fsqrt`，栈读写
   消失，热点指令与显式 builtin 诊断逐条相同。内存属性本身不能消除这种
   C ABI 调用边界。

组合诊断相对属性版耗时减少 62.58%，相对同批 Swift 减少 24.81%，接近 C++。
这证明本例在默认 O2 下有优化空间，且仅补这几类属性还不够。单项收益不能
相加；不能把全部差值归因于 sqrt 运算、某一条调用指令或某个 CPU 内部机制。

受控批次 36 项小输入检查及 108 次完整输入执行全部通过；Feng 各组正式输出
逐字相同。本轮仅确立该容器位置下的因果关系，未解决历史 macOS 的布局慢档，
也未将诊断中复制私有 runtime 实现的方式批准为正式发码方案。后续应设计通用
的小函数实现可见性机制，并完成语义回归及 macOS 验收；不按数组、Body 或 sqrt
名称加入特判。

完整三因素表、逐样本数组地址、CPU／wall、IR 与热点汇编见
[本轮归因报告](../../temp/apple-container-verify-20260929/c-attributes-nbody/gap-analysis/RESULTS.md)。

## 结论与范围

本例应优先解决核心编译器／构建链路中的跨调用优化信息，以及目标机器访存选择。
`Body` 是仅含七个 `f64` 的值对象；主要热循环没有逐步分配、retain/release 或
清理登记，因此继续套用 binary-trees 的聚合生命周期优化不能解决这里的主要差距。
本例普通数组始终满足 `length == capacity == 5`，没有 storage 插入、删除或迁移。
两种长度及迁移的含义引用[数组容器存储主规范](feng-array-storage-dev.md#42-核心不变量)；
不能把容器有效元素数可变，解释成本例数组会原地扩缩容量或移动存储地址。

本次确认了三类不同现象：

1. **高频操作及跨调用优化阻碍。** 每步 50 次数组访问产生 100 次 runtime 辅助调用，
   另有 10 次 `Math.sqrt` 调用。宿主编译器不能充分看到这些调用的效果，热循环
   保留寄存器溢出到栈、重新加载和整值写回。诊断组合能显著减少这些工作。
2. **与数组页内位置有关的执行波动。** 同一诊断二进制、同一输入，仅改变
   payload 的页内位置即可重复出现明显不同的 CPU 耗时。原程序约 1.8～3.8 秒的
   分布不能只用单次中位数概括，也不能仅归因于此前 ARC 优化。回撤后的等长
   机器代码对照进一步确认了原路径配对循环及位置更新的宽访存成本。
3. **本机安全软件的启动干扰。** 用户确认新程序需在 7 秒内授权，否则会被阻止。
   补测直接记录了首次启动 wall 数秒、CPU 数毫秒的情况；授权后启动等待显著缩短。
   这与第二项的持续 CPU 开销必须分开统计。

默认后端的 C/C++ 补测进一步区分了前两项：正式 C++ 的同一计算核接入相同的
Feng 分配位置后，也从约 0.66 秒退化到约 1.7 秒。布局慢档不是 Feng 独有；而在
三个没有该慢档的位置，信息可见的 Feng 副本仍比同布局 C++ 多约 0.13 秒。
具体方法、数字及边界见下文“默认后端下的 C/C++ 对照”。

公共测量口径引用[跨语言评测主规范](../../benchmarks/README.md)，工作负载引用
[nbody 用例](../../benchmarks/cases/nbody/README.md)。本次未修改正式用例、编译器、
标准库、runtime ABI、已有测试或系统安全设置。所有生成 C 的改写仅为临时归因实验，
不能代替通用实现，也不能替换正式五语言黑盒排名。

语言行为以[内建数组规范](../specifications/feng-builtin-type.md#5-数组)、
[表达式规范](../specifications/feng-expression.md)、
[C 互操作规范](../specifications/feng-interop.md)及
[Math 规范](../specifications/feng-std-math.md)为准；本文不另行定义语言语义。

## 证据强度与方案充分性复核

源码、生成 C、汇编及同制品核验能够直接支持热循环的调用数量、无逐步 ARC／
分配，以及此前生命周期优化没有改变本例二进制。回撤后的三因素组合测量证明：
数组地址查询、索引检查与 sqrt 的信息共同影响后端优化，组合收益明显大于单项。
实验没有把调用本身、栈保存／重载和写回逐条计费，不能按调用次数分摊或叠加收益。

页内位置控制已重复复现 CPU 耗时差异。`--keep-ir` 分析把优化副本的两个慢位置
对应到速度字段的 16 字节跨页读写；后续只替换这类访存、保留其余机器指令及地址
的实验消除了这两个慢档。回撤后又对原程序两段热循环分别干预，拆分全部 payload
宽访存后，五个位置收敛到约 1.63 秒。宽访存的成本不只发生在跨页位置，具体 CPU
内部惩罚机制仍未确定。安全授权的启动等待另行记录，不能将其与持续 CPU 耗时混合。

此前达标诊断组合为三项信息可见，加上关闭 SLP 及 AArch64 load/store 优化 pass 的后端
选项。多个受控批次的五个位置约 0.64～0.65 秒，正常分配的 15 次结果为
637.494～643.891 ms；同批 Swift 中位数为 880.025 ms。单独改 `-O3`、只减少
辅助调用或只拆宽访存都不够。这证明本机本例仍有达到目标的空间，**尚未证明这组
信息能够由通用编译器合法产生，也未证明全局后端选项对其他工作负载没有代价**。

跨包函数信息及 C ABI 到宿主可识别运算的通用实现还未验证。首轮实施结果否定了
仅凭原型进入交付的充分性；恢复实现前须重新审查通用适用条件、目标代码代价及
验收证据。下文保留早期实验；最新容器结果以“最新实测”节为准，实施回撤的
历史过程见“实施回撤与重新归因”。

## 性能目标

本轮 nbody 优化的目标为：**在相同环境、输入和正式黑盒评测口径下，Feng 与
Swift 持平或超越 Swift**。以同批正式采样的 Feng wall 中位数不高于 Swift 为
性能目标，并结合分位数、最小／最大值及重复独立批次确认结论。差异处于测量
波动范围时应报告为持平，不能据微小差值宣称稳定超越。

当前归档中 Swift 的中位数为 867.267 ms，对应本机 20,000,000 步约 0.87 秒的
目标量级；最终验收使用同批 Swift 实测值。仅降到 1 秒以内不足以认定达到本目标。

验收使用通用编译器生成的正式用例程序及正常分配路径，保留完整合法样本，
通过独立进程覆盖自然地址分布；地址控制实验用于诊断。若仍有明显慢档，应报告
其频率和范围并继续定位，不能只以有利布局或最快样本宣布达标。启动安全授权
按本文的干扰处理方法与正式采样分开，语言语义和正确性要求保持主规范约束。

## 语义与行为保持约束

本轮优化必须保持 Feng 原有语义及受现有契约约束的可观察行为。当前调查没有证明
现有实现存在需要改变这些行为的缺陷；性能目标不能作为修改规范、放宽正确性
标准或改变既有行为的理由。

每项通用变换必须明确适用前提、证明所用事实的来源、事实失效条件及原路径回退，
并用正例和反例验证。具体数组、所有权、求值顺序、整数、浮点及 ABI 行为仍以
前述主规范为准，本文的验证矩阵用于检查优化前后一致性，不另设语言规则。

若发现行为差异，先在未优化实现上构造最小复现、对照规范条款并定位既有缺陷，
记录预期行为和回归覆盖，再作为独立缺陷修复处理。不能把优化新引入的回归或
更快但不同的结果称为原实现问题；没有既有缺陷证据时，应修正或撤回相应优化。

## 实施回撤与重新归因

### 已撤回的实现及风险

按照人工要求，已备份并撤回四个已有文件的改动和三个新增文件；未提交代码。
编译器、FCTS 注册及 Codegen 注册均恢复到 `b2bb456c`，本节是回撤后的新调查记录。
原有测试断言未迁移。备份包含各阶段源码、逐次测量和构建身份，避免把不同阶段
的验证结果混用。

- 长度与地址联合缓存，在若干固定页内位置退化约 10%～37%，未交付。
- 单独地址复用的已测试版本，在五个固定位置中三个改善约 2.5%～4.4%，另两个
  在 ±0.6% 内；这不能证明稳定达到 Swift，也不能用自然分配中位数变化声称大幅提速。
- 提前缓存一次性访问已在 `makeNullTerminatedPath` 的机器代码中造成额外一条
  指令：函数从 304 字节增加到 308 字节。text-scan 的应用源码汇编逐字相同，
  链入 std 的代码发生变化。配对测量 wall 中位数约增加 0.9%、CPU 约增加 1.7%，
  尚未证明这一条指令是整体波动的原因。
- 地址复用实现有数组所有者条件、标量表达式白名单和赋值类型筛选；最后未验证
  的修订还区分复合赋值与一次性访问。没有按 nbody 名称、五元素或 Body 布局识别，
  但不能因此称为“没有特判”。这些条件已随实现撤销，后续必须逐项列入人工决策。
- 全量 `make test` 通过的是提前取址的中间版本。最后的延迟选择修订只完成构建，
  没有完成全量验证，不能承接中间版本的通过结论。当前没有交付该修订。

“32 位下标检查”是原有 `cg_emit_checked_array_index` 在 32 位目标平台接收
`i64/u64` 下标时的防截断路径，本机 64 位 nbody 不走该分支。`int` 是平台位宽；
数组长度范围与整数表达式的规则仍以[内建数组规范](../specifications/feng-builtin-type.md#5-数组)
为准。本轮不修改长度、下标、值语义、浮点或异常行为。

另外核实到既有文档不一致：`std/std/src/collections/Array.ff` 的 `length()`
实际返回 `int`，而数组扩展规范第 17、44 行仍写 `long（i64）`。历史记录显示
实现于 `f234af3ff` 已改为 `int`，规范对应文字仍来自更早提交。这不是本轮引入的
类型变化；本次只记录差异，不改写主规范。数组的 `at(index: int)` 方法与语言
`array[index]` 也需区分：后者的语义检查接受整数类型，并保留过宽整数的范围检查。

### 本轮归因方法

先恢复原编译器并核对 `--keep-ir` 制品身份，再进行以下临时诊断。所有诊断均在
`temp/nbody-reanalysis-20260928/` 中保存，与正式黑盒结果分离，不修改生产源码。

1. 从原生成 C 出发，分别向后端暴露现有 data 查询、现有索引检查的函数体，以及
   宿主可识别的 sqrt，比较各单项与组合。函数体与布局只用于测量当前实现的
   信息边界，不是批准内联私有 ABI 或按数学函数名称添加特判。
2. 对原路径宽访存做等长指令对照；拆分副本与填充对照保持其余机器指令、代码
   地址、运行输入和 payload 页内位置一致，用于分离宽访存与布局相关成本。
3. 使用多个固定页内位置、串行交替顺序及同批 Swift，记录 wall、CPU、RSS、
   校验输出、首次授权和失败。正常路径校验不能代替语言全域等价证明。
4. 对照优化后 IR／汇编，区分辅助调用本身、调用引起的寄存器保存及整值写回、
   循环范围证明和访存形状。组合效果不按比例分摊，不把未证明的 CPU 内部机制
   或安全软件影响写成确定根因。
5. 若完整信息可见后仍有布局慢档，临时比较优化级别、SLP 向量化、严格访存对齐
   及成对访存选择的后端选项，验证是否存在更小的改动组合。它们仅用于诊断，不修改
   正式构建默认值；全局选项的其他工作负载成本也不能由 nbody 推断。
6. 对达到目标量级的组合补做独立批次、正常分配对照，以及已有数组行为探针和
   本机数学特殊值对照。有限场景通过只能收窄风险，不能代替通用实现后的全量
   回归与各目标平台的语义验证。
7. 在相同候选后端选项下重新比较三项信息的全部组合，避免用不同后端条件的
   单项结果推断必要性。“最小”仅指已测方案中通过目标的最小组合，不表示已穷尽
   所有编译策略或已经证明生产补丁最小。

只有重新形成有证据的通用方案，并明确特判、代价与语义证明边界后，才恢复实施。

### 回撤后静态复核结果

## 默认后端下的 C/C++ 对照

本轮保持 SLP、循环向量化及 AArch64 load/store 优化开启。正式 C++ 归档使用

### 计算核与生成指令

将正式 C++ 的配对计算及位置更新提取成一个普通指针计算核，分别按 C11 和
C++17 编译。两份对象文件的 `__text` 均为 392 字节，机器码完全一致；再从正式
C++ 二进制提取 `advance` 的 392 字节，与二者也完全一致。共同 SHA-256 为
`b495cf1ea29fd943e3b28f0319d6d1186829318f3f01042cedf536928d2caa0c`。
因此这次接入 Feng 分配路径的 C/C++ 参照确实使用了正式 C++ 的同一个计算核。

该计算核要求调用者提供五个已初始化元素，不能作为取消 Feng 边界检查的生产
实现。其他诊断继续保留 Feng 的初始化、输入、能量计算、输出和同一地址控制
设施，只改变 `advance` 中被调查的因素。

| 诊断 | 最内层配对循环的静态指令数 | 目的 |
| --- | ---: | --- |
| 原发码，数组地址／检查／sqrt 实现信息可见 | 40 | 前轮信息可见副本，默认后端 |
| 改写为简洁 C 循环，仍逐次调用相同检查与地址 helper | 40 | 区分 C 写法与访问契约 |
| 已知五元素的普通 C 指针循环 | 31 | 无检查的计算核参照 |
| C 指针循环的位置更新改为整值复制／写回 | 31 | 区分值复制语义与实际访存 |
| 外部 C／C++ 计算核 | 31 | 与正式 C++ 完全相同的机器码 |
| 信息可见副本，仅化简合法 storage 的容量冗余分支 | 37 | 区分固定容量事实与长度检查 |

上述配对循环均无函数调用、无栈访问，并保留六条双通道浮点运算。原发码与
“简洁 C + 相同检查”的这段指令逐条相同；不能根据生成 C 很长，就将宏、临时
变量、回绕加法写法或整个值复制一概判为实际开销。位置更新仍有局部指令差异，
因此不把配对循环相同扩大为整个函数相同。

相对普通 C/C++ 核，信息可见的 Feng 副本仍在内层保留边界判断、容量查询及
空地址选择、重复地址计算，以及外层对象不变字段的重复加载。直接、稳定的
元素基址有利于后端复用这些字段；仅令函数体可见还不足以完全消除差别。
这里的指令计数不能换算成逐项耗时，必须结合相同布局的实测。

容量分支诊断只在现有 storage 不变量 `length <= capacity` 的范围内，用
`length > 0` 推出 `capacity > 0`，保留空数组返回 NULL 与全部原索引检查。
该副本没有修改 runtime 源码或 ABI，不覆盖破坏对象头的不合法状态；它用于
检验不变量是否影响后端结果，不代表已批准向发码暴露私有布局。

由此得到以下结论：

1. **同一个 C++ 核也有相同的布局慢档。** 外部 C++ 核在三个位置为
   658.204～668.551 ms，在 16184、16296 为 1759.251、1711.694 ms；对应 CPU
   为 1735.531、1691.527 ms，表明差异主要发生在执行期间。两个位置分别让
   第四、第二个 Body 的 `vx/vy` 16 字节读写跨页。此前仅用 C++ 栈数组的快结果
   对比 Feng 的自然堆分配，无法将全部差距都归为 Feng 发码。也不能据此泛化为
   “堆内存本身比栈慢”；本实验改变的是实际位置。
2. **Feng 信息／检查路径仍有可见差距。** 在三个没有慢档的位置，信息可见的
   Feng 副本比相同布局的外部 C++ 多 126.645～136.898 ms，约 19%～21%。把
   它改写成简洁 C 并保留相同 helper 后，主要差距仍在。仅化简容量分支也没有
   带来接近 C++ 的收益，不能将少三条指令包装成已达目标的修复。
3. **复制形式及函数边界不是主要解法。** 普通指针核中，整值复制与逐字段位置
   更新的结果接近；不内联 Feng 的 advance 则五个位置都更慢。当前证据不支持
   用全局禁止内联、取消值对象复制语义或仅精简 C 文本来解决主要问题。
4. **接近 C++ 的发码仍不保证所有位置达到 Swift。** 普通指针核在两个位置仍
   明显慢于同批 Swift。保留默认向量化的生产方案必须分别解决合法的信息传播
   和目标访存成本，不能把 C++ 的快布局约 0.66 秒当成全域性能承诺。

### 后端为什么没有移出重复读取

额外记录同一 Clang 默认优化流程中 LICM 的前后 IR 和 missed remarks。
在信息可见副本的最后一次内层循环 LICM 中，容量读取位于索引检查成功分支；
LLVM 明确报告 `load is conditionally executed`，前后 IR 均保留该读取。
容量加载随后决定 `NULL`／payload 的选择，又阻碍使用稳定基址复用外层对象的
字段。这个证据说明后端在此处缺少“提前执行该读取仍然安全”的证明，不能解释
成真实容量会变化，也不能笼统归因于缺少向量化。

普通指针核的配对循环没有这些失败分支，外层对象的位置和质量已经移到内层
循环之外。只有保留合法求值路径、对象存活、有效范围以及异常／终止次序的证明，
才能在 Feng 中合法取得相近结果。日志中其他“循环可能使值失效”的备注包含
实际会写回的字段及外层循环，不能不区分上下文地认定为后端错误。此次没有发现
足以改变 Feng 原有语义的实现缺陷，也未证明调整优化 pass 顺序即可解决差距。

## 热循环的代码证据

### 数组访问是高频路径

[Feng 源码](../../benchmarks/cases/nbody/feng/main.ff)每步遍历五个天体的十个配对：
每对读出 `a`、`b`，更新速度后分别写回，共 40 次数组访问；随后五个天体各读写
一次以更新位置，再增加 10 次。每次访问在当前生成代码中各调用一次
`feng_array_check_index` 与 `feng_array_data`。

因此，单是 advance 的 20,000,000 步就对应 20 亿次数组辅助调用，以及 2 亿次
`Math.sqrt` 调用。这里是按循环工作量和生成代码推导的次数，未进行运行时插桩。
初始化、前后能量计算和输出不计入这个热循环调用数。

发码入口为 [cg_emit_checked_array_index / cg_emit_index](../../src/codegen/codegen.c)，
写入由同文件的数组左值路径处理。[runtime 实现](../../src/runtime/feng_array.c)
显示：检查读取长度后判断越界；data 返回同一分配内的 payload。当前函数边界使
宿主不能仅从这些调用名推断固定长度、地址稳定、只读效果及越界后的终止性质。

`advance` 在 `-O2` 下已经内联到 main；它的 `FENG_CLEANUP_BOUNDARY_6` 为 0，
热循环汇编没有 retain/release、分配或清理登记。生成 C 中被条件编译排除的
frame 代码不能计作运行时开销。

### 普通值对象的复制仍受调用影响

`Body` 为 56 字节，数组五个元素的 payload 为 280 字节。本机数组头及对齐偏移
为 72 字节，总请求 352 字节；分配器探针的 `malloc_good_size(352)` 为 384 字节。
这些尺寸不代表通用 ABI 承诺，也不说明程序存在内存泄漏。

当前读出／修改／写回的 C 表示是正常的值复制。原热循环汇编仍需跨外部调用保存
数据，随后将包括未改变字段在内的值写回。诊断中，当边界控制流和平方根运算
都对宿主可见后，配对热循环不再有这些调用与循环内栈溢出／重载，并只写回
被修改的速度字段。应优先恢复这种通用优化机会，不能把值语义本身改成隐式引用。

### Math 包装很薄，但调用信息没有传到使用方

[Math.sqrt 实现](../../std/std/src/numeric/Math.ff)直接委托 `libm sqrt`。
当前 std 静态库的该包装函数反汇编只有到 `_sqrt` 的尾跳转，没有 ARC 或清理操作。
问题不在复杂的 std 算法，而在使用方仍将它视为外部调用。

普通 C ABI 导入由 [cg_emit_registered_extern_decl](../../src/codegen/codegen.c)
生成独立 C 标识符并绑定 `FENG_NATIVE_SYMBOL("sqrt")`。诊断直接调用此已有
导入标识符，汇编仍为 `bl _sqrt`；改用 `<math.h>` 的普通 `sqrt` 声明后，本机
同样的 `-O2` 将该处降为 `fsqrt`。仅去掉 std 的一层跳转没有充分收益。

这揭示两层阻碍：跨包薄包装的函数体／效果不可见，以及底层 C 符号虽相同，宿主
识别方式不同。还不能据此断言仅添加 LTO 参数就能解决，也不能按 Feng 的
`Math.sqrt` 名称私加内建特判。数值行为仍须满足主规范。

### 调用边界具体丢失了什么信息

生成 C 的配对循环可缩写为以下形式；省略变量名修饰和其余字段运算，不改变
这里展示的读取、调用、写回顺序：

```c
feng_array_check_index(bodies, i);
Body a = ((Body *)feng_array_data(bodies))[i];
feng_array_check_index(bodies, j);
Body b = ((Body *)feng_array_data(bodies))[j];
/* 根据 a、b 计算距离及速度增量，其中调用外部 Math.sqrt。 */
feng_array_check_index(bodies, i);
((Body *)feng_array_data(bodies))[i] = a;
feng_array_check_index(bodies, j);
((Body *)feng_array_data(bodies))[j] = b;
```

`feng_array_data`、`feng_array_check_index` 和 `Math.sqrt` 在优化后 IR 中均为
外部声明，属性组 `#2` 没有 `memory(read)`／`memory(none)`、`nounwind` 或
`willreturn` 等效果承诺。检查函数的 C 参数虽为 `const FengArray *`，也不等于
整个调用只读；宿主仍须保守考虑其他别名、全局状态和异常。

原始读取的 payload 指针与写回前重新调用所得的指针，在 IR 中是不同的 SSA 值；
宿主无法据这些声明确认其稳定关系及中间调用是否修改了内容。因而原 `a.x`、
`a.y`、`a.z`、`a.mass` 等未在局部修改的字段，仍与速度一起写回。这里的优化障碍
是调用效果和存储关系不透明，而不是 `Body` 含隐藏引用计数。

main 的清理区域还使这些调用在 IR 中表现为 `invoke ... unwind`，指向异常清理
块。它们在正常路径汇编中仍是普通 `bl`，没有逐次执行清理登记；不能把每条
`invoke` 另算一次异常处理开销。缺少不抛异常的信息是控制流优化约束，需与
调用指令、寄存器保存的实际成本区分。不能仅为消除这些边而给未知调用添加属性。

证据定位：本轮 `nbody.ll` 第 439～556 行是配对循环，826、882、970 行是上述
三个外部声明，977 行为属性组；`nbody.s` 第 590～712 行为对应机器指令。

### 实际保留的访存与已消除的表面开销

按一对天体的一次迭代，直接统计正常路径汇编得到：

| 项目 | 数量 | 含义 |
| --- | ---: | --- |
| 数组辅助调用 | 8 次 | 4 次检查、4 次取得 payload |
| 平方根包装调用 | 1 次 | 仍是外部 `bl`，本处没有 `fsqrt` |
| 显式栈写入／读出 | 11／14 条 | 写 88 字节、读 112 字节；读出包含一次常数加载 |
| payload 读取／写回 | 各 112 字节 | 两个 56 字节对象均完整读写 |

这只统计调用方指令，不含被调用函数内部工作，也不是硬件采样或 DRAM 流量。
后续五次位置更新保留另外 20 次辅助调用，并使用包含重叠读取的宽指令搬运值。
整个系统只有 280 字节 payload，不能据上述频繁读写宣称内存容量或主存带宽不足。

同时可以排除几项从原始 C 容易误判的成本：

- `advance` 已内联；热循环内没有分配、retain/release、聚合复制辅助函数或
  frame／cleanup 登记。其预处理后的函数体也没有这些清理操作。
- `__llvm_c_eh_configure` 等协议标记已由异常插件移除，没有成为热循环运行时调用。
- 保持整数回绕语义的 `__builtin_add_overflow` 没有变成溢出检查辅助调用。
  优化后 IR 已将本例有界归纳变量化简为 `add nuw nsw`，汇编是普通加法与比较。
  这是后端证明本例范围后的结果，不意味着可以全局放弃 Feng 的回绕语义。
- 配对外层已经化简出 `i < 4` 条件，后续五个位置更新已展开。因此不能把差距
  归因于“宿主完全不理解循环”；主要缺口是范围事实尚未与数组访问契约连通。

### 跨页指令与慢档的对应

本轮核验并重新导出了既有 `page-panic-array-sqrt` 与 `page-range-sqrt` 的汇编，
来源 C／二进制哈希均匹配原记录，汇编与原副本逐字一致。它们的正常配对路径
已经没有数组／sqrt 外部调用及循环内栈保存，但仍包含速度字段的宽读写：

```asm
ldur q5, [x14, #24]  // 从一个 Body 读取 vx、vy，共 16 字节
...
stur q5, [x14, #24]  // 写回同两个字段
```

上述指令见 `page-panic-array-sqrt.s` 第 688、691 行；另一操作数有对应的宽读写。
`Body` 步长为 56 字节，因此第 k 个元素的速度二元组区间为
`[56*k + 24, 56*k + 40)`。结合本机 16384 字节页大小，可直接算出此前五个
payload 位置的跨页情况：

| payload 页内位置 | 下一页边界相对 payload 的偏移 | 正常热路径宽访存跨页情况 | 既有 wall 中位数 ms |
| ---: | ---: | --- | ---: |
| 15896 | 488 | 无；整个 payload 位于同一页 | 849.832 |
| 16184 | 200 | `bodies[3]` 的 `[192, 208)` 跨页 | 1765.711 |
| 16216 | 168 | 无；边界恰在两个元素之间 | 851.142 |
| 16248 | 136 | 无；该版本将边界两侧字段分开访问 | 846.249 |
| 16296 | 88 | `bodies[1]` 的 `[80, 96)` 跨页 | 1740.201 |

每个慢位置的相应元素参加四个配对，每对一次宽读、一次宽写，位置更新再宽读
一次，即每步 9 条这样的跨页指令，20,000,000 步对应 1.8 亿次。该次数来自
指令及循环结构的静态推导，不是性能计数器测量。

这还解释了为什么仅说“数组跨页”不够准确：16216 和 16248 的数组同样跨页，
但该优化副本的单条访问不跨页，仍处于快档。原路径在 16248 处则保留
`bodies[2]` 的 z／vx 成对读写，16 字节覆盖 `[128, 144)`，跨过偏移 136；
该路径此前属于慢档。原路径使用 `ldp/stp d`，不能将其与单个 Q 寄存器访存的
硬件代价直接视为相同。

这一步静态分析将宽访存跨页确定为与慢档逐项对应的候选机制；后续运行对照见
“实施前定向验证结果”。没有发现这些访问越过合法数组范围，也不能据此声称
已经确定具体 CPU 惩罚、页缺失或安全软件监控机制。

### 数组发码原型的行为差分

使用临时 `array-probe.ff` 经当前编译器生成 C，再构造候选 C 原型：

- 在五个经源码逐一核实的函数中，参数指向固定实例、没有重新绑定，既有拥有者
  保证调用期间存活；缓存其长度和 payload。只复用存储位置，不缓存元素内容，
  不省略值对象的完整写回。
- 其余 24 个检查点在原位置重新取得长度，不跨引用替换等未证明区间复用事实。
- 失败边使用 `if (index >= length) { feng_array_check_index(array, index);
  __builtin_unreachable(); }`，保留原 runtime 的消息来源。其成立前提是比较与
  检查指向同一、存活且长度不变的实例；不能推广为无条件添加 `unreachable`。
- 原 retain/release、aggregate、frame、cleanup 和异常协议操作及顺序保留。
  静态核验只允许其中的 payload 表达式替换为缓存地址，没有移除所有权操作。

原型不包含通用事实分析器；五个函数的适用前提由本次人工分析确认，不能把这些
函数名写入生产优化。原版和候选各先做独立启动校验，再把以下 12 个场景各重复
两次，共 48 次行为运行，加两次启动校验共 50 次：

| 场景 | 检查结果 |
| --- | --- |
| 普通数组读写及重复循环 | 数值结果与原版一致 |
| 基址、下标、RHS 的副作用 | 次数与顺序一致，轨迹为 1、2、3 |
| 复合赋值中的别名写入 | 使用 RHS 前的旧值，结果为 15 |
| 值快照与别名写回 | 原快照的未修改字段仍恢复为 10，修改字段为 25 |
| 下标／RHS 中替换数组引用 | 写入原先选定的实例，后续访问使用新实例 |
| 仅字段拥有数组时替换引用 | 原赋值保活有效，析构完整轨迹与原版一致 |
| 空数组、零次循环 | 不执行元素访问或提前 panic |
| 正越界、负下标 | 原 panic 消息及 SIGABRT 保持，RHS 未执行 |
| 替换为更短数组后访问 | 使用新长度 1，原位置触发越界 |
| 循环中较晚发生越界 | 前两轮写入与输出先发生，再在第三轮 panic |
| RHS 抛出异常 | 临时对象清理、catch 及原元素保留与原版一致 |
| 含托管字段的值对象数组 | 值复制、替换及析构轨迹与原版一致 |

八个正常场景全部通过独立数值／顺序检查；四个终止场景的消息、退出状态和信号
符合预期。每一对原版／候选的 stdout、stderr、退出状态及信号完全一致。
因此，该范围内没有发现数组变换改变既有语义或行为。

验证中曾把初始化临时引用的析构时机假定得过早。原 C 明确保留该临时引用至块末，
因此按实际拥有关系修正临时验证器，再逐字比较完整轨迹；没有修改 Feng 或已有
测试来迎合假定。该观察没有被当作本轮数组优化需要改变生命周期的依据。

边界仍需明确：这里只验证本机 64 位目标及所列场景，未证明任意未知 C ABI
回调、内部可变 storage、所有泛型／捕获组合或 32 位目标安全。原型在函数入口
查询视图，零次循环虽行为相同却增加了查询；生产实现应在实际需要访问的路径
建立事实，不能照搬而给无访问路径增加开销。后续通用实现仍须新增正反例和全量
回归，已有测试需要修改时另行逐条批准。

### 对实施条件的影响

以下是回撤前的实施判断，不能继续作为恢复地址缓存实现的依据。当时据定向验证
选择通用数组访问事实及失败边的分阶段实现，保留语义证明、失效条件和原路径回退。
当前手工数组组合存在一个退化位置，未达到独立交付条件；实施后必须复核完整
机器代码及多位置性能，不能只以行为测试通过或调用减少验收。

完整的 Swift 目标还需要跨包数学调用的通用通路，以及有代价判断的宽访存处理。
当前拆分证明了改善慢档的路径，但没有批准全局改变布局、runtime ABI 或接受
其他路径的额外成本。以正式编译器生成、正常分配路径及独立重复批次验收的
要求保持不变。

## 候选优化方案与待补齐验证

### 回撤后建议的实施顺序

实测已把下一轮范围收敛到“通用信息可见性 + 目标访存代价”。建议先验证以下
两条通路，暂不恢复地址缓存实现，也不预设必须增加一套 Feng 循环范围优化器：

1. **保留可供后端使用的实现及调用效果信息。** 从已有函数／包／C ABI 表示和
   构建链路出发，验证通用的函数体或效果信息传播。先用原 nbody 证明由普通源码
   和正式编译流程产生可见的数组操作与数学运算；不能把临时复制的 runtime
   私有结构及函数体写进 Codegen，不能按 `Body`、数组长度或 `sqrt` 名称识别用例。
   LTO、包内实现信息或受契约约束的原生调用识别都只是待验证候选，本轮没有证明
   其中任何一条可以直接启用并达标。
   C/C++ 补测后还应明确区分“固定容量／物理基址”与“该读取现在就能安全执行”。
   针对 LICM 实际拒绝移动的读取，先证明对象存活和原路径必达条件，再传播已有
   不变量；不能用无条件提前缓存替代证明，也不能为零次循环或一次性访问增加
   无收益工作。
2. **依据目标代码及实测选择访存策略。** 诊断中的两个后端开关证明了机器发码
   仍有空间，但关闭整个 pass 比消除少数慢访存的作用范围大。需要在通用目标
   代价层面说明适用条件，并测量 binary-trees、text-scan 及相关访存场景的成本。
   全局禁用 SLP／load-store 优化已从生产候选中排除。限定目标平台、增加选项或
   改布局也不能据局部诊断直接用于生产；涉及特判、runtime ABI 或新增运行时成本
   时由人工决策。

本轮 C/C++ 对照采用以下顺序，不改变正式基准或编译器：先核对正式 C++ 制品，
再用 Feng 的同一 Clang、目标、SDK、`-O2` 和浮点设置编译共同的 C/C++ 计算核；
将计算核接入相同的 Feng 初始化、分配、输入和输出路径，并覆盖相同 payload
页内位置。分别检查函数边界、数组辅助调用与检查、值复制、循环结构及最终宽
访存，避免把栈数组与堆数组、不同工具链或不同布局混在一个因果结论中。
无检查的 C/C++ 计算核仅作为已知五元素输入的性能参照，不能替代 Feng 的检查
语义；任何按已知条件化简的诊断都必须单独标明其证明范围。

只有上述信息仍不足以让宿主证明范围或复用事实时，才评估下面保留的数组／循环
分析候选。原实验没有手动缓存每次访问或删除原检查，后端已能自行化简本例；
重复实现同样的分析会增加范围和维护成本，现有数据尚未证明有必要。

将这两条通路转为足以验收的修复方案，仍需补齐以下工作：

1. **语义证明与作用范围。** 每项变换按前述行为保持约束给出证明条件、失效与
   回退；在相同地址位置下补齐关键单项／组合对照，确认性能收益的适用边界。
2. **通用数学调用通路。** 验证跨包信息和原生调用优化能够由普通 Feng 源码及
   正式编译器产生；当前手工修改 C 的收益尚未经过这条完整链路。
3. **地址敏感性的通用实现。** 本轮已验证拆分指定宽访存可消除所测慢档，仍需
   将其转化为具有目标代价判断的通用方案，并覆盖其他地址与工作负载；不能忽略
   无跨页位置的成本而全局应用。
4. **最终目标验证。** 通用实现通过行为差分及全量回归后，在正常分配路径上按
   评测主规范完成同批正式对比及独立重复批次，才可判定达到 Swift 水平。

以下保留回撤前各候选的证明边界，供通用方案复用；它们不再代表实施顺序，
也不是已批准恢复地址缓存或已经证明能够达标的性能承诺。

### 原候选一：统一数组访问事实与失败控制流

若后续证明确有缺口，可在 Codegen 中建立可复用的数组访问事实，供读取、左值
定位和循环分析共同使用，避免各处散落局部特判。至少记录数组实例身份、拥有者存活区间、长度／
payload 的可复用区间、下标求值结果及已证明的范围；证明失败时保留现有路径。

实施起点是 `cg_emit_checked_array_index` 与读写数组路径的共同发码，而不是
修改 nbody。先消除同一实例、同一有效区间内重复的长度／payload 获取，再将
原访问点的检查表达为宿主能理解的比较与终止失败边。该方向不需要新增 runtime
入口，也不需要暴露 `FengArray` 的内部字段。

已有调用参数保活见 [call_arguments.c](../../src/codegen/detail/call_arguments.c)，
按值参数只读使用判断见 [parameters.c](../../src/codegen/detail/parameters.c)。
这些判断服务于各自的所有权场景，不能直接视为完整的循环不变或全局无副作用
证明；数组访问事实必须明确自己的有效范围，并保持既有求值快照与保活边界。

早期诊断使用现有 `feng_panic` 的不返回声明展示终止边的作用；本轮又验证了
在已证明必然失败的分支调用原检查函数并表达不可能正常返回的原型，复用原消息
来源。通用实现仍必须证明比较与原检查针对同一存活、长度稳定的实例，不能
无证明添加 `unreachable`，更不能让检查正常返回时进入未定义行为。

证明边界必须覆盖：

- 数组引用重新绑定、索引或右值中的副作用、捕获、别名写入、回调和未知调用。
  分别处理“数组实例地址稳定”与“元素内容不变”，不能混为同一个只读事实。
- 仅在已有拥有者保证存活时复用原始地址；不因缓存而削弱 ARC 或异常清理。
  对普通托管元素或包含引用字段的值对象，保留原有复制、替换和释放语义。
- 依据[数组容器存储主规范](feng-array-storage-dev.md#42-核心不变量)，分别分析
  固定物理容量 `capacity`、有效元素范围 `length` 和数组引用身份。对同一存活实例，
  容器的逻辑长度变化不使 allocation 或物理 payload 起点移动；容量变化通过创建
  新实例并迁移处理。因此，地址稳定、逻辑范围稳定、引用仍指向原实例是不同的
  证明条件，不能因内部 `length` 可变而一并否定固定容量及物理地址的不变量。
  同时，[现有 data 访问器](../../src/runtime/feng_array.c)在 `length == 0` 时返回
  `NULL`；物理 payload 起点稳定不直接等于该 API 返回值始终相同。迁移后的源
  存储还涉及有效范围及所有权转移，不能仅按 `FengArray *` 类型给全部 runtime
  调用添加全局不变／纯函数承诺；相关行为以存储主规范为准。
- 下标及基址求值次数、求值顺序、越界失败位置和窄平台转换遵守主规范。现有
  32 位目标上的 64 位下标先检查再收窄逻辑必须保留；不能提前触发本不会执行的检查。

### 原候选二：通用循环范围分析

在已证明的访问事实之上，利用支配条件、同一索引的既有检查和归纳变量范围删除
冗余检查。常量上下界、运行时长度上界、嵌套循环都由同一分析处理；不按天体
数量、函数名或 `Body` 类型生成特例。

必须按 Feng 的整数回绕规则证明范围，覆盖零次循环、循环中修改变量、提前退出
和未知回调。静态证明不足时维持原路径；若采用“入口条件选择快慢循环”，失败
分支应执行原循环，不能提前 panic 而改变此前副作用。额外分支、代码尺寸和
回退路径成本须在实施评审时明确，不能只展示最快路径。

本轮 IR 已证明宿主能够理解本例归纳变量范围。实施时应先验证通用路径暴露的
长度、稳定地址及失败边能否复用宿主已有分析，再依据剩余缺口决定 Feng 自身
需要补充哪些范围事实；不应预设必须重建一套完整循环优化器。

访问事实与循环分析可以分别验收，但单独缓存地址的实验已经表明：是否交付某一
中间优化，必须由完整机器代码、语义覆盖和多输入性能共同决定，不能仅统计少了
几个 runtime 调用。

### 跨包与 C ABI 调用信息的证明边界

继续在核心编译器及构建链路层面处理薄包装，研究通用的跨包函数体／效果信息传递，
以及合法 C ABI 声明如何让宿主识别原生库函数。必须同时考虑签名一致性、符号
冲突、重命名、调用约定和已有异常插件的处理顺序；未知外部函数保持保守。

C ABI 主规范明确互操作层不预设特定 C API 行为；仅有符号名 `sqrt` 及相似签名
不足以把任意导入当作 libm 运算。需要先证明调用目标及其数值／副作用契约，才能
让宿主应用相应优化；尚未具备该证明时保留原调用。

当前生成 C 标识符隔离还承担兼容职责：已有
[原生符号别名测试](../../test/codegen/test_codegen.c)要求不同 Feng 声明及不同 C
原型能够指向同一原生符号，并覆盖符号转义和目标平台重定位。因此，不能把所有
导入全局改为同名 C 标识符。这套隔离没有被证明为语言缺陷；数学优化不能通过
破坏这项既有行为获得收益。

可评估链接期优化或包内优化信息，但当前实验没有验证其包格式、工具链兼容性和
完整收益，不能直接宣布启用 LTO 即可完成。`Math.sqrt` 只作为此通用能力的验证
对象，无需先重写 std 数学算法。

现有 Math 规范要求委托宿主 libm。普通正有限输入的 nbody 校验不足以授权改变
NaN、无穷、有符号零、负数域或舍入行为。候选实现应保留标准库公开契约，并在
各目标平台验证宿主优化所保留的行为；本方案不提议启用 fast-math。

验证还需区分“Feng 未定义额外的 errno／浮点环境语义”与“任意 C ABI 调用都可
忽略外部可观察效果”；前者不能用来证明后者。不得未经证明添加 `pure`、
`readnone`、`noalias` 或不返回属性，也不能仅凭本例最终输出一致来替代上述判断。

### 地址敏感性的处理边界

将不同进程、页边界附近布局纳入性能验收，避免把一次幸运分配当作稳定收益。
先通过通用发码减少不必要的整值写回与跨调用保存，再判断剩余布局敏感性。
普通值赋值能否只回写部分字段，还依赖中间调用没有通过别名修改原存储的证明；
不得对所有值对象无条件省略未在局部修改的字段。

当前证据不足以确定具体硬件惩罚机制，也不支持立即修改数组头、值对象布局或
通用分配器对齐。后者会影响内存、ABI 和其他工作负载，若需推进应另行决策。

本轮已完成保持其他机器指令及位置不变的访存拆分对照，验证了所测慢位置的收益
以及快位置的额外代价。下一步应据此评估通用的目标代码生成策略，明确适用条件
和其他位置／工作负载的成本；不能由局部实验直接决定关闭全部向量化，也不构成
改变值语义或数组 ABI 的理由。
