## 1. 目标与边界

在[成员签名提示与重载切换修复](feng-lsp-member-signature-help-bugfix.md)的基础上，补齐合法调用仍无 Signature Help 的三类缺口：直接调用 callable 值、对象构造、spec 父契约与交叉成员调用。将已通过临时探查但尚未固定的边界场景纳入回归。

本阶段面向 LSP，拟修改范围为 `src/cli/lsp/`、现有 `test/cli/` 测试入口及本开发文档。保留既有用例、断言与测试阶段，不新增 Python、`.inc`、独立测试程序或构建目标。若必须迁移既有断言，先说明原因并取得人工批准。

语言行为以[函数规范](../specifications/feng-function.md)、[表达式规范](../specifications/feng-expression.md)、[类型规范](../specifications/feng-type.md)、[spec 规范](../specifications/feng-spec.md)、[泛型规范](../specifications/feng-generics-draft.md)及[可见性规范](../specifications/feng-visibility.md)为准，本文件不重新定义这些规则。缓存、调度、版本与性能边界引用 [LSP 性能架构主规范](feng-lsp-performance-optimize.md)。

除下述获批的 I04 外，不修改 lexer、parser、Semantic、Codegen、runtime、ABI、FT／FB 格式、标准库、编辑器 UI 或用户项目；不增加调用点强制语义分析，不在 LSP 复制完整类型检查或重载决议。若发现必须改动这些层才能解决的问题，先记录证据，再由人工决定范围。

实施中获批的唯一范围扩展：I04 的交叉 spec 实例修复，包含 Codegen 的组成实例／witness 选择、Semantic 的既有调用选择元信息记录及新增 Codegen／FCTS 注册，见第 7 节。用户要求同包与跨包均正确，并允许必要信息进入 FT；现有 FT 已足够，因此未扩展格式。其余边界不变。

## 3. 最小复现

以下三组完整源码均已单独通过基线 `feng check`，以便独立复现。Signature Help 的查询位置放在各目标调用的 `(` 之后，查询本身不执行函数；本次未对这三组源码进行发码或运行验证。

### H01：直接调用 callable 值

```feng
module signature.callable;

spec Callback<T>(value: T): T;
type Holder { let callback: Callback<i32>; }

func relay(fn: Callback<i32>): Callback<i32> { return fn; }
let global: Callback<i32> = (x: i32) -> x;

func probe(value: Holder, values: Callback<i32>[], fn: Callback<i32>) {
  fn(1);                // 对照：有签名。
  value.callback(1);    // callable 字段：无签名。
  values[0](1);         // callable 数组元素：无签名。
  relay(fn)(1);         // 返回值继续调用：第二个调用无签名。
  let alias = fn;
  alias(1);             // 推导别名：无签名。
  global(1);            // 全局 callable 绑定：无签名。
}
```

这些调用的签名参数均应来自 `Callback<i32>`：`value: i32`，返回 `i32`。既有用例中的 `value.callback(...).method(...)` 验证后续成员查询，不能替代 `value.callback(` 自身的签名验证。

### H02：构造函数

```feng
module signature.constructor;

type Point { func Point(value: i32) {} }

func probe() {
  let point = Point(1); // 在 Point( 后查询，当前返回 null。
}
```

构造函数的存在及分类已由源码／符号记录承载。这里缺少参数提示，不是要求增加新的构造语法或运行时能力。

### H03：spec 父契约和交叉成员

```feng
module signature.contract;

spec Parent<T> { func take(value: T): T; }
spec Child<T>: Parent<T> {}
spec Tag { func tag(): i32; }
spec Both<T>: Parent<T> & Tag;

func parent(value: Parent<i32>) { value.take(1); } // 对照：有签名。
func child(value: Child<i32>) { value.take(1); }   // 无签名。
func both(value: Both<i32>) { value.take(1); }     // 无签名。
func constrained<T: Child<i32>>(value: T) {
  value.take(1);                                 // 无签名。
}
```

后三处应从静态契约取得 `take(value: i32): i32`。父契约成员叠加和交叉成员合并的合法性、冲突与可见性规则继续由 spec 主规范定义。

## 4. 代码定位与通用方案

### 4.1 保留完整调用目标

现有 `resolve_signature_callee` 已使用 Feng parser，但随后要求 `call_callee_name_slice` 返回简单名称；该帮助函数只接受标识符、成员及泛型目标。数组下标和调用结果作为 callee 时，在进入类型查询前便被排除。

拟将签名请求的上下文保留为“当前调用及 callee AST、源码位置、词法作用域”，名称仅用于显示或具名声明查找，不再作为所有调用的前置条件。复用当前文档 AST；编辑状态需要恢复时仍使用现有范围定位和 parser，不增加表达式字符串识别规则。恢复 AST 及文本由同一请求持有到响应构建结束。

在既有调用查询上扩展，不再增加一条“失败后按名称猜测”的签名路径。已有函数、方法、局部 callable 请求须同时经过回归，保持词法遮蔽、模块身份和当前文档优先的行为。

### 4.2 从被调用值取得 callable 签名

H01 有三个直接阻断点：`build_signature_help_json` 排除字段候选；`resolve_local_signature` 只处理显式类型或直接 Lambda 初始化器；模块函数查询识别全局绑定后没有将其适配为 callable 签名。

复用 `resolve_completion_expr_type` 已有的局部绑定、字段、下标、调用结果和源码／FT 类型解析，取得 callee 的静态类型，再将 callable-form spec 的形参、返回值及 owner 泛参绑定交给统一签名适配和格式化。直接 Lambda 的已有参数信息也接入同一结果表示；不能为上述五种源码形态分别维护签名算法。

已有语义事实可用时复用它；编辑状态仅沿既有类型和表达式规则恢复可证明的信息，不重新分析函数体。非 callable 值、无法确定类型或真正的歧义不伪造签名，也不穿过同名局部值重新找模块函数。

调用结果没有简单名称时，仍必须能够形成签名。显示沿用现有签名格式；具名绑定使用其调用名称，无简单名称的目标使用已解析 callable 契约的声明信息。正式用例应固定展示样例，避免把整段接收者源码当作签名身份或重载选择依据。

### 4.3 构造函数作为已有 callable 分类消费

当前具名函数入口只收集函数／绑定，方法签名入口又没有覆盖构造目标。源码已有 `FENG_TYPE_MEMBER_CONSTRUCTOR`，符号已有 `FENG_SYMBOL_DECL_KIND_CONSTRUCTOR`。

在共同调用目标解析中识别类型目标，然后按已有构造分类、可见性和 owner 泛参绑定收集构造签名；保留全部可见重载并复用参数位置、选择和格式化处理。不得把普通静态方法混入构造重载，也不得仅按函数名与类型名相同来识别构造。

同时验证显式无参、多个构造、泛型类型、模块限定与导入别名。对隐式默认构造，实施前先核对现有类型／构造元信息如何表达其资格，按类型规范验证，不能因为查不到显式构造就无条件生成空签名。若现有查询确实无法表达所需信息，记录最小证据并由人工决定，不自行增加核心 API 或 FT 字段。

### 4.4 在共享成员查询中补齐 spec 成员闭包

当前 `member_collect` 收集直接 owner 成员和 fit，但没有沿 object-form 父列表、intersection-form 组成类型继续收集。`member_resolve_receiver` 将开放泛参映射到约束后，仍进入这个不完整的成员集合。

在现有共享查询中补齐可达成员，Completion 与 Signature Help 消费同一个结果；不新增专供 Signature Help 的 spec 搜索算法。可复用的信息包括：

- 源码的 `parent_specs`、intersection-form `members` 及完整类型实参。
- `feng_symbol_decl_declared_spec_count/at`、`feng_symbol_decl_intersection_member_count/at` 等已有符号接口。
- 已有类型绑定、结构比较、成员可见性、声明身份和请求内存管理。

每条父契约／交叉成员边都先应用当前 owner 绑定，再进入对应类型实例。访问判定保留成员原声明及所属契约；重复 requirement、子契约代表声明与合法重载的处理引用 spec 主规范，不能按裸成员名或未代入的声明指针直接合并。菱形路径和不同泛型实例必须分别验证。

优先消费适用的既有语义成员信息；源码／FT 查询适配也必须保持同一成员含义。编辑中出现环或无效类型时使用请求内的遍历保护，不无限递归，不把无效契约当作新的语言行为。该适配不承担核心编译器的满足检查、诊断或完整重载决议。

### 4.5 保留展示、缓存与生命周期边界

重载切换、失效选择、每个签名的活动参数，以及声明级方法泛参的展示沿用[上一修复](feng-lsp-member-signature-help-bugfix.md)；本阶段不顺带改变方法泛参的调用点展示策略。

补齐调用目标类型和 spec 成员来源后，继续复用 `FengLspSignatureHelpSet`、已有签名格式化器及泛型代入。适用的旧分支应改为消费共同结果；被替代的重复解析须删除，不能长期保留两套算法。

跨包继续使用既有模块来源选择，避免 AST 与同一公开 FT 重复加入候选。缓存优先级、后台发布及调度保持原策略；借用 AST／符号的生命周期受现有快照和请求管理保护，不新增持久缓存，不在请求中触发整项目分析或 I/O。公共查询调整后必须验证原 Completion 行为，不能用本次签名修复掩盖其退化。

### 实施前信息核对

- 默认构造的规则见类型主规范。`src/symbol/ft_write.c` 的 `writer_should_export_decl` 保留所有显式构造（包括 `seal`）及可见性，因此源码和 FT 均可区分“未声明构造”与“已声明但不可见”，不需要新增 FT 字段。

### I02：闭合块的结束位置被当成块内

新增矩阵发现 `func probe(){{let fn=(x:i32)->x;}fn();}` 在外层 `fn(` 查询时显示内层 Lambda 签名。基线 `95d068c1` 同样复现。根因是闭合块采用包含结束位置的范围；紧邻 `}` 的下一标识符起点恰好等于块的结束偏移，被算入内层作用域。修复共享块范围查询：已闭合块使用半开区间，未闭合的编辑片段仍允许光标位于末尾。不修改语法／语义，保留相邻块、控制流与块内调用正反例。

### I04：交叉 spec 的不同泛型实例通过检查但无法打包

初次新增跨包夹具 `spec Parent<T> { func take(value:T):T; } spec Dual: Parent<i32> & Parent<string>;` 通过 `feng check`，但 `feng pack` 报 `CE0048: default subject parent witness member mismatch`。修改前的 `95d068c1` 编译器也复现；删除 Parent 的静态方法后仍失败。当时本地 LSP 能返回两个正确代入的签名，跨包矩阵尚不能生成该声明的 FB。

这是独立的既有 Codegen 问题，发现时尚未修改核心层。用户决定纳入本轮，要求先 Review 通用修复方案。其他用例继续验证，保留该复现，不将检查通过当作打包通过；后续批准及修复结果如下。

代码根因已定位：`cg_register_user_spec_members` 把“交叉 spec 自身无泛参”误当成“组成 spec 也没有类型实参”，此分支读取 `flattened_members` 的裸声明并按声明查找，丢失 `Parent<i32>`／`Parent<string>` 的实例身份；而父 witness 图已经正确记录这两个实例。默认 subject 的父视图适配因此找不到匹配的已具化成员，触发 CE0048。

经 Review 获批的通用方案：

1. 交叉 spec 成员登记统一消费 `cg_register_spec_witness_parents` 已建立的组成实例图；不再区分“自身泛型”与“自身非泛型”两套成员来源，不重做重载决议。
2. 按组成实例复制已具化成员，复用既有成员合并、重载编号和 ABI bridge；叶成员来源始终保留完整类型引用，嵌套交叉继续传递叶来源。
3. 保持现有 runtime、ABI 协议与 FT 格式。改动发生在编译期，不增加生成程序的引用计数、分配或额外调用。
4. 新增编译与行为覆盖：自身无泛参但组成有实参、同一父 spec 的两个不同实例、泛型交叉对照、嵌套交叉、默认值与父视图转换、实例／静态成员、源码及隐藏源码跨包。复用原测试入口注册；既有用例及断言保持不变。

用户已批准上述通用方案与新增测试注册。若发现不能复用现有实例图或桥接规则，继续记录并提交人工决策。

第一轮验证：组成实例统一后，原最小项目打包通过，新增四种 Codegen 矩阵及全部既有 Codegen 用例通过；新增 FCTS 语义检查通过。行为验证在导入 `InstanceSubject` 转换为嵌套交叉视图时又报 CE0315，提示缺少 `InstanceParent<i32>.take` 实现。此项属于 I04 承诺的跨包具体 subject 路径，正在核对导入声明的实例身份及既有实现选择信息；不能据打包通过就认为 I04 已完整修复。

进一步证据：`FengSpecWitness` 以 `(subject_key, spec_decl)` 为键，不包含 spec 类型实参。该导入路径得到的裸声明 witness 中 `take` 实现为空，而已登记的具体类型方法中 `take(i32):i32` 能唯一匹配，string 重载不匹配。原 Codegen 只在 subject 自身为泛型实例时避开该裸声明 witness。补充方案将同一身份规则用于 target spec 泛型实例：两端任一为泛型实例时，使用现有完整具化类型的 `cg_resolve_witness_binding_fallback`；普通完整 witness 路径保持原状。引用对象与值装箱两处一致调整，保留精确类型与歧义检查，不增加 Semantic 字段或运行时操作。该补充方案已获下述同包／跨包修复授权并实施。

范围复核：同一组声明分别放在同包与两个包中，`feng check` 均通过；仅进行交叉视图转换时，两者均能打包。加入 `instance_static_int<InstanceSubject>()`（函数约束为 `T: InstanceBoth`）后，两者均报 CE0315。泛型调用触发相关 witness 的按需计算，随后 Codegen 读取裸声明缓存而失败。因此此项是核心 Codegen 的实例匹配问题，同包也受影响，不能只对导入路径处理；“所有泛型 spec 转换都会失败”也不符合实测。

用户已批准继续修复，要求同包与跨包均正确，必要信息可以进入 FT。先复用已具化方法与完整目标 spec 的精确匹配，引用对象和值装箱采用一致身份规则；补齐同包、源码依赖和隐藏源码 FB 行为验证后，才能判断是否需要扩展 FT。若现有 FT 能保留本次所需信息，不增加冗余字段。

共享体补测发现相同实例身份问题尚有调用端：`func shared<T: InstanceBoth>(value:T):string { return value.take("s"); }` 的语义检查通过，生成 C 却把结果当作 i32 再转换成 string 指针，宿主编译器给出 `-Wint-to-pointer-cast`。需核对共享体对“同一个成员声明的两个已具化槽”的选择；保留该测试并修复，不压制警告。测试中字段访问按既有语法使用 `self`，开放 T 调用成员直接使用约束，不把当前不支持的 T 到交叉视图显式转换作为编译正例。

调用端根因：返回类型推导已经统一处理 object／intersection 约束，但 `validate_call_expr` 记录实例成员调用时只接入 object 约束，交叉约束调用没有记录 `FengResolvedCallable`。Codegen 因此走未解析成员的名称查找，误取首个槽。将交叉约束接入同一现有重载解析与记录路径，使用现有 `owner_instance_type_ref` 保留被选中的 `Parent<string>`；无须新字段、FT 格式或运行时协议。新增断言直接检查共享体的选中声明及 owner 实参，并编译其生成 C、执行引用和值 subject 行为。

专项验证结果：全部 Codegen 用例通过，新增用例分别销毁生产方 AST 后，从 public／workspace 两种 FT 重新导入并编译生成 C；FCTS 1650／1650 通过，包含 6 组新增本地／跨包行为。引用对象、值装箱、默认值、父视图、嵌套／泛型交叉以及共享体的实例／静态调用均已验证。补充方案已实施；没有新增 FT 字段、runtime 操作或 ABI 变更。

### I05：未知嵌套实参退回开放形参展示

探查 `fn:Callback<Missing>` 的 `fn(` 显示 `func fn(value: T): T`。未知类型实参在共同类型适配时被存为 NULL，随后绑定失败而保留声明中的 T。修复应使存在未知子类型的源码类型整体解析失败，不把显式但无效的实参伪装为合法开放参数。补充未知泛型实参／数组元素、循环绑定和无效契约环的负例；有效开放参数仍由作用域身份表示。

### I06：未闭合块缺少签名恢复

新增 `func probe(){{let fn=(x:i32)->x;fn(` 编辑状态返回 null。现有签名恢复只补圆／方括号及分号，没有闭合外层尚未输入的块，恢复后的全文仍无法解析。修复在恢复文本的末尾按 lexer 的块嵌套补齐缺失右花括号，不改查询位置、真实文档或 parser 规则，并验证块内／块外作用域对照。此类无显式契约的 Lambda 是沿用既有 LSP 编辑恢复能力；完整程序会有 AE0520，不计作合法编译正例。

### I07：其他文件的未保存编辑没有进入源码索引
