## 1. 目标与规范归属

让明确标注 `@inline` 的 Feng 函数向后端提供内联提示，并在二进制包分发时，
为消费端 Clang 提供可用于优化的函数体。是否内联仍由 Clang 决定；不承诺每个
调用都展开，也不能用关闭检查或改变语言行为换取性能。

本文是开发方案，不另行定义已存在的语言规则。Review 通过后，先将新增规则
收敛到对应主规范，再实施代码和测试：

## 2. 已确认的设计边界

1. 注解是优化提示。为标注的函数生成对应 C 内联声明／属性，具体是否展开由
   Clang 决定，不使用 `always_inline` 强制所有调用展开。
2. 同包仍交由现有 Feng → C → Clang 链路优化。跨包需要让消费端得到可编译的
   函数体；只有声明或普通机器码静态库不能提供该函数体。
3. 函数体依赖检查采用**叠加后的最终包外可见性**，复用现有解析与可见性规则。
   不只检查声明是否写了 `open`；模块、所属类型与成员共同决定是否可达，默认
   公开成员也按其真实可见性处理。仅对特定 friend／mix 上下文开放不等于包外公开。
4. 用到非包外可见的依赖时编译期报错。不自动公开用户声明的私有依赖，也不为
   它们生成访问包装来绕过该检查。
5. 参数、局部变量及函数自身的泛型参数属于函数局部上下文，不要求声明 `open`。
   其引用的外部类型、成员等仍接受相同的最终可见性检查。
6. 不递归要求普通被调用函数的内部实现公开。`@inline A → open B → seal C`
   中，仅导出 A 的函数体时，A 调用 B 的普通公开符号，C 仍封装在 B 的实现中。
   若 B 自己也标注 `@inline`，则 B 独立接受其函数体的依赖检查。
7. 保留可调用、可取址的普通函数实现。未内联的调用继续使用库中的实现；不能
   因函数带注解而删除 callable 适配器所需的入口。
8. callable 继续采用既有表示、调用和相等规则，不增加一套 inline callable
   机制。展开后的代码必须保持原有对象身份、捕获、ARC 和清理行为。
9. 不改变求值顺序、值复制、异常传播、数组检查、浮点语义及其他现有可观察行为。
   已确认存在的问题须独立证明与修复，不能作为内联的隐含语义调整。
10. 不全局禁用向量化，不将默认优化等级改为 O3，不启用 Full LTO／ThinLTO。
    即使后续选择独立通用插件，也不得放入 `llvm_c_eh`；本草案不批准新增插件。

## 3. 建议的实现结构

### 3.1 语义阶段与依赖检查

在名称、重载、类型与调用身份已解析后，检查待导出函数体引用的声明。检查覆盖
函数、类型、字段、方法、构造、全局绑定以及解析得到的隐式源级依赖；不能只扫描
标识符文本，也不能因常量折叠或预期优化会删除某个分支而跳过语义检查。

诊断应指出使用位置、不可包外访问的声明及阻断它的可见性层级。注解合法位置、
重复注解和参数规则需要单独确定，见 §6；本文不预占错误码。

当前 `std/std/src/numeric/Math.ff` 中公开的 `Math.sqrt` 调用未公开的顶层
`extern sqrt`。按已确认的严格规则，给前者增加 `@inline` 会因依赖不可见而报错。
调整该声明或模块的公开 API 必须另行 Review，不能因它是 extern、libm 或 sqrt
而自动豁免。本文不修改 std。

### 3.2 C 发码、函数实现与链接

讨论中的候选是继续生成 `feng.c`，另用 `feng_inline.h` 承载需要导出的函数体，
让生产端与消费端使用同一份实现文本。头文件只是函数体载体，不是第二份可任意
重复定义外部符号的实现；生产端仍需产出普通函数符号供未内联调用及 callable 使用。

必须先用独立原型确认 C 声明／定义组合：生产端产出唯一普通实现，消费端取得
优化用函数体，O0 或未内联时引用普通实现。C 的 `inline`、`extern inline` 与
Clang 属性必须按其实际链接语义选用，不能把“带 inline 字样”视为已满足这些条件。
具体拼写、头文件包含位置及是否采用 GNU inline 语义属于 §6 的 Review 项。

同包函数仅有内联提示时，也要保持原有函数符号、调用 ABI 及调试映射。
不为某个基准、数组元素类型或数学函数选择不同的发码规则。

### 3.3 声明依赖与编译器生成的对象

头文件需要包含足以编译函数体的类型定义／前置声明、普通函数声明和其他依赖。
普通被调用函数不必因被引用而一并导出函数体；若它也有经验证的内联定义，可按
相同机制提供。多包、多头文件引用不能重复定义同一类型或普通函数符号。

源码中的依赖全部公开，并不能自动解决生成 C 中辅助对象的存储与链接。
应按“代码和声明”与“需要保持身份的存储实体”的通用规则处理，不能直接将
整个 `statics` 区复制进头文件。需要保持身份的已有对象，展开后仍引用原对象。
生成符号的命名、可链接性及依赖完整性仍须设计和 Review，不改变其 Feng 源码可见性。

callable 是该通用约束的一个验证场景。假设以下声明最终均对包外可见：

```feng
open spec Callback(): int;

open func work(): int { return 1; }

@inline
open func get(): Callback { return work; }

open func getFromLibrary(): Callback { return get(); }
```

当前同包发码为同一函数及 callable 类型复用对象。消费端直接调用 `get()`，与
通过库中的 `getFromLibrary()` 得到的结果，不能因前者展开而改变原有相等结果。
`work` 本身仍是同一个函数；若误复制包装对象，错误来自发码改变了对象身份。
此例不要求改变 callable 的相等规则，也不将所有闭包改成共享单例。

### 3.4 二进制包、FT 与缓存

二进制包需要将普通库实现与优化用函数体作为匹配的构建产物分发。消费端只使用
分发包也应完成编译，不依赖生产端工程目录、原始源码或本机临时文件。

FT 至少需要表达该声明的内联事实及对应产物身份；函数体放在 FT 文本中还是
独立头文件中，最终格式见 §6。C 文本必须与目标、ABI、依赖及生成器版本匹配，
不能将某个平台产出的 C 布局无条件用于所有平台。

函数体和依赖变化需参与缓存失效。包内多模块、传递依赖、重复包含及多个消费包
必须有一致的声明身份与链接行为。缺失、损坏或错配产物的处理需明确报错或回退
策略；不得在格式未定义时静默使用旧函数体。此次尚未发布，不额外设计旧包兼容层。

## 4. 性能证据与验收边界

[nbody 调查](feng-nbody-performance-optimize.md)已验证，在固定容器布局、默认 O2、
无 LTO 条件下，暴露函数体能减少热点外部调用、栈保存和冗余写回。该结果支持
研究函数体可见性，但不是本注解实现的性能成绩。

已有约 0.65 秒的组合还包含手工 C 属性及私有 runtime 函数体可见等诊断条件，
不能直接推导“实现 @inline 即可获得相同成绩”。数组 runtime 辅助函数的可见性
也不因新增 Feng 注解自动解决；其正式方案不得绕过 runtime 私有 ABI 的人工决策。

验收应从回撤后的正式基线开始，使用无手改 C 的生产编译链路：核对生成 C、LLVM
IR 与热点汇编，测量运行时间、代码体积和编译时间，并用正式输出校验保持行为。
容器结果与 macOS 结果分开记录；历史多布局慢档及安全软件启动干扰仍按调查口径处理。
目标仍为接近或超过同机 Swift，但必须以实施后的同批实测验收，不能预先保证。
