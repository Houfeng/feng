## 1 目标与规范归属

允许库自行定义具有普通成员和父契约的异常根 spec，编译器通过内建注解识别其
身份，不感知具体库、模块、类型名称或 `toString` 等成员名称。

根 spec 同时作为普通值类型和普通泛型约束：前者支持统一持有、传递不同具体
异常，后者证明泛型共享体中的值具有可抛资格。无需增加内建 `throwable` 类型、
关键字或另一套泛型约束系统。

## 2 已确认的语言边界

### 2.1 注解标记库中的契约

`@throwable` 用于 object-form `spec`。它标记一个已有的普通契约，不生成契约，
也不为其补充成员或实现。其他 spec 形态和其他声明种类不属于该注解的适用位置。

以下只展示用法；名称、所在模块和成员并非已经确定的标准库 API：

```feng
@throwable
open spec Throwable {
  func toString(): string;
}

type Error<T>: Throwable {
  let detail: T;

  func toString(): string {
    return "error";
  }
}

func raise<E: Throwable>(error: E) {
  throw error;
}

func forward(error: Throwable) {
  throw error;
}
```

库也可以按普通父契约规则复用 `Display` 等契约。编译器只根据注解登记的声明
身份判断异常根，根契约的成员满足、可见性、调用和 witness 均沿用普通 spec 规则。
根本身是否允许泛型、是否要求公开及注解参数写法，见第 8 节待决项。

`@final` 是[独立特性](./feng-final-annotation-dev.md)，可按其规则与根标记组合。
`@throwable` 本身不表示 final，不隐式禁止子 spec，也不依赖 `@final` 先实施。

### 2.2 在建立满足关系时检查载荷资格

统一规则：**具体类型声明满足异常根契约时，必须通过合法载荷检查和普通契约满足检查，
该满足关系才能成立。**

检查发生在具体 `type` 声明头与 `fit` 的契约关系验证处。关系指向根本身，或者
通过父契约闭包间接包含根时，都必须检查；普通契约关系继续使用原有规则。

合法载荷检查统一复用异常主规范的既有规则，并提前到声明满足契约时执行；本方案
不再按数据类别分别规定准入行为。检查失败在建立满足关系处报告；已被既有声明规则
拒绝的位置继续报告原有根因，不增加重复诊断。通过验证的根满足关系同时保证合法
载荷资格与契约能力，后续 throw 只消费该证明。

- `Error<T>` 是具名 type，允许声明满足根契约，不能因为声明中有开放泛参而拒绝。
  T 不必满足异常根：例如 `Error<int[]>` 的载荷是具名对象，不是其数组字段。
- 其他 spec 对根的父关系表示契约关系，不把该 spec 声明本身当作具体载荷类型检查。
  它的具体满足者仍必须经过上述载荷准入。

现有 `type_ref_is_exception_payload` 同时包含“载荷类别”和“当前类型引用仍含
开放泛参则拒绝”两类判断。实施时应抽取统一的合法载荷检查并前移，不能把整个旧函数
原样用于 `Error<T>: Throwable` 的声明验证。

### 2.3 throw 只消费根契约证明

对于 `throw expr`，完成表达式解析和通常的语句检查后，类型准入统一判断：
**能否按既有契约关系证明该表达式满足已登记的异常根。**

- 具体类型及 `Error<T>` 等具名泛型类型，根据已验证的满足关系证明。
- 直接泛参 E，根据普通 spec 约束证明；`E: Throwable` 无需另加内建 `throw` 约束。
- 已形成的根 spec 值可直接抛出；能够按既有契约关系证明根能力的其他 spec 视角，
  复用已有父契约或交叉契约投影，不另造结构匹配或联合类型准入规则。
- 无约束泛参、无关契约约束及没有根满足关系的具体类型不能抛出。

合法载荷检查已在建立满足关系时完成，throw 不再重复执行，也不维护另一套数据类别
判断。根值形成、泛型转传、字段保存、函数返回和跨包消费必须维持同一证明，不能绕过
关系准入。

以下非载荷规则不变：表达式解析与非 void 要求、匿名 catch 中 `throw;` 的作用域、
defer 限制、控制流终止与可达性、try 表达式规则、异常清理和 C ABI 边界规则。
根 catch 是具名 catch，不自动取得匿名 catch 的 `throw;` 权限。

### 2.4 catch 的允许形式

- 具体类型 catch 保持具体描述符身份的精确匹配；泛型实例按完整实际类型区分。
- 允许 `catch error: <根 spec>`，将任意合法异常绑定为根契约值，供普通成员调用、
  保存和传递使用。
- 保留匿名 catch。除根以外，不开放中间 object-form spec、intersection-form、
  union-form 或 callable-form spec 的 catch。
- `catch error: E` 继续禁止；也不因本方案顺带开放仍含泛参的 catch 类型引用。

具体 catch 的可用载荷类别沿用异常规范。根 catch 与匿名 catch 的排序和重复诊断
见第 8 节；不以支持根 catch 为由增加运行时的 spec 满足集合查询。

### 2.5 泛型与实际异常身份

是否属于泛型类型不是载荷资格的否决条件。发码必须能取得实际闭合类型对应的
描述符，正确形成载荷，并使具体 catch 与之使用同一身份。

当前闭合泛型实例已经支持 throw/catch；共享体内静态类型仍为 `Error<T>` 的 throw
则被旧 Semantic 提前拒绝，旧 throw 描述符发码也不能直接视为已接通全部重化路径。
本方案需要补齐该通路，不能仅删除语义检查就宣称完成。

泛型共享体分别复用方法／函数隐式描述符和类型 owner 描述符中的既有重化信息，
覆盖引用类型及值类型。不得把具体异常身份替换成 E、泛型模板或根 spec 的身份。

## 3 根信息登记与唯一性

### 3.1 每次编译持有一个根信息记录

编译期状态保存 **spec 信息**，不是 bool。建议记录：

- 根声明的规范化身份；
- 可供语义检查和发码使用的声明引用／查询句柄；
- 所属模块及用于重复诊断的来源信息。

成员、父契约和类型信息通过该声明查询，不复制另一套成员模型。记录归当前分析
上下文所有，生命周期覆盖相关阶段；不使用跨编译任务共享的进程级静态变量。
LSP 重新分析时按当前源码与依赖重建记录，避免旧标记残留。

### 3.2 登记规则

| 状态与候选 | 处理 |
| --- | --- |
| 尚无根，遇到合法标注 | 保存 spec 信息 |
| 再次得到同一规范化声明 | 幂等复用；重复引用和菱形依赖不构成重复定义 |
| 遇到另一个被标注的声明 | 编译错误，指出两个根的模块与声明来源 |

同一源声明重复书写注解，与同一声明被重复导入是两件事；前者的写法规则待 Review。
短名称相同不表示同一声明，导入别名不同也不表示不同声明。跨文件符号引用可复用
既有模块身份与符号 ID 的组合，不能只比较裸 `symbol_id` 或跨进程指针。
源码、缓存及不同 profile 的来源覆盖先遵循既有规则，再归一化为当前声明身份。

登记范围为当前编译的源码及实际参与编译的依赖闭包，不扫描未参与编译的安装包。
根必须在契约资格与函数体检查前可用，结果不能依赖源码或 import 顺序。

### 3.3 复用已有加载流程

当前 `feng_symbol_provider_add_bundle` 会读取 `.fb/mod/` 下的全部公开 `.ft`；
Semantic 则只接入被引用及其签名依赖的外部模块。因此，不能仅在 Semantic 已接入
模块中发现根，否则会漏掉输入依赖中未被直接引用模块上的第二个标注。

建议在已有声明收集、符号读取与归一化流程中同步收集根候选／模块摘要，再通过
中立的导入查询接口交给编译上下文统一登记。每个候选只需与已有根比较，不额外
遍历所有包的所有类型。核心 Semantic 不依赖 `.ft` section、reader 或 zip 路径。

注册摘要是编译期索引，不是运行时反射表。根的声明与成员可按既有导入机制解析，
无需为查找一个根而合成所有依赖模块的 AST。

## 4 `.ft` 与跨包消费

### 4.1 必须保存定义标记

定义根的包必须将标注作为 spec 的声明事实写入 `.ft`。建议追加所属 spec 的
`ATRS` 属性，复用现有声明、父契约和成员记录；不序列化 AST 指针或 witness 地址。
具体属性编号在符号表主规范中分配。

链路需要完整覆盖：源码标记 → 归一化符号事实 → writer → reader → 查询视图 →
导入声明恢复 → 根登记。package-public 和 workspace-cache 均需保留相应事实，
复制、LSP 符号形状比较和跨平台公开事实比较不能丢失标记。

已有 spec 导出会调用 `apply_decl_annotations`，但导入 spec 分支当前没有调用
`synthesize_decl_annotations_from_symbol`。因此增加属性读写之外，还必须补齐
spec 注解恢复或等价的统一声明事实访问，不能产生源码与二进制包两种判断结果。

### 4.2 定义与引用分开处理

假设 A 定义异常根，B 和 C 依赖 A，应用依赖 B、C：

- A 的 `.ft` 保存根定义标记。
- B、C 按已有机制保存使用根的类型引用和契约关系，不重新定义根。
- 依赖管理层展开并去重传递依赖；编译上下文最终登记同一个 A 中的声明。
- 若另一个依赖 D 定义了不同根，必须报告冲突，不按加载先后选择其中之一。

当前公开表不保证收录私有根或私有模块。根的公开性必须按第 8 节决定：若允许
私有根，需要明确额外的分发元信息与必要声明保留方式，不能默默跳过其唯一性检查。

根标记恢复后，源包建立满足关系时的载荷资格与消费侧的类型事实必须一致。
跨包同样覆盖 type、fit、父契约闭包和泛型声明，不以 provider 源码可见为前提。

建议沿用已采用的 `.ft` 2.0 加完整重编策略，具体兼容声明在 Review 后写入主规范。
重编范围包括依赖包、consumer、符号缓存及相关生成制品；不默许混用旧异常规则下
生成的库，也不为旧 `E: throw` 元信息增加隐式兼容语义。

## 6 发码与异常传播：已知基础及待完成闭环

### 6.1 已核实的基础

| 当前代码事实 | 对方案的含义 |
| --- | --- |
| `FengCatchClause.type` 为具体描述符或 NULL；`feng_region_matches_exception` 只比较描述符身份或匹配 NULL | 具体 catch 可继续精确匹配；所有合法抛出值受根约束后，根 catch 的匹配选择可使用已有兜底能力 |
| `FengUnwindException` 保存 `value`、`desc` 和匹配子句，不保存 spec witness | 当前异常传播不能直接提供根 catch 所需的完整 spec 值 |
| object-form spec 值由 subject 与 witness 组成 | 只拿到具体异常对象，不足以调用根契约成员 |
| `cg_emit_try_expr_catch_binding` 当前按具体引用类型或 ValueBox 提取绑定 | 必须新增根视角绑定路径，不能把 subject 指针直接当作完整 spec 值 |
| `FengSpecCoercionDescriptor`、重化依赖和泛参描述符已支持共享体形成 spec 视角 | 可复用静态 witness、装箱信息与闭合类型描述符，不能宣称现有异常传播已经携带这些信息 |
| 现有 spec 默认值生成隐藏 subject 与默认 witness | 默认根值、子契约默认值投影也需纳入闭环，不能只覆盖用户手写的 type / fit |

代码依据：[运行时异常结构](../../src/runtime/feng_runtime.h)、
[异常匹配与清理](../../src/runtime/feng_exception.c)、
[spec 视角、throw 与 catch 发码](../../src/codegen/codegen.c)。

### 6.2 必须保留的信息与行为

完整发码方案必须说明以下信息从抛出端到捕获端的来源、存储和生命周期：

1. 真实 subject 或具体 ValueBox，以及对应的精确异常类型身份。
2. 抛出端选择的根 witness；来源可能是直接满足、可见 fit、父契约投影或已有根值。
3. 标量和值类型的装箱布局、偏移和复制／移动规则。
4. 根 catch 绑定的持有关系；绑定保存到 catch 外后继续有效，结束 catch 不使其悬空。
5. 匿名重抛和显式重新抛出根值后的具体身份、根成员行为及清理次数。

匹配根 catch 与恢复根值是两个阶段。把 catch 描述符写成 NULL 只能解决前者。
`.ft` 中保存根身份也只解决编译期识别，不能替代传播中的 witness 信息。
现有类型描述符没有通用的“满足哪些 spec”集合；其重化转换槽按具体使用点分配，
不能未经设计就把某个固定槽解释成全局异常根 witness。

### 6.3 实施边界

沿用当前任务边界：未获人工新决策前，不修改 runtime，不变更 ABI，不引入额外
运行时查询、分配或分派成本。现有载荷构造所需的复制、持有和装箱继续按原值模型执行。

**目前尚未证明完整根 witness 传播能在上述边界内闭环。** 后续应先给出可审查的
表示与发码方案；如需新增载体、改变异常 value / desc 的解释或改变描述符用途，
必须说明对协议、所有权和运行成本的影响，由人工决策。不能仅凭 C 签名和结构体
字段数量未变就认定 ABI 不变，也不能用未验证的动态映射或转换回调补洞。

本节不选择新的存储结构，不授权 runtime 或 ABI 变更。方案确认后至少先验证：
跨包 throw → 根 catch → 调用库声明的成员 → 保存到函数外 → 再抛出 → 具体 catch，
并覆盖共享泛型体、引用和值类型载荷以及嵌套异常清理。

## 7 `E: throw` 与现有代码的迁移

### 7.1 移除内建约束的专属部分

拟按当前讨论方向定向撤销 `E: throw`，普通 spec 泛型约束不是该特性的新增能力，
不随其撤销。具体执行及既有测试迁移清单需在 Review 后确认。

- 移除该专属约束语法、AST kind、语义分支、专属发码和 `.ft` 属性消费，同步
  dump、LSP、标准库 Parser 与规范；保留新方案仍需使用的通用值操作和描述符能力。
- 将有价值的泛型抛出、跨包、实际身份及所有权测试场景迁移到根 spec 方案，
  不通过删掉验证场景来完成回退。
- 原有不可抛载荷检查早于该功能存在：`359b9820` 已包含数组禁抛等规则，
  `a742bc20` 新增内建约束时复用了它们；这些载荷规则应按第 2 节保留和调整职责。
- `a742bc20` 同时包含标准库 `FengParser.nextToken` / `peekToken` 的 EOF 循环修复。
  该独立修复及相应验证必须保留，不能整笔撤销后遗漏。

历史交付文档 [throw 泛型约束方案](./feng-throw-generic-constraint-dev.md) 在实际迁移
完成后标注被本方案取代，保留历史验证事实，不提前宣称已回退。

### 7.2 标准库与调用方

当前 `std.Error` 是满足 `Display` 的具体 type；`FengCompileError` 也是具体 type。
标准库多处直接抛出 string，并有具体 string catch。新根规则落地后，这些类型必须
在对应可见范围建立合法根关系，或迁移为选定的异常类型，不能无条件沿用旧源码。

库层根声明、成员面与原有异常的适配策略由人工 Review。编译器不得为了兼容旧
用例而自动给类型添加满足关系、硬编码 std，或在缺少根时退回旧 throw 白名单。

统一根值应验证跨字段、容器和泛型返回的保存／再抛出能力。Future 可作为这种能力
的应用场景；本方案不顺带重设计 Future / Promise 的调度、状态机或公开 API。
