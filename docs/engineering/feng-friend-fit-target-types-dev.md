## 1. 目标与范围

第一阶段在现有具体 `type` 主体范围内支持泛型和跨包。第二阶段在其交付基础上，
将 friend 主体范围扩展到 [fit 主规范](../specifications/feng-fit.md) 及其引用的
[内建类型 fit 规范](../specifications/feng-fit-builtin-type.md) 支持的目标类别。
包括枚举、内建标量、`string`、数组等；完整范围以 fit 目标规则为准，本文不另外
维护一套独立类型清单。

本阶段仅扩展哪些类型能够成为 friend 主体，不增加新的 fit 目标类型或 fit
语法。fit 不支持的类型不能因为可作为泛型实参而自动获得 friend 资格。

泛型与跨包的基础能力由第一阶段交付；本阶段复用其编译期事实、类型身份、
检查条件和消费链路，不另建 friend 授权机制。`fit F` 继续使用 `F` 的身份，
现有成员访问规则及签名检查职责保持一致；新增主体的签名上下文按第 6 节完成 Review。

## 3. 目标行为示例

以下示例展示本阶段目标，尚未作为当前实现可通过的测试：

```feng
module demo.friend.fit_target;

/** 直接向 int 授权。 */
type DirectVault {
  @friend(int)
  seal var value: int = 7;
}

/** 通过泛参指定 friend 主体。 */
type GenericVault<F> {
  @friend(F)
  seal var value: int = 7;
}

/** 两种注解形式都由 int 的 fit 使用同一主体身份消费。 */
fit int {
  /** 消费直接注解的授权。 */
  func readDirect(vault: DirectVault): int {
    return vault.value;
  }

  /** 消费泛参代入后的授权。 */
  func readGeneric(vault: GenericVault<int>): int {
    return vault.value;
  }
}
```

上例中的 `int` 不是特例。其他 fit 支持的目标类别同样经统一主体准入处理，
内建别名及数组身份仍按所属类型规范归一化。

| 场景 | 本阶段目标 |
| --- | --- |
| 直接 `@friend(int)` 与 `@friend(F)` 代入 `int` | 都允许成为 friend 主体，授权身份一致 |
| 枚举、`string`、数组等合法 fit 目标作为 friend | 直接注解与泛参代入使用相同规则 |
| 当前 fit 目标身份与成员的 friend 身份不相等 | 拒绝 friend 授权 |
| 跨包或第三包中的合法 `fit F` | 使用 `F` 的 friend 身份，继续通过普通访问与签名检查 |
| 仅持有 `F` 的值、处于顶层函数或访问未授权成员 | 不因此取得 friend 权限 |

允许成为主体不等于跳过签名或普通访问检查。没有声明 module 的主体如何进行
声明期签名检查，属于第 6 节的待 Review 设计。

## 4. 编译器实施方案

### 4.1 统一主体准入与类型身份

在第一阶段统一的主体准入入口扩展支持类别，使直接具体类型和泛参代入结果
经过同一判定。精确身份匹配沿用现有语义类型归一化，不按名称字符串匹配，
不为某个内建类型单独增加授权特判。

具名类型、枚举、内建类型和数组各自的身份组成按所属主规范处理。内建别名按
目标平台归一化；数组元素、层级和可变性等身份信息不能在 friend 记录中丢失。
尚不能判定的开放条件继续随泛型绑定转传，在具化点完成检查。

### 4.2 签名检查

有声明 module 的主体继续沿用既有声明期检查；实际 fit 访问继续从 fit 声明
上下文检查签名。新增内建标量、数组等主体没有声明 module，其声明期检查条件
必须先完成设计确认，不能将缺少声明 module 静默解释为签名可用。

本阶段不把 friend 声明合法性统一推迟到成员访问点，也不改变已确认的开放条件
保留和具化检查机制。新增主体的具体诊断按批准后的规则落实。

### 4.3 制品与工具链

复用第一阶段的 friend 事实和检查条件表示，确保新增主体的类型身份、绑定与
签名检查上下文能够在 Symbol/`.ft` 写入、读取、校验和 import 恢复后完整保留。
具体格式适配遵循符号表主规范的兼容要求。

Codegen 与 LSP 继续消费同一 Semantic 授权结果，覆盖源码、缓存及跨包制品。
编译产物与运行时边界沿用第一阶段方案第 5.5 节：不增加运行时权限检查、分派层
或 runtime API；若确需增加运行时开销或调整私有 ABI，须另行提交人工决策。

## 5. 验证计划

| 验证层次 | 必须覆盖的内容 |
| --- | --- |
| Parser / Semantic | 新增主体的直接注解、泛参代入、别名与重复项；仍不支持的主体；诊断码、位置与身份归一化 |
| 授权精确性 | 正确和错误主体；不同内建、枚举和数组身份；本包、跨包及第三包 fit；顶层与未授权成员拒绝 |
| 泛型与签名 | 开放条件保留和转传、具化点检查；具名主体既有签名行为；新增主体按批准规则验证声明期和 fit 访问点诊断 |
| Symbol | 两种 profile 往返、完整类型身份和检查条件恢复、畸形记录拒绝与缓存一致性 |
| Codegen / LSP | 新增主体消费已授权成员的生成代码，以及源码和导入路径的补全、Hover、定义跳转一致性 |
| FCTS | 各类新增主体的语言行为；仅依赖 `.fb` 的跨包消费；直接注解和泛参代入行为一致 |

编译器诊断、AST、IR 等用例放在 `test/`，语言行为用例放在 `fcts/`。既有测试
调整包含原有内建/数组负例，以及第一阶段新增的相应具化拒绝用例；只在批准范围
内改变这些预期，不能删除身份不匹配、不可见签名等仍有意义的负例覆盖。
