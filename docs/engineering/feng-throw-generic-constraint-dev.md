# Feng `throw` 泛型约束开发方案

> **状态**：已完成实施与验证；最终沙箱外 `make test` 的 UBSan、普通构建两轮全量回归均通过。
>
> **日期**：2026-09-18。
>
> **已确认需求**：保留 `throw` 的现有用法，新增 `throw` 作为泛型约束的用法；此次新增用法仅允许出现在泛型约束位置，不增加 `throwable` 关键字，不将 `throw` 定义为普通类型。
>
> **交付边界**：语言规则已收敛到主规范；本文记录实施方案、问题处理与验证结果。`.ft` 保持 2.0，按确认的边界重编制品；runtime 与 ABI 未变更。

## 1 目的与范围

本次变更前，异常规则允许一组具体静态类型作为异常载荷，但拒绝直接泛型类型参数和仍含开放泛参的类型。泛型函数因此无法仅凭参数 `E` 证明 `throw error` 合法。

本次通过内建约束 `E: throw` 表达：E 的实际类型必须满足现有可抛类型规则，泛型声明体可以依据这项保证抛出 E 的值。

语言规则的归属：

- 泛型声明、推导、转传、重载及跨包约束事实，以 [泛型主规范](../specifications/feng-generics-draft.md) 为准。
- 可抛具体类型集合、具体类型 catch 匹配、异常载荷所有权和原样重抛，以 [异常主规范](../specifications/feng-exception.md) 为准。
- 本文只描述新增能力的接入方式，不复制维护另一份可抛类型清单。

本次不包含异步机制、Future 异常存储、异常容器、动态异常类型匹配，也不替换现有异常展开机制。

## 2 语法边界

### 2.1 唯一新增位置

在泛型参数声明列表中，类型参数名称之后的约束位置允许使用 `throw`：

```text
TypeParameter := Identifier [ ':' Constraint ]
Constraint    := ExistingSpecConstraint | 'throw'
```

其中 `ExistingSpecConstraint` 表示既有的 spec 约束形式，不借此放宽其他类型作为约束的规则。现有每个泛参至多一个约束的规则保持不变，不新增组合约束语法。

```feng
// E 的实际类型必须能够作为异常载荷。
func raise<E: throw>(error: E) {
    throw error;
}

// 类型上的约束同样可以证明成员中的 E 可被抛出。
type Failure<E: throw> {
    let error: E;

    func raise() {
        throw self.error;
    }
}
```

该约束适用于现有已允许声明泛型参数的入口，不额外开放泛型声明位置。例如，既有对 object-form spec 方法级泛型参数的限制不因本次变更放宽。

### 2.2 保留现有用法

- `throw expr` 继续表示抛出异常值。
- 匿名 catch 中的 `throw;` 继续按已有作用域规则原样重抛。
- 既有语句分号、控制流终止及 defer 内的限制不变。

`E: throw` 是类型能力约束，不表示函数一定会抛异常，也不是函数的异常效果声明。

### 2.3 不允许的新位置

`throw` 不是可声明变量的值类型，不是可实例化类型，不是用户 spec，也不是表示任意异常值的联合类型。以下形式均不属于本次允许的语法：

```feng
let error: throw;                       // 不能用作变量类型
type Holder { let error: throw; }       // 不能用作字段类型
func consume(error: throw) {}           // 不能用作参数类型
func produce(): throw {}                // 不能用作返回类型
let value = Box<throw>();               // 不能用作泛型类型实参
spec Errors: throw | string;            // 不能用作联合成员
spec Throwable: throw {}                // 不能用作父 spec
try work() catch error: throw {}        // 不能用作 catch 类型
func invalid<throw>() {}                // 不能用作类型参数名称
```

这些示例仅展示应拒绝的位置，示例中的其他名称不构成本次类型或 API 定义。

## 3 约束检查与转传

### 3.1 闭合实参

显式类型实参和调用点推导得到的类型，都必须在 Semantic 阶段满足现有可抛具体类型规则。约束不扩大该集合，也不根据值的运行时内容猜测具体类型。

例如，字符串可以作为满足该约束的实参；数组、pointer、spec 等是否允许，直接复用异常主规范中的分类，不另建一份约束专用白名单。

即使某个 union 的各成员都可抛，union 自身仍是 spec；不能因成员可抛而自动把整个 union 判为满足 `throw` 约束。

### 3.2 开放泛参的证明

泛型声明体按声明的约束检查，不能依赖以后出现的具体调用点来补充能力。

```feng
// 约束随同一个类型参数继续传递。
func forward<E: throw>(error: E) {
    raise<E>(error);
}

// 无约束 E 无法证明符合目标要求，应在当前声明处拒绝。
func invalidForward<E>(error: E) {
    raise<E>(error);
}

// 无约束泛参仍不能直接抛出。
func invalidRaise<E>(error: E) {
    throw error;
}
```

约束证明应按泛参身份传递，不依赖参数名称是否相同。向不要求可抛能力的普通泛型参数传值，继续采用既有规则。

普通 spec 约束不自动获得可抛保证。`E: throw` 也不自动提供成员访问、比较、构造或 C ABI 兼容等其他能力。

### 3.3 保留实际类型

执行泛型 `throw error` 时，异常仍携带 E 对应的实际具体类型和值。不能把异常类型改成 `throw`、泛参名称、某个公共包装类型或约束本身。

已有具体类型 catch 仍按异常主规范精确匹配。约束不同不构成新的泛型重载身份；候选推导、约束筛选和诊断遵循现有泛型流程。

本次新增的是约束语法及其对直接泛参 throw 的证明能力。泛型 catch 与其他开放类型的既有限制见第 6 节。

## 5 实现要求

### 5.1 约束表示与解析

应将泛型约束作为独立语义概念，区分“spec 类型引用”与“内建可抛能力”，避免创建名为 `throw` 的伪类型来绕过名称解析。

对 `throw` token 的新增接纳必须限定在泛型约束解析入口，不修改通用类型解析使其在字段、实参或 catch 类型位置合法。

AST 的创建、复制、释放、遍历、打印与序列化须同步保留约束种类；具体数据结构在实现设计时明确，不在本文固定 C 字段布局。

### 5.2 语义与诊断

`E: throw` 的编译期检查分为三处：

1. **调用或实例化时**：检查实际类型是否可抛。
2. **泛型体中**：根据约束允许 `throw error`。
3. **泛型转传时**：检查来源约束是否足够。

- 上述检查覆盖显式类型实参、调用推导及重载候选筛选，非法实参不能延后到 Codegen 才失败。
- 为受约束泛参保留可抛能力证明；不得通过一律允许开放泛型来实现此功能。
- 实参的具体载荷分类复用现有异常规则，不能因“泛型调用”而改变同一个具体类型的可抛性。
- 在异常语句检查中，仅 throw 路径可依据直接泛参的可抛证明放行；typed catch 保持具体载荷分类，不因共享分类函数变更而获得泛型支持。
- 保留 `throw;` 的匿名 catch 作用域检查与 defer 限制。
- 诊断应区分非法语法位置、实参不满足约束，以及泛型体缺少可抛能力；具体诊断码实施时按错误码规范登记，不在本文虚构编号。

### 5.3 发码与运行时边界

仅让语义检查通过不足以交付该功能。共享泛型体必须能够取得实际类型描述信息、构造与普通具体 throw 一致的异常载荷，并保持值的复制、持有和释放规则。

不得以 provider 源码可见、全量单态化或同包优化为功能成立的前提；应覆盖仅通过 `.fb` 使用公开泛型声明的情况。

约束判定只在编译期完成，不增加运行时约束查询。本次禁止修改 runtime 实现，禁止变更 ABI，包括私有 runtime ABI、泛型共享实现的调用约定及运行时描述符布局。编译器发码必须复用既有泛型重化、异常表示与调用接口，不增加额外运行时开销。

保留具体异常类型匹配及 C ABI 异常边界。不能将 `E: throw` 理解为允许异常越过 C ABI，或允许 E 构成原本不合法的开放指针。

#### 当前代码核查结论

**“构造成异常载荷”可复用既有通路，不需要修改 runtime 或 ABI。** 类型级泛参和函数／方法级泛参均已有描述符来源；既有代码已具备具体异常载荷的装箱布局、分配、复制和释放能力。本次已补齐内建约束的静态信息绑定及泛型 throw 发码，并通过第 11 节的验证。

#### 编译器接入要求

泛参描述符的 `descriptor` 指向与 `kind` 对应的原值描述符；对值类型而言，它不是异常所需的 box 描述符，不能统一强转为 `FengTypeDescriptor *` 后直接抛出。所需信息可在现有表示内接入：

1. **闭合处绑定静态装箱信息**：对满足 `throw` 约束的值类型，复用具体类型的 box 符号和布局，将已有 `FengSpecCoercionDescriptor` 的 `box_descriptor`、`payload_offset` 填为编译期确定的值，其内部 spec `witness` 置空；通过泛参描述符既有的 `witness` 槽引用该静态记录。泛参的 `kind`、`descriptor` 继续描述原值，不改变复制与释放依据。约束种类决定编译器如何使用该槽，既有 spec 约束的解释不变，也不把 `throw` 建模为 spec。
2. **共享体形成载荷**：引用类型从泛参存储中取出原托管指针，按所有权状态持有或转移，并使用原类型描述符；值类型按静态装箱信息分配一次既有 `ValueBox<T>`，在载荷偏移处按原值描述符完成字节复制或聚合复制／转移，再将该 box 及其具体描述符传给 `feng_throw`。表达式只求值一次，临时值清理与所有权转移沿用现有规则。
3. **沿用传递与导出链路**：闭合泛参描述符继续由 `cg_closed_generic_param_descriptor_expr` 生成静态常量；同约束开放泛参转传继续传递已有描述符，类型级泛参继续保存在 owner 描述符上。消费侧根据导入的内建约束事实执行同样的闭合绑定，无需新增共享体隐式参数或描述符字段。

上述装箱信息只指导已通过编译期检查的值如何形成载荷，不承担运行时可抛性判断，也不引入转换回调、描述符搜索、逐次元数据构造或额外装箱。共享体读取描述符并执行必要的复制／持有属于该语句的发码，不能表述为完全没有执行成本。异常必须复用普通具体 throw 使用的描述符身份，不能另建公共异常 box 或克隆描述符，否则会破坏既有精确 catch。

当前 `cg_emit_throw` 已接入直接泛参，共享装箱信息与泛型值操作逻辑；同包、跨包及全量回归结果见第 11 节。

### 5.4 跨包与兼容性

现有泛型约束已经通过 `.ft` 导出。本次沿用该链路，仅补充内建 `throw` 约束的表示、导出、导入和文本重建，使消费侧能够执行同样的编译期约束检查。约束事实必须区分 spec 约束与内建约束，不能在消费侧丢弃为无约束泛参，也不能把 `throw` 按普通类型名解析。

约束事实的编码遵循 [符号表主规范](../specifications/feng-symbol-table.md)，既有 spec 约束及无约束泛型的语义与表示保持兼容。本次不新增包分发机制，不将包格式升级作为实施前提。

## 6 已确认的支持边界

本次仅增加直接泛参的可抛约束，不扩展以下既有语言边界：

- **泛型 catch**：`catch ex: E` 继续禁止，即使 E 声明了 `throw` 约束也不例外。typed catch 继续要求现有规则允许的具体类型；`catch ex: throw` 始终不合法。
- **含开放泛参的复合类型**：`Box<E>` 等在当前可用替换后仍含开放泛参的类型继续按现有异常规则拒绝，不因 E 带有 `throw` 约束而放行。闭合实例仍按现有具体载荷规则检查。

runtime 与 ABI 的硬边界及发码核查要求见第 5.3 节；既有 `.ft` 约束链路的同步范围见第 5.4 节。

## 7 规范更新与实施顺序

1. 更新 [泛型主规范](../specifications/feng-generics-draft.md)：在现有 spec 约束之外增加内建 `throw` 约束，定义限定位置、准入与转传；收敛“约束只能为 spec”的原有表述。
2. 更新 [异常主规范](../specifications/feng-exception.md)：明确有可抛约束的直接泛参可用于 throw，保留无约束泛参与不合法载荷的限制，并落实第 6 节的既有边界；将 throw 与 typed catch 的共同准入规则明确限定于具体载荷类型。
3. 在 [符号表主规范](../specifications/feng-symbol-table.md) 中补充既有泛型约束链路对内建约束的记录与恢复要求。
4. 按实际新增诊断更新错误码规范；相关总览仅引用主规范，不复制规则。
5. 按第 5.3 节已核实的通路及硬边界，实施约束表示、解析、语义、泛型发码及跨包约束同步。
6. 新增编译器测试和语言行为测试，完成全量回归。

实施按上述顺序更新正式规范、实现并新增测试。既有测试若需调整，应先列出具体清单取得批准。
