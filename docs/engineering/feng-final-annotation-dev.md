# Feng `@final` 注解开发方案

> **状态**：待 Review，尚未实施。
>
> **日期**：2026-09-18。
>
> **已确认边界**：`@final` 仅用于 object-form `spec`；定义 object-form `spec`
> 时，在编译期检查其全部直接父 `spec`，禁止以带 `@final` 的声明作为父契约。
> 其他语言行为和实现逻辑保持不变。本特性独立于异常重构。

## 1 目标与规范归属

允许契约作者表达“该 object-form `spec` 不能再有子 `spec`”，同时继续允许具体
类型按现有规则满足该契约。`@final` 不改变成员定义、满足关系、可见性或值表示。

## 2 已确认的语义边界

### 2.1 适用声明

`@final` 仅可标注 object-form `spec` 声明，包括既有规则允许的泛型 object-form
`spec`。不增加公开性、所在包、模块名或成员集合方面的限制。

callable-form、union-form、intersection-form `spec`，以及 `type`、`enum`、
`fit`、函数、绑定和成员声明均不能使用该注解。非法位置由注解适用域检查诊断，
不通过修改这些声明的语义来解释 `@final`。

### 2.2 父契约检查

在 object-form `spec` 声明的父列表检查中，按现有名称解析、可见性和泛型实参
检查结果，逐项取得直接父契约的声明；其中任何一个带有 `@final`，该父关系即非法。

以下片段展示声明边界，其他成员和满足检查仍按现有规则执行：

```feng
spec Base {}
spec Other {}

@final
spec Closed: Base {}              // 允许：final spec 自身可以有非 final 父契约。

spec Invalid: Other, Closed {}    // 拒绝：必须检查列表中的每个父契约。

type Value: Closed {}             // 允许：具体类型满足契约不受 final 限制。

func accept<T: Closed>(value: T) {} // 允许：仍可用作泛型约束。
```

泛型父引用按其声明判断，不能通过实例化绕过限制：

```feng
@final
spec Slot<T> {
  let value: T;
}

spec IntSlot: Slot<int> {}        // 拒绝：父契约声明 Slot 带有 @final。
```

判定不能依赖文件顺序、声明顺序、短名称或导入别名。父声明先于或后于子声明、
位于同文件、同包其他文件或外部包时，规则一致。

这里只增加对直接父列表的检查，不增加一次递归祖先检查。若 `A` 是 final，
`B: A` 已在定义 `B` 时被拒绝，因此合法声明不能再经由 `B` 间接派生 `A`。
现有循环父关系检查保持原样。

### 2.3 保持现有行为

具体 `type` 满足、`fit` 适配、泛型约束、spec 值形成与成员访问，以及其他形态
`spec` 对该契约的合法引用，都继续遵守各自主规范。不能把父契约位置的限制扩展
到这些使用位置，也不新增 union / intersection 组合限制。

`@final` 不改变布局、witness、类型描述符、代码生成、runtime 或任何 ABI，
不增加运行时检查，也不引入运行时的 final 属性。它与未来 `@throwable` 的识别、
登记、唯一性和异常处理规则互不依赖；本方案不实施任何异常重构。

## 3 待 Review 的注解写法细节

以下细节尚未由前述语义边界决定，本文提出建议，实施前需人工确认：

- **参数**：建议作为无参数标记；`@final` 与 `@final()` 等价，传入实际参数时报错。
  空括号由现有注解 Parser 接受，无需为本注解增加语法分支。
- **重复标注**：建议同一声明重复写 `@final` 时报错。此建议只定义该注解的规则，
  不修改其他内建注解的重复处理行为。

## 4 基于现有代码的实施方式

### 4.1 识别与语义检查

| 接入点 | 当前能力与拟议变更 |
| --- | --- |
| `src/lexer/token.h` 的内建注解表与枚举 | 登记 `final`；沿用注解 token，不增加 `final` 关键字或保留字 |
| `src/parser/parser.c` 的 `parse_annotations` | 已保留注解名称、kind 和参数；复用通用解析及 AST 注解数组 |
| `src/semantic/analyzer.c` 的声明、成员注解验证 | 检查目标必须是 object-form `spec`；落实 Review 后的参数及重复规则 |
| 同文件 `validate_spec_parent_spec_list` | 在已有解析成功、目标为 object-form `spec` 的检查后，判断父声明的 final 事实 |
| `src/cli/lsp/lsp_annotations.h` | 在现有内建注解清单中补充 `final` 及含义 |

final 事实应通过一致的声明查询获得。源码 AST 与导入 AST 使用同一检查路径，
不按来源、包名或标准库名称分支。父声明即使尚未执行自身声明体检查，其解析后
AST 上的标记也应可查询，避免引入先检查父声明的顺序依赖。

复用已有的失败类型引用处理：解析、可见性或实参数量已失败时，不追加依赖该
失败结果的 final 诊断；不改变其他独立错误的报告规则。

### 4.2 `.ft` 导出与恢复

final 会影响 consumer 是否允许定义子契约，因此必须成为可跨包恢复的声明事实。
只在生产包的 AST 中保留注解不足以实现本特性。

建议沿用现有附加声明属性机制：

1. 符号声明视图增加归一化 final 事实；`export.c` 从已验证声明提取。
2. 在现有 `ATRS` 中追加一个属于 object-form `spec` 的 final 属性，绑定所属
   `symbol_id`，不修改 `SYMS` 固定布局。具体 key 在符号表主规范统一分配。
3. writer / reader 保留该属性并校验其 owner；符号图复制、查询及比较路径同步保留。
4. `imported_module.c` 从归一化事实恢复 spec AST 的注解，使父列表检查可以复用。
5. package-public 与 workspace-cache 两种 profile 均保留已收录声明的 final 事实。
   不因 final 标记扩大私有声明导出集合，也不改变声明可见性。

已核实的接入细节：`export.c` 的 spec 分支已经调用 `apply_decl_annotations`，
可以扩展该归一化入口；但 `imported_module.c` 的 spec 分支目前没有调用
`synthesize_decl_annotations_from_symbol`，因此必须补上 spec 注解恢复，不能仅
增加属性的读写就认为跨包链路已经完成。

本次增加的是编译期符号事实，和运行时 ABI 是两个层面。制品策略建议延续当前
开发阶段的 `.ft` 2.0 加重编方式，重建 provider、consumer 及缓存，不提供旧编译器
正确消费新 final 属性的承诺；该兼容策略需在 Review 时确认，并写入符号表主规范。

### 4.3 诊断

区分“注解用在非法位置”与“以 final spec 作为父契约”两类根因，分别归入注解段
和 Spec 段。参数与重复诊断随第 3 节的 Review 结论确定。具体编号先检索已有错误码，
按错误码规范完成归属和 Review 后再使用，本文不提前占号。

父关系错误定位到子声明中对应的父类型引用，并指出子契约和被禁止作为父契约的
final spec。外部包诊断使用可获得的模块和声明身份，不要求公开 `.ft` 携带源码路径。

## 5 验证范围

`test/` 验证 AST、诊断和符号事实，`fcts/` 验证语言行为。新增用例不修改既有
用例；若实施中发现必须调整既有用例，先记录原因并取得人工批准。

| 维度 | 必须覆盖的情形 |
| --- | --- |
| 注解识别 | 无参形式、AST kind 和参数保留、LSP 内建注解清单；参数及重复结果按 Review 结论验证 |
| 适用位置 | 普通及泛型 object-form spec 通过；其他 spec 形态、其他声明及成员位置拒绝 |
| 父列表 | 单父、多父中不同位置的 final 父、泛型父实例化、子声明自身也标注 final |
| 顺序与身份 | 前向声明、交换文件输入顺序、跨文件、跨模块、限定名与导入别名、不同模块的同名 spec |
| 现有诊断 | 未知父类型、错误父形态、实参数量错误、重复父引用、循环父关系仍遵循现有规则 |
| 正向行为 | final spec 继承非 final 父、具体 type 满足、fit 满足、泛型约束、spec 值与成员调用 |
| 其他 spec 形态 | 原本合法的 union / intersection 使用继续合法；不将其引用解释成新禁止的父关系 |
| 符号往返 | 两种 `.ft` profile 的属性写入、恢复、查询；无标记声明；非法 owner 等格式校验 |
| 二进制消费 | provider 源码不可用、仅 `.fb` / `.ft` 可用时，子 spec 被拒绝而 type / fit 使用通过 |
| 缓存与工具 | 重建缓存后保留标记；源码或导入 AST 查询结果一致；多平台公开事实比较保留标记 |

合法程序的代码生成继续走原有路径；选择已有成员和 witness 行为建立新增正向用例，
验证 final 标记没有引入新的运行时表示或调用路径，无需为本特性增加运行时机制。
