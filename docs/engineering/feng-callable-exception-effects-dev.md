## 2 N08：展开期间 defer 再次抛出且逃逸

### 2.1 复现形态

```feng
module n08_example;

/** 用 code 区分原异常与清理异常。 */
type Error { let code: int; }

/** 向调用方抛出独立异常。 */
func fail(code: int): void { throw Error { code: code }; }

/** 原异常退出函数时，defer 调用再次抛出且没有内部处理。 */
func work(): void {
    defer { fail(2); }
    fail(1);
}

/** 当前实现会在进入该 catch 之前因清理链损坏而终止。 */
func main(args: string[]): void {
    try work() catch error: Error {
        // 这里最终应如何处理，取决于后续审定的 defer 异常逃逸规则。
    }
}
```

异常 A（`code == 1`）触发 `work()` 的栈展开；清理过程中执行 defer，异常 B
（`code == 2`）又启动一次向外展开。当前 runtime 在 personality 回调中执行函数
清理，因此第二次 throw 时，第一次 throw 及其 unwinder 仍在物理调用栈上。

LLDB 确认的关键调用顺序为：

```text
feng_throw(B)
  → fail(2)
  → defer 生成函数
  → __feng_personality_v0
  → unwind_phase2 / _Unwind_RaiseException(A)
  → feng_throw(A) / fail(1)
  → work()
  → 调用方
```

现有 `feng_cleanup_release_to_frame_marker` 按清理链顺序移除一个 function marker，
没有记录哪些 native frame 已在第一次展开中清理。第二次展开再次经过这些帧时，
会错误移除外层 try 边界，最终报告边界不在清理链上。仅忽略缺失边界不能修复资源
归属，也没有解决被中断的原异常记录应由谁持有和释放的问题。

## 4 设计方向与审定状态

### 4.1 记录 callable 可能向外传播的异常

分析对象是未被 callable 内部完整处理的异常。函数内部出现 throw，但该异常已被
内部 catch 完整处理，则不计入该 callable 的对外异常摘要。

后续摘要应能表达已知的可能异常类型、依赖泛参的异常信息及无法静态确定的部分。
已证明没有逃逸异常与尚无足够信息需要明确区分；具体数据结构由后续方案确定。

分析需要覆盖直接 throw、匿名重抛、调用链、递归、catch 内再次抛出、defer 调用，
以及函数、方法、构造函数、Lambda 等 callable 边界。异常身份和 catch 覆盖范围
复用主规范，避免另建一套类型匹配规则。

#### 4.1.1 泛型异常摘要与调用点替换

阶段一必须正确记录开放泛参，并在调用点按已经解析的类型实参代入异常摘要。
泛参引用需要保留所属声明及参数身份；仅保存名称 `T` 不足以区分不同声明中的同名
泛参，也不能将类型级与函数／方法级参数混为一个绑定域。

声明处保留参数化摘要，调用处取得替换后的摘要；调用处仍然开放时，继续映射到
调用者的泛参，直到具体使用点闭合。以下为摘要示意，不是新增 `throws` 语法：

| 场景 | 必须取得的摘要 |
| --- | --- |
| `raise<T: throw>` 直接抛出 T 的值 | `{T}`，其中 T 属于 `raise` 的声明 |
| `relay<U: throw>` 调用 `raise<U>` | `{U}`，已转换为调用者 `relay` 的参数身份 |
| 调用 `relay<MyError>` | `{MyError}`，LSP 与调用者分析均使用该具体身份 |
| 方法摘要同时依赖 owner 参数 T 和方法参数 U | 同时使用接收者类型实参与方法实参替换，不能遗漏任一绑定域 |

显式实参与推导实参必须得到一致结果。同一共享体可以在不同调用点产生不同的
异常摘要；替换不得修改声明处的通用摘要或污染其他调用点。开放泛参是有身份的
符号信息，不能仅因尚未闭合就退化成未知；能由已解析实参确定的类型必须准确还原。
该过程属于编译期分析，不需要为异常提示单态化函数体或读取运行时描述符。

捕获覆盖也可能依赖代入结果。例如泛型函数可能接收到类型 T 的异常，在内部仅
捕获 `IoError`，且处理代码不再抛出：T 为 `IoError` 时逃逸集合为空，T 为
`StateError` 时仍有 `{StateError}`。摘要必须保留这类依赖，待替换后正确求值；
不能在开放阶段丢掉捕获条件，之后只做类型名称替换。条件的具体表示及归约方式
在阶段一方案中审定，并与 FT 编码一并设计。

现有 [语义替换实现](../../src/semantic/analyzer.c) 的
`callable_type_bindings_init` / `substitute_type_ref_for_callable_instance`
已经联合处理 owner 与 callable 参数，可作为复用基础；这不表示异常摘要已经实现。

#### 4.1.2 建议的摘要模型（待 Review）

建议采用“声明处的参数化异常摘要 + 调用点代入求值”。以下是待 Review 的实现
建议，具体节点布局、归约算法和 FT 记录格式尚未定稿，不增加用户必须填写的语法。

**声明摘要与调用点结果分开保存。** 声明摘要引用真实类型、泛参和 callable 身份，
保持只读；调用点使用 owner／callable 实参及已知调用目标求值，得到具体类型集合、
仍然开放的依赖及未知部分。已证明为空可作为统一查询结果，不再独立维护另一套
`mayThrow` 事实。编译过程中的“尚未完成分析”须与最终的“合法但静态未知”分开，
不能在递归尚未收敛时作出无异常结论或发布最终提示。

**摘要保留必要的结构。** 建议至少支持以下含义；它们是编译期表示，不是 Feng 语法：

| 摘要组成 | 作用 |
| --- | --- |
| 空集合 | 已证明没有异常逃逸 |
| 类型项 | 具体异常类型或带声明身份的开放类型表达式 |
| 合并 | 汇总可能执行路径和调用产生的异常 |
| 调用依赖 | 记录被调用目标及其参数绑定，或对 callable 参数／spec 方法的调用依赖 |
| 捕获筛选与条件 | 按精确类型和子句顺序得到被捕获及剩余异常；仅在处理分支可能执行时计入该分支的异常 |
| 未知项 | 表示无法静态确定的异常来源，保留原因供诊断；不能冒充空集合 |

例如，原异常类型为 T，仅捕获 `IoError`，且该 catch 改为抛出 `LogError`。
代入 T 为 `IoError` 后，逃逸集合应为 `{LogError}`；代入 `StateError` 后，应为
`{StateError}`。摘要既要保留“移除已捕获异常”的条件，也要保留“何时执行 catch
处理代码”的条件。一般值条件不能静态判定时保守合并可能路径，类型条件能判定时
应归约，不把两种情况都无条件记录成 `{T, LogError}`。

**间接调用与 callable 值分开建模。** 能解析具体目标时使用该目标摘要；目标由
callable 参数或泛型约束决定时，保留相应依赖，在调用点能继续解析时求值；动态
目标无法确定时保留未知。创建、传递或返回 callable 值，与执行该 callable 是
不同事件：工厂返回一个会抛异常的闭包，不等于工厂本次调用会抛出闭包内的异常。
返回值或捕获环境中需要继续传递的调用依赖，必须纳入跨包摘要设计。

**递归使用依赖图和固定点求解。** 建议按调用依赖的强连通分量计算，以工作队列
传播变化，复用规范化摘要节点，避免逐调用展开整条链或每次重新扫描全项目。
实现前须说明参数化递归的终止与有限化规则；需要扩大为保守上界时必须保留其原因，
不能把达到迭代上限当成已证明安全，也不能将本可确定的普通泛型调用随意降为未知。

**诊断保留来源，格式化与证明共用结果。** 同一份求值结果供 FT、LSP、`@abi` 和
后续 defer 检查使用；集合按身份去重，来源位置作为相关信息保留。这样既能显示
可能的类型，也能解释“通过哪次调用传播”或“为何仍无法证明为空”。

### 4.2 跨包 FT 与间接调用

可跨包调用的 callable 需要导出异常摘要；私有辅助 callable 对外部的影响汇总到
导出的调用者，不要求为了该分析额外公开私有实现。

FT 导入方在看不到源码时仍需取得摘要。缺失或无法确定的信息应在分析模型中保留，
不能解释为“没有异常”。具体字段、兼容校验、缓存失效及重编要求留待 FT 方案 Review；
本次嵌套 catch 修复不改 FT。

callable-form spec、object-form spec 方法及泛型约束调用，需要明确声明契约、
实现方法和动态实际目标之间的异常信息关系。仅给每个具体函数增加一个标志不能
覆盖这些调用入口。

阶段一的跨包支持是交付必需项，不能留到阶段二：

- 生产包导出完整的参数化异常摘要，包括具体类型身份、泛参所属关系、必要的捕获条件及未知信息；消费包导入后按 §4.1.1 继续替换和分析。
- 泛参及具体异常必须按声明身份恢复，覆盖 owner／callable 参数、多模块同名类型、导入别名和多层依赖转传，不依赖字符串短名猜测。
- 消费者在依赖源码不可见、仅有正常发布包产物时仍须得到与源码分析一致的摘要和 LSP 提示；不能以读取依赖源码弥补 FT 缺失的信息。
- 缺失、不兼容、损坏或过期摘要必须按审定方案诊断、失效或保留未知，不能解释为空集合；正常构建的完整摘要不得无故降级为未知。
- 验证发布用 FT 与 workspace 缓存路径；LSP 对本地缓存的可选性仍遵循 [LSP 已交付方案](./feng-lsp-delivered.md)，不要求用户先手动构建当前项目才能获得提示。

现有 [FT 类型记录](../../src/symbol/ft_internal.h) 的 `TYPE_PARAM_REF` 含泛参
符号引用，[symbol 类型视图](../../src/symbol/internal.h) 也保存 `target_decl`。
这些是跨包恢复身份的已有基础；仍需增加异常摘要自身的读写、恢复与完整性验证。

对应 §4.1.2，建议增加专门的异常摘要记录，复用既有类型表与符号身份；保存摘要
节点、调用依赖、泛参绑定和捕获条件，消费端使用相同求值器。摘要引用的私有依赖
须保持原可见性，不因进入元数据就成为公开 API。FT 版本沿用此前确认的不升级、
重编方式；具体记录格式、必需信息校验及旧产物失效处理仍在阶段一方案中细化。

### 4.3 用于 N08 处理及异常信息提示

2026-09-21 人工确认以下提示方式和严格边界检查原则。语言规则的正式变更仍按
各阶段 Todo 更新到对应主规范，本文记录决策及实施边界。

#### 4.3.1 LSP 提示方式（已确认，阶段一）

- 函数／方法 Hover 展示异常摘要；泛型声明保留参数化信息，具体调用目标使用代入后的结果，未知部分明确标示。
- 调用处对仍可能向外传播、未被当前捕获范围完整处理的异常给出 Information 级提示。
- 提示表达“异常仍可能向外传播”；普通调用不因缺少 catch、存在已知异常或未知部分而编译失败。已经完整处理的部分不再作为未处理异常提示。
- 提示与严格边界的编译错误共用语义结果；具体文本、定位、相关位置与缓存更新纳入阶段一实现及协议测试。

将来是否增加强制显式处理要求属于独立后续议题，不纳入本次实施。

#### 4.3.2 严格边界的证明要求（已确认，分阶段实施）

只有能够证明相应边界的逃逸异常集合为空，才允许通过；存在已知异常、未能消除
的开放条件或未知部分，均不能视为已证明安全。判断必须在摘要求解和内部捕获处理
完成后进行，不能把调用前的摘要直接当成边界最终结果。

| 边界 | 检查范围 | 无法证明为空时 |
| --- | --- | --- |
| 普通 callable | 对外传播信息，不增加必须处理要求 | 按 §4.3.1 提示，允许继续传播 |
| `@abi` callable，阶段一 | 该 callable 向 C ABI 边界逃逸的异常 | 编译期报错，LSP 显示同一错误 |
| defer，阶段二 | defer 块自身向外逃逸的异常 | 编译期报错，LSP 显示同一错误 |

未知来源可以由边界内部的兜底 catch 完整处理；如果处理代码本身也没有逃逸异常，
最终集合可以为空，因此“调用目标未知”不等于该边界必然报错。相反，只捕获部分
类型、处理代码再次传播异常，或仅由边界外的 catch 处理，都不能证明该边界安全。
现有 defer 直接 `throw` 语句禁令按主规范保留，不因增加摘要分析而放宽。

阶段一迁移 `@abi` 检查时，应记录新增诊断及其依据；这可能使过去因分析不完整而
接受的代码被拒绝，不能通过将未知当作不抛异常来规避。C ABI `extern func` 等已有
契约明确的入口仍按主规范分类，不能仅因缺少函数体而一律归为未知。

异常摘要与 LSP 提示属于阶段一；defer 异常逃逸检查属于阶段二。阶段一保持现行
defer 规则，N08 用例继续完整注释保留，阶段一的全量回归通过不表示 N08 已修复。

优先在编译期完成分析及信息传递。若 N08 的最终方案仍需要 runtime／ABI 修改或
增加运行时开销，需先列明具体协议与成本，单独通过人工 Review。
