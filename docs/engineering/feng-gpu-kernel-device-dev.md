# Feng GPU `@kernel` / `@device` 开发方案

> **状态：待人工 Review，尚未实施。日期：2026-10-20。**
>
> 已确认采用混合文件：继续使用 `.ff`，普通函数默认 host，通过 `@kernel`、
> `@device` 标记设备函数。本次仅形成开发方案，不修改编译器、runtime、std、
> 工具链或测试，不将待决的设备后端、内存接口、ABI 和分发格式视为已获批准。

## 1. 目标、边界与规范归属

允许开发者直接用 Feng 编写 GPU kernel 和设备辅助函数，继续采用
“Feng → 生成源码 → 目标工具链”的架构。host 调度和设备计算可以放在同一个
`.ff` 文件，也可以由开发者自行分文件；文件位置和扩展名不决定执行域。

### 1.1 已确认方向

1. 普通函数默认属于 host，在 CPU 上执行。
2. `@device` 声明 GPU 辅助函数；`@kernel` 声明 GPU 执行入口。
3. 注解提供编译期声明事实，由编译器识别、校验和发码。不得引入 Feng 类型或
   函数的运行时注册、反射查找、按名称查表分派。
4. 编译器不感知 std 的包、模块、类型或成员名称；相同公开机制对所有包生效，
   std 不享有特权。设计原则与
   [`@throwable` 开发方案](feng-throwable-annotation-dev.md)一致，
   但本功能不依赖尚未实施的 `@throwable`。
5. 源文件混合不要求输出编译单元混合。host 与 device 可以分别发码和编译。
6. 复用既有类型、符号身份、可见性、泛型及依赖分析，不因 GPU 功能改变普通
   CPU 程序的语义；必要扩展须在实施前明确。
7. 本文不同时实施 `@simd`、异常优化或 ARC/runtime 改造。GPU 线程可以先执行
   标量计算，CPU SIMD 不是本功能的前置条件。

本文中的 host 指应用的 CPU 执行侧，不是“正在运行编译器的机器”。交叉编译时，
工具运行平台、应用 CPU 目标和 GPU 目标必须分别表达。

## 2. 当前实现依据与可复用部分

以下是本轮静态源码核对结果，不表示已做设备编译或 GPU 运行验证。

| 位置 | 当前实现 | 本方案的含义 |
| --- | --- | --- |
| `src/parser/parser.h`：`FengAnnotation` | 已有注解身份与参数形态表示 | 优先复用声明机制，不另设 GPU 文件解析器 |
| `src/codegen/codegen.h`：`FengCodegenOutput` | 主要输出单个 `c_source` | 需要表达 host 与设备输出，具体结构待实现设计 |
| `src/codegen/codegen.c`：`cg_finalize` | 生成代码包含 `feng_generated.h`、`feng_runtime.h`、`llvm_c_eh.h` | 设备输出不能直接沿用整个 CPU 编译单元 |
| `src/cli/compile/direct.c` | 当前写出 `ir/c/feng.c` | 增加设备中间制品管理，保留既有 CPU 路径 |
| `src/cli/compile/driver.c` | GNU C11、CPU target、异常插件、CPU runtime 链接 | 设备编译必须有独立参数与依赖集合 |
| `src/platform/platform.c` | 当前目标映射是应用 OS/CPU 平台 | GPU 后端和架构不能混同于已有 CPU 平台 |
| `src/symbol/` 与 FT `ATRS` | 已有声明属性和跨包恢复机制 | 执行域事实应进入相同符号链路 |
| `scripts/trim_llvm.sh` | 裁剪现有发行工具 | 尚未验证随包制品的 GPU backend、设备库及配套工具是否完整 |

Feng 标量是值，标量数组按值连续存储；`@value` 类型及其数组已有实现。不能把
这些能力列为 GPU 功能新增项，也不能把普通数组的每个标量元素描述为托管对象。

`&arr` 已按既有 C ABI 规则取得元素 payload 首地址，不是数组对象头地址；
其它合法取址按各自既有 ABI 规则解释。GPU 接入应复用此行为，不新增“剥离数组头”
机制。裸指针是否能由 GPU 访问，是内存来源与设备映射问题，不由取址表达式保证。

## 3. 编译期检查

本节是供 Review 的检查设计；未在 §1.1 确认的具体语法和准入集合，须由 §9
的对应决策收口后才能实施。

### 3.1 声明与调用边界

建议第一步从顶层函数实现注解。方法、extern、lambda、构造函数、泛型入口等的
准入不能默认为已支持；须明确允许集合及错误诊断。裸注解、空括号、参数、重复
标注以及同一声明同时标记两种注解的规则也须明确，不能依赖 Parser 偶然接受。

建议的调用矩阵：

| 调用方 | 普通 host 函数 | `@device` 函数 | `@kernel` 入口 |
| --- | --- | --- | --- |
| host | 原有普通调用 | 拒绝普通调用 | 通过明确的启动接口提交，不能作为普通函数调用 |
| device / kernel | 拒绝 | 允许合法的设备调用 | 第一阶段不开放设备侧启动；若后续需要，独立设计 |

不自动把未标注的 host 函数改为 device，也不根据调用者静默生成两份实现。
同一算法的双执行域复用需要独立规则，本方案不新增 `@host` 或双域注解。
即使 host/device 位于同一文件或模块，调用边界仍然生效。

### 3.2 完整调用与数据依赖

在普通名称解析、重载决议和类型检查后，按解析出的声明身份检查：

- 直接函数调用、方法及 fit 调用、构造和默认初始化所引入的调用。
- 泛型具化依赖、约束成员调用以及编译器生成的辅助函数。
- 全局值、常量、类型布局和生命周期依赖。
- callable、闭包、间接调用和递归；必须支持且验证，或明确拒绝，不能漏检。
- 同包、跨文件及跨包依赖；结果不依赖文件或 import 顺序。

设备闭包中的每个调用及数据依赖都必须具有设备可用实现。不能只检查根 kernel，
也不能因预期内联、死代码消除或 ThinLTO 优化而绕过语义检查。
CPU `extern` 声明不自动等同于 GPU 外部函数；设备库接口需要可验证的目标契约。

### 3.3 类型、内存与生命周期

建议以标量、无托管引用的值类型和明确的设备缓冲区视图形成首个验证范围。
这只是起步范围建议，不是已批准的完整类型清单。

必须明确：

1. kernel 参数、返回值与设备函数调用的 ABI，包括大小、对齐、位宽和布局。
   建议 kernel 先采用 `void` 返回、通过缓冲区输出，待人工确认。
2. 设备可访问地址及其地址空间。设备地址不能与普通 host 地址混用；
   `int` 等平台相关类型在 host/device 边界上的编码必须一致或明确转换。
3. host 资源拥有者与 device 访问视图分离。既有 `&arr` 可提供复制源/目标地址，
   但不自动建立映射、不复制数据，也不把所有权转移给 GPU。
4. 当前公共 `T*` 为不透明指针；kernel 中的索引、读写及共享内存需要公开、通用
   的表达机制。不能只添加两个函数注解就假定这些操作已经可用。
5. 默认零值、初始化顺序和数组越界行为。不能因 GPU 不支持 CPU `feng_panic`
   就删除检查；设备错误报告、trap 或其它契约必须先确认。
6. 托管字段、终结器、ARC、循环回收与异常展开。第一阶段建议拒绝依赖未提供的
   CPU runtime 能力；不能只看到 `@value` 就判定整个类型适用于 GPU。
7. 异步执行结束前的资源保活、读写互斥与完成同步。共享物理内存不等于不需要
   同步；任务失败、取消和提交失败也须正确释放资源。

若设备能力通过库类型或函数声明表达，编译器只识别公开的内建机制，不硬编码
某个 std Buffer 类型、方法名或库名。该机制的具体形式属于 §9 待决事项。

### 3.4 设备操作与数值行为

线程/工作组编号、工作组共享存储、屏障、原子操作以及后续子组操作，应有明确
的编译期操作身份与设备语义，不能以普通同名函数隐含获得特权。

屏障的执行一致性、原子操作的内存顺序及作用域必须定义。可静态证明非法的情况
应诊断；无法静态证明的同步使用条件要写入契约，不能承诺编译器检查所有死锁。

整数回绕、浮点转换、FMA、非正规数和数学函数精度按明确规范发码。CUDA 等
设备工具链的默认选项可能与现有 Feng 不同，不能直接继承导致静默语义变化。
使用显式融合或近似操作的范围另行确认，不全局改变普通 Feng 数值语义。

## 4. 发码与设备后端

### 4.1 输出划分

```text
同一组 .ff 源码与依赖声明
    → 名称/类型分析及执行域检查
    → 按声明身份形成 host 和 device 依赖闭包
        ├─ host → 原有 C 编译单元 → CPU 对象/库
        └─ device → 目标设备源码 → 设备对象/程序
```

优先复用表达式、控制流、标量和合法值类型的发码。设备入口标记、地址空间、
内建操作和必要的目标 ABI 使用独立的目标处理边界，不把目标分支散布到无关逻辑。
不以大规模 Codegen 重构作为前置工作，实际改动必须由首个后端需要证明。

设备输出不得直接复制整个 host 翻译单元：

- 不无条件包含 CPU runtime、异常头文件或 CPU 模块初始化与清理代码。
- 不将 host 的静态地址、描述符指针、witness 或 callable 存储直接传给 GPU。
- device 所需的常量、布局和辅助代码按依赖生成；同一源声明在两侧需要的布局
  及表示必须明确，不假定 CPU 结构在所有设备上天然相同。
- 普通 CPU 编译继续使用现有路径；不修改 `llvm_c_eh` 或原生符号插件来承载
  GPU 功能，不因增加设备编译而扩大发行版 CPU 优化选项。

### 4.2 候选后端

| 目标 | 可行的源码路线 | 尚需验证 |
| --- | --- | --- |
| NVIDIA | CUDA C++，计算主体可保持 C 风格 | Clang NVPTX 支持、CUDA 工具/设备库、设备链接和启动方式 |
| AMD | HIP C++ | Clang AMDGPU 支持、ROCm 依赖及设备链接 |
| OpenCL 设备 | OpenCL C | 所选实现接受的源码/IR/二进制形式、Clang 与设备运行环境的配合 |
| Apple GPU | Metal Shading Language | Apple Metal 工具链、库产物及 host API 接入 |

CUDA/HIP 不是当前 GNU C11 模式；OpenCL C 也有独立的语言和地址空间规则。
Apple GPU 不能仅凭随包通用 Clang 就承诺生成 Metal 制品。继续源码发码是已讨论的
架构方向，首个后端以及额外工具的获取/分发方式尚未选择。

不将 CPU ThinLTO bitcode 当作通用设备 IR。设备目标、地址空间、数据布局及依赖
不同，设备优化和链接选项需要独立验证。

## 5. FT、跨包与设备制品

### 5.1 声明事实

执行域和 kernel 属性沿完整链路传递：

```text
源码注解 → 语义声明事实 → 符号导出 → FT writer/reader
         → provider 查询 → 导入声明恢复 → 调用检查与设备发码
```

优先复用 FT `ATRS` 的声明属性扩展机制。字段编号、格式版本和兼容性处理在
主规范中确定；影响正确编译的设备事实不能被旧 consumer 当成可忽略注解丢弃。
package-public、workspace-cache、LSP 及签名一致性比较均须保留相关事实。

继续复用模块/符号身份和叠加后的最终可见性。不得以 GPU 为由公开私有声明，
也不依靠文件后缀或 std 身份恢复执行域。

### 5.2 实现制品

FT 只提供声明事实，不能代替设备函数体。跨包 device 调用需要与声明匹配的
设备实现及完整链接依赖；已有 CPU `.a` 即使含 bitcode，也不能直接作为 GPU 库。

需要设计设备归档或程序制品的身份，至少包含后端、设备目标、ABI/格式版本以及
对应包身份。具体目录、归档格式、公开索引和命名在 §9 确认，不预先添加文件布局。
现有 `.fb` 不将裸 `.o` 作为稳定分发接口，设备制品扩展必须显式更新包规范。

验证场景：

- A 定义 device 函数，B 的 kernel 调用 A，应用只依赖 B；传递依赖完整。
- A 内部辅助符号可正常设备链接，但不因此成为 Feng 包外可见声明。
- 多个包复用 A，符号不重复定义，也不丢失必需的私有实现。
- provider 源码不可见时仍能检查和链接；设备制品缺失、目标不匹配或版本不兼容
  时明确报错，不静默回退到 host 实现。

### 5.3 泛型与间接调用

现有泛型共享体可能依赖描述符与 witness，不能把 CPU 指针原样搬到 GPU。
闭合布局、泛型实现及隐藏依赖如何设备化，必须在实现前确认。
不能未经批准改为全局单态化，也不能假定 FT 已包含可在消费端重新具化的函数体。

建议首个可运行验证使用非泛型直接调用。泛型、方法、callable 和闭包后续分别
定义支持或拒绝边界；最终交付必须公布实际能力集合，不能把受限验证当作完整支持。

## 6. 构建、启动与分发

### 6.1 构建流程

1. 项目命令解析 manifest 和依赖，将 GPU 构建选择透传直编；核心编译器仍不
   自行解析项目依赖树。具体 CLI/manifest 字段名称待 Review。
2. 校验工具运行平台、应用 CPU 平台、设备后端与架构及必要 SDK/设备库。
   GPU 参数不能改变既有 `--platform` 的 CPU 平台含义。
3. 完成语义检查与 FT 输出，再生成对应的 host/device 源码。
4. 分别编译，解析设备跨包依赖并完成所需设备链接；按确定的方案生成启动桥接。
5. bin 组装 CPU 程序与设备制品；lib 保留可被消费端使用的声明和设备实现，
   不能提前裁掉公开设备入口。
6. build/run 使用相同设备配置；pack 收集并验证设备制品及传递依赖。
   未请求设备构建时如何处理包中的设备声明，须在阶段 0 确定。

缓存至少区分源码与依赖、编译器/设备工具链版本、设备架构、ABI、优化及数值选项。
只改 kernel 必须使对应设备制品和嵌入结果失效，不能复用旧设备程序。
`--keep-ir`、失败保留、clean、诊断源码映射须覆盖设备输出，具体路径待定。

没有 GPU 声明和配置的普通 CPU 项目应保持既有工具选择、编译参数和依赖，
不要求安装 GPU SDK。维护脚本按必要目标扩展，不预先把所有 GPU 工具加入发行包。

### 6.2 启动接口与所有权

普通 kernel 声明不是 CPU 可直接调用的函数指针，也不自动沿用普通 callable
表示。启动方式需要建立 kernel 身份、参数类型、参数编码及执行配置之间的关系。

候选是编译器生成已校验的入口信息/桥接，普通库通过公开机制完成设备分配、
加载、提交和同步。接口形式尚未确定；不能先写一个按名称查找的 GPU helper
冒充完整的类型安全启动机制，也不能硬编码 std 的启动函数名。

明确区分：

- **禁止的机制**：为识别 Feng 类型/函数，新增运行时注册表、反射扫描或查表分派。
- **设备执行所需操作**：驱动加载设备程序、取得原生执行句柄、提交队列和完成事件。

部分后端集成模式会自动生成设备映像注册代码，不能在未 Review 时直接采用。
显式加载、原生入口绑定与驱动内部行为的边界，需要在选择后端和启动协议时确认。
后端确实需要的加载/绑定行为应如实说明，不能声称“编译期确定”就能消除驱动交互。

异步资源保活优先由 host 库的普通拥有关系实现。仅当 Feng 与公开 C ABI 不能实现
必要能力时，才提出 runtime 私有 ABI 扩展并交由人工决定。

### 6.3 最终产物

混合文件与最终是否单文件没有绑定关系。可选：

- 将设备制品嵌入 CPU 可执行文件。
- 将设备制品作为独立文件随程序分发并显式加载。

本文不选定默认方式；单文件也不代表没有 GPU 驱动或平台库依赖。
完整分发应覆盖路径搬移、安装、设备不支持、程序加载失败及资源清理。
GPU 编译产物不应被误交给 CPU LLD 当作普通 CPU 对象链接。

## 7. 变更范围

| 层次 | 预计工作 | 约束 |
| --- | --- | --- |
| 主规范 | 注解、执行域、设备表示、构建与包规则 | Review 后先收敛规则 |
| Parser/AST | 复用注解机制，增加必要身份 | 不引入新文件语法 |
| Semantic | 执行域、调用闭包、类型与操作资格 | 不依赖优化偶然删除非法路径 |
| Symbol/FT/provider | 保存并恢复设备事实 | 源码与二进制依赖一致 |
| Codegen | 分离输出，复用通用发码，增加目标操作映射 | 不直接移植 CPU runtime 协议 |
| CLI/build/pack/run | 配置透传、设备编译/链接、缓存与打包 | 保持普通 CPU 路径 |
| 库 | 设备资源、启动、同步及错误处理 | 无 std 特权，优先普通 C ABI |
| 工具链维护 | 首个后端必需工具及许可处理 | 先验证再增加，不预设全部分发 |
| LSP/调试 | 注解与执行域诊断、设备源码位置 | host DAP 不自动等于 GPU 调试支持 |

GPU 源码级调试是否纳入首轮交付属于待决范围；至少必须保留可追溯的编译诊断。
本方案不批准修改现有 CPU DAP、异常插件、原生符号插件或 ARC 算法。

## 8. 分阶段 Todo 与验收

每个实施阶段均遵循“主规范 → 代码 → 测试”。已有用例修改须先获人工批准；
编译器用例验证诊断/AST/IR，FCTS 验证批准的语言行为。非文档变更执行 `make test`，
GPU 执行验证另需实际目标设备，不能由 CPU 回归或只有编译成功替代。

### 阶段 0：Review 与首个后端可行性验证

- [ ] 确认 §9 的首个后端、语言准入、内存/启动接口和交付边界。
- [ ] 将批准的规则写入主规范，明确尚不支持的行为。
- [ ] 在 `temp/` 隔离验证目标工具链：最小 kernel、辅助调用、设备链接及执行。
- [ ] 核对随包 Clang 实际后端、配套工具/设备库、发行许可与维护成本。
- [ ] 验证启动方式不引入未经批准的注册或查表机制。

验收：形成一条可运行、可解释依赖的设备链路和明确的实施范围。
不修改正式实现，不把单个探针成功解释为完整 Feng GPU 支持。

### 阶段 1：注解、执行域与 FT

- [ ] 实现批准的注解位置/参数规则及调用矩阵。
- [ ] 复用声明身份和依赖分析，检查显式与隐式调用、类型和全局依赖。
- [ ] 保存/恢复设备事实，覆盖 public/cache、跨包及 LSP。
- [ ] 补齐合法声明、误用、互斥、跨域调用、非法载荷和依赖顺序用例。
- [ ] 尚未接通的设备输出明确诊断，不误发为 CPU 普通函数。
- [ ] 全量回归，核对普通 CPU 项目参数和行为不变。

验收：源码与 FT 消费给出一致判断，无需 std 名称、运行时注册或查询。

### 阶段 2：设备表示与首个后端发码

- [ ] 实现批准的设备视图/地址空间、kernel ABI、线程索引与基础操作。
- [ ] 分别输出 host/device 源码，完整收集常量、类型及辅助函数。
- [ ] 将合法函数映射到目标入口与设备函数，隔离 CPU runtime/异常依赖。
- [ ] 确认默认值、越界失败、整数与浮点行为，不继承不兼容的后端默认选项。
- [ ] 用例覆盖参数布局、读写、边界、控制流、辅助调用和拒绝路径。
- [ ] 检查设备 IR/汇编与未解析符号，全量回归。

验收：设备代码可由所选工具链正确编译，未携带 host 地址或意外 runtime 调用。
线程数和数据量变化不依赖任何评测专用路径。

### 阶段 3：host 提交与最小运行闭环

- [ ] 实现公开的 kernel 绑定/启动机制与普通库接口。
- [ ] 明确并实现参数编码、传输/映射、异步保活及完成同步。
- [ ] 实现设备程序加载和必要的目标编译驱动接入。
- [ ] 真实 GPU 验证计算结果、多次执行、并发提交及资源释放。
- [ ] 覆盖分配、加载、提交失败和不支持设备的错误路径。
- [ ] 全量回归；记录 GPU 型号、驱动、设备工具链与执行结果。

验收：Feng host 能启动 Feng kernel，生命周期和结果正确。
编译成功或只在 CPU 上模拟执行不能代替这一验收。

### 阶段 4：跨包、项目构建与分发

- [ ] 实现批准的设备库格式、符号身份、传递依赖及设备链接。
- [ ] 打通直编、build/run/pack 的设备配置和一致校验。
- [ ] 验证 provider 源码不可见、多级依赖、私有辅助函数及重复依赖去重。
- [ ] 实现批准的嵌入/独立分发方式、缓存失效和 clean/keep-ir。
- [ ] 验证制品缺失、错误架构、版本不兼容、搬移安装及失败恢复。
- [ ] 全量回归及实际设备跨包执行验证。

验收：完整使用二进制依赖运行，声明事实与设备实现配套，不能只交付同文件示例。

### 阶段 5：算子验证与交付核验

- [ ] 在批准范围内验证工作组共享内存与同步；不支持时明确记录能力边界。
- [ ] 实现代表性逐元素、归约及分块计算用例；算法逻辑使用 Feng 编写。
- [ ] 与同算法、同精度、同布局的原生设备实现比较。
- [ ] 分别量化设备执行、提交、传输和端到端耗时；正确处理预热与 GPU 同步。
- [ ] 核验 CPU 非 GPU 项目无额外构建依赖或运行时开销；有新增成本提交人工决定。
- [ ] 全量回归与目标 GPU 验证，汇总已支持/明确拒绝/尚未验证的矩阵及 commit message。

性能目标和允许误差在阶段 0 明确，不以 CPU 五项评测替代 GPU 算子验证，
也不把完成首个后端写成 NVIDIA、AMD、Apple 全部支持。
