# if 表达式条件绑定作用域修复

状态：2026-10-21 已完成修复、正式用例和 Linux 全量回归。

## 问题与规范依据

`if value match err: Type { ... }` 的成功分支应能访问 `err`。条件绑定的
可见性、短路传播和头部／块作用域以[流程控制主规范 §3.3](../specifications/feng-flow.md#33-infix-match-运算)
为准；表达式结果与 return／throw 路径以该规范 §3.4、§4.1 为准。本次修复落实
既有规则，不新增语言规则。

以下合法程序在 `err` 处报 AE0001：

```feng
spec Value: int | string;
func read(value: Value): int {
  return if value match err: int { err } else { 0 };
}
```

同样的问题出现在 `return match ...` 的分支末尾包含带绑定的 `if` 时。
`examples/hello_world/src/demo.ff` 的 Rejected 分支属于该形态；错误发生在
名称解析阶段，不取决于绑定变量随后用于普通取值还是 throw。

## 已验证的原因

- Parser 按既有结果分支处理，将 match 表达式分支末尾的 if 语句转换为
  `FENG_EXPR_IF`；转换保留原条件和分支，并未丢失绑定信息。
- Semantic 的 `FENG_STMT_IF` 会收集条件中可见的 match 绑定，在头部作用域
  登记后解析成功分支；`FENG_EXPR_IF` 缺少该步骤，因此报未定义。
- Codegen 的语句路径已有条件 guard、绑定作用域及失败路径清理；表达式路径
  直接把条件求为 bool，不能直接沿用这种方式处理需要跨 `&&` 保留到成功分支
  的绑定。修复必须同时覆盖语义事实、结果值和条件临时值的生命周期。
- 在现有 Linux 容器中核验 commit
  `9c8b1b4448aef35c81a657a03160db130adb4ed8` 的 743 个文件和编译器身份后，
  8 组对照确认：普通 if 语句通过，直接 if 表达式及 match 分支末尾 if 均复现；
  原示例在临时副本中仅将 Throwable 换成旧版支持的 string，第 47 行仍复现。
  这是异常根变更之前已有的缺陷。

## 修复边界与实现方向

1. Semantic 复用现有可见绑定收集与登记能力，为 if 表达式的成功分支建立头部
   作用域；分支块继续作为子级作用域。失败分支和表达式外不继承这些绑定。
   条件的类型事实也在头部作用域内保存，供表达式后续推导读取。
   分支结果类型在其有效作用域中保留；退出作用域后的结果贴合优先读取已有
   表达式站点类型事实，避免被同名外层变量替代。不改变泛型推导算法。
2. Codegen 对含可见条件绑定的 if 表达式复用现有条件 guard 和作用域清理能力。
   条件只求值一次，`&&` 保持短路顺序；成功路径保留绑定到分支结束，失败路径
   在进入 else 前释放已产生的条件临时值。结果槽属于外层作用域，使用既有结果
   转移／持有规则；return、throw 沿用既有清理机制。
3. 不改 Parser 的末尾语句转换规则，不改异常根、throw／catch 协议、泛型机制、
   泛型共享体通用实现、描述符或 runtime ABI，不改标准库及原示例。
4. 普通无条件绑定的 if 表达式保持现有发码路径；有绑定路径使用现成的局部值、
   条件跳转和清理能力，不增加运行时查询、转换回调或额外载体分配。

## 实施与验证记录

- F01：首轮 Semantic 正例中，直接绑定与取值已通过；`v match err: int && err > 0`
  仍报 AE1102。`validate_if_expr` 在绑定头部作用域退出后重新推导条件类型，
  右操作数中的 err 已不可见。条件类型的检查也必须在绑定头部作用域内完成；
  这是同一条件绑定缺陷的验证遗漏，不扩大到通用类型推导或泛型机制。
- F02：新增同名变量正例确认，外层 err 为 string、条件绑定 err 为 int 时，
  成功分支结果被误读为外层 string，报 AE0034。已有分支结果类型读取函数先
  按当前作用域重新查名称，只在未知时使用保存的站点事实；应优先使用分支解析时
  已记录的准确事实，缺少事实时才推导。仅修正这一分支结果读取顺序，不新增类型
  表示、推导规则或泛型共享体处理。
- F03：FCTS 的纯字面量结果且无显式目标类型场景，仍在后续 if 表达式推导时
  重新推导 `&&` 条件，因绑定作用域已退出而丢失结果类型。最小对照
  `let result = if value match item: int && item > 0 { 1 } else { 0 };`
  后接 `result == 1` 可稳定复现。头部作用域内保存条件类型事实，if 表达式
  的后续推导优先读取该事实；缺少事实时保留原推导路径。补充无目标类型及
  单边退出的正式语义回归，不以给用例增加类型注解绕过此问题。
- F04（仅记录）：不含 match 绑定的 `let reader: Reader = if flag { () { ... } }
  else { () { ... } };`，当前编译器和旧 commit 均报 lambda 缺少显式 callable
  目标类型。该既有目标传递问题不属于本次条件绑定修复；闭包生命周期用例在
  分支内显式声明 Reader 局部变量后将其作为结果，仍验证捕获绑定逃逸和释放，
  不修改 callable 或泛型机制。
- F05（用例校正）：首轮 FCTS 运行 1732 项，1731 项通过；聚合结果生命周期
  用例将类型默认初始化产生的 id=0 对象也计入了目标资源的析构次数。最小对照
  确认，普通 union 和 if 语句同样产生这类默认对象；生成 C 显示既有 union／
  结果槽默认初始化及后续赋值会正常释放它们。显式构造的正 id 资源在直接 if
  与 match 末尾 if 中均保留到结果退出作用域，并只析构一次。新增用例采用
  现有聚合生命周期测试相同的正 id 计数规则，仍断言真实载荷的值、存活时间和
  精确析构次数；未修改已有测试、聚合实现或 runtime。
