# 泛型链式调用的目标上下文与补全修复

状态：C01–C06 已完成修复与覆盖验证，macOS ARM64／Linux ARM64 的完整 `make test` 均通过，等待人工 Review，未提交。基线：`5423d624`。本次不涉及 runtime、ABI、FT 格式或语言规则变更。

## 规范核对

[泛型主规范 §4](../specifications/feng-generics-draft.md) 规定：省略类型实参时必须尝试从已知实参、接收者静态类型与当前表达式的目标类型推导；同一泛参的已知绑定必须一致。[表达式主规范 §5](../specifications/feng-expression.md) 规定成员、下标、调用后缀按从左到右展开；其 §3.4、§6 规定字面量的目标贴合与数值／数组规则。

据此，下例的 `T` 可由 `"x"` 唯一确定为 `string`；`1` 可贴合 `i32`。`int` 是最终方法调用的返回目标，不能作为中间数组接收者的目标类型。

```feng
func values<T>(item: T, n: i32): T[] { return []; }
fit string[] { func strings(): int { return 1; } }
func probe(): int { return values("x", 1).strings(); }
```

**此处 AE0512 不符合现有定义，应作为 Bug 修复。** 保留真正的泛参冲突、无法推导、约束不满足与重载歧义诊断；不增加隐式转换规则。

## 已确认问题

当前共 **5 类问题、6 个实现缺陷**：C01／C02 为编译器与 LSP 的链式目标传播；C03 为推导返回类型的调用点代入；C04 为推导缓存生命周期；C05 为前向返回推导的待定状态；C06 为实参中的泛型调用缺少形参目标。均已展示最小代码并获准修复。无法根据现有规范确定的语义仍须人工决策。

- C01：同一链式表达式作为独立语句能编译，放入返回 `int` 的位置则报 AE0512。Semantic 将最终结果目标通过 callee／receiver 传入中间泛型调用，拿 `int` 与 `T[]` 比较。目标上下文应按表达式角色隔离，不能靠忽略 AE0512 或某个函数名绕过。
- C02：LSP 对完整合法语句可使用已发布类型事实，但新打开的 `values("x", 1).` 返回空。固定形参 `i32` 与整数的默认类型结构不等时，现有调用匹配丢弃了从另一实参得到的 `T = string`。该问题及前轮错误负例见 [fit 补全文档 I08](feng-lsp-fit-completion-bugfix.md#i08-交付复核合法泛型链式编辑状态仍缺候选)。

## 实现边界

1. Semantic 在共同的表达式操作数查询处保存／隔离／恢复目标上下文：调用目标、成员接收者、下标对象与索引不继承最终结果目标。调用自身继续使用其合法目标；已有实参、分支结果和聚合元素贴合规则继续由各自的类型上下文负责。
2. LSP 将“从泛型形参收集绑定”与“判断整个重载是否精确匹配”分开。先代入接收者与显式类型实参，再从实际参数收集尚未绑定的泛参。固定形参需要上下文贴合时，不抹去其他实参已证明的泛参绑定；泛参之间的实际冲突仍拒绝。精确候选优先；没有精确候选时，仅在可能候选给出一致且闭合的返回类型时继续成员查询。不得复制核心语义的常量求值、转换规则或运行函数体。
3. AST、有效 Semantic 事实与 FT 继续使用既有统一成员查询。每个调用的实参类型在该查询内计算一次，复用于不同重载；不引入新旧补全路径或新增持久缓存。
4. 缓存优先级、调度、runtime、ABI、FT、标准库不变。不实施与链式调用无关的候选身份扫描优化。
5. C03 统一调用结果查询：先取得 callable 的有效返回类型（显式声明或推导缓存），再对其中的类型引用使用既有 owner／fit／方法泛参代入。未知结果保留推导待定状态；标量、void、已确定声明等无泛参结果保持原有表示。不得把未知当作 void，不增加仅针对数组、string 或某个方法的路径。
6. C04 在返回类型首次进入缓存或实际变化时，复用 `clone_type_ref_for_inference` 深复制类型引用，并交由 Analysis 的既有合成类型管理负责释放。后续推导轮次复用未变化的缓存值；数组、指针、带类型实参的命名类型遵循同一所有权规则。非类型引用结果保持原有表示。该修复仅影响编译期对象生命周期，不改变生成程序的存储、运行时成本或 ABI。

## 问题与验证记录

实施中发现的问题先记录证据，再分析、修复；语义不确定、额外范围或运行时成本须由人工决策。

- C05（既有问题，已批准）：前向调用的返回类型仍待下一轮推导时，下标验证直接报 AE1021，阻断了推导收敛。基线 `5423d624` 与当前均复现；没有泛型或合成返回类型也会触发：

  ```feng
  func forward() { return later(); }
  func later() { let items: string[] = ["x"]; return items; }
  func probe(): string { return forward()[0]; }
  ```

  将 `later` 显式写为返回 `string[]`，两个版本都通过。已有 `expr_type_inference_is_pending` 能区分尚待推导与最终错误，但下标验证未使用。在操作数类型尚待推导时延后对应检查，保留最终不合法下标及不能收敛的诊断；同时检查成员／调用等后缀是否一致处理待定状态。

  行为用例补测：`chain_before()[0] == "forward"` 在返回尚待推导的轮次被二元运算检查报 AE1019；直接返回该下标已通过。一元运算、二元运算及条件检查同样直接拒绝未知类型；统一复用待定状态查询，仅对尚待推导的未知操作数延后验证，已知类型的错误不延后。补齐比较／算术／取反／条件及最终类型不符的正反例，不能通过改写行为断言绕过。

- C06（既有问题，已批准）：外层形参目标尚未代入时，内层泛型调用先报 AE0525。基线 `5423d624` 与当前均复现，下例不需要省略返回类型：

  ```feng
  func empty<T>(): T { let value:T; return value; }
  func take(value: string) {}
  func probe() { take(empty()); }
  ```

  对照 `let value:string = empty();` 能从目标得到 `T=string`。当前 CALL 先在无目标上下文中解析所有实参，随后才选择外层签名并验证参数。将依赖形参目标的内层推导推迟到外层签名匹配，保留真正无法推导及重载歧义；不能随意把整个外层返回目标传入实参。

  复用已有实参目标延后阶段：先完成名字／表达式解析，暂存已选 callable 身份；候选匹配在各自形参目标下查询类型，不提交候选的绑定。选中唯一签名后，只重新解析仍待定的实参，并提交其泛参绑定。直接函数、方法、构造及 callable-form spec 使用同一提交入口；显式未知泛参不可冒充已确定的返回类型。无候选或多个候选仍由已有诊断路径处理。

  嵌套实参补测发现两个“实际类型是否已知”的查询仍继承外层目标，与其前面的独立实参推导不一致；统一使用 C01 的操作数查询，避免 `take(identity(empty()))` 被错误拒绝。

  收敛已有的两个 resolved-call 签名查询为一个，包含构造函数，避免目标提交与返回推导分别维护声明分类。行为测试补充前向下标／成员／callable，以及嵌套调用、分支、数组、构造和动态 callable 的形参目标代入；LSP 验证这些完整程序发布的返回类型事实。

- C04（既有问题，已批准修复）：扩充 C03 矩阵后，独立最小例 `func values<T>(item:T) { return [item]; }` 在基线 `5423d624` 和本轮均报 AE0504，提示 `''`／`void*` 与 `T[]` 冲突。ASan 已确认 `heap-use-after-free`：`synthesize_array_type_ref` 分配类型，`resolver_free_scopes` 释放，下一轮 `validate_return_stmt → inferred_expr_types_equal → type_refs_semantically_equal` 读取该地址。`cache_callable_return_type` 借用的类型超出了 Resolver 生命周期。按普通返回规则推导为 `T[]`，让缓存拥有足够长生命周期的类型信息，不修改语言规则。
- C03 的普通 `items.element()` 与 `values("x",1).element()` 最小例先通过 `feng check`；扩充矩阵曾因 C04 失败，修复 C04 后重新通过，未删除复现。
- C03 补充验证：C04 修复后，矩阵中的 `func inferredEmpty<T>() { let item:T; return item; }` 配合 `func probe():string { return inferredEmpty(); }` 仍报 AE0525。调用结果查询已使用有效返回类型，但泛参收集、重载匹配与持久化调用记录仍只读取显式返回声明。统一让这些入口消费有效返回类型，删除各调用方重复的返回类型预处理，继续使用现有 owner／方法绑定逻辑。
- C04 最小复现已在修复后通过 ASan／UBSan／LSan 检查，扩展语义矩阵也已通过；最终全量验证见下文。
- C03 的跨包 LSP 验证：隔离诊断确认，同一导入模块的 source-index AST 与公开 FT 被同时加入重载候选。前者在编辑状态没有有效返回类型事实，后者已有完整类型；公开 FT 不含源码坐标，二者未被位置去重，未知候选阻止结果查询。沿用既有 Signature Help 的模块来源选择规则：有已发布导入模块时使用其完整元信息；当前模块使用当前源码，未发布的模块仍使用源码索引。函数、自有成员和 fit 共用同一来源判定，不猜测未知返回类型，不新增缓存或请求路径分析。
- 测试编写校正：指针对照最初使用 `T*`，被既有 AE0333 正确拒绝（开放泛参不能直接组成指针）。改为闭合 `int*`，以及把完整 `int*` 作为 `T` 实参的数组对照；不改变该语言规则。
- 新增不匹配返回目标反例正确报 AE1003；`T` 已由实参绑定，最终结果不符合目标类型，测试应断言该诊断，不错误要求 AE0512。
- FCTS 夹具语法校正：对象字面量后直接接 `.read()` 被既有 parser 拒绝；使用局部对象再调用方法，保持验证本地泛型方法推导返回值的目的，不扩展语法。
- 实参目标夹具校正：按类型主规范使用 `func Sink(v:string)` 声明构造函数；不存在 `ctor` 语法。callable-form spec 必须显式写返回类型，空结果为 `:void`；块 Lambda 使用 `(value:int) { ... }`。这些是新增夹具的编写错误，不是编译器缺陷。
- C03 行为验证曾失败：新增声明通过 Semantic，但生成 C 编译出现两处错误。保留完整用例，检查有效返回类型在发码中的消费，不将语义通过当作实现完成。
- C03 发码原因已确认：`cg_resolve_selected_callable_return_type` 把省略声明直接当成 void，而共享函数声明已通过 `cg_resolve_callable_return_type` 使用了推导结果，导致调用漏传 `_out`。修复该通用调用结果入口：类型引用复用现有调用点代入，其余事实复用现有返回类型解析；不增加类型特判或运行时／ABI 变更。FCTS 保留托管、标量、数组、泛型对象及跨包调用作为行为覆盖。

- V01：macOS 新增独立语义矩阵启动退出 137，日志为空；同一二进制重试仍被终止。签名校验正常，计时约 10.91 秒、user/sys 均为 0；已向人工确认安全软件授权情况，尚不能确认原因。未修改编译器规避。Linux 同组矩阵执行通过；最终两平台正式测试入口的完整回归均通过。临时入口被终止的原因未确定，未为此增加绕过代码。
- C03（既有问题，已批准修复）：新增完整语义发布场景中，省略泛型 fit 方法返回类型时，源码实际报 AE1003，LSP 无成功语义事实而显示声明中的 `void`。已用基线 `5423d624` 与本轮版本验证，下列不含链式接收者的最小例也均报 AE1003：

  ```feng
  fit T[] { func element() { return self[0]; } }
  func probe(items: string[]): string { return items.element(); }
  ```

  `infer_call_expr_type` 的显式返回类型分支使用 callable／owner 的泛型代入，省略返回类型分支直接取 `callable_effective_return_type`，保留了声明视角的 `T`。[函数主规范](../specifications/feng-function.md) 允许按一致的 return 路径推导返回类型。用户批准复用相同代入流程处理显式与推导返回类型，源码与导入保持一致。新增复现保留，未降低其断言。
