## 1. 状态、目标与范围

终止前状态（历史记录）：2026-09-29，第一阶段已实现并通过 Apple container 内正式全量 `make test`。
第二阶段的原实现也通过该次回归，但函数属性被放入 `llvm_c_eh`，且已有跨包无异常
摘要未被直接消费；该方案需要按 §6.2 修正，不能继续记为已完成。§7 保留原实现的
验证记录，不代表修正后的链路已经通过验收。Swift 性能目标另行实测。

目标是让编译器在不读取依赖包源码的情况下，取得可用于优化的函数内存访问摘要。
普通 Feng 函数由编译器推导，外部函数通过内建注解提供声明契约；摘要随符号及 `.ft`
跨包传递。与已有异常摘要一起，向后端提供准确的函数属性。

已确认的要求：

1. 普通 Feng 函数自动推导，手动内存注解限定在 `extern func`。
2. 无法证明的部分统一为 `unknown`，处理原则与异常推导一致。
3. 外部函数未显式标注时为 `unknown`；不按名称、库名、签名、返回类型或无异常
   属性猜测其内存行为，包括 `sqrt` 等已知名称。
4. 已证明的事实与未知部分分别保留，未知沿调用依赖及跨包摘要传播。
5. 异常、内存访问及是否返回是不同事实，不能互相代替。
6. 保持 Feng 现有语义与行为，不启用 LTO、不全局禁用向量化，默认保留 `-O2`。
7. `@memory` 采用 §4.1 的字符串参数形式：`none`、`read`、`write`、`readwrite`。
8. Feng 尚未公开发布，本次没有旧包兼容负担；现有模块统一重新编译。
9. 分两阶段交付：第一阶段完成内存访问推导、标注及跨包摘要；第二阶段基于这些
   信息优化发码。各阶段独立验收，不能将后端优化作为第一阶段交付的前提。
10. `llvm_c_eh` 仅负责 C 与 unwind 异常转换，通用函数属性不得加入该插件。
11. 同包和跨包统一消费 Feng 已有异常摘要，不因跨包缺少函数体而丢弃已证明的事实。
12. 内存和异常信息分别映射到可供后端优化的 C IR；单项已知即可使用，组合时只增加
    有依据的属性，不能要求两项同时已知，也不能附带未经证明的返回性承诺。

两阶段分别补齐编译器测试与 FCTS，并在 Apple container 内执行全量 `make test`。
macOS 原生验证由开发者另行安排。runtime 私有 ABI 和正式基准的行为保持不变。
分步 Todo 见 §8；未完成的项目不能视为交付。

规范归属：

- 现有异常语义及摘要只引用[异常规范 §6](../specifications/feng-exception.md#6-编译期异常摘要)。
- 外部声明与 ABI 只引用[互操作规范](../specifications/feng-interop.md)。

## 2. 已有基础与实际缺口

### 2.1 异常摘要已经跨包可用

当前异常分析记录声明模板和调用点事实；Symbol 持有摘要，FT 写出必要依赖，消费端
恢复后按实参求解。无需重新建立一套异常推导系统。

| 环节 | 现有实现 |
| --- | --- |
| 声明及调用点分析 | `src/semantic/exception_effects.c`、`exception_graph.c`、`exception_solver.c` |
| Symbol 挂接 | `src/symbol/export.c` 的 `attach_exception_templates` |
| FT 写出、恢复 | `src/symbol/ft_write.c` 的 `build_exception_section`、`ft_read.c` 的 `parse_exception_effects` |
| 无源码导入 | `src/symbol/imported_module.c` 的 `get_exception_template` provider |

函数内部完整捕获异常，且没有其他异常逃逸时，对外摘要为空。内部被调用函数仍然
可能抛出异常：调用者的空摘要不应删除内部实际需要的捕获路径。发码阶段应直接消费
已求解的摘要；异常插件原有的通用 IR 检查不替代 Feng 的证明，也不作为跨包属性
传递的前提。

### 2.2 本轮新增模块

- 结构化内存访问摘要、声明及调用点查询。
- 有函数体时的自动推导、调用传播及递归求解。
- `extern func` 的 `@memory` 校验与显式契约接入。
- Symbol、FT、导入及缓存对内存摘要的保留。
- 将已证明的摘要转换为准确的 C／LLVM 属性，而不附加未经证明的其他承诺。

对应入口为 `semantic/memory_effects.c`、`memory_graph.c`、`memory_solver.c`、
`symbol/memory_io.c` 和 `codegen/memory_contracts.h`。原先加入异常插件的
`FunctionContracts.cpp` 属于第二阶段待移除的实现，替代方式见 §6.2。

## 3. 摘要模型与推导

### 3.1 内部表示

语义定义仅见[主规范 §2–3](../specifications/feng-memory-access.md#2-访问与未知)。
实现用三个独立区域位集保存已观察到的 read、write、unknown，显式与隐式行为分别
保存。值域记录参数来源和 callable 目标／捕获环境；参数槽通过函数 ID 和槽位引用。

### 3.2 自动推导的处理路径

1. 复用完成类型与调用解析后的声明、接收者、实参及 callable 来源。
2. 汇总直接读写及实际会执行的隐式操作，形成参数化摘要。
3. 调用处代入被调用者摘要；泛型、spec 分发和回调沿用已解析身份，无法确定的依赖
   保留 `unknown`，不能按函数名或本次 benchmark 形态推断。
4. 对递归调用依赖求解到稳定状态；不能用迭代次数耗尽或未完成分析作为空摘要。
   需要终止求解的情形只能保守扩大为未知。
5. 发布不可变的声明摘要及调用点结果，供 Symbol、FT 和代码生成共同消费。

声明与调用点的查询根一起参与求解。查询不能在声明发布后才引入尚未求解的依赖。
递归闭包的捕获环境持续扩张时，只将递归部分扩大为未知；非递归嵌套闭包仍保留来源。

### 3.3 首轮精度及隐式边界

普通标量／指针槽位和数值控制流、已解析的直接调用、不可变回调及返回闭包可传播
事实。泛型／spec 的开放分发、共享可变 callable、未证明的 ARC、数组辅助操作、
对象构造／清理及全局初始化保守为 unknown；不把具体实参误当成完整的原生 ABI 证明。
隐式转换按目标类型处理，包含 union／spec 装箱、C ABI 桥接及隐藏结果存储。
浮点 `%` 的 libm 调用、defer 登记／执行、异常载荷也没有被当作局部纯算术。

## 4. `@memory` 的形式与契约

### 4.1 已确认的注解形式

四种字符串参数、适用位置、契约责任及诊断以[主规范 §4](../specifications/feng-memory-access.md#4-外部契约)
为准。字面量按既有字符串语法解释，覆盖原始字符串和转义；不接受绑定或常量表达式。
测试同时检查与 C 调用约定注解组合、重复注解、错误参数及精确诊断位置。

`errno` 是需要考虑的状态。当前 `std/std/src/numeric/Math.ff` 的 `sqrt` 是未标注的
外部声明，按已确认规则仍为 `unknown`；本文不批准给 libm 函数批量添加 none。
未来若需表达“仅访问某类状态、不会修改参数内存”，应在同一范围模型中扩展，不能
为某个函数名添加特殊规则。

### 4.2 “分区域”与“按参数声明”的含义

这两项指手动契约的精细程度，不是 `read`／`write` 等访问种类的替代：

| 声明粒度 | 回答的问题 | 概念示例 |
| --- | --- | --- |
| 函数整体 | 整个调用是否读取或写入对调用方可观察的内存？ | 一个复制函数整体可能读写内存 |
| 分区域 | 读写发生在参数可达内存、全局或其他状态中的哪些区域？ | 只读写参数可达内存，不访问全局及其他状态 |
| 按参数 | 各个参数可达内存分别允许哪些访问？ | 复制函数只通过 `src` 读取、只通过 `dst` 写入 |

这里的“参数可达内存”是通过参数引用或指针能够访问的存储，不是参数槽位本身。
函数整体的 `readwrite` 不承诺“只访问参数内存”；区域声明可进一步排除对全局等
状态的访问，按参数声明则可进一步区分输入和输出。上述示例仅解释粒度，不新增
注解语法，也不声明某个现有库函数满足这些条件。

精细契约仍不能代替别名分析：如果 `src` 与 `dst` 指向重叠存储，通过 `dst` 写入
也可能改变之后通过 `src` 读到的内容；不能由“`src` 只读”推导出该存储保持不变。

内部摘要需要表达访问范围，见 §3.1；这不等于必须同时开放对应的手写注解。
当前已批准的注解范围是 §4.1 的函数整体形式。是否追加分区域／按参数声明仍待
人工决策，未批准前不扩展注解语法。

## 5. 跨包、FT 与缓存

复用现有异常摘要的生命周期与 provider 方式，内存摘要作为独立事实保存，不复用
异常节点去表达内存操作，也不要求发布函数体或通用控制流图。

需要保存：声明身份、参数化访问范围与读写信息、未知部分及必要调用依赖。
私有辅助函数的影响应能够汇总到可导出声明，但不因此改变私有符号的语言可见性。

导入方必须在没有生产端 AST／源码时得到一致结果；调用点替换不能修改共享的声明
摘要。已知回调和泛型实参可参与代入，仍开放或动态的部分保持未知。

实现采用独立的 `memory_graph`、`memory_solver` 和 `memory_effects` 模块。图保存
访问、参数来源、callable 集合、调用及返回来源；求解器按实参抽象值建立调用实例，
在有限的区域／目标集合上单调求不动点。源码名称不参与优化识别。

FT 的唯一编码定义见[符号表规范：内存摘要元数据](../specifications/feng-symbol-table.md#内存摘要元数据)。

摘要必须与对应库实现、目标配置和依赖身份一致，参与缓存失效及发布产物完整性检查。
按已确认的重编策略，本次不增加旧产物兼容读取分支，也不为缺少摘要的旧产物
合成可继续消费的摘要。现有模块及对应依赖重新编译，符号表、库文件和缓存保持一致，
不能只更新 FT 后继续链接旧库。

缺少新增必需摘要或摘要损坏时，产物无效：本地缓存按现有失效路径回到源码重建；
依赖包报告需要重新构建。合法摘要中的 `unknown` 与缺失元数据不同，前者可保守
消费，后者不能解释为 none 或用 unknown 掩盖。

包错误路径也须保留诊断所需数据的生命周期：先构造包含包／FT 路径的错误消息，
再释放路径和底层读取错误。本次检查发现 C 编译驱动的既有 FT 失败分支顺序相反；
该分支随必需摘要校验一起修复并补充拒绝旧格式／损坏摘要的测试。

未标注的外部声明明确保存未知，不能在导入或代码生成阶段因识别库名／符号名而替换
为更强的 Feng 摘要。现有 C ABI 链接名称隔离和符号身份规则保持不变。

## 6. LLVM 消费方式及证明边界

### 6.1 两类信息的分工

| 事实 | LLVM 可消费的信息 | 不能据此推导 |
| --- | --- | --- |
| 实际原生函数没有向外传播的异常 | `nounwind` | 没有内存访问、一定返回、内部没有捕获路径 |
| 已证明／显式声明的内存访问范围与权限 | `memory(...)` 或等价属性 | 不抛异常、一定返回、不别名、数值运算身份 |
| 未知 | 不添加对应的限制性属性 | none、只读或不展开承诺 |

函数内部可以抛出并捕获异常，函数本身仍可满足 `nounwind`；内部可抛调用及其捕获
路径必须保留。发码使用 Feng 已求解的声明摘要，跨包使用对应 FT 摘要；异常含义与
隐式求值的传播规则只由[异常规范 §5–6](../specifications/feng-exception.md#5-与-c-abi-的边界约束)
定义。不能把外围 catch 筛选后的调用点结果贴到内部被调用函数上，也不能把元数据
缺失、未知或尚未求解误当作空摘要。

LLVM 的 [函数属性定义](https://llvm.org/docs/LangRef.html#function-attributes)及
[异常处理示例](https://llvm.org/docs/ExceptionHandling.html#windows-runtime-support)
分别说明这些属性和内部捕获的边界。

### 6.2 发码链路必须实际传递信息

FT 中存在摘要还不够，需要连接“导入摘要 → 原生声明／调用 → LLVM 属性”。
无函数体的声明也能承载这些属性，不要求 LTO 或调用内联。

Feng 发码按解析后的声明身份查询两类摘要，分别生成属性。已证明无向外传播异常时，
在 C 声明上使用 `__attribute__((nothrow))`，由 Clang 转为 `nounwind`；同包和跨包
遵循同一规则。内存为 unknown 不应阻止传递无异常信息，异常未知也不应抹掉已证明
的内存权限。通用属性生成和传递不进入 `llvm_c_eh`，也不新增异常候选表让该插件
重新判断 Feng 已完成的异常证明。

当前 bundled Clang 22.1.8 在不加载插件时的直接属性映射已经核验：

| 已有事实 | 需要传递的 LLVM 属性 | 现有 C 属性的表达边界 |
| --- | --- | --- |
| 无向外传播异常，内存任意 | `nounwind` | `nothrow` 可独立表达 |
| 内存 none，异常未知或可能传播 | `memory(none)` | `const` 还会添加 `nounwind willreturn`，不能直接使用 |
| 内存 read，异常未知或可能传播 | `memory(read)` | `pure` 还会添加 `nounwind willreturn`，不能直接使用 |
| 内存 none／read，且无向外传播异常 | 对应内存属性及 `nounwind` | 仍不能据此添加 `willreturn`；不能直接等同于 `const`／`pure` |
| 内存 write 或按区域限制 | 对应 `memory(...)` | 已核验的现有 C 属性不能精确表达，需确定独立传递方式 |
| 内存 readwrite 或全未知 | 不收紧内存权限 | 仍独立保留已知的异常属性 |

证据见[无插件属性核验](../../temp/apple-container-verify-20260929/ATTRIBUTE-CHECK.md)；
[Clang 22.1.8 的实现](https://github.com/llvm/llvm-project/blob/llvmorg-22.1.8/clang/lib/CodeGen/CGCall.cpp#L2290-L2303)
明确为 `const`／`pure` 添加上述三类属性。不存在由“不访问内存且不抛异常”推出
“一定返回”的规则；例如无内存访问的无限循环仍须保留。

替代机制尚待确认：若要求完整传递独立内存权限，可由 Feng 所属的独立属性转换
pass 消费 C IR 中的编译期元信息，仅将已证明事实转换成 LLVM 属性，不重新推导
异常，不依赖 `llvm_c_eh`。这与仅使用现有 C 属性是两种实现范围；后者不能完整
表达上表，必须明确未消费的事实，不能宣称第二阶段已经完整交付。该选择不改变
第一阶段摘要，也不授权增加返回性推导、修改工具链或新建插件。

本轮属性落在原生函数声明／定义上。已求解的调用点事实可独立查询，但某次回调
实参代入得到的更强结果不能用于收紧共享函数的声明属性；本轮未新增调用点属性。

原实现的待移除表格式见[函数契约传递协议](c-ir-function-contracts.md)，不再作为新方案。

### 6.3 能完成哪些优化，不能保证什么

信息足够精确且满足其他条件时，LLVM 可利用它减少调用后重复加载、冗余写回及
不必要异常边，并为寄存器保留和向量化创造条件。只读调用允许读取内存，因此不能
一般地跨越可能修改其读取范围的写操作移动或合并。

这两类摘要不包含函数的具体计算结果，不能让一个任意外部函数自动变成硬件 `fsqrt`。
它们也不直接证明数组下标范围、对象存活、指针可解引用、数组基址关系或所有访存
对齐条件。某些删除／外提还需要返回性、别名及安全执行证明。

因此应区分三个结论：

1. LLVM 能利用独立异常／内存属性：本轮静态 IR 对照已确认，见 §7.2。
2. 仅这两类属性足以重现前期 nbody 所测配对循环的指令改善：本轮已确认，但仍有
   数组辅助实现可见的诊断前提，见 §7.2。
3. 正式 Feng 因此稳定达到 Swift：链路实现后的验证见 §7.3–7.4；热点仍有未证明
   信息，正常分配及 macOS 多位置对照也未完成，不能由前两项推导。

### 7.2 本轮独立属性静态核验

2026-09-28 启动，2026-09-29 整理。使用 bundled Clang 22.1.8、`-O2`、默认
向量化及现有异常插件，不使用 LTO；只生成 LLVM IR 和汇编，不链接或运行新程序。
方法、命令及原始输出见[独立属性核验](../../temp/memory-attributes-20260928/RESULTS.md)。

先从同一份 C 取得未优化 IR，再只修改一条外部函数声明，分别加入 `nounwind`、
`memory(none)`、两者、两者加 `willreturn` 及前期完整组合。被调用函数没有函数体；
脚本核对逆向替换后能够逐字节恢复共同输入，避免 C 属性暗含额外承诺。

最小外部调用用例得到以下结果：

| 提供的信息 | 调用前后读取次数 | 该调用的异常边 | 返回值未使用的调用 |
| --- | ---: | --- | --- |
| 无 | 2 | 保留 | 保留 |
| 仅 `nounwind` | 2 | 消除 | 保留 |
| 仅 `memory(none)` | 1 | 保留 | 保留 |
| 两者 | 1 | 消除 | 保留 |
| 两者加 `willreturn` | 1 | 消除 | 删除 |

nbody 的静态对照继续使用数组辅助实现可见的原诊断基线：

| 提供的信息 | 配对循环指令数 | 外部调用 | 栈访问指令 | 双精度向量算术指令 |
| --- | ---: | ---: | ---: | ---: |
| 无 | 83 | 1 | 22 | 0 |
| 仅 `nounwind` | 83 | 1 | 22 | 0 |
| 仅 `memory(none)` | 43 | 1 | 2 | 6 |
| 两者 | 51 | 1 | 7 | 3 |
| 两者加 `willreturn` | 51 | 1 | 7 | 3 |
| 前期完整属性组合 | 51 | 1 | 7 | 3 |

前期完整组合为 `mustprogress nofree nosync nounwind willreturn memory(none)`。
无属性及完整组合两组，分别与前期实验对应循环的规范化指令逐条一致；两项属性组
也与完整组合组逐条一致。规范化只处理空白与基本块标签的函数编号。
LLVM 从已提供的内存属性自行推导出 `nofree`／`nosync`，两项组并没有获得 `willreturn`。

由此确认：

1. **LLVM 确实能独立消费这两类信息，无需函数体、LTO 或强制内联。**
2. **在数组辅助实现已经可见的诊断前提下，这两项已足以重现前期 nbody 配对循环的
   关键指令改善，不需要额外手动声明 `willreturn`。**
3. 它们不是所有优化的充分条件：最小用例中删除未使用的调用仍需要返回性信息；
   nbody 的开方调用仍保留，数组事实及宽访存慢档也没有因此解决。

“仅内存”组的静态指令更少，但代码调度不同，本轮没有计时，不能认定该组更快。
不能为追求某个指令形状而隐瞒已证明的异常信息。

该次前期静态实验尚未验证完整 `@memory → FT → 导入 → 正式发码` 链路，也没有行为运行及
黑盒性能结果。上述结论只针对提供属性后的后端能力；不能将旧计时作为本轮成绩，
也不能宣称仅这项机制就能让正式 Feng 在所有数组位置达到 Swift。

原始诊断另存为 `/private/tmp/feng-memory-attributes-20260929.tar.gz`，SHA-256：
`c981b42603fd6d93f685585015fd85c0879c547d6cec038715d9cdc122976a27`。

### 7.4 正式黑盒基准与编译成本

同一容器、相同输入、Clang 22.1.8／O2，无 LTO，默认向量化；每项预热两轮，
前后版本与 C++ 交替测量七轮，使用既有独立参考结果校验输出。Feng 的 std 使用
对应编译器分别重建。完整命令、CPU 时间、RSS、全部样本及制品 SHA-256 见
[performance/results.json](../../temp/apple-container-verify-20260929/performance/results.json)。

| 基准／输入 | Feng 修改前中位秒 | Feng 修改后中位秒 | 同批 C++ O2 中位秒 | Feng 前／后峰值 RSS 中位 MiB |
| --- | ---: | ---: | ---: | ---: |
| nbody／20,000,000 步 | 1.9025 | 1.8995 | 0.6357 | 2.398／2.398 |
| binary-trees／深度 16 | 0.3969 | 0.4086 | 0.3087 | 29.910／29.883 |
| text-scan／32,000,000 行 | 8.8951 | 8.8172 | 0.1158 | 491.301／490.820 |

三个正式基准的前后二进制逐字节相同，SHA-256 与 `.text` 段校验均一致。
因此没有可归因于本轮改动的运行时收益或回退。计时差异来自相同程序的运行波动；
text-scan 还出现 49.9／53.9 秒的长尾，所有样本均保留，未筛选后重算成绩。
本结果也不能替代 macOS 的 Swift 同机及数组位置对照。

原因边界明确：本轮没有给未标注的 `Math.sqrt` 虚构内存契约，未证明的数组辅助
操作和 ARC 仍为 unknown。新链路能优化信息已充分的用例，不能为这些调用补齐尚未
证明的事实；当前正式 nbody 仍约为同批 C++ 的三倍耗时，Swift 目标尚未验收。

完整单文件编译（含 FT 读取、发码、Clang 与链接）中，nbody 三次中位数由
0.1720 秒增至 0.2258 秒，增加约 54 毫秒／31.3%；总 CPU 中位数约从 0.113 秒
增至 0.171 秒。峰值 RSS 约 61.8／61.9 MiB。binary-trees 与 text-scan 的各一次
编译样本分别为 0.1751→0.2213 秒、0.1603→0.2213 秒，不能据单次结果推断稳定比例。
这些是完整编译成本，不是单独的推导耗时；子进程峰值可能掩盖前端自身的内存变化。
CPU 使用 bash 内建 time，包含测量器的少量开销。

测量发生在最后一处坏包诊断生命周期修复之前；该修复只调整 FT 读取失败分支，
本表成功编译及运行路径未经过该分支。对应测量编译器、生成 C 和二进制均已留档。
