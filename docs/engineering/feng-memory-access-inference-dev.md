# Feng 内存访问推导与 `@memory` 注解开发方案

## 1. 状态、目标与范围

状态：2026-09-29，开发设计，尚未实现。本文记录本轮已确认的要求、实施边界及
LLVM 优化验证；不表示现有编译器已支持 `@memory`，也不表示 nbody 性能目标已达成。

目标是让编译器在不读取依赖包源码的情况下，取得可用于优化的函数内存访问摘要。
普通 Feng 函数由编译器推导，外部函数通过内建注解提供声明契约；摘要随符号及 `.ft`
跨包传递。与已有异常摘要一起，向后端提供准确的函数属性。

已确认的要求：

1. 普通 Feng 函数自动推导，手动内存注解限定在 `extern func`。
2. 无法证明的部分统一为 `unknown`，处理原则与异常推导一致。
3. 外部函数未显式标注时为 `unknown`；不按名称、库名、签名、返回类型或无异常
   属性猜测其内存行为，包括 `sqrt` 等已知名称。
4. 已证明的事实与未知部分分别保留，未知沿调用依赖及跨包摘要传播。
5. 异常、内存访问及是否返回是不同事实，不能互相代替。
6. 保持 Feng 现有语义与行为，不启用 LTO、不全局禁用向量化，默认保留 `-O2`。

本轮交付为开发文档及静态诊断，不修改生产实现、现有测试、runtime 私有 ABI 或
正式基准。注解参数形式、FT 编码及后端传递方式的候选细节在实施前完成 Review。

规范归属：

- 现有异常语义及摘要只引用[异常规范 §6](../specifications/feng-exception.md#6-编译期异常摘要)。
- 外部声明与 ABI 只引用[互操作规范](../specifications/feng-interop.md)。
- 符号持久化及完整性只引用[符号表规范](../specifications/feng-symbol-table.md)。
- 内存摘要及注解批准实施前，应先形成独立主规范；语言概要、互操作与符号表规范
  按职责引用，本文保留实现方案，不在多个文件重复定义行为。

## 2. 已有基础与实际缺口

### 2.1 异常摘要已经跨包可用

当前异常分析记录声明模板和调用点事实；Symbol 持有摘要，FT 写出必要依赖，消费端
恢复后按实参求解。无需重新建立一套异常推导系统。

| 环节 | 现有实现 |
| --- | --- |
| 声明及调用点分析 | `src/semantic/exception_effects.c`、`exception_graph.c`、`exception_solver.c` |
| Symbol 挂接 | `src/symbol/export.c` 的 `attach_exception_templates` |
| FT 写出、恢复 | `src/symbol/ft_write.c` 的 `build_exception_section`、`ft_read.c` 的 `parse_exception_effects` |
| 无源码导入 | `src/symbol/imported_module.c` 的 `get_exception_template` provider |
| 后端原生异常证明 | `third_party/llvm-c-eh/src/Lowering.cpp` 的 `refineNoUnwind` |

函数内部完整捕获异常，且没有其他异常逃逸时，对外摘要为空。内部被调用函数仍然
可能抛出异常：调用者的空摘要不应删除内部实际需要的捕获路径。当前原生 IR 证明
更保守，会检查内部调用是否可能展开；它尚未消费 FT 对外异常摘要。

### 2.2 待增加的能力

- 结构化内存访问摘要、声明及调用点查询。
- 有函数体时的自动推导、调用传播及递归求解。
- `extern func` 的 `@memory` 校验与显式契约接入。
- Symbol、FT、导入及缓存对内存摘要的保留。
- 将已证明的摘要转换为准确的 C／LLVM 属性，而不附加未经证明的其他承诺。

现有内建注解中没有 `@memory`。上述能力属于新增开发范围。

## 3. 摘要模型与推导

### 3.1 分开记录行为、知识状态及访问范围

摘要描述函数执行对调用方可观察内存的访问上界，不是某次运行的计数。候选行为分类
为不访问、只读、只写、可读写；`unknown` 单独表示证据不足。

“已知可能读写”与“未知”在某些后端场景中都需要保守处理，但编译元信息不能将它们
混为同一证明结果。分析尚未完成也不等于已证明没有访问。

模型需要区分参数可达内存、全局及其他状态，并保留调用／泛型／回调的依赖。
某一范围存在未知，不能抹掉其他范围已证明的事实；但未知调用如果可能触及全部范围，
就不能继续声称其中某个范围一定不被修改。具体范围编码及首轮精度待 Review。

未逃逸的局部临时存储与对调用方可观察的存储应区分。读取常量、分配器内部状态、
释放对象以及向调用者返回新分配存储的情况，需要按实际可观察行为建模；不能简单地
把“出现过 load/store”作为函数级摘要。

### 3.2 自动推导的处理路径

1. 复用完成类型与调用解析后的声明、接收者、实参及 callable 来源。
2. 汇总直接读写及实际会执行的隐式操作，形成参数化摘要。
3. 调用处代入被调用者摘要；泛型、spec 分发和回调沿用已解析身份，无法确定的依赖
   保留 `unknown`，不能按函数名或本次 benchmark 形态推断。
4. 对递归调用依赖求解到稳定状态；不能用迭代次数耗尽或未完成分析作为空摘要。
   需要终止求解的情形只能保守扩大为未知。
5. 发布不可变的声明摘要及调用点结果，供 Symbol、FT 和代码生成共同消费。

普通分支保守合并可能访问。完整捕获异常只改变异常传播结果，不会撤销抛出前已发生的
内存读写，也不会消除 catch 中的内存访问。

### 3.3 必须计入的隐式行为

推导必须覆盖最终实现，不得只检查 Feng 源码中显式赋值：

- ARC retain／release 对引用计数的读写，以及释放可能触发的终结器和回调。
- 参数、返回值、聚合值复制及清理所需的运行时操作。
- 全局／静态字段的惰性初始化、构造及隐式调用。
- 异常载荷、清理链、捕获状态等运行时访问。
- 外部调用实际可能产生的内存访问及回调。

如前端不能完整证明这些操作，相关部分为 `unknown`，后端不得据此发射更强属性。
源级事实与最终原生函数属性之间需要明确的校验边界；不能给源码看似只读、实际会修改
引用计数的整个原生函数无条件添加 `memory(read)`。

## 4. `@memory` 的候选形式与契约

以下参数形式是供 Review 的方案，尚不是已发布语法：

| 候选形式 | 声明内容 |
| --- | --- |
| `@memory("none")` | 没有对调用方可观察的内存读写 |
| `@memory("read")` | 可能读取，但不修改相应范围的内存 |
| `@memory("write")` | 对外只产生写入；局部临时存储等按摘要模型处理 |
| `@memory("readwrite")` | 可能读取和修改相应范围的内存 |
| 未标注 | `unknown`，不推测外部实现 |

注解限定在 `extern func`，产生与自动分析相同的结构化摘要。Feng 包内普通函数即使在
消费端没有源码，仍使用生产端推导后保存的 FT 摘要，不需要再由消费方手动声明。

声明是外部绑定作者提供的契约。编译器可检查适用位置、参数、冲突及结构，但在看不到
外部实现时无法证明契约真实；错误标注可能导致错误优化。摘要必须约束整个外部调用，
包括被它调用的函数及回调，不能只描述外部函数的部分正常路径。

内存注解不承诺 `nounwind`、`willreturn`、`noalias`、不会捕获参数或可任意提前执行。
这些性质有各自的来源及证明，不通过内存标注暗中增加。浮点环境、同步和其他可观察
行为也不能因内存摘要为 none 就被忽略。若当前模型无法证明这些行为与拟添加的
LLVM 属性相容，则保持未知或不添加该属性，不能强行映射为 none。

`errno` 是需要考虑的状态。当前 `std/std/src/numeric/Math.ff` 的 `sqrt` 是未标注的
外部声明，按已确认规则仍为 `unknown`；本文不批准给 libm 函数批量添加 none。
未来若需表达“仅访问某类状态、不会修改参数内存”，应在同一范围模型中扩展，不能
为某个函数名添加特殊规则。

## 5. 跨包、FT 与缓存

复用现有异常摘要的生命周期与 provider 方式，内存摘要作为独立事实保存，不复用
异常节点去表达内存操作，也不要求发布函数体或通用控制流图。

需要保存：声明身份、参数化访问范围与读写信息、未知部分及必要调用依赖。
私有辅助函数的影响应能够汇总到可导出声明，但不因此改变私有符号的语言可见性。

导入方必须在没有生产端 AST／源码时得到一致结果；调用点替换不能修改共享的声明
摘要。已知回调和泛型实参可参与代入，仍开放或动态的部分保持未知。

摘要必须与对应库实现、目标配置和依赖身份一致，参与缓存失效及发布产物完整性检查。
旧产物缺少内存摘要不能解释为 none。FT 的节类型、版本／特征位以及旧发布包采用
保守读取还是要求重编，应在实施前确认；损坏元数据不能当作可信属性继续使用。

未标注的外部声明明确保存未知，不能在导入或代码生成阶段因识别库名／符号名而替换
为更强的 Feng 摘要。现有 C ABI 链接名称隔离和符号身份规则保持不变。

## 6. LLVM 消费方式及证明边界

### 6.1 两类信息的分工

| 事实 | LLVM 可消费的信息 | 不能据此推导 |
| --- | --- | --- |
| 实际原生函数没有向外传播的异常 | `nounwind` | 没有内存访问、一定返回、内部没有捕获路径 |
| 已证明／显式声明的内存访问范围与权限 | `memory(...)` 或等价属性 | 不抛异常、一定返回、不别名、数值运算身份 |
| 未知 | 不添加对应的限制性属性 | none、只读或不展开承诺 |

函数内部可以抛出并捕获异常，函数本身仍可满足 `nounwind`；内部可抛调用及其捕获
路径必须保留。现有 FT 空异常摘要作为输入，结合隐式调用及原生异常边界证明后，
才能安全用于原生函数；不能把外围 catch 筛选后的调用点结果贴到内部被调用函数上。

LLVM 的 [函数属性定义](https://llvm.org/docs/LangRef.html#function-attributes)及
[异常处理示例](https://llvm.org/docs/ExceptionHandling.html#windows-runtime-support)
分别说明这些属性和内部捕获的边界。

### 6.2 发码链路必须实际传递信息

FT 中存在摘要还不够，需要连接“导入摘要 → 原生声明／调用 → LLVM 属性”。
无函数体的声明也能承载这些属性，不要求 LTO 或调用内联。

不能未经核验把 `@memory("none")` 直接翻译成 C `__attribute__((const))`：此前
本机实验中，Clang 由后者同时生成了 `memory(none)`、`nounwind`、`willreturn`
等属性，会超过单独的内存契约。

实施时优先核验当前 bundled Clang 能否准确表达每个独立事实；不能直接表达时，再
评审通用的声明／调用元信息到 LLVM 属性的传递方式。不要把 Feng 包格式或函数名
识别塞入现有语言无关的异常插件。信息的落点和执行阶段必须通过优化前后 IR 确认。

### 6.3 能完成哪些优化，不能保证什么

信息足够精确且满足其他条件时，LLVM 可利用它减少调用后重复加载、冗余写回及
不必要异常边，并为寄存器保留和向量化创造条件。只读调用允许读取内存，因此不能
一般地跨越可能修改其读取范围的写操作移动或合并。

这两类摘要不包含函数的具体计算结果，不能让一个任意外部函数自动变成硬件 `fsqrt`。
它们也不直接证明数组下标范围、对象存活、指针可解引用、数组基址关系或所有访存
对齐条件。某些删除／外提还需要返回性、别名及安全执行证明。

因此应区分三个结论：

1. LLVM 能利用独立异常／内存属性：本轮静态 IR 对照已确认，见 §7.2。
2. 仅这两类属性足以重现前期 nbody 所测配对循环的指令改善：本轮已确认，但仍有
   数组辅助实现可见的诊断前提，见 §7.2。
3. 正式 Feng 因此稳定达到 Swift：还需要完整发码链路、正常分配及多位置实测，
   不能由前两项推导。

## 7. 验证记录

### 7.1 前期证据及限制

前期[属性实验](../../temp/nbody-sqrt-effects-20260928/RESULTS.md)使用数组辅助实现
可见的诊断基线，开方调用保留；属性组同时包含内存、异常与返回性等信息。该组配对
循环由 83 条指令／22 条栈访问变成 51 条／7 条。该历史批次没有分离各项属性，不能
仅据该批将全部收益归于本方案的两类摘要；本轮补充验证见 §7.2。

该批三个数组位置约 0.78～0.79 秒，同批 Swift 约 0.88 秒；另两个位置仍约
1.96～2.05 秒。完整位置、输入和前提见原记录；这些是历史诊断数据，不是本轮新测量。
宽访存造成的慢档及已有因果对照引用
[nbody 调查](./feng-nbody-performance-optimize.md#实施前定向验证结果)，不在本文重新定义
分配或后端访存方案。

### 7.2 本轮独立属性静态核验

2026-09-28 启动，2026-09-29 整理。使用 bundled Clang 22.1.8、`-O2`、默认
向量化及现有异常插件，不使用 LTO；只生成 LLVM IR 和汇编，不链接或运行新程序。
方法、命令及原始输出见[独立属性核验](../../temp/memory-attributes-20260928/RESULTS.md)。

先从同一份 C 取得未优化 IR，再只修改一条外部函数声明，分别加入 `nounwind`、
`memory(none)`、两者、两者加 `willreturn` 及前期完整组合。被调用函数没有函数体；
脚本核对逆向替换后能够逐字节恢复共同输入，避免 C 属性暗含额外承诺。

最小外部调用用例得到以下结果：

| 提供的信息 | 调用前后读取次数 | 该调用的异常边 | 返回值未使用的调用 |
| --- | ---: | --- | --- |
| 无 | 2 | 保留 | 保留 |
| 仅 `nounwind` | 2 | 消除 | 保留 |
| 仅 `memory(none)` | 1 | 保留 | 保留 |
| 两者 | 1 | 消除 | 保留 |
| 两者加 `willreturn` | 1 | 消除 | 删除 |

nbody 的静态对照继续使用数组辅助实现可见的原诊断基线：

| 提供的信息 | 配对循环指令数 | 外部调用 | 栈访问指令 | 双精度向量算术指令 |
| --- | ---: | ---: | ---: | ---: |
| 无 | 83 | 1 | 22 | 0 |
| 仅 `nounwind` | 83 | 1 | 22 | 0 |
| 仅 `memory(none)` | 43 | 1 | 2 | 6 |
| 两者 | 51 | 1 | 7 | 3 |
| 两者加 `willreturn` | 51 | 1 | 7 | 3 |
| 前期完整属性组合 | 51 | 1 | 7 | 3 |

前期完整组合为 `mustprogress nofree nosync nounwind willreturn memory(none)`。
无属性及完整组合两组，分别与前期实验对应循环的规范化指令逐条一致；两项属性组
也与完整组合组逐条一致。规范化只处理空白与基本块标签的函数编号。
LLVM 从已提供的内存属性自行推导出 `nofree`／`nosync`，两项组并没有获得 `willreturn`。

由此确认：

1. **LLVM 确实能独立消费这两类信息，无需函数体、LTO 或强制内联。**
2. **在数组辅助实现已经可见的诊断前提下，这两项已足以重现前期 nbody 配对循环的
   关键指令改善，不需要额外手动声明 `willreturn`。**
3. 它们不是所有优化的充分条件：最小用例中删除未使用的调用仍需要返回性信息；
   nbody 的开方调用仍保留，数组事实及宽访存慢档也没有因此解决。

“仅内存”组的静态指令更少，但代码调度不同，本轮没有计时，不能认定该组更快。
不能为追求某个指令形状而隐瞒已证明的异常信息。

本轮没有验证完整 `@memory → FT → 导入 → 正式发码` 链路，没有新的行为运行及
黑盒性能结果。上述结论只针对提供属性后的后端能力；不能将旧计时作为本轮成绩，
也不能宣称仅这项机制就能让正式 Feng 在所有数组位置达到 Swift。

## 8. 实施顺序与验收

1. 完成主规范和 Review：明确内存范围、注解参数、隐式调用覆盖、FT 兼容及后端落点。
2. 实现自动推导与外部注解输入，复用符号／调用身份，分别暴露声明与调用点摘要。
3. 接入 Symbol、FT、无源码导入及缓存，完成跨包完整性验证。
4. 接入独立 LLVM 属性传递，保持未知、异常匹配及清理语义。
5. 完成编译器测试、语言行为和性能验证。非文档实现必须在沙箱外通过全量 `make test`。

编译器测试重点：

- none／read／write／readwrite 与 unknown 的区分，分支、递归、泛型、spec 和回调传播。
- 无注解 extern 始终未知；不根据函数名、签名或异常摘要补强。
- 注解位置、参数与冲突诊断；具体诊断码在实施设计时分配，不预占现有编号。
- ARC、惰性初始化、构造／析构和失败路径不会被遗漏。
- 捕获异常不撤销内存访问；无外抛函数的内部异常路径保持正确。
- 两种 FT profile、销毁生产端 AST 后导入、多级依赖、损坏记录及缓存失效。
- 生成 IR 只具有获准的属性，不意外添加 `willreturn`、`noalias` 或移除真实异常边。

FCTS 重点：跨包调用前后的读写可见性、别名、回调、异常捕获／重抛、ARC 与清理顺序。
既有测试修改仍须逐项取得人工批准，不用调整断言掩盖行为变化。

性能验证保持既有 nbody 黑盒输入，覆盖正常分配及已知地址位置，记录 wall／CPU、
代码与制品身份，并复查 binary-trees、text-scan 及编译耗时／内存。新摘要在编译期
处理，不增加运行时检查；若实现需要新增运行时开销、特判或 runtime ABI 修改，
按仓库规则另行提交人工决策。
