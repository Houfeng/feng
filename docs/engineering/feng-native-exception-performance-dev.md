# Feng 原生异常处理性能优化方案

## 1. 状态、目标与边界

状态：2026-09-25 人工批准开始实施；CFG／非外抛契约优化已通过完整 `make test`。
五个目标的 std／FCTS release 行为验证也已通过；整体性能目标尚未完成，资源边界
候选 O04／O11 待人工决定。
本文基于 S11 修复提交 `426adb15` 的代码和既有测量，不把候选优化写成已验证收益。

人工明确本次目标：**异常相关开销不能明显比同工具链 C++ 差，其他优化后续单独处理。**
在保障行为正确的前提下，将本范围内的异常处理开销压到当前工具链和目标平台能够
达到的最小。正常路径因异常处理增加的成本与实际抛出路径分别优化，`-O0` 和
release 同等纳入验收，不能用 release 的结果抵消 O0 的退化，也不能因某次计时
接近就宣称零开销。

具体要求：

1. 消除 S11 转换带来的可消除跳转、临时保存、不必要异常边和重复处理。
2. 对剩余开销逐项说明用途、正确性约束、机器码证据及优化尝试；不能统一归为
   “原生异常机制必需”，也不能未经验证承诺所有程序与旧实现逐指令相同。
3. 正常路径不因本次优化增加异常状态检查、协议查询、堆分配、ARC、锁或 TLS 访问。
4. 保持调用内联和原有优化级别；不恢复 `setjmp/longjmp`，不增加整函数禁优化、
   强制禁内联、手工异常跳转或按源码写法／函数名称生效的插件特判。
5. 保持调试、sanitizer、异常匹配、泛型、跨包、清理顺序与所有权行为。
6. 使用标量和普通函数调用建立 C++ 对照，比较异常能力／try 的正常路径增量，
   以及实际 throw／catch 的成本，方法见 §6.3。纯标量总耗时作为控制数据，
   不将“Feng 整体执行速度接近 C++”扩大为本次交付目标。

“最小”的验收依据是可重复的行为测试、IR／机器码检查和性能测量，而不是一个脱离
输入与平台的百分比。本范围内发现仍有可行优化时须继续分析；有残余成本无法消除
或存在性能取舍时，将具体证据交人工决定，不自行降低目标或宣布全部完成。

既有函数 marker／TLS 清理链的维护、ARC、通用算术与普通函数发码等，作为本次
对比的背景成本记录，不开展独立优化。它们与异常安全存在关联，但不因此纳入整套
资源管理重构。异常专属或本次新增的操作仍计入异常成本，不能借此排除。

以下规则仅引用主文档，本文不重复定义：

- 异常与 defer 语义：[异常规范](../specifications/feng-exception.md)、
  [defer 规范](../specifications/feng-defer.md)。
- 原生 EH 协议、独立插件职责及构建：[插件开发文档](./c-ir-llvm-exception-plugin-dev.md)。
- driver、sanitizer 链接器及分发布局：[工具链接入文档](./feng-llvm-c-eh-integration-dev.md)。
- S11 原因、正确性修复、历史版本与原始成本：[S11 修复文档](./feng-release-exception-unwind-bugfix.md)。

本方案保留 C IR、通用插件和原生展开路线，不默认改变 LLVM 版本、driver 选项、
链接器、FT 格式、语言诊断、runtime 对外签名或结构布局。需要越过这些边界时，
先记录原因、替代方案及成本，由人工决定。

## 2. 已确认的成本与证据边界

### 2.1 测量口径

原始数字集中保存在 [S11 §7.1](./feng-release-exception-unwind-bugfix.md#71-正常与异常路径成本待人工-review)。
测量使用同机 LLVM 22.1.8，旧编译器及配套 runtime 从 `0575d00d` 重建，源码和
结果断言相同；一次预热后交替运行七次，记录总运行时间的中位数。

其中普通调用为 **2000 万次循环，每轮调用一次函数**。函数包含条件抛出，但测量
输入全部正常返回；O0 从 106.360 ms 增至 119.159 ms，即多 12.799 ms，约 12.03%。
这是包含循环等工作的程序耗时，不是单独计量一条 call 指令。try 正常返回样本也是
2000 万次；实际抛出并捕获样本为 20 万次，不能混用循环次数。

旧 release 的异常处理有 S11，不能把其错误执行作为“更快且等价”的目标。
保存的部分汇编使用较短循环，能说明相同循环体的指令差异，但不能冒充长循环计时
二进制的逐字节反汇编；正式优化验收须将源码、二进制、汇编与测量一一关联。

### 2.2 实施前的检查结果

以下记录 S11 修复基线，优化后的变化与验证结果见 §9。

| 编号 | 已确认事实 | 对应实现与含义 |
| --- | --- | --- |
| P01 | O0 普通函数入口有连续无条件跳转，正常调用返回后可见额外结果写栈／读栈 | Codegen 生成根清理入口；插件拆分调用后继，但转换结束后没有统一的结构清理。应区分可删除中转块与真正 `invoke` 的必要边界。 |
| P02 | `feng_frame_push`、`feng_try_frame_push`、`feng_frame_pop` 的声明没有不抛异常属性 | 当前实现维护清理链，错误路径调用最终 abort 的 `feng_panic`，不调用用户回调。插件只对 `doesNotThrow()` 为真的调用免建异常边，存在补齐真实契约的机会。 |
| P03 | 原生异常表在 search／cleanup 阶段由 personality 查询 | decoder 逐项读取编码字段、调用点及 action 链；清理入口执行后可能调用 `_Unwind_Resume`。这是实际 throw 的工作，尚未测出各项占比。 |
| P04 | release 普通调用样本的热点循环指令相同；部分 try 样本反而更快 | 优化器可消除中转块与临时保存，新实现也删除了旧区间登记判断及保活读取。不能推广为全部正常路径无增量。 |
| P05 | 部分 O0 栈帧和 release finalizer 栈帧增大，代码／异常表体积增加 | 即使运行时间没有稳定差异，也必须继续检查栈、寄存器保存和冷代码体积。栈大小变化本身不能直接换算为耗时。 |

代码依据：

- [Codegen](../../src/codegen/codegen.c)：`cg_emit_function_eh_prologue`、
  `cg_emit_function_fallthrough`、`cg_emit_scope_eh_state`。
- [插件转换](../../third_party/llvm-c-eh/src/Lowering.cpp)：`prepareCFG`、`analyze`、
  `invoke`、`createLandings`、`lower`。
- [runtime 声明](../../src/runtime/feng_runtime.h)、
  [异常实现](../../src/runtime/feng_exception.c)、[panic 实现](../../src/runtime/feng_panic.c)。
- [LSDA decoder](../../src/runtime/feng_exception_lsda.c)。

既有 `FengFrameMarker` 的压栈／弹栈和 TLS 清理链在 S11 前就存在，不能把它们的全部
成本算成 S11 增量。已有异常载荷分配和 ARC 也不属于本轮已确认新增成本。

S11 基线的纯标量样本 release 热点循环保留 `feng_frame_push`／`feng_frame_pop`，
即使循环内没有执行 retain／release，也会进行函数调用、marker 字段初始化及 TLS
清理链访问。因此，“不触发 ARC”不等于“已经没有 Feng 的额外运行时工作”；当前
实施前尚无这组 Feng 与 C++ 的等价基准结果（实施后对照见 O07／O11）。
此项背景成本须与异常增量分开报告，
本次不以消除它、达到纯标量总性能一致为目标。

LLVM 的“零成本异常”指正常路径无需检查异常状态或执行检查点保存，不保证寄存器
分配、代码布局、栈大小以及真实 throw 的成本完全不变。
参见 [LLVM Exception Handling](https://llvm.org/docs/ExceptionHandling.html#itanium-abi-zero-cost-exception-handling)。

## 3. 分层职责与拟改动范围

| 层次 | 优化职责 | 边界 |
| --- | --- | --- |
| 通用插件 | 清理协议转换的结构残留，消费真实 LLVM 调用属性，保留必要原生 EH | 不读取 Feng 异常图、类型、runtime 名称或资源布局；无协议输入保持既有行为。 |
| Feng Codegen | 正确提供 callable／调用点事实，消除建立原生 EH 所引入的发码冗余 | 不扩展为普通算术、调用或资源管理优化，不通过新增运行时判断替代编译期证明。 |
| Feng runtime | 声明经过审计的非外抛契约，优化原生异常表查询与展开衔接 | 不直接扩大异常记录、catch context 或 frame 布局，不牺牲清理与重入正确性。 |
| 测试与维护 | 固定性能基准、扩充正确性覆盖、重建并验证插件产物 | 复用现有构建入口，不新增 Python 脚本，不改变发行／sanitizer 默认配置。 |

下列路线按顺序实施和测量，分别记录收益，避免多项叠加后无法归因。
本范围内路线均需评估；只有获得证明和收益的实现才进入产品。发现其他层的优化
机会时记录后续项，不自动纳入；若它阻碍本次异常性能目标，提交证据由人工决定。

## 4. 正常路径优化

### 4.1 清理协议转换后的控制流

在原生异常边和 SSA 结果建立完成、协议标记已消除之后，执行有边界的结构清理：

1. 根据完整普通边和异常边删除真正不可达块；不能在转换前仅从普通入口判死 landing。
2. 折叠没有实际选择的中转分支、合法的单前驱 PHI，合并可安全合并的连续普通块。
3. 清理协议转换遗留的无用值，减少不必要的异常结果中转；保留有副作用、sanitizer
   检查、用户变量和正常／异常路径真正需要的值。
4. 核查正常返回路径的块布局，使不必要的绕行有机会成为直接落入后继的执行路径。
   是否减少机器跳转必须看目标机器码，不能只统计 IR 中的块数。
5. 重新校验 dominance、PHI、调用属性、调试记录及整个函数，保证转换幂等。

优先复用 LLVM 22.1.8 的基本块工具，避免自建第二套 CFG 优化器。清理作为协议
转换的一部分在 O0 也执行，只作用于本次转换的函数；不移除 `optnone`，不运行
整套 O1／O2 优化，不改变无协议函数。仅处理协议转换引入或暴露的结构残留，
不扩展为普通源码控制流或算术的通用优化项目。

**不能把每个调用后的分块都当成冗余。** `invoke` 自身就是带普通／异常后继的终结
指令，不能为了合块恢复成可能丢失异常边的普通 `call`。LLVM 的
[`MergeBlockIntoPredecessor`](https://github.com/llvm/llvm-project/blob/llvmorg-22.1.8/llvm/lib/Transforms/Utils/BasicBlockUtils.cpp)
也会拒绝破坏展开终结指令的合并。因此本步骤不预先承诺能消除全部 O0 spill／reload；
残留项应结合下一步的非外抛证明和同等语义的原生 EH 对照继续分析。

需要重点保持 DAP 的行级停靠、同一行多个语句、多行 if／match／try／return、
局部变量和单步行为。不能以隐藏用户源码位置或减少既有断点断言换取更短机器码。

### 4.2 补齐 runtime 的真实非外抛契约

先审计 `feng_frame_push`、`feng_try_frame_push`、`feng_frame_pop` 及其错误路径，
再沿不必要异常边涉及的实际调用图审计。每个候选都记录函数实现、间接调用／回调、
失败方式、声明传播位置与验证结果；不按 `feng_*` 前缀批量标记。这里只消除错误保守
假设产生的异常处理工作，不优化这些函数原本的 marker 初始化或清理链操作。

对证明不会向调用方展开异常的函数，在共享声明上提供 C 的 `nothrow` 属性，使 Clang
产生 LLVM `nounwind`。复用已有声明与属性组织，不在插件中加入函数名名单，不新增
供生成程序调用的 runtime API。声明和实现必须一致，相关对象按既有流程重编。

插件已有 `doesNotThrow()` 消费逻辑，预期可避免相关调用变成 `invoke`，减少正常
后继分块、异常表条目及可能的寄存器保存。实际改善仍需用 IR、机器码及计时确认。

以下情况不能据此自动标记：

- `feng_frame_release_to`、catch begin／end、release 等可能执行用户清理逻辑的路径。
- 仅有 `noreturn` 的 throw／rethrow；“不正常返回”不代表“不展开”。
- 没有可靠声明的外部调用、回调、动态 spec 调用，以及尚未审计的间接调用。
- 只因为某组输入没有抛出，或本次运行没有观察到异常。

错误的 `nounwind` 会使实际展开成为未定义行为，不是可保守尝试的性能提示。
依据见 [LLVM LangRef：函数属性](https://llvm.org/docs/LangRef.html#function-attributes)。
审计中不能证明的函数保留原生异常边，也不能改成 abort 或吞异常来满足属性。

### 4.3 使用现有异常元信息继续消除不必要异常边

此步骤须在前两步之后评估残留成本，使用现有编译期元信息，不增加诊断文本、
LSP 逻辑或 FT 格式。入口为
[`FengExceptionCallFacts`](../../src/semantic/exception_effects.h) 与现有 callable 模板。

语义层的“可能异常”不能不经审计就等同于 LLVM 的“不发生原生展开”。建立属性前
必须同时证明：

1. 源码调用在该位置的可能外抛集合为空，元信息存在、有效且已完成所需泛型代入。
2. 隐式发码中的分配、转换、ARC／析构、清理、桥接及运行时辅助调用也不会外抛，
   或已由函数内部正确捕获。
3. 间接目标、跨包导入和泛型共享体的适用范围与所标注的函数／调用点一致。
4. 声明、定义、包装函数和调用点对这一事实的表达一致，不通过函数指针转换绕过证明。

必须区分两件事：

- **函数整体不向外抛**：内部仍可能先抛再 catch；函数内部对应 `invoke` 不能删除。
- **某次调用不会抛**：不能使用调用方外层 catch 扣除后的集合来证明。
  `FengExceptionCallFacts.escaping_effects == 0` 可能只是异常被外层捕获，
  不能因此取消该调用到 catch 的异常边。

泛型共享体不能因为 `T=int` 的某次调用安全，就把所有 `T` 共用的函数定义标成
`nounwind`。函数级证明须覆盖所有允许实参；调用点证明只能用于适用的具体调用。
未知、缺失、未闭合或不完整事实一律保留异常边，不把 `unknown` 当成空集合。

优先复用当前查询和声明发码路径。如果完成这项证明需要新增跨包契约、改变语义
分析含义或引入新的通用分析接口，先提交实际缺口与最小方案，由人工决定后再实施。

### 4.4 既有资源清理成本的范围边界

函数 marker 的压栈／弹栈属于既有正常路径成本。标注非外抛属性不会自动删除这些
调用；也不能因为某个函数不抛就认定其没有资源管理职责。

本次保持既有函数 marker、TLS 清理链、ARC 和 defer 注册机制，不省略或重构资源
边界。其常规成本在对照中如实记录；相关独立优化留到后续任务，不是本文实施 Todo。

这不意味着所有名为 marker／TLS 的工作都可从异常成本中排除。例如新增 try 专属的
登记、catch 状态维护和异常值交接，确实因异常处理而发生，必须计入并分析。若达到
性能目标需要改变既有资源机制，明确记录影响和方案，由人工决定，不顺带实施。

## 5. 实际抛出路径优化

### 5.1 先分解成本

使用可重复的抛出／捕获基准及采样，将以下工作区分开：

- 既有异常记录和载荷构造、销毁。
- 展开器 search／cleanup 阶段、personality 的调用频次。
- LSDA 头、调用点条目、action 链及类型标识解码。
- 进入生成清理代码、处理逻辑作用域、再次 `resume`。
- catch 类型分派、进入／退出 catch、重抛和嵌套异常存续。

优先使用外部采样；若定位必须临时插桩，单独标明诊断构建，最终计时使用未插桩
产物。不能用“整个 throw 变慢约 43%”断言 decoder 占了全部增量。

### 5.2 按证据选择通用优化

| 候选 | 需要的证明与收益证据 |
| --- | --- |
| 减少不必要调用点／landing 条目 | 优先由真实 `nounwind` 和 CFG 清理自然产生；不手工删除仍可达的异常入口。 |
| 减少同一次查询中的重复解码／计算 | 不改变编码支持、类型匹配顺序、现有边界／溢出／action 环校验与错误返回。 |
| 根据 search／cleanup 实际需求减少工作 | 明确 handler frame、纯 cleanup、forced unwind 和重抛分别需要哪些结果，保留原有支持边界；如需调整 decoder 私有接口，列明调用方和测试影响后 Review。 |
| 精简生成清理块的中转和异常值保存 | 原异常记录与 selector 在全部父区域传播中保持一致，清理准确一次，内联后仍尊重各逻辑边界。 |

不默认引入跨查询缓存、全局索引、预登记、每次 try 初始化或额外 TLS 字段。
这些方法可能用正常路径开销、内存、锁或生命周期复杂度换取 throw 速度。
只有性能分析证明必要，并明确量化取舍后，才能提交人工决定。

不得删除必要的 cleanup／`resume`，不得恢复 S11 前“物理帧等同于逻辑函数”的
假设。旧 release 的不完整清理路径即使更快，也不是正确性等价的实现。

## 6. 性能验证方法与验收

### 6.1 三组对照与产物记录

固定三组源码／工具链组合：S11 前 `0575d00d`、已修复基线 `426adb15`、优化候选。
每组使用自身配套 compiler、runtime 与适用插件，禁止混用旧对象；在同一机器、
相同参数下比较。旧版仅用于行为断言能通过的参考路径；正式优化以 S11 正确版本
为主要基线，并追查 S11 引入的正常路径差额。

每项保存提交与本地 diff、Clang／链接器／插件身份、完整命令、目标架构、优化与
sanitizer 参数、源码、二进制、对应 IR／汇编、原始计时、退出码和结果断言。
存放工程 `build/`／`temp/`；全量清理前保留必要证据，禁止从系统临时目录执行产物。
这些记录不放入发行 `toolchain` 目录。

### 6.2 基准矩阵

| 维度 | 必须覆盖 |
| --- | --- |
| 普通调用 | 原 2000 万次非抛出循环、确定不外抛函数、有条件抛出但正常返回函数、动态输入避免循环被整体折叠。 |
| try 正常路径 | 无 try／单层／嵌套 try，具体 catch／兜底；正常返回、break／continue、提前 return。 |
| 资源 | 无资源／对象／值类型及聚合／defer／finalizer，分别记录正常退出与异常退出。 |
| 泛型 | 函数／类型／方法泛参、共享体、不同实参混用、开放约束和动态 spec 目标。 |
| 调用边界 | 同翻译单元允许正常内联；独立翻译单元／静态库保留实际调用；直接与间接调用。 |
| 抛出频率与深度 | 零抛出、稀疏抛出、每轮抛出；本地捕获与多层传播，嵌套 catch、重抛。 |
| 异常表规模 | 不同调用点数、catch 数和父区域深度，区分查表与实际资源清理成本。 |
| 构建 | O0／O2／O3 真实执行，O1 同时保留 IR／正确性覆盖；sanitizer 结果另列，不与非插桩计时混用。 |

原基准保留复测；额外基准补足其局限。普通 release 微基准中部分计算已被优化，
因此还需运行时输入和跨翻译单元对照。不能通过给产品加 `noinline`、循环内强加
`volatile` 或改变算法来制造收益。

独立插件基准复用现有
[`benchmark.sh`](../../third_party/llvm-c-eh/test/benchmark.sh) 的组织方式，增加
同等调用、清理、返回值语义的原生 EH 对照，用来区分协议转换残留与 LLVM 后端
本身的成本。它不能代替真实 Feng 基准，也不能用无清理的纯 C 函数作不等价对照。

### 6.3 异常相关开销的 C++ 对照

本组用真实 Feng 程序与等价 C++ 程序比较。Feng 仍由正式 driver 生成并编译 C IR，
不能用手写 C 模拟 Feng 发码取代，也不能给 C++ 人工加入 Feng 的 marker／TLS
维护后再宣称性能相同。目标是比较异常相关开销，不能把纯标量程序总耗时之差直接
当作异常开销之差。独立插件的等价原生 EH 对照用于辅助归因，不能替代真实 Feng
程序的结果。

“不触发 ARC”限定在被计时的循环及其调用路径：无对象／数组／string 构造、引用
计数增减、闭包分配、隐式装箱或资源析构；以生成代码和实际可达路径确认，不能只看
源码变量是标量。入口参数构造、进程启动／退出、计时和打印放在该区间外，另行报告
端到端耗时。当前 Feng 入口会构造 `args` 数组，不能将这部分当作标量循环的成本。

基本矩阵：

| 组别 | Feng 与 C++ 执行相同工作 | 对照目的 |
| --- | --- | --- |
| C01 | 标量运算、分支、循环，不调用其他函数 | 记录基础计算成本，作为控制项，不开展对应优化。 |
| C02 | 标量参数／返回值，调用不外抛的普通函数 | 记录普通调用与既有维护成本，并检查是否残留不必要异常边。 |
| C03 | 函数含条件抛出，全部计时输入走正常返回 | 查看异常能力对正常路径的影响；不能因这批输入不抛就错误标成 `nounwind`。 |
| C04 | try／catch 内调用 C03，单层及嵌套，计时期间均不抛出 | 查看 catch 存在时的正常路径成本。 |

每组都增加不计时的边界与错误输入验证，特别是 C03／C04 的实际抛出与捕获，避免
通过删除异常能力获得虚假的正常路径收益。无 ARC 但含 defer／其他清理动作的代码
仍有实际清理语义，按 §6.2 使用等价清理的对照，不能混入“纯标量、无清理”基准。

公平性要求：

1. Feng 生成的 C 与 C++ 使用同一套 Clang 22.1.8、目标架构、CPU 参数、优化级别、
   链接器及可比构建配置，保留各自真实 runtime 依赖；不改变日常 driver 默认配置。
2. C++ 保持异常启用，不使用 `-fno-exceptions`。只有同样可证明不外抛的场景才允许
   使用 `noexcept`；不能给可能外抛的 C++ 对照额外的优化承诺。
3. 算法、循环次数、输入、标量位宽、符号性和结果断言相同。优先采用双方语义一致
   的无符号运算；使用有符号数时须约束不溢出，不能利用 C++ 有符号溢出的未定义
   行为与 Feng 回绕语义之间的差异取得“优势”。
4. 同翻译单元允许两侧正常内联；另设跨翻译单元／静态库且均不开 LTO 的组别，
   保留实际调用边界。两组分开报告，不靠给一侧加 `noinline` 对齐结果。
5. 使用运行时输入和可观察结果，检查两侧优化后的实际工作。允许合法内联与常量
   折叠，但若整个循环被消除，该组只能说明优化结果，不能用来计算每次调用成本。
6. 纯性能主对照均关闭 sanitizer；另外以匹配的 sanitizer 配置验证行为。不能将
   Feng 插桩构建与 C++ 非插桩构建混比，也不降低既有 sanitizer 检查。

按以下层次报告结果：

1. 保留两侧 C01–C04 的原始总时间、热点机器码、栈与 runtime 调用；背景成本不能
   从记录中消失，但不将它们的全部差值归因于异常。
2. 对相同 C03 callee 分别测无 try 和有 try 的正常返回路径，在每种语言内部配对
   求差，再比较两侧 try 增量。C03／C02 的异常能力对照也须保持正常计算和调用
   边界可比，并结合机器码确认差异来源。
3. 使用 S11 前、修复后、优化后的对照，以及通用插件与等价原生 EH 对照，检查
   两组样本共有的异常支持成本，避免仅作 try／无 try 相减而漏掉公共额外工作。
4. 时间相减不自动等于某段实现的精确成本：内联、寄存器分配和布局变化必须核对。
   C++ 增量接近零时报告绝对纳秒数、置信范围或样本离散程度，不以近零分母计算
   夸大比例。不能凭估计减去 marker／TLS 耗时后宣称达标。

O0 和 release 分别判断异常相关开销是否明显差于 C++；“明显”须有可重复测量和
归因支持，不自行设置宽松比例掩盖稳定退化。总程序仍有非异常性能差距时，单列
后续项，不能据此扩展本次优化范围。

实际 throw 的标量也可能需要异常载荷构造；Feng 当前标量 throw 会装箱并涉及载荷
所有权。因此实际抛出路径另按 §5 测量，不归入本组“计时区间无 ARC”的正常路径。
该路径同样与 C++ 对照：匹配载荷位宽、传播深度、catch 条件及必要清理，保留双方
真实异常记录／载荷构造、展开、捕获与销毁的总成本。异常发生才产生的这些成本
不能作为“其他优化”从结果中扣除；分项数据用于定位，不替代完整 throw／catch 数据。

### 6.4 测量与通过条件

- 预热后按配对顺序交替运行基线与候选，至少保留七组原始样本；小差异应增加
  样本与测量时长。记录中位数、离散程度和配对差值，不只选最快一次。
- 单独记录总时间、每次操作的平均时间、热点指令、分支、栈读写、栈大小、代码及
  异常表体积；硬件计数器不可用时明确记为未测，不能由汇编静态条数推算周期。
- O0 必须显式复测本次 12.03% 退化。目标是消除可消除增量；未恢复的差额逐项
  归因并提交 Review，不能以“debug 性能不重要”结案。
- release 各正常路径不能出现未经解释和批准的稳定退化。部分用例加速不能抵消
  另一个用例的退化，时间改善也不能掩盖栈或代码体积显著增加。
- 实际 throw 路径须先证明结果与清理完全一致，再报告收益；没有可靠收益的复杂
  优化不合入，未能实现的优化目标和原因必须明确交付。
- 不把固定毫秒数或一次微小波动写成共享 CI 的硬门槛；IR／行为不变量可自动断言，
  统计上仍不确定的性能结论继续测量或交人工 Review，不直接标为零增量。

通过条件包括：本范围内各候选都有评估结论；不存在未处理的已知可消除异常开销；
正常路径异常增量和实际 throw／catch 均有 C++ 对照，未发现未经解释和人工审定的
明显性能差距；剩余成本有必要性证据；全部功能回归通过。不能仅以一项微基准变快
宣布“最小开销”，也不将通用资源管理或普通计算速度一致加入交付条件。

函数尾部，typeid 随原 handler 移入该块，而 resume 块在前。计划将三者改为各自
验证存在和操作数；landingpad 的 cleanup／catch 连续性，以及调用属性、调试记录、
无协议函数不变、非法输入和幂等断言全部保留。修改前提交人工批准。

人工已批准本项迁移：操作存在性采用无顺序 DAG 检查，landingpad 的连续属性采用
独立 FileCheck 前缀。新增结构清理测试接入插件 Makefile 与现有维护构建脚本，
覆盖 optnone、真实可抛调用、无协议函数及逐字节幂等性。

### O04：正常路径剩余的 try 专属成本（2026-09-25，待人工决策）

有效配对测量与汇编均显示：组合优化后，try 正常路径仍有每层约 2 ns 的增量，
七轮结果见 O07；O06 后同翻译单元 O2 的无 try／有 try 分别为 2.250／4.269 ns。
汇编确认新增 try 的正常路径仍执行 `feng_try_frame_push` 与 `feng_frame_pop`；
无论保护体是否拥有待清理
资源，当前 Codegen 都无条件建立这一边界。不能把这部分 try 专属操作排除出目标。

拟采用通用的资源需求判定：根据发码时真正建立的清理所有权，决定某个 try 的
保护体是否需要正常路径 marker。无待清理资源时，将该 try 的 marker 初始化延后
到匹配 catch 的异常路径，再调用现有 catch begin；未匹配时直接向父区域传播。
有资源、defer 或内层 catch 所有权可能跨越异常边时保留现有保护边界；无法证明
同样保留。正常 return／break／continue 的 scope 退出须消费同一判定，不能另做
按源码表达式类型、函数名或基准名称生效的分支。

此方案不改函数级 marker、不新增 runtime API／字段、不改变 ARC 或 defer 机制，
但会改变 try 的资源边界建立时机，超出 §4.4 当前的保守边界。需要人工批准后才
实现，并覆盖资源临时值、嵌套 catch、重抛、早退、泛型与跨包；当前尚未修改该逻辑。

### O05：实际抛出对照的调用深度（2026-09-25）

首版基准把浅层实际抛出也经过递归 relay（depth=0）。汇编显示 C++ 消除了这一
层，而 Feng 的既有函数 marker 使其仍需进入 relay 并执行清理／resume。因此该
模式不是相同物理深度的浅层异常对照，不能用其差值断言 decoder 或异常本身慢。
修正新增基准：浅层和稀疏抛出直接调用 step；递归仍单列，按实际保留帧数解释。
修正后重新构建、采样，不复用旧二进制计时；尚未形成最终性能结论。

### O06：原生非外抛证明的层次（2026-09-25）

现有 `FengExceptionCallFacts` 记录语言层可能异常，没有单独承诺隐式 ARC、桥接、
描述符辅助调用的原生展开行为。因此不直接把空 effects 写成 nounwind，也不修改
语义查询 API 或 FT。共享体、跨包声明、动态调用继续保守处理。

对插件刚完成降级的函数，可以在 LLVM 层复用 `Instruction::mayThrow`、
`CallBase::doesNotThrow` 与真实定义属性给出更完整但保守的证明：全部可达指令均
不展开时才补函数 nounwind；随后仅在本模块已降级调用方中消除被证明无必要的
invoke 边，并再次清理真正不可达的 landing。通过调用者工作队列传播事实，不运行
普通算术优化或整套 IPO，不修改无协议输入。

不推断只有声明的外部符号、可替换定义或间接目标；递归若不能由已有声明证明，
同样保留。实际可抛调用、resume、未知清理辅助函数会阻止证明。该方法覆盖已经
发出的隐式原生调用，不需要把编辑器、诊断或展示逻辑引入核心编译器，也没有新增
跨包或 runtime 契约。正确性与收益需由独立 IR 用例、真实 Feng 和完整回归确认。

审计 LLVM 22.1.8 的 `Instruction::mayThrow` 实现后，确认它可把本地处理的 invoke
视为不外抛；这不足以替任意使用方的 personality 承诺全部异常类别都被捕获。
因此证明对所有 CallBase 显式要求 `doesNotThrow()`，其他指令包含 phase-one 检查，
不依赖“有 catch-all 就安全”的推断。

新增 IR 反例同时验证动态目标、递归自调用、weak 定义及其调用方继续保留异常边。
七轮配对测量中，同翻译单元 O0 的确定不抛普通函数，从 CFG＋属性的 8.020 ns／轮
降为 6.040 ns／轮；逐轮差值中位数为 −1.969 ns，区间 −2.536～−0.185 ns。
条件可抛函数、try 与实际抛出并未获得相同收益，release 也未观察到相应稳定收益；
跨包没有新增 nounwind 契约，不宣称能获得相同优化。原始数据与逐轮差值分别保存为
`proof-paired.tsv`、`proof-deltas.tsv`。本项已通过完整回归；整体性能目标仍有 O04／O11
所述差距，不能据此宣称全部完成。

### O11：原生控制结果与函数边界剩余项（2026-09-25，待人工决策）

共用同一个 C++ producer、计时对象及异常 runtime 的独立翻译单元对照完成七轮。
下表单位为 ns／次；无插桩、LLVM 22.1.8、macOS ARM64，真实抛出为 20 万次，
正常返回为 2000 万次。原始记录为 `native-control-samples.tsv`，完整产物已归档。

| 路径 | O0 协议 C／原生 C++ | O2 协议 C／原生 C++ | O3 协议 C／原生 C++ |
| --- | --- | --- | --- |
| 无 try 正常返回 | 1.600／1.667 | 1.202／1.216 | 1.210／1.190 |
| try 正常返回 | 1.920／1.813 | 1.195／1.204 | 1.219／1.210 |
| 实际 throw／catch | 2200.390／2195.470 | 2200.485／2216.215 | 2195.315／2193.230 |

协议 C 与原生 C++ 的 O0 invoke 返回均有相同的结果写栈／读栈，前者保护函数栈为
32 字节，后者 48 字节；协议 C 没有新增状态查询、TLS 或堆分配。O0 正常返回仍有
约 0.1 ns 的样本差异，不能宣称逐条机器码或性能完全相同。实际抛出结果接近，
不支持“整个 Feng O0 差距都来自协议转换”的判断。

实际 Feng 的纯标量 step 仍有函数 marker，因此 throw 要先进入自身 cleanup、
调用 release_to，再 resume；原生 C++ 的标量 producer 没有这一清理入口。Feng
与 C++ 的载荷分配、展开库也不同，尚不能将全部差额精确归因于这一个因素。

同翻译单元 release 的内联可以消除部分此类清理层，但独立翻译单元仍有差距：
O06 后 O2 浅层 throw／catch，Feng 为 3218.820 ns／次，C++ 为 2208.795 ns／次。
因此不能只用同翻译单元中 Feng 的 1677.505 ns 对 C++ 的 1859.370 ns 宣称抛出
路径已经达标。两组均来自同一轮次组织的七轮记录 `proof-report.tsv`。

若继续尝试消除这一异常路径开销，需要越过 §4.4 的函数边界冻结：复用 O04 的
通用清理资源需求判定，仅对本 callable 没有任何清理所有权、catch 所有权或 defer
的情况省略函数 marker 及其根清理区；有资源、开放描述符或无法证明的情况保留。
不改 runtime API／布局，不按函数名、类型名或基准特判；正常和异常退出必须共用
同一证明。该候选也会减少原有函数 marker 成本，因此须人工批准范围后再实现，
不能把它包装成单纯插件合块。本轮目前没有修改函数或 try 的资源边界发码。
