# Feng 原生异常处理性能优化方案

## 1. 状态、目标与边界

状态：2026-09-25 根据人工要求整理，待 Review；尚未实施优化。
本文基于 S11 修复提交 `426adb15` 的代码和既有测量，不把候选优化写成已验证收益。

目标是极致性能：在保障行为正确的前提下，将异常处理开销压到当前工具链和目标平台
能够达到的最小。正常路径与实际抛出路径分别优化，`-O0` 和 release 同等纳入验收，
不能用 release 的结果抵消 O0 的退化，也不能因某次计时接近就宣称零开销。

具体要求：

1. 消除 S11 转换带来的可消除跳转、临时保存、不必要异常边和重复处理。
2. 对剩余开销逐项说明用途、正确性约束、机器码证据及优化尝试；不能统一归为
   “原生异常机制必需”，也不能未经验证承诺所有程序与旧实现逐指令相同。
3. 正常路径不因本次优化增加异常状态检查、协议查询、堆分配、ARC、锁或 TLS 访问。
4. 保持调用内联和原有优化级别；不恢复 `setjmp/longjmp`，不增加整函数禁优化、
   强制禁内联、手工异常跳转或按源码写法／函数名称生效的插件特判。
5. 保持调试、sanitizer、异常匹配、泛型、跨包、清理顺序与所有权行为。

“最小”的验收依据是可重复的行为测试、IR／机器码检查和性能测量，而不是一个脱离
输入与平台的百分比。发现仍有可行优化时须继续分析；有残余成本无法消除或存在性能
取舍时，将具体证据交人工决定，不自行降低目标或宣布全部完成。

以下规则仅引用主文档，本文不重复定义：

- 异常与 defer 语义：[异常规范](../specifications/feng-exception.md)、
  [defer 规范](../specifications/feng-defer.md)。
- 原生 EH 协议、独立插件职责及构建：[插件开发文档](./c-ir-llvm-exception-plugin-dev.md)。
- driver、sanitizer 链接器及分发布局：[工具链接入文档](./feng-llvm-c-eh-integration-dev.md)。
- S11 原因、正确性修复、历史版本与原始成本：[S11 修复文档](./feng-release-exception-unwind-bugfix.md)。

本方案保留 C IR、通用插件和原生展开路线，不默认改变 LLVM 版本、driver 选项、
链接器、FT 格式、语言诊断、runtime 对外签名或结构布局。需要越过这些边界时，
先记录原因、替代方案及成本，由人工决定。

## 2. 已确认的成本与证据边界

### 2.1 测量口径

原始数字集中保存在 [S11 §7.1](./feng-release-exception-unwind-bugfix.md#71-正常与异常路径成本待人工-review)。
测量使用同机 LLVM 22.1.8，旧编译器及配套 runtime 从 `0575d00d` 重建，源码和
结果断言相同；一次预热后交替运行七次，记录总运行时间的中位数。

其中普通调用为 **2000 万次循环，每轮调用一次函数**。函数包含条件抛出，但测量
输入全部正常返回；O0 从 106.360 ms 增至 119.159 ms，即多 12.799 ms，约 12.03%。
这是包含循环等工作的程序耗时，不是单独计量一条 call 指令。try 正常返回样本也是
2000 万次；实际抛出并捕获样本为 20 万次，不能混用循环次数。

旧 release 的异常处理有 S11，不能把其错误执行作为“更快且等价”的目标。
保存的部分汇编使用较短循环，能说明相同循环体的指令差异，但不能冒充长循环计时
二进制的逐字节反汇编；正式优化验收须将源码、二进制、汇编与测量一一关联。

### 2.2 当前实现的检查结果

| 编号 | 已确认事实 | 对应实现与含义 |
| --- | --- | --- |
| P01 | O0 普通函数入口有连续无条件跳转，正常调用返回后可见额外结果写栈／读栈 | Codegen 生成根清理入口；插件拆分调用后继，但转换结束后没有统一的结构清理。应区分可删除中转块与真正 `invoke` 的必要边界。 |
| P02 | `feng_frame_push`、`feng_try_frame_push`、`feng_frame_pop` 的声明没有不抛异常属性 | 当前实现维护清理链，错误路径调用最终 abort 的 `feng_panic`，不调用用户回调。插件只对 `doesNotThrow()` 为真的调用免建异常边，存在补齐真实契约的机会。 |
| P03 | 原生异常表在 search／cleanup 阶段由 personality 查询 | decoder 逐项读取编码字段、调用点及 action 链；清理入口执行后可能调用 `_Unwind_Resume`。这是实际 throw 的工作，尚未测出各项占比。 |
| P04 | release 普通调用样本的热点循环指令相同；部分 try 样本反而更快 | 优化器可消除中转块与临时保存，新实现也删除了旧区间登记判断及保活读取。不能推广为全部正常路径无增量。 |
| P05 | 部分 O0 栈帧和 release finalizer 栈帧增大，代码／异常表体积增加 | 即使运行时间没有稳定差异，也必须继续检查栈、寄存器保存和冷代码体积。栈大小变化本身不能直接换算为耗时。 |

代码依据：

- [Codegen](../../src/codegen/codegen.c)：`cg_emit_function_eh_prologue`、
  `cg_emit_function_fallthrough`、`cg_emit_scope_eh_state`。
- [插件转换](../../third_party/llvm-c-eh/src/Lowering.cpp)：`prepareCFG`、`analyze`、
  `invoke`、`createLandings`、`lower`。
- [runtime 声明](../../src/runtime/feng_runtime.h)、
  [异常实现](../../src/runtime/feng_exception.c)、[panic 实现](../../src/runtime/feng_panic.c)。
- [LSDA decoder](../../src/runtime/feng_exception_lsda.c)。

既有 `FengFrameMarker` 的压栈／弹栈和 TLS 清理链在 S11 前就存在，不能把它们的全部
成本算成 S11 增量。已有异常载荷分配和 ARC 也不属于本轮已确认新增成本。

LLVM 的“零成本异常”指正常路径无需检查异常状态或执行检查点保存，不保证寄存器
分配、代码布局、栈大小以及真实 throw 的成本完全不变。
参见 [LLVM Exception Handling](https://llvm.org/docs/ExceptionHandling.html#itanium-abi-zero-cost-exception-handling)。

## 3. 分层职责与拟改动范围

| 层次 | 优化职责 | 边界 |
| --- | --- | --- |
| 通用插件 | 清理协议转换的结构残留，消费真实 LLVM 调用属性，保留必要原生 EH | 不读取 Feng 异常图、类型、runtime 名称或资源布局；无协议输入保持既有行为。 |
| Feng Codegen | 正确提供 callable／调用点事实；必要时减少通用发码冗余 | 不通过新增运行时判断替代编译期证明，不为特定表达式或测试发码。 |
| Feng runtime | 声明经过审计的非外抛契约，优化原生异常表查询与展开衔接 | 不直接扩大异常记录、catch context 或 frame 布局，不牺牲清理与重入正确性。 |
| 测试与维护 | 固定性能基准、扩充正确性覆盖、重建并验证插件产物 | 复用现有构建入口，不新增 Python 脚本，不改变发行／sanitizer 默认配置。 |

下列路线按顺序实施和测量，分别记录收益，避免多项叠加后无法归因。
全部路线均需评估；只有获得证明和收益的实现才进入产品。需要更大范围变更的候选
单独提交人工 Review，不因标题为性能优化而自动取得修改其他层契约的授权。

## 4. 正常路径优化

### 4.1 清理协议转换后的控制流

在原生异常边和 SSA 结果建立完成、协议标记已消除之后，执行有边界的结构清理：

1. 根据完整普通边和异常边删除真正不可达块；不能在转换前仅从普通入口判死 landing。
2. 折叠没有实际选择的中转分支、合法的单前驱 PHI，合并可安全合并的连续普通块。
3. 清理协议转换遗留的无用值，减少不必要的异常结果中转；保留有副作用、sanitizer
   检查、用户变量和正常／异常路径真正需要的值。
4. 核查正常返回路径的块布局，使不必要的绕行有机会成为直接落入后继的执行路径。
   是否减少机器跳转必须看目标机器码，不能只统计 IR 中的块数。
5. 重新校验 dominance、PHI、调用属性、调试记录及整个函数，保证转换幂等。

优先复用 LLVM 22.1.8 的基本块工具，避免自建第二套 CFG 优化器。清理作为协议
转换的一部分在 O0 也执行，只作用于本次转换的函数；不移除 `optnone`，不运行
整套 O1／O2 优化，不改变无协议函数。

**不能把每个调用后的分块都当成冗余。** `invoke` 自身就是带普通／异常后继的终结
指令，不能为了合块恢复成可能丢失异常边的普通 `call`。LLVM 的
[`MergeBlockIntoPredecessor`](https://github.com/llvm/llvm-project/blob/llvmorg-22.1.8/llvm/lib/Transforms/Utils/BasicBlockUtils.cpp)
也会拒绝破坏展开终结指令的合并。因此本步骤不预先承诺能消除全部 O0 spill／reload；
残留项应结合下一步的非外抛证明和同等语义的原生 EH 对照继续分析。

需要重点保持 DAP 的行级停靠、同一行多个语句、多行 if／match／try／return、
局部变量和单步行为。不能以隐藏用户源码位置或减少既有断点断言换取更短机器码。

### 4.2 补齐 runtime 的真实非外抛契约

先审计 `feng_frame_push`、`feng_try_frame_push`、`feng_frame_pop` 及其错误路径，
再沿正常路径实际调用图扩大审计范围。每个候选都记录函数实现、间接调用／回调、
失败方式、声明传播位置与验证结果；不按 `feng_*` 前缀批量标记。

对证明不会向调用方展开异常的函数，在共享声明上提供 C 的 `nothrow` 属性，使 Clang
产生 LLVM `nounwind`。复用已有声明与属性组织，不在插件中加入函数名名单，不新增
供生成程序调用的 runtime API。声明和实现必须一致，相关对象按既有流程重编。

插件已有 `doesNotThrow()` 消费逻辑，预期可避免相关调用变成 `invoke`，减少正常
后继分块、异常表条目及可能的寄存器保存。实际改善仍需用 IR、机器码及计时确认。

以下情况不能据此自动标记：

- `feng_frame_release_to`、catch begin／end、release 等可能执行用户清理逻辑的路径。
- 仅有 `noreturn` 的 throw／rethrow；“不正常返回”不代表“不展开”。
- 没有可靠声明的外部调用、回调、动态 spec 调用，以及尚未审计的间接调用。
- 只因为某组输入没有抛出，或本次运行没有观察到异常。

错误的 `nounwind` 会使实际展开成为未定义行为，不是可保守尝试的性能提示。
依据见 [LLVM LangRef：函数属性](https://llvm.org/docs/LangRef.html#function-attributes)。
审计中不能证明的函数保留原生异常边，也不能改成 abort 或吞异常来满足属性。

### 4.3 使用现有异常元信息继续消除不必要异常边

此步骤须在前两步之后评估残留成本，使用现有编译期元信息，不增加诊断文本、
LSP 逻辑或 FT 格式。入口为
[`FengExceptionCallFacts`](../../src/semantic/exception_effects.h) 与现有 callable 模板。

语义层的“可能异常”不能不经审计就等同于 LLVM 的“不发生原生展开”。建立属性前
必须同时证明：

1. 源码调用在该位置的可能外抛集合为空，元信息存在、有效且已完成所需泛型代入。
2. 隐式发码中的分配、转换、ARC／析构、清理、桥接及运行时辅助调用也不会外抛，
   或已由函数内部正确捕获。
3. 间接目标、跨包导入和泛型共享体的适用范围与所标注的函数／调用点一致。
4. 声明、定义、包装函数和调用点对这一事实的表达一致，不通过函数指针转换绕过证明。

必须区分两件事：

- **函数整体不向外抛**：内部仍可能先抛再 catch；函数内部对应 `invoke` 不能删除。
- **某次调用不会抛**：不能使用调用方外层 catch 扣除后的集合来证明。
  `FengExceptionCallFacts.escaping_effects == 0` 可能只是异常被外层捕获，
  不能因此取消该调用到 catch 的异常边。

泛型共享体不能因为 `T=int` 的某次调用安全，就把所有 `T` 共用的函数定义标成
`nounwind`。函数级证明须覆盖所有允许实参；调用点证明只能用于适用的具体调用。
未知、缺失、未闭合或不完整事实一律保留异常边，不把 `unknown` 当成空集合。

优先复用当前查询和声明发码路径。如果完成这项证明需要新增跨包契约、改变语义
分析含义或引入新的通用分析接口，先提交实际缺口与最小方案，由人工决定后再实施。

### 4.4 既有资源边界的进一步精简

函数 marker 的压栈／弹栈属于既有正常路径成本。标注非外抛属性不会自动删除这些
调用；也不能因为某个函数不抛就认定其没有资源管理职责。

完成前述优化后，如它仍是主要成本，评估是否能用统一的作用域／所有权事实证明
某类边界完全无用。证明必须涵盖正常退出、异常退出、子调用、内联、资源转移、
defer、catch 存续及嵌套重入，不能仅检查“函数没有显式 throw／局部变量”。

插件不解释 Feng 清理链。任何边界省略都应在 Feng 层以通用事实驱动；删除 marker
会改变实际清理链，须先提交独立证明和对照结果供人工决定。本项是本方案要求评估
的候选，不是默认批准重构 ARC／资源管理系统。

## 5. 实际抛出路径优化

### 5.1 先分解成本

使用可重复的抛出／捕获基准及采样，将以下工作区分开：

- 既有异常记录和载荷构造、销毁。
- 展开器 search／cleanup 阶段、personality 的调用频次。
- LSDA 头、调用点条目、action 链及类型标识解码。
- 进入生成清理代码、处理逻辑作用域、再次 `resume`。
- catch 类型分派、进入／退出 catch、重抛和嵌套异常存续。

优先使用外部采样；若定位必须临时插桩，单独标明诊断构建，最终计时使用未插桩
产物。不能用“整个 throw 变慢约 43%”断言 decoder 占了全部增量。

### 5.2 按证据选择通用优化

| 候选 | 需要的证明与收益证据 |
| --- | --- |
| 减少不必要调用点／landing 条目 | 优先由真实 `nounwind` 和 CFG 清理自然产生；不手工删除仍可达的异常入口。 |
| 减少同一次查询中的重复解码／计算 | 不改变编码支持、类型匹配顺序、现有边界／溢出／action 环校验与错误返回。 |
| 根据 search／cleanup 实际需求减少工作 | 明确 handler frame、纯 cleanup、forced unwind 和重抛分别需要哪些结果，保留原有支持边界；如需调整 decoder 私有接口，列明调用方和测试影响后 Review。 |
| 精简生成清理块的中转和异常值保存 | 原异常记录与 selector 在全部父区域传播中保持一致，清理准确一次，内联后仍尊重各逻辑边界。 |

不默认引入跨查询缓存、全局索引、预登记、每次 try 初始化或额外 TLS 字段。
这些方法可能用正常路径开销、内存、锁或生命周期复杂度换取 throw 速度。
只有性能分析证明必要，并明确量化取舍后，才能提交人工决定。

不得删除必要的 cleanup／`resume`，不得恢复 S11 前“物理帧等同于逻辑函数”的
假设。旧 release 的不完整清理路径即使更快，也不是正确性等价的实现。

## 6. 性能验证方法与验收

### 6.1 三组对照与产物记录

固定三组源码／工具链组合：S11 前 `0575d00d`、已修复基线 `426adb15`、优化候选。
每组使用自身配套 compiler、runtime 与适用插件，禁止混用旧对象；在同一机器、
相同参数下比较。旧版仅用于行为断言能通过的参考路径；正式优化以 S11 正确版本
为主要基线，并追查 S11 引入的正常路径差额。

每项保存提交与本地 diff、Clang／链接器／插件身份、完整命令、目标架构、优化与
sanitizer 参数、源码、二进制、对应 IR／汇编、原始计时、退出码和结果断言。
存放工程 `build/`／`temp/`；全量清理前保留必要证据，禁止从系统临时目录执行产物。
这些记录不放入发行 `toolchain` 目录。

### 6.2 基准矩阵

| 维度 | 必须覆盖 |
| --- | --- |
| 普通调用 | 原 2000 万次非抛出循环、确定不外抛函数、有条件抛出但正常返回函数、动态输入避免循环被整体折叠。 |
| try 正常路径 | 无 try／单层／嵌套 try，具体 catch／兜底；正常返回、break／continue、提前 return。 |
| 资源 | 无资源／对象／值类型及聚合／defer／finalizer，分别记录正常退出与异常退出。 |
| 泛型 | 函数／类型／方法泛参、共享体、不同实参混用、开放约束和动态 spec 目标。 |
| 调用边界 | 同翻译单元允许正常内联；独立翻译单元／静态库保留实际调用；直接与间接调用。 |
| 抛出频率与深度 | 零抛出、稀疏抛出、每轮抛出；本地捕获与多层传播，嵌套 catch、重抛。 |
| 异常表规模 | 不同调用点数、catch 数和父区域深度，区分查表与实际资源清理成本。 |
| 构建 | O0／O2／O3 真实执行，O1 同时保留 IR／正确性覆盖；sanitizer 结果另列，不与非插桩计时混用。 |

原基准保留复测；额外基准补足其局限。普通 release 微基准中部分计算已被优化，
因此还需运行时输入和跨翻译单元对照。不能通过给产品加 `noinline`、循环内强加
`volatile` 或改变算法来制造收益。

独立插件基准复用现有
[`benchmark.sh`](../../third_party/llvm-c-eh/test/benchmark.sh) 的组织方式，增加
同等调用、清理、返回值语义的原生 EH 对照，用来区分协议转换残留与 LLVM 后端
本身的成本。它不能代替真实 Feng 基准，也不能用无清理的纯 C 函数作不等价对照。

### 6.3 测量与通过条件

- 预热后按配对顺序交替运行基线与候选，至少保留七组原始样本；小差异应增加
  样本与测量时长。记录中位数、离散程度和配对差值，不只选最快一次。
- 单独记录总时间、每次操作的平均时间、热点指令、分支、栈读写、栈大小、代码及
  异常表体积；硬件计数器不可用时明确记为未测，不能由汇编静态条数推算周期。
- O0 必须显式复测本次 12.03% 退化。目标是消除可消除增量；未恢复的差额逐项
  归因并提交 Review，不能以“debug 性能不重要”结案。
- release 各正常路径不能出现未经解释和批准的稳定退化。部分用例加速不能抵消
  另一个用例的退化，时间改善也不能掩盖栈或代码体积显著增加。
- 实际 throw 路径须先证明结果与清理完全一致，再报告收益；没有可靠收益的复杂
  优化不合入，未能实现的优化目标和原因必须明确交付。
- 不把固定毫秒数或一次微小波动写成共享 CI 的硬门槛；IR／行为不变量可自动断言，
  统计上仍不确定的性能结论继续测量或交人工 Review，不直接标为零增量。

通过条件包括：本方案各候选都有评估结论；不存在未处理的已知可消除开销；剩余
成本有必要性证据；全部功能回归通过。不能仅以一项微基准变快宣布“最小开销”。

## 7. 正确性覆盖与完整交付

| 层次 | 验证要求 |
| --- | --- |
| 插件结构 | 无协议输入不变；协议标记消除；普通入口／landing 隔离；PHI 与 dominance；循环、分支合流和早退；保留调用约定、属性、调试记录；重复执行幂等；非法输入仍拒绝。 |
| 非外抛证明 | 真正不抛的调用不产生多余异常边；真正可抛、unknown、缺失事实、动态目标仍保留；外层 catch 扣除后为空不导致误删；`noreturn` 与 `nounwind` 分开验证。 |
| 泛型／跨包 | 类型／方法／函数泛参、共享体多实参、递归调用；隐藏生产者源码，仅消费 FT／静态库；生产者和消费者 O0／release 四种组合。 |
| 异常／资源 | S11 原始 BIND10 与最小复现；具体／兜底／未匹配 catch；catch 再抛；异常记录身份与生命周期；嵌套、重入及线程隔离；内联前后清理顺序、次数、ARC 和 defer 一致。 |
| decoder | 既有合法编码、边界值、无 landing、action 链、类型顺序、溢出、截断与环负例全部保留；针对每项优化增加相应边界与对照。 |
| 调试 | O0 行级断点、同一行多语句、多行表达式、循环、catch／defer、stepIn／next／stepOut、locals／hover／watch 不退化。 |
| sanitizer | 使用 Release 插件编译正常与 UBSan 使用方，保留真实 UB 检测、恢复／终止行为；执行既有 ASan 覆盖，不修改 sanitizer 默认策略。 |

测试分工继续遵循仓库约定：`test/` 验证诊断、IR、代码生成和 runtime；`fcts/`
验证语言行为；插件独立测试验证协议。修改任何既有测试前须取得人工批准，不能
自行改语义、断言或门槛。如原断言限制了合法优化，先说明它验证的契约及替代断言，
由人工批准后再迁移。

实施后必须执行沙箱外完整 `make test`，并显式执行完整 std／FCTS release 回归。
后者当前不是 `make test` 自动覆盖的完整套件，不能省略或混写为已自动执行。
每个平台分别记录实际命令和结果。

插件变更后，通过现有维护脚本重建三个 host 产物；正常与 sanitizer 两种上层配置
均验证。目标程序覆盖 macOS ARM64，以及 Linux ARM64／x64 的 GNU／musl 目标。
交叉编译、原生执行和 Rosetta 执行分别记录；性能结论只依据对应架构的原生运行，
缺少原生环境时保留待验收项，不能以模拟执行冒充。

不顺带升级工具链、修改补丁 LLD、增加发布文件或改变 CI 策略。确有新增需求时
单列原因，由人工决定。
