## 1. 目标与规范归属

保留 Feng 的 ARC 和 Bacon–Rajan 试验性删除方向，按以下职责分层完善：

1. 编译器完整分析托管强引用关系；只有证明不可能参与环的类型才标记为无环。
2. 在正确分类的基础上，通用地消除有完整保活与生命周期证明的冗余 ARC 对；
   不以类型可能成环作为禁止消除的充分理由。
3. 对保留的释放操作，无环对象不登记循环候选；其余对象在强引用减少且未归零时
   登记为待检查候选，保证真实拥有关系消失时不遗漏不可达环。
4. 再量化并降低剩余候选登记、同步和收集成本，以消除全局 STW 为后续目标。

性能目标保持为提升或持平，不增加未经人工接受的运行时成本。不按评测名称、
具体类型名或固定对象规模选择实现，也不以漏回收、延迟普通 ARC 销毁、改变
终结器与复活行为换取性能。分阶段验证不等于接受阶段性退化作为最终交付。

生命周期规则以[生命周期主规范](../specifications/feng-lifetime.md)为准；泛型、
跨包和 ABI 边界分别引用[泛型规范](../specifications/feng-generics-draft.md)与
[互操作规范](../specifications/feng-interop.md)。本文只定义优化讨论范围，不另立
一套语言语义。若方案需要澄清或调整现有规范，先提交人工确认，再修改主规范。

## 2. 与现有算法是否冲突

**结论：上述分层与 ARC、Bacon–Rajan 没有根本冲突；但候选过滤的正确性、遍历
完整性和并发一致性必须分别成立，不能仅凭一个类型标记推导整条路径安全或廉价。**

[Bacon 与 Rajan 的原论文](https://link.springer.com/chapter/10.1007/3-540-45337-7_12)
第 3 节讨论同步试验性删除，第 3.2 节专门讨论利用类型信息排除固有无环对象。
因此，编译期证明与候选过滤符合算法方向；论文中的无环分类条件与 Feng 的
完整表示模型不能直接等同，仍需建立本项目的证明与覆盖。

| 本方案职责 | 与现有机制的关系 | 兼容前提 |
| --- | --- | --- |
| 编译期无环证明 | 为循环收集减少候选，不替换 ARC | 不能把任何可能参与强引用环的实例归入无环类型 |
| 通用 ARC 成对消除 | 减少冗余临时拥有者及其派生工作 | 证明保活与生命周期正确，保持真实拥有者释放及候选完整性，不能只看增减成对 |
| 引用计数归零 | 继续由普通 ARC 处理 | 保留终结器、复活和候选记录的生命周期约束 |
| 非归零释放登记候选 | 符合 Bacon–Rajan 的候选来源 | 候选只是待检查对象，不代表已成环或已不可达 |
| 收集器判断不可达 | 继续通过子图及引用关系确认 | 不能仅凭引用数为 1 或类型可能成环就释放 |
| 优化登记与扫描 | 可以改善当前实现 | 保持候选不遗漏、边计数正确和存活对象不误回收 |
| 无全局 STW | 与算法家族方向不矛盾 | 当前同步实现不能通过删除锁直接变成并发算法 |

### 2.1 类型图与实例图的关系

类型图必须保守覆盖所有实际托管强引用边。运行时若存在强引用环，沿该环投影到
完整类型关系中，也必须存在相应的闭合路径。因此，完整证明某类型不能参与环，
可以用于排除该类型对象的候选资格；反之，类型图存在环只表示可能性。

判定针对具体类型，不要求整个程序的类型图都无环。`Node → Option<Node> → Node`
即使在某个程序中只被用于构造树，仍属于潜在循环关系。本文不把构造顺序、逃逸
分析或实例无环证明作为首轮修复前提；字段为 `let` 也不等于可达对象全部不可变。

“覆盖所有场景”要求不漏判，不要求每种类型都得到精确答案。不能证明时保守
处理；错误地标为无环可能漏回收，保守标为潜在循环则可能增加检查成本。

### 2.2 不登记候选，不等于跳过相关子对象

“无环对象永不进入循环回收器”在本方案中仅指：不作为候选根登记，普通 ARC
释放绕过候选管理。不能据此跳过子引用处理或直接在 walker 中遇到无环标记就返回。

例如 `A ↔ B → C`，`C` 不参与环，但回收 `A/B` 时仍需正确处理对 `C` 的引用；
若 `C` 还有外部拥有者，必须存活，否则应按生命周期规则释放。原论文第 3.2 节
也明确保留了死环所持无环对象的处理。当前 Feng 的候选过滤和子引用遍历是分开的。

还需区别“对象自身不能参与环”和“它的整个可达子图不含环”。前者不能自动作为
跳过整个子图的证明。本文不提出这样的遍历裁剪。

union 漏判的复现、独立补丁及历史受控性能结果，统一见

并发方面还有必须核实的边界：runtime 注释描述锁保护潜在循环对象的 retain/release，

把“所有图修改都被锁保护”作为后续优化已成立的前提。

## 4. 编译期分类的细化方向

### 4.1 证明对象与未知信息

分析沿实际拥有的托管强引用关系展开，不沿名称、方法签名或非拥有原始指针猜测。
必须覆盖以下表示及组合，并区分内嵌存储和独立托管对象：

- 普通对象、内嵌值对象、tuple、union 的所有可能活动成员及嵌套组合。
- 数组及多维数组、闭包环境、捕获单元、装箱对象等实际拥有托管引用的表示。
- object spec、交集／擦除表示等动态 subject；无法完整限定实际类型时保守处理。
- 泛型实际参与存储的参数、具体实例以及递归泛型；未使用的泛参不凭空产生强引用边。
- 同包、跨包公开 FT 和本地缓存 FT；不以依赖源码恰好可见作为正确性的前提。

“未知”不能作为一个没有出边的普通叶节点结束分析。必须保证未知关系可能形成的
回边及受影响类型仍被保守覆盖。递归类型的求解必须终止，不能无限展开实例组合。

### 4.2 事实如何传给 runtime

优先复用现有描述符的 `is_potentially_cyclic`：已证明无环对应 false，其余对应 true。
这不要求 runtime 增加第三种状态，也不要求每次 release 重新分析类型图。

阶段 1 的分类约定已收敛到生命周期主规范；实现不增加 FT 字段、泛型摘要格式
或 runtime ABI 字段。图节点只属于编译器临时分析数据。

必须逐类确认分类事实能到达实际对象头所使用的描述符。特别是共享数组描述符、
闭包和装箱表示，不能因普通 `type` 描述符正确就认为整个托管对象范围已覆盖。
如需调整元数据承载方式，先给出最小方案和成本，交由人工决定。

### 4.3 第一阶段实施范围

分类约定以 [生命周期规范 §11](../specifications/feng-lifetime.md#11-编译期) 为准。
本阶段仅补齐分类与描述符事实传递，不增加 ARC 消除规则，不修改候选阈值、锁或收集流程。

- 在 `semantic/cyclic.c` 内扩展现有类型图与迭代 Tarjan 求解，复用
  `FengTypeRef.resolution_decl`／`resolution_program` 和字段类型事实。
  具化节点按声明身份及替换后的实参区分；不增加 FT 字段或 runtime ABI。
- 开放泛型声明中实际参与存储的未知实参按未知处理；具体实例单独查询同一分析，
  使 `Box<int>`、`Box<Leaf>` 与带回边的具化能够得到各自结论。
- 对同一求解路径重复出现的声明，完全相同的实例复用节点；实参结构严格缩小的
  嵌套实例继续展开；其余不断变化的递归具化保守归入未知，防止无限扩展。
  这是通用的有限证明边界，不按类型名、评测或固定展开深度处理。
- 未知信息沿强引用反向传播；已知 SCC 本身的标记不无条件传播给外部拥有者。
  内嵌表示只展开实际字段／成员，静态字段和方法签名不参与。
- Codegen 为具体泛型对象查询具化结果；同时审计默认 spec subject、闭包、捕获单元、
  值装箱的实际对象描述符。现有安全的保守标记保持，不增加释放入口。
- 数组候选登记的描述符调整已获人工批准：仅增加一份私有静态描述符，创建时依据
  已有元素表示选择；无托管槽使用原无环描述符，含托管引用保守使用可能成环描述符。
  两份描述符须注释说明用途；不增加字段或实例大小，不改 API 或 release 算法。
  现有所有权判断中“所有数组均不登记候选”的前提随之校正，保留原有保守策略；
  这不实施第二阶段解除循环标记限制的 ARC 优化。

新增验证覆盖无环与直接／间接环、嵌套 union／value／tuple、推导字段、静态字段与
原始指针对照、同名不同声明、动态 subject、开放／闭合／递归泛型及未使用泛参，
并核对源码与两类 FT 的一致性、实际描述符与真实生命周期。Linux 容器运行
`make test`，以同工具链和输入对照修改前后的五项评测，另测数组候选路径的成本。
分类修正导致的成本须如实报告，不以实施后续 ARC 优化为由掩盖或接受退化。

## 5. ARC 与候选登记的边界

### 5.1 真实拥有关系与候选完整性

下表描述逻辑职责，不规定原子操作和锁的先后顺序；并发安全的具体顺序仍需证明。

| 正常 release 的结果 | 处理职责 |
| --- | --- |
| 引用计数归零 | 沿用 ARC 销毁流程，处理已有候选记录和终结器复活 |
| 引用计数未归零，已证明无环 | 不登记循环候选 |
| 引用计数未归零，可能成环或未知 | 进入候选登记，避免同一轮重复登记 |

保留 `feng_release` 单一释放实现和现有签名；不新增按类型区分的释放 API。
候选记录不是新增一份程序强引用，不能改变用户可见存活判定；但必须有明确的
内存有效性保障，不能让缓冲区保留已释放对象的裸指针。

候选登记、实际扫描与最终回收是三个不同事件。不能用 `refcount == 1` 证明对象
无环，也不能因对象一度被扫描为存活，就永久取消之后重新成为候选的机会。
终结器复活、再次失去外部引用及收集中产生的新候选，沿用主规范的行为边界。

这里兼容 Bacon–Rajan 的关键条件是：不可达环不能因过滤或事件遗漏而失去发现
机会。仅证明“每个环里至少有一个类型带 true 标记”还不够，必须核对实际发生的
引用递减与重新登记，尤其是最后外部拥有者通过容器或动态 subject 释放的情况。

### 5.2 类型成环与 ARC 成对消除分别证明

类型图分析回答“该类型的实例是否可能参与强引用环”；所有权分析回答“这份临时
引用是否需要独立保活”。两者不能互相替代：潜在循环对象可以安全借用，无环对象
也可能需要额外 retain。不能只因类型可能成环就恢复全部临时计数，也不能只因
局部值不逃逸、retain/release 数量相等就删除操作。

通用消除复用[所有权优化文档](feng-arc-ownership-performance-dev.md)的保活、转移
与退出清理证明。本方案明确：循环标记本身不作为消除的否决条件；每一对候选
操作仍须证明以下条件，未知时保留原操作：

1. 已有真实拥有者或稳定的强引用保活路径覆盖待消除引用原本应保障的整个生命周期，
   不能仅覆盖最后一次读取而提前执行终结器；路径必须连接到有效的外部拥有者，
   不能把环内互相持有误当成外部保活。
2. 后续实参求值、赋值、别名写入、回调及受支持的并发访问不会破坏对象身份或
   保活路径。`let`、只读语法和局部不逃逸均不能单独代替该证明。
3. 正常、早退和异常退出都保持最后真实拥有者的释放时机及普通 ARC 销毁行为；
   返回、存储、捕获或跨边界传递需要独立所有权时，仍按现有契约建立或转移。
4. 若临时所有权完全消除，仅同步移除其独占的清理登记，保持其余 LIFO 清理、
   defer、终结器和复活规则。不借此重写异常机制或省略其他资源清理。
5. 保留真实拥有关系消失对应的 release 和必要候选登记，覆盖存活扫描后再次
   失去外部引用的情况；不可达环不能因消除临时操作而失去发现与最终回收机会。

稳定借用结束并不等于最后真实外部拥有者消失，不必为此制造一份临时强引用再
释放。只有上述条件成立，才可同时减少计数、临时清理及其引发的候选／扫描工作。
不增加运行时所有权猜测，也不按语法形态或评测类型名设置例外。

### 5.3 不保留冗余临时引用偶然触发的扫描

生命周期主规范明确环内对象的回收时机不具确定性。因此，消除已证明冗余的
临时 retain/release，不要求保留原候选次数、每一次扫描或由该临时 release 偶然
决定的循环终结器执行点。先前以“可能触发其他对象的收集”为由一律阻止消除的
约束过强，本方案不再沿用；终结器与复活流程仍须符合主规范。

验收重点是存活对象不误回收、保证不可达环最终可回收，以及普通 ARC 的
确定性释放和其他生命周期行为不变。消除冗余操作后扫描次数减少，不等于修改
收集器阈值策略；不能反过来依赖冗余临时引用作为收集器必需的调度来源。

**候选完整性与收集进展需要分别验证。** 当前实现的触发入口是候选达到阈值与
runtime 关闭阶段，没有周期性或后台主动扫描。若候选一直低于阈值且不再产生
新候选，正常运行期间不会仅因时间经过而启动扫描。对持续运行的进程，“不可达环
最终回收”的进展保障还需在收集器阶段细化，不能仅凭已登记候选就宣称达成。
本方案不因此预先批准定时器、后台线程或新的触发策略；ARC 阶段若发现必要回收
机会被消除，必须作为正确性阻塞报告，不能留待下一阶段而宣称整体通过。

### 5.4 已有保活证明及复用边界

当前编译器已有以下事实与消费入口；本阶段复用这些机制，不另建运行时所有权检查。

| 已有事实／入口 | 代码位置 | 可以复用的证明及限制 |
| --- | --- | --- |
| `CGOwnedLocal`、`local_owner`、`borrowed_owner` | [ownership.c](../../src/codegen/detail/ownership.c) 的 `cg_result_borrows_local`、`cg_result_ownership_source`、`cg_stable_result_owner` | 以作用域和局部索引识别真正拥有整值的存储，跟随已有借用并检查祖先作用域覆盖；捕获、条件清理、动态存储等不能直接套用 |
| `managed_identity_is_stable` | [codegen.c](../../src/codegen/codegen.c) 的 `ExprResult`、`cg_emit_identifier` | 表示当前语句求值期间引用身份及拥有路径稳定；不能直接扩展为任意局部变量整个作用域的保活证明 |
| 不可变字段路径 | 同文件的 `cg_user_field_managed_identity_is_stable`、`cg_emit_user_field_borrow` | 稳定接收者加 `let` 字段可继续传播稳定性；字段投影不继承整值的 `local_owner`，也不表示整个可达对象图不可变 |
| 内嵌托管槽不可变 | [ownership.c](../../src/codegen/detail/ownership.c) 的 `cg_ownership_slots_are_immutable` | 检查闭合 union 各成员和内嵌值字段；引用对象停在句柄，不要求其所有子对象不可变；ABI 可写存储、未知布局继续保守 |
| 调用保护及参数契约 | [call_arguments.c](../../src/codegen/detail/call_arguments.c) 的 `cg_prepare_call_operand`、`cg_call_parameter_is_readonly`，以及 [parameters.c](../../src/codegen/detail/parameters.c) | 复用调用者保护实参、被调函数借用或建立独立参数存储的现有分工；参数默认不可重绑定不等于函数无副作用，仍须检查源拥有路径及值槽 |
| match 快照及实参借用 | [codegen.c](../../src/codegen/codegen.c) 的 `cg_materialize_match_subject`、[ownership.c](../../src/codegen/detail/ownership.c) 的 `cg_result_has_stable_aggregate_borrow` | 固定布局、槽位不可变且消费方式允许借用时，可不建立额外拥有者；保留快照语义、求值次数及原有退出清理 |

只读借用参数的存活依据来自调用者已保护的实参，不能仅因它是参数就将其视为
新增的独立强引用根；递归调用也须沿此契约连接到真实拥有者。普通
`let p = holder.child` 的字段借用不能只凭
当前语句的稳定标记跨越后续所有语句；若要消除整个局部绑定的引用，必须另证
原拥有者及字段引用覆盖 `p` 的完整生命周期。此类扩大覆盖不作为首轮热点消除的前提。

match 绑定规则由[控制流主规范 §3.2／§3.3](../specifications/feng-flow.md)定义：默认
不可变，也可显式声明 `var`。当前 `cg_materialize_match_subject` 发现任一分支使用
`var` 绑定时，会回退到独立拥有副本。首轮沿用此边界，即使该 `var` 分支暂未执行
赋值，也不据此省略托管副本；可变绑定的重绑定必须保留原有语义及清理责任。
默认／显式 `let` 则只是借用的必要条件之一，仍须通过拥有者和槽位证明。

## 6. 成本与优化方向

类型图求解发生在编译期，但改变分类结果会改变生成代码和运行路径。一个标记
判断的成本不能代表锁、候选维护、扫描、清理登记以及失去后端优化的总成本。

### 6.1 优先分离已知成本

先保持工具链、编译选项、runtime 和标准库可比，分别记录：

- 类型分类修正后恢复了哪些 retain/release、异常清理登记和实际机器码操作。
- 潜在循环对象归零与非归零释放各占多少，锁、候选去重／插入／移除各耗费多少。
- 扫描访问的节点／边、重复扫描、候选缓冲区分配和实际回收工作量。

诊断计数或对照变体不进入正式发布实现；性能收益以关闭诊断后的正式构建验证。
有缺陷的旧分类可用于归因，不能作为正确性合格的候选实现。

阶段 0 在 Linux 容器的独立源码、构建和运行目录中进行，临时文件放在 `temp/`。
可以仅在隔离副本中复现历史分类修正，不覆盖正式编译器、runtime、std 或 toolchain。
阶段 0 的归因对照保持锁、扫描、借用条件与阈值不变；后续 ARC 优化另按 §5.2
建立证明，不能以未经证明地放宽条件制造所谓优化收益。

优先使用采样剖析，辅以保持原有操作顺序的诊断计数。需要计时时先测量探针自身
扰动，分别报告未插桩耗时、插桩耗时和采样局限。成本归属采用以下口径，不能将
嵌套调用的包含时间反复相加：

| 类别 | 测量内容与边界 |
| --- | --- |
| 锁 | 获取／释放锁及实际等待；持锁期间执行的扫描不重复记为锁耗时 |
| 候选维护 | 去重、插入、移除、缓冲区维护；扣除由登记触发的实际收集 |
| 实际扫描／回收 | 扫描轮数、节点／边数、存活／垃圾结果及收集耗时；单列终结器／释放工作 |
| 额外 ARC | 修正前后的实际 retain/release、aggregate 操作与清理登记数量，结合最终 IR／汇编和热点归因 |

额外 ARC 操作也可能触发锁、候选或扫描，数量差和时间比例属于不同维度，不能
再次相加。无法可靠分离的部分标为未量化，不用函数调用数乘一个假定单次耗时
代替实测。完整保留计算校验、输入与算法，不修改评测主体。

### 6.2 候选优化及约束

| 方向 | 要解决的成本 | 实施前的约束 |
| --- | --- | --- |
| 通用 ARC 发码证明 | 正确分类后恢复的保活、清理及其派生候选／扫描 | 按 §5.2 证明每份临时所有权是否冗余；循环标记不单独否决消除，不要求保留偶然扫描 |
| 归零释放与同步路径 | 实际树、链表等也走潜在循环锁路径 | 不能直接取消锁或把锁移到递减之后；要证明与试验性删除、候选内存和复活协调正确 |
| 候选缓冲区复用与查找 | 重复分配、线性移除 | 保持嵌套终结器产生候选时的轮次隔离；额外常驻内存或对象头字段须评估并人工决定 |
| 收集工作组织 | 重复访问存活子图、终结器阶段查找 | 保留完整边计数和复活传播；不能把不参与环当作跳过子图的证明 |
| 触发策略与工作预算 | 同步扫描延迟及最终回收的进展保障 | 目前阈值触发由主规范规定；与 ARC 消除导致的扫描减少分开评估，策略变更需先 Review |

先完善类型图分析，再消除可证明冗余的 ARC 对，最后根据剩余成本选择收集器优化。
不能直接删除现有循环类型限制而跳过 §5 的证明；也不把该保守限制视为必须永久
保留的语义。收益和维护成本未确认前，不预选新的数据结构或调度算法。

### 6.3 无全局 STW 的边界

当前实现是带全局互斥锁的同步试验性删除，不等于已经实现 Bacon–Rajan 的并发
版本。后台线程仍可持有同一把锁阻塞业务；仅拆小扫描批次也不自动解决图并发变化。

后续设计需要明确：如何获取一致的引用关系、如何协调 retain/release 和字段修改、
候选对象如何保持有效、何时允许释放、如何处理终结器与复活，以及新增同步／记录
成本。可参考[后续并发循环收集研究](https://csaws.cs.technion.ac.il/~erez/Papers/CycleCollection.pdf)
所讨论的一致性与进展问题，但本文不批准直接移植某一并发算法。

无全局 STW 是待完成目标，不能通过更名或移到后台宣称达成；也不等于所有操作
无等待或任意用户终结器都具有固定耗时。验收需分别观察业务线程阻塞与收集延迟。

### 6.4 Linux 首轮隔离量化结果

2026-10-16，以 `e1b14b34` 为基线，在 Ubuntu 26.04 ARM64 容器中验证：4 个 vCPU、
8 GiB 内存，随仓 Clang／LLD 23.1.3，Release `-O2`、ThinLTO、`-ffp-contract=off`。
两个编译器的唯一源码差异是历史 patch 中的 `src/semantic/cyclic.c`；runtime、std
包和工具链完全相同。补丁未应用到正式工作区，也未改变评测算法、锁、阈值或扫描。

使用现有 binary-trees 的标准深度 16，先预热两轮，再交错测量七轮；每次都校验
结果，另校验深度 6、7、8。这里是针对已知退化的诊断，不是五项正式评测或全量回归。

| 未插桩版本 | 耗时中位数 | 七轮范围 | RSS 中位数 |
| --- | ---: | ---: | ---: |
| 当前分类，包含 union 漏判 | 304.4 ms | 301.9–309.2 ms | 17.27 MiB |
| 隔离副本修正 union 分类 | 1,684.3 ms | 1,674.2–1,698.2 ms | 17.26 MiB |

退化约为 5.53 倍，内存基本相同。前一行含已知正确性缺陷，只用于解释差距。

**未插桩机器码的采样归因。** 分别保留符号用于 `perf`，已核对其 `.text` 与原
Release 程序逐字节一致。每个版本采样五轮，使用 `task-clock:u`、997 Hz 与
16 KiB DWARF 栈；修正分类版本共 8,394 个样本，未报告丢样。候选管理已内联到
`feng_release` 的部分按汇编地址范围归类，扫描包含其内部调用，但不再计入锁或 ARC。

| 修正分类版本的互斥归因类别 | 合并样本占比 | 各轮范围 |
| --- | ---: | ---: |
| 实际扫描／收集 | 47.3% | 46.2%–48.6% |
| 锁获取、释放及 `pthread_once` 检查 | 10.0% | 9.3%–11.0% |
| 候选去重、插入、移除、缓冲区维护，排除扫描 | 2.3% | 1.6%–2.7% |
| ARC、aggregate 遍历、清理及普通销毁，排除以上类别 | 30.8% | 29.7%–32.1% |
| 分配、其他 libc 操作及剩余计算／控制流 | 9.7% | — |

这是用户态 CPU 采样比例，不是精确的独立计时。第四项含原本必需的销毁工作，
不能全部称为“额外 ARC”；内联到计算函数的部分清理指令计入最后一项，尚未逐条
分离。该用例只有一个业务线程，锁数据不能用于估计多线程争用、等待时间或 STW
延迟。本轮发现的主要瓶颈是扫描及 ARC／清理，而非候选表维护。

**诊断计数。** 另建只增加计数、不改变原操作顺序的 runtime 副本；九次深度 16
运行的计数完全一致，所有输出校验通过。有效 retain/release 排除 NULL 与 immortal
提前返回；以下是插桩路径的事件数，不把逻辑事件数等同于最终机器码调用次数。

| 每次运行的事件 | 当前分类 | 修正分类 |
| --- | ---: | ---: |
| 有效 retain | 88,697 | 29,973,123 |
| 有效 release | 15,074,888 | 44,959,314 |
| 引用计数归零 | 14,986,191 | 14,986,191 |
| aggregate retain／release，每种 | 87,378 | 60,118,364 |
| aggregate 清理登记 | 87,378 | 60,118,364 |
| 收集器锁获取／释放，每种 | 1 | 44,957,707 |
| 候选登记请求 | 0 | 29,971,804 |
| 去重后实际插入 | 0 | 15,149,534 |
| 已入队对象归零后移除 | 0 | 4,193,758 |
| 移除的指针比较总数 | 0 | 88,298,088 |
| 候选缓冲区 `realloc` | 0 | 171,188 |
| 非空候选收集轮数 | 0 | 42,796 |
| 扫描候选根总数 | 0 | 10,955,776 |
| 标灰节点／恢复黑色节点，每种，跨轮重复计入 | 0 | 36,277,424 |

也就是说，修正分类后恢复了 **29,884,426 对有效增减**。普通 ARC 销毁数量未变，
但额外保活操作使存活树进入候选，并反复触发“试验性减引用 → 证明存活 → 恢复引用”。
42,796 轮全部没有 WHITE 节点；这不能作为对其他程序跳过扫描的依据。

生成 C 和最终汇编同时确认：`check` 的 match 临时值与左右实参恢复 aggregate
retain/release 和清理登记；原来的一个递归分支可转为循环，修正后保留两个递归调用
及返回后的清理。因此，历史 patch 并未新增运行时类型分析；它改变编译期分类，
启用了原有运行路径，并使原借用证明不再成立。

这里“不再成立”指当前证明函数因循环标记而拒绝借用，并非已经证明这些临时
引用全部必需。首轮计数本身不构成安全证明；后续逐项静态审计已确认本用例两类
新增操作的保活依据，见 §6.5.1。通用实现、回归及消除后的性能尚未验证。

**探针扰动与证据。** 同批交错计时中，修正分类版本为 1,717.8 ms，计数版本为
1,815.3 ms，增加约 5.7%；当前分类版本为 318.7／310.3 ms，范围重叠。因此不使用
计数版耗时作为优化结果。另测 perf 内部目标进程耗时，当前分类为 310.7／307.1 ms、
修正分类为 1,698.9／1,695.7 ms（不采样／采样）；本轮未观察到明确增量，但不据此
声称采样完全没有扰动。

小型原始证据保存在本地 `temp/cycle-cost-20261016/evidence/`：`unmodified-timing.json`、
`profile-summary.json`、`counts.json`、`counter-overhead.json`、`perf-overhead.json`，
以及生成 C、最终汇编、制品哈希和 `.text` 一致性记录。诊断脚本在其上一级目录；
完整 perf 数据留在容器 `/workspace/temp/cycle-cost-20261016/evidence/profiles/`。
这些临时文件不进入提交；本节保留可 Review 的结论和测量边界。

### 6.5 基于量化结果的最小通用方案

按以下顺序逐项设计和验证，不直接套用历史 patch：

1. **先完善类型图分析。** 建立 §4 的完整保守分类，修复漏判；不以维持错误的
   无环标记保住性能。独立量化正确分类带来的路径变化，作为后续优化的依据。
2. **再进行通用 ARC 成对消除。** 按 §5 分离成环分类与临时保活证明，依次完成
   §6.5.2 的现有借用规则解耦和 union 转换事实传递；同一证明适用于满足条件的
   普通程序，不按评测类型筛选。消除成立时，一并去掉该临时所有权独占的清理，
   减少源头上的计数和派生扫描；不为保留偶然扫描而恢复冗余引用，也不混入
   异常清理机制重构。
3. **最后优化循环回收器。** ARC 消除后重新量化剩余锁、候选与扫描成本，再决定
   内部遍历、候选维护、同步或调度的具体优先级。§6.4 的历史比例不能直接代表
   消除后的瓶颈；归零销毁的真实 release 仍可能承担锁成本，不能预先宣称已解决。

原先优先提出的内部遍历回调收敛，移到第三阶段作为候选：当前只读 aggregate
遍历经 `cyc_aggregate_for_each_pointer_slot → cyc_visit_pointer_only → 实际 visitor`，
最终汇编仍有两层间接分派和栈上 bridge。可验证复用已有可写 slot 的 visitor 签名、
由只读 visitor 忽略 slot 参数的方案，但必须保留遍历顺序、活动成员、边计数和
生命周期协议；不新增公开 runtime API，不改变 `feng_release` 签名或对象布局。
该方向实际净收益尚未验证，不能将历史扫描占比全部视为可消除收益。

候选维护与同步也留在第三阶段按剩余热点选择，不预先增加对象头索引、哈希表或
常驻存储，不直接删除锁。触发策略及无全局 STW 的变化分别按 §5.3、§6.3 证明并
Review。现有五项评测与通用对象场景均需验证，不能只凭 binary-trees 的扫描减少
宣称收集器整体更高效。

这些是实施前的逐项方案；阶段 2 的实际验证见 §10。§6.5.1 的静态结论仅针对
已核对的操作及保活路径，不能推广为所有循环类型的增减均可删除，也不能据此
承诺必然恢复到约 0.30 s。若无法在保留语义的前提下达到持平，必须如实报告
剩余成本，不能默认接受退化。

#### 6.5.1 binary-trees 操作归属与安全依据

本次核对[评测源码](../../benchmarks/cases/binary-trees/feng/main.ff)、现有 Codegen
及 §6.4 保存的两份生成 C，未修改或重新执行程序。深度 16 的工作负载包含
`N = 14,985,902` 个真实节点、`R = 87,378` 棵树，父子边数为 `N - R`。
以下有效引用增减的拆分由源码执行次数与已保存计数交叉核对，不是新增性能结果。

| 操作来源 | 有效 retain/release 对数 | 静态结论与保活依据 |
| --- | ---: | --- |
| `check` 中 `match node` 的拥有快照 | 14,985,902（N） | 可消除额外引用；调用者已保护 `node`，分支绑定 `n` 不可变，match 期间不替换 payload，不使借用逃逸 |

证明链从 `temporary` 中的 `tree` 或 `main` 中的 `longLived` 开始，沿调用者的
实参保护、不可变 match 投影和 `left`／`right` 强引用传递。`check` 只匹配、读取
和递归计数，不修改路径；根拥有者的原有清理在遍历之后。这里不以实例图无环
作为消除条件，也不把环内互相持有当作外部保活。

空成员仍可能经过 aggregate helper，但不产生有效对象引用增减，所以表中数字
不等于 helper 调用总数。删除冗余临时所有权时，只移除其独占清理，不提前释放
根、父节点或其他资源；异常、早退及捕获等通用边界仍须通过 §7 的用例验证。

#### 6.5.2 阶段 2 的最小实施范围

阶段 1 的类型图分析与事实传递必须先完成并独立验证；以下两个子步骤建立在正确
分类之上，不能恢复错误无环标记，也不将其混入类型图修复。

**2A：让现有安全借用适用于潜在循环类型。** 复用 §5.4 的拥有者、路径稳定性、
不可变槽位及调用契约，调整 `cg_borrow_pair_has_no_effect` 与
`cg_result_has_stable_aggregate_borrow` 的借用判定，将“可能触发循环收集”与
“是否需要独立保活”分开。match 和实参继续共用该证明；保留所有与存活和表示
有关的检查，不把 `cg_ownership_pair_has_no_effect` 全局改为无条件成功。该函数
还参与整值出口转移，首轮不同时扩大出口转移的适用范围。

此步主要在 [ownership.c](../../src/codegen/detail/ownership.c) 调整编译期证明；
[call_arguments.c](../../src/codegen/detail/call_arguments.c) 与
[codegen.c](../../src/codegen/codegen.c) 的现有消费入口仅在确有必要时接入新判定。
复用原有借用发码和清理路径，保留求值顺序及快照语义，不重写异常机制。

**2B：在固定布局 union 注入时保留已成立的保活事实。** 当前
`cg_emit_union_spec_coercion` 传递 `owns_ref`，但丢失源值的稳定借用信息。
对仅添加 tag、包装原 payload 的转换，证明转换不建立新资源且源拥有者覆盖消费
区间后，传递该保活事实；嵌套注入遵循同一条件。仅传播借用依据，不把不同类型的
源／目标冒充同一份可转移所有权，不直接复制整值 `local_owner` 来绕过类型检查。
产生新拥有值的转换、可变来源和未知布局保留现有物化及清理。

首轮不新增 runtime API、对象头字段、FT 格式或运行时检查，不引入全程序逃逸
分析。显式 `var` match 绑定、不能证明稳定的可变字段、间接／外部调用和动态布局
等现有保守边界不顺带放宽；泛型／跨包的正确性覆盖仍须完整，不能优化时保留引用。
这两个子步骤不修改锁、阈值和收集策略；真实归零 release 的锁成本仍留给阶段 3
按剩余热点量化，不能把消除 29,884,426 对直接等同于整体性能已达标。

本轮交付完整的 2A／2B。生成 C 与 IR／汇编须确认被消除的是额外引用及其独占
清理，真实拥有者的释放和类型成环标记保持。新增正例与保守反例独立组织；既有
`__cyclic__` 借用预期迁移及 Codegen／CLI／FCTS 入口注册已获人工批准。Linux
`make test` 通过后，以同工具链、同输入交错比较阶段 1 前的 `a07102e6`、阶段 1

CPU 时间近似；不把计数乘假定单次成本，也不从这些数值推导精确的纳秒级函数耗时。

### 11.3 真实环的成本不能用树负载代替

使用相同保守描述符构造独立通用诊断：反复生成两节点真实环、带终结器的两节点
环，以及有外部拥有者保活的环。前两者保留默认阈值 256；存活环使用测试接口将
阈值设为 1，以隔离反复扫描，未改变正式默认值。每种五轮采样，分别获得
6,195／3,064／2,726 个样本，均无丢失：

| CPU 样本归属 | 普通真实环 | 带终结器真实环 | 反复扫描存活环 |
| --- | ---: | ---: | ---: |
| 实际收集，包括内部遍历、分配、销毁与终结器 | 54.08% | 81.59% | 58.77% |
| 收集之外的锁与初始化 | 13.19% | 4.90% | 21.20% |
| 收集之外的候选维护 | 2.55% | 0.82% | 8.84% |
| 其他 ARC、工作负载及 libc | 30.18% | 12.70% | 11.19% |

这是互斥的包含时间归属：表中“收集”包含它调用的 allocator、终结器和锁操作，
不与其余行重复相加。这里没有将全部扫描步骤进一步拆为独立精确耗时。
带终结器场景约 48.04% 的全部样本落在 `count_intra_in_visit`，该函数通过
`white_index_of` 线性查找白色对象的位置。它是后续收集路径的明确调查入口；
尚未验证索引表、缓存或缓冲区复用的净收益，不据此批准新存储或改变复活协议。

### 11.4 两个通用候选及其安全边界

**候选 A：仅缓存当前线程已完成全局初始化这一事实。** 隔离实现只涉及
`feng_cycle.c` 的一个私有 `_Thread_local bool` 和 `feng_cycle_lock`：

```c
if (!g_initialized) {
    pthread_once(&g_cycle_once, cycle_init_once);
    g_initialized = true;
}
/* 以下原生加锁和错误处理保持不变。 */
```

标志只在 `pthread_once` 返回后设置。每个线程的首次进入仍通过它等待初始化完成
并获取已发布的状态；后续调用仍逐次执行原来的 `pthread_mutex_lock/unlock`。
当前 shutdown 只清理候选，不销毁 mutex 或重置 once 状态，故缓存不会因 shutdown
失效。这个结论依赖现有终生初始化约定；未来若支持重新创建 mutex，必须重新审查。

**候选 B：在 A 上增加同线程嵌套锁深度。** 最外层仍获取原递归 mutex，嵌套层只
增减 TLS 深度，最后一层才执行原生 unlock，并保留深度溢出检查与原生错误处理。
它对所有通过这两个锁函数进入的路径生效，不识别对象类型、树形结构或评测输入。

| 操作次数，binary-trees | 基线 | A：初始化缓存 | B：再复用嵌套锁 |
| --- | ---: | ---: | ---: |
| `pthread_once` | 14,986,079 | 1 | 1 |
| 原生 mutex lock／unlock，各自 | 14,986,079 | 14,986,079 | 87,555 |
| 逻辑加锁／解锁、release、归零、候选及扫描事件 | 原值 | 全部不变 | 全部不变 |

A、B 都保持 `feng_release` 单一实现与原签名，不改 runtime API、对象／数组／
aggregate 描述符、实例布局或编译器。普通 ARC 的销毁顺序、候选阈值、终结器复活
与扫描时机没有调整；不是用延迟释放换取性能。

B 复用嵌套锁的前提是当前线程已在最外层成功取得原生 mutex；所有受保护操作
仍位于最外层原生加锁／解锁之间，嵌套进入及退出不能让其他线程进入。已确认
mutex 私有，源码中没有绕过锁函数的直接解锁／销毁或条件等待。新增隔离检查由另一线程直接 trylock 原生
mutex，在三层嵌套及逐层退出的 500 个观察点检查该不变量。

这些局部证明没有补齐 §3 已记录的整体并发契约差异：`feng_retain` 和字段写入
并非都持有全局锁。不能据此证明任意并发改图都安全，也不能据此删除全局锁。
两个候选均不解决 STW 或低于阈值时的回收进展边界。

九轮交错测量的 A 结果如下。ns 是完整一组操作的摊销耗时，包含同一循环框架，

| 操作 | 基线 ns | A ns | 观察 |
| --- | ---: | ---: | --- |

无托管槽数组和带终结器环又做长采样：每进程分别 5,000 万／200 万组、一轮预热、
十五轮采样，并加入“原源码仅按隔离路径重新编译”的空白对照。无托管数组基线／
空白对照／A 为 8.838／8.510／8.563 ns，A 与空白对照区间重叠；带终结器环为
152.348／152.735／151.464 ns，区间同样重叠。这两项未确认 A 带来稳定退化。

**B 不能据树负载的收益直接通过 Review。** 无托管槽数组的短测为
8.591 → 8.805 ns；长测为 **8.702 → 8.979 ns（+3.19%）**，空白对照为
8.652 ns。基线与 B 长测区间分别为 8.550–8.734、8.850–9.060 ns，存在稳定

候选筛选还发现两点：仅增加嵌套深度、保留每次外层 `pthread_once` 时，叶子

4.7%–5.7%。调整为结构化外层分支消除了该多余跳转，但未消除最终 B 的上述

四线程短测出现过明显双峰，故另用同步起跑、每线程 500 万对操作、十一轮采样
验证，并加入固定到四个 vCPU 的对照。A 的四线程每对操作中位数为
42.770 → 38.434 ns，固定 vCPU 后为 42.975 → 39.749 ns；最终 B 为
42.897 → 40.544 ns，固定后为 43.546 → 41.565 ns。B 单线程为
8.382 → 8.394 ns，区间重叠。长测未复现短测的大幅退化；这里只报告不同测量

## 12. 第三阶段继续验证：达标方案

本节保留正式实施前的隔离验证记录；获批后的实现及验收见 §13。

人工确认继续寻找完整达标方案，不以 §11 候选 A 的部分收益结束本阶段。验收保持
为 binary-trees 回到类型图修复前的水平，同时其余四项及通用诊断没有确认的稳定
退化；仍在 Linux 隔离副本验证，正式代码不动，STW 可在本目标达到后另行优化。

先核实候选 B 的无托管数组差值：比较实际执行指令，并用预先固定的多组链接布局
区分运行路径新增成本与代码位置影响；布局变体仅用于诊断，不把固定函数对齐、代码填充
或选择最快布局带入生产方案。在证据支持时，比较更紧凑的私有锁状态及快慢路径
组织，保持 mutex 的原保护区间、候选事件、普通 ARC 销毁和终结器语义。

最终候选必须重新验证五项评测、无托管／托管数组、扁平／递归对象、共享对象、
真实环、终结器及并发场景；不得用一种场景的收益抵消另一种的稳定退化。新增
线程存储与仍未确定的结论继续明确列入 Review，不据局部测试宣称所有平台达标。

### 12.1 直接解决 STW 是否能替代本轮优化

目前没有证据支持“直接解决 STW 就能达标且其他场景无退化”。§11.2 的计数表明，
binary-trees 没有实际循环扫描，主要同步成本来自普通释放路径反复进入原生递归锁。
仅把扫描搬到后台或拆分为增量步骤，不会消除这些普通释放操作的成本。

若进一步取消释放路径上的全局锁，则须先解决 §6.3 的一致性与生命周期问题，
同时核实 §3 已记录的 retain／字段写入边界。新增同步、屏障或记录是否带来
其他负载退化，需要独立验证；不能用直接删除锁的诊断结果代替安全并发方案。

因此，当前先验证保持原生互斥保护区间的同线程嵌套锁复用。它不解决 STW，但
直接对应树负载的已确认成本；是否可以交付，仍以其他场景无确认退化为条件。

### 12.2 两类负向结果的分离验证

无托管数组的差值不能解释为“执行了新增的嵌套锁判断”：它没有走这条路径。
固定使用默认布局及链接随机种子 1、7、42、101，交错运行九轮、每进程 5,000 万次
数组生命周期。候选 B 相对基线，在这些布局下分别约为 +2.6%、+3.4%、−0.1%、
−3.6%、−0.4%；代码位置确实影响结果，但这不能抹去 §11 默认构建的稳定负向证据。

进一步将每线程首次初始化留在单独的 `cold`／`noinline` 私有函数中，常用路径
保留深度计数和原生加解锁，不把每次外层加解锁都改成辅助函数调用。该候选
`initcold` 的无托管数组及终结器长测未确认退化，五项单线程也通过了第一轮筛选，
但持续四线程的每对操作由约 43.7 ns 增至 47.9 ns，固定 vCPU 后由 43.1 ns 增至
48.9 ns。因此，它单独不能交付。

这次线程差值与共享数据的位置有关。该线程制品中，原生 mutex 起始地址位于
64 字节块的偏移 56；其锁状态与拥有者信息跨越块边界。只改变 BSS 链接位置，
保持同一候选的输入 bitcode、代码段位置和尺寸不变，将 mutex 分别放在偏移
0、8、16、24、32、40、48、56。五轮交错对照中，`initcold` 在偏移 0–48 时为
39.1–41.4 ns/对，偏移 56 时为 48.6 ns/对。该实验确认了数据位置的影响。
容器报告的缓存行大小为 64 字节，宿主机报告 128 字节；没有可用的硬件 PMU，
因此不声称已经测得某一级缓存的具体失效率。

将原生 mutex 改成 `PTHREAD_MUTEX_ERRORCHECK` 的替代实验没有通过：单工作线程
成本增加约 3%–5%，终结器长测也出现负向结果。本轮保留原来的递归 mutex 类型、
错误处理和保护范围，不采用这一替代实现。

### 12.3 最终隔离候选的最小实现范围

候选名为 `aligned`，仅改变 `feng_cycle.c`：

1. 增加私有线程深度计数及初始化标志。每个线程首次进入时仍通过 `pthread_once`
   完成初始化；后续已初始化的线程跳过这次调用。
2. 仅最外层进入／退出调用原来的原生 mutex；同线程嵌套进入／退出只更新深度。
   保留溢出检查和原生错误处理，不改变 mutex 实际保护的起点与终点。
3. 首次初始化放入一个 `cold`／`noinline` 私有辅助函数，避免将其代码重复展开到
   常用释放路径。该辅助函数不是每次外层进入都会调用的加锁包装。
4. 对私有原生 mutex 的**数据存储**指定 64 字节对齐。Linux ARM64 中该对象为
   48 字节，使其完整落入一个 64 字节块；这不同于固定函数地址或选择最快链接布局。
   正式实施仍须核对支持目标的 mutex 大小与实际链接对齐。

保持 `feng_release` 的单一实现和签名；不改变 runtime API、对象／数组布局、
描述符、ARC 操作、候选条件、扫描阈值、销毁顺序及终结器与复活行为。编译器、
std、评测算法及优化级别不变。无环路径仍不访问新增的线程状态。

原生递归锁仍负责跨线程互斥，私有计数只表示本线程已经持有的嵌套层数；最内层
退出不提前解开原生锁。shutdown 没有销毁 mutex 或重置 `pthread_once`，因此
线程初始化缓存可以保留；已新增隔离检查覆盖 shutdown 后再次进入。

这仍是供 Review 的隔离方案，不是正式实现。新增线程存储和数据对齐填充属于
明确成本，不能用时间上的收益代替人工对这些成本的判断。
