# nbody 插件后性能差距归因

日期：2026-09-29。范围：原数组 runtime 与 Math.sqrt 函数体可见的诊断组合，
macOS 加载[原生符号名称还原插件](feng-native-symbol-normalization-dev.md)。
本轮只进行调查；未修改正式编译器、runtime、std、插件、基准或既有用例。

## 1. 结论

插件解决 sqrt 名称识别之后，所测主要剩余差距已通过机器指令级干预定位：

1. **不跨页位置的约 0.14 秒差距**：当前 Feng 循环中，一条合并读取 `vz` 与
   `mass` 的 `ldp` 造成退化。只把该指令拆为两条原地址的 8 字节读取，保留
   其余指令及地址，20M 步由约 0.810 秒降到 0.669 秒，接近同批 C++。
   LLVM 22.1.8 的 `aarch64-ldst-opt` 记录确认了该合并的产生阶段。
2. **约 1.8 秒与 2.5 秒的慢档**：分别是速度二元组、坐标二元组的 16 字节
   读写跨越系统页边界。针对性拆分这些访存后，慢档分别降至约 0.85、0.83 秒。
   等长指令对照排除了代码地址变化；浮点计算、边界检查、数组地址均保留。

Linux 也能复现这两类退化。此前平台成绩的主要差距来自目标 CPU 配置与
实际分配位置，不是 macOS 仍调用 libm，也不是 LLVM IR 核心计算缺失优化。
这里定位到了造成退化的指令和条件；没有硬件计数器证据，不能进一步宣称
已经确认 CPU 内部的存储转发、TLB 或执行端口机制。

## 2. 方法与边界

- Feng 使用同一批保存的发布版库、相同函数体、Clang 22.1.8 O2，无 LTO，
  启用默认向量化。组合版没有新增 `@memory`、C 行为属性或手工 sqrt builtin。
- 通过既有冷路径迁移助手控制实际数组数据地址，运行后核验页内偏移；没有
  更改生产 allocator。数组仍为五个 Body，每个 56 字节，共 280 字节。
- 先预检与小输入校验，再串行交错计时。关键组两轮预热、五轮正式运行，
  每次 20M 步。探索组单独保留；记录 wall、CPU、输出、命令与制品散列。
- 拆分只改变读写宽度及必要的寄存器位搬运，浮点运算和顺序不变。宽访存
  对照补 `nop` 保持指令数量一致，反汇编核验其他指令及地址完全相同。
- CPU 参数切换、手工汇编拆分都是归因实验，不是批准的生产优化方案。

本地证据主要位于 `temp/nbody-plugin-gap-20260929/`；Linux 位于
`temp/apple-container-verify-20260929/native-gap-linux/`。两处 `build.json`
保留构建参数和散列，各测量目录的 `results.json` 保留所有逐次样本。
本机为 Apple M4 Pro；文中的 apple-m1 是 Clang 目标配置，不是物理 CPU 型号。
汇总为 255 项小输入检查、20 次启动预检、398 次长运行（289 次正式计时），
所有测量命令成功，所有 Feng 长运行输出跨平台逐字一致；没有丢弃慢样本。
见 `validation-summary.json`。

证据可用性更新（2026-09-30）：上述根目录 `temp/` 工件被后续全量回归的
既有清理步骤删除，尚未完整恢复。本文保留历史调查结果，不能再将这些路径
作为当前可读取的原始记录；经过见[插件接入记录 §8.1](feng-native-symbol-normalization-dev.md#81-证据保留记录)。

## 3. 不跨页时，差距精确到一条成对读取

macOS 以默认 `apple-m1` 目标生成的最内层循环含有：

```asm
ldp d6, d7, [x4, #-8]     // bodies[j].vz 与 bodies[j].mass
```

该处 `x4` 指向 `bodies[j]` 数据起点加 48 字节。对照只改为：

```asm
ldur d6, [x4, #-8]
ldr  d7, [x4]
```

基线则保留 `ldp` 并补一条 `nop`。两份反汇编均为 11172 条指令，仅地址
`0x100000d14`、`0x100000d18` 的两条不同，其余机器指令及地址完全一致。
原汇编重链接的指令与原 C 编译制品也逐条一致。

固定 payload 页内偏移 912，五轮中位数如下，单位秒：

| 诊断 | wall | CPU |
|---|---:|---:|
| 原 apple-m1 组合版 | 0.809905 | 0.795 |
| 仅 target CPU 改为 generic | 0.669422 | 0.656 |
| 只移植 generic 最内层循环 | 0.668417 | 0.655 |
| 原 ldp＋nop | 0.809840 | 0.796 |
| 仅拆分这一条 ldp | 0.668585 | 0.653 |
| C++ O2 | 0.675135 | 0.662 |
| Swift -O | 0.875318 | 0.859 |

`ldst-trace.log` 显示，该 pass 之前为两条独立的 `LDURDi`／`LDRDui`，之后
变为 `LDPDi`。`generic` 的指令排列未形成这处合并。单条拆分复现了整个
CPU 参数切换的收益，因此不能继续笼统解释为“macOS 调度不同”，也不能将
这约 0.14 秒直接算作 Feng 剩余边界检查的成本。

这不证明所有 `ldp` 都慢。当前 C++、Swift 制品也存在类似指令，但它们的
循环、寄存器依赖及访存排列不同。禁止由这一局部证据推导全局关闭成对访存。

证据：`cpu-inner/results.json`、`pair-{padded,split}.disassembly.s`、
`ldst-trace.log` 和对应命令记录。

## 4. 跨页慢档的两种具体字段

Body 的字段偏移为 `x/y/z = 0/8/16`、`vx/vy/vz = 24/32/40`、`mass = 48`。
macOS 页大小为 16384 字节，原正式自然分配组合版出现的慢位置可以具体对应：

| payload 页内偏移 | 页边界相对 payload | 跨页字段区间 |
|---:|---:|---|
| 16184 | 200 | `bodies[3].vx/vy`，`[192,208)` |
| 16296 | 88 | `bodies[1].vx/vy`，`[80,96)` |
| 16264 | 120 | `bodies[2].x/y`，`[112,128)` |

前两处每步有四次配对涉及该 Body，相应宽读写共八次，位置更新再宽读一次，
合计九次跨页访存；20M 步为 1.8 亿次。坐标慢位置每步配对读取四次，位置更新
一读一写，合计六次，20M 步为 1.2 亿次。这是根据循环及地址计算的次数，
不是硬件计数器采样。

速度字段实验只拆分两处配对宽读、两处配对宽写及五处位置更新的速度读取。
等长两份制品均为 11189 条指令，仅选定位置的 26 条不同。五轮中位数如下：

| 页内偏移 | 宽访存＋nop/s | 拆分速度访存/s | 拆分后 CPU/s |
|---:|---:|---:|---:|
| 912（不跨页） | 0.806571 | 0.852873 | 0.839 |
| 16184 | 1.821612 | 0.852133 | 0.840 |
| 16296 | 1.801318 | 0.855113 | 0.840 |

仅拆读、仅拆写、仅拆位置更新的探索都未完全消除慢档；不能把全部收益
归给某一条读或写，也不能忽略拆分在快位置增加的约 5.7% 成本。

坐标字段实验只拆分配对的两处坐标读取，以及第三个 Body 在位置更新中的
一读一写。两份制品均为 11179 条指令，仅选定位置的 12 条不同：

| 页内偏移 | 宽访存＋nop/s | 拆分坐标访存/s | 拆分后 CPU/s |
|---:|---:|---:|---:|
| 904（相同低位、不跨页） | 0.808924 | 0.831397 | 0.817 |
| 16264 | 2.455031 | 0.833835 | 0.818 |

两类慢档都通过固定地址、等长代码的实验消失，已超过地址相关性层面的证据。
但拆分速度字段并不解决坐标字段的跨页，不能将其中一个诊断包装为所有地址
均达标的生产实现。

证据：`final-velocity/`、`xy-boundary/`、`instruction-audit.json`、
`combined-instruction-audit.json`；探索保留在 `explore-macos/`。

## 5. Linux／macOS 反向对照

Linux ARM64 容器页大小 4096。3896、4008 对应距离页尾 200、88 字节，
与 macOS 的两个速度字段慢位置相同。Linux 本轮实际加载插件；插件不改变
Linux IR。固定位置、五轮中位数如下：

| Linux 目标 CPU | 912（不跨页）/s | 3896/s | 4008/s |
|---|---:|---:|---:|
| generic | 0.655298 | 1.807972 | 1.807398 |
| apple-m1 | 0.797171 | 1.809742 | 1.785575 |

Linux 将 CPU 参数改为 apple-m1，快档也由约 0.65 秒退化到约 0.80 秒；
固定到跨页位置后也出现约 1.8 秒慢档。macOS generic 不跨页的 CPU 中位数
0.656 秒与 Linux generic 的 0.655 秒接近；wall 的小差别还包含进程启动退出。

额外边界对照中，macOS 的 3896、4008 虽跨越 4 KiB 边界，却没有跨实际
16 KiB 系统页，apple-m1 约 0.786／0.795 秒，generic 约 0.658／0.659 秒。
保持低位同余并远离页尾的 824、936 也处于快档。由此区分了系统页边界与
仅由缓存行偏移或固定的 4 KiB 地址边界引发的解释。

证据：Linux `platform-cpu/` 与 macOS `boundary-controls/`。边界探索为
一轮预热、三轮正式，不能与其他五轮组混算。

## 6. 为什么 C++、Swift、Rust 的原成绩没有出现同样慢档

原自然分配批次只记录了 Feng 的数据地址，C++、Swift 的地址字段为空，Rust
没有参加该批次。因此，准确表述是“该批次只在 Feng 观察到跨页相关慢档”，
不能把其他语言未出现慢档等同于逐次确认了它们没有跨页。

具体地址有运行环境相关性，但已经触发后的退化不是随机噪声。当前四种程序
并没有相同的存储路径：

| 程序 | 当前基准的数据存储 |
|---|---|
| Feng | 托管堆数组；macOS 数据偏移 72 字节，五元素申请 `72 + 280 = 352` 字节 |
| C++ | `std::array<Body, 5>` 局部值，当前制品放在栈上 |
| Rust | 源码为局部 `[Body; 5]`，没有为这组 Body 创建堆上的 `Vec` |
| Swift | 托管 Array；当前制品请求 312 字节，数据从对象起点加 32 字节开始 |

对象头、申请大小、对齐、此前分配序列及栈布局会影响数据的具体落点。不能
把这批 Feng 样本较常出现页尾地址，推广为所有 Feng 程序的概率结论；也不能
认为换成其他语言便不会触发相同的宽访存成本。Rust 本轮未做同位置控制测量，
其原有时间成绩不足以证明不存在该问题。

Feng 的这批自然分配 payload 对 16 取余均为 8；Swift 的本次取样为 0。
但把 payload 对齐到 16 字节也不构成通用解法：Body 步长 56 字节，且坐标、
速度二元组相对偏移分别为 0、24，宽访存中仍会出现仅 8 字节对齐的地址。
它会改变可能跨页的具体字段与落点，而不是自动消除全部跨页。

**C++ 已复现过同一问题。** 原程序使用栈上的固定数组；此前将同一个 C++
计算核放到受控位置后，16184、16296 分别由快位置约 0.66 秒退化到
1.759／1.712 秒。原始证据见[既有同布局对照](feng-nbody-performance-optimize.md#相同布局的重复实测)。
本轮重新检查当前 C++ 制品，热循环仍有相同类别的宽访存。
只读调试另一次取样的数组页内偏移为 7984，位于栈指针加 16 字节处，
280 字节数据没有跨页；这也不是原正式计时批次的地址记录。

**Swift 也没有被证明能规避此问题。** 当前 Swift 制品的 `advance` 同样有
`ldur/stur q`，涉及相同的坐标和速度二元组，没有按页边界选择窄访存的分支。
对原二进制的只读调试取样显示，数组数据页内偏移为 13968，280 字节数据全部
位于同一页。这次取样在调试器下启动，不是原性能批次的地址记录，不能推广
为 Swift 每次分配的位置，也不能宣称所有 Swift 数组都会避免跨页。

因此，现有稳定成绩不能当作 C++／Swift 的语言保证；C++ 已有受控反例，
Swift 当前证据是同类指令存在、取样落点未触发。尚未完成 Swift 原数组
受控迁移到跨页位置的性能测量，不将静态分析写成 Swift 已复现的结果。

证据：`cpp-current.disassembly.s`、`cpp-address.log`、`swift-current.disassembly.s`、
`swift-address.lldb` 与 `swift-address.log`。

### 6.1 Feng 自然分配为什么集中在页尾

继续使用原组合版二进制追踪，条件断点确认数组调用 `calloc(1, 352)`，最终
进入本机系统库的 `mfm_alloc(384)`；返回对象的 `malloc_size` 为 384。
这识别出了具体分配路径，而不是根据地址猜测 allocator。
Apple 的 [xzone allocator 文档](https://github.com/apple-oss-distributions/libmalloc/blob/main/doc/xzone_malloc.md#early-allocator)
说明，每个大小及类型分组的早期申请可以使用独立的早期分配器。
[MFM 源码](https://github.com/apple-oss-distributions/libmalloc/blob/main/src/early_malloc.c)
先查找可复用块，没有合适块时从连续区域向后分配；不保证每个对象均位于单页内。
公开源码用于解释机制，本机实际调用以断点记录为准。

原启动路径及测量助手复核七次，数据页内偏移再次出现
`15960、16216、16264、16296`，复现了原样本的页尾分布。Feng 在创建 Body
数组之前，会创建参数数组并把 `argv[0]` 等文本复制为托管字符串。
保持二进制、计算输入和启动文件不变，仅改变传入 `argv[0]` 的文本长度，
每档启动三次，得到：

| `argv[0]` 字节数 | 三次数据页内偏移 |
|---:|---|
| 16 | 16136、16136、16168 |
| 128 | 16264、16264、16216 |
| 512 | 328、360、280 |
| 2048 | 2200、1944、1944 |

512 与 2048 字节组的 280 字节数组均在单页内。该干预证明前置分配会移动
同一 Feng 程序的数组落点；页尾聚集是本次程序启动分配序列与本机 allocator
状态共同形成的结果，不是数组头 72 字节必然导致的结果，也不能解释为每次
独立、均匀随机选址。这里未追溯系统启动阶段每一块内存的来源，不能进一步
把各离散偏移的差别都归因于某一条具体分配。

另有 30 次独立 C 探针启动，每次连续分配 16 个对象，对照 `malloc`／`calloc`
和 312／352／384 字节申请。六种组合的首对象页内偏移均为 7664，352 字节
申请的实际块大小为 384；因此单独使用 `calloc` 或该申请大小并不会自动把
对象放到页尾。该探针与 Feng 的启动分配序列不同，不替代 Feng 原程序结果。

上述 19 次 Feng 运行输出逐字一致，均用于地址归因；启动助手产生的计时记录
不加入前文性能汇总。最初探针批量启动曾被 SIGKILL，失败记录单独保留；用户配合授权
后 30 次探针及 19 次 Feng 运行全部成功。调试器启动也曾取得非页尾地址，
因此调试取样不能冒充原正式批次的地址记录。

新增证据位于 `temp/nbody-allocation-origin-20260929/`：`mfm-branch.log`、
`feng-calloc.log`、`probes.json`、`natural-probes.json`、`validation.json`。
本次没有改变 allocator 设置或生产代码。C++ 的栈布局、Swift 的申请大小与
前置分配序列不同；它们原成绩不构成规避跨页的保证，证据边界仍见本节正文。

## 7. 组合干预的收益与限制

同时拆分已定位的 `vz/mass` 成对读取和速度二元组宽访存，在 912、16184、
16296 的五轮中位数分别为 0.825689、0.823366、0.822542 秒；同批 Swift
为 0.870978 秒。原五位置中的其余 15896、16216、16248 另批重复，分别为
0.825134、0.824805、0.824246 秒，同批 Swift 为 0.871987 秒。

这证明两类干预可以组合，但收益不能相加。速度拆分所增加的指令有成本，
组合后并没有普遍达到单独窄读取在不跨页位置的 0.67 秒。该组合也未处理
坐标跨页，不能声称所有位置已达标；本轮没有构造或交付全局拆分宽访存的方案。

## 8. 优化建议与验收边界

名称还原插件保持独立。剩余问题应分别评估：

- 针对已定位的成对加载退化，形成 LLVM 后端最小复现，评估通用的合并收益
  判断及循环依赖，而不是在 Feng 发码中识别 nbody、某个字段名或直接全局
  改用 generic。此实验只能证明当前循环的收益，不能替代其他负载回归。
- 针对宽访存跨页，评估通用的布局与后端访存策略。手工拆分在快位置有成本，
  不能全局关闭向量化，也不能未经决策改变 runtime ABI 或增加运行时分支。
- 正式验收必须同时保留快位置、各类跨页慢位置、自然分配、同批 C++／Swift
  以及正确性检查。只测一个有利落点不足以交付“稳定达到 Swift”。

本轮明确了造成所测主要差距的指令与条件；没有实施生产修复，也没有改变
Feng 原有语义或行为。只有文档和忽略目录内的诊断产物，因此本轮未重复运行
根目录 `make test`；此前插件交付的完整回归记录仍见插件开发文档。
