# Feng 泛型组合场景 FCTS 补强开发文档

> 状态：已完成
>
> 泛型语言规则以
> [feng-generics-draft.md](../specifications/feng-generics-draft.md) 为准；本文只定义现有能力的
> 组合测试范围、实施顺序和验收门槛，不新增或改变语言语义。

## 1 目标

针对近期暴露的泛型组合问题，系统复查现有 FCTS，只为尚未覆盖的组合补充行为测试：

- 普通 `type`、`@value type`、泛型 tuple；
- 顶层函数、成员函数和 lambda；
- object-form、callable-form、父子关系及交叉约束等多种 `spec`；
- 多种不同类型构成的多层异构泛型；
- 多种泛型类型通过成员、参数和返回值形成双向关系。

新增用例必须验证运行结果和完整值内容，不能只验证源码能够编译。

## 2 现有覆盖与本轮缺口

### 2.1 已有覆盖

以下现有用例已经验证单项能力，本轮不重复增加等价断言：

| 能力 | 现有用例 | 已覆盖内容 |
| --- | --- | --- |
| 普通泛型类型和函数 | `test_generic.ff` | `T` 字段、参数、返回值、泛型成员方法、自约束、泛型 spec 继承及单层嵌套 |
| 泛型 `@value type` | `test_value_type.ff`、`test_reified_value_callable.ff` | trivial/managed 布局、值复制、参数和返回值、嵌套 reified 布局、泛型方法及 callable ABI |
| 泛型 tuple | `test_tuple.ff` | 构造、复制、字段访问、顶层函数参数和返回值、managed 成员 |
| 多种 spec 形态 | `test_spec.ff`、`test_intersection_generic.ff`、`test_spec_upcast.ff` | 泛型 object-form/callable-form spec、交叉约束、父子 spec 向上转换 |
| lambda、顶层函数和成员函数值 | `test_reified_value_callable.ff` | 以同一个泛型 `@value` 参数和返回值验证三种 callable 来源 |
| 跨包嵌套泛型 | `test_generic_constraint_forwarding.ff`、`test_nested_generic_callback.ff`、`test_cross_package_private_representation.ff` | 普通泛型嵌套、`Action<Event<T>>`、私有表示类型及 FT round-trip |

### 2.2 尚未覆盖的组合

现有用例主要分别验证上述能力，尚未形成以下组合闭环：

1. 普通 `type`、`@value type` 与 tuple 同时出现在同一个多层闭合泛型布局中；
2. 上述异构复合值同时经过顶层函数、成员函数和 lambda 的参数与返回值；
3. object-form、callable-form、父子关系和交叉约束等不同 spec 同时参与同一条泛型数据流；
4. 不同泛型类型通过字段以及双方的方法参数、返回值互相引用；
5. 上述组合经 `fcts_lib` 导出后由 `fcts_bin` 消费的完整 FT、共享泛型函数体和运行时行为。

本轮以这些缺口为边界。已有单项能力只作为组合场景的一部分出现，不为它们另建重复用例。

## 3 测试组织

- 可跨包公开的测试模型定义在 `fcts/fcts_lib/src/test/`；
- 所有可执行断言定义在 `fcts/fcts_bin/src/`，并使用 `std.test` 的 `describe`、`test` 和 `assert`；
- `fcts/fcts_bin/src/main.ff` 只增加一次新测试入口调用；
- 测试库不使用 `puts` 或其他额外输出；
- 新增独立测试文件，不修改已有测试的语义或断言。若修复缺陷必须调整已有用例，先取得人工批准。

## 4 分组实施

### 4.1 第一组：异构多层泛型布局

构造至少包含以下层次的跨包闭合类型：

1. 普通泛型 `type`；
2. 内嵌泛型 `@value type`；
3. 内嵌泛型 tuple；
4. 叶子同时包含 managed 值和标量，用于检查完整复制及字段偏移。

覆盖该复合类型的成员存储、顶层函数参数/返回值和成员函数参数/返回值。使用至少两种闭合实参，确保实现没有只对某一种布局成立。

验收：专项运行 `./build/bin/feng run fcts/fcts_bin` 通过后，执行一次 `make test`。

### 4.2 第二组：三种 callable 来源

复用第一组的异构复合类型作为 callable 的参数和返回值，分别验证：

- lambda；
- 顶层函数值；
- 实例成员函数值。

三条路径使用相同的语义签名和结果断言，确保差异只来自 callable 来源。现有用例已覆盖单层 reified `@value`，本组只增加异构多层闭合类型的组合路径。

验收：专项运行通过后，再执行一次 `make test`。

### 4.3 第三组：多种 spec 的组合数据流

在同一条泛型数据流中组合并验证：

- 泛型 object-form spec 值；
- 泛型父 spec 与子 spec 的契约关系及向上转换；
- 由多个 object-form spec 组成的交叉约束；
- 参数和返回值使用复合泛型类型的 callable-form spec。

spec 值需要经过字段、参数和返回值，并在消费端调用成员或 callable，以同时验证 subject、witness、泛型实参替换和闭合 callable ABI。已有各 spec 形态的独立用例不重复增加。

验收：专项运行通过后，再执行一次 `make test`。

### 4.4 第四组：泛型类型间的双向包含

定义多个职责不同的泛型类型，使它们通过以下方式形成双向关系：

- A 的成员引用 B，B 的成员引用 A；
- A 的成员函数接受或返回 B，B 的成员函数接受或返回 A；
- 至少一条关系中包含 `@value type` 或 tuple，验证间接嵌套的具体布局；
- 使用普通引用类型作为递归边界，不定义无限尺寸的直接递归 `@value type`。

测试需要真实写入并读取双方的数据，而不是只依赖默认值或只验证声明可编译。

验收：专项运行通过后，再执行一次 `make test`。

## 5 缺陷处理门槛

每组严格执行以下流程：

1. 只增加当前组的模型与断言；
2. 先运行 FCTS 专项命令定位用例自身问题；
3. 专项通过后，在沙箱外运行 `make test`；
4. 如发现编译器缺陷，停止增加下一组，先在本文记录复现形态和根因；
5. 修复必须复用通用的泛型表示、描述符、witness 或 callable ABI，不得增加具体类型、具体测试模型或 TUI 相关特判；
6. 若修复会增加编译后 Feng 程序的运行时开销或需要变更 runtime 私有 ABI，先提交人工决策；
7. 缺陷修复及其回归全部通过 `make test` 后，才进入下一组。

## 7 实施中发现的缺陷

### 7.1 显式类型实参未参与包装参数的候选匹配（已修复）

第一组首次专项运行发现：

```feng
func roundTrip<T>(value: Value<T>): Value<T> { ... }

roundTrip<i64>(value);
```

定义经公开 `.ft` 往返后仍完整保留一个类型参数、一个值参数和返回类型，因此不是 FT
事实丢失。实际根因是函数重载候选探测只把直接参数 `T` 作为可推导位置；对
`Value<T>` 这类包装参数，普通 Feng 函数又不会启用仅供既有 extern 路径使用的包装形状
推导。即使调用方已经显式给出 `i64`，候选探测也没有先将 `T` 替换为 `i64`，因而把
本应适用的函数错误排除。

修复要求：显式类型实参数量与候选声明一致时，候选匹配必须先以这些实参替换参数中的
方法级或函数级类型参数，再执行现有参数兼容检查。该修复只补齐显式调用的既有语义，
不改变包装形状的隐式推导范围，不调整重载优先级，也不增加生成后程序的运行时开销。

### 7.2 imported 顶层泛型函数声明未使用完整共享参数 ABI（已修复）

修复 7.1 后，第一组继续在宿主 C 编译阶段复现声明与调用不一致：provider 的共享泛型
函数把布局依赖 `T` 的 `Value<T>` 参数正确声明为 `const void *`，consumer 的 imported
函数声明却只在参数本身等于直接 `T` 时使用地址 ABI，把 `Value<T>` 错误声明为固定
结构体按值参数；调用点仍按正确规则传递地址。

根因是 imported 顶层泛型函数声明没有复用 provider 定义和调用点共同使用的
`cg_shared_generic_param_uses_address` 判定。修复必须让三处统一复用该判定，覆盖直接 `T`
以及任意布局依赖泛型参数的 tuple / `@value type`。这只是纠正编译期生成的跨包 C 声明，
不改变既定 ABI，也不增加运行时开销。

### 7.3 调用解析失败后重复报告显式类型实参数量错误（已修复）

第一组全量回归发现：显式类型实参参与参数匹配后，预打包变参类型不匹配会正确拒绝
候选并报告 `AE0524`；但后续类型实参数量检查仍在未解析出调用目标时执行，把目标错误地
视为 0 个类型参数并追加 `AE0233`。

修复规则为：显式类型实参数量仅能针对已经成功解析的调用目标检查。调用解析失败且已有
主诊断时，不追加缺少目标依据的类型实参数量诊断。该修复只调整编译期诊断流程，不改变
合法程序行为、运行时 ABI 或运行时开销。

### 7.4 imported 泛型交叉约束缺少扁平成员信息（已修复）

第三组专项运行发现两个连续问题。首先，`.ft` 写入 union / intersection 的结构成员序列
时，在序列区间中穿插了泛型成员自身的类型实参序列；读取方按连续区间读取，导致
`Intersection<T>: Left<T> & Right` 的 `Left<T>` 在跨包后丢失或错位。其次，交叉 spec 的
扁平成员 sidecar 只在本地声明进入 semantic resolve 时生成，而 imported package 会跳过
该阶段。即使类型引用完整，consumer 仍无法取得 imported intersection 的扁平成员集合，
并会在泛型候选约束检查时把同时实现所有成员 spec 的具体类型错误地判定为不满足约束。

修复要求：union / intersection 写入必须先递归序列化全部成员类型，再一次性写入外层连续
成员区间；在本地声明解析前，还要按声明所在模块及嵌套交叉 spec 的依赖顺序，为所有
imported intersection spec 预计算同一种扁平成员 sidecar。本地声明仍由现有完整验证流程
生成并覆盖。两项修复不得引入新的运行时表示或路径，只补齐 `.ft` 和编译期 imported 元数据，
因此不改变 runtime、生成 ABI 或 Feng 程序运行时开销。

### 7.5 闭合与开放泛型 object-spec 的 witness ABI 不兼容（已修复）

修复 7.4 后，第三组继续到宿主 C 编译阶段。`Spec<string>` 的闭合 witness 对签名依赖
`T` 的成员使用具体 C ABI，而共享泛型函数中的 `Spec<T>` witness 使用地址参数和 out-slot
擦除 ABI。现有 spec 值直接传入 `func consume<T>(value: Spec<T>)` 时虽然
`{ subject, witness }` 值布局固定，但两种 witness 方法签名不兼容，不能通过结构体复制或
C 强制转换安全桥接。

已批准采用以下通用方案：

1. 泛型 object-form / intersection-form spec 的成员 ABI 由泛型 spec 原始声明槽位决定，
   不根据某个闭合实例替换后的具体类型重新分类；
2. 槽位不依赖 spec 类型参数时继续使用直接 ABI；已知为引用表示的泛型相关槽位使用擦除
   指针 ABI；其他依赖类型参数的参数使用地址 ABI，返回值使用 out-slot；
3. 同一泛型 spec 原点的闭合与开放实例共享兼容的固定 fat-value / witness C 表示；各实例
   仍保留各自的类型描述符、aggregate 描述符、具体 witness 常量和名义类型信息；
4. 具体 witness thunk 在已知闭合类型的编译期上下文中完成稳定槽位 ABI 与实现方法 ABI
   之间的转换，不做运行时类型判断；
5. 禁止堆适配、装箱、sidecar、descriptor 动态分派、函数指针强制转换和额外间接调用层；
   spec 值继续保持 `{ subject, witness }` 两个机器字；
6. 非泛型 spec 的表示与调用 ABI 保持不变，runtime 私有 ABI 和 runtime 源文件保持不变。

依赖类型参数的闭合 spec 成员调用会使用统一地址参数或 out-slot。这是共享泛型体与二进制
分发共同要求的必要调用约定，不以当前不兼容、无法正确执行的路径作为有效性能基线；除此
之外不得增加 Feng 程序运行时开销。

### 7.6 多个同源开放泛型依赖错误共用首个描述符键（已修复）

第四组专项编译发现：`Left<T>` 持有 `List<Right<T>>`，同时 `Right<T>` 持有
`List<Left<T>>` 时，第二个字段初始化报 `CE0007: no reified_type_dep found for generic
managed dependency`。两个依赖的外层泛型原点都是 `List`，但完整类型实参不同。

根因是共享泛型体建立 reified dependency 索引时，开放泛型托管类型和聚合类型的描述符
查找只按泛型声明原点选择第一个已注册实例，没有比较完整类型实参及当前泛型参数上下文。
因此 `List<Right<T>>` 和 `List<Left<T>>` 会错误映射到同一个开放实例描述符；表达式解析仍
能取得正确的第二个实例，最终因描述符键不一致而报错。

修复要求：托管类型和聚合类型必须统一按“泛型声明原点、完整类型实参、当前泛型参数上下文”
查找精确的开放实例，不改变依赖排序、描述符表布局或共享体调用协议。该修复只纠正编译期
描述符符号选择，不增加生成程序的运行时操作，不变更 runtime 私有 ABI。

### 7.7 开放泛型字段元数据引用不存在的具体描述符（已修复）

修复 7.6 后，第四组进入跨包链接阶段。provider 为开放泛型类型的托管字段生成
`FengManagedFieldDescriptor.static_desc` 时，直接写入了依赖当前泛型上下文的开放实例描述符
符号，例如 `List<State<T>>`；该符号只是共享体中的编译期身份，不存在可由 provider 或
consumer 链接的具体描述符实体，因而产生 undefined symbol。

`static_desc` 按 runtime 契约只是托管指针槽的可选静态提示，实际对象描述符始终来自对象头，
当前循环收集路径也不依赖该提示。修复要求：当字段类型仍含活动泛型上下文时，将其
`static_desc` 统一生成为 `NULL`；完整闭合实例仍保留具体静态描述符。直接对象字段和嵌入
聚合中扁平化出的对象槽必须复用同一规则。该修复不增加运行时分支或间接访问，不改变字段
布局、描述符 ABI 或 runtime 私有 ABI。

### 7.8 嵌套共享泛型调用按替换后类型误判形参 ABI（已修复）

修复 7.7 后，第四组可完成跨包编译和链接，但在 `Left<T>` 的共享方法体中调用
`List<State<T>>.add(State<T>)` 时发生非法引用计数访问。`List<U>.add(U)` 的共享方法 ABI
由原始形参槽位 `U` 决定，必须接收值存储的地址；调用方却按替换后的 `State<T>` 判断，
将对象指针本身直接传入。被调共享体随后把对象头误读为 `U` 的值存储，产生无效指针。

修复要求：共享泛型方法的调用参数必须复用原始声明槽位 ABI 分类，以泛型类型和泛型方法
声明的类型参数共同构成分类作用域；不能根据替换后的具体类型重新决定调用约定。地址 ABI
必须先保证实参具有可寻址存储，再传入该存储地址；固定表示的参数继续按直接 ABI 传递。
该规则同时适用于类型级和方法级泛型，不得针对 `List`、当前测试类型或具体参数位置增加特判。

该修复只纠正已有共享 ABI 的调用方适配，不增加堆分配、装箱、运行时分支或额外间接调用，
不改变描述符布局和 runtime 私有 ABI。
