## 2 已确认的设计方向

1. 使用无栈状态机实现 `async` / `await`。
2. Future 是普通 Feng 类型，编译器通过 `@future` 协议识别，不依赖类型名或 std 模块名。
3. 先对源 AST 做语义分析，再在发码前完成 async AST lowering，以及生成节点所需的局部语义处理。
4. 最终发码接收普通、类型完整的 AST，不感知 `async` / `await`。
5. Future 单向持有状态机；状态机不反向持有所属 Future。
6. 异步计算的完成结果或失败信息保存在状态机，Future 从状态机读取。
7. Future 实际销毁时销毁其状态机，并清理注册到自身的回调。释放一个引用但对象仍存活，不等于销毁。
8. 跨挂起点的绑定与 `defer` 清理信息进入状态机；不跨挂起点的内容按普通局部逻辑处理。
9. 销毁挂起中的状态机时，不继续执行业务代码，但执行已经生效、尚未执行的清理。
10. Scheduler、executor、线程池与 event loop 的选择不是语言强制要求。

## 3 源码语义

### 3.1 类型记号

本文以 `F` 表示任意满足 `@future` 协议的类型，以 `T = ResultType(F)` 表示其完成结果类型。

`Future<T>` 只是便于讨论的记号，不表示编译器内建某个泛型类型，也不要求所有协议实现具有相同的泛型参数布局。`ResultType` 的具体表达方式待确定。

### 3.2 返回值与调用

普通函数保持原有返回类型规则：声明返回类型为 `F` 时，返回表达式必须满足普通的 `F` 类型检查，不因 `F` 带有 `@future` 而允许返回其结果类型 `T`，也不自动将 `T` 包装成 `F`。

async 函数采用 C# 的返回值处理方式：声明返回类型为 `F` 时，函数体的逻辑返回类型为 `T = ResultType(F)`，返回表达式按 T 检查，由编译器通过协议完成异步结果。不再为 `return F` 提供自动等待或结果接纳；等待另一个 F 并返回其结果，应显式使用 `return await`，见第 3.5 节。

| 源码形式 | 语义要求 |
| --- | --- |
| `f()`，其中 `f` 声明返回 `F` | 表达式类型为 `F` |
| `await expr`，其中 `expr` 类型为 `F` | 表达式结果类型为 `T` |
| 普通函数声明返回 `F`，执行 `return value`，其中 `value` 类型为 `T` | 不提供异步结果包装，按普通返回类型规则检查 |
| 普通函数声明返回 `F`，执行 `return future`，其中 `future` 类型为 `F` | 按普通返回规则返回该值 |
| async 函数声明返回 `F`，执行 `return value`，其中 `value` 类型为 `T` | 合法；形成成功结果，具体构造/完成操作由协议支持 |
| async 函数声明返回 `F`，执行 `return future`，其中 `future` 类型为 `F` | 仍按 T 检查；不满足 T 的返回类型要求时编译期报错，不自动等待或展开 |
| async 函数声明返回 `F`，执行 `return await future`，其中 `future` 类型为 `F` | await 得到 T，再以该值完成当前异步计算 |

有无 `await` 改变调用结果的使用方式，不改变被调用函数对外返回 `F` 的事实。本条不是任意表达式位置均允许 `T` 到 `F` 的隐式转换规则。

`await` 判断操作数类型是否满足协议，不判断该值是否来自 `async` 函数。库手工创建的可等待值也应能够参与等待。

`await` 只允许用于 async 函数内，普通函数和顶层不允许使用。嵌套函数按其自身是否为 async 判断，不能继承外层函数的 async 身份。defer 体是否允许挂起仍需单独确认，不能由“位于 async 函数内”直接推出。

### 3.3 语义阶段的职责

语法阶段识别 `async`、`await` 及相应 AST 节点，不生成状态机。语义阶段沿用普通函数的绑定、类型、作用域与控制流检查，并补充：

- 识别和验证 `@future` 协议，得到 `F` 与 `T` 的对应关系。
- 对声明返回 F 的 async 函数，按逻辑结果类型 T 检查返回表达式；普通函数继续按声明返回类型检查。
- 检查 `await` 的操作数与使用位置，确定其结果类型。
- 保留 lowering 所需的类型、符号、作用域、清理与异常处理关系。

语法和语义阶段对异步的理解限定为 async/await 及 T/F 的源码规则，不进行状态机转换。lowering 是语义后、发码前的独立阶段。

### 3.4 隐式选择协议类型

需要隐式确定 Future 类型时，按该位置的可见面收集合法的 `@future` 类型，遵循现有名称可见性规则，不扫描不可见类型：零候选报错、唯一候选自动选择、多个候选在编译期报歧义。显式声明返回类型时使用该类型，无须隐式选择。触发隐式选择的具体源码形式及与返回类型推导的衔接仍待确定。

### 3.5 等待另一个 F 并返回结果

Feng 采用 C# 方式，显式等待另一个异步计算的结果：

```text
async func forward(): Future<int> {
    return await other()
}
```

其中 `other()` 返回结果类型为 int 的合法 `@future` 值。await 得到 int 后完成当前函数的状态机，调用方持有的外层 Future 不被替换。该 await 与其他 await 遵循相同的异常捕获、挂起及作用域清理规则。

若逻辑结果类型 T 本身也是某个 Future 类型，则返回该类型的值属于普通的嵌套结果，不自动展开。

以下保留相关语言的行为比较：

| 语言 | async 函数返回另一个异步对象时的行为 |
| --- | --- |
| JavaScript | `return promise` 合法，外层 Promise 接纳内层 Promise 的最终成功值或失败原因；不是把已经返回的外层对象替换成内层对象 |
| C# | `async Task<T>` 的有效返回类型是 T；通常需要 `return await otherTask`。普通函数返回 `Task<T>` 才能直接转发该任务。若 T 自身是任务类型，则属于嵌套任务结果，不是自动展开 |
| Rust | `async fn ... -> T` 的函数体产生 T；要从另一个 Future 得到 T，需使用 `.await`。将 Future 本身作为输出是另一种结果类型，不会自动展开 |

参考：[ECMAScript AsyncBlockStart 与 Promise 解析规则](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-asyncblockstart)、[C# 有效返回类型](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/classes#15611-method-body)、[Rust async 函数](https://doc.rust-lang.org/reference/items/functions.html#async-functions)。

## 4 状态机结构与所有权

### 4.1 所有权

```text
Future
  └─ owns → StateMachine
               ├─ 执行位置和生命周期状态
               ├─ 跨挂起点的绑定及必要临时值
               ├─ 跨挂起点的有效清理信息
               └─ 成功结果或失败信息
```

状态机不持有其所属 Future，也不通过反向引用向 Future 写入结果。Future 负责外部生命周期与等待通知，状态机负责计算及其结果。

状态机是编译器内部结构，不进入源码可引用的公开符号空间。Future 如何访问不透明状态机，具体布局、函数签名及调用约定尚未确定。

### 4.2 概念字段

以下是语义信息，不要求对应独立字段、堆分配或运行时列表：

| 信息 | 用途 |
| --- | --- |
| 执行位置 | 确定恢复后继续的位置 |
| 生命周期状态 | 区分运行、挂起、成功、失败及销毁过程 |
| 提升后的绑定与临时值 | 保存恢复执行或清理仍需要的数据 |
| 有效清理信息 | 确定已生效、尚未执行的清理及顺序 |
| 结果存储 | 保存成功值或异常值及其必要类型、所有权信息 |

不再使用附件中语义前 lowering 的未定类型 slot：源表达式已完成语义分析，生成字段应具有确定类型。

### 4.3 绑定提升

跨挂起点仍需使用的绑定进入状态机，包括业务代码、异常处理和清理代码所需的绑定。不得只检查 `await` 后的正常业务代码。

清理读取或修改原绑定时，提升后仍应访问同一逻辑绑定，不能擅自把引用语义改为注册时的值快照。

恢复后立即使用且不跨后续挂起点的临时值，不必因此永久占用独立字段。具体字段复用属于后续实现优化。

### 4.4 启动与首次挂起

Feng 采用 C# 标准 Task 模型的启动语义：

1. 调用 async 函数时建立 Future 与状态机，在当前调用中立即推进函数体。
2. await 的对象已经完成时，直接读取结果并继续执行；若是失败结果，在该 await 位置按异常规则处理。
3. await 的对象尚未完成时，建立等待关系并挂起，将当前 Future 返回调用方。
4. 若未发生挂起就完成计算，返回已经成功或失败的 Future；函数体未捕获的异常仍按第 8.1 节保存在状态机中。

调用 async 函数不意味着自动创建线程或向线程池提交任务。首次启动与挂起后的恢复调度是两个不同问题；恢复调度仍遵循第 9 节的库边界。

以下保留相关语言的行为比较：

| 语言 | 调用 async 函数后的启动行为 |
| --- | --- |
| C# 标准 Task 模型 | 调用时开始执行函数体，直到首次实际挂起或完成；已完成的 await 可以继续同步执行 |
| JavaScript | 调用时开始执行函数体，执行到 await 时让出；即使等待值已完成，await 后续也经异步恢复 |
| Rust | 调用只构造 Future，函数体在 Future 被 poll 时开始执行 |
| Python | 调用只创建 coroutine；由 await 或调度 Task 等方式驱动执行。Task 可以配置立即启动，不能与单纯调用 coroutine 混为一谈 |

参考：[C# async 函数执行](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/classes#15143-evaluation-of-a-task-returning-async-function)、[ECMAScript AsyncFunctionStart / Await](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-async-functions-abstract-operations-async-function-start)、[Rust async 函数](https://doc.rust-lang.org/reference/items/functions.html#async-functions)、[Python coroutine 与 Task](https://docs.python.org/3/library/asyncio-task.html)。

## 5 `@future` 协议边界

### 5.1 语义能力

本节只列协议必须解决的协作问题，不定义可直接实现的方法集合：

| 能力 | 要解决的问题 |
| --- | --- |
| 结果类型关联 | 从 `F` 确定 `T` |
| 创建与绑定 | 构造返回对象并使其拥有对应状态机 |
| 结果访问 | 从状态机读取完成状态、成功值或失败信息 |
| 等待注册 | 在完成与注册交错时不丢失通知 |
| 完成通知 | 计算结束后唤醒等待者，无须状态机反向持有 Future |
| 销毁与失效 | 终止后续恢复，执行清理并销毁状态机 |

状态机由谁推进、推进后由谁检查完成并触发通知，需要在协议中明确。不能因为需要通知就隐式引入所属 Future 的反向强引用。

### 5.2 等待关系

附件中的回调模型保留为协议设计基础：被等待对象未完成时保存等待回调，已完成时立即通知；“检查完成状态并注册等待”的整体语义不得丢失通知。具体同步实现不在本草案中选定。

```text
ParentFuture owns ParentStateMachine
ChildFuture 保存等待完成的通知
通知使 ParentStateMachine 获得继续执行的机会
```

状态机不反向持有所属 Future，也不预设通过持有被等待 Future 并再次读取它来取得结果。通知如何交付结果、结果在读取期间如何保持有效，属于第 10 节待决策的协议内容。

清空 ParentFuture 自身的回调，不能自动撤销已经注册到 ChildFuture 或已投递到执行上下文中的恢复通知。协议必须保证销毁后这些通知不再访问已释放状态机；本草案不擅自选择弱引用、注销令牌或其他具体机制。

已完成对象可能立即通知，协议还需明确同步通知与状态机当前执行的衔接方式，不能把“立即通知”等同于可任意重入推进状态机。

### 5.3 非 async 来源的值

普通库代码创建的 `@future` 值也应可等待。如何为这类值提供结果存储及与生成状态机一致的访问协议，留待接口设计，不要求它必须具有 async 函数的控制流结构。

### 5.4 协议方法定位

编译器识别 `@future` 后，按协议定位类型的方法，不依赖具体 Future 类型名。当前有两种待选方式：

- `@future`：协议约定固定的方法名，编译器按名称解析并检查签名。
- `@future("poll")` 等参数形式：注解指定协议方法名，编译器在所标注类型上解析并检查签名；`poll` 在此仅为命名示例。

两种方式都应在编译期完成方法绑定；注解参数不表示运行时按字符串查找方法。最终采用哪种形式、需要指定哪些方法及各方法的语义和签名，仍待确定。

## 6 AST 转换流程

async AST lowering 是独立编译阶段，位于源程序语义分析之后、发码之前。语法和语义阶段只处理源码层的 async/await 与 T/F 规则；状态机结构、控制流拆分、字段提升和清理路径均由 lowering 构造。生成节点所需的局部语义处理是 lowering 产物进入发码前的配套处理，不把状态机转换合入初始语义阶段。

```text
parse
  ↓
源 AST
  ↓
语义分析：绑定、类型、作用域、F/T 与 await 检查
  ↓
async AST lowering
  ├─ 分析挂起点与跨挂起点的数据、清理
  ├─ 生成状态结构与启动、恢复、完成、销毁路径
  ├─ 将 await 转换为等待、挂起和恢复控制流
  └─ 将结果完成和读取转换为协议操作
  ↓
生成节点所需的局部语义处理
  ↓
普通且类型完整的 AST
  ↓
现有发码
```

转换需要保留源程序的求值顺序、短路行为、循环与分支、作用域退出、异常捕获及资源清理。生成符号、字段访问、调用和控制流必须具有有效的语义信息；不能只改变 AST 而保留失效的语义引用。

“局部语义处理”的具体范围须依据实现中语义信息的存储方式确定，不预先声称只需要类型回填。

清理的作用域与有效性信息必须保留到状态机正常退出和销毁路径均构造完成；异常处理关系必须在控制流拆分后仍对应源程序的逻辑位置。

## 7 `defer`、作用域与状态机销毁

### 7.1 适用范围

已有块作用域和清理顺序以 [defer 规范](../specifications/feng-defer.md) 为准。本节只定义新异步方案中的生命周期衔接。

执行到挂起点时，已生效且所属作用域仍然有效的 `defer` 跨越该挂起点。所属作用域可以是当前块，也可以是仍有效的祖先块。

这类 `defer` 的清理信息进入状态机，其引用的跨挂起数据也进入状态机。清理动作本身可以生成静态代码；不要求每个 defer 都分配节点或维护动态列表。

### 7.2 行为表

| 事件 | 清理行为 |
| --- | --- |
| 执行到 `defer` 注册位置 | 对应清理生效 |
| `await` 挂起 | 保留仍有效的清理，不因推进函数返回而执行 |
| 从 `await` 恢复 | 清理继续有效，不因恢复而自动移除 |
| 正常或异常退出所属作用域 | 执行该作用域的有效清理并使其失效 |
| 销毁挂起中的状态机 | 执行全部仍有效的清理，然后释放状态机存储 |

清理遵守原有逆序，`defer` 与局部对象释放仍保持原有相对顺序，不改为“全部 defer 之后统一释放所有局部值”。尚未执行到注册位置的 defer 不执行，已经执行过的不得重复执行。

概念上，先从有效集合取出清理动作，再执行它，避免同一动作因清理中的异常或重入而重复执行。具体异常处理策略见第 10 节。

### 7.3 示例

```text
{
    resource = acquire()
    defer resource.close()
    await work()
    use(resource)
}
```

| 路径 | 行为 |
| --- | --- |
| 等待完成后正常退出块 | 执行 `use(resource)`，随后关闭资源 |
| 在等待期间销毁状态机 | 不执行 `use(resource)`，仍关闭资源 |

即使删去 `use(resource)`，`resource` 仍因清理引用而需要跨挂起保存。

### 7.4 销毁路径

状态机必须具有与正常恢复分开的销毁路径。销毁需要使后续恢复失效，执行仍有效的清理，并释放状态机持有的绑定、结果或失败信息及自身存储。

这些是生命周期要求，不是已确定的并发算法。正在执行的恢复与销毁如何协调、何时能够安全释放内存，须由协议补全。

## 8 async/await 与异常处理

### 8.1 跨挂起点的失败结果

异常先按源程序所在作用域的捕获逻辑处理。未捕获而导致异步计算失败时，将失败信息保存在状态机；等待方读取失败结果时，在对应 `await` 的逻辑位置进入异常处理。

不能让仅负责调度的回调代替 await 消费者接收该异常。保存的异常值及其必要元信息应具有足够生命周期，不能保存已失效的栈展开记录。

`poll` 若被用于命名接口，必须明确它表示推进计算还是读取结果；目前不把这两个职责合并成已确定的接口。

### 8.2 异常路径与作用域清理

异常传播与捕获遵循 [异常规范](../specifications/feng-exception.md)，作用域清理遵循第 7 节。async lowering 需要将物理推进函数退出与源程序作用域退出区分开：挂起保留仍有效的清理，异常离开逻辑作用域则执行相应清理。

销毁挂起中的状态机时执行仍有效的清理，不恢复 await 后的业务代码。销毁过程中清理再次失败的处理策略仍见第 10 节。

### 8.3 与现有 defer 清理失败处理的衔接

defer 调用的函数抛异常不是 async 特有问题，已有行为说明见 [defer 工程文档 §6.3](feng-defer-dev.md#63-defer-块内调用的外部函数抛出异常)。当前代码路径如下：

- 正常退出时，发码先调用 `feng_cleanup_pop()` 移除当前 defer 节点，再调用其清理函数。
- 异常清理时，运行时同样先推进清理链顶指针，再执行当前节点。
- 若被调用函数的异常未在 defer 内捕获，当前 defer 的后续语句不执行；已有工程方案通过新的异常展开继续处理仍留在链上的清理。
- `feng_throw` 当前释放已有的异常记录并建立新记录；此路径不是自动保留多个异常的聚合机制。

实现依据：[正常退出清理发码](../../src/codegen/codegen.c)、[运行时清理链与异常入口](../../src/runtime/feng_exception.c)。以上为文档与代码核查结论，不代表已额外运行清理中再次抛异常的回归验证。

异步方案应复用已有作用域清理行为。状态机销毁仍需明确其调用边界：当前运行时在 finalizer 执行期间调用 `feng_throw` 会直接 panic。如果销毁清理放在该边界内，就不能假定它与普通函数中的 defer 抛异常具有相同传播行为。具体销毁入口及失败如何报告仍需确认，不在此定义新的异常机制。

## 9 std 与执行上下文

附件中的 `AsyncContext` 定位保留：它是 std 提供执行上下文的一种设计，不是编译器强制识别的类型。是否捕获当前上下文、何时捕获、是否投递恢复，由 Future/执行上下文的库协议确定。

线程池、UI event loop、测试上下文等可以采用不同策略；本草案不要求统一 Scheduler 类型，也不增加既定的 runtime ABI。需要底层入口时，应先确认能否使用 Feng 与 C ABI 表达，再决定私有 runtime 能力。

## 11 后续验证范围

本草案仅整理设计，不修改代码和既有测试。设计确认后的验证需覆盖普通函数返回类型规则不变、async 函数按 T 检查返回值、显式 `return await`、不合法的直接返回 F、嵌套 Future 结果、不同协议类型、调用时立即启动、已完成 await 同步继续、未完成 await 挂起、分支与循环挂起、跨挂起点的异常捕获与失败传播、祖先块 defer、多次挂起、清理引用的绑定、正常清理后销毁不重复执行，以及销毁后的通知失效。销毁中清理失败的策略确定后，还需验证其行为。
