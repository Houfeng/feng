## 1 原则与两个阶段

- 编译器将 async/await 转成无栈状态机；lowering 位于源码语义分析之后、发码之前。Codegen 接收普通 AST 及完整的类型、绑定和生命周期信息，不处理 await 控制流。
- 薄状态机保存执行位置、跨挂起数据及有效清理；厚 Future 保存完成状态、结果、异常和等待关系。
- Future 单向拥有状态机；状态机不保存所属 Future。结果经推进调用边界交付。
- `@future` 采用单槽注册，不绑定类型名或 std 模块名，规则见 §2。
- 编译器只识别 `@future` 和 `@future("start")`。编译器为 Future 生成隐藏托管字段，创建并初始化 Future、绑定状态机后调用实例 start；start 允许 seal，由库负责首次驱动，不要求特定构造函数。
- 无结果异步按 [void 类型方案](feng-void-type-dev.md)使用 `Future<void>`，与有结果实例共享声明槽；该前置方案最终采用后独立交付，不在本文重复定义。
- 调用时立即执行至首次实际挂起或完成；已完成的 await 同步继续。`return await f` 显式等待，`return f` 不自动展开。
- runtime 的状态机 API 接收 Future，经描述符定位隐藏字段后操作状态机。调度由库实现；std 提供同步上下文，支持线程池、事件循环等实现。

| 层次 | 职责 | 不承担 |
| --- | --- | --- |
| 编译器 | 生成隐藏托管字段及状态机；按 §4.1 创建、初始化并绑定；调用实例 start；生成 await 输入／输出适配及隐藏字段定位信息 | 为 Future 另写 ARC 流程、识别完成查询／等待登记／结果读写等库方法 |
| runtime | 接收 Future，通过描述符定位状态机并提供推进、恢复输入、查询和关闭清理能力；释放复用普通对象流程 | 调用库成员、按 Future 类型特判释放、注册库启动回调、管理等待列表或调度 |
| 库 | 实例 start、Future 业务字段初始化、结果／异常／等待关系、串行驱动、通知、同步上下文及调度 | 声明或访问隐藏字段、传递状态机指针、手动维护状态机引用计数 |

| 阶段 | 交付 | 验收依赖 |
| --- | --- | --- |
| 一：编译器与 runtime | §2—§8 的语义、lowering、私有 API、FT 元数据和语言服务；§10 的编译器及行为测试 | 测试专用 Future 和手动驱动器，无须先实现 std 调度器 |
| 二：库 | std Future/Promise、同步上下文、线程池及事件循环接入；见 §9 | 使用阶段一的同一协议，不再修改语言规则才能运行 |

## 2 单槽注册

每次分析在源码及实际依赖闭包中登记一个规范化类型声明。源码声明收集、依赖元数据读取时顺带登记，不增加独立的类型遍历；未直接引用的依赖公开模块也参与，不扫描未使用的安装包。

| 输入 | 处理 |
| --- | --- |
| 首个合法声明 | 保存声明身份、协议成员和诊断来源 |
| 同声明重复导入、别名或菱形依赖 | 幂等 |
| 第二个不同声明；同声明重复标注 | 报错，冲突诊断指向双方来源 |
| 无注册且未使用协议 | 允许 |
| 使用协议但无注册 | 使用处报错 |

登记必须先于协议使用检查，且与文件／导入顺序无关；LSP 每次分析重建。泛型实例化共享声明槽。显式返回类型不能绕过注册冲突，仍遵循普通可见性规则。

协议类型为公开模块中的公开、引用语义对象 `type`；不允许 `@value`、`@abi`、tuple 或 spec 作为协议实现主体。泛型参数布局不固定；各实例的成员签名按普通泛型规则代入。

## 3 源码规则

### 3.1 独立前置：void 类型

void 的目标语义、实施范围及验收统一见 [Feng void 类型开发方案](feng-void-type-dev.md)。本文以该方案最终采用并交付为前提，不为 Future 单独放宽类型规则。

两份文档分别 Review、实施和验收：void 可在没有 async/await 时独立交付；async/await 接入其结果，仍按 §1 的编译器／runtime、库两个阶段交付。若 void 方案未采用，本文的无结果协议须重新 Review，不能默认为切换双槽或 Unit。

### 3.2 语法与类型

```feng
// 示例名称由库定义；Future<int> 对应的异步结果类型为 int。
async func twice(): Future<int> {
  let x = await load();
  return x * 2;
}

// 同一声明的 void 实例；body 可以空 return 或正常落尾。
async func save(): Future<void> {
  await write();
  return;
}
```

- `async func` 用于有实现体的普通函数／方法；Lambda 写作 `async (参数) -> 表达式` 或 `async (参数) { ... }`，仍须具备现有 callable-form spec 目标类型。泛型 callable 同样适用。
- `async` 在上述前缀位置、`await` 在 async callable 的一元表达式位置作为上下文关键字；`std.async`、`obj.await()` 等成员／模块名称仍合法。async body 内的局部绑定及参数不得命名为 `await`，嵌套 callable 独立判断。
- `await` 与其他前缀一元表达式同级，操作数包含完整的后缀调用／成员链；`await f() + g()` 等于 `(await f()) + g()`。普通函数和顶层使用 await 报错。
- 构造函数、终结器、`main`、`extern func`、顶层 `@abi func` 不接受 async。同步入口通过库驱动异步；普通外部函数可以按其既有 ABI 返回合法值，但不参与状态机生成。
- spec 中只声明返回 F 的普通方法／callable 签名，不标 async；实现可以同步返回 F，也可以使用 async。
- `F` 必须来自 §2 的声明；`T` 从注册声明的结果类型参数关系确定，不从库方法的签名推导。T 按普通类型规则检查，包括 §3.1 引用方案中的 void；该参数关系的精确定义见 §11 待 Review 项。
- async body 按 T 检查返回值及正常落尾；调用表达式类型为 F。普通函数不自动把 T 包装成 F。T 本身为 Future 时保持嵌套，不自动展开。
- defer 自身不允许 await；嵌套 async Lambda 的 body 独立检查。try/catch、分支、循环、普通表达式均可挂起。

### 3.3 返回类型推导

有显式 F 或 Lambda 目标 F 时，按注册的结果类型参数关系得到 T。否则先按[函数规范](../specifications/feng-function.md)及 §3.1 引用的 void 增量推导 body 的 T，再反求 F 的类型实参；全部实参唯一确定且满足约束才得到 F。结果类型参数关系须先按 §11 定稿，不能借助已删除的结果读取角色补推导。

不反推隐式转换，不补猜测实参；无法唯一确定时要求显式 F。无 return 或仅空 return 的 body 推导 T 为 void，再按同一规则确定 F；只有无目标类型的 `()` 等表达式、无法确定 T 时要求显式返回类型。推导不扫描其他协议声明。

## 4 类型与实例 start 协议

以下为**签名模式**，不是完整可编译的类。F 为当前注册声明的实例，T 为结果类型，E 为已注册 `@throwable` 根 spec。库不需要声明状态机类型或指针。

| 标记 | 标注目标／形状 | 契约 |
| --- | --- | --- |
| `@future` | Future 类型声明 | 单槽注册；声明的泛型实例共享该槽 |
| `@future("start")` | 实例方法 `seal func start(): void` | 对已初始化且已绑定状态机的 self，同步首次驱动至实际挂起或完成 |

start 在注册声明内恰好一个，随成员收集登记，按成员身份绑定，重复报错，不增加独立遍历。它是同步、无显式参数、返回 void 的实例方法，不允许成员级泛参。类型和方法名不固定；隐藏字段由编译器生成，不参与源码成员注册。

start 可以为 seal；编译器生成的调用按已绑定成员身份忽略普通可见性限制，该权限不扩展到用户源码。跨包和纯 FT 保留其身份、签名和可见性。隐藏字段不是可由库访问的 seal 成员，不暴露到源码成员查找或补全中。

隐藏字段见 §6；完成查询、等待登记、结果读取、成功／失败发布及驱动均为普通库行为。state、ready、poll、value、resolve、reject、resume 角色及 new 名称不是有效注解参数。

### 4.1 创建与首次执行

```text
生成入口：
  按普通顺序求值并保存参数／接收者
  创建 Future 实例 f，执行普通字段初始化
  创建状态机，保存本次调用的输入
  通过普通托管字段赋值，将状态机绑定到 f 的隐藏字段
  调用 f 的已注册实例 start()
  返回 f；临时持有按普通返回及异常路径清理

库的 start：
  完成首次驱动所需的库侧准备
  经库驱动逻辑调用 runtime API(self)，执行至实际挂起或完成
  返回 void
```

编译器负责实例创建，不依赖特定构造函数，也不跳过普通字段初始化器。start 不再创建或返回 Future；进入 start 前，字段初始化及状态机绑定均已完成，库侧准备须在执行 body 前完成。runtime 不注册或转调库启动入口；首次驱动不等于投递线程池。

隐藏字段赋值、调用及返回均使用普通托管引用规则。创建、初始化或 start 失败时，释放该路径已经建立的局部持有；绑定前后均不得泄漏或重复释放。库不手动绑定或释放隐藏字段。

参数求值、Future 初始化、建帧和 start 的库侧准备失败沿同步调用传播；body 的未捕获异常由生成边界捕获并作为失败结果交给库，包括首次挂起前的异常。库将其保存到 Future，不从 start 重新抛出该业务异常。初始化／启动异常与 body 失败必须区分。

async 调用按普通值边界保存参数和接收者：引用类型保活原对象；值类型接收者复制到该次计算的状态中，之后的 self 修改该副本。闭包捕获可变绑定继续共享原绑定单元，不转为注册时快照。此接收者规则是本次新增提案。

## 5 await 与库驱动

以下是边界上的逻辑事件，不预设新增公开类型或具体 ABI；其编码和跨结果类型访问方式须按 §11 定稿。

```text
状态机执行到 await child_expr：
  求值一次并保活 child
  保存继续位置，交付 Waiting(依赖对象、依赖类型、预期结果类型、等待标识)

库驱动器收到 Waiting：
  依赖已完成 → 取得结果／异常，立即经 runtime 恢复，不入队
  依赖未完成 → 原子复查并登记完成通知，实际挂起
  通知到达   → 按库调度策略取得结果／异常，经 runtime 恢复

状态机恢复：
  将本次等待的成功结果送入原 await 表达式，或在该位置抛出异常
  释放本次等待专用的依赖持有，继续源码控制流

状态机结束：
  交付 Succeeded(T) 或 Failed(E)
  库保存 Future 的完成结果，并通知等待者
```

库必须保证完成检查与通知登记之间不丢失完成事件，每次等待至多恢复一次。同步到达的通知不得递归推进正在运行的帧；采用库内串行控制，推进、通知及用户代码在临界区外执行。不得仅因通知到达就绕过结果就绪或等待标识检查。调度和恢复上下文见 §9。

Future 的结果由库保存，允许多个等待者及重复 await，读取不消耗结果；手工 Promise 即使没有状态机也必须可等待。编译器不读取依赖 Future 的内部字段，不通过其是否有状态机推断完成，也不直接调用约定名称的库方法取结果。等待对象到库接口的具体桥接仍须在 §11 闭合。

库的等待通知及队列任务强持有目标 Future，直到执行或移除；父状态机只持有 child 等源码数据，不保存所属 Future 或其驱动回调。该持有策略是待 Review 提案，对象图可能成环，须按 §6 回收。丢弃一个外部引用不等于取消。

## 6 状态机与 runtime 私有 API

### 6.1 表示、持有与清理

编译器在普通字段布局和生命周期分析之前，为注册的 Future 生成一个源码不可见的、**类型擦除的托管引用槽**，并生成遵循普通托管引用规则的字段赋值。该槽不固定具体对象类型，也不是源码裸指针字段；库不声明或访问它，不为此引入内部 State spec。

每个 async 函数／Lambda 定义生成自己的具体状态机类型，保存所需的跨挂起绑定；同一定义的每次调用创建独立实例，泛型按现有泛型机制处理。槽在表示上可持有不同具体类型的托管对象，但本协议只允许编译器将生成的状态机写入其中。实际对象保留对象头、具体类型描述符及清理信息；同一 Future<int> 的布局不随状态机类型变化。类型擦除不意味着 runtime 可以把任意托管对象当作状态机推进。

编译器须明确表达该槽的托管所有权，并接入普通字段处理：赋值维护持有，描述符枚举引用，字段释放函数释放持有，强引用图包含 `Future → 状态帧`。不能因具体目标类型被擦除而遗漏强边或判为无引用；无法证明无环时遵循既有保守分析规则。接入后复用现有 ARC 和循环回收，不为 Future 另写计数、trace 或释放算法；不能假定加入一个无具体类型的槽就已自动完成接入。库终结器不重复释放隐藏字段。

runtime 的对象释放路径不判断对象是否为 Future。ARC 归零、终结及复活检查、字段释放、循环回收统一遵循[生命周期规范](../specifications/feng-lifetime.md)。仅状态机操作 API 根据描述符中的定位信息访问隐藏字段；其布局定位契约见 §6.2。

所有注册 Future 实例均具有同一规则生成的隐藏字段，包括普通库代码创建的实例；布局不能取决于当前模块是否含 async body。手工 Promise 的 Future 可以没有关联状态机，仍按 §5 的库等待协议工作；不为其创建空状态帧。

状态帧使用现有托管对象头及描述符，包含 pc、执行状态、跨挂起值和有效清理信息。尚未初始化／已释放的值槽采用编译器生成的普通 `Empty | T` 具名 union，默认 Empty；T 在源码求值位置才构造，避免建帧时提前执行 T 的默认初始化。该 tag 同时决定槽是否参与 trace／release，不保存未定类型值。

帧内引用在保存时持有或转移所有权，挂起不释放仍然活跃的槽；覆盖、作用域退出和关闭时按有效状态清理。帧的生成终结路径执行尚未执行的清理，循环路径同样适用，不能只依赖不会在该路径执行的 release-children。每个清理先失效再调用，保持 defer／局部释放的交错逆序。普通生命周期规则引用[生命周期规范](../specifications/feng-lifetime.md)，不新增另一套计数或循环回收器。

帧关闭幂等；正常完成已经清理过的作用域不再执行。关闭开始后不能恢复业务代码；即使清理导致对象复活，帧也保持 Closed，库按关闭态处理，不能重新运行。尚未初始化的槽不释放。持有类型参数的帧保存普通泛型描述符，不改变泛型 ABI。

### 6.2 runtime 操作边界

状态机操作 API 接收 Future，通过其描述符中的定位信息取得隐藏字段，再操作所关联的状态机；不按字段名查找，不假定固定偏移，不调用库成员。定位元数据仅服务于状态机操作，不替代普通托管字段元数据。下表定义所需能力，不固定入口数量、函数名、整数状态编码或 C ABI；具体签名在 §11 Review 后补齐。

| 能力 | 契约 |
| --- | --- |
| 首次推进 | 从 Ready 执行，交付 Waiting、Succeeded 或 Failed |
| 恢复并推进 | 仅向当前等待交付匹配的结果／异常；验证等待标识及类型，再执行至下一个事件；不能无输入跳过 await |
| 查询 | 区分没有关联状态机与已有状态机的执行状态，不执行用户代码，不查询库的 Future 完成结果 |
| 关闭清理 | 与推进互斥；先置 Closed，再执行有效清理；重复关闭无操作，不能继续业务代码 |

推进过程中为 Running，交付等待后为 Waiting，完成后为 Done；Done／Closed 不允许重新执行或重复交付完成结果。没有关联状态机的 Future 不能用于推进；其等待和完成仍由库处理。runtime 调用期间须保证传入 Future 及所关联帧有效，按既有托管调用边界保活；不将该 Future 保存为帧的反向引用。关闭不等于释放所有引用，不要求库调用 async 专用 retain/release API。

库必须串行化同一状态机的推进、恢复、关闭及相关查询。runtime 不调度、不阻塞等待、不创建线程、不额外维护 Future 锁；非法并发不以运行时检查替代库同步。同步重入检测及状态错误的具体处理在 ABI Review 中确定。

生成的状态机入口与 runtime 共享推进／清理约定；隐藏字段定位信息由编译器提供，start 生成按成员身份绑定的直接实例调用。runtime 不持有库方法分派表，也不借推进 API 承担 Future 的结果发布、通知或调度。

### 6.3 等待、结果及异常交付

等待请求必须携带依赖对象的有效持有、具体类型身份、预期结果类型及本次等待标识。恢复输入必须区分成功值与异常，不以 `T | E` 去重后的类型分支代替成功／失败标记。T 为 void 仍有明确的成功事件，无载荷不等于未完成。

运行时不得从裸载荷指针猜类型。编译器生成对应挂起点的类型适配，结果／异常按普通复制、持有与释放规则传递；E 是普通异常根值，不是 `_Unwind_Exception` 或 TLS catch 指针。事件载荷的实际表示、有效期、移交及跨泛型实例访问须在 §11 定稿；不能假定库已能安全消费未定义的类型擦除接口。

挂起保留逻辑作用域，只拆除本次物理异常框架；恢复失败在原 await 的词法位置抛出。状态机成功／失败先完成源码作用域清理，再通过推进边界交付结果；Future 的长期结果与通知由库维护，不存入状态帧。输出交付期间的临时持有须覆盖库接收过程，不额外假定结果盒或额外堆分配。

## 7 lowering、异常与工具链

### 7.1 转换顺序

```text
Parser → 源码 Semantic → async lowering → 生成节点语义／生命周期事实 → Codegen
```

1. 先将含 await 的表达式拆为有序临时绑定和控制流，保留短路、分支、循环及求值次数。
2. 对正常、异常、清理边求活跃信息；跨挂起值进入帧，闭包共享单元及已取地址存储保持身份。原始指针借用仍按互操作规范由调用方保活 owner，不新增隐式安全承诺。
3. 生成普通内部类型、创建／绑定入口、advance／close 函数及 pc 分派；生成声明不进入用户可见符号空间。Future 的隐藏字段按 §6.1 在布局和生命周期分析前补齐；挂起只退出物理推进，不退出源码逻辑作用域。
4. 重建受影响的符号、成员绑定、泛参替换、异常和所有权旁表；不复用指向已替换节点的语义引用。源码 AST 保留给 LSP 和诊断，生成节点关联原源码位置。

已完成的 await 由库驱动器同步恢复，不设置调度任务；Waiting 路径保存 pc 和必要数据后交付依赖。close 只执行有效清理及释放，不运行 await 后续业务代码。共享绑定和需要稳定地址的槽不参与字段复用；其他字段复用属于正确性验收后的优化。

### 7.2 异常衔接

- body 失败经推进边界交付 E，由库保存；恢复输入为失败时按原 await 的词法位置抛出和捕获。调度回调不能成为业务异常接收者。
- catch 内允许 await。挂起时将仍活跃的异常载荷及其类型身份保存为受持有的值，退出本次 TLS catch／cleanup 框架；恢复后重建逻辑 catch 关系。`throw;` 保留原载荷身份，原生展开记录不跨挂起保存；内层 catch 不覆盖外层保存值。
- `f()` 的摘要包含参数求值、Future 字段初始化、建帧及 start 的同步逃逸；body 的失败由生成边界捕获。await 将恢复输入的失败计入该表达式异常效果，无法证明具体异常类型时保留 unknown，不宣称无异常；不再读取约定库方法的摘要。阶段一不增加跨任意 Future 值的精确失败来源追踪系统。
- [defer 主规范](../specifications/feng-defer.md#6-与异常模型的关系)已经禁止异常逃逸，原规则不变。当前 `feng_throw` 在 finalizer 中无条件 panic，尚不满足[生命周期规范 §13.2](../specifications/feng-lifetime.md#132-终结器执行流程)允许内部捕获的要求。
- 阶段一必须统一修正终结器异常边界：建立边界保护框架，允许边界内 catch；无匹配内部处理器时在越过边界前终止，不能被外部 catch 接管。throw 与 rethrow 使用同一边界规则，不按“是否 async”分支。此项是已有语义的 runtime 配套修正，须单独验证。

### 7.3 元数据与诊断

FT 保存 async 源声明标记、唯一 Future 声明身份、start 实例方法的身份／签名／可见性、结果类型参数关系，以及隐藏槽的类型擦除／托管所有权事实和 runtime 定位契约所需的元数据。源码、纯 FT 和缓存对同一实例生成一致布局，不重复添加隐藏字段。seal start 可供编译器内部绑定，隐藏字段不进入源码可见面。按既有版本／缓存失效规则更新格式。LSP Hover/SignatureHelp 展示调用返回 F、await 得到 T；生成函数及隐藏字段不成为用户补全结果。

新增诊断覆盖：类型／start 标记的目标／参数／签名错误、重复注册、缺失协议、非法 async/await 位置、F/T 不匹配、推导不唯一、defer 挂起和源码越权访问 seal 成员。编号按现有诊断主表分配；避免在类型解析失败后追加依赖性协议错误。创建及绑定由编译器保证；start 是否首次驱动属于库的执行契约，不能声称仅凭签名检查即可证明。

## 8 第一阶段实施顺序与成本

进入本阶段实施前，[void 类型方案](feng-void-type-dev.md)须已独立交付；其基础语义和工具链验收不并入本文。

| 顺序 | 工作及完成条件 |
| --- | --- |
| A | 闭合 §11 的结果类型参数关系和等待／结果 ABI，Review 批准实施细节；将源码行为收敛到相关主规范，旧 async 方案标为历史方案 |
| B | Lexer/Parser、单槽与类型／start 标记登记、F/T 检查、隐藏字段及 FT／缓存布局一致性；非法程序在源码语义阶段诊断 |
| C | 独立 lowering、Future 创建／初始化／绑定、普通字段生命周期接入、以 Future 为参数的 runtime 操作及字段定位、输入／输出适配、终结器边界；直接完成、挂起恢复、挂起关闭均可运行 |
| D | 接入测试 Future 的 seal 实例 start 及手动驱动、语言服务，完成 §10 验收；仅随后进入 std 阶段 |

成本目标：每次调用一个 Future 和一个状态帧；有捕获的通知闭包按现有规则分配，不声称每次 await 零分配。库对已完成依赖不登记通知、不入队；不跨挂起的局部不提升；defer 使用静态槽／标志，不分配注册节点。类型与 start 绑定均在编译期，start 生成直接实例调用；非 async 函数不增加状态机或驱动控制，但其创建的注册 Future 同样包含隐藏字段。库承担串行驱动同步成本；可能成环的帧及 Future 须保持正确的循环回收行为。

等待事件交付及恢复增加的边界调用、载荷复制和类型适配成本必须测量，不宣称与旧的直接方法快速路径等价。ABI 定稿须同时评估已完成 await 的路径，未经 Review 不引入额外装箱或分配。

阶段一记录同步完成、一次／多次挂起的分配数、retain/release、耗时及峰值内存，与等价手工协议实现对照。不得为性能省略清理或所有权；额外装箱、额外运行时全局表或通用同步开销需另行 Review。

## 9 第二阶段：std 与同步上下文

std 实现 §4 的唯一 Future 声明及 Promise，以普通字段初始化器建立业务字段初值；实例 start 在编译器完成 §4.1 的创建和绑定后，通过 runtime API(self) 首次驱动。库不声明状态机字段。手工 Promise 的 Future 可以没有关联状态机，完成状态及等待关系仍由库维护；它与 async Future 使用同一套库等待逻辑。

库的驱动器按 §5 消费状态机事件。完成查询、等待登记、结果读取、成功／失败发布和再次驱动的方法名及组织方式由库决定，均不增加编译器标记。库在同步保护下发布终态并取走等待列表，锁外通知；失败保存为普通 E 值。完成通知不能向调度器逃逸业务异常。

库的内部关闭请求先阻止新推进；若正在推进，只登记请求，由驱动者在本次推进返回后处理，不等待自己。无在途推进后将 Future 传给 runtime，关闭其关联状态机；原来未完成的 Future 发布 `Error("async/closed")`，已完成结果不变。该关闭步骤用于生命周期协调，不新增公开取消 API。

若清理后对象复活，库在串行控制下通过 runtime API(Future) 查询关联帧状态，为 Closed 时同样转换为关闭失败，不重新挂起；无状态机是手工 Promise 的合法情况，不等于 Closed。不可达对象回收只释放通知，不投递新任务。runtime 关闭操作本身不构造这种库错误。

库接口提案为 `Promise<T>.future: Future<T>`、`resolve(value: T): void`、`reject(error: E): void`；Promise 不能重复完成。Future 对外提供 `isReady(): bool` 和 `result(): T`，后者只读取已完成结果；这些名称不构成编译器协议。普通函数需要等待时使用上下文的库驱动入口，不把阻塞等待放入 Future。无业务结果使用 `Promise<void>`／`Future<void>`，成功完成调用 `resolve(void)`。

同步上下文的最小契约如下，类型名不是编译器协议的一部分：

```feng
// 接口示意；W 是库定义的无参数、返回 void 的 callable-form spec。
open spec SynchronizationContext {
  func post(work: W): void;
}
```

库提供当前线程上下文的读取及作用域安装。实际登记等待时捕获当前上下文；完成后通过该上下文 post 恢复任务，没有安装上下文时使用线程池上下文。已完成 await 不 post。执行任务时安装该上下文，退出恢复原上下文；上下文存取和恢复全部在库中。

post 不内联执行 work，必须保证接受的任务最终执行；停止上下文前先排空任务，不静默丢弃。线程池实现不保证同一线程；事件循环实现固定在线程内执行。任务强持有目标 Future，恢复前检查关闭状态；同一 Future 即使收到同步通知也由库串行推进。跨线程共享数据的同步责任不因 async 改变。

不把取消、超时、异步流或异步析构追加为本轮语言特性；后续库扩展不得改变上述状态机契约。

已确认：单槽注册 Future，仅保留类型与 start 标记。编译器生成隐藏的类型擦除托管引用槽，按 §4.1 创建、初始化并绑定后调用实例 start，start 允许 seal；槽的表示、使用边界及普通 ARC 接入按 §6.1 执行，runtime 接收 Future 并经描述符定位状态机。Future 的业务行为与调度属于库。void 决策集中在其独立开发方案中。
