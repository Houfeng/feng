# Feng 空清理边界性能优化方案

## 1. 状态与目标

状态：2026-09-25，方案待人工 Review，尚未实施。本文承接
[原生异常性能方案的 O04／O11](./feng-native-exception-performance-dev.md#9-实施记录)，
独立定义后续清理边界优化；此前批准的插件优化不代表本方案已获实施批准。

目标：根据编译期能够证明的实际清理责任，省略不必要的函数／try marker、配套
TLS 清理链操作和空异常清理入口。在保持 C IR 与原生 EH 的前提下，同时降低正常
调用、try 正常返回以及异常经过无资源函数时的成本。

基线为 `a0e0956a`，实施时冻结其配套编译器、runtime、插件与测量产物。本文不预先
承诺收益比例，也不把所有函数／try 都省略 marker 作为目标。

语言规则只引用主规范：

- [对象生命周期](../specifications/feng-lifetime.md)：所有权、终结器与循环回收。
- [异常](../specifications/feng-exception.md)：展开、匹配、重抛及异常载荷所有权。
- [defer](../specifications/feng-defer.md)：作用域退出与清理顺序。
- [插件协议](./c-ir-llvm-exception-plugin-dev.md)：C 发码与原生 EH 的交接。

## 2. 已确认的实现与成本

| 事实 | 代码依据 | 含义 |
| --- | --- | --- |
| 普通 callable 入口建立函数 marker 和根 cleanup region | `src/codegen/codegen.c` 的 `cg_emit_function_eh_prologue` | 没有本地清理资源的函数也可能保留 push／pop；异常经过时进入空清理再 resume |
| try 保护体前建立 marker，正常退出时弹出 | 同文件的 `cg_emit_try_expr`、`cg_release_scope` | 当前不依据保护体实际清理责任省略正常路径登记 |
| marker 初始化写字段并修改本线程清理链 | `src/runtime/feng_exception.c` 的 `feng_frame_push`、`feng_try_frame_push`、`feng_frame_pop` | 不是 ARC 计数操作，但仍有调用、栈写入和 TLS 成本 |
| catch begin 将 try marker 转为异常记录的清理所有者 | 同文件的 `feng_exception_catch_begin`、`feng_exception_catch_end` | 不能因为保护体没有资源，就把 catch 的所有权登记一起删除 |
| 正常退出和显式控制转移已共用作用域清理入口 | Codegen 的 `Scope`、`Local`、`cg_release_scope`、`cg_release_through` | 可复用既有清理组织，不另建按语法形式分支的退出机制 |

已有耗时、汇编及原生 C++ 对照集中保留在
[O04](./feng-native-exception-performance-dev.md#o04正常路径剩余的-try-专属成本2026-09-25待人工决策)
和 [O11](./feng-native-exception-performance-dev.md#o11原生控制结果与函数边界剩余项2026-09-25待人工决策)。
这些证据支持继续检查空边界，不足以把完整 Feng／C++ 的差额全部归因于 marker。
marker 在 S11 前已经存在，其收益与 S11 新增成本的消除必须分别报告。

## 3. 范围与职责

本方案只改变已经证明无必要的清理边界发码。已有资源的登记、释放、ARC 计数、
defer 执行及 catch 记录管理仍走现有机制。

| 层次 | 拟承担的工作 |
| --- | --- |
| Feng Codegen | 复用 `ExprResult`、`Local`、`Scope` 与实际登记入口，收集清理需求；据此统一决定边界建立、正常退出及异常退出发码 |
| 通用 LLVM 插件 | 消费既有协议，继续执行原生 EH 转换与已有 CFG／nounwind 优化，不识别 Feng 类型或 runtime 名称 |
| runtime | 使用现有接口与布局；本方案不新增或修改函数签名、结构字段、TLS 表示和清理顺序 |
| 验证 | 增加发码／IR 检查和语言行为覆盖，复用异常性能基准，分别验证正常路径与异常路径 |

不改变公开插件协议、版本、FT、语言异常检查、ABI、工具链版本、发布流程及
sanitizer 配置。暂不做逐个资源的静态异常清理替代、清理链重构、ARC 消除或异常
记录分配优化。[ARC 所有权优化](./feng-arc-ownership-performance-dev.md)独立 Review、
实施和交付。

## 4. 通用清理需求判定

### 4.1 判定对象

判定单位是一个 callable 的清理边界，或一个 try 保护体的清理边界。事实来自实际
发码所建立的所有权，不以 AST 中是否出现对象声明、是否有 `throw` 或参数是否为
标量代替证明。

至少记录以下清理需求：

1. 托管局部和临时值，包括调用参数保活、转换、装箱、捕获及表达式结果存储。
2. 按值聚合体、开放泛型和重化存储的清理，包含条件初始化后的资源。
3. defer 登记及其环境中由本边界负责的资源。
4. 活跃 catch 的异常记录所有权，以及异常退出时必须移除的清理节点。

仅当覆盖该边界所有可达路径，且证明没有上述责任时，结果才是“可省略”。存在
资源或事实不完整时保留当前行为。已清空但仍留在 LIFO 链中的节点同样属于责任，
不能因其不再执行 release 而忽略。

函数是否可能抛出，与本层是否需要清理是两个独立事实。调用的异常集合为
`unknown`，本身不意味着调用者拥有资源；反之，函数不会外抛，也不意味着没有
ARC 或 defer。隐藏桥接／临时值仍须计入，不能用源码异常集合推导清理为空。

### 4.2 收集与发码

建议复用现有局部登记和退出发码入口维护结构化的编译期事实，在实际资源登记、
defer、catch 所有权及条件存储建立处完整记录；子作用域释放编译器元数据前，将
需要的事实归入所属边界。不能在最终 `Scope.items` 上计数，因为子作用域可能
已经弹出，早退路径也可能已发码。

先完成边界内的事实收集，再组织入口、主体和各出口的输出。优先采用现有发码
缓冲与结构化边界记录，禁止通过搜索／替换生成 C 文本来删除 push、pop 或 label，
也不增加运行时“是否为空”的判断。

`return`、`break`、`continue`、正常落出及异常路径必须消费同一份判定。Lambda、
defer thunk、方法和生成的 callable 各有独立根作用域；不能把外层函数的判定直接
用于内层 callable。

### 4.3 泛型与跨包

共享体的证明须适用于它支持的全部实参。开放描述符可能要求托管／聚合清理时，
保留边界；不能因为某次调用传入 `int` 就删除共享体的清理。仅借用且无需本层管理
的值，与拥有独立副本的值，按已有调用和存储约定区分。

跨包调用继续使用已有参数／返回所有权约定和当前实际生成的桥接。省略调用者的
空边界不要求读取被调用函数体，但必须证明调用者自己没有清理责任，并保持被调
用者正常返回和原生展开时的既有责任。缺少必要事实时保留边界，不新增 FT 契约。

## 5. 两项发码优化

### 5.1 无资源 try：把 marker 建立移到匹配 catch 的路径

对通过 §4 证明的 try：

| 路径 | 拟发码行为 |
| --- | --- |
| 正常进入／完成保护体 | 保留 EH 区域和异常后继，不执行 try marker push／pop |
| 正常 return／break／continue | 按真实作用域退出，恢复父 EH 区域，不弹出不存在的 marker |
| 匹配某个 catch | 在调用现有 `feng_exception_catch_begin` 前建立该 context 的 try marker，然后保持原 catch 所有权流程 |
| 本层没有匹配 catch | 不调用针对该 try 的 `feng_frame_release_to`，以同一异常记录向父区域传播 |

`FengCatchContext`、异常记录和 selector 的使用仍遵守既有协议；延后的是 marker
登记，不是重新抛出异常，也不是省略 catch begin／end。记录从 landing 交接到
catch owner 前不能插入可能外抛的用户代码；匹配完成后先建立有效 owner，再执行
绑定、转换和 catch body。

保护体中存在资源、defer，或内层 catch 所有权可能经过该边界时保留现有登记。
本 try 自己的 catch 所有权在匹配路径建立，与保护体是否需要正常路径 marker
分别判断。

### 5.2 无资源 callable：省略函数 marker 和根清理区域

对通过 §4 证明的 callable，成组省略函数 marker 的声明、push／pop、根 cleanup
region、对应 `release_to` 和传播入口。该函数仍可向调用者传播异常，不得因此
标记为 `nounwind`；确有 catch 的区域也不能因省略纯 cleanup 而丢失。

首轮证明要求整个 callable 没有自身清理责任；包含 catch 所有权、defer、资源或
未知清理的 callable 保留函数边界，不扩展为逐条路径的动态 marker 懒初始化。
EH 区域编号及父区域须一致更新，不能留下指向已删除根区域的引用；协议配置是否
仍需输出按既有协议处理，不靠删除异常元信息强迫宿主忽略异常。

两项分别实施、测量，再检查组合效果。资源存在时仍使用原清理机制，不通过
关闭内联、降低优化级别或增加堆分配实现简化。

## 6. 正确性验证矩阵

`test/` 检查清理需求判定、C／LLVM IR 与协议结构；`fcts/` 检查可观察行为。
每类正向优化用例都要有必须保留边界的反例，不能只验证标量成功路径。

| 维度 | 必须覆盖 |
| --- | --- |
| 边界组合 | 函数空／非空、try 空／非空、只消除函数、只消除 try、组合；相邻和多层嵌套 |
| 控制流 | 普通落出、各层 return、循环 break／continue、短路、if／match／try 表达式及分支抛出 |
| 资源 | 局部、临时值、参数保活、结果合流存储、条件初始化、托管字段聚合体、defer 和已清空但未弹出的节点 |
| 异常 | 具体／兜底 catch、匹配／不匹配、内层处理后继续、重抛／抛新值、catch 内调用再抛及异常记录准确一次释放 |
| 泛型 | 函数／类型／方法泛参、开放共享体与闭合实例、受管值／平凡值／聚合值、描述符恢复与隐式桥接 |
| 调用边界 | 普通函数、方法、Lambda、defer thunk、spec／callable 间接调用、跨包且生产者源文件不可见 |
| 生命周期 | 终结器顺序、defer LIFO、返回值存活、嵌套异常保活、原有终结器异常屏障 |
| 工具与目标 | O0／O2／O3、普通／现有 sanitizer 配置、DAP 断点及单步、五个既有目标平台 |

复用既有 `test/codegen/test_native_exception.c`、`test_nested_exception.c`、
`test_defer_generic_context.c` 及相应 FCTS 的覆盖组织，新增针对性用例。
既有测试预期若依赖“所有函数必有 marker”等旧结构，先逐项列明迁移原因并获
人工批准，不能弱化语言行为、调试停靠或安全性断言。

## 7. 性能验证与验收

测量方法复用 [异常性能基准说明](../../test/exception_perf/README.md)：固定源码和
配套产物，动态输入、预热、交替多轮测量，区分 O0／release、同翻译单元／跨包。
本方案至少保存“基线、只优化 try、只优化函数、组合”四组，不能只给组合总收益。

除原有正常调用、try、浅层／深层／稀疏抛出外，补足有资源及无法证明为空的对照。
记录 marker／TLS 操作、清理入口和 resume 的静态结构及热路径执行情况、栈大小、
代码／异常表体积和耗时。无 marker 不等于没有任何异常相关的寄存器或栈成本。

验收需同时满足：

- 能证明为空的边界确实消除了对应操作；有责任或无法证明的边界仍正确清理。
- 正常与异常退出保持语义，不能用 release 的收益掩盖 O0 退化。
- 分别报告相对 `a0e0956a`、S11 前有效行为样本和同工具链 C++ 的结果；对比口径
  参见原生异常性能方案，不把旧 S11 错误执行纳入有效性能基线。
- 沙箱外完整 `make test` 与显式完整 std／FCTS release 回归通过；五目标分别记录
  编译与执行结果，模拟执行不能代替原生性能测量。缺失环境不得标为通过。
- 未新增运行时检查、分配、ARC、锁或协议操作；若出现性能取舍，先记录并交人工决定。

如按方案不改插件源码，无需重建插件；若实施发现必须改变公开协议、runtime、ABI
或 FT，停止该扩展，提交原因和替代方案 Review，不顺带实施。
