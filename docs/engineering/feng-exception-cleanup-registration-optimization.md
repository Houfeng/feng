# Feng 异常清理登记通用优化方案

> **状态：方案草案，待人工 Review；未实施。日期：2026-10-16。**
>
> 与[值对象构造期清理登记修复](feng-value-literal-conditional-cleanup-bugfix.md)分两步交付。
> 先用既有机制修复清理遗漏，再选择和验证本文的优化，不承诺未经验证的收益。

## 1. 目标与现有边界

目标是通用地减少异常清理登记的正常路径成本，同时保持正常退出、异常展开、
终结器／defer 顺序、所有权转移和调试行为。不能针对具体类型名称、库或评测用例
选择不同实现。语言规则引用[生命周期](../specifications/feng-lifetime.md)、
[异常](../specifications/feng-exception.md)和[defer](../specifications/feng-defer.md)主规范。

当前普通语句和表达式已经使用同一异常分析器与求解器，包含调用、参数、分支、
循环和捕获处理。拥有资源的局部值仍主要按所有权规则登记，未根据其后续整个
存活区间的异常风险统一省略节点。

`feng_cleanup_push`／`feng_cleanup_push_aggregate` 初始化栈上节点并修改线程
清理链；正常退出 `pop`，异常由现有清理入口消费。节点不需要堆分配，但仍有
栈写入、线程局部存储访问以及可能的函数调用、寄存器和栈布局影响。

已有[空清理边界优化](feng-cleanup-boundary-performance-dev.md)处理没有资源责任
的函数／try marker。本文处理有资源时的登记，不重做该优化；资源节点减少后，
边界是否还能省略应继续使用其既有统一规则。

## 2. 统一的证明对象

分析对象是“一份拥有权需要保护的区间”，而非“某条语句本身是否抛异常”：

| 拥有者 | 需要分析的区间 |
| --- | --- |
| 普通局部变量／拥有参数副本 | 取得拥有权后，直到释放或转移；包含后续语句、分支和循环 |
| 构造中的值／tuple | 已取得资源后，直到完成并交给消费者；默认字段和构造结果也计入 |
| 表达式、接收者和实参临时值 | 取得资源后，直到消费完成；包括后续实参求值及调用 |
| 条件产生的拥有者 | 覆盖实际初始化分支及合流后的存活路径，不能读取未初始化存储 |

例如 `let a = makeResource(); mayThrow();` 中，即使第一句不抛异常，仍不能取消
`a` 在第二句执行期间的保护。外围 catch 使函数的外抛集合为空，也不能证明其内层
作用域没有异常退出。内部 catch 处理后继续使用资源，与异常越过资源清理边界，
必须区分。

证明还应覆盖编译器插入的初始化、转换和调用，不能只检查源码中显式写出的调用。
已经由语言规范禁止向外传播异常的操作，沿用其既有规则。

统一规则：只有证明区间内不存在需要本层异常清理的退出，才可省略异常登记；
未知、缺失或未完成的事实保留登记。正常 `return`／`break`／`continue` 和作用域
结束的释放不能一起删除。defer 执行责任、catch 异常记录和已清空但尚未退链的
节点也不能由“没有托管字段”或“函数不外抛”推断为无责任。

复用现有异常图、求解器、FT 摘要及 Codegen 所有权事实。语义阶段提供统一边界
结果，Codegen 消费结果，不在不同语法分支中分别实现推导。共享泛型体的证明
必须适用于所有允许实参；跨包、间接调用及未知 callable 保持保守。

## 3. 已确认的前置缺口

前一候选验证发现：对象字面量的构造实参未完整进入异常图，构造调用未携带实参
的 callable 信息。最小复现形态为：

```feng
type Built { let n: int; func Built(n: int) { self.n = n; } }
func fail(): int { throw "failed"; }
func probe(): int { return (Built(fail()) {}).n; }
```

基线 `3dbdb9c2` 的摘要为 `none`；实验补齐实参求值后为 `string`。将已知安全、
抛异常或未知 callable 作为构造实参时，也需要保留其调用依赖，不能只补顶层 throw。
该修复曾在候选中验证，但按本轮缩减范围撤回，尚未交付。

在依据异常信息删除登记前，必须补齐这一缺口及其独立 Semantic／Codegen／
源码隐藏跨包覆盖。分析不完整不能当成无异常证明。复现证据保留在本地
`temp/value-conditional-cleanup-20261016/evidence/constructor-summary-*.txt`，
候选 diff 和用例另存于 `temp/value-cleanup-registration-20261016/backup/`。

## 4. 候选方案及取舍

### 4.1 依据保护区间省略不必要的登记

建议首先验证这一方向。保留通用的编译期拥有权信息，只省略无需异常保护的
节点登记和相应撤销；正常释放及显式提前退出继续使用同一拥有者信息。

接入应覆盖普通拥有局部、参数副本、构造临时值及表达式临时值，避免只有某类
语法使用一套长期独立规则。允许保守地保留无法证明的区间，但必须共用判定接口
和安全条件。接口形态、边界记录位置和首轮覆盖范围在实施前 Review。

此方向可消除已证明安全路径的节点，不会自动消除确实可能异常退出路径的成本。
必须检查生成代码中的节点、marker 和隐藏临时拥有者，不能只减少一个 push。

### 4.2 复用已有登记，减少构造与消费者之间的重复保护

检查构造临时值与最终局部、返回值或实参是否对应同一份连续拥有权。如果存储、
清理责任和生命周期都兼容，考虑直接在最终存储构造，或让原登记随拥有权移交，
避免“撤销构造节点，再登记完成值”。

这是可能同时改善受保护成功路径的方向，但尚未证明可行性和收益。必要约束：

- 不能提前暴露尚未初始化的源语言绑定，不能改变字段求值或终结器时序。
- 不因复用扩大／缩短拥有权存活范围，不额外复制值或增减 ARC。
- 节点记录的地址必须始终指向正确存储，存储和节点寿命均覆盖展开区间。
- 不越过仍活跃的生产者临时节点破坏 LIFO；正常、异常、提前返回均只能清理一次。
- 固定布局、具化存储、嵌套构造和多参数求值使用同一规则，不为某个类型单独实现。

现有 `cleanup_pop_only` 仅表示退出时不重复释放，不等同于已经实现登记复用。
优先确认现有所有权表示能否支持；需要新增 runtime API 或改变生命周期约定时，
先提交独立设计，不直接扩大实施。

### 4.3 缩短登记区间

对于资源存活区间中的一段已证明不会异常退出的代码，可研究将登记延迟至首个
确需保护的位置，或在最后一个风险位置后提前撤销。此方向只移动保护，不移动
资源创建、字段求值或释放。

循环、多分支和多次调用可能使一次登记变成多次登记，因此不默认采用。必须比较
路径频率、静态指令和实测结果；不增加运行时“是否可能抛异常”的检查。

### 4.4 由静态异常清理块承担部分职责

研究能否让编译器直接生成异常路径清理块，使用现有释放操作处理该点实际活跃的
资源，减少正常路径的线程清理链维护。这属于后续架构候选，尚未验证，不是本轮
修复的一部分。

需先确认 C 发码与[现有 LLVM EH 协议](c-ir-llvm-exception-plugin-dev.md)能否表达局部资源可见性、部分初始化状态、
分支合流、嵌套捕获、defer 及重新抛出。不能假定添加 C cleanup 属性即可与现有
personality 和协议正确组合。需要改动插件协议或 runtime 时，单独人工 Review。

“静态清理”不意味着整体绝对零成本：仍要比较寄存器保存、栈空间、代码及异常表
体积，并验证 O0、优化构建、ThinLTO 和调试行为。

### 4.5 降低仍然必要的节点维护成本

从最终 IR／汇编确认重复清零、冗余线程链读写或不能内联的原因，再评估是否能用
现有统一实现改善。ThinLTO 已开启仍不代表这些操作一定消失。

不为单个类型增加专用登记函数，不为性能静默删除校验，也不以新增锁、堆分配或
全局编译选项取舍换取局部收益。节点布局和 runtime ABI 变更只有在证据表明必需、
且人工批准后才进入设计。

## 5. 历史实验的适用范围

2026-10-16 的字段专用条件登记候选基于 `3dbdb9c2`，在 Linux ARM64 使用 Release／
ThinLTO，对同一输入交错采样 15 轮，另有两轮预热：

| 构造密集诊断（3200 万次） | 修改前 | 字段条件登记候选 | 结果 |
| --- | ---: | ---: | --- |
| 已证明无异常 | 310.921 ms | 309.845 ms | 最终二进制逐字节相同 |
| 可能抛异常，实际成功 | 308.029 ms | 326.347 ms | 增加约 5.95%，每次约 0.57 ns |

该候选的五项标准评测生成 C 和二进制均与基线相同，不能据此宣称所有实际应用
无额外成本。最终汇编确认受保护路径仍有节点初始化和线程清理链维护；把两条
路径内联在同一函数时，栈帧及布局也发生变化。

这些结果仅证明“省略无必要登记有独立价值，而必要登记仍有成本”。候选已撤回，
不是当前纯登记修复的性能结论，也不是本文通用方案已实现的证据。

当前直接登记修复的完整回归和重新测量结果，以[修复文档 §3～§4](feng-value-literal-conditional-cleanup-bugfix.md#3-用例与验证计划)
为准；后续正式优化应在该正确版本提交后重新固定基线。

## 7. 验证与验收

| 维度 | 验证要求 |
| --- | --- |
| 证明边界 | 无异常、直接抛出、实参／接收者抛出、未知调用、内部捕获、外围捕获、重抛／抛新异常 |
| 生命周期 | 初始化前后、后续语句抛出、条件拥有者、嵌套构造、多实参、移动／借用、返回值存活 |
| 控制流 | 正常结束、提前返回、循环退出、短路、分支合流、循环后续迭代抛出 |
| 资源 | 普通对象、数组、字符串、值对象、tuple、union、callable、泛型固定／具化存储 |
| 清理职责 | 终结器顺序、defer LIFO、catch 载荷及重入、不会遗漏或重复释放、默认值资源 |
| 包与构建 | 同包、源码隐藏跨包、Debug／Release、LTO off／thin、现有 sanitizer 配置 |
| 工具 | Codegen 的 C 与 LLVM IR／汇编、FCTS 可观察行为、DAP 变量／停靠、Linux 与 macOS 实际回归 |

沿用现有测试机制。先补独立用例；既有断言需要迁移时先获得人工批准，不放宽
清理次数、顺序或异常行为要求。每个正式代码阶段执行 `make test`；缺失的目标
执行条件单独记录，不以交叉编译替代实际执行。

性能测量同时包含无异常、潜在异常但实际成功、实际抛出、嵌套清理及未知跨包
调用，另跑五项标准评测。固定工具链和参数、动态输入、交错采样并校验输出，
分别记录节点／marker 数量、TLS 访问、栈空间、运行时间、RSS 及制品体积。

目标是在正确行为下性能持平或提升；一组收益不能抵消另一组稳定退化。检查或
复用登记不等于已经达到零新增成本，结论必须以最终生成代码和测量为依据。
涉及新增运行时成本、ABI／插件协议变更或不能保持原行为时，先交人工决定。
