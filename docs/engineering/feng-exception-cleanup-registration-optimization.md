# Feng 异常清理登记通用优化方案

> **状态：方案草案，待人工 Review；未实施。日期：2026-10-16。**
>
> 与[值对象构造期清理登记修复](feng-value-literal-conditional-cleanup-bugfix.md)分两步交付。
> 先用既有机制修复清理遗漏，再选择和验证本文的优化，不承诺未经验证的收益。

## 1. 目标与现有边界

目标是通用地减少异常清理登记的正常路径成本，同时保持正常退出、异常展开、
终结器／defer 顺序、所有权转移和调试行为。不能针对具体类型名称、库或评测用例
选择不同实现。语言规则引用[生命周期](../specifications/feng-lifetime.md)、
[异常](../specifications/feng-exception.md)和[defer](../specifications/feng-defer.md)主规范。

当前普通语句和表达式已经使用同一异常分析器与求解器，包含调用、参数、分支、
循环和捕获处理。拥有资源的局部值仍主要按所有权规则登记，未根据其后续整个
存活区间的异常风险统一省略节点。

`feng_cleanup_push`／`feng_cleanup_push_aggregate` 初始化栈上节点并修改线程
清理链；正常退出 `pop`，异常由现有清理入口消费。节点不需要堆分配，但仍有
栈写入、线程局部存储访问以及可能的函数调用、寄存器和栈布局影响。

已有[空清理边界优化](feng-cleanup-boundary-performance-dev.md)处理没有资源责任
的函数／try marker。本文处理有资源时的登记，不重做该优化；资源节点减少后，
边界是否还能省略应继续使用其既有统一规则。

### 1.1 原生 unwind 与动态清理登记的区别

当前实现是“原生栈展开＋动态资源清理链”，两者承担不同职责：

| 职责 | 当前实现 | 正常路径成本 |
| --- | --- | --- |
| 异常发生后找到处理入口 | 原生异常表、personality、landingpad | 正常执行不进行异常展开或查表 |
| 记录异常时需要清理哪些资源 | 栈上 `FengCleanupNode` 和线程清理链 | 初始化节点、修改 TLS 链、正常退出撤销登记 |
| 释放资源 | ARC、aggregate 清理、defer | 正常退出本来就需要的释放，不等于异常登记成本 |

代码依据是 [runtime 清理链](../../src/runtime/feng_exception.c)中的
`feng_cleanup_push`、`feng_cleanup_push_aggregate`、`feng_cleanup_pop`，以及
[Codegen](../../src/codegen/codegen.c) 的 `cg_emit_function_eh_prologue`：异常入口
调用 `feng_frame_release_to` 消费动态链。采用 unwind 不会自动消除这些显式操作。
`__llvm_c_eh_*` 是由插件消除的编译协议标记，不应与实际运行的清理登记混为一谈。

### 1.2 C++ 静态清理的可借鉴部分

Linux／macOS 的 C++ 表驱动异常模型通常在编译期确定各调用位置的清理责任，
生成静态异常表和清理代码。例如第一个字段已完成、第二个字段初始化失败时，
对应异常入口只析构第一个字段；第一个字段尚未完成时，不执行该字段的析构。
具体调用位置由异常表关联到清理入口，不需要为这个责任逐次维护运行时链表。

LLVM IR 中的 `invoke` 表达正常与异常两个后继；正常机器码仍是普通调用，
异常发生后才由展开器查表转入清理代码。即使调用确实可能抛异常，正常返回时
也不必为该资源执行动态登记。这与 §4.1 的“证明不会异常退出后省略登记”不同。
机制依据见 [LLVM 异常处理说明](https://llvm.org/docs/ExceptionHandling.html#itanium-abi-zero-cost-exception-handling)
及 [`invoke` 定义](https://llvm.org/docs/LangRef.html#invoke-instruction)。

这里的“零开销”指避免正常路径的异常状态检查和动态登记，不保证启用异常前后
机器码完全相同。异常路径所需的值可能增加寄存器保存、栈空间和优化约束；清理
代码与异常表也占体积。§5.2 的本地编译对照确认了这一边界，尚未验证 Feng 收益。

## 2. 统一的证明对象

分析对象是“一份拥有权需要保护的区间”，而非“某条语句本身是否抛异常”：

| 拥有者 | 需要分析的区间 |
| --- | --- |
| 普通局部变量／拥有参数副本 | 取得拥有权后，直到释放或转移；包含后续语句、分支和循环 |
| 构造中的值／tuple | 已取得资源后，直到完成并交给消费者；默认字段和构造结果也计入 |
| 表达式、接收者和实参临时值 | 取得资源后，直到消费完成；包括后续实参求值及调用 |
| 条件产生的拥有者 | 覆盖实际初始化分支及合流后的存活路径，不能读取未初始化存储 |

例如 `let a = makeResource(); mayThrow();` 中，即使第一句不抛异常，仍不能取消
`a` 在第二句执行期间的保护。外围 catch 使函数的外抛集合为空，也不能证明其内层
作用域没有异常退出。内部 catch 处理后继续使用资源，与异常越过资源清理边界，
必须区分。

证明还应覆盖编译器插入的初始化、转换和调用，不能只检查源码中显式写出的调用。
已经由语言规范禁止向外传播异常的操作，沿用其既有规则。

对于 §4.1 的直接省略方案，只有证明区间内不存在需要本层异常清理的退出，才可
删除登记而不提供替代保护；未知、缺失或未完成的事实保留登记。§4.4／§4.6 若
由静态清理代码承担相同责任，属于替换保护方式，不能套用为“无异常证明”。
正常 `return`／`break`／`continue` 和作用域结束的释放不能一起删除。defer 执行
责任、catch 异常记录和已清空但尚未退链的节点也不能由“没有托管字段”或
“函数不外抛”推断为无责任。

复用现有异常图、求解器、FT 摘要及 Codegen 所有权事实。语义阶段提供统一边界
结果，Codegen 消费结果，不在不同语法分支中分别实现推导。共享泛型体的证明
必须适用于所有允许实参；跨包、间接调用及未知 callable 保持保守。

## 3. 已确认的前置缺口

前一候选验证发现：对象字面量的构造实参未完整进入异常图，构造调用未携带实参
的 callable 信息。最小复现形态为：

```feng
type Built { let n: int; func Built(n: int) { self.n = n; } }
func fail(): int { throw "failed"; }
func probe(): int { return (Built(fail()) {}).n; }
```

基线 `3dbdb9c2` 的摘要为 `none`；实验补齐实参求值后为 `string`。将已知安全、
抛异常或未知 callable 作为构造实参时，也需要保留其调用依赖，不能只补顶层 throw。
该修复曾在候选中验证，但按本轮缩减范围撤回，尚未交付。

在依据异常信息删除登记前，必须补齐这一缺口及其独立 Semantic／Codegen／
源码隐藏跨包覆盖。分析不完整不能当成无异常证明。复现证据保留在本地
`temp/value-conditional-cleanup-20261016/evidence/constructor-summary-*.txt`，
候选 diff 和用例另存于 `temp/value-cleanup-registration-20261016/backup/`。

## 4. 候选方案及取舍

### 4.1 依据保护区间省略不必要的登记

这是保留当前异常后端的增量方向。保留通用的编译期拥有权信息，只省略无需异常
保护的节点登记和相应撤销；正常释放及显式提前退出继续使用同一拥有者信息。
与 §4.4 静态清理方案的实施优先级由人工 Review 确认。

接入应覆盖普通拥有局部、参数副本、构造临时值及表达式临时值，避免只有某类
语法使用一套长期独立规则。允许保守地保留无法证明的区间，但必须共用判定接口
和安全条件。接口形态、边界记录位置和首轮覆盖范围在实施前 Review。

此方向可消除已证明安全路径的节点，不会自动消除确实可能异常退出路径的成本。
必须检查生成代码中的节点、marker 和隐藏临时拥有者，不能只减少一个 push。

### 4.2 复用已有登记，减少构造与消费者之间的重复保护

检查构造临时值与最终局部、返回值或实参是否对应同一份连续拥有权。如果存储、
清理责任和生命周期都兼容，考虑直接在最终存储构造，或让原登记随拥有权移交，
避免“撤销构造节点，再登记完成值”。

这是可能同时改善受保护成功路径的方向，但尚未证明可行性和收益。必要约束：

- 不能提前暴露尚未初始化的源语言绑定，不能改变字段求值或终结器时序。
- 不因复用扩大／缩短拥有权存活范围，不额外复制值或增减 ARC。
- 节点记录的地址必须始终指向正确存储，存储和节点寿命均覆盖展开区间。
- 不越过仍活跃的生产者临时节点破坏 LIFO；正常、异常、提前返回均只能清理一次。
- 固定布局、具化存储、嵌套构造和多参数求值使用同一规则，不为某个类型单独实现。

现有 `cleanup_pop_only` 仅表示退出时不重复释放，不等同于已经实现登记复用。
优先确认现有所有权表示能否支持；需要新增 runtime API 或改变生命周期约定时，
先提交独立设计，不直接扩大实施。

### 4.3 缩短登记区间

对于资源存活区间中的一段已证明不会异常退出的代码，可研究将登记延迟至首个
确需保护的位置，或在最后一个风险位置后提前撤销。此方向只移动保护，不移动
资源创建、字段求值或释放。

循环、多分支和多次调用可能使一次登记变成多次登记，因此不默认采用。必须比较
路径频率、静态指令和实测结果；不增加运行时“是否可能抛异常”的检查。

### 4.4 由静态异常清理块承担部分职责

保留原生 unwind，由编译器直接生成异常路径清理块，使用现有释放操作处理该点
实际活跃的资源，以替代对应的动态登记。这是架构候选，尚未在 Feng 中原型验证，
不属于已经交付的值对象清理修复。

现有 [LLVM EH lowering](../../third_party/llvm-c-eh/src/Lowering.cpp) 已将保护区内
调用转为 `invoke`，建立 `landingpad`，并通过父区域或 `resume` 传播异常；清理
入口的内容由生成 C 提供。因而已有表达静态清理的基础，不需要先改为 C++ 发码，
也不能据此断言完整迁移无需调整协议。

拟验证的通用发码方式：

1. 复用 Codegen 拥有权信息，为每个异常退出位置确定已经取得、尚未转移的资源。
2. 生成按既有顺序释放这些资源的清理块，复用现有释放操作，不新增类型专用释放函数。
3. 用现有 EH 协议关联调用位置与清理块；证明保护等价后删除对应 push／pop。
4. 核查最终机器码确实没有新增的登记或状态检查，再比较性能。

需先确认 C 发码与[现有 LLVM EH 协议](c-ir-llvm-exception-plugin-dev.md)能否表达局部资源可见性、部分初始化状态、
分支合流、循环、所有权转移、嵌套捕获、defer 及重新抛出。未知调用仍需异常边，
不能因不使用清理链而忽略它。特别要保留[异常规范 §4.1](../specifications/feng-exception.md#41-异常路径上的资源清理)
要求的未捕获异常／ABI 边界终止前清理；当前 `feng_throw`／`feng_rethrow` 对未捕获
路径调用 `feng_cleanup_release_all`，不能仅删除登记后认为该行为自然成立。

不能假定添加 C cleanup 属性即可与现有 personality 和协议正确组合。需要改动
插件协议或 runtime 时，单独人工 Review。结合 §5.2，建议优先评估静态清理原型，
用于确认确有异常可能的成功路径也能免于登记；这仍是建议，不表示已批准后端改造。

“静态清理”不意味着整体绝对零成本：仍要比较寄存器保存、栈空间、代码及异常表
体积，并验证 O0、优化构建、ThinLTO 和调试行为。

### 4.5 降低仍然必要的节点维护成本

从最终 IR／汇编确认重复清零、冗余线程链读写或不能内联的原因，再评估是否能用
现有统一实现改善。ThinLTO 已开启仍不代表这些操作一定消失。

不为单个类型增加专用登记函数，不为性能静默删除校验，也不以新增锁、堆分配或
全局编译选项取舍换取局部收益。节点布局和 runtime ABI 变更只有在证据表明必需、
且人工批准后才进入设计。

### 4.6 TLS 异常状态＋逐层提前返回

这是开发者提出的另一候选：不使用 unwind 传播 Feng 异常，而由 `throw` 保存
TLS 异常状态，各层执行本地清理后返回，调用方检查状态并捕获或继续传播。
仅记录方案与待决事项，尚未实现、实测或批准替换当前后端。

TLS 状态是异常的传递渠道，不负责控制转移。`throw` 必须由 Codegen 转入当前
Feng 函数的错误出口；仅让一个设置 TLS 的 runtime helper 返回，会继续执行
原函数后续代码，不等价于 throw。每个可能传播异常或未知的调用返回后，也必须
在继续求值或消费结果前检查状态。已证明不传播异常的调用可省略检查，但不能
跳过其接收者／实参求值中的风险；§3 的摘要缺口同样必须先补齐。

开发者明确的候选语法是：每个可能产生异常的调用都必须显式加 `try`；`catch`
可以省略，省略时自动上抛。外围调用的 try 不能代替实参中可能异常调用自身的
try。若 `outer`、`left`、`right` 都可能异常，示意写法为：

```feng
// 候选语法，尚未实现。
try outer(try left(), try right()) catch { ... }
```

生成代码按既有求值顺序在各个显式 try 对应的调用后检查状态；一旦某个实参
失败，就不能继续其他实参或执行 `outer`。不能仅在整个外层表达式末尾读取一次
TLS。省略 catch 省去的是本地捕获代码，不是异常检查和离开作用域时的清理。
层间传播也需要检查，除非中间层已证明可直接转发、无需继续求值或执行本地清理。
显式 try 使检查及传播位置在源码中可见；成功路径仍可能有状态读取和条件分支，
具体数量取决于证明及后端优化，该方案不保证正常路径零开销。

资源清理仍需 §2 的拥有权与初始化状态。若错误出口直接执行静态清理，可取消
相应动态登记；若只是改为 TLS 传播而保留原清理链，登记成本并不会自动消失。
还需设计并验证以下契约：

- 待传播异常与活跃 catch 的持有分离；清理期间调用的 defer／终结器若内部处理
  另一异常，不能覆盖原异常。沿用异常及 defer 主规范，不简化为一个可任意覆盖的槽。
- 定义失败返回时的结果有效性；调用方在确认成功前不能读取、复制、retain 或
  转移结果，覆盖标量、托管值、aggregate 及具化返回存储。
- 精确匹配、原样重抛、清理顺序、未捕获终止和 C ABI 边界行为保持现有规范。
- 即使 C 函数签名不变，跨包传播协议也已变化；旧 unwind 包与新 TLS 包不能
  默认混用，需要明确统一重编边界、callable 调用和 runtime 契约。

上述逐调用显式 try、catch 可省略并自动上抛，是本候选已明确的语法意图。
历史上的 unwind 实现曾支持无 catch 的 `try expr;`；提交 `2ac095fd`
（2026-05-25，`feat(parser): forbid try without catch clause`）增加了 parser 的
零 catch 拒绝检查，并迁移了原先接受该写法的用例。开发者说明，当时取消的原因
是普通调用本就自动传播异常，无 catch 的 try 与直接调用没有行为区别。

因此，本候选的 catch 可省略属于恢复曾有的语法；“可能异常的调用必须逐一写
try”则是使该标记成为调用处必需声明的规则变化。这两点不应混为全新语法，也
不能把显式 try 当成 TLS 独有的要求：原生 unwind 同样可以采用该源码规则。

当前[异常主规范 §1、§3.2、§6](../specifications/feng-exception.md)允许普通调用
自动传播异常，且 try 必须附带 catch，与候选不同。TLS 后端本身也可以通过
编译器自动插入检查来保留现行语法，因此传播后端与源码规则应分别 Review。
本文只记录候选，不修改主规范，也不表示已经批准实施语言规则变更。

| 候选 | 可能异常调用正常返回时 | 异常发生后 |
| --- | --- | --- |
| 当前 unwind＋动态清理链 | 为受保护资源维护登记／撤销 | 原生展开，清理入口消费链 |
| unwind＋静态清理 | 不需逐资源登记或调用后状态检查；仍可能有寄存器／栈成本 | 原生展开，执行对应静态清理块 |
| TLS＋返回＋静态清理 | 需要调用后的异常状态读取／分支，证明安全时可省略 | 本地清理并逐层返回，调用方检查、捕获或继续传播 |

TLS 候选可研究减少异常后端的平台依赖，但不能据此宣称比当前实现或静态 unwind
更快。若获批原型，应让三者采用相同资源语义，对正常成功、不同异常频率及不同
调用深度分别测量；不只与当前动态登记方案比较。

## 5. 验证证据及适用范围

### 5.1 历史字段条件登记实验

2026-10-16 的字段专用条件登记候选基于 `3dbdb9c2`，在 Linux ARM64 使用 Release／
ThinLTO，对同一输入交错采样 15 轮，另有两轮预热：

| 构造密集诊断（3200 万次） | 修改前 | 字段条件登记候选 | 结果 |
| --- | ---: | ---: | --- |
| 已证明无异常 | 310.921 ms | 309.845 ms | 最终二进制逐字节相同 |
| 可能抛异常，实际成功 | 308.029 ms | 326.347 ms | 增加约 5.95%，每次约 0.57 ns |

该候选的五项标准评测生成 C 和二进制均与基线相同，不能据此宣称所有实际应用
无额外成本。最终汇编确认受保护路径仍有节点初始化和线程清理链维护；把两条
路径内联在同一函数时，栈帧及布局也发生变化。

这些结果仅证明“省略无必要登记有独立价值，而必要登记仍有成本”。候选已撤回，
不是当前纯登记修复的性能结论，也不是本文通用方案已实现的证据。

当前直接登记修复的完整回归和重新测量结果，以[修复文档 §3～§4](feng-value-literal-conditional-cleanup-bugfix.md#3-用例与验证计划)
为准；后续正式优化应在该正确版本提交后重新固定基线。

### 5.2 C++ 部分构造的静态清理对照

2026-10-16 使用仓库 Clang 23.1.3，对以下独立 C++ 示例生成 IR 和汇编：

```cpp
// 不透明调用保留字段求值与资源操作；释放保证不向外抛出。
extern "C" void *acquire();
extern "C" int may_throw();
extern "C" void consume(void *);
extern "C" void release(void *) noexcept;

// 已构造的资源必须在后续字段失败时释放。
struct Resource {
    void *value;
    Resource() : value(acquire()) {}
    ~Resource() noexcept { release(value); }
};
// 第二个字段的初始化可能失败。
struct Value { Resource first; int second; };

// 不显式书写 try/catch 或登记操作。
extern "C" void build_value() {
    Value value{Resource{}, may_throw()};
    consume(&value);
}
```

公共参数为 `-x c++ -std=c++17 -O2`，目标分别为
`--target=aarch64-unknown-linux-gnu` 与 `--target=arm64-apple-macos26.0`。
启用异常使用 `-fexceptions -S -emit-llvm`／`-fexceptions -S`；汇编结构对照为
`-fno-exceptions -S`。该例不使用 SDK 头文件，无需链接或执行二进制。

| 两个目标均观察到的项目 | 启用异常 | 关闭异常，仅作结构对照 |
| --- | --- | --- |
| 动态清理节点／TLS 登记 | 无 | 无 |
| 正常路径调用 | acquire、may_throw、consume、release | 相同四项调用 |
| 异常清理 | landingpad 中 release，然后 resume | 无异常清理 |
| 栈帧大小 | 48 字节 | 32 字节 |
| 为异常路径保留资源所需的额外寄存器保存 | 有 | 无 |

IR 确认 `may_throw` 失败时释放已取得的第一字段，`consume` 失败时释放完整对象
中的资源；对应调用在汇编中仍为普通 `bl`，异常表将调用范围关联到清理入口。
两种编译模式在异常发生时不具备相同语义，关闭异常不能作为生产替代方案。

本地原始产物位于 `temp/cpp-unwind-analysis-20261016/`，可能随 temp 清理；上文
保留复现源码、参数和观察结果。这里只做了两目标交叉编译对照，没有执行计时，
不代表 Feng 静态清理方案已实现、已回归或已证明性能提升。

## 7. 验证与验收

| 维度 | 验证要求 |
| --- | --- |
| 证明边界 | 无异常、直接抛出、实参／接收者抛出、未知调用、内部捕获、外围捕获、重抛／抛新异常 |
| 生命周期 | 初始化前后、后续语句抛出、条件拥有者、嵌套构造、多实参、移动／借用、返回值存活 |
| 控制流 | 正常结束、提前返回、循环退出、短路、分支合流、循环后续迭代抛出 |
| 资源 | 普通对象、数组、字符串、值对象、tuple、union、callable、泛型固定／具化存储 |
| 清理职责 | 终结器顺序、defer LIFO、catch 载荷及重入、不会遗漏或重复释放、默认值资源 |
| 包与构建 | 同包、源码隐藏跨包、Debug／Release、LTO off／thin、现有 sanitizer 配置 |
| 工具 | Codegen 的 C 与 LLVM IR／汇编、FCTS 可观察行为、DAP 变量／停靠、Linux 与 macOS 实际回归 |

沿用现有测试机制。先补独立用例；既有断言需要迁移时先获得人工批准，不放宽
清理次数、顺序或异常行为要求。每个正式代码阶段执行 `make test`；缺失的目标
执行条件单独记录，不以交叉编译替代实际执行。

性能测量同时包含无异常、潜在异常但实际成功、实际抛出、嵌套清理及未知跨包
调用，另跑五项标准评测。固定工具链和参数、动态输入、交错采样并校验输出，
分别记录节点／marker 数量、TLS 访问、栈空间、运行时间、RSS 及制品体积。
静态清理需确认相应动态登记确实消失；TLS 原型若获批，还应记录调用后检查数量、
传播深度、嵌套表达式求值是否及时停止，并与相同清理语义的静态 unwind 对照。

目标是在正确行为下性能持平或提升；一组收益不能抵消另一组稳定退化。检查或
复用登记不等于已经达到零新增成本，结论必须以最终生成代码和测量为依据。
涉及新增运行时成本、ABI／插件协议变更或不能保持原行为时，先交人工决定。
