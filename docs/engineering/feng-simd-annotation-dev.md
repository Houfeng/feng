# Feng `@simd` 向量类型开发方案

> **状态：待人工 Review，尚未实施。日期：2026-10-20。**
>
> 本文整理库定义类型、编译器通过 `@simd` 识别向量表示的方案，覆盖 CPU 与
> GPU 使用边界。仅新增开发文档，不修改编译器、runtime、std、工具链或测试。
> 已确认采用类型上的 `@simd`，以及 `extern` 函数上的 `@simd(操作标识)`。
> `@simd` 类型是值类型，内部隐含 `@value` 并复用既有值类型实现。
> 类型布局、具体操作签名及支持范围尚待确认，不视为已批准实现。

## 1. 目标与已确认方向

允许开发者在库中定义向量值类型，通过公开的内建注解声明其编译期含义，
继续由 Feng 生成目标源码，再交给目标编译器优化。

1. 类型可以在 std 或其他包中定义；编译器不感知 std 的包名、类型名或成员名。
2. `@simd` 的“注册”仅指编译期识别声明身份及表示信息，不生成运行时注册表、
   类型名称查询或动态操作分派。
3. `@simd` 类型是值类型，由多个标量分量组成；无需显式重复标注 `@value`。
   编译器内部隐含 `@value`，复用既有值语义实现，不另建 SIMD 专用值语义机制，
   也不将每个分量包装为托管对象。
4. 向量类型可用于 CPU 函数，也可在设备后端支持时用于 GPU 函数。
   `@simd` 不决定执行位置，不隐式把函数变成 `@device` 或 `@kernel`。
5. 不承诺一次向量运算对应一条机器指令；指令选择取决于目标能力和优化结果。
6. 不改变普通 Feng 类型、所有权、数值及异常语义，不针对评测用例选择实现。
7. 复用现有表达式、函数调用及注解语法。无函数体的操作接口沿用 `extern`
   声明，通过 `@simd(shuffle)` 等标明内建操作身份；具体规则见 §4.1。

本功能与 [`@throwable` 开发方案](feng-throwable-annotation-dev.md)共享
“库声明、编译器按公开注解识别”的原则，但不依赖该功能先实施。
GPU 执行域、设备构建与启动由
[GPU 开发方案](feng-gpu-kernel-device-dev.md)负责，本文不重复定义。

## 3. 类型声明与编译期检查

### 3.1 注解表达的信息

编译器至少需要知道：声明身份、分量标量类型、分量数量，以及合法的表示规则。
类型使用裸注解 `@simd`；分量类型、数量及字段表示的具体声明方式仍需确认，
不同时维护两份可互相冲突的类型定义，也不根据 `Float4`、`x/y/z/w` 等名称猜测。
带操作标识的形式用于 `extern` 函数，不用于声明类型布局。

类型上的 `@simd` 隐含 `@value`。实现时沿用现有 `@value` 的早期标记路径，
使类型声明具有 `is_value = true`，后续赋值、传参、返回、捕获及生命周期处理
复用现有值类型机制，不重复实现。这不要求在 AST 中额外合成一条 `@value` 注解。
若同时显式标注 `@value`，值语义相同且只处理一次。

SIMD 的合法性检查和目标表示仍需单独记录；不能仅凭 `is_value` 将普通值类型
当作向量。函数上的 `@simd(操作标识)` 不触发类型的值语义标记。

类型部分仍需 Review 的事项：

- 字段如何表达或投影到分量；是否允许附加存储字段、构造函数和自定义默认值。
- 首批允许的标量类型及分量数量，是否包含 `bool`、平台位宽整数及三分量类型。
- 是否允许泛型声明，何时确定具体标量和数量；不假定现有泛型已有整数常量参数。
- 重复注解、参数错误、错误声明位置以及与其他内建注解组合的规则。

建议从无托管分量、固定数量的具体值类型开始验证。具体准入集合需人工确认，
不能先允许任意类型，再把错误交给 Clang。

### 3.2 统一检查链路

源码、同包跨文件及 FT 导入均检查相同的声明事实：

1. 分量类型和数量合法，大小计算不溢出，目标后端有明确实现。
2. 表示中不存在未经批准的托管字段或生命周期行为。
3. 注解表示与声明字段、默认初始化和取址行为一致。
4. 别名、泛型具化、嵌套值、数组、union、callable 和 spec 值边界不能丢失表示信息。
5. 不同包定义的同形状类型按既有名义身份处理，不因分量相同自动合并为同一类型。
6. GPU 使用还需通过设备执行域、地址空间和设备 ABI 检查；CPU 支持不代表 GPU 支持。

无法确定的开放泛型事实不能被当成“已支持向量”发码。需要决定是保留到具化点
校验，还是限制首期入口，并为该边界提供明确诊断。

## 4. 向量操作与数值契约

### 4.1 已确认的操作声明方式

`@simd` 告诉编译器值如何表示，但普通库函数的名称不能自动成为内建操作。
例如库中的 `add`、`shuffle`、`load` 不能仅因名称相同就获得特殊发码。

复用同一个内建注解，按声明位置和参数形式区分：

| 形式 | 声明位置 | 含义 |
| --- | --- | --- |
| `@simd` | 类型声明 | 标记向量值类型，表示规则见 §3 |
| `@simd(shuffle)` | 无函数体的 `extern` 函数 | 声明向量重排操作 |
| `@simd(load)` | 无函数体的 `extern` 函数 | 声明向量加载操作 |
| `@simd(store)` | 无函数体的 `extern` 函数 | 声明向量存储操作 |

`shuffle`、`load`、`store` 是注解定义的编译期操作标识，不是普通变量、
函数引用或运行时字符串，不参与普通表达式名称查找。不能执行注解参数，也不能
根据运行时值选择操作。表中确认的是声明形式和操作含义，不代表具体函数签名
或全部操作集合已经确定。

沿用 Feng 仅 `extern` 函数可省略函数体的规则，不新增另一种无函数体声明：

- 普通 `extern` 保持现有外部符号调用行为。
- 带合法操作注解的 `extern` 由编译器验证签名和实参，直接生成目标操作；
  不要求外部库提供该声明对应的函数符号，不退回普通外部符号调用。
- 库自行选择函数名和所在包；任何包均使用相同机制，std 不享有特权。
- 未知操作、错误声明位置、非法参数形式或签名不匹配，在 Feng 编译期诊断，
  不延迟为 Clang 错误或链接错误。

基础算术可扩展现有运算符的向量语义；特殊操作使用上述普通函数调用入口，
无需新增表达式语法。具体运算符集合仍待确认。加载、存储及 shuffle 本身
不要求新增 runtime API 或独立 C 函数，可生成合法内存访问或 Clang builtin；
相应边界、对齐及别名条件仍须满足 §4.2、§6 的契约。

操作签名、泛型约束、是否要求某些实参为编译期常量须逐项定义。例如 shuffle
索引是否必须为常量应由其契约决定，不能无条件接受动态索引再交由后端拒绝。
这类声明能否作为 callable 使用，以及与现有 extern 符号绑定配置的组合规则，
也须在实施前确认；不能假设它天然具有可取地址的外部函数实现。

普通循环实现可作为正确性参照，不能把“后端可能自动向量化”当成显式 SIMD
功能已经交付的证明。

### 4.2 必须明确的操作契约

| 类别 | 需要确定的规则 |
| --- | --- |
| 构造、广播、提取、替换 | 默认零值、分量顺序、索引范围、参数求值次数及顺序 |
| 加减乘除、位运算、移位 | 逐分量语义，整数溢出、除零、移位范围及错误行为 |
| 比较与选择 | 掩码表示；逐分量比较与整个值相等不能混淆 |
| 数值转换、位表示转换 | 二者分离；截断、舍入、范围、大小及合法目标类型 |
| 分量重排与归约 | 重排索引规则；归约顺序及浮点精度契约 |
| 内存加载、存储 | 长度、对齐、越界、别名、有效生命周期和 GPU 地址空间 |
| 融合及近似计算 | 若提供，须显式表达；不得静默放宽普通运算语义 |

不能直接照搬 C 向量运算符而忽略 Feng 语义。尤其是掩码的位表示、向量比较返回值、
整数提升以及未定义行为，均需由发码保证符合批准后的契约。

普通向量乘法后加法不自动获得融合许可；归约也不自动允许浮点重排。
不因引入 SIMD 全局改变 FMA、fast-math 或标量数值规则。

## 5. CPU 与 GPU 发码

### 5.1 CPU 路径

候选实现是将已确认的向量类型映射为 Clang `ext_vector_type` 等向量表示，
继续生成 C。Clang 可将其表达为 LLVM 向量，再按目标生成 SIMD 指令或拆分操作。
具体映射必须经过实验证明，不能把库里的任意普通结构体直接视为 C 向量。

仅扩展向量类型和相关操作的发码路径，不要求改为直接生成 LLVM IR，不新增 LLVM
插件，不把本功能放入异常插件。不全局添加 `-march=native` 等改变发行目标的选项。

目标不支持所需宽度时，采用语义等价拆分还是编译期拒绝属于 Review 项。
若允许拆分，必须明确性能不保证；不能依赖后端告警来替代能力检查。
首期不引入运行时 CPU 特性探测或多版本函数分派。

### 5.2 GPU 路径

相同向量表达可在设备后端支持时复用，但具体源码映射按后端验证：
OpenCL C、CUDA/HIP C++、Metal 的类型、操作和 ABI 不能假定完全一致。

向量值属于单个设备线程。GPU 的 warp/subgroup 是多个线程的执行集合，
不是 `@simd` 类型中的分量。跨线程交换、集体归约和屏障由设备操作机制负责，
不得把向量内重排静默转换成跨线程通信。

单线程向量可能被拆为多个标量寄存器操作；也可能匹配打包指令。需要衡量寄存器
用量、占用率和访存，不能承诺 GPU 使用向量类型必然比标量线程代码更快。
CPU 阶段可独立交付，GPU 验证依赖 GPU 开发方案的实际后端及硬件。

## 6. 布局、内存与 ABI

向量的逻辑分量数量不必等于物理存储大小除以标量大小。例如某些三分量向量
会使用四分量大小和对齐。因此以下内容必须以所选表示验证，不能直接假设紧密排列：

- 大小、对齐、数组步长、嵌套字段偏移、union payload 和临时存储。
- 栈、堆、数组、泛型擦除存储、spec 装箱、callable 参数及返回值。
- 跨模块函数原型、外部 C ABI、CPU/GPU 数据传输布局。
- `&` 取得的地址所对应的实际表示，以及合法的按标量访问方式。

不改变既有 `&arr` 取得 payload 地址的规则；地址本身不能证明满足 SIMD 对齐。
若当前分配路径无法保证所需对齐，应比较降低存储对齐并采用安全加载、限制首期
支持范围、扩展通用对齐能力等方案，再由人工决定。不擅自增加 runtime API，
不扩大所有对象或数组的对齐，也不增加普通路径的分配成本。

载入和存储不得越过实际有效元素，即使多读的内存“通常可访问”也不合法。
尾部元素处理、未对齐访问和重叠缓冲区需要可验证的规则。

目标 ISA 选项可能影响向量传参 ABI。包生产者与消费者必须使用兼容 ABI；
不能只凭“分量类型和数量相同”认定可直接链接。不默认把内部 C 向量表示
作为任意外部库的公共 ABI，也不假设 host/device 可以直接复制同一布局。

## 7. FT、跨包、泛型与开发工具

沿现有链路传递向量类型事实及 `extern` 操作身份：

```text
注解声明 → 语义校验 → 符号导出 → FT → 导入恢复 → 布局及操作发码
```

隐含的值语义复用已有 `is_value` 导出和恢复路径；SIMD 表示事实另行保存，
不建立第二套值类型标记协议。源码消费与隐藏源码的跨包消费必须具有相同值语义。

优先使用 FT `ATRS` 的扩展能力；具体属性编码及版本策略在主规范中确定。
影响表示或操作发码的必要属性不能被不支持的消费者静默忽略；尤其不能将
带操作注解的 `extern` 恢复为普通外部符号调用。package-public、
workspace-cache 和 LSP 恢复都要验证，且不要求消费端能看到库源码。

复用既有泛型共享体与描述符机制，先验证大小、对齐、复制、参数及返回边界；
不能为 SIMD 擅自改成全局单态化。普通值复制与既有通用描述符不属于新增运行时
注册，但它们的成本和对齐能力仍需验证。具体向量操作不经名称查询动态分派。

调试应显示逻辑分量，保持源变量和类型身份；内部向量表示、优化掉的值及 DAP
可展示能力须实测。语言服务须理解注解及其参数。不得宣称 CPU DAP 已因此支持 GPU。

## 10. 技术依据

- [Clang `ext_vector_type`](https://clang.llvm.org/docs/AttributeReference.html#ext-vector-type)：
  类型可映射为 LLVM 向量；这不等于保证一条硬件指令。
- [Clang 向量扩展](https://clang.llvm.org/docs/LanguageExtensions.html#vectors-and-extended-vectors)：
  向量类型、操作及布尔向量有专门规则，不能照搬普通结构体表示。
- [CUDA SIMT 模型](https://docs.nvidia.com/cuda/archive/12.9.2/cuda-c-programming-guide/index.html#simt-architecture)：
  设备线程并行与单线程持有的向量值属于不同层次。
