# 私有表示类型方案的代码调查

> 状态：调查完成

本文只记录当前实现、临时验证和方案复杂度结论。语言规则与实施 TODO 见
[公开类型的私有表示类型修复](./feng-private-representation-type-bugfix.md)。

## 1. 结论

基于当前代码，Go 方案更简单，但差距不大。

两种方案都必须贯通私有依赖的 `.ft` 收录、声明身份恢复、内部注册和 codegen。
C# 方案不能省略该底座，因为公开类型的私有成员仍可使用私有类型。

在共同底座之外：

- C# 方案需要新增覆盖全部公开 API 组成类型的递归可见性检查、诊断和测试。
- Go 方案需要扩大私有类型依赖闭包，并让不可命名类型按声明身份参与推导和 codegen。

当前实现已经分离公开查询与全部声明查询，也已支持部分按声明身份推导的路径。
因此 Go 方案所需增量少于 C# 方案。

## 2. 当前实现

| 环节 | 当前行为 | 影响 |
|---|---|---|
| 符号图构建 | 先收集源码中的全部顶层声明 | 私有声明在导出前已经存在，无需重新解析源码 |
| 公开 `.ft` 筛选 | 公开顶层声明、字段及非私有方法会被写出；私有顶层类型不会被写出 | 私有字段的类型引用可能存在，但对应私有类型声明缺失 |
| 具名类型写入 | `NAMED` 和 `NAMED_GENERIC` 只写名称及泛型实参 | 已定义的 `sym_ref` 没有写入 |
| 具名类型读取 | reader 读取 `sym_ref`，但构造具名类型时未使用 | 导入后只能按名称重新查找声明 |
| 内存类型视图 | `FengSymbolTypeView` 只有名称、结构和泛型实参 | 无法保存目标声明身份 |
| 外部模块缓存 | 只把公开顶层声明合成为语义模块 | 即使 `.ft` 含私有声明，当前也不会注册为内部依赖 |
| 名称查询 | provider 同时提供公开声明查询和全部声明查询；用户类型解析只使用公开查询 | 已具备“内部可用、用户不可见”的查询基础 |
| 类型事实 | 语义类型事实可保存 `TYPE_REF` 或具体 `DECL` | 按声明身份传递已有基础 |
| codegen | 泛型类型仍按名称和当前程序可见性查找 | 私有泛型依赖会因调用方不可见而产生 `CE0031` |

## 3. 临时验证

验证代码只创建在 `build/` 下，调查完成后已删除，未修改编译器源码。

| 场景 | 当前结果 | 说明 |
|---|---|---|
| 外部调用返回私有类型的公开函数，再把结果传给接受该类型的公开函数 | 编译并运行通过 | 不显式命名类型时，部分传递路径已可用 |
| 外部显式声明 `provider.Hidden` | `AE1013` | 用户名称查询仍正确隐藏私有类型 |
| 外部对公开函数返回的私有类型值调用公开方法 | `AE0306` | 显式返回类型被保留为名称引用，未恢复目标声明 |
| 外部使用推导类型为私有类型的公开顶层绑定 | 语义阶段可解析其公开方法 | `DECL` 类型事实路径已经可用；后续遇到无关的跨模块顶层绑定 codegen 问题 |
| 公开泛型类型的私有字段使用私有泛型类型 | `CE0031` | codegen 仍按名称和调用方可见性查找私有泛型声明 |

验证表明：Go 方案不是新增一套“不可命名类型”机制，而是把现有的声明身份路径贯通到
`.ft`、导入模块和 codegen。

## 4. 两种方案的共同修复

无论选择 C# 还是 Go 方案，都需要：

1. 按所选语言规则收集 codegen 所需的私有依赖。
2. 为 `NAMED`、`NAMED_GENERIC` 及其递归组成类型写入目标声明身份。
3. reader 恢复声明身份，外部模块缓存将已收录私有依赖注册到内部声明表。
4. 用户名称查询继续只返回可见声明。
5. 语义分析和 codegen 按声明身份解析内部依赖，不重新套用调用方源码可见性。

因此，“私有类型进入 `.ft`”包含 writer、reader、内部注册和消费链路，不能只修改导出筛选。

## 5. 方案增量

### 5.1 C# 方案

共同修复之外，还需：

- 递归检查公开顶层绑定、函数、类型、`spec`、`fit`、实例与静态成员的公开签名。
- 检查参数、返回类型、字段类型、泛型约束和所有递归组成类型。
- 同时覆盖显式类型与推导后形成的公开类型。
- 增加可见性不一致诊断及对应测试。

现有 ABI 签名检查可作为遍历结构的参考，但没有实现上述可见性规则。

### 5.2 Go 方案

共同修复之外，还需：

- 将公开 API 可达的私有类型纳入依赖闭包。
- 让外部代码通过推导获得该类型后，可按声明身份完成赋值、传参、成员访问、泛型推导和 codegen。
- 保持显式类型引用、导入、构造和补全不可见。

公开查询隔离、成员可见性检查及 `DECL` 类型事实已经存在，可直接沿用。

## 6. 复杂度判断

| 比较项 | C# 方案 | Go 方案 |
|---|---|---|
| 私有依赖与声明身份底座 | 必须 | 必须 |
| 新增递归可见性规则 | 必须 | 不需要 |
| 新增诊断 | 必须 | 不需要 |
| 不可命名类型流动 | 不需要 | 需贯通现有声明身份路径 |
| 对当前实现的复用程度 | 中 | 较高 |

结论：采用通用声明身份方案时，Go 方案更简单。若只为当前报错增加局部绕行，
代码量可能更少，但无法统一解决 `.ft`、语义分析和 codegen 的声明身份问题，不属于可交付方案。
