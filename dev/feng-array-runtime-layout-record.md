# FengArray 运行时布局选择记录

> 性质：设计决策记录，不是语言规范，不是开发任务，也不包含待实施清单。
>
> 目的：记录 `FengArray` 从多种候选结构收敛为“瘦引用 + 尾随内联 payload”的原因，避免后续重复推导或遗忘已经确认的取舍。
>
> 规范归属：数组语义以 [Feng 内建类型规范](../docs/feng-builtin-type.md) 为准，运行时生命周期以 [Feng 生命周期规范](../docs/feng-lifetime.md) 为准，切片能力以 [Feng 标准库数组扩展规范](../docs/feng-std-array.md) 为准。本文若与主规范不一致，以主规范为准。

## 1. 决策背景

Feng 数组同时追求以下目标：

1. 普通数组创建尽量只执行一次堆分配。
2. 数组赋值、传参和返回保持廉价，不让所有数组值永久承担胖值复制成本。
3. 数组元素连续存储，便于下标访问、批量复制和运行时遍历。
4. 数组是 ARC 管理的引用类型，元素类型信息、终结和循环回收遍历必须有统一的运行时入口。
5. 语言层普通数组创建后长度固定，不需要为普通数组公开动态增长语义。
6. 切片和动态容器需求不应反向扩大每一个普通数组值的固定成本。

这些目标无法由某一种结构同时无代价地满足，因此需要在“分配次数”、“数组值大小”、“访问间接层数”和“动态扩容便利性”之间取舍。

## 2. 曾评估的三种方案

### 2.1 托管对象头 + 独立 payload allocation

概念结构：

```text
array reference
      |
      v
[FengArray header | payload pointer]
                         |
                         v
                    [elements...]
```

优点：

1. 数组值仍是单指针瘦引用。
2. `FengArray` 对象地址可以保持不变，payload 指针可单独替换。
3. 对独占 payload 执行 `realloc` 时，只需更新 header 中的 payload 指针，不会移动托管对象头。

代价：

1. 每个非空数组需要分配 header 和 payload 两块内存。
2. 数组释放需要对应的两次回收路径。
3. 每次取得元素地址都需要先读取 payload 指针，增加一层间接访问。
4. header 与 payload 分离，内存局部性较差，allocator 元数据和碎片开销也会扩大。
5. 该方案用“所有数组都多一次分配”换取“部分动态容器扩容时可能原地增长”，不符合普通定长数组是主体的语义。

Feng 早期运行时曾采用这种分离布局，后续为减少数组创建时的分配次数和元素访问间接层而被替换。

### 2.2 胖值 + 堆 payload

概念结构：

```text
array value = [payload reference | length]

或：

array value = [payload reference | length | capacity]
```

优点：

1. 数组 length 可以直接从值中读取，无需通过对象指针读取 header。
2. 不同数组值可以对同一 payload 保存不同的区间元数据，适合直接表达切片。
3. 若 payload 独占，可以在更新胖值中指针的前提下尝试增长 payload allocation。

代价：

1. 64 位平台上，单指针数组引用通常是 8 字节；`reference + length` 至少是 16 字节，再携带 capacity 则通常是 24 字节。
2. 成本不只发生在某个容器实现内，而是扩散到每次数组赋值、传参、返回、字段存储、闭包捕获、元组和泛型 aggregate。
3. 数组值中的 payload reference 仍需要参与 ARC，胖值没有消除 retain/release，只是在复制引用的同时额外复制长度和容量。
4. 更大的值会增加 ABI 传递、寄存器占用、spill 和 aggregate 布局成本。
5. 长度或容量成为每个值的局部元数据后，同一 payload 的多个别名可拥有不同观察边界，语义会更接近切片值，不再是当前的单一固定长度数组对象。
6. Feng 普通数组长度固定，让所有数组值都重复携带 length，主要为不常用的切片或动态扩容场景服务，全局收益不足以覆盖普遍成本。

因此，Feng 没有把内建数组定义为胖值。

### 2.3 瘦引用 + 尾随内联 payload（最终选择）

概念结构：

```text
array value = [FengArray reference]

FengArray allocation:
[managed header | array metadata | alignment padding | elements...]
```

收益：

1. 数组赋值、传参和返回只需复制一个托管引用。
2. header、数组元数据和 payload 由同一次 allocation 创建。
3. payload 地址可由对象起始地址加对齐后的固定偏移计算，不需要读取第二个 payload 指针。
4. 数组 length、元素大小、元素类别和相关 descriptor 只保存一份，由数组的所有引用共享。
5. 数组终结、aggregate 元素处理和循环回收遍历继续以 `FengArray` 为统一运行时对象。
6. 该布局与普通数组“创建后长度固定”的语义直接匹配。

代价：

1. 由于 header 与 payload 位于同一 allocation，任何可能移动 allocation 的操作都会同时改变托管对象地址。
2. 动态增长不能在普通引用赋值语义下直接对 `FengArray` 使用 `realloc`。
3. 需要不同容量时，必须创建新数组对象并迁移有效元素。
4. 切片不能仅由单指针内建数组值同时表达 origin 和区间，需要独立的视图类型。

这些代价都被限定在实际需要动态容量或切片的场景，没有扩散到每个普通数组值。

## 3. 最终决策

`FengArray` 固定采用“托管瘦引用 + 对齐后尾随内联 payload”布局：

1. 语言层数组值是指向 `FengArray` 的单个强引用，不在数组值中携带 length 或 capacity。
2. `FengArray` 对象头保存 ARC、类型、长度和元素生命周期所需的元数据。
3. 元素 payload 位于同一 allocation 中的对齐后尾部，`struct FengArray` 不保存 payload 指针或柔性数组占位成员。
4. payload 起始地址必须由统一的运行时 helper 按对齐偏移计算，不在多条路径重复手写地址计算。
5. 托管数组对象地址在其生命周期内保持稳定；不通过移动已暴露引用的 allocation 来调整容量。
6. 普通数组的长度保持固定，动态容器不改变普通数组的公开语义。

已交付的布局改造过程记录在 [Feng 数组运行时优化](./feng-array-optimize-delivered.md)。该文档记录实施过程，本文则保留选择该结构的长期理由。

## 4. 切片与胖视图的分层

Feng 没有为了切片而把所有内建数组扩大为胖值，而是把区间视图下沉到 `std.collections` 中的独立 `Span<T>` 能力：

```text
普通数组：
[array reference]

区间视图：
[origin array reference | start | end]
```

该分层的考量是：

1. 不使用切片的数组仍只支付单指针引用成本。
2. 只有实际创建区间视图时，才需要携带 origin 和边界。
3. `Span<T>` 可以独立定义右开区间、边界检查、嵌套切片和 `toArray()` 等标准库行为，无需扩大内建数组语义。
4. 视图保持 origin 数组引用，由 ARC 自然延长底层数组生命周期。

当初的分层方向是由标准库 `@value` 视图类型承担胖值成本，而不是让内建数组成为胖值。当前 `std/src/collections/Span.ff` 中的 `Span<T>` 已承担上述切片职责，但现实现为普通 `open type`，尚未标注 `@value`。本记录只如实区分原设计考量与当前实现，不在此决定或安排 `Span<T>` 的后续改动。

## 5. 对动态容器的影响

尾随内联优化了所有普通数组的创建、存储和访问，但它也意味着 List 之类的动态容器不能通过普通 `realloc` 原地调整 backing array：

1. `realloc` 可能移动包含 header 和 payload 的整块 allocation。
2. 旧数组引用仍保留旧地址，普通赋值路径随后 release 旧引用时会访问野指针。
3. `refcount == 1` 只能排除其他别名，不能消除调用方槽位在赋值完成前仍持有旧地址的问题。
4. 若要支持 `realloc`，必须引入“从调用方槽位取出并消费旧引用”的 contract 或编译器特殊发码，会扩大语义和实现复杂度。

因此，动态容器使用数组作为 backing storage 时，容量变化应通过“创建新数组 + 批量迁移有效槽位 + 释放旧数组”完成。迁移保留元素时不应产生不必要的元素级 ARC 增减。

这是局部取舍：

- 所有普通数组都获得“瘦引用 + 一次分配”的稳定收益。
- 只有实际需要不同容量的动态容器，才支付新 allocation 和批量迁移成本。
- 配合几何容量增长，迁移次数为对数级；批量槽位迁移也比逐元素 retain/release 更符合 Feng 的 ARC 性能目标。

具体的内部 capacity 模型和 storage runtime contract 由 [Feng 数组容器存储 API 开发方案](./feng-array-storage-dev.md) 单独设计。该方案尚未交付；本记录不把拟议中的 capacity 字段或 storage API 描述为已实现现状。

## 6. 为什么不为 List 反转普通数组决策

`List<T>` 是通用标准库容器，不只服务于 TUI。但 List 的动态增长仍不应反向改变所有内建数组的布局：

1. 将 `FengArray` 恢复为独立 payload 会让所有非空数组恢复两次分配。
2. 将内建数组改为胖值会扩大所有数组传递和存储成本。
3. List 使用几何增长时，扩容只发生对数次，适合通过私有 storage API 实现安全的批量迁移。
4. 普通数组布局是全局基础成本，List 扩容是局部且低频的容器行为，不应用前者持续补贴后者。

因此，List 的后续优化应延续当前 `FengArray` 布局，而不是重新引入第二套数组底层存储模型。

## 7. 决策边界

本记录固定的是结构选择及其考量，不固定具体 C 字段顺序、容量增长系数、List 缩容策略或 storage API 签名。这些内容仍由各自的主规范或开发方案决定。

只有当未来出现以下级别的新证据时，才值得重新评估这一布局选择：

1. 实测证明数组创建的一次分配收益已不再重要，而动态增长成为全局主要瓶颈。
2. Feng 整体引用或 ABI 模型改变，使胖值数组不再扩大普遍复制与 ARC 成本。
3. 运行时引入能够安全更新所有引用的移动对象机制，或语言引入明确且通用的 consuming/take 语义。
4. 新方案能同时证明对普通数组、切片和动态容器的整体收益，而不是只优化某一个局部场景。

在没有上述新证据前，“瘦引用 + 尾随内联 payload”是 `FengArray` 的已确定运行时结构方向。
