Core pillars

官网先回答的，不是“语法像谁”，而是“边界怎么定”。

强类型 / 静态类型

所有类型在编译期确定，类型转换必须显式写出，没有 any 逃生口。

spec / fit 显式契约

契约形状与满足关系都用显式语法表达，不依赖隐式结构匹配。

C 互操作边界清晰

通过 @fixed、extern fn 与调用约定注解建立 ABI 兼容层，不把异常和托管对象随意穿透过去。

.fb 二进制分发

统一包格式承载公开 .ft 与正式库文件，兼顾闭源复用、编译加速和跨语言使用。

项目工作流分层

编译器只关心源文件与 .fb，feng build / check / pack 负责清单、依赖与项目组织。

Workflow

当前仓库里一条最短的试跑路径。

01

构建 CLI

Makefile 当前会生成 build/bin/feng，可直接拿来试跑项目命令。

make cli
02

初始化项目

在空目录下生成 feng.fm 和 starter 源文件。

mkdir -p demo
cd demo
../build/bin/feng init demo
03

先检查，再构建

项目级命令统一从 feng.fm 解析工作区范围。

../build/bin/feng check
../build/bin/feng build
04

运行或打包

可执行项目走 run；库项目走 pack 生成 .fb。

../build/bin/feng run
# lib 项目
../build/bin/feng pack
